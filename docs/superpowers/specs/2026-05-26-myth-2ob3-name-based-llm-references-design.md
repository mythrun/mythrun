# Name-Based LLM References (myth-2ob3) — Design Spec

> **Status:** draft, pre-implementation. Pending user sign-off.
> **Beads:** myth-2ob3
> **Related, closed:** myth-zpku (misfiled — description column already exists)

## 1. Problem

Stages that ask the LLM to copy 36-character UUIDs back from a worldDump produce two visible failure modes:

1. **Hallucinated UUIDs.** Observed 2026-05-25: 52 `fix_relationship` patches dropped across 4 worlds in a single day for `unknown relationshipId`. The model echoes the correct UUID prefix (UUIDv7's millisecond bucket) and invents the suffix. Apply step (correctly) refuses, dropping the patch silently. Net effect: coherence pass shipped zero relationship corrections for those worlds. Stage 4 (entity_relationships) hallucinates at a much lower baseline rate (~1%) — but the failure shape is identical.

2. **Self-refuting structured fields.** Even when UUIDs resolve correctly, the LLM frequently writes a structured `(source, type, target)` triple whose `description` field explicitly contradicts it. Observed examples from two production worlds:

   - `Pell Orvast leads The Gate-Wardens' Brotherhood` — description: *"not a leader of the Gate-Wardens' Brotherhood — his facts and prose describe him as an Anchorage resident with no Brotherhood connection."*
   - `Master Solven Drest allied_with The Compact Shadow` — description: *"making personal Shadow ties inconsistent with her established character."*
   - `Sister Almene located_in The Salt-Pillar Shrine` — description: *"she is found seated at the great astrolabe there, not at the Salt-Pillar Shrine."*

   The model has the correct knowledge; it states the correction in the description; it commits the wrong structure anyway. This is exacerbated by the 16-verb closed enum forcing nuanced relationships ("courted-by but resisting," "former apprentice," "professional counterparty") into the nearest fit.

## 2. Architectural decisions

### 2.1 LLM I/O uses names, not UUIDs

Every LLM-emitted reference to an entity or relationship becomes a NAME (for entities) or a NAMED-TRIPLE (for relationships: `source_name + target_name + type`). The model never sees nor writes a UUID. A deterministic post-processor resolves names → UUIDs before persistence.

**Why:** Names are short, semantic, and were just generated by the model in earlier stages. They're trivial to echo back correctly. UUIDs aren't. This is the same trick the streaming-extractor already uses with synthKeys.

### 2.2 The `relationship_type` closed enum is dropped

`relationship_type` becomes free-text. The 16-verb `RELATIONSHIP_TYPES` array is removed. The model emits whatever verb fits.

**Why:** Three things drove this:

- The closed enum's "closest fit or skip" prompt directive systematically produces misclassification (`allied_with` for "courted-by-but-resisting"; `member_of` for "mentored-by-someone-from").
- The graph's consumers (Slow Thinker, Scribe, Session-Runtime) are all LLM-driven. They read prose; they don't run mechanical `SELECT WHERE type='X'` queries.
- The architectural alignment with ZFC: pre-categorizing relationship semantics into a small enum is exactly the "framework cognition" the project's principles say to delegate to AI.

`relationship_type` stays as a column (it's window-dressing for graph views + a compact one-liner for context-budget-constrained ST renderings), but its values come straight from the LLM with no validation.

**Verb-shape guidance lives in the prompt, not the schema.** The prompt rewrite (§7.1, §7.2) instructs the model to emit "a short verb or verb-phrase predicate — typically 1-3 words, snake_case preferred, ≤30 characters. Examples: `allied_with`, `pursues`, `former_servant_of`, `courted_by`, `professional_counterparty_of`." The Zod schema bounds (`min(2).max(60)`) are a safety floor, not the contract. This keeps the column compact enough for ST renderings and stable enough for coherence-pass `current_type` echoing, without re-introducing a closed enum.

### 2.3 UUIDs stay as the canonical storage identifier

The `entities.id`, `relationships.id`, and `facts.id` UUID columns are unchanged. Renames, conquests, narrative events, and coherence-pass corrections all pivot around UUIDs. The frontend tracks entities by UUID (post-finalize) or synthKey (pre-finalize). UUIDs are immortal; names are mutable.

### 2.4 SynthKeys are unchanged

SynthKeys remain the ephemeral streaming identifier for entities and edges that exist in the LLM's emitted JSON but haven't been INSERTed yet. The LLM doesn't see them. The server emits them on `entity-added` / `edge-added` SSE events; the frontend tracks pre-finalize entities by synthKey; `finalized` events rebind synthKey → UUID at commit time.

**Why this doesn't change:** The streaming-buffering pattern is orthogonal to the names-vs-UUIDs question. The LLM doesn't need to participate in synth-key identification at all.

### 2.5 Coherence-pass renames are handled via existing mechanisms

When coherence-pass emits a `rename_entity_by_name` patch:

1. Server resolves `old_name` → UUID.
2. `UPDATE entities SET name='new_name' WHERE id=...`.
3. SSE event: `entity-updated` keyed on UUID (post-finalize) or synthKey (pre-finalize), with `patch: {name: 'new_name'}`. Frontend updates its label.
4. Stale prose in other entities that references the old name is fixed by coherence-pass's existing `fix_prose_by_name` patches (the prompt already lists "stale prose referencing renamed entities" as a target).
5. If a future Scribe call reads stale prose and tries to resolve the old name, the resolver drops it with a warning. The Scribe's next turn gets the world rendered with current names; self-corrects.

## 3. Schema changes

### 3.1 `relationships` table

No DB schema change. `relationship_type` is already a `text` column with no PG-level enum constraint. The closed-enum constraint exists only in `backend/src/llm/schemas/entity-relationships.ts` and gets dropped.

### 3.2 Zod schemas — entity_relationships (stage 4)

**Before** (`backend/src/llm/schemas/entity-relationships.ts`):

```ts
export const relationshipItemSchema = z.object({
  from: endpointSchema,          // z.union([z.uuid(), placeholderIdSchema])
  to: endpointSchema,
  relationship: z.enum(RELATIONSHIP_TYPES),
  description: z.string().min(10).max(600),
})
```

**After:**

```ts
export const relationshipItemSchema = z.object({
  from_name: z.string().min(1).max(200),
  to_name: z.string().min(1).max(200),
  relationship: z.string().min(2).max(60),    // free text; no enum
  description: z.string().min(10).max(600),
})
```

Same change to `hierarchyStragglerItemSchema` (parent/child by name). `declarationItemSchema` already uses names — unchanged except the placeholder-ID mechanism may drop (see §3.4).

### 3.3 Zod schemas — coherence_pass

**Before** (`backend/src/llm/schemas/coherence-output.ts`):

```ts
const fixRelationshipPatch = z.object({
  kind: z.literal('fix_relationship'),
  relationshipId: z.uuid(),
  newType: z.string().min(2).max(60).optional(),
  newDescription: z.string().min(10).max(600).optional(),
  rationale: z.string().min(20).max(400),
})
```

**After:**

```ts
const fixRelationshipPatch = z.object({
  kind: z.literal('fix_relationship'),
  source_name: z.string().min(1).max(200),
  target_name: z.string().min(1).max(200),
  current_type: z.string().min(2).max(60),     // disambiguates when multiple rels exist between same pair
  newType: z.string().min(2).max(60).optional(),
  newDescription: z.string().min(10).max(600).optional(),
  rationale: z.string().min(20).max(400),
})
```

Analogous rewrites:

- `fixFactPatch`: `factId` → `entity_name + fact_topic`
- `fixProsePatch`: `entityId` → `entity_name`
- `renameEntityPatch`: `entityId` → `old_name` (+ `new_name`)
- `deleteRelationshipPatch`: `relationshipId` → `source_name + target_name + current_type`

### 3.4 Phantom entity declarations (stage 4 only)

Today: stage 4 declares missing entities with placeholder IDs (`new-001`) and references them in relationships' from/to fields. The phantom-declaration entries persist into `worlds.entity_consolidation_pending` for stage 4b to materialize.

**Decision: LLM-side declarations are name-keyed; SERVER mints synthetic `new-NNN` IDs internally for the SSE wire and the pending-JSONB.**

```ts
export const declarationItemSchema = z.object({
  name: z.string().min(1).max(200),
  entity_type: z.enum(['faction', 'location', 'npc']),
})
```

The LLM emits declarations by name only. The server-side resolution context, on first sight of each declaration, mints a `new-NNN` synthetic ID and binds it to the declared name. This synthetic ID is what flows over the SSE wire (preserves the frontend's existing `new-` prefix discrimination per §5) and what gets written to `worlds.entity_consolidation_pending`. Stage 4b reads the same JSONB shape it does today — `{ placeholderId: 'new-NNN', name, entityType }` for declarations and `{ from: 'new-NNN' | UUID, to: 'new-NNN' | UUID, relationship, description }` for deferred relationships. **No JSONB shape change.**

Resolution precedence (per §4): inventory match wins over declaration match. If the model declares a phantom with a name that matches an existing inventory entity, the declaration is dropped with WARN and the relationship resolves to the inventory entity.

Edge case: the model emits two relationships referencing "The Whisper Council" intending the same future entity. The resolver groups by name automatically — same name = same synthetic ID = same future entity. (This is stricter than today's mechanism, which required the model to explicitly reuse `new-001`.)

Edge case: the model emits a relationship referencing a name that's NOT in the inventory AND NOT in `new_entity_declarations`. Today these are dropped silently (orphan placeholder). Same behavior: drop with a structured warning.

## 4. The name-resolution layer

New module: `backend/src/llm/prep/name-resolution.ts`. Exports pure-functional resolvers used by both stage 4 and coherence pass.

```ts
export interface NameResolutionContext {
  // Nested Maps avoid key-string collisions from name/topic content
  // containing the delimiter character.
  entityIdByName: Map<string, string>                  // name -> entityId
  factIdByPair: Map<string, Map<string, string[]>>     // entityName -> (topic -> [factId, ...])
  relIdByTriple: Map<string, Map<string, Map<string, string[]>>>
                                                       // srcName -> tgtName -> type -> [relId, ...]
}

export function buildResolutionContext(inv: WorldInventory): NameResolutionContext

// All resolver outputs use a tagged-union to make every partial-resolve
// outcome explicit; downstream callers `switch` on `kind`.
export type RelationshipResolution =
  | { kind: 'resolved'; sourceEntityId: string; targetEntityId: string; relationshipType: string; description: string }
  | { kind: 'phantom_target'; sourceEntityId: string; phantomName: string; ... }
  | { kind: 'phantom_source'; phantomName: string; targetEntityId: string; ... }
  | { kind: 'phantom_both'; sourceName: string; targetName: string; ... }
  | { kind: 'dropped'; reason: 'unknown_source' | 'unknown_target' | 'unknown_both' | 'ambiguous_source' | 'ambiguous_target' }

export function resolveRelationship(
  ctx: NameResolutionContext,
  emitted: { from_name: string; to_name: string; relationship: string; description: string },
  declarations: ReadonlyMap<string, { name: string; entityType: string }>,
): RelationshipResolution
```

Resolution rules (in order of application):

1. **Normalize names at lookup time** — trim leading/trailing whitespace, collapse internal whitespace runs, NFC-normalize Unicode. The inventory's keys are normalized when the context is built; lookups normalize the emitted name the same way before hashing. This is **hygiene**, not fuzzy matching — there's no string-distance computation, no token comparison, no case adjustment.

2. **Case-sensitive exact match only after normalization.** "The drowned quarter" still does NOT match "The Drowned Quarter." Case discipline is on the model; we don't paper over case drift.

3. **Lookup precedence: inventory before declarations.** Resolver checks `entityIdByName` first; if no match, checks `declarations` map. If a phantom declaration's name collides with an existing inventory entity, **the declaration is dropped with WARN** and the relationship resolves against the inventory entity (the LLM almost certainly meant the existing one).

4. **Ambiguity = drop, not pick-older.** If a name has multiple matches in the inventory (duplicate names within a world — currently zero in practice, but theoretically allowed), the resolver returns `kind: 'dropped'` with `reason: 'ambiguous_source'` or `'ambiguous_target'`. Never silently pick. Same for fact resolution: multiple facts under the same `(entity, topic)` → drop. Same for relationship-triple resolution: multiple relationships with the same `(source, target, type)` → drop. The fail-safe direction is "do nothing" not "pick arbitrarily."

5. **Drop reasons are logged as structured WARNs**, mirroring today's `unknown_entity_uuid` drop pattern. Logs include the LLM-emitted name verbatim so an operator can spot consistent typos in prompt-engineering pass.

### 4.1 Coherence-pass rename batch ordering

Coherence-pass patches can rename entities. The resolver context is built ONCE at the start of the pass (from a single inventory snapshot). To prevent in-batch references to renamed entities from dropping:

- **`rename_entity_by_name` patches apply LAST**, after all other patches have resolved against the pre-rename context.
- Within the rename batch, patches apply in the order the LLM emitted them; conflicts (rename A→B then rename A→C) drop the second with WARN.
- The prompt explicitly instructs the LLM: *"Within a single coherence pass, reference every entity by its CURRENT name throughout. If you rename an entity, use the old name in any other patches referring to it."* This makes the implicit ordering rule explicit to the model.

Renames that propagate stale prose into the prose kernels of OTHER entities are coherence's job to fix via `fix_prose_by_name` patches; the prompt enumerates this. Renames that propagate into the Scribe's future turns are a known degradation surface (the next-turn world render uses current names; the Scribe's prose-reading sees the current names; only references to the OLD name in prose that wasn't fixed will drop). The Scribe self-corrects over time because each turn re-renders the world fresh.

## 5. Streaming-extractor impact

The streaming-extractor (`backend/src/llm/prep/streaming-extractor.ts`) emits `entity-added` and `edge-added` SSE events mid-stream as the LLM's JSON parses. Today these events carry `from` and `to` as UUIDs (when the model emits them) or as `new-NNN` placeholders.

**The SSE wire format keeps `new-NNN` synthetic placeholder IDs for not-yet-finalized entities.** The LLM emits names; the SERVER mints a `new-NNN` synthetic ID for each declared phantom and emits that on the wire. The frontend's existing prefix-based lexical discrimination (`v.startsWith('new-')` at `dev-tool/src/shell/drawer/drawer.ts:34-39`) keeps working unchanged. The change is server-internal: names are the LLM's identifier; UUIDs are the storage identifier; `new-NNN` is the streaming-buffer identifier for the gap between them. **The LLM never appears in the SSE wire format.**

**Resolution flow for `edge-added`:**

1. Stage 4's wrapper builds a `NameResolutionContext` from the entity inventory before the LLM call begins. It also maintains a `pendingDeclarations: Map<string, { synthId: string; entityType: string }>` populated as the LLM emits items into `new_entity_declarations`.
2. The streaming-extractor's emit gate fires when a relationship's entry is "closed" (current behavior at `streaming-extractor.ts:117-138`). At that point both `from_name` and `to_name` are present.
3. The extractor calls the resolution context to map each name to one of: real UUID (inventory match), `new-NNN` synthetic ID (declaration match — minted server-side when the declaration first appeared), or drop (no match anywhere).
4. If both endpoints resolve, publish `edge-added` with the resolved values in `from`/`to` (UUIDs or `new-NNN`).
5. If either endpoint fails to resolve, **do not publish the mid-stream event**. The post-stream persist pass will retry resolution against the final `new_entity_declarations` array; rows that still don't resolve are dropped with WARN.

**The `StreamingExtractorConfig` interface gains two optional fields**: `nameResolutionCtx?: NameResolutionContext` and `pendingDeclarations?: Map<string, { synthId: string; entityType: string }>`. Stages 2 and 3 don't pass them; stage 4 does. The extractor's publish path is conditional: if the context is present, run resolution; otherwise emit the LLM's raw identifier (today's behavior). This keeps stages 2/3 unchanged.

**JSON-key-ordering hazard.** The LLM's structured output may emit `relationships` before `new_entity_declarations`. The mid-stream resolver sees no declarations when relationship N closes; the phantom-target edge fails resolution and the mid-stream event is suppressed. **The post-stream persist pass catches it correctly** — at that point both arrays are fully parsed and resolution succeeds. The cost is wire-log latency: a phantom edge appears at persist time, not at stream time. That's a UX regression in the dev-tool drawer but not a correctness break. To mitigate, the prompt rewrite (§7.1) orders `new_entity_declarations` BEFORE `relationships` in the requested output shape — most current models honor field-order guidance in structured-output prompts and emit accordingly. This is a soft guarantee, hence the persist-time fallback.

### 5.1 World-dump renderer behavior under the new design

`renderWorldDump` (`backend/src/llm/prep/world-dump.ts`) currently emits UUIDs prominently as entity/fact/relationship section headers:

```
## Entity 019e6131-... (faction) [access_level: known]: Mother Ehren Salt-Tongue
### Facts
- Fact 019e6120-... [role, known]: Elder of the Salt-Bleach Circle...
### Relationships (outgoing)
- Relationship 019e6131-... → target 019e6131-... [leads]: Mother Ehren serves as the primary voice...
```

**Decision: the renderer is unchanged for this spec.** The UUIDs in the dump are not load-bearing for the LLM under the new design — the model is constrained by the Zod schema to emit `from_name`/`to_name` strings, not UUIDs. Empirical validation: the 3-trial × 3-variant coherence-pass experiment (logged at `/tmp/coherence-exp-*.json`) ran against this exact renderer with V3 (names-based output) and produced 100% valid identifiers across all 9 trials. The model writes names even when UUIDs are visually present.

Keeping the renderer as-is has two benefits: (a) shared with the character-integration worker per the comment at `world-dump.ts:7-9`, so changing it would require coordinating across consumers; (b) the UUIDs in the dump serve as auditable provenance for an operator inspecting prompts — they confirm which exact DB rows were rendered.

## 6. Apply-step changes

### 6.1 Stage 4 (`entity-relationships.ts:persist*`)

Current flow: read validated tree → INSERT relationships with from/to UUIDs (model-emitted) → handle phantoms via `worlds.entity_consolidation_pending` jsonb → emit finalized events.

New flow: read validated tree → resolve every from/to name → if both resolve to current entities, INSERT relationship → if either is a phantom-declaration, defer to consolidation pending → if neither matches, drop with warn. Otherwise unchanged.

### 6.2 Coherence pass (`coherence-pass.ts:applyPatch`)

Current `applyPatch` dispatches by `kind` and looks up by UUID. New dispatch: same five `kind`s, but each resolves its name-based identifiers via the resolution context before applying. Existing apply logic (delete + recreate for fix_relationship to maintain synth-key invariants) is unchanged.

## 7. Prompt rewrites

### 7.1 `backend/src/llm/prompts/prep/entity-relationships.txt`

Drop the "## Entity Inventory" section's "you MUST reference entities by their UUID exactly as listed" framing. Replace with "you reference entities by their **name** as listed above — exact case-sensitive match." Drop the closed-enum verb list. Drop the worked example using `new-001` placeholder IDs (or rebrand to use the declared name directly).

Add **verb-shape guidance** (per §2.2): "The `relationship` field is a short verb or verb-phrase predicate — typically 1-3 words, snake_case preferred, ≤30 characters. Example values: `allied_with`, `pursues`, `former_servant_of`, `courted_by`, `professional_counterparty_of`, `mentors`. Do not write a sentence here; the texture goes in `description`."

**Order the output schema fields so `new_entity_declarations` appears BEFORE `relationships`** (§5's JSON-key-ordering mitigation). The structured-output JSON shape the model sees should list declarations first; relationships second. This lets mid-stream resolution find phantom declarations by the time a relationship references them.

The "Guidance" section that exists in the current prompt about how to think about relationships stays — the change is purely about identifier format, verb vocabulary, and field ordering, not about what relationships to identify.

### 7.2 `backend/src/llm/prompts/prep/coherence-pass.txt`

Drop the "Each entity is listed by its real UUID... do not abbreviate, do not paraphrase" framing. Replace with "you reference entities, facts, and relationships by their **name** (entity names, fact topics, relationship endpoints + current type) as listed in the world dump."

Add the **same verb-shape guidance** as §7.1 for the `newType` field in `fix_relationship` patches.

Add the **rename ordering instruction** (per §4.1): "Within a single coherence pass, reference every entity by its CURRENT name (as shown in the world dump) throughout all patches. If you emit a `rename_entity_by_name` patch, continue referencing that entity by its OLD name in any subsequent patches in the same response — the system applies renames last so other patches resolve against the pre-rename world."

Add a **stale-prose reminder**: "When you rename an entity, audit other entities' prose for references to the old name and emit `fix_prose_by_name` patches for each one. Renames without prose-fix patches leave the world incoherent."

The "What you are looking for" section is unchanged. The patch-kinds list is unchanged in spirit but renamed to `*_by_name` variants per §3.3.

## 8. Migration of existing worlds

No data migration needed. Existing worlds have `relationship_type` values that happen to be one of the 16 enum verbs; after the schema change those values stay as-is (they're just text now). New worlds will have free-text values that may include the old verbs plus anything else the model wants to write.

The prep pipeline's idempotence-on-replay invariant is preserved.

## 9. Testing

### 9.1 Unit tests

- `name-resolution.test.ts` (new): exact-match resolution, collision behavior, drop semantics, phantom handling.
- `entity-relationships.test.ts` (existing, updated): the streaming-extractor + persister test cases run against the new schema; existing relationship-validation tests get name-based fixtures.
- `coherence-pass.test.ts` (existing, updated): apply-step tests now exercise name-based patches against the resolver.

### 9.2 Integration / end-to-end

The existing `world-gen-processor` integration test runs a mocked stage chain. We update its fixtures to emit names not UUIDs.

### 9.3 Live smoke

Per CLAUDE.md's dev-tool E2E discipline + the `myth-2ob3` bead: run one real-LLM world-gen end-to-end against the new code. Success criteria:

- **Coherence-pass apply rate: ≥80%** of emitted patches successfully resolve (today's production rate: 0% applied for `fix_relationship`, the dominant patch kind). Measured: patches emitted by the LLM vs patches successfully applied to the DB.
- **Stage 4 apply rate: ≥98%** (today's baseline is ~99% — the change should not regress this).
- **Zero `unknown_entity_uuid` or `unknown_relationshipId` warnings.** Those classes of drop should not exist post-change. Drops should only fire for `unknown_name` / `unknown_triple` / `ambiguous_*`, and those rates should be low.
- **No silent state corruption.** Inspect a sample of post-coherence relationships and confirm every emitted patch's intent is reflected in the DB (rename actually renamed, relationship-type-fix actually changed type, etc.).

If the apply rate falls below the targets, prompt-engineer the verb shape + name-discipline instructions and re-run. The 3-trial × 3-variant experimental data already in hand (`/tmp/coherence-exp-*.json`) is the pre-change baseline.

## 10.1 Known degradation surfaces

Documented for awareness; not blocking.

- **Mid-stream phantom edges land at persist time, not at stream time.** When the LLM emits `relationships` before `new_entity_declarations` in a single response, phantom-target edges fail mid-stream resolution and the SSE wire log shows them only after the stream completes. The prompt's field-ordering directive (§7.1) mitigates this for compliant models. The dev-tool drawer's wire-log latency is the only user-visible cost.
- **Coherence-pass renames + stale Scribe references.** If a future Scribe turn reads prose that references the old name (because coherence-pass didn't fix every prose kernel referencing the renamed entity), the resolver drops the reference with WARN. Each subsequent turn re-renders the world with current names, so the Scribe self-corrects over multiple turns — but isolated facts may be lost. This is a known cost of name-as-LLM-identifier; UUIDs would not have this property. Accepted because it's rare and recoverable.
- **Free-text verb variance across worlds.** Without the closed enum, two worlds generated weeks apart may use slightly different verb vocabularies for similar relationships (`allied_with` vs `aligned_with`). Within a single world the prompt's verb-shape guidance + the model's local context keep usage consistent. Cross-world aggregation queries become harder; we don't run any today.

## 11. Non-goals

- **Fuzzy / typo-tolerant name matching.** Exact match only. If the model typos a name, drop with warning.
- **Replacing UUIDs throughout.** Internal storage stays UUIDs. The change is wire-format-with-LLM only.
- **Adding new patch kinds to coherence pass.** The five existing kinds get renamed/rescoped; no new ones added.
- **Auditing/expanding the relationship vocabulary.** The closed enum is dropped; free text is what the model emits. We don't curate a recommended-but-not-required vocabulary list.
- **Reciprocity / inversion invariants.** No automated `A allied_with B → B allied_with A` insertion. The model emits the edges it sees in the prose.
- **DB UNIQUE constraint on `(world_id, name)`.** Defer — adds complication for future legitimate cases (two NPCs sharing a first name).
