## 1. Goal

Replace the stubbed FastThinker with the real player-facing prose tier: a **Sonnet** model driving an **interleaved agentic tool loop** (text → tool call → resolve → feed the result back as a constraint → continue), under **enforced ignorance**, streaming prose to clients and resolving mechanical truth through tools. Ship the loop framework + an extensible tool registry + the two prototype-validated tools (`roll_dice`, `roll_skill_check`).

**Done when:** a triggered turn streams FT prose; the FT can call `roll_skill_check` (a pre-generated DC table → deterministic roll → matched outcome injected as a constraint that the FT narrates around) and `roll_dice`; the per-turn tool-iteration cap holds; the FT never sees plot secrets and never generates a random number.

## 2. The core model: SDK-driven interleaved tool loop

A DM turn's FastThinker pass is a **multi-step generation** conducted by the Vercel AI SDK's tool loop (`ai@6`), on **Sonnet**:

```ts
streamText({
  model: SONNET,                              // wrapped with logAndNormalizeMiddleware
  system,                                     // multiplayer ft-system.txt (public-tier)
  messages,                                   // ftHistory (multi-part) + character-attributed trigger batch + ST direction
  tools,                                      // the registry: roll_dice, roll_skill_check (extensible)
  stopWhen: stepCountIs(FT_MAX_TOOL_STEPS),   // hard per-turn cap (§3.6)
  prepareStep,                                // final step → injected prose-close instruction (§3.6)
  abortSignal,                                // per-turn timeout (§6)
  providerOptions,                            // anthropic.cacheControl + mythrun log bindings
})
```

The SDK feeds each tool result back to the model and continues until it stops (no more tool calls) or the cap fires. **Constraint-injection (§17.2):** each tool returns the authoritative mechanical/factual truth; the FT writes prose *informed by* it but never *decides* the outcome — a failed check → the FT narrates *how* it fails. That discipline lives in the FT system prompt + the tool-result shape, not in code.

**Why the SDK loop (not a hand-rolled one):** verified against `ai@6.0.176` — `streamText` + `tool()` + `stopWhen: stepCountIs` + `prepareStep` (per-step `system`/`messages`/`activeTools`) + the typed `fullStream` (text-delta / tool-call / tool-result / **error** / **abort** parts) + per-message `cacheControl` (§3.9) + the native `timeout` config cover **every** requirement, including the cap's graceful final-prose pass (via an injected instruction, NOT `toolChoice:'none'` — §3.6). Round 2 of blind review (§13) corrected four SDK-mechanics claims by reading the installed dist — the load-bearing semantics (error/abort surface as in-band parts, not throws; `toolChoice:'none'` strips tools on Anthropic; tools execute at pipeline pace, not consume pace; cache breakpoints are per-message) are now stated as the dist actually behaves. The SDK calls the model's `doStream` once per step; our `logAndNormalizeMiddleware` wraps each call independently (own `terminated` flag, each step terminating with a `finish` part of `finishReason` `tool-calls`/`stop`), so per-step cost logging + the `mythrun` context bindings flow on every step (verified in `middleware.ts`; re-asserted in the smoke, §10). Re-implementing the loop is strictly more bug surface for no capability gain.

## 3. Components

### 3.1 `streamTextWithTools` — new `ai.ts` wrapper

The wrapper the FT calls. `ai.ts` has `generateObject`/`streamObject`/`generateText` but **no streaming-with-tools** surface — this is the net-new primitive.

```ts
// src/llm/ai.ts (new export)
export interface StreamTextWithToolsOpts {
  readonly model: LanguageModel
  readonly system: string
  readonly messages: ModelMessage[]
  readonly tools: ToolSet
  readonly stopWhen: StopCondition            // stepCountIs(N)
  readonly prepareStep?: PrepareStepFunction
  readonly callSite: string
  readonly timeoutMs?: number                 // per-TURN budget → SDK-native timeout.totalMs (§6)
  readonly providerOptions?: unknown          // mythrun log bindings ONLY — cache_control rides per-MESSAGE providerOptions (§3.9)
  readonly maxOutputTokens?: number
}
export interface StreamTextWithToolsResult {
  readonly fullStream: AsyncIterable<TextStreamPart<ToolSet>>
  readonly response: Promise<{ messages: ModelMessage[] }>   // the multi-part turn
  readonly stepUsage: Promise<LanguageModelUsage>            // FINAL step only → the §3.11 context-fill signal
  readonly totalUsage: Promise<LanguageModelUsage>           // cumulative across all steps → spend attribution
}
export function streamTextWithTools(opts: StreamTextWithToolsOpts): StreamTextWithToolsResult
```

- **NO output-repair chain** (it's prose, not structured output — repair is `generateObject`'s concern). **Malformed tool-call inputs** are a distinct concern: a strict Zod `inputSchema` rejection surfaces as a `tool-error` part the model recovers from on its next step (the SDK default). We do **not** wire `experimental_repairToolCall` in MYT-68 — the model's own re-call is sufficient for two simple tools; revisit if the smoke shows repeated malformed calls.
- **Timeout = the SDK's native `timeout: { totalMs, chunkMs }`** (verified to exist in ai@6): `totalMs` is the per-turn budget; `chunkMs` covers the myth-4omh silent-stall hazard better than one whole-turn signal. **The timeout does NOT throw** — it surfaces as an in-band `abort` part + graceful stream close (verified in dist); the consume loop owns converting it to `LlmTimeoutError` (§3.2 step 5, §5). An abort *after* any frame has been broadcast is terminal, not silently retried (§5).
- **`usage` vs `totalUsage` are different numbers** (verified): the SDK's `result.usage` is final-step-only; cumulative spend is `result.totalUsage`. The wrapper exposes both, explicitly named — context-fill (§3.11) wants the final step's `inputTokens`; billing wants the total. A 5-step turn billed off `usage` under-counts ~4 Sonnet passes.
- **Guarded promises:** if the turn fails/aborts before ANY step completes, everything derived from the final step (`response`, both usages) **rejects** (verified) — the wrapper pre-attaches handlers so a consumer throwing out of the `for await` doesn't leave an unhandled rejection to kill the worker. Conversely, a `response` that resolves after a mid-turn failure carries partial data + `finishReason: 'other'` — not proof of a clean turn.
- Errors mapped via `mapToMythrunError`; the wrapped model carries `logAndNormalizeMiddleware`. **Note the SDK's internal retry layer is inert under it** (it retries only raw `APICallError.isRetryable`, which the middleware has already mapped away) — see §5's no-mid-turn-retry posture.
- `ai.ts` re-exports for consumers (the lint rule forbids direct `'ai'` imports): `tool`, `ToolSet`, `ModelMessage`, `TextStreamPart`, `stepCountIs`, `StopCondition`, `PrepareStepFunction`. `GenerateObjectOpts` additionally gains an optional external `abortSignal` (combined internally via `AbortSignal.any`) so the skill-check resolver can thread the turn's signal into its nested Haiku call (§3.5 step 3).
- Lives in `ai.ts` alongside the other call wrappers. The wrapper exposes the stream + the resolved multi-part `response.messages` + `usage`; the FT does the gating/persistence.

### 3.2 The FastThinker implementation — `src/session/tiers/fast-thinker.ts`

Implements the (widened) `FastThinker` interface. Constructor deps (injected — testable): the skill-check resolver (which itself holds the dice engine + the `repo`), the model config, the prompt loader.

`render(ctx: FtTurnContext, emit: TurnEmitter): Promise<AssistantMessage>`:
1. **Build the system prompt** — `loadPrompt('session', 'ft-system', vars)` with the var contract in §7 (multiplayer-attributed; public-tier). The `{{ft_context}}` var is the curated, enforced-ignorance-safe prep document from `session_preps.ft_context` (§3.10) — the FT's stable world/party/situation grounding.
2. **Build the messages — the FULL session transcript, never windowed.** `ctx.ftHistory` is the entire session's history (multi-part, §3.7), **reconstructed each turn from `session_messages`** (PG-direct, §3.7) by a **deterministic** rows→messages mapping — deterministic so the assembled prefix is byte-stable across turns and the prompt cache (§3.9) keeps hitting. The FT holds the **complete verbatim transcript in context every turn** (~50–200KB at the cap), like any chat app; it does **not** narrate from a compressed summary (that would invite the hallucination the full transcript prevents). Append the current trigger batch attributed by **character name** (§7) + the ST `direction` fused onto the batch (the controller already does the fusion; format reconciled in §7; ST is stubbed in MYT-68 → no direction injected). The `runningSummary` is **not** the FT's grounding and the FT never reads it — it's the ST's tool (§7). The transcript never compacts; the context cap *is* the session-length bound (§3.11); the every-turn load IS the recovery path (§3.7) — an incoherent durable transcript fails the turn loud, never degrades onto a summary.
3. **Build the tool set** — the registry (§3.3). Tools are **pure resolvers**: `execute` closes over `ctx` (the SDK supplies `{ toolCallId, abortSignal }` as its second argument — the natural abort-threading point) and returns data only. Tools NEVER emit frames — all frame emission happens in the consume loop, in stream-part order (step 5).
4. **Run the loop** — `streamTextWithTools({ model: SONNET, system, messages, tools, stopWhen: stepCountIs(FT_MAX_TOOL_STEPS), prepareStep })`.
5. **Consume `fullStream` — the SINGLE emission point, in part order:**
   - `text-delta` → `await emit.emitText(delta)`.
   - `tool-result` → `await emit.emitSkillCheck(frame)` / `emitDiceRoll(frame)`, the frame built from the result + its tool-call args. Emitting from the consume loop — NOT from inside tool `execute` — is what makes cross-process order real: the SDK executes tools at internal pipeline pace, ahead of the consumer (verified in the ai@6 dist: `runToolsTransformation` runs `execute` upstream of the consumer, and accessing `result.response`/usage triggers an eager background drain), so an execute-side publish can hit the wire *before* the prose deltas that precede the tool call in the model's output. `fullStream` interleaves tool-call/tool-result parts at their true positions, so part-order emission IS model-output order — and it also serializes the player-visible frames of parallel tool calls within one step (the SDK may execute those concurrently; emission order stays deterministic).
   - **`error` parts → `throw part.error`.** The part already carries the Mythrun-mapped error (the middleware maps it at the model layer), but `streamText` re-surfaces a model-stream failure as an in-band `error` part and closes the stream **gracefully — the `for await` itself will NOT throw** (verified in dist: the step driver catches and re-enqueues). A loop that ignores `error` parts ends "normally" and marks a truncated turn successful (§5).
   - **`abort` parts → `throw LlmTimeoutError`.** Same mechanism: when the per-turn timeout fires, `streamText` enqueues `{ type: 'abort' }` and closes gracefully — no throw, no `error` part (verified in dist). Without this arm the *designed* per-turn-budget path completes "successfully" with truncated prose persisted as canon.
   - The loop `await`s each emit before advancing the iterator (the publisher is a single connection with awaited PUBLISH, so worker-side emit order = wire order).
6. **Return** the multi-part `AssistantMessage` (built from `response.messages`) for the conductor to persist into `ftHistory`.

### 3.3 The tool registry — `src/session/tiers/ft-tools.ts`

Extensible. MYT-68 wires two tools as `tool({ description, inputSchema, execute })`; the other five (§17.2) register here when their resolvers land (MYT-70/72/75).

- **`roll_dice`** — `inputSchema: { count: z.int().min(1).max(100), sides: z enum of the standard die set {2,4,6,8,10,12,20,100} }`. `execute`: `rollDice(count, sides)` (deterministic, §3.4) → returns `{ results, total }`; the consume loop emits the `dice_roll` frame from the tool-result part (§3.2 step 5). Bounds enforced **in code** (Zod + a defensive clamp in the engine) — an unbounded `count` would stall the worker (it holds the session lock); out-of-range rejects to a `tool-error` the model narrates around. For non-skill rolls (damage, wild magic). Scope note: no modifier param — a "2d6+3" total would be LLM arithmetic in prose; acceptable for MYT-68 (authoritative damage math is MYT-75's combat engine), never treated as mechanical truth.
- **`roll_skill_check`** — `inputSchema: { character_name, skill, context, advantage?, disadvantage? }`. The resolver (§3.5). `character_name` resolves against the **session roster** (`session_participants`, a closed known set) — never a free-text DB key; see §3.5 step 1.

**Parallel tool calls within one step are allowed** (Anthropic may emit several `tool_use` blocks per assistant message; the SDK executes them concurrently). Part-order emission (§3.2 step 5) keeps the player-visible frame order deterministic, and one multi-call step is how a full-party group check ("everyone roll Perception") fits inside the §3.6 cap — five *sequential* steps could not. The §6 timeout budget counts **checks**, not steps (concurrent DC calls shorten wall time); `anthropic.disableParallelToolUse` remains available if same-step concurrency ever misbehaves. The smoke (§10) drives a multi-check group turn.

### 3.4 The dice engine — `src/session/dice/engine.ts` (ported, Principle #4)

Pure functions over `crypto.randomInt` (the LLM never generates a random number): `rollD20WithType(type)` returning the **kept** roll for advantage/disadvantage (roll twice, keep higher/lower), `rollDice(count, sides)` (with a defensive bound), `calculateModifier(score) = floor((score-10)/2)`, `proficiencyBonusByLevel(level)` (used for character *generation/validation*, **not** the live skill-check path — see §3.5 step 2). Deterministic + unit-testable (injectable RNG for tests).

### 3.5 `roll_skill_check` resolver (Principle #5) — `src/session/skill-check.ts`

The full pre-gen-DC-table flow:
1. **Resolve the roller from the session roster — `session_participants`, which carries `character_id` directly.** `character_name` is normalized (trim + case-fold) and matched **exactly** against the session's participants — a closed set, so this is structural validation (ZFC-exempt); **no fuzzy matching** (that would be the local string-intelligence ZFC forbids). Resolution targets **`session_participants`** (session-scoped, `character_id NOT NULL`, maintained on every WS join via `repo.sessionParticipants.join`) — NOT a name-keyed `campaign_characters` lookup: a campaign member who never joined the session isn't rollable, and resolving to a `character_id` is ambiguity-resistant at the ID level. **Roster population is part of this issue — it does not exist today** (verified: the only `:state` writer is session start at `routes/sessions.ts:304-305`, which writes `participants: []`, and nothing updates it — as the code stands, every check would fail-soft and the headline feature would never fire). MYT-68 makes the WS join/leave path maintain `:state.participants` (character names, for the FT prompt roster §7 — covers mid-session joins by construction), and the resolver reads `session_participants` joined to `characters` per check (one indexed read, trivial next to the Haiku call). **No name match, or an ambiguous name** (two participants may share one — no schema uniqueness prevents it) → fail-soft error-constraint (§5), never a throw.
2. **Compute the modifier — read the per-skill proficiency level (DIVERGES FROM THE PROTOTYPE).** `SKILL_ABILITIES[skill]` (ported map; normalize the skill key) → ability modifier from the character's ability score. Then read `character_skills.proficiency_level` for the requested skill — **normalizing BOTH sides of the join**: `character_skills.skill_name` is itself unconstrained LLM output from the character-sheet stage (`z.string().min(2).max(40)`, no enum), so case-fold + trim both the FT's string and the stored name, and canonicalize sheet-stage writes to the 18-skill enum (a silent miss here is a wrong modifier with **no error** — the worst mechanics bug class). **Absent row → `none`** (the sheet stage only emits proficient skills; the default must be explicit). Levels: `none → +0`, `proficient → +proficiency_bonus`, `expertise → +2×proficiency_bonus`. **The prototype flattens this to a boolean (`proficient ? +PB : 0`) and has no expertise path — do NOT port that math.** Use the stored `characters.proficiency_bonus` column (authoritative); `proficiencyBonusByLevel` is for generation only. A dedicated **expertise unit test** is required (the prototype has none). Mechanical computation (ZFC-exempt). An **unknown/unmapped skill** (the FT is free-text; it will eventually emit a string outside the 18-skill map) → fail-soft error-constraint (§5), never a throw.
3. **Pre-generate the DC table** — one Haiku call: `generateObject({ model: HAIKU, schema: SkillCheckResultSchema, system: loadPrompt('session','skill-check', {…}), timeoutMs, abortSignal: <threaded from the FT turn> })` → `{ dc, outcomes: { fail, success, great_success } }` (ported template + schema). The outcomes are *narrative constraints*, not dialogue. The FT turn's abortSignal is **threaded into this nested call** so a turn abort cancels the in-flight DC call (no orphaned spend). DC-table failure (or abort) → fail-soft (§5).
4. **Roll** — `rollD20WithType(type)` where `type` resolves per 5e: `advantage && disadvantage → normal` (they cancel), else `advantage → advantage`, `disadvantage → disadvantage`, else `normal`. (The prototype lets advantage silently win when both are true — that is not RAW; fix it.) Add the modifier → `total` (deterministic). **No nat-1/nat-20 auto-fail/crit on ability checks** (RAW: crits apply only to attack rolls); the tier is purely `total` vs `dc`.
5. **Match the tier** — `total ≥ dc+5 → great_success`; `≥ dc → success`; else `fail`. The matched `outcomes[tier]` string is the **constraint**.
6. **Return** `{ character_name, skill, outcome_tier, constraint, roll, kept-roll detail, modifier, total, dc }` as the tool result — the consume loop builds + emits the `skill_check` frame from it (§3.2 step 5). The frame **carries `character_name`**: the prototype's frame shape is single-player and lacks attribution, but in multiplayer every client must see *whose* check fired — same for the persisted roll-event row. The FT narrates informed by `constraint`.

### 3.6 The cap

`FT_MAX_TOOL_STEPS = 5` (config). `stopWhen: stepCountIs(FT_MAX_TOOL_STEPS)` stops *after* N steps. **The forced prose close does NOT use `toolChoice: 'none'`** — verified against `@ai-sdk/anthropic@3.0.76`: `toolChoice:'none'` strips the `tools` param entirely, and an Anthropic request whose history contains `tool_use`/`tool_result` blocks but defines no `tools` is rejected (400) — so the cap-close as originally designed would error out on exactly the turns that hit the cap. Instead, `prepareStep` on the final step **keeps `tools` defined and injects a close instruction** (`prepareStep` may return per-step `system`/`messages` — verified): wrap up in prose, do not call tools. If the model defies the instruction and emits a tool call on the final step, the loop stops at the cap and the conductor **drops the dangling tool-call from the persisted turn** (logged) — under PG-direct the persisted rows are Mythrun-owned, so the rebuilt history stays clean (no orphan `tool_use` to 400 the *next* turn). **Precise semantics:** up to `FT_MAX_TOOL_STEPS − 1` tool-calling steps + 1 instructed prose-close step; a full-party group check fits in ONE step via parallel tool calls (§3.3). The smoke (§10) asserts the boundary — the second-to-last step may call a tool, the final step closes in prose, and a cap-hitting turn does **not** 400.

### 3.7 Seam widening (the MYT-66 H5 / H12.f points)

- **`TurnEmit` → `TurnEmitter`** — widen the frame-agnostic emit from `(text) => Promise<void>` to a small object: `{ emitText(text), emitSkillCheck(frame), emitDiceRoll(frame) }`, each returning `Promise<void>`. The conductor binds it via the turn-publisher (§3.8).
- **`ConversationMessage.content` → multi-part, with a Mythrun-owned versioned shape.** Widen from `string` to a multi-part content (text + tool-call + tool-result blocks). **Do NOT couple the durable shape to the raw SDK `ModelMessage`**: the durable representation is the `session_messages` row schema (below); the Mythrun-owned multi-part type maps rows ↔ SDK messages at the FT boundary, so an `ai` minor bump can never make a stored transcript unparseable. (The earlier design's serialized-Redis-blob + checkpoint-version worries disappear under PG-direct — there is no serialized history blob anywhere.)
- **`FtTurnContext`: add `ftContext`, REMOVE `runningSummary`.** The type gains `readonly ftContext: string` (the FT-safe prep doc, §3.10) and **drops `runningSummary`**: the FT never reads it, and an ST-authored field sitting on the FT's context type is exactly what "secrets have nowhere to live" forbids — from MYT-69 (when the ST writes the summary with `sd_playbook` in context) the boundary would otherwise be a promise, not a type. The ST/Scribe get the summary via their own view (the existing `TurnContext = FtTurnContext & StSecrets` plan, `types.ts:57`); the controller keeps summary in Redis turn state, just not on the FT context. Public-by-construction is thereby *strengthened*: `ft_context` is FT-safe by construction; `sd_playbook` is never loaded here (ST constructor deps, MYT-69).
- **`FastThinker.render`** — `emit` becomes the `TurnEmitter`; the skill-check resolver is a constructor dep.
- **Storage model: PG-DIRECT — `session_messages` is the ONLY transcript store (revised 2026-06-09; supersedes the Redis `ft_history` hot cache).** The FT's history and the player transcript were two representations of the same artifact; MYT-68 unifies them into one. Player messages already persist to `session_messages` on receipt (MYT-65); MYT-68 appends the completed DM turn's player-facing prose + its roll events (`skill_check`/`dice_roll`) as new row kinds at turn end, in **ONE transaction** (all rows or none — a partially-appended turn in the durable transcript would brick every subsequent reconstruction under the crash-loud contract), **idempotent on `turnId`** (a `turn_id` column + uniqueness — a migration, §11), **taking seqs from the existing `:seq` INCR**: the architecture already assigns server-side monotonic seqs to ALL messages, player and DM (overview §607) — the earlier "defer the seq model" framing was wrong, and `seq INTEGER NOT NULL UNIQUE` on `session_messages` forces the decision anyway. (What still defers from §12: the client gap-detection/backfill protocol and seqs on live frames.) Reconnect replay (`listAfterSeq`) then covers DM rows with zero new machinery. Each turn, the controller **reconstructs the FT's multi-part history from `session_messages`** via one repo read — **`repo.sessionMessages.loadFtHistory(sessionId, maxPlayerSeq)`**, keyed by `sessionId` (the table is session-keyed; a campaign-keyed read would concatenate prior sessions' transcripts and silently break the §3.11 session-cap model on every campaign's *second* session; `TurnJobPayload` already carries `sessionId`) with a **single-piece predicate** (refined at plan time): `(message_type = 'player_message' AND seq ≤ maxConsumedSeq) OR message_type IN (DM row kinds)`, ORDER BY seq. Player rows are bounded at the consumed watermark — rows above `maxConsumedSeq` (mid-turn arrivals) are EXCLUDED, they're the next turn's batch — while **DM rows are ALWAYS included regardless of seq** (a DM turn's rows can carry seqs *above* an early-arriving next-batch player message when chat races the turn's end; a pure seq cutoff would silently drop the DM's own prior reply). This single load IS the whole FT context — the current batch rows are part of it, the controller no longer appends a separate batch, and the payload's `triggerMessages` serve only the classifier — so there is exactly ONE formatter by construction and the duplicate-batch / dual-formatter / cache-divergence hazards are structurally gone. The `[DM direction:]` fusion targets the last player message ≤ `maxConsumedSeq`. Rows must carry **rebuild-sufficient structure** (tool-call/result detail, not just rendered prose). Redis keeps only the SMALL hot session state it is genuinely for: `:state` (participants + `ftContext`), `:summary` (the ST's tool), `:usage`, the per-turn lock, `seq`, pub/sub. The Redis `:ft_history` key and its 5-min checkpoint are **retired**. Rationale (cache-benefit interrogation + independent Fable consult, 2026-06-09): the transcript has ~1 reader — the FT itself, next turn — so there is no fan-out for a cache to serve; the per-turn `(session_id, ordinal)` range-scan is noise against the 5–30s LLM call at launch (~1MB/s) *and* viral scale (a 10K-session working set ≈2GB fits in `shared_buffers`; append-only indexed scans are Postgres's best case); the expensive repeated "read" in this architecture is the input *tokens*, already handled by the prompt cache (§3.9). Single-store also eliminates dual-representation coherence outright. The load sits behind ONE repo function so a read-through cache is an afternoon's add if PG metrics ever demand it. `buildReconnectFrame` extends to replay DM rows too, so reconnect shows prior DM turns. **Scope kept tight:** durable + queryable transcripts (per-turn ordinal ordering), NOT the full §12 server-assigned global-sequence model — that, plus the §17.7 lookback search surface, stays a dedicated follow-up.
- **Recovery IS the load path — exercised every turn, crash loud on incoherence.** With one store there is no cache to drift and no rarely-run rebuild branch: the rows→multi-part reconstruction runs on EVERY turn, so any fidelity bug surfaces on turn 2 of the first smoke rather than at 3am in an eviction. If `session_messages` is absent/incoherent for a session that should have history, that is a persistence-layer invariant violation — a fundamentally broken system — so **fail the turn loud** (typed fatal error → `turn_error`), never degrade onto the summary. This supersedes runtime §524 (summary-as-continuity) and the architecture's "eviction loses 0–5 min" framing: the transcript is per-turn durable, so there is nothing to lose. **End-of-turn write ordering + the post-commit window:** check lock liveness (`isLockLost`) immediately **before** the PG commit — a stalled worker that lost its lock must not append rows after a successor has declared the turn dead (today's lock checks bracket only load/process/flush, `turn-worker.ts:133-137`). Then the **PG append commits** (the turn is durable once it commits), then the Redis MULTI for summary/usage + the responded-watermark + `turn_end`. Every failure AFTER the commit (Redis flush, watermark, BullMQ ack, worker crash) re-runs the job, and the re-run MUST **converge to completion, never `turn_error`**: DM rows for this `turnId` exist in PG → the turn happened → finish the Redis flush, advance the watermark, publish `turn_end`. (Otherwise clients are told to discard prose the transcript *keeps*, the watermark never advances, and the next trigger re-answers the same batch — a duplicate DM reply in canon.) The **emitted-anything latch** is pinned to three properties: **Redis SET-NX keyed by `turnId`** (cross-container — BullMQ retries/stalled-reclaims land on any worker; an in-memory latch only covers same-process retries), **set BEFORE the first publish** (set-after leaves a crash window that re-streams divergent prose under the same `turnId`), and **checked at job start** (a stalled-reclaimed job doesn't arrive via a failure path). Terminal arm uses BullMQ's `UnrecoverableError` (skips remaining attempts). Decision order on any re-run: PG rows exist for `turnId` → converge to `turn_end`; else latch set → terminal `turn_error`; else → safe to re-run from scratch (nothing was shown or stored).
- **Consequence — ST directions are per-turn ephemera, never transcript.** The fused `[DM direction: …]` exists only in the in-memory messages assembled for *that* turn's render; it is never written to `session_messages` (player rows persist at receipt, pre-fusion; DM rows are output only). So past directions don't accumulate in the FT's reconstructed context, and a direction can never leak into the player-visible transcript / reconnect replay — its narrative effect survives via the prose it shaped. (Under the old Redis model the fused string persisted inside `ft_history`; PG-direct makes the FT's memory *exactly* the public transcript + the current turn's direction — a strictly cleaner enforced-ignorance posture, §8.)

### 3.8 Contract frames + client-side gating

Add to `contract/session-events.ts`:
- **Server frames** `skill_check` + `dice_roll` (mirror the prototype's `SkillCheckMessageSchema` / `DiceRollSchema` shapes) → `SERVER_FRAME_TYPES` + `ServerFrame`. The SessionHub fan-out is frame-type-agnostic (confirm), so these flow to clients.
- **`roll_complete` is NOT added to the live client allowlist in MYT-68.** The existing gate is `classifyClientFrame` (a boolean allowlist tripwire), not `parseClientFrame` (the draft misnamed it). Adding `roll_complete` to `CLIENT_FRAME_TYPES` with no server handler would make the transport *accept* a frame nothing consumes — exactly what the contract file's header warns against. It is documented as a **deferred** frame (owned by the frontend roll-animation issue) and added to the allowlist only when a handler exists.

**Gating is client-side** (decided). The worker emits the `skill_check`/`dice_roll` frame **then** the dependent narration `text_delta`, in order (the §3.2 part-order emission invariant — all frames from the consume loop, never from inside `execute` — plus the publisher's single-connection awaited PUBLISH guarantee cross-process order; frames carry no seq today, so arrival order is the only ordering — hence the invariant is load-bearing). The client's gating must also degrade safely if a roll frame is lost on the lossy pub/sub channel (render the narration ungated rather than buffering forever). The frontend (later milestone) plays the dice animation and reveals the buffered narration locally.

**This is an explicit amendment to runtime §10's server-side synchronized-reveal model** (`waitingForRoll` buffers continuation deltas server-side; the first client's `roll_complete` unblocks *everyone*). Rationale: a cross-process session lock cannot be held pending a human animation ack (it would stall the worker + the queue). The accepted tradeoff: roll-animation reveal becomes **per-client**, not globally synchronized — different clients may see the outcome beat at slightly different times. The roll *result* is identical for all clients (deterministic, resolved once); only the animation timing desyncs. Consequence to document for the (deferred) frontend: `turn_end` now fires at model speed, *before* a client finishes animating — the client treats `turn_end` as "stream complete," not "turn visually done," and continues local reveal after the animation. (MYT-68 builds **no** server-side buffer + **no** cross-process ack.)

### 3.9 Prompt caching (the §17.2 cost lever)

Ephemeral `cache_control` with a **sliding breakpoint**, matching the prototype's validated approach (not static-prefix-only). **Placement (verified against the provider dist):** the Anthropic provider reads `cache_control` from per-MESSAGE / per-part `providerOptions` (and the system *message's*), **never** from the call-level `providerOptions.anthropic` — a top-level setting is silently inert: no error, just full input price on every step of every turn. So the wrapper passes the system prompt as a system-role message, and the FT attaches `{ anthropic: { cacheControl: { type: 'ephemeral' } } }` to (a) the system message + the **immutable `ft_context`** head (the prep doc never changes within a session — the ideal anchor), and (b) the **last settled message** (end of the prior turn), so each of the up-to-5 steps re-uses the cached prefix rather than re-paying full input cost on the accumulating tool-result tail. This is what makes the full-transcript-always design (§3.2) affordable at scale. Anthropic allows up to 4 breakpoints; the growing in-turn tail past the last breakpoint is uncached. Caveat: an ST intervention invalidates the prefix from the fusion point on the *following* turn (the persisted row lacks the fused direction) — one full cache re-write per intervention, bounded cost (MYT-69-era). The smoke asserts **`cacheReadInputTokens > 0` on turn ≥ 2** — caching regressions are otherwise invisible.

### 3.10 `ft_context` — the FT's curated world grounding (`session_preps.ft_context`)

The session-prep pipeline (MYT-59/61) already produces a first-class, **enforced-ignorance-safe-by-construction** prep artifact per `(campaignId, sessionNumber)`: `session_preps.ft_context` — a prose-markdown document (`## The World`, `## The Party`, `## Where You Are`, `## The Situation`, `## People You Know`, `## People You Don't Know (Yet)`, `## Factions`, `## Places of Interest`, `## Encounters & Set Pieces`, `## DM Guidance`) explicitly authored as *the* Fast-Thinker context, with secrets quarantined into the sibling `sd_playbook` field (ST-only). MYT-66's `FtTurnContext` never loaded it; MYT-68 wires it in:

- **`FtTurnContext` gains `readonly ftContext: string`** (the FT-safe doc). Public-by-construction is *preserved* — `ft_context` is the public slice by construction; `sd_playbook` is **not** loaded here (MYT-69 gives the ST its secrets via constructor deps).
- **Load once per session, cache in Redis `:state`.** `ft_context` is immutable per session (`ON CONFLICT DO NOTHING`). The cheapest correct path for 200–500 concurrent sessions: load `repo.sessionPreps.getBy(campaignId, sessionNumber)` once at session start and store `ftContext` in the `:state` blob (next to `participants`), so the per-turn hot path reads it from the already-loaded blob with no extra DB round-trip; the SessionController threads it through `buildContext()`. (Exact load hook — session-start vs. lazy-on-first-turn — is plan-time; both are acceptable.)
- **`:state` miss → re-load from PG, never degrade.** `ft_context` is durable + immutable in `session_preps`; if the `:state` blob is evicted/expired mid-session (2h TTL), the loader re-reads `repo.sessionPreps.getBy(...)` and re-caches — the FT must not silently lose its canon for the rest of a session over a Redis eviction. (Same eviction nulls `participants`; the join-path repopulation in §3.5 step 1 plus the `session_participants` read keep checks working — an eviction must never be that quiet.) Only if the prep row itself doesn't exist (prep never ran) does the FT proceed on **transcript-only grounding**, logged loudly. It does NOT fall back onto the running summary — the FT never reads it (§7); an earlier draft's parenthetical said otherwise and was a leftover leak path, deleted (round 2, Orion).
- **It's the cache anchor (§3.9)** and the FT's stable grounding — combined with the full transcript (§3.2), the FT narrates from curated canon + verbatim history, not a lossy summary.

### 3.11 Session length is bounded by the FT context — graceful wind-down, never compaction

The FT holds the **literal full transcript** every turn (§3.2). There is **no compaction, no in-session summarization, no windowing — ever.** The FT's true context window is therefore a **hard cap on session length**, and that is by design: a Mythrun "session" is the fundamental unit of play precisely because it is what fits in one context window.

- **Graceful wind-down, not a hard cutoff (runtime §14 / §546; overview §7.4).** As the running transcript approaches the FT context/token budget, the session is brought to a natural close: at ~90% of the budget the ST issues a **wind-down instruction**, the narrative reaches a stopping point, and the server broadcasts `session_end` — *"no hard cutoff mid-response."* The system never silently drops or summarizes transcript to keep going.
- **Cross-session continuity is at the seams, not mid-session.** What carries forward is the **Scribe's session-end reconciliation** (§710 — one full-context pass producing durable world state) + the **next session's `ft_context` prep** (§3.10). Continuity is *between* sessions, not via compressing *within* one.
- **MYT-68 scope.** MYT-68 holds the full transcript (no compaction) and accumulates `usage` (the budget signal — already threaded through the controller). The wind-down itself is an **ST behavior** (the ST is stubbed in MYT-68 → real wind-down is MYT-69) plus **session-end orchestration** (its own issue). MYT-68 must not contradict this model — i.e. it introduces no summarization/windowing escape hatch. If a context-budget *observability/guard* is wanted inside MYT-68 (surface the % so a human/dev can see it), that is a small add; the wind-down decision stays with the ST.

## 5. Error handling

The error model is written against how `ai@6` actually surfaces failures (a `for await` over `fullStream` does **not** throw on an in-band `error` part unless the consumer/middleware makes it):

- **In-stream provider error** — the middleware maps the model-layer error (`middleware.ts:158-162`), but `streamText` re-surfaces it as an in-band `error` part and closes the stream gracefully — **the `for await` does NOT throw** (verified in the ai@6 dist). The consume loop must `throw part.error` on every `error` part (§3.2 step 5). Same for **`abort` parts** (timeout): in-band part + graceful close — the loop throws `LlmTimeoutError`. **Never** let either part fall through and end the loop "normally" (a truncated turn marked as a successful `turn_end`, persisted as canon). The FT additionally inspects the final step's `finishReason`: `'error'` ends a stream "gracefully" at the middleware layer (logged as provider-graceful) — the FT treats a final `finishReason` of `'error'`/`'unknown'` as turn failure, not completion.
- **Per-turn timeout** — SDK-native `timeout.totalMs` (+ `chunkMs` stall guard); surfaces as the `abort` part above.
- **No retry layer remains mid-turn (accepted knowingly):** the SDK's internal retry fires only on raw `APICallError.isRetryable`, which the middleware has already mapped away — so a transient 429/529 opening step ≥2 becomes an in-band `error` part, and under terminal-after-first-frame that is a dead turn with no retry at any layer. Accepted: a divergent re-stream is worse than a rare dead turn; revisit only if launch metrics show transient-blip turn deaths at meaningful rates.
- **Retry vs. divergent re-stream (the turnId hazard).** The turn-worker rethrows non-lock-lost errors → BullMQ retries the job. The recovery invariant keeps Redis at the pre-turn snapshot, so a retry re-runs the FT from scratch — but Sonnet is non-deterministic and `roll_*` re-rolls, so a retry would re-stream **divergent prose + divergent rolls under the same `turnId`**. Decision: **a failure AFTER any frame (text/skill/dice) has been broadcast for a `turnId` is terminal** — publish `turn_error` for that turnId, do **not** silently retry a partially-streamed turn. A failure **before any frame emitted** is safe to retry (nothing was shown). The worker distinguishes the two via an "emitted-anything" latch on the turn (mirrors MYT-67's `claimTurnErrorPublish` latch pattern). The client discards partial content on `turn_error`.
- **Tool-execute throws → resolvers must be TOTAL.** An uncaught throw in a resolver becomes a `tool-error` part the SDK feeds back, and the loop **continues** — which for a skill check would let the model narrate an outcome with **no roll** (a #4/#5 violation). Therefore every resolver is `try/catch`-total and returns a **structured error constraint** ("the check could not be resolved — do not narrate a definite outcome"), and the ft-system prompt instructs the model how to handle an error constraint without inventing a result.
- **Fail-soft enumeration (the skill-check resolver never throws mid-turn):** (a) **DC-table Haiku failure or abort** → a neutral fallback `{ dc: <fixed default>, outcomes: { fail, success, great_success } }` of **tier-neutral** templates ("the attempt clearly fails / clearly succeeds / succeeds remarkably"); the deterministic roll + tier-match **still execute** against the fallback DC, so #5's "roll then match" holds. (b) **Unknown / ambiguous `character_name`** → error constraint. (c) **Unknown / unmapped `skill`** → error constraint. (d) **`roll_dice` out-of-range** → `tool-error` the model narrates around. All logged.
- **Cap hit mid-intent** → `prepareStep` already forced a prose close; no dangling tool call.
