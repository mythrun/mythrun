Schema

The Postgres shape Mythrun runs on: 31 application tables grouped into identity, worlds, campaigns, sessions, and ops; 21 named performance indexes; 3 empty SRD reference tables waiting on data load. Every primary key is a UUIDv7. The schema is enforced at the DB layer, not the app layer.

How it fits together

The schema is the union of six migration files in backend/migrations/: 001_initial_schema.sql ships every CREATE TABLE in topological FK order, 002_indexes.sql adds the named performance and uniqueness indexes, 003_srd_reference_data.sql creates the three empty SRD tables, 004_credit_ledger_invariants.sql tightens the credit_ledger with defense-in-depth CHECKs, an idempotency partial-unique index, and a CASCADE→RESTRICT swap on the user FK, 005_drop_profile_columns_users.sql reduces the users row to its minimal-claims shape and switches its UNIQUE on username to be case-insensitive, and 006_drop_billing_config_tables.sql drops the four legacy billing-config tables (subscription_tiers, session_packs, user_subscriptions, purchases) now that the tier and pack credit-allocation contract has moved into a checked-in TS file at Stripe contract. The migrations runner applies all six end-to-end on a fresh database. The diagram clusters tables by the story they tell — read it left to right.

Identity and billing

users is the gravitational center of the identity cluster. The row carries six product-load-bearing fields: cognito_sub (the external Cognito identity, UNIQUE), username (player-chosen handle, UNIQUE on LOWER(username)), display_name (the social-recognition surface in member lists and chrome), stripe_customer_id, free_trial_used, and suspended_at. Subscription state itself lives in Stripe — Mythrun's view of "what tier is this user on" comes from a per-user Stripe API read at session-start, not from a local mirror table. Migration 006 dropped the four legacy billing-config tables (subscription_tiers, session_packs, user_subscriptions, purchases) because the tier and pack credit-allocation contract is now a checked-in TS enum (backend/src/billing/lookup-keys.ts); see Stripe contract. MYT-42 will recreate purchases with a new shape (lookup_key TEXT instead of the previous session_pack_size INTEGER) when the webhook handler lands.

Minimal-claims user row, no email / avatar / auth_provider — migration 001 originally carved email, avatar_url, and auth_provider out of the OAuth claims, but Cognito is already the authentication surface and the user picks their own identity at onboarding. The duplicated provider claim drifted from Cognito over time (a user who relinked from Google to Discord would have a stale auth_provider); the email copy was a GDPR liability that didn't earn its keep; the avatar URL we never displayed. Migration 005 drops all three. Future profile fields (uploaded avatar, bio) ship post-launch as user-uploadable attributes, not OAuth-derived ones.
Case-insensitive UNIQUE on LOWER(username) — Postgres TEXT is case-sensitive by default, which would let Admin / admin / ADMIN register as three distinct users. That's a moderator-impersonation lane: an attacker squats the casing variant the deny list misses. Migration 005 drops the original users_username_key constraint and replaces it with a UNIQUE expression index users_username_lower_key ON users (LOWER(username)). The display preserves the user's chosen casing; uniqueness collapses across casings. Repository lookups use WHERE LOWER(username) = LOWER($1) so they hit the expression index.

credit_ledger is the only place credit balance lives. There is no credit_balance column on users. Granting credits is an INSERT; spending credits is an INSERT with a negative amount; the current balance is a sum over rows. The idx_credit_ledger_user_type composite index makes that sum a hot-path query.

Append-only ledger, not a mutable balance column — billing accuracy is load-bearing. A mutable balance is a single row that can be wrong; a ledger is an audit trail that can be replayed. Refunds, gifts, expirations, and disputes all become INSERTs with an explicit source_type (purchase | subscription | gift | trial | refund | debit), not in-place edits we'd have to reconstruct from Stripe webhooks. The Billing & Cost Controls spec picks this up; the schema commits to it now so we don't ship a mutable balance and then try to unship it.

Migration 004 adds three CHECK constraints and a partial-unique index that pin the ledger's invariants at the database layer: (source_type = 'debit') = (amount < 0) — debits are negative and only debits are negative; source_type <> 'debit' OR source_id IS NOT NULL — debits must carry the per-user idempotency key; source_type <> 'debit' OR expires_at IS NULL — debits represent consumption and never expire; and uniq_credit_ledger_debit_idempotency ON (user_id, credit_type, source_id) WHERE source_type = 'debit' — the same debit cannot land twice. The same migration also swaps the user_id FK from ON DELETE CASCADE to ON DELETE RESTRICT for the same reason a bank ledger isn't garbage-collected when an account closes.

RESTRICT on a financial table, not CASCADE — the original migration declared the FK as CASCADE alongside the rest of the per-user data. For a revenue ledger that's wrong: a hard delete (admin error, GDPR erasure path) would silently erase every purchase, refund, and debit belonging to that user, breaking Stripe reconciliation and any audit downstream. RESTRICT forces the deletion to fail loudly until the rows are dealt with explicitly. GDPR erasure becomes a soft-delete / pseudonymize flow tracked separately. The same shape will apply to the MYT-42-recreated purchases table and to stripe_events when their consumers ship.
Application-layer enforcement and DB-layer CHECKs — the repo layer already guarantees these invariants in the happy path (only atomicDebit writes negative amounts; only grant writes positive). The CHECKs are belt-and-suspenders for everything that doesn't go through the repo: a future admin tool, a Stripe webhook backfill, a one-off corrective migration. A bug in any of those gets a clear constraint violation at insert time instead of a silently mis-shaped balance the team discovers months later.

Worlds and entities

A world is the prep-engine output: a setting with a concept, tone, geography, political situation, and a tree of entities (NPCs, locations, factions, items). Each entity carries a prose_kernel (1:1, the LLM-authored prose chunk that gets re-served whenever the entity surfaces in play) and zero or more facts with explicit access_level (public | private | secret) and narrative_status (undelivered | delivered | developed | resolved). The enforced-ignorance boundary in the runtime reads access_level directly from this column — the schema is what makes the boundary checkable.

worlds.source_world_id is a self-reference for forks: a copy of someone else's shared world starts as a child row pointing back at its origin. ON DELETE SET NULL preserves the fork even if the origin is deleted; the link goes nullish, the world stands alone.

relationships connects two entities by string-typed kind ("owns", "rules", "estranged-from"); entity_hierarchy is the parent/child tree separately because a village belongs to a region belongs to a kingdom and we walk that often. random_tables + random_table_entries hold per-world rollables. stat_blocks + stat_block_actions are the combat-relevant numbers, attached to entities by FK with ON DELETE SET NULL so you can swap a stat block out without losing the entity.

Campaigns and play

A campaign is a play instance over a world. world_id cascades on delete; source_world_id records "this campaign was created from this prep snapshot of the world" and goes nullish on origin deletion. campaign_members ties users to campaigns with role IN ('owner', 'player') and a UNIQUE(campaign_id, user_id) so no one is on the same campaign twice. campaign_invites hold redeemable codes with optional expiry and use caps.

characters are the player avatars: stats, hit points, level, class, the character_skills / features / equipment / spells satellites. A character points at its campaign (CASCADE) and optionally at an entity (SET NULL) — when a player retires a character, the entity that represented them in the world stays.

Live play happens in a session bound to a campaign. session_messages hold every line of the transcript with a seq column so replay is deterministic; session_participants records who was present. world_snapshots is a point-in-time freeze of world state used by session_preps (the FT context + ST playbook the runtime loads at session start). session_usage tracks per-session token spend for the budget caps.

Partial-unique idx_sessions_one_active instead of an app-layer check — at most one session per campaign can be in status = 'active' at a time. An application-layer check ("query for an active session, refuse to start a second") loses to a race: two clients both query, both see no active session, both INSERT. Postgres CREATE UNIQUE INDEX ... WHERE status = 'active' moves the invariant into the database: the second INSERT errors with a unique-violation, which the runtime translates into a user-facing "your campaign already has an active session." The partial predicate matters: ended and crashed sessions accumulate freely; only active is bounded to one. The Multiplayer Session Runtime spec depends on this guarantee.

Pipeline runs and ops

pipeline_runs is the prep-engine and session-prep job ledger: one row per (world or campaign) × stage × user attempt, carrying status, token counts, cost, and start/complete timestamps. The "one row per (world|campaign, stage, user)" invariant ships as a separate CREATE UNIQUE INDEX, not a table-level UNIQUE: 

CREATE UNIQUE INDEX idx_pipeline_runs_unique
  ON pipeline_runs (
    COALESCE(world_id, campaign_id),
    stage,
    COALESCE(user_id, '00000000-0000-0000-0000-000000000000'::uuid)
  );
UNIQUE INDEX with COALESCE, not a table-level UNIQUE — Postgres table-level UNIQUE constraints accept only column lists, not expressions. The invariant we want is "the same stage can't run twice for the same world-or-campaign and the same user," but the identifier is split across world_id and campaign_id (one is set, the other is null), and user_id can be null for system-initiated runs. A naive UNIQUE(world_id, campaign_id, stage, user_id) wouldn't enforce uniqueness across the null columns at all (NULL ≠ NULL in SQL). The COALESCE collapses the null cases to a sentinel — for user_id the all-zeros UUID with an explicit ::uuid cast so type unification works — and the resulting expression-based index does what we want. The original spec §4 had this as a table-level UNIQUE and would have failed to apply; that bug got fixed in the same commit as this transcription.

world_marketplace and moderation_flags are schema-ready but not built at launch — the columns exist so the marketplace and trust-and-safety milestones don't need a schema-migration ceremony when they ship. settings is a key-value bag for global feature flags and ops knobs, intentionally simple.

SRD reference tables

srd_monsters, srd_spells, srd_conditions are read-only reference data — the System Reference Document content used by the combat engine and prep pipeline. The tables exist now; the data load is a follow-up bead in the prep-pipeline milestone. Until then, no test or seed should reference an srd_* row by id.

Cascade rules: which deletes ripple

The FK cascade rules encode the cleanup paths. Deleting a user RESTRICTs on credit_ledger (a revenue ledger is never garbage-collected; see migration 004 above), and leaves worlds and campaigns orphaned (the FK is NO ACTION on created_by) — user deletion is a billing-team operation, not a content-delete operation. Deleting a world CASCADEs through entities → facts + prose_kernels + relationships + entity_hierarchy, and through campaigns → sessions → session_messages: a world delete is a tear-everything-down operation. Stat blocks detach to SET NULL on entity deletion; characters detach to SET NULL on entity deletion. The schema-parity test in migrate-schema.test.ts pins each of these rules — including the credit_ledger RESTRICT, the four migration-004 invariants, migration 005's drop-and-replacement of the username UNIQUE, and migration 006's drop of the four legacy billing-config tables — so a future migration can't silently flip a CASCADE to a NO ACTION (or vice versa), re-introduce a case-sensitive username uniqueness, or quietly re-add the dropped tables under their old shapes.

What's not in the schema yet

UUIDv7 generation. Tables declare id UUID PRIMARY KEY with no default; the application generates the id at insert time using a UUIDv7 library. The DB-level fallback function is roadmapped to a separate ticket.

Repository layer. backend/src/db/ ships migrate.ts, lock-key.ts, and postgres.ts; the typed namespaces over these tables live next door at backend/src/repo/ and ship six namespaces today (users, worlds, campaigns, sessions, credits, invites). The remaining namespaces ship batched with their consumers.

Operating this piece

Apply the schema locally

  1. pnpm db:up if Postgres isn't running. pnpm db:reset wipes the docker volume and gives you a fresh database — recommended whenever you pull a branch that touches migrations.
  2. pnpm db:migrate applies all six migration files end-to-end. A second run is a no-op.
  3. Verify the shape: 
    docker compose exec postgres psql -U mythrun -d mythrun -c "\dt"
docker compose exec postgres psql -U mythrun -d mythrun -c "\di"
    You should see 35 tables (1 _migrations + 31 application + 3 SRD), the idx_* index set, the uniq_credit_ledger_debit_idempotency partial-unique index from migration 004, the users_username_lower_key expression index from migration 005 (with no email / avatar_url / auth_provider columns on users), and no subscription_tiers / session_packs / user_subscriptions / purchases tables (migration 006 dropped them).

Recover from the MYT-32 → MYT-33 transition

  1. Symptom: the runner emits migrate.drift_missing_files with missing: ["001_smoke.sql"] and a hint field pointing at pnpm db:reset.
  2. The cause: your local database was migrated under MYT-32 (which shipped 001_smoke.sql) and now MYT-33 has replaced that file with 001_initial_schema.sql. The smoke row is still in _migrations with no file on disk.
  3. Fix it forward: pnpm db:reset && pnpm db:migrate. The reset wipes the docker volume (clearing the stale _migrations rows); the second command applies the three real migrations cleanly. The drift warning goes away.

Integration points

The migrations runner applies these six files; the runner's _migrations bookkeeping is what the drift hint is reasoning about. Downstream, the backend runtime's repository layer will read and write these tables; the auth & billing stories build on users, credit_ledger, and stripe_events, with the Stripe contract page covering how Mythrun's view of "what tier is this user on" comes from a per-user Stripe API read instead of a local mirror table; the world & campaign pipeline writes worlds + entities + facts + prose_kernels. For the column-by-column view — every type, default, constraint, index, and FK — see the schema reference page.

Schema-parity test

backend/src/db/__tests__/migrate-schema.test.ts runs all six migrations against a clean DB and asserts the full set: every table name, every idx_* index name, every CHECK constraint, every FK ON DELETE rule, the partial-unique predicate on idx_sessions_one_active, and the absence of the four tables migration 006 dropped. A transcription typo or a future schema-drift PR fails the test with a clear diff.
