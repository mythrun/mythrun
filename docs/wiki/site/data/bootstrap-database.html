Bootstrap Database

How an operator brings a new RDS instance from "shell secret only" to "app password populated" — by running bootstrap-databases.sh inside a one-shot ECS task. The same path is used for password rotation and drift recovery.

Why a one-shot ECS task

RDS sits in private subnets and is not publicly accessible, so the script can't run from a laptop. We don't keep a bastion EC2 because that's an always-on cost surface for an operation that runs at most every few weeks. Instead, we ship a dedicated container image with the script baked in and execute it as an aws ecs run-task against the existing Mythrun ECS cluster. The task definition + image build pipeline are versioned Terraform + GitHub Actions; nothing is ad-hoc.

The four script modes

Always run --verify first. Its single-token output tells you which mode to run next.

--verify outputRun withWhy
OK nothing — already bootstrapped DB + user + secret all present
MISSING bootstrap_db_run_task_default Creates DB + user + secret
DB_ONLY bootstrap_db_run_task_user_only DB exists; create user + write secret
SECRET_MISSING bootstrap_db_run_task_secret_only DB + user exist; rotate password + write secret
OK but migrations 500 with permission denied for schema public --grant-only override DB + user + secret present but the app role lacks CREATE on schema public (Postgres 15+ default ACL). Idempotent.
Why the schema-grant step is separate from the DB+user grant — Postgres distinguishes between database-level privileges (granted at CREATE USER + GRANT ALL PRIVILEGES ON DATABASE) and schema-level privileges. Postgres 15+ revoked PUBLIC's default CREATE on schema public; non-owner users now need an explicit grant. The script's create_db_and_user and create_user_only paths run GRANT USAGE, CREATE ON SCHEMA public on the target database after creating the user. The --grant-only mode exists for the rare case where the user pre-dates this fix (database state from before commit 21456e7).

First-time setup runbook

  1. Land the Terraform.

    cd infra/environments/shared && terraform apply
cd ../staging && terraform apply

    The shared apply creates the mythrun-bootstrap-db ECR repo + lifecycle policy. The staging apply creates the task definition family, IAM roles, security group, log group, and the GitHub Actions IAM extension for ECR push.

  2. Build + push the bootstrap image. Path-triggered on script/Dockerfile/workflow edits, or dispatch manually:

    gh workflow run bootstrap-db-build.yml
RUN_ID=$(gh run list --workflow=bootstrap-db-build.yml --limit=1 --json databaseId -q '.[0].databaseId')
gh run watch "$RUN_ID" --exit-status

  3. Pin the new image tag. Capture the literal one-liner from the workflow's output:

    gh run download "$RUN_ID" -n bootstrap-image-tag-line && cat bootstrap_image_tag.line

    Replace the existing bootstrap_image_tag line in infra/environments/staging/terraform.tfvars with the captured line. Commit + push, then:

    cd infra/environments/staging && terraform apply
    Don't apply before the image is in ECR. If you pin bootstrap_image_tag to a tag that hasn't been pushed yet, terraform apply succeeds (the task definition just stores the tag string) but the next run-task invocation fails with CannotPullContainerError after a 60-90s Fargate provisioning wait — a non-obvious failure mode at 2am. The gh run watch --exit-status gate above is what makes this safe.

  4. Verify network + IAM + image. Read-only — always safe:

    RUN_TASK_CMD=$(terraform output -raw bootstrap_db_run_task_verify)
TASK_ARN=$(eval "$RUN_TASK_CMD" --query 'tasks[0].taskArn' --output text)
echo "Task: $TASK_ARN"

# Wait for the task to finish. Cold-start is 60-120s; cold pull-through cache
# can stretch this further. `wait tasks-stopped` polls every 6s up to 100
# attempts = 10 min ceiling. If you hit that ceiling, inspect lastStatus before
# concluding failure:
#   aws ecs describe-tasks --cluster mythrun --tasks "$TASK_ARN" \
#     --query 'tasks[0].lastStatus'
# PROVISIONING ⇒ network/IAM still resolving; STOPPING ⇒ already failed.
aws ecs wait tasks-stopped --cluster mythrun --tasks "$TASK_ARN"

# Exit code + stoppedReason.
aws ecs describe-tasks --cluster mythrun --tasks "$TASK_ARN" \
  --query 'tasks[0].containers[0].{exitCode:exitCode,reason:reason,stoppedReason:stoppedReason}'

# Read THIS task's logs (stream-name-prefix avoids interleaved historical output).
TASK_ID="${TASK_ARN##*/}"
aws logs tail /ecs/mythrun-staging-bootstrap-db \
  --since 30m --format short \
  --log-stream-name-prefix "bootstrap/bootstrap/$TASK_ID"

    Expect: exitCode 0; the log prints one of OK, MISSING, DB_ONLY, or SECRET_MISSING on a line by itself.

  5. Run the appropriate mode. Use the verify→mode table above, then the same wait + describe + log-tail flow as step 4. For example, on SECRET_MISSING:

    eval "$(terraform output -raw bootstrap_db_run_task_secret_only)"

Failure modes

Match by substring — AWS's literal stoppedReason strings drift across releases. The diagnostic command in the third column is the fastest next step.

ECS stoppedReason substring Container log line Likely cause First check
CannotPullContainerError (no container log — task never started) Image tag pinned in TF doesn't exist in ECR (stale bootstrap_image_tag or build hadn't completed) aws ecr describe-images --repository-name mythrun-bootstrap-db --image-ids imageTag="$TAG"
ResourceInitializationError: ... secrets or registry auth (no container log) Task-execution role missing ECR pull or KMS decrypt Check aws_iam_role.task_execution policy attachments
Essential container in task exited (exit code 1) RDS master secret missing 'X' Master secret payload is malformed or rotated to an unexpected schema aws secretsmanager get-secret-value --secret-id <master-arn> and inspect the JSON shape
Essential container in task exited (exit code 1) psql: could not connect RDS SG ingress rule didn't apply, or RDS endpoint changed aws ec2 describe-security-groups --group-ids $RDS_SG_ID looking for an ingress from the bootstrap SG
Task stuck in PROVISIONING for >2 min then stops with Network Configuration error (no container log) Subnets have no NAT route OR SG egress 443 missing Check route table on the subnets; check bootstrap_https egress rule
Essential container in task exited (exit code 2) Log line starting with unknown arg: The run-task command had a placeholder token instead of one of the five discrete outputs Use terraform output -raw bootstrap_db_run_task_verify (or one of the four other discrete outputs); don't string-substitute

Recovery from a half-applied --secret-only

If --secret-only exits non-zero between the ALTER USER (logged as the SQL line) and the secret write (logged as Rotated password), the database password and Secrets Manager are divergent and the app can't connect. Re-run the same --secret-only invocation — the script generates a new password, runs ALTER USER again, and re-writes the secret. The script is idempotent for this. Do not manually paste the password from CloudWatch logs (passwords are not logged by design).

If --verify itself errored

--verify is read-only but it can still exit 1 for three reasons:

  • Master-secret read failure — IAM denial. Check the task role policy attachments.
  • Malformed master secret — the master was rotated to an unexpected JSON schema. Inspect with aws secretsmanager get-secret-value and escalate; do not run any non-verify mode against a malformed master.
  • psql connectivity — network path missing. See the failure-modes table above.

Updating the script

Edit infra/scripts/bootstrap-databases.sh, push to main; the path-trigger fires bootstrap-db-build.yml; wait for the workflow to succeed; copy the literal bootstrap_image_tag = "..." line from the workflow's ::notice:: output (or the bootstrap-image-tag-line artifact); replace the existing line in terraform.tfvars; commit + push; terraform apply.

See also: Migrations — the migration runner is what runs after bootstrap puts the password in place.
