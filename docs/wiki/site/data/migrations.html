Migrations

How the Postgres schema evolves: append-only .sql files in backend/migrations/, applied one transaction at a time by a CLI that takes a pinned advisory lock and writes a tracking row per file.

How it fits together

Every schema change is a numbered .sql file under backend/migrations/. Filenames follow [0-9]{3,}_[a-z0-9_]+\.sql — three-or-more digits, an underscore, lowercase identifier — so a lexicographic sort is also a chronological one. Once a file lands on main, it is immutable; corrective work ships as a new file with a higher number. The runner reads the directory at boot, compares it against a tracking table, and applies whatever's pending in order.

Append-only is enforced in CI, not on the honor system — the Migrations Append-Only workflow (.github/workflows/migrations-append-only.yml) runs on every pull request that touches backend/migrations/*.sql and rejects any diff entry whose status isn't A (added). Edits, deletes, and renames against files that already exist on main fail the PR. The runtime migrate.drift_missing_files warning remains as a backstop for the case where someone alters an applied file outside git (a restored backup, a manual SSH'd-in edit) — operational accidents the CI gate can't see.

The advisory lock and the session it lives in

Two simultaneous runners — a deploy task and an operator running pnpm db:migrate against the same DB — would both SELECT the same pending list and both try the same CREATE TABLE. The second one would crash on duplicate_table. The runner avoids this with pg_advisory_lock(LOCK_KEY): a session-scoped mutex Postgres provides for exactly this kind of cross-process coordination. The lock is held for the run and auto-releases when the socket closes, so a SIGKILL'd runner doesn't strand the lock.

Advisory lock, not a unique-PK guard on _migrations — a unique-PK guard catches the duplicate insert, but the second runner has already started executing the migration's DDL by then. With DDL like CREATE EXTENSION or CREATE FUNCTION the failure mode is "second runner crashes mid-statement, half- applied state left behind." The advisory lock serializes the whole run, including the read of _migrations, so the second runner blocks until the first one is fully done.

LOCK_KEY is a pinned bigint in backend/src/db/lock-key.ts, derived once from SELECT hashtextextended('mythrun_migrate', 0) against PostgreSQL 16. A drift test asserts the literal so a future refactor can't silently change it during a rolling deploy (which would put old and new code on different lock keys, defeating the guard).

The lock, the bookkeeping insert, and the migration SQL all share one pg.PoolClient. Advisory locks are session-scoped — they don't survive checking the client back into the pool — so the runner uses a max: 1 pool, holds the same client throughout, and only releases at the very end. Connection timeout is bounded at 10 seconds; the default of 0 hangs forever and that's not what an operator wants when RDS is unreachable.

Session hygiene: SET LOCAL and DISCARD ALL

Each migration runs inside BEGIN / COMMIT. Before executing the file, the runner sets three session variables — but only with SET LOCAL, so they reset on COMMIT. statement_timeout goes to 0 (migrations can be slow), lock_timeout goes to 30s (so a stuck DDL doesn't wait indefinitely on a row-level lock from the API), and application_name goes to mythrun-migrate so the migration session shows up distinctly in pg_stat_activity and Performance Insights.

Why SET LOCAL application_name, not bare SET — bare SET application_name = 'mythrun-migrate' survives release() back to the pool. The next checkout — eventually the API server, when this runner shares a pool with server boot — would see itself as mythrun-migrate in pg_stat_activity until it reconnected, polluting triage. SET LOCAL scopes to the transaction; on COMMIT the value is gone. Test 12 in the suite pins this invariant.

On the success path, the runner also calls DISCARD ALL before release(). SET LOCAL is enough if every change in the file uses it; DISCARD ALL is the broader defense for a migration author who reaches for a bare SET or RESET application_name. On the error path the client is destroyed via release(err) instead — pg-pool's documented signature for "close this socket, don't return it to the pool" — so DISCARD is unnecessary there.

The tracking table and the per-file transaction

_migrations is a single-column table created inside the locked section (CREATE TABLE IF NOT EXISTS, so a fresh-DB race doesn't trip duplicate_table). The underscore prefix is the framework-metadata convention; no application table uses one. version stores the full filename as the natural key — no surrogate id, no checksum column yet.

For each pending file: BEGIN, SET LOCAL, run the file contents, INSERT INTO _migrations, COMMIT. A SQL error rolls the whole transaction back, including the bookkeeping insert, so the next run sees the file as still pending. The runner emits migrate.failed with the file's durationMs, re-throws an Error with cause chained to the pg error, and stops — later files don't attempt.

One transaction per file, not one transaction for the whole run — bundling all files into one transaction sounds atomic but isn't useful here: the second migration in a run often depends on the first having committed (e.g. an index on a table the previous file just created). Per-file gives "all-or-nothing for this change" without coupling unrelated changes. The cost — a partial run leaves the DB at an intermediate version — is exactly what _migrations tracks, so the next run picks up where the failed one stopped.

Validation: filename grammar and dollar-quote-aware body scan

Two checks before the runner touches the DB. First, the filename grammar regex above; anything else in backend/migrations/ is rejected with a clear error (no spaces, no unicode, no missing prefix). Second, a body scan that rejects top-level BEGIN/COMMIT/ROLLBACK/END/START TRANSACTION — the wrapper transaction is ours, and nested transaction control breaks the per-file atomicity story.

The body scan is dollar-quote-aware — a naive ^\s*BEGIN\s*$ regex would falsely reject DO $$ BEGIN ... END $$; blocks and CREATE FUNCTION ... AS $$ ... $$ bodies, which are exactly the shapes the real schema migrations will use for triggers and helpers. The validator strips dollar-quoted runs (preserving line numbers for error messages) before scanning. CREATE INDEX CONCURRENTLY is also rejected because it's incompatible with the wrapper transaction; an opt-in -- pg-migrate: no-transaction header is roadmapped.

Out-of-order detection and drift warning

After computing applied vs pending, the runner compares lexicographically. If a pending file is less than the highest applied version (e.g. 002_x.sql shows up after 003_y.sql already ran in staging), the run errors out with a "rebase to a version greater than the highest applied" message. A teammate's branch that adds 002_x.sql while 003_y.sql is already deployed is the canonical case.

The opposite case — an applied row whose file is missing from disk — is a warning, not an error: migrate.drift_missing_files with the missing list and an actionable hint field. The hint names the canonical recovery (pnpm db:reset && pnpm db:migrate) so a contributor seeing the warning during the MYT-32 → MYT-33 transition knows what to do without grepping the design doc; if drift surfaces outside that transition the same hint says "investigate before continuing." The run continues either way. The CI append-only gate prevents this in the normal case — file disappears from the tree → PR fails. The runtime warning is the out-of-band backstop for restored backups or manual edits on a live host.

Lock-wait heartbeat: visibility while blocked

Without a heartbeat, a runner blocked behind another runner's lock would emit migrate.start and then go silent — leaving an operator unable to distinguish "wedged" from "crashed." The runner instead loops on pg_try_advisory_lock with a 500 ms poll, and every 5 seconds emits migrate.lock_waiting with waitMsSoFar and a holder snapshot (pid, application_name, query state) read from pg_stat_activity. The holder query is best-effort — if it fails on permissions, the heartbeat still fires with holder: null — but most of the time it tells the operator exactly which process is blocking them.

Signal handling and exit codes

The CLI installs SIGINT/SIGTERM handlers (the same installSignalHandlers the backend boot gate uses) wired to an AbortController. SIGTERM does not cancel an in-flight pg query — that's a Postgres limitation, not a runner choice. What it does is trip the abort signal, which the runner checks between migrations: any in-flight file completes (or fails normally), then the runner returns the migrations applied so far and exits 130 instead of 0. Exit 1 is reserved for crashes (env load failure, unreachable DB, SQL error). The deploy-script bead picks up that distinction to tell "told to stop" apart from "broke."

Why MIGRATE_DATABASE_URL takes precedence over DATABASE_URL — the API container connects with a least-privileged app role (Auth & Users spec). The migration container needs rds_superuser for CREATE EXTENSION and similar. Two roles, two secrets, but only one URL contract: if MIGRATE_DATABASE_URL is set the runner uses it, otherwise it falls back to DATABASE_URL so local dev (one role, one URL) keeps working. The check is an explicit length test, not ??, because Terraform cond ? var : null patterns sometimes emit empty strings that ?? would not skip.

Structured logs and CloudWatch

Every event is a pino structured-JSON line with a top-level event key, the runId (a UUIDv7 generated per invocation by backend/src/repo/uuidv7.ts, the same wrapper every repo create uses — single seam), and either a version / durationMs pair (per-file events) or a totals payload (run-level events). A custom err serializer wraps pino.stdSerializers.err to recurse into err.cause and strip connectionParameters / connectionString fields — pg's DatabaseError can otherwise leak the password from the connection URL into a log line. pino.redact with explicit paths is layered behind the serializer as defense in depth.

Operating this piece

Run migrations locally

  1. pnpm db:up if the local Postgres isn't running. The runner connects to whatever DATABASE_URL resolves to in backend/.env.development; the safety guard refuses anything other than localhost + mythrun(_test|_ci) when invoked from tests.
  2. From the repo root: pnpm db:migrate. On a fresh DB, the runner applies 001_initial_schema.sql, 002_indexes.sql, 003_srd_reference_data.sql, 004_credit_ledger_invariants.sql, 005_drop_profile_columns_users.sql, 006_drop_billing_config_tables.sql, 007_recreate_billing_tables.sql, 008_billing_metering.sql, and 009_character_portability.sql in order — the current schema. A second run is a no-op that logs migrate.no_pending and exits 0.
  3. To author a new migration: add NNN_short_name.sql to backend/migrations/, where NNN is the next number after the highest file currently in the directory. Lowercase identifier, underscores only.
  4. Never edit an applied migration file. If the change is wrong, ship a new file that fixes it forward. The append-only convention is what makes "what runs in staging runs in prod" meaningful.

Inspect a migration run in CloudWatch

  1. Open Logs Insights against the ECS task's log group. Every migration event carries component = "migrate" at the base, so cross-component noise filters out cleanly.
  2. Recent failures with context: 
    filter component = "migrate" and event = "migrate.failed"
| fields @timestamp, runId, version, durationMs, err.code, err.message
| sort @timestamp desc
| limit 50
  3. Slow migrations (look for outliers across runs): 
    filter component = "migrate" and event = "migrate.applied"
| stats avg(durationMs), max(durationMs), count(*) by version
| sort max(durationMs) desc
  4. Lock-contention investigation — every migrate.lock_waiting event carries a holder snapshot: 
    filter component = "migrate" and (event = "migrate.lock_waiting" or event = "migrate.lock_acquired")
| fields @timestamp, runId, waitMsSoFar, waitMs
| sort @timestamp desc
  5. Reconstruct a single run end-to-end given a runId from another query: 
    filter component = "migrate" and runId = "<paste-runId>"
| sort @timestamp asc
  6. Did the last deploy actually migrate anything? 
    filter component = "migrate" and (event = "migrate.complete" or event = "migrate.no_pending")
| fields @timestamp, runId, count, versions
| sort @timestamp desc
| limit 10

Recover from a bad migration

  1. Find the failing run in CloudWatch — the recent-failures query above gets you the runId and version in one shot. Pull the full run with the "reconstruct a single run" query to see the SQL error and where it stopped.
  2. Open a session into a running task with ECS Exec (enableExecuteCommand is provisioned per the serving module): 
    aws ecs list-tasks \
  --cluster mythrun \
  --service-name mythrun-staging-api \
  --region us-east-1

aws ecs execute-command \
  --cluster mythrun \
  --task <TASK_ARN> \
  --container api \
  --interactive \
  --command "/bin/sh"
  3. Connect with the migration role (the one with rds_superuser if the failed statement needed it). Apply corrective SQL by hand and commit.
  4. If the next run should reapply the fixed migration, delete the row: DELETE FROM _migrations WHERE version = '<filename>'. Otherwise leave the row in place and ship a new NNN_fix_*.sql that does the cleanup forward.
  5. Trigger another deploy (or run the migration task directly). Verify with the "did the last deploy actually migrate anything?" query above that the corrective change shows up in versions.

Integration points

The runner applies the current schema — nine files in backend/migrations/, the union of which lays down the application tables, named indexes, and three empty SRD reference tables — onto a fresh database; the schema page is the explainer for what those files lay down. The runner reuses createPgPool from the backend workspace and the installSignalHandlers shape the boot gate already established. The eventual server-boot wiring will call runMigrations after the waitFor(pg) probe and before app.listen; the MigrateLogger type is narrowed to a Pick of pino's base logger so Fastify's app.log satisfies it without a cast. The deploy pipeline (CI/CD) will pick up a one-off ECS task pattern as a follow-up bead — the runner already supports that mode by virtue of being a CLI; the bead is task- definition wiring and the migration-role secret. The runner also assumes the per-env app password secret has been populated — see Bootstrap Database for that one-time setup.

Appendix: inputs & outputs

Environment variables

Var Default Notes
MIGRATE_DATABASE_URL unset Takes precedence over DATABASE_URL when set and non-empty. Production points this at the migration role's secret; the API role connects via DATABASE_URL.
DATABASE_URL — Fallback when MIGRATE_DATABASE_URL is unset or empty. Component-form (DB_HOST / DB_USER / etc.) also accepted by loadEnv.
LOG_LEVEL info debug available for future per-statement timing. Lock-wait heartbeats are info-level on purpose.

Exit codes

Code Meaning
0 Success — every pending migration applied, or nothing was pending.
130 Graceful abort — SIGTERM/SIGINT received between migrations. Any migration in flight at the time of the signal completed normally; no half-applied state.
1 Crash — env load failure, unreachable DB, validation error, or SQL error. The deploy orchestrator's job is to retry; the runner converges on re-run.

Structured log events

Event Level Fields (in addition to runId)
migrate.start info migrationsDir, pgServerVersion, dbHost, nodeVersion
migrate.lock_waiting info waitMsSoFar, holder (pid, applicationName, state, queryStartedAt, queryPreview)
migrate.lock_acquired info waitMs
migrate.lock_released info holdMs
migrate.unlock_failed warn err (auto-release on socket close is the backstop)
migrate.plan info pending, total, pendingVersions
migrate.applied info version, durationMs
migrate.failed error version, durationMs, err
migrate.aborted warn appliedSoFar, remaining
migrate.drift_missing_files warn missing (versions in _migrations with no file on disk), hint (recovery guidance — points at pnpm db:reset for the MYT-32 → MYT-33 transition)
migrate.no_migrations_found info —
migrate.no_pending / migrate.complete info count, versions
migrate.done info applied, totalMs
migrate.fatal error err, hint? (mapped from SQLSTATE / errno), nextStep

Filesystem layout

Path Notes
backend/migrations/ Append-only .sql files. Lives outside backend/src/ so it isn't compiled. The Dockerfile runtime stage copies it to /app/migrations.
backend/src/db/migrate.ts runMigrations() + the CLI entrypoint guarded by import.meta.url.
backend/src/db/lock-key.ts The pinned LOCK_KEY bigint. A drift test asserts the literal.
_migrations (in DB) (version TEXT PRIMARY KEY, applied_at TIMESTAMPTZ DEFAULT now()). Created inside the locked section. The only _* table the application owns.
