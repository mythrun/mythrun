World-store retrieval

How the world store becomes queryable. Two paths over one substrate: a write path that embeds every fact and entity into a 512-dim vector, and a read path that answers a turn's question two ways — pgvector cosine search over those vectors (semantic lore) and recursive-CTE walks over the relationship graph (who-knows-whom, faction trees). Both over-pull every access tier; the Slow Thinker gate downstream is the single tier-safety boundary, not this layer.

How it fits together

The world store the prep engine produces — worlds, entities, facts, prose kernels, relationships — is rich but inert. The live-play tiers need to ask it questions: "what does the world know about a volcanic dragon lair?" (the Fast Thinker's in-character lookup, MYT-72), "does this improvised NPC already exist in canon?" (the Scribe's match-vs-mint, on the durable-canon path), "who is this faction's parent organization?" Retrieval is the substrate that turns the store into something queryable, and it is deliberately split from its consumers: this ticket builds and proves the substrate; its consumers import it. MYT-72 was the first — the Fast Thinker's world-knowledge lookups drive all three resolvers in live play, behind the Slow-Thinker vet. MYT-73 added the in-session working-set read-merge on top: searchLore now returns its query vector so a session's invented facts can be cosine-ranked against it and unioned into the lore hits at the consumer (the LoreHit type gains a third working_set source for those merged hits).

Everything funnels through one barrel, backend/src/world/retrieval/index.ts — the only surface a consumer imports. It re-exports the search resolvers (createSearchResolvers → searchLore / findSimilarEntities), the two graph walks (charactersKnownTo, factionTree), the write-path entry (embedWorld), and every camelCase result type. The internal tuning constants and the snake_case DB-row types are deliberately not re-exported: consumers depend on the resolver shape, never the SQL layer underneath it.

Over-pull, no tier filter anywhere in this layer — not the SQL binder, not the search resolvers, not the graph walks apply an access_level predicate. Every query returns known, discoverable, and secret rows alike. That is intentional and load-bearing: the tier-safety boundary is the Slow Thinker gate that sits between retrieval and the player-facing Fast Thinker. A tier filter here would blind the Slow Thinker to the very secrets it needs to reason about — and would be a second, weaker enforcement point competing with the real one. The resolver's job is recall; the gate's job is safety. Putting a filter in this layer would be a bug, and the code comments say so.
Over-pull means surfacing the tier, not dropping it — all three resolvers now tag every row — the gate downstream can only do its job if it can see each row's tier. The lore search always carried accessLevel on its hits; MYT-72 surfaced the same access_level on the graph walks' results too (KnownCharacter and FactionNode now project it), since two of the three substrates were otherwise blind to it. The walks still over-pull every tier — the annotation is added to the projection, never used as a filter — so the lookup's vet receives a tier-annotated block ([tier=secret] …) it can reason over for all three resolvers.

The vector substrate: pgvector on the rows it describes

Migration 026_world_retrieval.sql enables the vector extension and adds two columns to both facts and entities: an embedding vector(512) and an embedded_at timestamptz. The embedding lives on the row it describes — a fact's vector sits on the fact, an entity's on the entity — rather than in a side table. Both columns are nullable: a row with a NULL embedding is simply unsearchable until it gets embedded, never a crash. The embedded_at timestamp lets a future backfill find rows whose content changed after they were embedded (drift), not only the never-embedded ones.

HNSW, not IVFFlat — the index is HNSW with cosine ops on each embedding column. IVFFlat needs a populated table to train its centroid lists; the Scribe inserts new facts incrementally at the end of every session, so the table is never "done" being populated. HNSW has no training step, indexes inserts as they land, and gives higher recall — the correct tradeoff for a corpus that grows one session at a time. NULL embeddings aren't indexed.
The image swap that has to land first — stock postgres:16-alpine bundles pgcrypto but not vector. Local docker-compose and the CI Postgres service both run pgvector/pgvector:pg16 so CREATE EXTENSION vector resolves. The migrate role already holds rds_superuser on RDS (it runs CREATE EXTENSION pgcrypto in migration 001), so the extension is authorized with no parameter-group change.

The heavy read SQL lives behind the canonical worldRetrievalNs(c) binder in backend/src/repo/world-retrieval.ts, exactly like every other repository namespace. pgvector's <=> operator is cosine distance; the binder selects 1 - (embedding <=> $query) as the score, so the whole codebase speaks one convention: score in [-1, 1], higher is more similar. Postgres has no native vector parameter type, so the caller passes the '[f1,…,f512]' text form and the SQL casts $2::vector.

One schema wrinkle the binder absorbs: facts has no world_id column (schema drift since migration 001), so a fact search scopes through JOIN entities e ON e.id = f.entity_id WHERE e.world_id = $1, mirroring every other world-scoped fact read. Entity searches scope on entities.world_id directly.

The write path: embedWorld

embedWorld(deps, worldId, opts?) in world/retrieval/embed-write.ts reads a world's un-embedded facts and entities, embeds each kind's text through Voyage, and writes the vectors back. It is the core of the operational backfill and the seam both the world-gen embed stage and the character-integration post-pass call. Facts and entities are independent passes — separate read → embed → write — so a facts-success paired with an entities-failure correctly leaves facts embedded and entities NULL. Partial success is the contract.

The Voyage round-trip never sits inside a transaction — each pass is strictly: read the rows-to-embed via the repo (no tx), embed the whole list (no tx), then write the vectors in a short, write-only repo.transaction. RDS kills idle-in-transaction connections at 60 seconds, and a large document-embed batch can take longer than that. Holding a BEGIN open across the slow network call would risk a 25P03 kill mid-write. So the slow I/O is always outside the transaction; only the UPDATEs are inside it. This is the same discipline the prep pipeline learned in MYT-55.

An entity's embedded text is its name concatenated with its prose-kernel content, so the prose is baked into the entity vector at write time — there is no kernel join at read time. PCs are excluded from the entity embed set (entity_type <> 'pc'): a player character is not world lore. Without --force, both passes select only embedding IS NULL rows — the cheap incremental backfill, safe to re-run. With --force, every fact and entity in scope is re-embedded, which is a real Voyage spend event.

Only the embed call is wrapped in try/catch. A Voyage throw increments voyageErrors, leaves that kind's rows NULL (retryable on the next backfill), and skips its writes — the rows stay searchable-once-recovered, never corrupted. The write transaction is not wrapped: a DB write error is not a Voyage error, and mislabeling it would hide a real failure, so it propagates to the caller's catch site. The returned EmbedSummary carries embedded / leftNull / voyageErrors counts plus an optional configErrorKind — set only when a failure was a configuration error (see the resilience section), so callers can escalate a misconfiguration loudly instead of treating it like a transient blip.

The read path, part one: semantic search

createSearchResolvers(deps) in world/retrieval/search.ts is pure orchestration over the binder. It builds two resolvers with deliberately asymmetric error policies, because they sit on different criticality paths.

searchLore(worldId, queryText, opts) embeds the query (outside any transaction), runs the fact-arm and entity-arm cosine searches concurrently inside one short read transaction, merges the two result sets, re-ranks by score descending, and slices to the (clamped) limit. It returns a { hits, queryVec } pair — the ranked hits plus the query vector it embedded — so the in-session working-set read-merge (MYT-73) can cosine-rank the session's invented facts against the same vector without a second Voyage call. It is total: any thrown error — embed failure or query failure — is logged at warn and returns { hits: [], queryVec: [] }. The Fast Thinker's lookup tool narrates a blank rather than crashing the turn; lore retrieval is best-effort context, never a hard dependency. The caller-supplied limit is clamped into [1, 50], defaulting to 10.

findSimilarEntities(worldId, text, opts) embeds the query and over-pulls only the entity arm (PCs excluded by construction; an optional entityType narrows to one kind). It throws on any failure — the opposite policy — because it feeds the Scribe's canon write path. Swallowing a transient embed blip and returning an empty candidate list would make the Scribe think no similar entity exists and mint a duplicate canonical entity. The failure must propagate so the write is retried, not silently duplicated.

One SET LOCAL keeps the world filter from starving the top-k — the read transaction's BEGIN prelude issues SET LOCAL hnsw.iterative_scan = 'relaxed_order' (pgvector ≥ 0.8). Without it, an HNSW probe returns its first ef_search candidates and then applies the world-scope filter — which can drop the result count below the requested limit when a world's rows are sparse in the index. Relaxed iterative scan lets the index keep pulling candidates past the first batch until the filtered limit is satisfied, trading a little ordering precision for filtered-recall completeness. The SET LOCAL is transaction-scoped and lands in the same transaction as the search SELECT, because the prelude is part of that transaction's BEGIN.

The read path, part two: graph walks

Not every world question is semantic. "Who does this character know?" and "what is this faction's subtree?" are structural — answered by walking edges, not comparing vectors. world/retrieval/graph.ts is the thin deterministic shell over two recursive-CTE binders; it never opens a transaction and never touches a vector column.

charactersKnownTo(deps, entityId, opts) walks the relationships graph outward from a seed entity, in both edge directions (the recursive term unions source→target and target→source expansions), to a clamped depth (default 2, hard cap 5). The walk is cycle-safe via a path array (NOT next_id = ANY(path)) and diamond-deduped to each node's minimum depth with DISTINCT ON. The seed is depth 0. An optional nameFilter is applied as a mechanical, normalized exact-match post-filter in JavaScript — lower(btrim(name)) equality, no fuzzy matching. PCs are included on graph paths (unlike the lore searches), so the result type carries the widened GraphEntityType that includes 'pc'.

factionTree(deps, entityId) walks entity_hierarchy parent→child from a root faction. Because child_entity_id is unique, the hierarchy is a strict tree — no diamonds, no path array needed. The walk is bounded at the max graph depth, and the result carries a truncated flag: true when any returned node sits at exactly that depth, signalling the subtree may continue below the bound. The graph walks deliberately do not catch DB errors — there is no totality contract at this layer; MYT-72's tool-error handling is the catch site.

The Voyage embeddings client

backend/src/llm/embed.ts is the embeddings wrapper — a plain fetch to Voyage's /v1/embeddings, no third-party SDK. It exposes two methods with asymmetric input types: embedDocuments sends input_type: 'document' for stored rows, embedQuery sends input_type: 'query' for a search. The two halves are also given different timeouts — the write path is generous (60s; indexing runs offline where latency isn't player-visible), the read path is tight (5s; it sits in front of a waiting player, so it fails fast rather than stalling a turn). Every embedding is hard-asserted to be exactly 512-dim before it's returned.

Voyage, because Anthropic has no embeddings API — Mythrun's entire LLM surface is Anthropic, and the LLM client page documents that single abstraction. But Anthropic ships no embeddings endpoint, so semantic retrieval needs a second provider. Voyage is the embeddings vendor Anthropic itself recommends. The model is voyage-4-lite at 512 dimensions (a Matryoshka-truncated output — a good recall/size tradeoff at this corpus scale). The model id and output dimension are config constants in world/retrieval/config.ts, re-verified against Voyage's live model list each release because model ids drift and silently 400.

The wrapper classifies every failure into a taxonomy whose one operationally-meaningful split is config versus transient. A config error never self-heals — wrong key (auth, 401/403), wrong model id or output dimension (bad_request, 400), or a returned vector of the wrong width (dim_mismatch). A transient error recovers on its own — a 5xx, a network blip, a timeout, or a rate-limit (429) that survives a bounded exponential backoff. isVoyageConfigError collapses the taxonomy to that binary, and that binary is what the boot probe and the embed callers branch on.

The boot probe: a bad key can't ship silently

backend/src/boot/voyage-probe.ts validates Voyage at boot with one real embedQuery — asserting the live 512-dim round-trip against a real key. It is wired into both the worker and the API server boot sequences, right after the Postgres wait, alongside the Stripe contract probe.

Crashloop on misconfig, degrade on outage — never silent either way — the generic waitFor() boot helper crashloops on any persistent failure. That is wrong for Voyage: a transient Voyage outage must not crashloop the worker, because world-gen content still works and embeddings can backfill once Voyage recovers. So the probe splits on isVoyageConfigError. A config error throws — the process crashloops and the ECS deploy goes red, so a misconfigured key can never deploy and leave every world silently un-embedded. A transient failure is retried a couple of times, then logged loud (error level) and the process boots degraded. Either way the failure is observable; the one outcome that's forbidden is a quiet one.

The same config-vs-transient split is what makes the embed callers escalate correctly. When embedWorld reports a configErrorKind, the world-gen embed stage and the character-integration post-pass both log at error with an alarmable event (embed_world_misconfigured / embed_misconfigured) — every world is affected until the key, model, or dim is fixed. A transient voyageErrors > 0 logs at warn (embed_world_degraded): rows left NULL, the backfill recovers. A clean run logs the routine info line.

Where embedding gets triggered

A world becomes searchable through three triggers, all of which call embedWorld:

World-gen embed stage. llm/prep/stages/embed-world.ts runs after coherence_pass (the last content stage) and before worlds.status flips to complete, so a freshly generated world is semantically searchable the moment it lands. It is a total stage: it must never fail the world, so it catches its own errors and triages the summary three ways (misconfig→error, transient→warn, clean→info). Voyage spend is off the Anthropic cost cap, so the stage always reports zero cost regardless of how many rows it embedded — the cumulative cost check must never see Voyage spend.

Character-integration post-pass. Character integration inserts new PC-backstory facts onto existing world NPCs after the world-gen embed stage already ran — so those rows ship NULL-embedded. The processor runs a terminal embed post-pass (re-embed the world's NULL rows, no force) so the world stays searchable. It is non-fatal by construction: the integration is already committed and stage-completed by the time the post-pass runs, so a Voyage or DB error here must never flip the completed stage to failed — it catches and logs, with the same three-way triage.

Operational backfill. scripts/world-embed-backfill.ts (pnpm world:embed-backfill) is the out-of-band entry point — embed one world (--world <id>) or every world (--all), incremental by default or a full re-embed under --force. This is what recovers the NULL rows a transient Voyage degrade left behind.

Operating this piece

Backfill world embeddings

  1. To recover rows a transient Voyage degrade left NULL for one world: pnpm --filter @mythrun/backend world:embed-backfill --world <world-id>. The default (no --force) embeds only embedding IS NULL rows — cheap and safe to re-run.
  2. To sweep every world after a Voyage outage recovers: pnpm --filter @mythrun/backend world:embed-backfill --all.
  3. A full re-embed of the entire corpus (only after a model or dimension change) adds --force: ... world:embed-backfill --all --force. This re-embeds every fact and entity — a real Voyage rate and spend event. Run it knowingly, not casually.
  4. Each world logs a one-line JSON summary (embedded / leftNull / voyageErrors). A non-zero leftNull after a run means rows are still un-embedded — re-run once Voyage is healthy.

Populate the Voyage API key (staging)

  1. Terraform creates the secret shell (mythrun/staging/voyage-api-key) with a placeholder version — the app boots, but the first embed call 401s and the boot probe crashloops. The real value is set out-of-band.
  2. Mint a key in the Voyage dashboard, then: aws secretsmanager put-secret-value --secret-id mythrun/staging/voyage-api-key --secret-string <key>.
  3. Roll the ECS services so tasks pick up the new version: aws ecs update-service --cluster mythrun --service mythrun-staging-api --force-new-deployment (and the -worker service). The Voyage boot probe now passes; a previously-degraded worker boots clean.
  4. Backfill any worlds generated during the degraded window (see backfill world embeddings).

Run the real-Voyage retrieval smoke

  1. With VOYAGE_API_KEY set, pnpm --filter @mythrun/backend smoke:world-retrieval seeds a scratch world in mythrun_dev, embeds a tiny corpus through real Voyage, and asserts the pgvector round-trip: a semantically-near entity ranks first, a far entity over-pulls below it, and a secret-tier fact surfaces (proving over-pull).
  2. The smoke also drives the negative case: a deliberately invalid key must make the boot probe throw a classified config error — the "never silently un-embedded" guarantee. The script gates on the key (skips cleanly when absent) and tears down its scratch world.

Integration points

The substrate sits on the world-store schema (the vector(512) columns migration 026 adds to facts and entities) and its read SQL is one more namespace in the repository layer (repo.worldRetrieval). Embedding is triggered from the world-gen pipeline's terminal embed stage and the character-integration post-pass; the Voyage boot probe runs in both the worker and server boot sequences. The resolver barrel is the import surface for the Fast Thinker's world-knowledge lookups (live since MYT-72, behind the synchronous Slow-Thinker vet, with the MYT-73 working-set read-merge unioned in at the consumer). The Voyage key is a manual secret on the serving module, distinct from the Anthropic key the LLM client uses.

Resolver barrel (world/retrieval/index.ts)

Export What it does
createSearchResolvers(deps) Builds searchLore (facts ∪ entities, total → { hits, queryVec }; empty on failure) and findSimilarEntities (entity-only, throws).
charactersKnownTo(deps, entityId, opts) Both-direction relationship walk to a clamped depth; cycle-safe, min-depth deduped.
factionTree(deps, entityId) entity_hierarchy subtree with a truncated flag at the depth bound.
embedWorld(deps, worldId, opts?) Read → embed → write the world's facts + entities; returns an EmbedSummary.
LoreHit, EntityCandidate, KnownCharacter, FactionNode camelCase result types (the snake_case DB rows stay internal to the binder).
