Repository layer

The single seam every read and write to Postgres flows through. Each table cluster is authored once as a binder closure over a ClientLike; createRepo(pool) binds the pool for plain reads and single-statement writes, and repo.transaction(tx => …) binds an in-flight transaction client for multi-table atomic work. Callers say repo.users.create(...), never pool.query(...) directly.

How it fits together

createRepo(pool) in backend/src/repo/index.ts is the entry point. It takes a pg.Pool and returns the table-cluster namespaces — one per cluster (users, worlds, campaigns, sessions, sessionPreps, credits, invites, characters, characterConcepts) plus the former standalone Tier-2 modules (entities, facts, proseKernels, relationships, entityHierarchy, statBlocks, purchases, userSubscriptions, stripeEvents, billingHistory, pipelineRuns) and the world-gen support namespaces the prep pipeline added (randomTables, settings, and worldInventory — the last a composite multi-table read that replaced the former repo.pool escape hatch) plus worldRetrieval (the world-store retrieval binder — pgvector cosine search and recursive-CTE graph walks) — and a transaction method. The return type is exported as type Repo; the backend runtime's AppDeps carries it alongside pg, the two Redis clients, and the derived redisKeyPrefix (${MYTHRUN_ENV}:${REGION_PREFIX}:) every Redis-keyed subsystem prepends to its keys; server.ts threads createRepo(pgRef) into buildApp on both boot paths.

One method body, two bindings: the ClientLike binder

Each namespace is authored once as a binder closure — worldsNs(c: ClientLike), creditsNs(c), and so on, one per backend/src/repo/*.ts file — that captures a ClientLike and returns the typed methods for its table. The method bodies call c.query(...); they never see whether c is a pool or a single connection. The binding happens in two places. createRepo(pool) runs every binder over the pg.Pool, producing the default surface: each method acquires-and-releases a pooled connection per call, the right shape for plain reads and single-statement writes. repo.transaction runs the same binders over an in-flight transaction client (its TxRepo shape), so the same method bodies write inside one BEGIN/COMMIT.

One binder, not two factories — the alternative was a pool-bound factory and a parallel tx-bound factory per table, the SQL duplicated between them. Binding the same closure over a ClientLike (the structural subset of pg.PoolClient both Pool and PoolClient satisfy) means the SQL, parameter binding, and snake-to-camel mapping live exactly once. createRepo picks the pool; repo.transaction picks the connection; the method body is indifferent.

repo.transaction: the multi-table atomic-write primitive

repo.transaction(async (tx) => { … }, opts?) (in backend/src/repo/_client.ts) is the one sanctioned way to write across several tables atomically. It acquires a pooled connection, issues a BEGIN with a per-call SET LOCAL prelude, binds the namespaces over that connection as tx, runs the callback, then COMMITs and releases. The callback writes only — every read it needs to make a decision happens through the same tx. Whatever it returns is handed back to the caller after the COMMIT, so post-commit side-effects (a BullMQ enqueue, an SSE publish) fire on the committed value rather than inside the open transaction. Returning the ROLLBACK sentinel discards the transaction as a clean no-op — no thrown error, no webhook retry — for the idempotent-discard paths (a Stripe duplicate redelivery, an unknown event type). A throw rolls back and propagates.

Slow I/O stays OUTSIDE the callback — MYT-55's staging smoke crashed the world-gen worker when an LLM call ran inside a held transaction: RDS sets idle_in_transaction_session_timeout = 60s, so any model call exceeding it triggered FATAL: terminating connection due to idle-in-transaction timeout mid-stream. The contract is that callers do the slow work (LLM, Stripe) before calling repo.transaction; the callback holds writes and nothing else. The same incident is why the return-value-after-commit shape exists (MYT-56): a queue.add inside the callback could enqueue work referencing a row the COMMIT then failed to persist.
Per-call SET LOCAL, not a baked-in default — the audit found isolation and timeout knobs varying by site (register, billing webhook, world-create each differ). opts carries isolation (default 'read committed', always pinned explicitly so a pool-config drift can't silently change the contract), lockTimeoutMs, and statementTimeoutMs; unset timeouts inherit the server default. The prelude is emitted as one multi-statement string so the SET LOCALs land in the same transaction as the BEGIN — a SET LOCAL with no active transaction is a silent no-op. The captured tx handle is fenced after the transaction settles: touching it post-commit throws rather than corrupting the recycled pooled connection.

Two idioms: composable binders vs. self-managing methods

Most methods are composable: they run over whatever ClientLike they were bound to, so they appear on both the pool surface and inside repo.transaction's tx. A few methods own their connection and lock discipline outright and are NOT composable — they're added only on the pool surface by createRepo, never on TxRepo. These are credits.atomicDebit / grant / tryDebitForSession, invites.create / acceptInvite, users.getByCognitoSubWithTimeout, and the lock-order-sensitive refund path. Each opens its own connection, runs its own BEGIN + bespoke SET LOCALs, takes its row lock, and commits — a self-contained transaction the caller doesn't compose.

Self-managing methods can't go inside tx — because they live only on the pool surface, TxRepo = ReturnType<typeof bindTx> mechanically excludes them: calling tx.credits.atomicDebit is a compile error, not a silent second-connection write that escapes the caller's transaction. The one composable exception is credits.grantInTx(tx, input) — it deliberately takes a caller's client so the webhook dispatcher can run the stripe_events idempotency check, the audit-row write, and the credit grant under one COMMIT. The pool-bound grant is the right shape for one-off route-handler grants; the composable grantInTx is the right shape for a caller who already owns the transaction.

The enforced-ignorance split: getSnapshotSummary vs. getById vs. getWikiSummary

worlds.getSnapshotSummary(id) is the single-sourced home of the world-column allowlist the Fast Thinker is allowed to see. It SELECTs only id, name, concept, tone, themes, era, vocabulary_registry and returns a WorldSummary — a type that structurally cannot hold the plot-bearing columns (key_tensions, political_summary, world_overview, geography_summary, starting_situations, follow_up_questions). worlds.getById returns the full World row, plot columns included, and is the prep / Slow-Thinker tier read. The composite world-snapshot view (worldSnapshotView.fetch) composes getSnapshotSummary, then re-projects it to the plot-safe WikiWorldSummary shape before the wire (myth-0xwos follow-up) — dropping concept, since the snapshot endpoint is now member-readable.

MYT-74c adds a third world-summary projection: worlds.getWikiSummary(id), the home of the even-narrower player allowlist. It returns a WikiWorldSummary of id, name, tone, themes, era, vocabulary_registry — getSnapshotSummary's list minus concept. The owner's raw freeform concept seed can contain plot, so no player-facing wire carries it: the play wiki composes getWikiSummary directly, and the member-readable world-snapshot view re-projects into the same plot-safe shape (myth-0xwos follow-up). Like getSnapshotSummary, the SELECT lives once in worlds.ts, so widening the player wire is a deliberate edit, never an accidental SELECT *.

The allowlist has exactly one home, per audience — enforced ignorance is a hard boundary (CLAUDE.md Non-Negotiable Principle), and a hard boundary needs one definition, not a column list copied into every player-facing read. Pointing a Fast-Thinker world read at getById re-exposes the plot fields, so the split makes that a type error rather than a silent leak: a player-facing caller takes WorldSummary or WikiWorldSummary, neither of which can carry the heavy plot columns. Since both the snapshot and the play wiki are now member-readable, neither serves concept on the wire — the wiki composes getWikiSummary and the snapshot view re-projects into that same plot-safe shape — so the split is composition, not audience. concept survives only in the repo-layer WorldSummary (never surfaced to a client), and a future widening is a deliberate, reviewed edit to one projection rather than a leak across a shared one.

The player campaign-wiki view

campaignWikiView.fetch(client, worldId) in backend/src/repo/campaign-wiki-view.ts is the composite read behind GET /api/campaigns/:campaignId/wiki — the members' known-tier view of the world they are playing, which grows as each session promotes facts into known. It is a deliberate sibling of worldSnapshotView, not a reuse: it composes the narrow getWikiSummary (with the registry entries further filtered to known), the known entities (id/name/type via entities.listByWorld(worldId, {accessLevels:['known']})), their live known facts (facts.listByEntities(ids, {accessLevels:['known'], liveOnly:true})), and the known-tier relationships among them (relationships.listAmong). It attaches no prose kernels and no stat blocks.

A separate view, because the snapshot carries more than a play wiki should — the tempting shortcut is to point the play wiki at worldSnapshotView. The two now share the same plot-safe world summary (both re-project to WikiWorldSummary, so concept is on neither wire since myth-0xwos), but the snapshot still attaches per-entity prose kernels and stat blocks — FT-facing generation artifacts that are not tier-gated, so a play-promoted secret entity's kernel is its full characterization blob. The wiki view therefore composes its own narrower surface and attaches neither kernels nor stat blocks. The two reads are distinct surfaces for distinct moments in a campaign's life, exactly like the three world-summary projections above (the split is composition, not audience). The reconcile page covers the route's member-auth, no-bypass, and readiness gates.

The CLAUDE.md mandate and the no-raw-db-access lint rule

The mandate is concrete: every TS file outside backend/src/repo/ that reads or writes the database calls repo.<namespace>.<method>, and multi-table atomic work goes through repo.transaction. No raw pool.query(...), no hand-managed BEGIN/COMMIT in route handlers, services, or workers. The repo layer is what makes that enforceable — one place to grep for SQL changes, one place where parameter binding is audited, one place where the updated_at = now() bump is guaranteed on every UPDATE.

The lint half is the custom rule mythrun/no-raw-db-access (backend/eslint-rules/no-raw-db-access.cjs), registered under the mythrun plugin in the repo-root eslint.config.js. It bans, outside an allowlisted set of files (the repo/db layer plus the boot entrypoints that legitimately own a pool): raw .query / .connect calls, destructured or aliased forms of them, value-importing pg (type-only imports compile away and are fine), bare BEGIN / COMMIT / ROLLBACK / SET LOCAL string literals, a SQL-string pass-through helper that would launder raw access through the allowlist, and a queue.add / .publish / .emit side-effect lexically inside a repo.transaction callback (the MYT-56 shape).

Set to 'error' — the migration is complete — the unification is done. Every production DB access now goes through repo.X / repo.transaction; the count of raw-SQL sites outside the repo/db layer is zero. With the consumers fully migrated, the rule flipped from 'warn' to 'error': a raw .query / .connect call, a value-import of pg, or a bare tx-control literal outside the repo/db layer is now a build failure, not a warning. The only carve-outs are test files (which legitimately seed prerequisite rows via raw pool.query / redis, exempted via a per-file override) and the @mythrun/wiki build tooling (which introspects the live schema via raw DDL queries and lives under its own docs/wiki/eslint.config.js root). A tripwire, not a wall — the rule matches the literal shapes that caused the MYT-55/56 incidents, not full dataflow; the documented residual evasions are listed in the rule's own header.

Namespace boundaries: shipped vs. deferred

Spec §5 of the Backend Core architecture lists 25 namespaces. The layer ships the ones with a live consumer and defers the rest. The unification folded what used to be two separate kinds — pool-bound table-cluster factories and standalone transaction-scoped Tier-2 modules — into one binder shape, so createRepo now exposes them all on a single surface: users, worlds, campaigns, sessions, sessionPreps, sessionMessages, sessionParticipants, credits, invites, characters, characterConcepts, plus the world-content and billing namespaces (entities, facts, proseKernels, relationships, entityHierarchy, statBlocks, purchases, userSubscriptions, stripeEvents, billingHistory, pipelineRuns), plus the world-gen support namespaces the prep pipeline's migration off raw SQL added (randomTables for the stage-5 table writer, settings for the cost-cap policy reads, and worldInventory for the composite world-dump read). The webhook handlers, billing routes, and world-gen worker consume them. sessionMessages and sessionParticipants landed with their first consumer, the multiplayer session transport (append-only transcript + per-session participant rows), and grew with the turn engine: sessionMessages is now the only transcript store, so it gained the PG-direct DM-turn surface (listFtContextRows / turnRowsExist / appendDmTurn) and characters gained the session-roster resolution the Fast Thinker's skill checks read (findSessionParticipantCharacterByName / listSessionParticipantCharacters) plus the class/background roster the Slow Thinker reads for its world-state block (listSessionParticipantRoster, MYT-69 — a new read, leaving the FT-hot-path sibling untouched). The namespaces still unfilled by any consumer are tracked as beads under the repo-deferred label and ship batched with their consumers.

Producer batched with consumer — designing primitives without the consumer in view produces guesses. credits shipped on the same principle: the atomic-debit pattern was held back from the v1 repo until MYT-40 picked up Billing's first consumer-facing surface, because designing grant / debit / getBalance as separate primitives without the spend path in mind is exactly how a TOCTOU race ships. invites followed in MYT-38 alongside its routes consumer; the multi-step acceptInvite transaction (lock invite → membership check first → expiry check → cap check → INSERT with ON CONFLICT → uses-bump) only fell into shape with the HTTP layer co-designed. characters was landed ahead of MYT-53's campaign-setup consumer for a different reason: migration 009 reshaped the storage contract (user-owned + join table), and authoring the campaign-setup pipeline against the final shape was cheaper than chasing schema churn mid-milestone. The deferral list is in the v2 design spec; bd list --label=repo-deferred is the live view.

Within each shipped namespace, the method set is similarly scope-cut. worlds.fork is deferred to the prep pipeline — fork semantics involve entity copy and fact deduplication that belong with the pipeline that owns them. sessions.updateRunningSummary is deferred to the Slow Thinker work that consumes it. users.softDelete and campaigns.transferOwnership follow the same rule: no consumer in flight, no API design today. characters ships the portable-shape primitives (create, addToCampaign, listForCampaign, findUserCharacterForCampaign); MYT-53's character-creation processor reaches the four satellite tables (skills / features / equipment / spells) and the characters.entity_id backfill directly through its per-stage SQL rather than through a satellite repo, because those operations are owned end-to-end by the stage handlers. character_concepts follows the rule: its own repo (backend/src/repo/character-concepts.ts) ships under MYT-53 with exactly the primitives the routes and the worker need (upsert, getByCampaignAndUser, listSubmittedByCampaign, countCompleted, the four status flips, and the composable flipSubmittedToProcessing), because the concept lifecycle has a real consumer to shape it against. Cluster C dropped that flip's explicit BEGIN/COMMIT so it composes into POST /characters' repo.transaction (upsert → flip → seed the character_concept recovery row), with the BullMQ enqueue moved to AFTER the commit (the MYT-56 shape).

Camel out, snake in: mappers at the boundary

The schema is snake_case (cognito_sub, created_by, geography_summary); the TypeScript surface is camelCase. Each table has two interfaces: a XxxDbRow in mappers.ts matching what pool.query returns, and a Xxx in types.ts that callers see. A toXxx function bridges them — invoked once per row at the repo boundary.

Explicit mappers, not a pg-types parser — node-postgres lets you register a type parser that rewrites every result row globally. Tempting, but global: it would convert keys for every query in the process, including future code paths that genuinely want raw pool.query for diagnostics or one-off scripts. Keeping the conversion at the repo boundary scopes it to where the API contract is camelCase and leaves the rest of the system alone.

Update input types are spelled out (not Partial<Pick<User, …>>) so exactOptionalPropertyTypes semantics are intentional: each key is omitted to leave the field unchanged, or supplied with a value to set it. The identity field cognitoSub is never in the Update type — mutating it would break Cognito linkage in ways the layer above doesn't want to think about. username and displayName are mutable through Update because the user owns them; the schema catches case-insensitive collisions via users_username_lower_key if a rename conflicts.

Narrowing helpers for enum-like CHECK columns

Several columns in the schema are TEXT with CHECK constraints enforcing a small enum: worlds.status, worlds.moderation_status, campaigns.status, sessions.status, credit_ledger.credit_type, credit_ledger.source_type, campaign_members.role. The schema guarantees the SQL invariant, but the mapper still refuses to bare-cast row.status as 'generating' | 'complete' | 'failed'. Instead, a small helper validates and narrows: 

function toCampaignMemberRole(v: string): 'owner' | 'player' {
  if (v !== 'owner' && v !== 'player') {
    throw new Error(`unexpected campaign_members.role value from DB: ${v}`)
  }
  return v
}
Defense in depth, not paranoia — if a future migration adds a new role option but the TS interface stays at 'owner' | 'player', a bare cast would silently mistype every row. The helper fails loudly at the boundary and the test suite or production logs flag it before the bug spreads. Every CHECK-constrained text column gets one of these.

UUIDv7 in its own seam

backend/src/repo/uuidv7.ts is a one-line wrapper: export const uuidv7 = (): string => uuidv7Pkg(). Every create method generates the id app-side via this function — id UUID PRIMARY KEY in the schema declares no default. Time-ordered ids give clean B-tree locality on PK indexes, which matters for the high-write-rate tables (session_messages, credit_ledger) the future namespaces will land.

The wrapper exists so tests that need deterministic ids can vi.mock('./uuidv7.js'), and so a future swap to a different UUIDv7 library is a one-file change. The migration runner's CLI block uses the same wrapper for its runId — single seam, no second import path of the underlying package.

INSERT … RETURNING *: one round-trip, callers get the row

The Backend Core spec example shows create returning Promise<string> (the new id). The repo deviates: every create uses INSERT ... RETURNING * and returns the full mapped row.

RETURNING *, not just the id — every consumer the next handful of tickets will add (signup flow, prep-pipeline kickoff, session start) immediately needs the created_at, the defaulted status, the database-side now() for updated_at. Returning only the id forces a refetch round-trip. Returning the full row costs marginal extra bandwidth and matches what callers want.

UPDATE … COALESCE($n, col): fixed-form patches

Update methods take a partial patch and emit a single fixed SQL string. Each mutable column is written as col = COALESCE($n, col) — the parameter is either the new value or null, and null means "don't change this field." updated_at is always set to now() in the same statement. 

UPDATE users
   SET username           = COALESCE($2, username),
       display_name       = COALESCE($3, display_name),
       stripe_customer_id = COALESCE($4, stripe_customer_id),
       free_trial_used    = COALESCE($5, free_trial_used),
       updated_at         = now()
 WHERE id = $1
 RETURNING *
Fixed COALESCE, not dynamic SQL — building a SQL string at runtime by walking the patch object's keys is the alternative; it gives "only update what was supplied" without COALESCE's NULL-as-sentinel weirdness. The cost is real: every dynamic builder is an injection surface to audit, an unstable EXPLAIN plan to debug, and a typing puzzle (TypeScript can't tell what columns are in patch). The fixed form has one stable plan, parameterized binding for free, and the column whitelist is in the SQL itself.
Mandatory updated_at = now() on every UPDATE — the schema declares updated_at TIMESTAMPTZ NOT NULL DEFAULT now() but has no BEFORE UPDATE trigger. Forgetting the bump leaves the column stuck at insert time forever, silently breaking any "what changed since" query downstream. Each namespace's integration test asserts updated_at advances after update; the sessions table is the lone exception (no updated_at column, only started_at + ended_at).
COALESCE caveat: nullable fields can't be cleared — passing { stripeCustomerId: null } to users.update is indistinguishable from omitting the key entirely; both encode as a SQL null parameter and the COALESCE leaves the column unchanged. This is a deliberate v1 trade-off, documented at the type site. When a real consumer needs to clear a stripe id (a customer-record reset, a refund-flow rebuild), the API grows a sentinel value or a dedicated clearStripeCustomerId() method — not before.

The boot gate's stub pool, composed

The boot gate has two paths. With BOOT_GATE_ENABLED=1, server.ts opens a real pool and calls createRepo(pgRef). With the gate off, fallbackStart constructs a stub pool whose query throws synchronously — and then calls createRepo(stubPool) over it. Any repo method invoked on that stub repo propagates the throw naturally, the same way it would for any other unreachable database.

Compose over the stub pool, don't Proxy the namespace layer — an earlier design used a Proxy to fake the entire { users, worlds, … } shape with throwing methods. The bug: repo.users.create() would throw on repo.users (a function-shaped Proxy trap), not on create(), and the error message would say "namespace not available" instead of "repo unavailable: BOOT_GATE_ENABLED is off." Composing createRepo over the stub pool inherits the pool's existing throw contract; no special-casing in the repo factory.

Per-namespace shape

users — create, getById, getByCognitoSub, getByCognitoSubWithTimeout, getByUsername, update; plus the standalone findOrCreateStripeCustomer(pool, stripe, userId) helper exported alongside the closure. Each getByX maps 1:1 to a column with an index that supports it (or, for getByUsername, the users_username_lower_key expression index); adding a method is the deliberate act of sanctioning a new lookup path. A generic getBy(filter) would silently accept filters with no supporting index — a sequential-scan trap that wouldn't surface until production load — and would force readers to inspect every call site to learn which lookup shape was used. We accept the small cost of "several methods instead of one" to get index-as-API-surface and exact searchability.

findOrCreateStripeCustomer is a three-phase prefetch-then-write — the helper has to call Stripe's customers.create with an idempotency key, and that SDK call cannot run inside a held DB transaction (a Stripe outage would pin the PoolClient). Phase 1 reads the existing stripe_customer_id in a short tx; if populated, return immediately. Phase 2 calls Stripe outside any tx, deterministic idempotency-key (customer_for_${userId}) so concurrent racers all hit the same Stripe-side record. Phase 3 opens a short tx with the MYT-40 timeout discipline, re-reads the row FOR UPDATE, and either uses a racer's value (the cus_* we just minted becomes a Stripe-side orphan) or writes our own. The helper is exported as a function rather than as a method on the closure so the billing routes can call it without going through the closure's pool-binding.
getByCognitoSubWithTimeout wraps the read in a transaction — the requireOnboarded hook calls this on every protected request to confirm a real users row exists for the caller's cognitoSub. A wedged Postgres would otherwise pin the request thread until pg's default statement_timeout fires (or never, if it isn't set). The method opens a dedicated client, runs BEGIN; SET LOCAL statement_timeout = '200ms'; + the SELECT, commits, and releases — bounding any single lookup to the configured budget. SET LOCAL only takes effect inside a transaction, so the BEGIN/COMMIT wrapper isn't optional even though the read itself is single-statement. SQLSTATE 57014 (statement_timeout) maps to a LookupTimeoutError the route layer translates to a 503.

getByUsername uses WHERE LOWER(username) = LOWER($1) so the users_username_lower_key expression index serves the lookup directly — case-folding on both sides keeps the planner from falling to a sequential scan. The case-insensitive uniqueness story is in the schema page's identity-cluster section; the repo simply consumes that invariant.

worlds — create, getById, getDemo, listByUser, update, updateStatus, incrementForkCount. updateStatus is a one-purpose UPDATE on status alone; the prep pipeline calls it many times per run, and a dedicated method keeps pipeline tracing legible. listByUser is the simple ownership filter WHERE created_by = $1 ORDER BY created_at DESC — no JOIN. getDemo returns the singleton row whose is_demo=true flag is pinned by the partial unique index idx_worlds_one_demo from migration 008; the trial entry-point uses it as the fork source for new-user sessions.

campaigns — create, getById, listByUser, update, plus the membership methods: addMember, getMembership, getOwner, listMembers, and the MYT-67 countAcceptedMembers. listByUser joins campaign_members directly in SQL to filter to "campaigns I'm a member of with an accepted invite." addMember uses INSERT … ON CONFLICT (campaign_id, user_id) DO NOTHING RETURNING * so a re-add is idempotent — when the conflict swallows the row, the method falls through to a follow-up SELECT and returns the existing membership. listMembers joins users for username + display_name and filters out suspended accounts so a banned member doesn't surface in another player's roster. countAcceptedMembers counts only invite_accepted = true rows — the DM trigger's solo-vs-multiplayer gate needs the accepted count, not the unfiltered listMembers length, so a pending invite doesn't make a solo game look multiplayer.

Membership methods on campaigns, not their own namespace — the v2 namespace plan reserved a campaign_members namespace, but membership is read and written exclusively in service of campaign-scoped operations (owner check, member list, invite acceptance). A separate namespace would force every consumer to import two factories and reason about ordering between them. Keeping the methods on campaigns matches how callers think — "what's true about this campaign" — and lets the lock-order convention (campaigns → invites → members) sit naturally inside one factory's transactions.

sessions — create, getById, getActiveByCampaign, getMostRecentByCampaign, listByCampaign, update, recordUsage, budgetSummary, markReconciled, plus MYT-74b's markEnded, writeAnalysis, and getPriorContextForPrep. getActiveByCampaign uses LIMIT 1 defensively — the partial-unique index idx_sessions_one_active guarantees at most one active row per campaign, but the LIMIT 1 at the SQL site makes the contract self-documenting. recordUsage + budgetSummary are the per-session cost-tracking primitives MYT-43 added; the cluster has its own narrative on the billing-metering page. The remaining methods are the end-of-session primitives. getMostRecentByCampaign + markReconciled are MYT-74a's: getMostRecentByCampaign backs the /start reconcile-pending interlock, and markReconciled is the conditional UPDATE … SET reconciled_at = now() WHERE id = $1 AND reconciled_at IS NULL — it returns the rowCount so the reconcile commit can use it as an idempotency mutex (0 rows → another execution already reconciled → roll back). MYT-74b adds three more in the same conditional shape: markEnded (the finalize's flip to ended only when not already ended, returning the rowCount so session_end broadcasts exactly once), writeAnalysis (the recap + handoff write, gated on summary IS NULL so a retry is idempotent), and getPriorContextForPrep (the prep's newest-first read of prior ended sessions with a written analysis).

sessions.update doesn't bump updated_at — the sessions table doesn't have an updated_at column at all (only started_at + ended_at, which carry the lifecycle a session row needs). The "every UPDATE bumps updated_at" rule applies wherever the column exists; this one is the documented exception. session_usage rows are the same: their created_at stamps the first recordUsage call; subsequent UPSERTs increment counters in place without touching it.

recordUsage and budgetSummary

recordUsage(sessionId, model, deltas) writes per LLM call. The function computes the call's USD contribution at write time via computeCostUsd, then runs an UPSERT against session_usage keyed on session_id: first call inserts a row, subsequent calls increment the running totals. The post-update row is returned, so the Session Runtime can compute the wrap-up signal (“did we just cross 80% of the cost cap?”) inline without a second round-trip. session_usage keeps three input-side token classes as separate columns (input_tokens, cache_write_tokens, cache_read_tokens) alongside output_tokens and estimated_cost_usd; the schema page covers the column shape.

UPSERT keyed on session_id, not append-per-call — per-call rows would inflate the simplest receipt query (“what did this session cost?”) from a SELECT to a SUM-over-thousands-of-rows and add a hot-path INSERT per turn. The single-row UPSERT is the cheapest shape that still answers every consumer question; per-model breakdown is deferred until a real analytics consumer earns it. The idx_session_usage_one_per_session partial unique index from migration 008 makes the ON CONFLICT (session_id) DO UPDATE work and prevents accidental dup rows.

budgetSummary(sessionId) is the read-side for non-hot-path consumers (receipts, dashboards, end-of-session reports). Plain SELECT, returns the row or null for sessions with no LLM calls yet. The Session Runtime hot path doesn't call it — it uses recordUsage's return value, saving one round-trip per turn.

Bad sessionId is a tripwire, not a silent no-op: recordUsage's SELECT-FROM clause returns zero rows if the session was deleted or never existed, and the function throws SessionNotFoundError from backend/src/repo/sessions-errors.ts. The hot path should never see this; it's a caught-loud signal for upstream bugs that route an LLM call to a fictional session. recordUsage is also non-idempotent under retry — a retried call double-counts. The Session Runtime is responsible for not retrying after partial failure; per-call reportingId + composite unique constraint is the documented path if real retry-safety is ever needed.

credits — balance, grant, atomicDebit, tryDebitForSession, listEntries, plus standalone grantInTx + recordClawback exports for transaction composition. The full credit-ledger story has its own section below; the short version is "balance is a SUM over an append-only ledger; debits go through a transaction-scoped lock anchored on the user row, not on the ledger."

invites — create, ensurePrimary, getByCode, getCodePreview, listForCampaign, revoke, acceptInvite. Invites are how new players join a campaign in MYT-38's onboarding flow; getCodePreview is the only read this layer exposes to unauthenticated callers (the public preview the SPA shows on the join page before the user signs in). The rest are authenticated. Two methods are non-trivial: acceptInvite has its own section below, and ensurePrimary (myth-y5c4q) is an idempotent get-or-create for the campaign's one primary invite — the durable share link — run under a per-campaign lock so concurrent owner tabs collapse to a single row, with the migration-036 partial unique index (is_primary) as the DB backstop. revoke clears is_primary alongside expiry, so the "an is_primary=true row is the active primary" invariant is maintained in this layer.

characters — create, addToCampaign, listForCampaign, findUserCharacterForCampaign. The split mirrors migration 009's two-step storage contract: create writes the user-owned row; addToCampaign writes the campaign_characters join row. create takes a ClientLike rather than reading from the closure's pool (the same shape users.create uses for the onboarding flow) so callers can compose it with their own transaction. addToCampaign opens its own short transaction off the pool because the join INSERT is a single statement and the typed unique-violation translation only needs to span that one statement. listForCampaign joins through campaign_characters ordered by joined_at, id; findUserCharacterForCampaign is the per-player lookup the read routes use to answer "what character does this player have in this campaign?" In practice MYT-53's character-creation processor reaches the characters, campaign_characters, and four-satellite-table writes through its own per-stage SQL (the whole sheet is one tightly coupled transaction inside character-sheet.ts); the typed characters repo primitives are the read-side surface today. MYT-70 added a sibling binder, charactersLedgerNs (characters-ledger.ts), composed into repo.characters so its methods surface as repo.characters.* / tx.characters.* — the scoped LedgerOps projection the Rules Lawyer mutates. It lives in its own module purely to keep characters.ts under the 400-line cap; the narrative for the guard-predicate debits, the §5a HP single owner, and the per-turn snapshot is on the character ledger page.

The Rules Lawyer receives LedgerOps, not the whole repo — the ledger binder is exposed as a narrow interface (LedgerOps) the turn worker hands the FT's resolvers, the same scoped-boundary discipline as the skill-check resolver's mechanical-reads projection. A debit is a single guard-predicate UPDATE … WHERE <guard> RETURNING (rowcount 0 = adjudicated rejection — no SELECT-then-UPDATE), and the multi-row writes (the HP↔unconscious pair, the party-wide rests) run on a tx-bound client so the mutation and its ledger_events journal row commit atomically.
Translate 23505 by constraint name, not by FK shape — the join's two UNIQUEs ((campaign_id, character_id) and (campaign_id, user_id)) both produce SQLSTATE 23505 on collision, and a caller needs to distinguish them: the first means "this character is already in this campaign" (idempotent retry), the second means "this user already has a different PC in this campaign" (real conflict). The repo inspects the pg error's constraint field directly and maps to CharacterAlreadyInCampaignError vs UserAlreadyHasCharacterInCampaignError. The Postgres-default UNIQUE constraint names (campaign_characters_campaign_id_character_id_key and campaign_characters_campaign_id_user_id_key) are stable because the schema declares the constraints inline rather than via CREATE UNIQUE INDEX — renaming requires a deliberate ALTER CONSTRAINT migration.

The credits namespace: append-only ledger with an atomic spend

credit_ledger is the only place credit balance lives — the schema page covers the table shape and migration 004's defense-in-depth invariants. The repo surface the rest of the system sees is four pool-bound methods plus two transaction-bound helpers (grantInTx + recordClawback) exported as standalone functions.

balance(userId, type) is a single read: SELECT COALESCE(SUM(amount), 0) filtered by user_id, credit_type, and expires_at IS NULL OR expires_at > now(). Expired grants drop out; debits stay in (they're immutable consumption). Two credit types live on the same table — session and world_gen — and they're isolated: a session debit never sees world-gen grants.

grant(input) writes a positive-amount entry with source_type in purchase | subscription | gift | trial | refund; the closure-bound version opens its own short tx with the user-row lock. atomicDebit(input) writes a negative-amount entry with source_type = 'debit'; the amount is a positive integer in the input, recorded as -amount in the row so polarity invariants hold at the DB layer. Both methods take the per-user transaction lock described next. atomicDebit returns { entry, consumedSourceType } — the second field is the source-type class of the oldest unexpired positive credit at debit time, used by the Session Runtime as the trial-mode signal under MYT-43's mutual-exclusion invariant.

Trial-burn fires inside grantInTx, not inside atomicDebit — earlier drafts considered a "trial-FIRST consumption" rule that made atomicDebit drain trial credit before paid credit. Replaced by mutual exclusion at grant time: when grantInTx is called with sourceType in 'purchase' | 'subscription', it sums the unexpired trial balance for the same (userId, creditType) and writes a single negative-amount debit row burning it. The burn's source_id is a deterministic UUIDv5 derived from (userId, creditType) against a Mythrun-pinned namespace (backend/src/repo/uuidv5.ts); webhook redelivery is idempotent via ON CONFLICT … DO NOTHING. The billing-metering page covers the UX motivation.

tryDebitForSession(userId, sessionId) is the wrapper the future Session Runtime's session-start route will call. It debits exactly one session credit, keys idempotency off sessionId, and translates InsufficientCreditsError into a typed { ok: false, code: 'insufficient_credits', available, required } result the route layer maps to 402 Payment Required. Other errors (UserNotFoundError, IdempotencyConflictError, DebitTimeoutError) still throw — the typed result is for the gentle out-of-credits UX path only. The success branch carries the same consumedSourceType the wrapped atomicDebit returns.

grantInTx + recordClawback are standalone exports for webhook handlers — the closure's grant opens its own connection and tx, which is the right shape for one-off grants from route handlers (a manual gift) but the wrong shape for the webhook dispatcher's already-open tx. The standalone grantInTx(tx, input) takes a ClientLike and runs the user-row FOR UPDATE lock, the trial-burn for paid grants, and the grant INSERT — all on the caller's connection (Postgres tuple-lock re-entrancy lets the lock re-acquire safely on the same xid). recordClawback(tx, input) is its negative-amount sibling for refund events: writes source_type = 'debit' with a negative amount and the originating grant row's UUID as the idempotency key. Both let the webhook handlers compose one transaction across the stripe_events idempotency check, the audit row write, and the credit grant — a single COMMIT covers all three.
Lock the users row, not the ledger — the natural-feeling design is SELECT … FROM credit_ledger … FOR UPDATE, then read the balance, then INSERT. It doesn't work: PostgreSQL row locks are physical, not predicate. FOR UPDATE on a query that returns zero rows locks zero tuples, so two concurrent debits on a fresh user both see balance = 0 and both succeed. The fix is anchoring on a row that always exists — SELECT id FROM users WHERE id = $1 FOR UPDATE — which serializes every concurrent atomicDebit and grant for that user. The first transaction takes the lock, reads the balance, inserts the debit, commits; the second one waits, then sees the new balance. grant takes the same lock for symmetry: any operation that could decrease available balance (today: atomicDebit; future: refund clawbacks) goes through the same gate.

Each transaction starts with three SET LOCALs: transaction_isolation = 'read committed' (defense in depth — the pool default already provides this; the SET LOCAL makes it per-transaction explicit so a future pool-config drift can't silently change the contract); lock_timeout = 1s (cap on how long the FOR UPDATE waits before giving up — bounds pool exhaustion under load); and statement_timeout = 5s (cap on the whole transaction, the second of two distinct failure modes). Both timeouts surface as the same error subclass to callers; the SQLSTATE distinguishes them in logs.

atomicDebit requires a sourceId — the per-user idempotency key. The method does the idempotency check first, before the balance check: a retry of the same (userId, creditType, sourceId) returns the prior entry without inserting a second row. A different amount with the same key throws IdempotencyConflictError; the same amount returns the original. The DB-level uniq_credit_ledger_debit_idempotency partial-unique index from migration 004 is the safety net for any future caller that bypasses the repo.

Don't gate on balance(); atomicDebit IS the gate — the tempting consumer pattern is "check balance, decide whether to act, then debit." That's a TOCTOU race regardless of how the lock is implemented: the balance read and the spend decision happen outside any transaction. The repo's contract is that atomicDebit either succeeds and returns the new entry, or throws InsufficientCreditsError with the actual available balance — callers branch on the result, not on a prior balance() call. The error class is exported from credits-errors.ts for HTTP-layer mapping.

Errors callers narrow on: InsufficientCreditsError (balance check failed — available + requested in the error), IdempotencyConflictError (same sourceId, different amount), UserNotFoundError (the user-row anchor came up empty — the spec's required invariant before any other check), and DebitTimeoutError (lock or statement timeout fired — sqlstate 55P03 or 57014 mapped to one error class). Every error path ROLLBACKs the transaction explicitly so connections never leak in idle in transaction state; the integration test asserts this on every error class. The sessions namespace has its own typed error: SessionNotFoundError from sessions-errors.ts, thrown by recordUsage when the SELECT-FROM clause matches zero session rows.

listEntries(userId, opts) is the audit view — DESC by (granted_at, id), default limit 100 (overridable; null means no LIMIT). It includes expired entries, unlike balance(), because the audit story is "what happened to this user's credits over time," not "what can they spend right now."

The world-content namespaces: streaming stages share a caller-owned transaction

MYT-52's streaming pipeline added five more namespaces consumed by the prep worker's wave-2/3/4 stage handlers: entities, proseKernels, facts, relationships, and entityHierarchy. Like every namespace they're now authored as ClientLike binders, so they're bound on the pool surface by createRepo and equally over an in-flight transaction client. The stages exercise the transaction-client binding: each world-gen stage handler does its LLM work first, then opens a single repo.transaction(tx => …) and runs every write through that tx — INSERT, UPDATE, DELETE, all on the same connection. A handler throw cascades to a single ROLLBACK that unwinds all the stage's writes atomically.

Caller-owned transaction, not per-method txs — a streaming stage writes hundreds of rows: one entities + one prose_kernels + N facts per region/faction/location/NPC. If each method opened its own transaction, a stage failure midway would leave half the world's entities persisted without their facts and prose — visible to the client through a future read query, but unfinishable by any retry. One caller-owned transaction means the stage's commit boundary is the same as the cost-cap check's view of "completed work."

entities exposes insert(client, input), findByWorldAndName (case-sensitive, returns null on miss), listByWorld(client, worldId, opts?), and — MYT-72 — findIdByWorldAndNormalizedName(worldId, name), a world-scoped lower(btrim(name)) exact-match resolver returning just the entity id (null on miss, never fuzzy) that the Fast Thinker's lookup tools call to turn a colloquial name into the id a graph walk seeds from. The insert caller supplies the id (UUIDv7-generated app-side per the uuidv7 seam) so the stage's finalized-event payload can reference the row before the INSERT lands. InsertEntityInput also requires createdIn: string — a provenance tag the caller stamps to mark which pipeline stage (or play-runtime path) wrote the row. World-gen callers pass 'stage:world_and_factions' (stage 2), 'stage:locations_and_npcs' (stage 3), and 'stage:entity_consolidation' (stage 4b's ghost entities); the future Scribe runtime will write 'session:<uuid>'. Migration 017 backfills every existing row to 'stage:legacy' via the column DEFAULT. listByWorld is what stage 3's parent resolver calls in pass 2 to build the name → entityId map, and what stage 4 calls at stage start to build the entity-inventory the prompt feeds into the LLM. The optional opts.accessLevels argument (added under myth-exac) constrains results to the named tier set — the world-snapshot view passes ['known'] in the standard case and ['known', 'discoverable', 'secret'] when dev-mode bypass is in effect. entity_type is constrained by the table's CHECK to 'npc' | 'location' | 'faction' | 'item'; regions are persisted as type='location' per the pipeline spec's flat enum. entities.access_level defaults to 'known' at insert time and is CHECK-constrained to the same three-tier vocabulary as facts.access_level. MYT-74a adds markTouchedByPlay(ids) — the end-of-session reconcile calls it to flag every entity it minted or matched as modified_by_play = true in one statement — and MYT-74c adds the sibling promoteToKnown(entityIds): UPDATE entities SET access_level='known', updated_at=now() WHERE id = ANY($1) AND access_level <> 'known', returning the rowCount. The reconcile commit calls it on the distinct owning entity ids facts.promoteToKnown returned, so an entity follows its promoted fact into the known tier (else the player wiki, which filters entities by tier first, would orphan the now-public fact). Idempotent, set-based, last-write-wins on the updated_at bump.

Provenance as a required field, not an optional one — making createdIn mandatory means every code path that inserts an entity declares which origin it represents at compile time. The alternative (an optional field defaulted by the repo) silently labels every new caller with whatever fallback string the repo chose, losing the audit trail that lets stage 4b cascade-delete only its own ghosts on a stage-4 retry (DELETE FROM entities WHERE world_id = $1 AND created_in = 'stage:entity_consolidation'). A required field forces the caller to think about provenance once, and the test fixtures pay 'stage:test' as their tag.

proseKernels exposes insert, updateByEntityId, and listByEntities (added under myth-exac for the world-snapshot view's composition pass). The table has UNIQUE(entity_id) — exactly one prose blob per entity — so insert errors on conflict (the stream-stages caller has guaranteed fresh entities upstream). updateByEntityId is the coherence pass's fix_prose path. The two write paths are deliberately NOT collapsed into an upsert: the design (§4.3) calls out the separation so the failure mode "INSERT collided" can't silently degrade to "the LLM rewrote a region's lore in coherence pass." When a coherence patch needs to land, it goes through updateByEntityId explicitly. listByEntities short-circuits to [] on empty input.

facts exposes insertMany, updateContentById, listByEntities(client, ids, { accessLevels, liveOnly? }) (added under myth-exac for the world-snapshot view), and — MYT-74a — insertReconciled + setSuperseded. insertMany runs a single parameterized multi-row INSERT with one constant baked in — narrative_status = 'undelivered'. The LLM never emits the narrative_status field; the persister stamps the value as part of the INSERT shape. Play-runtime owns subsequent transitions of that column (delivered → developed → resolved). source uses the column default 'prep'; no explicit value passed. updateContentById is the coherence pass's fix_fact path. listByEntities applies a mandatory tier filter — the caller is required to name the access levels it's authorized to see, so a future caller can't accidentally read the full unfiltered set by omitting the option — and now also a liveOnly flag (default true) that appends AND superseded_by IS NULL so a reader sees only live canon, never a corrected-away fact; pass liveOnly: false for the full append-only log. insertReconciled appends a session-improvised canon fact (stamping source = 'session' and narrative_status = 'delivered', returning the new id), and setSuperseded(oldId, newId) points a corrected fact's superseded_by at its replacement and NULLs its embedding — the end-of-session reconcile's append-only correction primitives, retiring updateContentById from the canon-correction path. MYT-74c adds promoteToKnown(factIds) — the reconcile commit's tier-promotion primitive: a single UPDATE facts SET access_level='known' WHERE id = ANY($1) AND access_level <> 'known' AND superseded_by IS NULL RETURNING entity_id, whose returned entity ids are deduped in JS ([...new Set(...)]) because two promoted facts can share one owning entity and the contract is "distinct owning entity ids." The <> 'known' + superseded_by IS NULL guards make it idempotent and keep it from ever resurrecting dead canon. facts.access_level was renamed under migration 014 from (public, private, secret) to (known, discoverable, secret); the new vocabulary mirrors D&D-mechanic semantics, and — read top to bottom — it is a one-way promotion state machine (secret / discoverable → known on discovery), the model the reconcile page tells in full.

relationships exposes insertMany, listByWorld, listAmong (added under myth-exac for the world-snapshot view — filters at the DB level to pairs where both endpoints are in a given entity-id set), deleteByWorld, updateById, and deleteById. deleteByWorld is the stage-4 retry-idempotency primitive: the very first DB action stage 4 takes is relationships.deleteByWorld(worldId), so a retry after a partial run lands in a clean slate. The schema has no UNIQUE(source, target, type) constraint by intent — application code owns idempotency at stage-start time, not at row-insert time. updateById + deleteById are the coherence pass's fix_relationship_by_name (modelled as DELETE + INSERT, not in-place UPDATE) and delete_relationship_by_name paths. The DELETE + INSERT shape is deliberate: it produces a clean edge-removed + edge-added event pair on the wire, matching the contract's "every relationship change is observable" rule. InsertRelationshipInput requires synthKey: string (myth-p4sz, migration 020) — stages 4, 4b, and 7 mint the wire-format synthKey at INSERT time and the row carries it back through listByWorld for stage 7's synthKeyByRelationshipId lookup map. The previous code recomputed the entity-side synthKey for relationship rows and silently missed every edge-removed event; persisting the column is what made stage 7's wire events honest.

entityHierarchy exposes insert(client, input) and listForWorld(client, worldId) (added under myth-exac to feed the world-snapshot view; the entity_hierarchy table has no world_id column, so the query joins through entities to constrain to world-internal rows). The table has UNIQUE(child_entity_id) — at most one parent per entity — and the repo deliberately does NOT include ON CONFLICT. The caller (stage 4's straggler insert) pre-filters against the existing rows in entity_hierarchy to enforce the "stage 3 wins" collision rule from §D9, then INSERTs only rows that won't conflict. Keeping the policy in the caller rather than the repo means future changes to the collision rule are a caller-side decision, not a schema migration.

Stage 4 pre-filters; stage 3 just INSERTs — stage 3's parent resolver builds its name → entityId map fresh from entities.listByWorld on every run, so it never sees a stale collision; it INSERTs straight into entity_hierarchy. Stage 4's straggler path runs AFTER stage 3 and can collide with rows stage 3 wrote in the same world's same retry-attempt — hence the pre-filter. The two callers operate at different points in the pipeline and the asymmetric error handling reflects that.

The four billing namespaces: tx-composed by the webhook, pool-bound by the routes

stripeEvents, purchases, userSubscriptions, and billingHistory are ClientLike binders like the rest. They serve both bindings without changing shape: the webhook dispatcher opens one transaction per event and threads its connection through every handler's writes, while userSubscriptions and billingHistory are also read from the billing routes through the pool-bound repo surface. Because the methods bind a ClientLike rather than reaching for a captured pool, the same method body answers a pooled route read and a webhook-tx write unchanged.

stripeEvents exposes one method: recordOrSkip(tx, event_id, event_type) runs an INSERT ... ON CONFLICT (event_id) DO NOTHING RETURNING event_id and returns either 'inserted' or 'duplicate'. The dispatcher branches on the result: 'duplicate' means the event was already processed and the rest of the tx is skipped.

purchases exposes insertMany, getByPaymentIntent, and markRefunded. insertMany runs a single multi-row INSERT for à-la-carte cart lines, using the composite (stripe_payment_intent_id, lookup_key) UNIQUE for idempotency — a redelivered checkout.session.completed for the same payment intent is a no-op. markRefunded flips status='refunded' on a row the refund handler has resolved.

userSubscriptions exposes upsertFromStripe, markCanceled, and getActiveForUser. The first is the load-bearing method: a single INSERT ... ON CONFLICT (stripe_subscription_id) DO UPDATE with a strict WHERE excluded.stripe_event_created_at > user_subscriptions.stripe_event_created_at filter rejects same-second or earlier deliveries as no-ops. Combined with stripe_events idempotency, this absorbs both Stripe's at-least-once delivery and Stripe's no-guaranteed-ordering across event types.

Strict > on the stale-event filter, not >= — Stripe doesn't guarantee event-ordering by created timestamp at second precision. Two events for the same subscription can carry the same created second; the second one to arrive could be the one that fires first on a multi-worker setup. >= would let the second-arriving same-second event overwrite the first; > rejects it as a no-op. The checkout.session.completed + customer.subscription.created race is the textbook example: both fire within the same second on a fresh checkout.

billingHistory exposes append, find, listByUser, and markRefunded. append uses the composite (kind, source_id_stripe) UNIQUE with ON CONFLICT DO NOTHING + follow-up SELECT so a redelivered event is a no-op. listByUser is the cursor-paginated query backing GET /api/billing/history; the cursor is a (occurred_at, id) pair so two events at the same second don't drop a row at the page boundary.

(timestamp, id) cursor, not offset pagination — Stripe events arrive near-real-time and the audit feed grows append-only. Offset pagination drifts on every new row written between page fetches. A (occurred_at, id) cursor is stable; the row id breaks ties when two events share the same Stripe second-precision timestamp.

Tests: real Postgres, TRUNCATE-based reset

Each namespace has an integration test under backend/src/repo/__tests__/<ns>.test.ts that runs against a real Postgres (the docker-compose stack locally, the CI Postgres service in CI). beforeAll runs all migrations once; beforeEach calls a helper that TRUNCATE … RESTART IDENTITY CASCADEs every application table in dependency order. The schema stays intact across tests; only data is reset, which is roughly 50× faster than re-running migrations between every test.

mappers.test.ts is a pure unit test over the mapper functions and the narrowing helpers — hand-constructed XxxDbRow objects, no DB. Schema-parity invariants (table names, CHECK constraints, FK rules) live in the schema-parity test from MYT-33; the repo tests trust that and exercise behavior, not structure.

credits.test.ts adds two test groups beyond the per-namespace shape: a schema-invariants block that asserts each migration-004 CHECK rejects the row it's supposed to (and includes an EXPLAIN assertion that the idempotency SELECT uses the partial-unique index, not a sequential scan), and a concurrency block run against a separate small pool that exercises parallel debits. The race tests cover the empty-ledger case (the bug the user-row lock fixes), the exactly-one-succeeds case, the parallel-same-sourceId idempotency case, the lock-timeout case, and a "every error path issues ROLLBACK" sweep that catches idle-in-transaction leaks.

Integration points

The migrations runner shares the uuidv7() wrapper — both the CLI's runId and every repo create read from backend/src/repo/uuidv7.ts. The backend runtime's AppDeps carries the repo alongside pg; the billing routes and the onboarding routes consume it as the seam for all data access. The webhook handlers consume the billing namespaces through repo.transaction (and the composable grantInTx / recordClawback), composing every event's writes under one COMMIT. The schema is what the repo's queries are typed against — every XxxDbRow matches a table the migration files define.

eslint-rules/no-raw-db-access.cjs The mythrun/no-raw-db-access rule — bans raw .query / .connect, pg value-imports, bare tx-control literals, SQL pass-through laundering, and in-tx side-effects outside the repo/db allowlist. Registered in the repo-root eslint.config.js at 'error' — the migration is complete, so a raw-DB site outside the repo/db layer is a build failure. Test files are carved out via a per-file override; the @mythrun/wiki build tooling lives under its own ESLint root.
