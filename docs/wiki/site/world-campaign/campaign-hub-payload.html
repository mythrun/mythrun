The campaign hub payload

GET /api/campaigns/mine assembles everything a home-hub card needs — the world, the party, the play record, and a per-viewer status — in two batched queries with no fanout, then hands the frontend a ready-to-render CampaignSummary[].

How it fits together

The home hub is one screen showing many campaigns at a glance, so its endpoint has to gather a lot per card — the world name and colours, the party roster with who-has-a-character, a session count and last-played time — without turning into an N+1 loop or a cartesian join. listHubCardsForUser in the repo does the gathering; the route's toHubCardSummary projects each row to the wire shape and derives the viewer-relative status. The repo stays pure data access; the per-viewer judgment lives at the route.

Two batched queries, no fanout

The first query joins campaigns ⋈ worlds ⋈ users (the world's creator) and reads the session aggregate through a LEFT JOIN LATERAL — a per-campaign subquery counting sessions and taking max(started_at). It returns the caller's campaigns — owned or joined collapse into one list via campaign_members — filtered to accepted memberships and non-archived campaigns, newest first.

The session count rides a LATERAL, not a third join — joining sessions directly alongside campaign_members would multiply each session row by the party size and inflate the count. Running the aggregate in its own lateral subquery keeps it exactly one number per campaign, independent of how many members the campaign has.

The second query reads the party roster for all the returned campaigns at once (WHERE campaign_id = ANY($ids)), joining users for display names and campaign_characters for hasCharacter (a character row exists for the member). The rows are grouped per campaign in application code.

Batched roster, not a per-card lookup — calling a getPartyRoster per campaign inside the map would be a classic N+1: one hub with twenty campaigns becomes twenty-one round trips. One ANY($ids) read fetches every roster in a single trip and the grouping happens in memory. The whole payload is therefore exactly two queries regardless of how many campaigns the viewer has.

The viewer-relative cardPhase

A campaign's card says something different depending on who is looking: the same campaign reads "make your character" to a player who hasn't, and "waiting for players" to one who has. So the status is not a single global value — it is deriveCardPhase, a pure projection the route computes per viewer from the campaign status, the world status, whether the viewer has a character (their own roster row), and whether the whole party is ready. It resolves to one of six states:

  • generating — the world is still being built.
  • failed — world-gen failed, or character-integration exhausted its repair chain.
  • needs-character — the world is ready and this viewer hasn't made a character.
  • waiting-for-players — the viewer is ready but not every member is.
  • not-played — everyone's ready (or the campaign just went active) with zero sessions.
  • played — the campaign is active and has sessions; the card shows the play record.
The character-creation window is setup, not active — a campaign stays setup through both world-gen and character creation, and flips to active only as the final write of character-integration, once every PC is woven in. So the viewer-relative branches (needs-character / waiting-for-players) gate on setup; by the time a campaign is active the party is complete and the card is either not-played or played. Getting this wrong would strand a fully-set-up campaign on the wrong line.
A sibling of derivePhase, not a replacement — the same file already hosts derivePhase, the global SSE pipeline phase that is identical for every member (see Pipeline status). deriveCardPhase is added alongside it rather than folded in: the hub needs a per-viewer projection, the SSE channel needs the global one, and keeping the terminal failed signal (which an earlier "is the world ready?" boolean erased) matters to both.

From row to wire

toHubCardSummary finishes each card: it derives cardPhase, validates the stored colour pair against WorldColorPairSchema (an invalid or half-set pair collapses to null, which renders the ghost band), and serializes the Date columns to ISO strings — the contract models the wire, not the database row. Notably the avatar pigment is not on the wire: it is a deterministic frontend derivation from the display name, so returning it would create a second source of truth. The result is the widened CampaignSummary the frontend consumes.

Integration points

The wire shape is defined in frontend/contract/src/rest/campaigns.ts and consumed by the campaign hub screen through its useMyCampaigns hook. The colour pair each card carries is produced by the world colour identity stage. deriveCardPhase shares a file with the SSE pipeline phase derivation. The endpoint is one of the dev tool's poll targets.

Appendix: the wire shape

Each element of the campaigns array (beyond id / name):

Field Type Notes
worldName string Joined from worlds
worldColors {from, to} | null Validated pair; null → ghost band
creator string | null Creator display name, null when the viewer owns the world
party {userId, displayName, hasCharacter}[] Accepted members only
sessionCount / lastPlayedAt number / string | null From the LATERAL aggregate; ISO string on the wire
cardPhase six-state enum Viewer-relative; drives the card's state line and click target
