Campaign create

The path a player takes to turn an idea into a campaign. Two ways in — write your own paragraph, or name three things you love — and one proposal checkpoint both pass through: read the world back, optionally rework it once, then commit. Everything before the commit is non-charging; the proposal lives in Redis under an opaque preview id and the credit is spent only when the player presses Begin.

How it fits together

Creation forks two ways at its first screen. Start from an idea is freeform prose the player writes themselves; build from what you love is the brainstorm path, where a Sonnet synthesizer invents an original concept from three media-picks. The two differ only in what they hand the synthesizer. From there they share everything: the same route, the same stream, the same input gate, the same Redis holding pen, the same preview screen, the same commit.

Preview, then commit — because world-gen is expensive — committing kicks off roughly ten minutes of multi-stage world generation and debits a credit. So the flow gives the player a proposal to read before they spend anything: synthesize, look, change their mind once, and only then commit. The whole preview loop is deliberately cheap enough to abandon.
Freeform used to skip the checkpoint, and that was the asymmetry worth closing (myth-6t06f) — the player who wrote their own paragraph went straight from the field to ten minutes of world generation, sight unseen, while the player who named three films got to read a brief first. Routing both through the proposal means the freeform player also sees what their words became before buying it. The cost is one extra Sonnet call on a path that previously had none; the gain is that the one irreversible click always comes after a read.

Where the gate sits, per path

Whatever reaches the preview store has passed the input gate — one Sonnet call over three axes (does it fit the SRD, is it a thinly-veiled franchise clone, is it inappropriate). Each path runs exactly one gate call, but at a different moment. The brainstorm path has no raw words worth judging — its input is three media titles — so it synthesizes first and gates what it wrote. The freeform path gates the player's own text before a token of synthesis burns.

Freeform gates first, and the order is load-bearing — it is the exact check the commit route used to run on this text, kept in the same position relative to the player's input. A synthesis in between would launder the concept: the gate would then be judging a Sonnet paraphrase rather than what the player actually typed, and a rejected idea could survive by being reworded on its way through. Gating first also keeps an abusive input at one cheap call instead of a full synthesis. There is no second gate on that path — the proposal is a paraphrase of text already judged, and re-judging it would burn Sonnet on an input the caller could not have altered.

The proposal has a name

The synthesizer emits a title alongside the concept, and it rides the whole way through: into the PreviewRecord, out on the complete frame and the 201, through a rework, and onto the preview screen as the headline above the prose. The page never mines a name out of the first words of the concept — the stage that wrote the world is the stage that names it.

The screen state machine

The SPA flow (campaign-new.tsx) is a thin screen state machine over a back-history stack. fork is the permanent root; freeform and guided collect the two kinds of input; synthesizing renders the proposal as it streams; preview shows the settled proposal and its actions; rejection is the calm dead-end. Each screen is pure presentation firing neutral intents — it never navigates itself. The controller owns the carried payloads (the live stream handle, the parked proposal, the rejection reason) and maps each intent to the next screen.

Because both inputs now feed one checkpoint, the controller also remembers the origin — which screen produced the proposal currently on display. Every “back to the start of my path” exit reads it: start over from the preview, a start over from the rejection screen, and a commit-time 410 all return the player to their own input rather than to the other path's. Origin also gates the preview's “woven from” credit line, which is only true of a brainstorm proposal — a freeform one was woven from words the player is already reading.

The synthesizing beat swaps, it doesn't push — when the proposal finishes the controller replaces the top of the history with preview (or rejection) rather than pushing onto it. So a ← back from the preview lands on the input the player gave, not on a half-written proposal they can never return to meaningfully. The writing beat is a transition, not a place.

Both inputs survive a reload, by different seams. The three picks round-trip through sessionStorage; the freeform concept is held in localStorage and written back on every keystroke, so a closed tab reopened later still holds the world the player had described. The freeform text lives in the controller, not the screen, because the screen unmounts between flow steps. Entering freeform no longer blanks the field first: whatever is there is the player's own words, whether typed earlier or carried over from the rejection screen's “edit as freeform”. Only an actual commit clears both drafts, exactly once.

localStorage for prose, sessionStorage for picks — a media title is cheap to retype and belongs to one sitting. A paragraph the player composed themselves is the expensive artifact in this flow, and losing it to a reload or a closed tab is the loss they actually feel. The storage tier follows the cost of re-creating the thing.

Synthesize — streamed and non-charging

The primary action on either input screen opens a one-shot stream against POST /api/campaigns/synthesize-preview/stream. The screen owns the open, so every pre-stream failure stays a calm inline notice right where the player can act on it; the moment the 200 head arrives it hands the live stream to the controller and advances to synthesizing, which renders the arriving prose (a paper-register streaming block, no spinner). The server runs the identical guard chain, then hijacks the response into SSE: delta* frames carry the prose, and exactly one terminal frame (complete | rejected | error) closes it. A synchronous twin, POST /api/campaigns/synthesize-preview, returns the whole proposal as a single 201 — the dev-tool panel and any non-streaming client drive that one.

The request body is a union of the funnel's two inputs: { picks } with exactly three media-picks, or { concept } with the player's own text bounded at 20–4000 characters (the same bounds the commit route's freeform source carried). Both synthesize into the same output shape, so the gate, the preview store, the wire union, and every screen downstream are identical either way and never branch on which path opened the stream.

Underneath, synthesizeConcept (picks) and synthesizeFromConcept (prose) are single Sonnet calls through the canonical generateObject wrapper, producing a title, a concept, and an intentSummary (aesthetics, themes, and an internal sourcesInternal list). Each has a structural twin over streamObject — same prompt, schema, and repair chain — deriving prose deltas from the growing concept field. The validated output, not the streamed text, is authoritative: a post-stream schema repair can rewrite what the player watched arrive, so the terminal frame's proposal wins.

The concept has a floor but no ceiling — the synthesizer schema puts a .min(50) on the concept (a too-short proposal is malformed) but deliberately no .max(). A max ceiling would terminal-fail an otherwise good over-length generation instead of accepting it, and the concept's destination — worlds.concept — is a bare TEXT column with no length check, so nothing downstream needs a mirror. LLM prose gets a floor, never a cap.
The stream is not the reconnecting SSE client — synthesis is a non-idempotent POST: a silent reconnect would re-run Sonnet and bill a second proposal. So startSynthesisStream is its own small client (a zustand store, the StreamingFetch seam — EventSource is banned), and a dropped connection is a terminal failed{stream_interrupted} that keeps the halted partial text on the page, never a retry. The player retries deliberately, from their own input. This is why it doesn't reuse the reconnecting transport the play and world-gen flows run on.

Rejection

A reject verdict becomes a concept_rejected outcome — a 422 on the synchronous route, a terminal rejected frame on the stream, identical payloads. Both arms share one emitter, which increments the rejection-storm counter, logs the model's axis reasoning server-side, and shapes the response. The gate also receives sourcesInternal, which closes a prompt-injection path: the synthesizer's own note of what it drew from is visible to the judge but never echoed to the player and never fed to a later stage.

Whether the judged text rides back is stated, not inferred — the emitter used to decide from a mode: 'freeform' | 'guided' flag, on the assumption that only guided rejections needed to show what was judged. The freeform path's checkpoint broke that equivalence: a freeform rejection now lands on the standalone rejection screen, which has nothing but the payload to render and to seed its “adjust it yourself” affordance from. So the flag became an explicit echoJudgedConcept. It is true for every proposal-route rejection on both paths, and false in the one place the caller already holds the text inline — the commit route's freeform arm, which answers the very screen the concept was typed on.
The player sees a message, never the reasoning — a rejection carries a server-authored rejectionMessage and the judged concept. The model's raw axis reasoning is logged server-side only; it never reaches the response body. The rejection screen falls back to a calm generic line when the model declined to author a message.

content_filtered is a distinct terminal: Anthropic's content policy blocked the prompt, so retrying the same text hits the same filter. That screen offers no rework or edit — only start over.

Rework — one change, gate-pass-only

A parked proposal buys the player exactly one change. Ask for one change reveals a note field; POST /api/campaigns/preview/:previewId/rework feeds the parked { title, concept } and the note to reviseConcept (again one Sonnet call, same output contract), re-runs the input gate, and — only on a pass — overwrites the stored proposal, bumping reworkCount from 0 to 1. A second attempt is a 409. Passing the title in is what keeps a revision recognisable as the world the player was shown rather than a differently-named one. The change note is capped at 800 characters, the same bound the synthesizer puts on a pick's “why I like it”: a note is a sentence or two, not an essay.

A rejected rework leaves the budget intact — nothing is persisted until the gate passes. If the revised concept is rejected, the original gated proposal and reworkCount: 0 survive untouched — the player still holds their one budgeted change. The rejection still increments the rejection-storm counter, so a loop of rejecting reworks trips the cooldown on the next request rather than burning Sonnet unbounded.

Where the proposal lives

Between synthesis and commit the proposal sits in Redis, not Postgres — a PreviewRecord (the title, the concept, the intent summary, the rework count) under the key {env}:{region}:campaign-preview:{userId}:{previewId} with a 30-minute TTL. An abandoned proposal reaps itself; nothing accumulates. The commit reads the record but doesn't delete it — the TTL is the only cleanup.

The user id is baked into the key — that is the whole IDOR defence — a proposal is keyed by the authenticated user, never a client-supplied id. So a stolen or guessed previewId read under a different user simply misses the key and returns the uniform 410 (preview_expired) — the same response a genuinely expired proposal gives. There is no surface where user B reads user A's concept.

Commit — from proposal to world-gen

Begin calls the shared create endpoint with a wrapped { mode: 'guided', previewId } body — the wire name for “commit what the checkpoint parked”, on either path. The commit loads the already-gated proposal by (authenticated user, previewId) and re-uses its concept verbatim: no re-synthesis, no re-gate. From there it debits one world_gen credit inside an advisory-locked transaction and enqueues world generation; that half of the story is World gen. A commit whose proposal has aged out returns a 410, and the flow restarts at whichever input the player used, re-prefilled from its draft.

Begin is double-submit-guarded, because it is the one charging click (MYT-102) — pressing Begin is the only action in the whole flow that spends a credit, and busy/disabled are async React state: two clicks in the same tick both pass the disabled check and fire two createCampaign calls — two campaigns and two world_gen debits off one impatient double-tap. The Begin CTA closes that with a synchronous useRef latch set before the async state flips, so the second click returns immediately (the same guard the character-creation submit uses).

Cost and rate posture

Preview and rework never charge a credit, but they do burn Sonnet, so the same cheap guards run before any model call on every proposal route — synchronous, streamed, and rework alike. In order: a Zod body parse (three picks, or a 20–4000-character concept), a per-user rate limit of five requests a minute, a read-only rejection-storm cooldown peek, and a non-charging credit-balance peek. Only then does the first Sonnet call fire. Because the guards run before the SSE hijack, a trip on the streamed route is a plain JSON status the client handles exactly like the synchronous endpoint's errors — which is why both input screens keep the same three inline notices (cooldown, credits, transient retry) and route every gate verdict to the rejection screen instead.

A zero-credit user is stopped before the first token — the credit peek is a non-charging balance check, and it runs before any LLM call even though preview itself doesn't debit. There's no point letting someone synthesize and rework a proposal they can never afford to commit; blocking at the peek keeps a zero-balance account from driving Sonnet cost at all.
The storm counter is checked at the start, incremented at the end — the rejection-storm counter increments on each gate rejection but is read at the start of the next request. So a request that trips the threshold (more than three rejections in an hour) still gets its own answer; the following request is the one that 429s into the cooldown. It's the cheapest possible rejection — no LLM call — for a user who has been repeatedly rejected.

Disconnects are handled as cost, not just correctness: the streamed route's SSE sink aborts the Sonnet stream on client close, and the SPA controller closes the stream handle on back-out, replacement, and unmount. A closed tab stops the token burn instead of generating into the void.

Integration points

The streamed synthesis rides the SSE framing described on Realtime transport and Pipeline status, but deliberately as its own one-shot client rather than the reconnecting one. The commit endpoint and the credit debit belong to World gen, which this flow hands off to; that page's create route still carries a freeform arm of its own, and it is the one caller that suppresses the judged-concept echo. The parked concept becomes worlds.concept; the campaign it seeds surfaces on the campaign hub, and the world's palette is picked separately by world colour identity. The synchronous preview route is one of the dev tool's targets. The wire union for the stream is SynthesizeStreamEvent in frontend/contract/src/events/synthesize-stream.ts.

Appendix: the proposal routes

Route Charges? Terminal outcomes
POST /api/campaigns/synthesize-preview No 201 { previewId, title, concept } · 422 concept_rejected · 400 / 403 / 429
POST /api/campaigns/synthesize-preview/stream No delta* → complete{previewId, title, concept} | rejected | error; guard trips are pre-hijack JSON (400 / 403 / 429)
POST /api/campaigns/preview/:previewId/rework No 200 { previewId, title, concept } · 409 rework_exhausted · 410 preview_expired · 422 concept_rejected
POST /api/campaigns (proposal commit) 1 world_gen 201 { campaignId } · 410 preview_expired — see World gen

Both proposal routes accept either body shape: { picks } (exactly three, each a title of 1–200 chars and a reason of 1–800) or { concept } (20–4000 chars). A rework note is 1–800 chars; the preview TTL is 30 minutes; the rate limit is five requests a minute per user per route; the rejection-storm cooldown trips after more than three gate rejections in an hour.
