JWT middleware

How an inbound Authorization: Bearer <jwt> turns into a claims-only request.user on every protected route — a two-plugin family (real Cognito validation and a development bypass), a six-layer defense that keeps bypass mode out of any AWS-managed runtime, and the deploy gate that re-checks the boot env before rolling tasks.

How it fits together

Auth lives in backend/src/auth/ and is composed by buildApp via registerAuth(app, authOpts). The dispatcher inspects opts.mode and registers exactly one of two siblings: jwtPlugin for real Cognito validation, or bypassPlugin for local development. Both are fastify-plugin-wrapped Fastify plugins; both decorate the app with a single sentinel and install one onRequest hook; both attach the same AuthUser shape to request.user. The split is deliberate — there is no "if (env.bypass) skip validation" branch inside a single plugin. Two named plugins make grep-for-the-bypass-codepath work, and the dispatcher refuses to cross-wire opts (real mode requires userPoolId+appClientId; bypass mode forwards Cognito vars only so its Layer 3 check can scream if any are populated).

Two plugins, not one with a flag — a single plugin with if (mode === 'bypass') return DEV_USER is one accidental refactor away from a catastrophe: a future contributor flips a tristate, a config bug picks bypass in production, no reviewer notices because the diff is small. Two named plugins, two file paths, one dispatcher whose only job is to pick — every layer of defense in this page is conditioned on which file is loaded, not on a runtime flag.

The plugin family wraps with fastify-plugin for one reason: Fastify's default behavior is to encapsulate a registered plugin in a child scope, so a hook installed inside that child applies only to routes registered under the same scope. The fastify-plugin wrapper opts out of encapsulation, which is exactly what we need — the auth hook has to apply at the parent app's scope so it covers /health, /health/ready, and every future route landed onto the same instance. Without the wrapper, the hook would attach to a child scope nobody ever registers routes under, and every inbound request would silently bypass auth.

Forgetting fastify-plugin here is a silent failure, not a loud one — Fastify won't warn that your hook attached to a scope without routes. Tests would still pass (the unit suite registers the plugin and asserts the hook fires); production would 200 on every protected route. The wrapper is also why both plugins refuse double-registration via a shared mythAuthRegistered decorator: opting out of encapsulation means a second app.register(jwtPlugin) would silently double-install the hook.

The claims-only AuthUser

request.user is { sub, cognitoUsername, scopes } — three fields, all derived from the verified access-token payload, all frozen. sub is Cognito's stable per-user identifier and the canonical key for cross-system reference; the onboarding flow creates the matching users row on first call to POST /api/users/register, and the requireOnboarded hook gates every default-auth route on that row's existence. cognitoUsername is the federated identity's internal username (Google_<sub> / Discord_<snowflake>) and is treated as opaque — never substring-parsed for provider routing. scopes is the OAuth scope string parsed once at the boundary into a frozen array, so handlers do scopes.includes('admin') rather than scope.includes('admin') — the latter would substring-match 'administrator', which is a real authorization bug class.

No email, no name, no internal user UUID — those live in the users table that the requireOnboarded hook gates protected routes on. Today's middleware is the first half of a two-stage attach: validate the token and surface its claims; defer the DB lookup to the onboarding gate. A protected handler that needs the internal user id reaches through repo.users.getByCognitoSub(request.user.sub); the onboarding routes are the only ones in flight today that do so.

Routes default-require auth and opt out per-route via config.auth on the route config:

  • config: { auth: 'public' } — skip validation entirely; no request.user attached. Used by /health, /health/ready, the invite preview, the SKU listing, the Stripe webhook, the WebSocket session-transport upgrade (which authenticates via its ws-ticket preHandler, not the JWT chain — a browser WS can't send a header), and the three BFF session routes (the caller has no access token yet on /session; /refresh and /logout authenticate by the refresh cookie). Pinned by the public-route allowlist hook.
  • config: { auth: 'jwt-no-db' } — verify the JWT, attach the claims, do not look up the users row. Used by POST /api/users/register and GET /api/users/check-username: the row doesn't exist yet at first call. The requireOnboarded hook enforces a boot-time allowlist that pins which routes may use this opt-out — see the Onboarding page.
  • auth unset (the default) — verify, attach, and run the requireOnboarded chain: cognito-sub lookup + suspended_at check + frozen request.dbUser attach. The access-control middleware reads request.dbUser on routes that gate further on per-resource authorization.

The public-route allowlist

backend/src/auth/public-route-allowlist.ts exports a closed PUBLIC_ROUTE_ALLOWLIST set of ${METHOD} ${URL} strings and a registerPublicRouteAllowlistHook(app) function that installs an onRoute hook. The hook fires once per route registration; if the route's config.auth is 'public' and its ${method} ${url} isn't in the allowlist, it throws. Fastify's app.ready() propagates the throw and the deploy fails. The hook is registered first inside buildApp — even before the /health route — because onRoute only fires for routes registered after the hook on the same scope.

Boot-time enforcement, not a code-review checklist — relying on reviewers to flag every config: { auth: 'public' } introduction is fragile: a public route that ships by mistake is a security incident, and code review fatigue makes the omission plausible. A boot-time hook fails the deploy on the first run; the deploy can't ship a public route that wasn't authored alongside the allowlist entry. The ten entries today cover the two health probes, the sitewide LLM-outage readout (GET /api/llm-health — a binary {state, since} with no tenant data, public so the notice strip's per-tab 60s poll doesn't burn a JWT verify per minute), the invite preview, the SKU listing, the Stripe webhook, the WebSocket session-transport upgrade (GET /ws/session/:sessionId, authenticated by its ws-ticket preHandler rather than the JWT chain), and the three BFF session routes (POST /api/auth/{session,refresh,logout}, which carry the further reviewer note that any change to those three is security-sensitive) — adding an eleventh is two file edits in the same PR, both visible in the diff.
Skip auto-generated HEAD routes — Fastify auto-generates a HEAD route for every GET registration. The onRoute hook fires for it, but HEAD semantics are identical to GET and need no separate allowlist entry. The hook detects the auto-generated HEAD by the presence of a non-null onSend array on the route options and skips it.

Protected handlers narrow request.user from optional to required via requireUser(request). The helper throws if the user is missing — a runtime guard against a route that accidentally shipped with config.auth: 'public' and then tried to read request.user.sub. request.user!, request.user?.sub, and request.user as AuthUser are all forbidden by a CI grep gate (the lint-auth workflow at .github/workflows/lint-auth.yml) — narrowing helpers force a single, auditable place where "what if no user?" gets answered.

Grep-gate, not an ESLint rule — an ESLint rule for "no non-null assertions on request.user" would need a custom plugin to scope the check to that one identifier and would silently break if the property got renamed. A six-line workflow that greps for the three forbidden patterns and exits 1 is auditable in one screen, runs on every PR touching backend/src/, and excludes auth/__tests__/ by directory rather than by comment annotation.

Hydrate-at-boot in the JWT plugin

jwtPlugin creates a CognitoJwtVerifier at registration and immediately calls verifier.hydrate() — fetching the User Pool's JWKS (the JSON Web Key Set used to verify token signatures) once, so the first protected request after a cold start doesn't pay the JWKS fetch latency on top of its own work. Three details around the hydrate matter:

  • 0–1 s jitter before the fetch. A rolling deploy starts every API task within seconds of each other, and a herd of containers all hitting Cognito's JWKS endpoint at the same moment is exactly the thundering-herd shape worth defusing for the cost of one setTimeout.
  • 10-second Promise.race timeout. A wedged Cognito (or DNS, or a misrouted egress) would otherwise hang the plugin indefinitely. Bounding the wait gives the boot a deterministic failure mode: log auth.jwks_hydrate_failed with the issuer + error class, throw, let the container crash-loop into operator visibility.
  • Late-rejection guard before the race. The hydrate promise has a .catch(() => {}) attached before Promise.race. If the timer wins and the underlying hydrate later rejects, that rejection has nowhere to go. Node 24's default policy is to terminate the process on an unhandled rejection — the boot would pass, the listener would come up, then a moment later the process would die with a stack trace pointing at no obvious cause.

The verifier is built over a TtlBoundedJwksCache — a subclass of aws-jwt-verify's SimpleJwksCache that expires the cached JWKS set after a 6h TTL. The default cache only re-fetches on a cache miss (an unknown kid), so a key AWS has revoked stays verifiable until the container restarts. Bounding the cache to 6h forces a re-fetch once a cached set is past the TTL, so a revoked compromised key drops within 6h instead of living for the life of the process — without paying a network fetch on every verification. The hydrate-at-boot flow above is unchanged; the TTL only governs how stale the cached keys are allowed to get afterward.

Bumping pluginTimeout to 30 s — Fastify's default plugin-load timeout is 10 s, which is exactly our hydrate budget plus jitter. Without the bump, a slow Cognito would trip Fastify's generic timeout first and the operator would see FST_ERR_PLUGIN_TIMEOUT instead of our specific auth.jwks_hydrate_failed log line. The 30 s bump leaves headroom for the boot gate's waitFor retries on adjacent dependencies without changing the auth contract.

The bypass-mode multi-layer defense

Bypass mode exists for one workflow: a developer running pnpm dev against the local docker-compose stack, pre-Cognito, wanting request.user to be a fixed bypass identity so route handlers can be exercised. The default sub is bypass:<sanitized-os.hostname()> — the bypass: prefix is fixed (it's keyed on by dev-credits, the per-sub rejection-storm counters, and the cognito_sub NOT LIKE 'bypass:%' CHECK), but the suffix is derived per-machine so two developers sharing a dev or staging DB each register a distinct users row instead of colliding on one literal. A MYTHRUN_BYPASS_SUB env override, when set, pins the sub verbatim; the integration suite sets it to bypass:dev-1 so the many test files that hardcode that sub stay deterministic across machines. It is the one piece of code in the system whose accidental activation in production would give every request the same all-permissions identity. Six independent layers stand between the bypass plugin and an AWS-managed runtime:

Layer 1 — loadEnv refuses ambiguity

config/env.ts's loadAuthConfig requires AUTH_MODE to be exactly 'real' or 'bypass'. Two cross-checks gate the value: bypass + any NODE_ENV other than development or test throws; real + NODE_ENV=production + BOOT_GATE_ENABLED not set to '1' also throws. Real mode requires all four COGNITO_USER_POOL_ID/COGNITO_APP_CLIENT_ID/COGNITO_ISSUER_URL/COGNITO_HOSTED_UI_DOMAIN to be present.

Layer 2a — bypass plugin's NODE_ENV allow-list

At registration, bypassPlugin reads process.env.NODE_ENV directly and refuses to install if the value is anything other than 'development' or 'test'. This is duplicated, on purpose, with loadEnv's check — defense-in-depth against a future code path that constructs BypassPluginOptions by hand and skips the env loader. The hook also re-runs the same check per request, so a runtime mutation of NODE_ENV (a stray test-helper, a vendor-instrumentation library) gets caught the next time the hook fires rather than only at boot.

Layer 2b — the ECS task-metadata HTTP probe

This is the load-bearing layer. ECS tasks (Fargate or EC2) have a link-local IP at 169.254.170.2 serving the task-metadata API at /v2/metadata. That address is unroutable from anywhere except inside an ECS task's network namespace. At registration, the bypass plugin issues a 1-second fetch to that URL: if the request succeeds (any HTTP status, including non-2xx — the responder being reachable is the signal), the plugin throws "ECS task-metadata endpoint reachable — bypass forbidden in any ECS runtime." If the request fails (refused, timeout, DNS) — the local-dev case — the plugin proceeds.

Why a probe, not just an env var like BYPASS_FORBIDDEN_IN_PROD=1 — every env-var-based gate I considered had the same failure mode: an operator with permission to set the env can also unset it. Bypass exists to be loadable, by definition. The HTTP probe is independent of any value an operator can override: the only way to make it return "not on ECS" is to actually not be on ECS, or to compromise the task-metadata responder, which is a much harder problem than fat-fingering an env var. 169.254.170.2 is reachable only from inside an ECS task; AWS Lambda has its own metadata at 169.254.169.254, and the probe will refuse there too if a future deploy ever lands the API on Lambda.

Layer 3 — Cognito vars must be empty in opts and raw env

The bypass plugin checks both its plumbed BypassPluginOptions (the loader-derived copy) and process.env directly for any of the four COGNITO_* names. Either populated → throw. The dispatcher in auth/index.ts always forwards Cognito vars to bypass mode for exactly this reason: a misconfigured boot that sets AUTH_MODE=bypass alongside a real COGNITO_USER_POOL_ID trips here rather than silently running with bypass identity against an otherwise-real environment. The per-request hook re-runs this check too, narrowing the same window NODE_ENV is re-checked in.

Layer 4 — loud structured-log warning at registration

Whenever the bypass plugin successfully installs, it emits a single warn-level structured event: { event: "auth.bypass_mode_active" }, message "AUTH BYPASS MODE: all requests authenticated as dev user. NEVER run in staging/production." This is the canary an operator searches for at incident time — zero occurrences in CloudWatch is the contract for staging and production. The query lives in the runbook below.

Layer 5 — Terraform serving module force-pins the env

The serving module's main.tf builds the API task definition's environment from concat(var.extra_env, [...module-owned values]). Module-owned position-last is deliberate: Terraform's concat + the ECS schema's last-write-wins on duplicate names means a malicious-or-mistaken duplicate from extra_env gets shadowed. The module-owned entries include AUTH_MODE = var.auth_mode (defaulted to "real") and NODE_ENV = var.node_env (defaulted to "production"). extra_env additionally has a validation block at the variable level that fails terraform plan if any element's name is AUTH_MODE, NODE_ENV, BOOT_GATE_ENABLED, or any of the four COGNITO_* names — so the shadowing doesn't even get a chance to be exercised; the plan refuses outright.

Layer 6 — tests verify every gate

backend/src/auth/__tests__/ covers each of the layers above with a per-gate negative test: a test that flips NODE_ENV to production and asserts the throw, a test that mocks fetch to resolve the metadata probe and asserts the throw, a test that injects a Cognito var into process.env and asserts the throw, and so on. Around twenty-four cases between the JWT and bypass plugins. The tests are the one place the bypass plugin's pessimism is in fact exercised on every CI run; they are the operational-correctness audit trail.

Per-request sub override via x-mythrun-dev-sub

Inside the bypass-only code path, the request hook reads an x-mythrun-dev-sub header and, if present + non-empty, uses its value as request.user.sub instead of the per-machine default (bypass:<sanitized-hostname>, or the MYTHRUN_BYPASS_SUB override when set). The override preserves cognitoUsername, scopes, and the Object.freeze contract; only the sub field changes. Without the override, every bypass-mode request in a single test run collapses to one identity, which breaks integration tests that need distinct simulated users — most acutely, the per-sub rate-limit keying on /api/users/register, which would otherwise share one counter across every test that calls register.

Why this is safe to add to a security-sensitive plugin — the header is read after Layers 1–3 + 5 have already gated registration, so the override only fires when the plugin has proven (a) NODE_ENV is development or test, (b) the ECS task-metadata probe failed (not on ECS), (c) no Cognito vars are populated, and (d) the Terraform serving module pinned AUTH_MODE away from bypass in any deployed env. Production traffic can never reach this hook because the plugin itself can never register in production. The header widens the dev-only seam without weakening any defense layer.

The 404 fall-through guard

Fastify v5 supports a custom setNotFoundHandler, which buildApp uses to return a stable JSON 404 instead of the default HTML-ish error. The interaction with the onRequest hook is subtle: under the not-found path, Fastify still invokes application-level onRequest hooks, and request.routeOptions is a non-nullable object — but its .url, .method, and .config are all undefined for unmatched paths. Without a guard, the auth hook would read request.routeOptions.config.auth, see it as undefined, treat the unmatched path as a default-protected route, and answer 401 to a request that should answer 404.

Both plugins start their hook with one line: if (request.routeOptions.url === undefined) return. The unmatched path falls through cleanly to the not-found handler; the matched path proceeds through the rest of the hook. The check is on .url rather than on .config because .config's undefined-ness is also the shape of a route registered without a config block — two cases the inner check would have to disambiguate. The url is undefined exactly when the path is unmatched.

Why the guard sits in both plugins, not in the dispatcher — the dispatcher only picks; it doesn't install the hook. The hook is per-plugin (one hook per registered plugin) and the guard is per-hook. Hoisting it to a "wrap every onRequest hook" abstraction would mean rewriting Fastify's hook-registration internals; one-line guards in the two known callers are cheaper and survive the next refactor.

Boot wiring across both startup paths

buildApp is now async, takes (deps, authOpts), and is awaited from both startup paths in server.ts. The boot-gate path (BOOT_GATE_ENABLED=1) loads env, opens real pg + redis, runs the waitFor probes, calls createRepo(pg), then await buildApp(realDeps, authOpts). The fallback-start path (boot gate off) skips the data-layer probes but still calls loadEnv and buildApp(stubDeps, authOpts) — the auth plugin registers in both cases, so a misconfigured boot fails fast in either mode rather than silently shipping a health-only listener with no auth.

The custom logger configured at buildApp time matters for the auth surface: pino's redact is set to mask req.headers.authorization, req.headers.cookie, and res.headers["set-cookie"] with a censor token, and a custom req serializer strips the query string from logged URLs. The query-string strip is what keeps the WebSocket ticket nonce out of CloudWatch — without it, a one-shot ticket attached as ?ticket=<nonce> on the WS upgrade would land in logs the first time a connection got recorded. The path is preserved so an operator can still tell which route was hit.

Operating this piece

Enable bypass mode locally

  1. In backend/.env.development, set AUTH_MODE=bypass and NODE_ENV=development. Leave the four COGNITO_* values unset — Layer 3 throws if any of them are populated even by an empty assignment that survives shell quoting.
  2. Start the backend with pnpm dev. Expect a single warn-level log line carrying { event: "auth.bypass_mode_active" } and the "NEVER run in staging/production" message. If you see auth.jwks_hydrate_failed instead, the dispatcher picked the JWT plugin — AUTH_MODE isn't bypass in the running process.
  3. Hit any protected route without an Authorization header. Expect a 200 with the handler reading requireUser(request) as { sub: "bypass:dev-1", cognitoUsername: "bypass_dev_1", scopes: ["bypass"] }.
  4. Switch back by setting AUTH_MODE=real (and providing the four COGNITO_* values). The boot gate will refuse to start with mismatched config — that's the contract.

Read the auth events at incident time

  1. Open CloudWatch Logs Insights against the API task's log group (per serving). Auth events all carry an event field on the structured log line.
  2. Verify bypass mode never activated in staging/prod: 
    filter event = "auth.bypass_mode_active"
| sort @timestamp desc
| limit 50
    Zero results is the contract. Any result is a P0: a task is running with bypass auth.
  3. Catch JWKS hydrate failures (boot won't complete; tasks crash-loop): 
    filter event = "auth.jwks_hydrate_failed"
| fields @timestamp, issuer, errorClass
| sort @timestamp desc
| limit 50
    Common causes: a Cognito us-east-1 partial outage, a misrouted egress (ECS task can't reach the public Cognito endpoint), or a stale COGNITO_ISSUER_URL after a User Pool recreate (see the Identity recovery runbook).
  4. Investigate per-request verify failures by client / route: 
    filter event = "auth.jwt_verify_failed"
   or event = "auth.jwt_missing_sub"
   or event = "auth.jwt_missing_username"
| fields @timestamp, req.method, req.url, errorClass
| sort @timestamp desc
| limit 200
    Spikes correlate with token-rotation events at the SPA, expired-token retry storms, or — if req.url is consistently a single path — a frontend bug pinning a stale token.

Verify the deploy gate rejects bypass

  1. The gate lives in .github/workflows/deploy.yml as the "Verify AUTH_MODE is set in the latest task-def" step before Render new task definition. It calls aws ecs describe-task-definition against mythrun-staging-api and reads the AUTH_MODE env entry from the container.
  2. Local dry-run, with an AWS profile that can describe the staging task-def: 
    aws ecs describe-task-definition \
  --task-definition mythrun-staging-api \
  --query 'taskDefinition.containerDefinitions[0].environment[?name==`AUTH_MODE`].value' \
  --output text
    Expected output: real. Empty (Phase A skipped — Terraform never registered a revision with AUTH_MODE) or anything other than real (somebody slipped bypass into the env) fails the deploy.
  3. To smoke-test the gate's negative path without putting bypass into staging: stand up a temp task-def family in the dev account, register a revision with AUTH_MODE=bypass, and rerun the workflow against it. The check exits 1 with the "rejected by this gate" message. Tear the temp family down after.

Roll the API after a Cognito User Pool recreate

  1. A User Pool recreate (recovery runbook) changes COGNITO_USER_POOL_ID, COGNITO_APP_CLIENT_ID, and COGNITO_ISSUER_URL. Every existing JWT becomes invalid; existing tasks will crash-loop on auth.jwks_hydrate_failed when they next restart, because the JWKS at the old issuer no longer exists.
  2. terraform apply in the env workspace registers a new task-definition revision with the updated COGNITO_* values.
  3. Run the deploy workflow manually (gh workflow run Deploy). The workflow's task-def-render step swaps in the real ECR digest; the deploy gate above re-checks AUTH_MODE stays real; the service rolls onto the new revision.
  4. Watch CloudWatch for auth.jwks_hydrate_failed to stop and a fresh batch of auth.jwt_verify_failed appearing as old client tokens get rejected. The latter fades as clients re-authenticate; the former should hit zero within one task-replacement cycle.

Integration points

The Identity page covers the upstream — the User Pool, the App Client, the Hosted UI, and the IdPs that mint the access tokens this middleware verifies. The four COGNITO_* env vars travel from infra/modules/auth/ outputs through the serving module's task-definition shape and into loadAuthConfig. The backend runtime page describes the buildApp + server.ts wiring that registerAuth composes against; this page is the auth-specific deepening of that surface. requireUser is the seam every protected handler reaches through. requireOnboarded registers as the next plugin and layers the DB-row gate on top of this middleware's contract; the onboarding + invite routes are today's consumers.

Value Behavior Today's consumers
