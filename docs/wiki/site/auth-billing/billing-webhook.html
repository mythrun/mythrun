Billing webhook

How Stripe events become Mythrun state. An encapsulated Fastify plugin owns the raw-body parser and signature verification at the edge; a two-phase dispatcher reads from Stripe outside any DB transaction, then opens one short transaction that records the event ID for idempotency and invokes the per-event handler. Eight handlers cover subscription lifecycle, à-la-carte purchase, and refund.

How it fits together

The route lives in backend/src/routes/webhook.ts as an encapsulated plugin: it is registered as a child scope of the main app, so the content-type parser it installs only applies inside that scope. The dispatcher in backend/src/billing/webhook.ts is what every verified event flows through, and the eight per-event modules under backend/src/billing/webhook-*.ts are the handlers it routes to. The repository layer exposes the four billing-table namespaces the handlers write to (stripeEvents, purchases, userSubscriptions, billingHistory) plus the credit-ledger grantInTx + recordClawback helpers.

The encapsulated plugin and its raw-body parser

Stripe's signature verification is HMAC over the raw request bytes. Fastify's default JSON parser reads the body to a string and parses it before any handler sees it; HMAC over a re-serialized JSON object would not match Stripe's signature because key order and whitespace would differ. The webhook plugin removes the inherited JSON parser inside its child scope, then registers a buffer pass-through that delivers request.body as a Buffer for any application/json request landing at POST /webhooks/stripe.

Encapsulated child plugin, not app.addContentTypeParser at the root — Fastify v5's addContentTypeParser is encapsulation-scoped, not route-scoped. Installing the buffer parser on the top-level app would replace the JSON parser for every other route in the system; every JSON body across the API would arrive as a Buffer. Wrapping the route in a child plugin scope is the smallest unit of isolation Fastify offers and keeps the rest of the API's JSON parsing intact.
removeContentTypeParser first, then add — Fastify v5 inherits the parent's default application/json parser into child contexts. Registering a second parser for the same MIME without removing the first throws FST_ERR_CTP_ALREADY_PRESENT at app.ready(). The remove-then-add ordering is what the spec call-out flags as the v5 footgun.

The route handler runs four gates before dispatch: it requires a Stripe-Signature header, asserts request.body is a Buffer (defense in depth — a future refactor that drops the encapsulated parser would otherwise silently HMAC against re-serialized JSON), calls stripe.webhooks.constructEvent, and on signature failure logs only err.message + err.type (the full err object would log the offending signature value). A signature mismatch returns 400 invalid_signature; a successful verify hands the constructed Stripe.Event to the dispatcher.

The route is on the public-route allowlist — Stripe never carries a Mythrun user's JWT, so the route opts out of authentication via config.auth: 'public'. To prevent an honest mistake from shipping another public route silently, the boot-time allowlist hook rejects any registration that pairs auth: 'public' with a path not in the closed set. POST /webhooks/stripe is one of five entries.

The dispatcher: api-version gate, idempotency tx, prefetch-then-write

The dispatcher's contract is "the same event delivered ten times produces one set of writes." It runs in three steps. First, a fail-closed api-version gate: each event carries Stripe's api_version, and a mismatch against the SDK's pinned STRIPE_API_VERSION (2026-04-22.dahlia at MYT-42) is treated as silent corruption — typed field access against the wrong version would read fields whose meaning has shifted between versions. The dispatcher records the event ID in a short single-purpose transaction so Stripe stops retrying, then returns without invoking any handler.

Record-only ack on api-version mismatch, not a 5xx that retries — letting Stripe redeliver wouldn't change the version mismatch, just accumulate noise. Recording the stripe_events row alone (no downstream writes) acks the event, surfaces the mismatch as a paging-grade log line, and leaves the response state on the manual-reconciliation path. The version pin is bumped via spec patch alongside an SDK upgrade — see Stripe contract.

Second, phase 1: prefetch outside any DB transaction. Several handlers need fields that aren't on the event payload — Stripe's webhook payloads don't deep-expand by default, so a checkout.session.completed event has the session ID but no line_items, and a customer.subscription.updated event doesn't carry the price's lookup_key on the items it sends. The dispatcher's PREFETCHERS table maps event types to optional async functions that call the Stripe SDK to retrieve whatever else is needed. These calls happen before opening the dispatch transaction.

Stripe API calls outside the DB tx — running an SDK call inside a held transaction pins the PoolClient for the call's duration. A Stripe outage with multi-second tail latency would block one connection per concurrent webhook delivery. The pool exhausts; unrelated requests get connection_terminated_unexpectedly; the cascade reaches /health/ready and the ALB pulls the task. Prefetch-then-write means a Stripe outage delays processing without pinning any pool slot.

Third, phase 2: a single dispatch transaction with the MYT-40 timeout discipline. The dispatcher opens a tx with three SET LOCAL statements bundled into one multi-statement query: transaction_isolation = 'read committed', lock_timeout = '1s', statement_timeout = '5s'. Inside the tx it records the event via stripeEvents.recordOrSkip (an INSERT ... ON CONFLICT (event_id) DO NOTHING RETURNING event_id), and on duplicate it ROLLBACKs and returns. On first-write the dispatcher invokes the handler with the prefetch payload and the open ClientLike, then COMMITs.

Idempotency anchored on stripe_events, not on per-handler idempotency checks — every handler runs inside a transaction whose first INSERT is the event ID. If the same event is redelivered, the conflict fires before the handler runs; the handler never sees the duplicate. Per-handler idempotency would have to reason about partial-write rollback scenarios on each handler separately. One row, one fact: this event was processed exactly once.
Three SET LOCALs, not one — same recipe as atomicDebit's. read committed is the pool default but stating it per-tx defends against future pool-config drift. lock_timeout bounds FOR UPDATE waits. statement_timeout bounds the whole transaction. SQLSTATE distinguishes them in logs.

The validation_failed sentinel

A handler returns one of three results: 'ok' commits cleanly, 'validation_failed' commits the stripe_events row and nothing else, and throw rolls the whole tx back so Stripe redelivers. The 'validation_failed' sentinel exists for a narrow case: a delivered event passes signature verification and api-version check but fails a domain-level invariant (a multi-line subscription session, a missing lookup_key, a Stripe-side amount that doesn't match the SKU cache). Re-delivering wouldn't change the answer; but the event must be acked so Stripe stops retrying. The dispatcher logs at error level so paging-grade alarms can fire on the pattern.

Three return values, not two — without the sentinel, a handler facing a domain invariant violation would have to choose between throwing (Stripe redelivers; log noise) or committing the writes anyway (corruption). The sentinel splits the third path — the stripe_events row commits, the rest of the writes don't, the operator gets a paging log line. The handler is contractually required to have written nothing else when it returns the sentinel; a regression test pins this.

The eight event handlers

Each handler is a single file under backend/src/billing/webhook-*.ts and exports one function plus an optional prefetcher. The dispatcher's HANDLERS table maps event types to those functions; new event types ship as new files plus one line added to the table.

checkout.session.completed

Two distinct branches keyed by session.mode. Both first lock the users row referenced by session.metadata.userId and cross-check session.customer against users.stripe_customer_id — a mismatch is a paging-grade event but the handler returns 'ok' so the row commits and Stripe stops retrying (manual reconciliation handles the corruption).

In subscription mode the handler upserts user_subscriptions and writes nothing else. The credit grant is owned by the downstream invoice.paid delivery (~100 ms later for a card payment, longer for SCA or ACH). Splitting subscription state from credit grants makes both handlers idempotent regardless of delivery order.

In payment mode (à-la-carte) the handler looks up each line item against the SKU cache (the cache was populated by the boot probe — see Stripe contract), inserts one purchases row per line, inserts one billing_history row keyed on the PaymentIntent ID with kind='purchase', and grants credits via grantInTx for each line. The whole thing is one transaction; the stripe_events idempotency makes redelivery a no-op.

Subscription credit grant lives on invoice.paid, not on checkout.session.completed — Stripe's checkout-mode subscription session fires completed the moment the cart is paid, but the canonical "this billing period's credit is granted" event is the invoice.paid that arrives once the invoice settles. Treating invoice.paid as the only credit-grant trigger means the same handler covers cycle renewals (where there's no checkout session at all), trial-end conversions, and payment-method retries. The checkout-completed handler upserts subscription state without granting credit; the invoice-paid handler grants the credit when the invoice is paid.
First paid grant burns the user's trial credit (MYT-43) — when grantInTx is called with source_type in 'purchase' | 'subscription', it sums the user's unexpired trial-credit balance and writes a single deterministic-ID debit row burning it, in the same transaction as the paid grant. The handler doesn't have to reason about it; the seam lives one level down. The billing-metering page covers the mutual-exclusion invariant in full.

invoice.paid

The canonical subscription credit-grant event. The handler branches on invoice.billing_reason: 'subscription_create', 'subscription_cycle', and 'subscription_update' all grant credits; other reasons ('manual', 'subscription_threshold', etc.) are logged and skipped — Mythrun doesn't emit them today, and a stray manual invoice in the Stripe Dashboard shouldn't grant Mythrun credits. The handler resolves the tier's lookup_key via the SKU cache's byPriceId reverse map, inserts a billing_history row keyed on the invoice ID with the originating PaymentIntent stored on a separate column, and calls grantInTx with source_type = 'subscription' and source_billing_history_id pointing at the row just written. The billing_history insert uses ON CONFLICT (kind, source_id_stripe) DO NOTHING, so a redelivery is a no-op even before stripe_events sees it.

The PaymentIntent lives on billing_history, not derived at refund time — when a refund event arrives, the handler needs to find the originating invoice's billing_history row to flip its status to refunded and to read the lookup_key for the clawback. The natural shape would be an SDK call from the refund's payment_intent to the invoice; Stripe's invoicePayments.list requires invoice as the filter, not payment, so PI → invoice is not a single-call lookup. Storing the PI on the invoice row at write time and resolving via SELECT ... WHERE stripe_payment_intent_id = $1 AND kind='invoice' is one DB read with a partial index (idx_billing_history_invoice_pi) and no Stripe-side dependency.

customer.subscription.created / .updated

Both event types share handleSubscriptionUpsert: write through to userSubscriptions.upsertFromStripe. The repo method is a single INSERT ... ON CONFLICT (stripe_subscription_id) DO UPDATE with a strict WHERE excluded.stripe_event_created_at > user_subscriptions.stripe_event_created_at filter — a same-second or earlier event is rejected as a no-op. A pending_update on the subscription is treated as a gate: an upsert that would advance items mid-flight is recorded but the item shape is left at the pre-upgrade value, so the user's tier doesn't flip until pending_update_applied fires.

Strict >, not >= — Stripe's webhook ordering is not guaranteed; two events with the same created second can arrive out-of-payload-order. >= would let the second-arriving same-second event overwrite the first; > rejects it. The checkout.session.completed + customer.subscription.created race is the textbook example: both events fire within the same second on a fresh checkout.

customer.subscription.deleted

Calls userSubscriptions.markCanceled: status flips to 'canceled' and the handler preserves the payload's cancel_at_period_end bit. The distinction matters for downstream reads — a user-clicked cancel that defers to period end carries cancel_at_period_end = true, while a Stripe-initiated terminal cancel (failed-card cascade, fraud lock) sets false. The credit-ledger is not touched: per-tier credits granted earlier in the cycle remain spendable until they expire.

No credit reclamation on cancel — the spec is explicit: a cancellation does not claw back already-granted credits. The grant was paid for; the user gets to spend it through the end of the billing period it was issued for. Refunds are the lever for clawing back paid credits, and they have their own handler.

customer.subscription.pending_update_applied

This is the canonical credit-grant trigger for an in-period tier upgrade (see tier upgrade below). When a user upgrades via POST /api/billing/upgrade-tier, Stripe issues a proration invoice with payment_behavior: 'pending_if_incomplete'. If the proration settles synchronously, the subscription's items[] advance immediately and Stripe fires pending_update_applied. The handler upserts the new tier, writes a billing_history row for the proration invoice, and grants the difference in credits. If the proration goes async (SCA, ACH), pending_update_applied fires when it eventually settles; the same handler runs.

customer.subscription.pending_update_expired

No-op + log. A pending_update that didn't settle within Stripe's window expires; the upgrade route already returned upgrade_payment_pending to the caller, and the user is still on their pre-upgrade tier. There's nothing to write.

refund.created / .updated

Both share handleRefundEvent. The handler resolves the refund's payment_intent to its originating billing_history row via the partial index idx_billing_history_invoice_pi (for subscription invoices) or via purchases.stripe_payment_intent_id (for à-la-carte purchases). It inserts a new billing_history row with kind='refund', flips the originating row's status to 'refunded', and calls recordClawback on the credit ledger (a negative-amount entry with source_type = 'refund'). Re-running on the updated event is a no-op via the composite unique on (kind, source_id_stripe).

Refund post-lock re-check on the originating row — between the refund resolution and the clawback insert, a concurrent process could in principle have already flipped the row to refunded. The handler reads the row FOR UPDATE and re-checks status = 'completed' after acquiring the lock; a second-arriving update finds the row already flipped and skips the clawback. Same shape as the atomicDebit pattern's empty-ledger gotcha — the lock has to anchor on the row whose state the decision depends on.

Operating this piece

Rotate the Stripe webhook signing secret

  1. In the Stripe Dashboard, open the POST /webhooks/stripe endpoint configuration. Click Reveal signing secret to mint a new whsec_* value (the existing endpoint keeps the prior secret active until the rollover completes).
  2. Write the new value into Secrets Manager: aws secretsmanager put-secret-value --secret-id mythrun/<env>/stripe-webhook-secret --secret-string <value>. The secret shell is Terraform-managed with ignore_changes = [secret_string] on the value, so this write is safe.
  3. Roll the API service so running tasks pick up the new secret on their next boot: aws ecs update-service --cluster mythrun --service mythrun-<env>-api --force-new-deployment.
  4. Once the rollover completes, the old signing secret is auto-retired by Stripe after a brief grace window. No second-step revocation is needed; verify in CloudWatch that no stripe_webhook_signature_invalid log lines fire on the new tasks.

Diagnose a failing webhook delivery

  1. Filter CloudWatch for the request id Stripe shows in the Dashboard's webhook attempts UI: 
    filter event in ['stripe_webhook_signature_invalid',
                'stripe_webhook_api_version_mismatch',
                'billing.handler_validation_failed_committed',
                'billing.checkout_orphan',
                'billing.checkout_customer_mismatch']
| fields @timestamp, event, event_id, event_type, err
| sort @timestamp desc
| limit 50
  2. stripe_webhook_signature_invalid → secret drift. Compare Secrets Manager value against Dashboard's Reveal signing secret; rotate per the runbook above.
  3. stripe_webhook_api_version_mismatch → Stripe's account default API version was changed in the Dashboard, or a webhook endpoint is configured with an explicit API version different from the SDK pin. Both should be set to the SDK's pinned STRIPE_API_VERSION value.
  4. billing.handler_validation_failed_committed → a handler returned the 'validation_failed' sentinel. The log line includes event_id; pull the event payload from Stripe's Dashboard and reconcile manually (operator review).
  5. billing.checkout_orphan or billing.checkout_customer_mismatch → a paid checkout session arrived for a user/customer pair that doesn't reconcile against users.stripe_customer_id. Operator review: typically a Stripe-side customer record was edited out-of-band, or a stale checkout session from a deleted user account settled.

Integration points

The webhook plugin sits inside the backend runtime's Fastify app and registers before the user-facing routes — the encapsulation isolates its raw-body parser. Signature verification depends on the STRIPE_WEBHOOK_SECRET env var, which the serving module's task definition wires from Secrets Manager. The eight handlers write through the repository layer's billing namespaces and into migration 007's three tables. The Stripe contract page covers the SKU cache the handlers read for tier resolution, and billing routes covers the user-facing endpoints that produce the events the webhook ingests.

Handler return contract

Result Tx outcome Stripe sees Use case
'ok' COMMIT all writes 200, stops retrying Normal success path; orphan-but-acked paths.
'validation_failed' COMMIT (only stripe_events row) 200, stops retrying Domain invariant violation (multi-line sub, missing lookup_key, amount mismatch).
throw ROLLBACK 5xx, redelivers Programming error or transient failure that retry might fix.
