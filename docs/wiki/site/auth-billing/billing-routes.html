Billing routes

The seven HTTP routes that comprise the player-facing billing surface: one public catalogue endpoint, three authenticated reads (balance, current subscription, paginated history), one Stripe Checkout creator, one Customer Portal launcher, and one in-period tier upgrade that uses Stripe's pending_if_incomplete proration to make the upgrade non-gameable.

How it fits together

All seven routes live in backend/src/routes/billing.ts as one Fastify plugin, registered last in buildApp so it inherits the auth and onboarded chain. The plugin shares three module-level seams: the SKU cache populated by the boot probe, the findOrCreateStripeCustomer helper that lazily creates Stripe Customer records on first checkout, and the four billing-table repository namespaces that read the audit feed and subscription state.

Six routes require a JWT and a real users row (the requireOnboarded gate). One route — GET /api/billing/skus — is on the public-route allowlist because it serves the marketing-page pricing tile pre-signin. Per-route rate limits cap the SKU endpoint at 60/min and the write endpoints at 30/min to bound the cost of an attacker spinning up Stripe Checkout sessions.

Read endpoints

GET /api/billing/skus serves the SKU cache's publicListing projection — lookup_key, display name, type, credit allocation, price. The stripe_price_id is deliberately stripped from the public shape (principle of least disclosure on an unauthenticated endpoint). A 5-minute Cache-Control header lets edge caches absorb traffic spikes; the data only changes when the boot probe re-runs against a Stripe-side catalog change.

Two SKU projections, one cache — webhook handlers and the checkout route need the stripe_price_id reverse map (price ID → lookup key, lookup key → price ID for cart resolution); the public route does not. The cache holds both as separate maps and the public endpoint reads publicListing only. A future leak in the public response shape can't expose stripe_price_id because the field isn't in the projection at all.

GET /api/billing/balance returns { session, world_gen, active_subscription } — two credit-balance numbers (each a SUM over the credit ledger) plus a summary of the user's active subscription if one exists. The three reads run in parallel via Promise.all. The active_subscription shape is a small projection of the underlying row (tier_lookup_key, current_period_end, cancel_at_period_end, status) — enough for the UI to render "Sojourner, renews in 3 days" without exposing internal columns.

GET /api/billing/subscription returns the same active_subscription projection but with the additional fields the account-management UI needs (stripe_subscription_id, current_period_start, cancel_at). One row or null; cancelled subscriptions are not surfaced.

GET /api/billing/history is the cursor-paginated audit feed backed by billing_history. The cursor is a base64url-encoded { t: occurred_at_iso, i: row_id } pair — the row id breaks ties when two events share the same Stripe timestamp. Page size is 50; the response includes nextCursor: null when the feed is exhausted. An invalid cursor (decode failure, shape mismatch) returns 400 invalid_cursor.

(timestamp, id) cursor, not offset pagination — Stripe events arrive in near-real-time and the audit feed grows append-only. Offset pagination drifts on every new row written between page fetches (page 2 starts on what was the bottom of page 1). A (timestamp, id) cursor is stable: the second page picks up exactly where the first left off, even if a hundred new rows landed in between. The composite is necessary because two webhook events from one Stripe customer can carry the same second-precision timestamp.

Write endpoints

POST /api/billing/checkout takes a cart shape ({ items: [{ lookup_key, quantity }], success_url, cancel_url }), validates it against four cart rules, resolves the items against the SKU cache, ensures the user has a Stripe Customer record (lazy-creating one if not), and creates a Stripe Checkout Session. The response is { checkout_session_id, url } — the SPA redirects the user to that URL. Stripe handles payment collection; on success Stripe fires checkout.session.completed at the webhook, which produces the credit grant and audit row.

The four cart rules:

  1. Every lookup_key exists in LOOKUP_KEYS.
  2. No duplicate lookup_key in the same cart.
  3. Tier and à-la-carte items don't mix in the same cart (a recurring item can't sit alongside one-time items).
  4. A tier cart is exactly one item with quantity 1 (no quantity-2 subscription).

Each rule maps to a distinct error code (unknown_lookup_key, duplicate_lookup_key, mixed_cart, tier_cart_shape) so the SPA can show a precise message without parsing free-form text.

Server-side cart rules, not just client-side — the SPA does its own client-side validation, but the server is the only enforcement point that survives a malicious client. Stripe will happily create a Checkout Session for a five-tier cart; preventing that has to happen here. The rules are also where the spec's "no client-supplied price IDs" promise lives: the client sends lookup_key strings, the server resolves them through the SKU cache to the actual Stripe price IDs that go on the Checkout Session.
findOrCreateStripeCustomer runs OUTSIDE any held DB tx — the helper makes a Stripe SDK call to customers.create with an idempotency key. That call has multi-second tail latency under Stripe outage. Holding a PoolClient across it would pin the connection for the call's duration; the route opens no surrounding tx and invokes the helper as a top-level await. The helper itself is internally three phases (read short tx → Stripe call → write short tx with FOR UPDATE) and absorbs concurrent racers via Stripe's idempotency-key cache.

POST /api/billing/portal takes a { return_url } body, lazy-creates the Stripe Customer if needed, and creates a Customer Portal session. The response is { url }. The Portal is where users self-manage payment methods, see their invoices, and downgrade or cancel their subscription. Tier upgrades within the current billing period don't go through the Portal — see the upgrade route below.

Customer Portal handles downgrades and cancels; the API handles upgrades — Stripe's Customer Portal can switch between plans, but its proration knob isn't tunable per switch. The asymmetry that makes Mythrun's pricing fair (upgrades prorate from period start; downgrades take effect at period end) requires proration_date = current_period_start on the upgrade path, which Portal doesn't expose. The boot probe verifies the Portal config carries the asymmetric schedule_at_period_end.conditions rule for downgrades. See probe and its error classes.

POST /api/billing/upgrade-tier takes a { target_tier_lookup_key } body and orchestrates an in-period upgrade through Stripe's pending_if_incomplete payment behavior. The handler validates the target is a strict upgrade against the current tier (matching unit_amount_cents), retrieves the live subscription, refuses if a prior upgrade is already mid-flight (a populated pending_update), then calls subscriptions.update with payment_behavior: 'pending_if_incomplete', proration_date: current_period_start, and proration_behavior: 'always_invoice'.

Stripe's response carries either a populated pending_update (the proration didn't settle synchronously — SCA / ACH / decline; the handler returns 502 upgrade_payment_pending) or a null pending_update (the proration settled, items advanced; the handler returns 200 with the proration invoice ID). The pending_update_applied webhook is what produces the credit grant — see the corresponding handler.

pending_if_incomplete, not error_if_incomplete or default_incomplete — the three behaviors differ on what happens when the proration invoice can't settle synchronously. error_if_incomplete rejects the whole upgrade if SCA is needed; default_incomplete immediately advances items with a payment-pending status; pending_if_incomplete records a pending_update on the subscription, leaves the items at the pre-upgrade tier, and waits for the proration to settle before advancing. The user sees their old tier until the bank confirms; if SCA fails or the card declines, the subscription is unchanged. No "we charged you but haven't given you the upgrade" gap.
proration_date = current_period_start — period-start proration charges the tier difference for the entire current period, regardless of when in the period the upgrade happens. The alternative — proration from the upgrade timestamp — creates a gameable loop: a user upgrades on day 29 of a 30-day cycle for one day's-worth of premium credits, then cancels at period end, and ratchets through tiers paying a fraction of each. Period-start proration eliminates the lever; an upgrade is a full-tier-difference charge with no time-based discount.
Idempotency key omits period_start — the key is upgrade:${userId}:${sub_id}:${target_tier}. A naive shape would include the period start, but a user clicking the upgrade button right at a period boundary would generate two distinct keys (the first request's period vs the second's), which would let Stripe charge twice. The early-exit on tier_unchanged handles the post-COMMIT replay case where Stripe's 24-hour idempotency cache has expired but our DB shows the new tier already.

Operating this piece

Diagnose a stuck tier upgrade

  1. Symptom: a user reports clicking upgrade and seeing upgrade_payment_pending, but their tier hasn't advanced after several minutes.
  2. Pull the user's active subscription from Stripe Dashboard or via GET /api/billing/subscription as the user. If pending_update is still populated on the Stripe-side subscription, the proration invoice hasn't settled yet — SCA, ACH, or a card retry is in flight.
  3. Filter CloudWatch for billing.upgrade_* events around the user's request: 
    filter event like /billing.upgrade/ or event like /billing.handler/
| fields @timestamp, event, userId, stripe_subscription_id, latest_invoice_id
| sort @timestamp desc
| limit 50
  4. If the proration eventually settles, pending_update_applied fires; the handler advances the subscription row and grants credits. If it expires, pending_update_expired fires; the user is left on the original tier and the SPA's next balance fetch shows no change.
  5. Manual intervention is rarely the answer here — the user's bank or card is the bottleneck. Direct the user to retry from a different payment method via the Customer Portal.

Reconcile a checkout with no credit grant

  1. Symptom: a user reports a Stripe charge but no credits in their account.
  2. Look up the user's most recent rows in billing_history and credit_ledger. If billing_history has the row but credit_ledger doesn't, the handler returned 'validation_failed' or threw — both surface as paging-grade log lines.
  3. If billing_history doesn't have the row at all, the webhook never fired or failed signature verification. Check the Stripe Dashboard's webhook attempts UI for the event delivery status; rotate the signing secret if signature failures are frequent (see webhook signing secret rotation).
  4. For a one-off reconciliation grant, write a credit_ledger row directly with source_type='gift' and a free-text source_id linking to the support ticket. Don't backfill via the webhook handler — the dispatcher's idempotency check would skip the redelivery.

Integration points

The routes share the SKU cache populated by the Stripe contract boot probe; checkout and tier-upgrade both need byLookupKey for cart resolution. The webhook is the asynchronous counterpart to checkout and upgrade — Stripe fires events at the webhook when the operations complete, and the handlers there produce the credit grants and audit rows. findOrCreateStripeCustomer sits in backend/src/repo/users.ts; the helper's three-phase shape is documented on the repository layer page. Cart rule failures and upgrade preconditions return errors from the closed BillingErrorCode union in backend/src/billing/errors.ts so the SPA can branch on response.code without parsing prose.
