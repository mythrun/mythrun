Dev tool

A local-only engineering UI: a Vite-served single-page shell whose sidebar lists six entity-scoped workflow pages — Campaigns, World, Characters, Users & Access, Billing & Credits, System — and each page composes the relevant single-purpose panels into one scrolling column. A header chrome bar pins an always-on backend health pip and an active-campaign dropdown above the banner; a persistent right-side wire-log drawer owns the SSE streams for the active campaign — the player-facing pipeline stream plus, in dev, a live session-prep prose pane. The tool itself is throwaway — not a prototype of the production frontend. The ship gate (pnpm dev-tool:check) plus a four-invariant registry test keep coverage honest.

How it fits together

The dev tool is a Vite + vanilla TypeScript workspace under backend/dev-tool/, exposed as @mythrun/dev-tool in the monorepo. It serves on http://127.0.0.1:5273 via pnpm dev:dev-tool and talks to the local backend on localhost:3000 (or whatever PORT is set in backend/.env.development). The browser only sees same-origin requests because Vite's dev server proxies /api/* and /health/* to the local backend process; no CORS plugin sits on the backend.

Local-only, not staging-pointable — Mythrun ships a six-layer defense against the auth-bypass plugin ever booting in a deployed environment (see JWT middleware). A dev tool that could swap origins to point at staging would be an internet-exposed surface that mints requests with arbitrary x-mythrun-dev-sub identities — a credentialless RCE on auth. There is no env switcher, no staging mode, no CORS plugin. Staging validation goes through smoke testing instead.

The shell

src/main.ts mounts the identity switcher into the page's <header> and the shell composition root (src/shell/shell.ts) into <main> on load. The shell builds, in vertical order: the header chrome row (always-on health pip + active campaign dropdown), the banner row, then a horizontal flex row containing sidebar | mainPane | drawer. Header chrome, banner, sidebar, and drawer mount once and persist for the lifetime of the page. The mainPane is the single slot the shell lazy-mounts a workflow page into when the user clicks a sidebar leaf, tearing the previous page down before mounting the next.

Workflow-per-page, not panel-per-route — an earlier iteration of this UI mounted one panel at a time, with the sidebar listing every backend endpoint × method as its own leaf. Real E2E walks of the prep pipeline showed the cost: contextually related actions (create a campaign, watch its status, inspect its snapshot, pick a starting situation) were spread across four sidebar leaves and four mount/unmount cycles, when they should sit on one scroll. The workflow reorg flips the model: the sidebar now lists six entity pages (Campaigns, World, Characters, Users & Access, Billing, System), and each page mounts the relevant single-purpose panels inline into one scrolling column. Click "World" once → see status, live-events, snapshot, hierarchy, and random-tables stacked vertically, all wired to the same active campaign.

Every workflow page returns a PanelHandle = { root, unmount() } — the same contract individual panels return. The shell holds the currently-active handle; on sidebar selection change it calls activePage.unmount(), clears the mainPane's children, looks up the new page's mount function in the WORKFLOW_MOUNTS registry, and mounts it. The page composer's mount function in turn calls buildPageBody(parent, title) to lay out the scrolling column, then iterates over its panel list calling body.mountSection(id, mountFn) for each one. A page's unmount() walks its panel handles in reverse order, calling each panel's own unmount() before removing the section host. The sidebar's selected leaf persists across reloads in localStorage under devtool.selectedWorkflow.

The sidebar

src/shell/sidebar.ts renders the six workflow leaves from WORKFLOWS in src/shell/workflow-registry.ts: Campaigns, World, Characters, Users & Access, Billing & Credits, System — in that fixed order. Each leaf is a single line of text (no HTTP-method dimming, no per-endpoint nesting). Leaves whose entry carries requiresCampaign: true — currently World and Characters — render disabled (dimmed, cursor-not-allowed) when the active-campaign store is null, and become selectable the moment a campaign is picked. The page that owns the selected workflow is mounted lazily through getWorkflowMount(id); workflow-registry.ts itself only carries the static descriptor list (id + title + requiresCampaign) so tests that need the shape don't pay for the full panel graph at import time. The page composers register their mount fns via registerWorkflowMount(id, fn) as a side effect of being imported by main.ts.

The header chrome

src/shell/header-chrome.ts mounts a narrow always-on row above the banner with two widgets: a backend health pip that polls GET /health every five seconds and renders a green/red dot plus the round-trip latency, and an active-campaign dropdown that polls GET /api/campaigns/mine every ten seconds and lets the operator switch the active campaign without first navigating to the Campaigns page. Changing the dropdown writes through the shared setActiveCampaignId store, which fires every other subscriber (banner, sidebar dim-state, drawer SSE re-subscribe) the same way a row click in the My Campaigns panel would.

Chrome lives outside the banner, not inside it — the banner re-renders on every SSE event so its stage label can tick live with the worker. If the dropdown were nested inside the banner, the operator's open-but-not-yet-clicked select element would thrash and close on every stage transition. Pinning the chrome row above the banner gives the dropdown a stable DOM tree of its own. The health pip is in the same row only because they share the "always-on, small, monospace" visual register; the two widgets are otherwise independent.

The active-campaign store

src/shell/active-campaign.ts owns the single source of truth for "which campaign is the operator currently working on." It persists to localStorage under devtool.activeCampaignId and exposes getActiveCampaignId(), setActiveCampaignId(id | null), and onActiveCampaignChanged(cb). Four subscribers fan out from a change: the header chrome's dropdown updates its selection, the banner reads it to render its anchor and resets the cached campaign name, the sidebar re-renders to enable or dim requiresCampaign leaves, and the drawer's subscription manager opens an EventSource for the new id and closes the one for the old. A sibling activeCharacterId key co-lives in the same module; the roster panel sets it when the operator clicks "View" on a completed character, and the character-view panel reads it on mount. Clearing the campaign id automatically clears the character id — a character only exists in the context of its campaign.

The six workflow pages

Each page lives in src/pages/<workflow>-page.ts and consists of a single exported mount<Workflow>Page(parent) function plus an idempotent registerWorkflowMount(id, mountFn) call at the bottom. The composer pattern is the same across all six: call buildPageBody(parent, title) from the shared _shared/page-skeleton.ts helper, then mount each panel-section in order via body.mountSection(id, mountFn). Pages whose sections depend on an active campaign use a onActiveCampaignChanged subscription to mount or unmount that block as the store flips.

Page composition is dumb, the panels are smart — the page composers are pure layout (mount these N panel mount fns into a scrolling column, listen for active-campaign changes to show/hide the per-campaign block). All UI state lives inside the panel modules themselves, which remain single-purpose and individually testable. Splitting composition from behaviour lets the same panel module be reused by tests, by the verify harness, and (in principle) by future shells without dragging in the page-level reactive layer.

Cross-page navigation

Two custom DOM events wire panel-internal "drill in" actions to the shell's workflow switcher. mythrun.navigate-workflow carries { workflowId } and asks the shell to switch the sidebar directly — the post-create "Watch progress →" button on the campaign-create panel dispatches it with workflowId: 'world' to land the operator on the World page the moment a new campaign is in flight. mythrun.navigate (legacy) carries { method, path }; the shell maps the route to the workflow page that composes the matching panel and switches there. The roster panel's "View" button dispatches this with the character-view route, and the shell switches to the Characters page where the character-view panel sits inline among its siblings.

The wire-log drawer

src/shell/drawer/drawer.ts is the persistent right-side pane that owns every SSE subscription for the page. It composes a subscription manager (subscriptions.ts) that holds one SSE connection per subscribed campaign id, an in-process pub/sub event bus (event-bus.ts) that fans messages out to in-page subscribers, a 500-event FIFO ring buffer (buffer.ts) that holds the recent-history view, the drawer's own UI controls (pause / clear / export-to-clipboard, collapsible to a 36-px stripe), and — below the wire log — the session-prep prose pane (prose-view.ts), fed by a separate prose stream. The shell wires the pieces together once at mount time and the drawer renders rows on every bus.publish.

One SSE connection per active campaign, owned by the drawer — multiple panels need to react to the same SSE stream (status, snapshot, members, character views). If each panel opened its own connection, multiple sockets would race to the same campaign channel and multiplying open connections would trip the per-user rate limit on GET /status/stream (see pipeline status). Centralising the socket in the drawer and fanning out through an in-process bus means one socket per active campaign, and panels become cheap bus subscribers.
Fetch-based SSE, not native EventSource — the browser's built-in EventSource cannot set custom request headers, so it cannot carry x-mythrun-dev-sub to the backend's auth plugin. Every native subscription returned 403 and the drawer stayed silent. The subscription manager now uses the fetch-based openSse() helper in src/sse-client.ts: fetch with the identity header set, then a hand-rolled SSE frame parser over the response's ReadableStream. The drawer-facing API (subscribe / unsubscribe / closeAll) is identical; the in-page bus + buffer don't know which transport opened the socket.

The shell's own subscription to the bus has one extra responsibility: it forwards SSE phase, stage-started, stage-completed, and stage-failed events into the banner's stage label, so an operator watching the pipeline run sees the live stage update at the top of the page without manually refreshing any panel. The status panel inside the World page polls GET /api/campaigns/:campaignId/status every three seconds while mounted — a tactical refresh until the panel migrates to direct bus subscription. The status panel also re-renders its in-progress duration cell every one second via a local setInterval, so the "running" row counts up against the wall clock without re-fetching.

Auto-subscribe happens at three points: on shell mount, if the active-campaign id is non-null; on identity switch, after the bridge re-runs subscriptions.subscribe(active); and on every onActiveCampaignChanged notification (a row click in My Campaigns, the header dropdown changing, or a panel calling setActiveCampaignId directly). Unsubscribe happens when the active id changes (the old SSE connection aborts), when identity changes (every open socket closes via closeAll()), and when the shell itself unmounts. Pause + clear state persists across reloads in localStorage.

The session-prep prose pane

Below the wire-log list the drawer also hosts a prose pane (drawer/prose-view.ts): two accumulating <pre> panes labelled ft_context (Fast Thinker — public) and sd_playbook (Slow Thinker — secret) that fill in live while a session prep generates. It is fed by a second createSubscriptionManager the shell instantiates with urlFor: (id) => /api/dev/campaigns/${id}/prep-prose, driven by the same four lifecycle sites (mount, identity switch, active-campaign change, unmount) as the wire-log manager. Each incoming prep-delta event appends its text onto the matching field's <pre> via applyProseDelta — a pure reducer; rendering uses textContent, never innerHTML, so the prose is inert. On a campaign switch or identity change the pane resets so a new campaign's deltas don't append onto the prior one's.

A second subscription manager, not a second stream on the first — createSubscriptionManager keys its open-connection map by campaignId and early-returns if a campaign already has a connection, so it can't hold two streams per campaign. A second manager instance is the cheapest way to run the prose stream alongside the status stream without reworking the manager's keying. The prose feed pointedly does not go through the shared wire-log bus: sd_playbook prose may carry plot secrets, so it flows straight from the dev-only prep-prose route into the prose view and nowhere else — the dev-tool side of the enforced-ignorance boundary. That route exists only under AUTH_MODE=bypass, so the prose pane is dark in any environment but local dev.

The identity bridge

src/shell/identity-bridge.ts registers a single window-level listener for mythrun.identitychanged — the event the identity switcher dispatches when the operator picks a new dev-user-N. The handler runs the shell's onIdentityChange callback, which closes every drawer subscription, re-subscribes to the active campaign id (if any), and re-renders the sidebar. One listener at the shell level is enough because the active page's unmount path runs its own cleanup and the shell-owned stores are what panels read from on mount.

The panels

Forty-plus single-purpose panel modules live under src/components/. Each is a mountXxxPanel(parent) function returning a PanelHandle. They share a split-view skeleton at src/components/_shared/panel-skeleton.ts (title + action pane on the left + feedback pane on the right + a data-state attribute the verifier keys on) and a handful of shared renderers (error-block.ts, json-disclosure.ts for expandable JSON dumps, progress-strip.ts for long-running flows). Panels that need live wire data subscribe to the drawer's bus rather than opening their own SSE connection.

Three panels — hierarchy, random tables, character view — graduate beyond raw-JSON disclosure to domain renderers. The hierarchy panel parses the entity tree into a parent → child structure and renders an indented list with caret markers and child counts. The random-tables panel renders one <table> per entry with Roll | Entry columns (ranges collapse to a single value when min === max). The character view delegates to character-view-render.ts to draw a character-sheet card: name and subtitle, ability-score table with modifiers, vitals, and three sections for features, equipment, and spells. The raw-JSON disclosure stays in each panel as a collapsible footer so the operator can inspect the underlying payload when the rendered view isn't enough.

Identity

The header's identity dropdown is wired to the DEV_SUBS list (dev-user-1 through dev-user-5) from src/identity.ts. The selected value lives in localStorage under mythrun.devtool.devSub; src/api-client.ts reads it on every call and stamps it as x-mythrun-dev-sub. On first load main.ts self-bootstraps the active sub against POST /api/users/register so a developer landing on the page against a clean DB sees working panels without manual setup. Identity switches dispatch mythrun.identitychanged, which the identity-bridge catches and uses to drive the drawer + sidebar re-sync.

Verify-registry invariants

backend/dev-tool/__tests__/verify-registry.test.ts is the build-time gate against the registry rotting. It enforces four invariants over the workflow-page registry in backend/dev-tool/verify-registry.ts:

  • Forward coverage — every module under src/components/ that exports a mount* function is composed by at least one page (its id appears in some page's panels[] in PAGE_REGISTRY) OR is listed in EXEMPT_PANELS.
  • Workflow coverage — every WorkflowId in workflow-registry.ts's WORKFLOWS list has a matching PAGE_REGISTRY entry, and every PAGE_REGISTRY key is a real WorkflowId. Two-way bijection so adding a workflow forces a page composer.
  • Reverse coverage — every page composer file under src/pages/ is imported by main.ts, so registering a page that nothing pulls into the bundle is a red test.
  • Route exhaustion — the union of PANEL_EXERCISES[id] for every panel id reachable from any PAGE_REGISTRY entry's panels[], plus EXEMPT_ROUTES, covers every entry in BACKEND_ROUTES. The exempt list must itself reference real backend routes (so a stale exempt entry that names a removed route fails the test).
A test, not a runtime check — invariants enforced at runtime fail in the browser, with no actionable signal. As a vitest test they fail at CI time with a clear message ("panel X is on disk but not composed by any page") and the build never reaches the dev server. PANEL_EXERCISES is a separate map from PAGE_REGISTRY on purpose: it declares the (panel id → routes it exercises) edges without forcing the page entries to repeat them, and the route-exhaustion calculation unions them across whichever pages reach those panels.

The ship gate

The dev tool is the only place inside the repo where the prep pipeline's HTTP, SSE, and BullMQ surfaces are exercised by a human. Without enforcement, "add a new route" silently means "the dev tool has no way to trigger or observe it" — the next contributor finds out by guesswork. The gate makes the wiring an explicit, mechanical step.

Three files at backend/src/contract/ are the source of truth: pipeline-routes.ts (HTTP routes, format 'METHOD /api/path'), pipeline-events.ts (SSE event names), and pipeline-jobs.ts (BullMQ job names). Each is a readonly string[]. backend/dev-tool/coverage.json declares what the dev tool actually covers, in three matching arrays plus an exempt object whose values are human reasons for entries the tool deliberately skips. pnpm dev-tool:check runs backend/scripts/dev-tool-check.ts, which loads the contracts and the coverage JSON and calls the pure checkCoverage(contracts, coverage) function from backend/src/dev-tool-check/check-coverage.ts. It errors when a contract entry is missing from coverage and not exempt, when an exempt reason is shorter than 20 characters, and when an exempt entry references a contract entry that no longer exists; it warns when a coverage entry is no longer in the contract.

Pure function under a CLI shell, not a single script — the same pure checkCoverage runs under Vitest with synthetic fixtures, so the gate's behaviour is exercised on every test run, not only when a contributor remembers to run the CLI. The CLI shell is the thinnest possible filesystem-and-process wrapper around the pure core.

CI wires the gate through .github/workflows/dev-tool-check.yml, a peer of wiki-check.yml: it runs on every pull_request and on push: branches: [main], scoped via paths: to the gated surface so unrelated PRs don't pay CI minutes. The pipeline contract files are populated and the gate is load-bearing: the routes and events that ride the registry today are all driven by panels in the dev tool, and as of MYT-62 every BullMQ job — world-gen, character-creation, character-integration, and now session-prep — is too. The session-prep entry moved out of the exempt list when its driver landed: the live prose pane is what exercises it. (The jobs gate checks listed-or-exempt; no automated harness drives the job, so the prose surface's correctness is proven by the MYT-64 end-to-end smoke, not the gate.)

The exempt list

Two distinct exempt lists exist — one for the pipeline contracts (coverage.json's exempt object, enforced by dev-tool-check) and one for the all-routes panel-registry invariant (EXEMPT_ROUTES in backend/dev-tool/verify-registry.ts, enforced by the vitest test). The pipeline contracts' exempt object is now empty: every route, event, and job has a real coverage entry. (The session-prep job left it when MYT-62 shipped its prose-pane driver.) The verifier's EXEMPT_ROUTES currently lists four entries: POST /webhooks/stripe (signature-verified consumer, no human UI), POST /api/users/register (probe-helper embedded inside the USERS / Me panel + the dev tool's self-bootstrap), GET /api/users/check-username (same shape, embedded in the register probe-helper), and GET /api/dev/campaigns/:campaignId/prep-prose (the live prep-prose SSE — consumed by the wire-log drawer's prose pane, which is header chrome rather than a JSDOM-mountable page panel, so it can't be credited to a PAGE_REGISTRY panel).

The prose route is exempt, not panel-credited — the route-exhaustion invariant credits a route only when some PAGE_REGISTRY panel exercises it. The prose pane lives in the wire-log drawer, which is shell chrome the JSDOM verifier never mounts — the same reason the two status-SSE routes can't be credited to a panel. So the prep-prose route is exempted with a justification naming the drawer surface and the MYT-64 E2E smoke that proves it. It does not appear in coverage.json's routes[] (which is checked against PIPELINE_ROUTES, and the bypass-only prose route is deliberately not a pipeline route).
20-character minimum on exempt reasons — without a floor, the gate's escape hatch becomes a single keystroke. Twenty characters is enough room for "MYT-NN tracked, defer" and short enough that "we'll exempt this for now" stays uncomfortable.

Hard rules

Five conventions are enforced by code review and the structure of the codebase itself:

  • Local-only by design. No env switcher, no staging mode, no @fastify/cors plugin on the backend. Staging validation lives in smoke testing.
  • All HTTP calls go through api-client.ts's apiCall. No bare fetch anywhere else. No absolute URLs. The path guard rejects bare URLs (missing leading /) AND protocol-relative paths (leading //) so fetch('//evil.com/x') can't leak x-mythrun-dev-sub to a foreign origin.
  • Use .textContent, never .innerHTML. Defense against any stored-XSS-shaped response surface ever appearing in a future panel.
  • No secrets in localStorage. Only mythrun.devtool.devSub, devtool.activeCampaignId, devtool.activeCharacterId, devtool.selectedWorkflow, and a few UI prefs (drawer open / paused state) live there. Tokens, JWTs, Anthropic keys do not.
  • The ship gate is not skippable. pnpm dev-tool:check runs on every PR; merging a contract change without the matching coverage entry (or a real exempt reason) is a red CI build.

Operating this piece

Run the dev tool locally

  1. Bring up the backend per the backend page: pnpm db:up, then pnpm dev in one terminal. Wait for the app.listen log line.
  2. In a second terminal, from the repo root: pnpm dev:dev-tool. Vite reports Local: http://127.0.0.1:5273/.
  3. Open the URL. The shell mounts, the header chrome reports the backend's GET /health latency and the active campaign in its dropdown, the banner reports the active campaign (or "(no active campaign)"), the sidebar shows the six workflow leaves, and the drawer renders empty. If the active sub doesn't have a users row yet, main.ts's bootstrap fires POST /api/users/register automatically.
  4. Pick an identity from the header dropdown. The selection persists across reloads via localStorage. Every subsequent call carries it as x-mythrun-dev-sub; the drawer re-subscribes to the active campaign as the new identity.

Add a pipeline route (the shape the gate enforces)

  1. Append the route to backend/src/contract/pipeline-routes.ts in the 'METHOD /api/path' form. (And to backend-routes.ts for the all-routes invariant.)
  2. Add the route handler under backend/src/routes/ and wire it into app.ts's plugin registration.
  3. Add a panel module under backend/dev-tool/src/components/ that drives the route via apiCall. The module exports a mount<Panel> function returning PanelHandle.
  4. Decide which workflow page should compose the new panel. Open src/pages/<workflow>-page.ts and add a body.mountSection(id, mountFn) call at the right position in the column. Update verify-registry.ts: add the panel id to that page's panels[] array in PAGE_REGISTRY, and add a PANEL_EXERCISES entry mapping the panel id to the route(s) it exercises.
  5. Add the same 'METHOD /api/path' string to the routes array in backend/dev-tool/coverage.json.
  6. pnpm dev-tool:check locally — must exit 0. pnpm --filter @mythrun/backend test backend/dev-tool/__tests__/verify-registry.test.ts locally — must pass. The same PR contains all six changes; CI runs the same checks on push.

Exempt a contract entry (rare)

  1. Add the contract string as a key under coverage.exempt.<routes|events|jobs> in backend/dev-tool/coverage.json. The value is the reason.
  2. Write a real reason of at least 20 characters: who decided, why the dev tool can't drive it, and the Linear/MYT-* issue tracking the gap.
  3. Open the PR with the exempt change visible alongside the contract change. Reviewers push back if the reason isn't substantive.
  4. When the issue lands and adds coverage, the exempt entry is removed in the same PR — leaving a stale exempt entry whose contract entry no longer exists red-CI's the gate.

Diagnose a failing dev-tool:check

  1. The script prints one error: line per problem. Read the line — each names the kind (routes / events / jobs), the entry, and the action required.
  2. "in contract but not in coverage and not in exempt" — add the panel + page composition + coverage entry, or add an exempt entry with a real reason.
  3. "exempt reason is too short" — write a real reason (≥ 20 characters).
  4. "in exempt but no longer in contract" — drop the exempt entry.
  5. Warnings (warn: prefix) — coverage entry no longer in contract. Non-fatal; consider removing the coverage line.

Integration points

The dev tool drives the backend's HTTP surface through the Vite proxy and consumes the same x-mythrun-dev-sub header the auth-bypass plugin in the JWT middleware reads to populate request.user in development. The wire-log drawer attaches to the pipeline status stream, which the world-gen worker and the character-creation pipeline publish events into. The Characters page renders the character-integration finalize button alongside the per-player submission panels. Staging validation goes through smoke testing, not this tool.
