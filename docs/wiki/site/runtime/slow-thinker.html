Slow Thinker

The omniscient narrative director (Opus) — but it runs off the hot path. After each DM turn completes, a background pipeline decides whether the scene needs direction and, if so, writes a leak-safe stage direction the Fast Thinker consumes on its next turn. It owns the running summary, gates its own expensive Opus call behind a cheap Haiku classifier, and signals the session wind-down. Player-visible latency is unaffected: every turn's time-to-first-token is purely the FT.

How it fits together

The architecture's spec ran the Slow Thinker before the Fast Thinker on evaluated turns, blocking the player-visible stream behind an Opus call. MYT-69 moves it after the turn, into a background pipeline. A flushed DM turn enqueues an st-evaluation job; a dedicated worker — the sixth in the worker process — runs policy → gate → evaluate → write, all off the hot path. Its outputs land in Redis slots the next turn's worker reads. The session-turn conductor no longer calls the ST at all; the in-turn tier seam is retired.

Post-hoc beats the spec'd pre-FT flow — the ST's monitors are retrospective by nature: tonal monotony, pacing stalls, NPC-only revelations, and missing agency all judge what has been happening. Run post-hoc, the ST also sees what the FT actually wrote, which a pre-FT ST never could. Player-visible latency goes to zero permanently. The accepted trade is that interventions land one turn late — fine for narrative nudges, which are session-level and age well. The two cases that need in-turn ST judgment are out of this path by construction (the world-fact lookup relay and the secret tripwire are later issues' resolvers, not this background loop).

This is also the mechanism behind Mythrun's NPC authenticity. The FT cannot plot-dump what it does not know — from its seat a merchant genuinely has nothing to offer a stranger but weather and prices, so it plays small talk in full and trust builds the way it does at a real table. The ST holds the secrets and the social clock: it watches rapport build and decides when a conversation has earned a reveal, portioning out exactly what the NPC entrusts. Enforced ignorance is not only the safety boundary here; it is the authenticity engine.

The queue: single-flight per campaign, no TTL

The producer is the turn worker's post-turn finally phase, gated on the flushed-success path only (a failed / lock-lost / converge run has no fresh FT response to evaluate) and wrapped in its own try/catch, so an enqueue hiccup never masks the turn outcome. enqueueStEval adds one job with the per-campaign dedup id st-eval:{campaignId} and no TTL.

No dedup TTL — the key must die with the job — this is the same BullMQ lesson the DM trigger debounce learned: a ttl'd dedup key outlives the job and silently swallows every re-add until it expires. Without a TTL the key clears at job finalization, so the next turn's enqueue schedules fresh. The job carries no delay, so replace-mode is inert — dedup is the only mechanism in play. Adds while the job is waiting collapse losslessly (the job reads current state at run time). Adds while the job is active — the gate plus an Opus call, up to ~2.5 minutes — are swallowed, which is what the self-re-arm below closes.
Single-flight-per-campaign is an explicit invariant, not a dedup accident — the producer must never remove the dedup key (removing it under a waiting job would double-run). Only the job itself re-arms: at start it snapshots the responded-seq watermark; at end it checks whether newer turns landed and, if so, clears its own dedup key (removeDeduplicationKey) and re-adds — the exact dm-trigger-worker self-re-arm pattern, because a running job cannot be replaced through its own key. The residual honesty: an evaluation can lag the table by up to one job duration; "latest wins" on the slots covers the quality side.

The deterministic policy and the Haiku gate

Inside processStEvalJob, the first decision is mechanical code, not a model. Two arms force an evaluation outright, skipping the gate: turns-since-the-last-ST- run ≥ ST_EVAL_FLOOR_TURNS (the every-N-turns oversight floor), or total session usage ≥ WIND_DOWN_FRACTION × SESSION_TOKEN_BUDGET (which also flips wind-down mode on). These are policy arms around the gate — like a rate limit, they are ZFC-exempt mechanical thresholds, never prompt content.

When the policy doesn't force the evaluation, one cheap Haiku call decides whether to spend the Opus call. It sees the full secret-bearing sd_playbook, the running summary, and the recent exchange window, and returns { needed, confidence, reason }. The rule, stated in the only direction that matters: skip the Opus call IFF !needed && confidence ≥ ST_GATE_CONFIDENCE_FLOOR. Everything else evaluates — fail toward oversight.

The gate holds secrets freely because its output is consumed by code only — the gate is ST-side infrastructure: its verdict reaches no player and no FT, exactly like the DM-trigger classifier. So it reads the whole playbook (a code-side trigger extraction would be ZFC-violating string intelligence). It fires on the bookkeeping case too: "small talk with a playbook-relevant NPC is in progress" is evaluate-worthy even though the ST will likely stay out — a pass-through evaluation still rewrites the summary, which is how rapport built during small talk enters the ST's memory at all. Gate-fires ≠ intervene.
Gate independence is a hard rule — the gate's verdict and reason are never fed to the director. The gate decides only whether the Opus call happens; the director independently decides whether to intervene, and its prompt keeps "most turns: no" as its own judgment. A wrong gate must not bias the judge. A gate failure skips the cycle and logs; the floor guarantees an evaluation within ST_EVAL_FLOOR_TURNS regardless.

The Opus evaluation: the structural split

When the evaluation runs, runStDirector assembles an extensible world-state block — the sd_playbook, the running summary, the current standing directive and any unconsumed one-shot (read, never consumed — the ST manages its own slots informed, not blind), the recent exchange slice, and the PC roster with class and background — and calls Opus through the LLM client's generateObject. The output schema is the channel's leak bound:

  • reasoning — private. The ST's secret-aware thinking. Logged server-side only; it never crosses into any FT-facing artifact.
  • direction — public-facing. The one-shot stage direction (1–2 sentences, what-not-how). It crosses into the FT via the fusion seam.
  • standingDirective — a discriminated op ({ action: 'set' | 'clear' | 'keep', text }), not an empty-string/null trichotomy. One composed text the ST rewrites whole each evaluation.
  • summaryUpdate — the full replacement running summary (rewrite, not append).
The reasoning/direction split is the leak bound — there is no independent checker — forcing the secret-aware rationale into its own reasoning field is what keeps ride-along leaks out of the direction text (the dominant leak mode: a secret rationale riding along in the direction). The contract, stated precisely: a direction carries behavior plus ST-sanctioned reveal content — bounded to exactly what the ST decided the NPC may surface — never unsanctioned secret rationale. An earned reveal ("on a successful Persuasion he shares that he saw the bargehand try the lock — nothing more") is information crossing the channel, and that is sanctioned by design: the ST is the single gate, the reveal text is its output, and the why stays private. A blanket classifier over the direction can verify form (behavioral phrasing, no verbatim secret strings) but not sanction, which lives in the unobservable reasoning — so prompt hygiene plus the E2E secret-string grep are the realistic enforcement, permanently.
A repaired result is discarded whole — generateObject's repair chain hands the malformed tree, secret-bearing reasoning included, to Haiku/Sonnet with license to fix it — a repaired direction would be text the ST did not author crossing the boundary. So the wrapper surfaces repairAttempted unchanged and the worker discards the entire result when it is true: no direction, no standing change, no summary write. The cycle is simply skipped (the floor will re-evaluate). For the same reason the schema carries no .refine cross-field constraints — the set/text coupling is validated in code, not in a shape the repair chain could "fix" into validity.
The summary is a rewrite, not an append — rapport, reveal-ladder state, and time are mutable state. An appended-delta summary accumulates contradictions ("Hobb is curt" + "Hobb is warm") with no current-value semantics, and an ever-growing summary would ride every gate call and unbound the Opus cost the slice design keeps bounded. The director returns the full replacement (~150–300 words) each evaluation, with the old summary in context to rewrite from. Its content mandate is the trust machinery: NPC rapport levels, in-progress reveal-ladder state (and the rule that a directed reveal must actually appear in the transcript before a ladder advances), and coarse time progression.

The seven direction classes

The prompt's taxonomy spans craft and content. The four classic monitors — tonal monotony, pacing stalls, NPC-only revelations, missing agency — are craft interventions (how, not what: "three exchanges of dread — inject something mundane and warm"). On top of those sit the content classes the authenticity thesis makes first-class: earned reveals (a graded, behaviorally-bounded reveal once rapport warrants it), check-gated reveal ladders (staged across evaluations — direct the tell, let the check ride the FT's roll_skill_check, direct the next rung after the pass lands), playbook beats (secret-free behavioral events), secret-integrity steering (a boundary phrased without naming the protected content), grounding step-ins, and wind-down.

Bounds are phrased behaviorally, never by naming the withheld content — a scope bound reads "he's said all he'll say; he deflects further pressing to Vane", never "nothing about the ledger" — the latter itself tells the blind FT that a ledger exists. The craft rule both the ST and the prep prompt carry: never gate critical-path progression behind a check — gate optional or corroborating clues, and let a failure mean the information arrives by another road. And a direction is an opportunity, not an order: it was written one turn ago, so if the scene has moved against it the FT lets it go (the ft-system prompt carries the same conditionality).

The slots and how the next turn consumes them

Two direction shapes land in trigger-state (campaign-scoped Redis), consumed differently by the next DM turn:

  • One-shot (direction:oneshot) — latest-wins SET (a newer evaluation overwrites an unconsumed direction; the ST saw the pending value, so the overwrite is informed). The turn worker takes it atomically (GETDEL) on its fresh-run arm only — after lock acquisition and after the converge/latch early exits — and the conductor fuses it onto the last user message before the FT render, through the unchanged fusion seam.
  • Standing (direction:standing) — set/replaced/cleared by the ST, read (not cleared) every DM turn and appended as a raw [DM direction: …] tail message at the FT boundary, after buildModelMessages places the cache breakpoints.
Take only on the fresh-run arm; read the standing every turn — taking the one-shot before the converge/latch exits would burn a sanctioned reveal on a turn that never renders, and a take by a contention loser would starve the lock holder. So the GETDEL sits on the same fresh-run arm that does the render. The standing directive, by contrast, is a persistent constraint, so it is read (not consumed) on every turn. Tail placement is load-bearing: appended after the breakpoints, it rides the always-uncached zone, never perturbing the cached prefix and never shifting the sliding-breakpoint index — see the Fast Thinker's prompt assembly. The fuse-the-one-shot step runs before the standing tail is appended, because the fuser targets the last user message and appending first would fuse onto the ephemeral tail.

Summary ownership and the dedicated usage key

The running summary is the ST's artifact: the job writes the :summary key directly after each evaluation (a plain SET carrying the session-state TTL; the job is the only writer). The turn flush shrank to usage-only — the controller's summary code is deleted — which removes the background-write-vs-turn-flush clobber race outright. The summary is the ST's own compression, the Scribe's session-end input, and nothing the FT ever reads.

ST spend rides a dedicated :usage:st key, summed at read — the shared :usage blob can't carry the ST's increment safely: the turn worker reads :usage at turn start, accumulates in memory across a minutes-long render, and blind-SETs at flush — an ST increment landing in that window is erased no matter how atomically it was written. So the gate's and director's tokens go to a separate :usage:st counter (atomic INCRBY), and the wind-down policy reads :usage + :usage:st summed. A Lua/WATCH on the shared key can't survive the stale-read-then-SET; only the separate-key design satisfies the bidirectional non-clobber requirement.

Wind-down and session boundaries

Wind-down is the budget policy arm: once (usage + usage:st) ≥ WIND_DOWN_FRACTION × SESSION_TOKEN_BUDGET, the evaluation is forced with the wind-down flag and the director sets a standing directive steering toward a natural close — resolve the current scene, open no new threads or NPCs — and keeps directing toward closure on subsequent evaluations. This is the ST-side signal only; the actual session_end orchestration and the FT-context hard cap belong to the session-end issue.

Session start must wipe the ST's keys, or a replayed session is born dying — a same-campaign session started within the keys' lifetime would otherwise inherit the prior session's usage and a standing wind-down directive. So POST /api/sessions/:campaignId/start resets the spend keys (:usage, :usage:st, :summary) and the ST-owned trigger-state (both direction slots + the turns-since-ST counter). The smoke surfaced the sibling hazard too: a stale responded-seq watermark made every new batch (staleWatermark, max] empty, so the DM never fired — the session-start reset now sweeps the no-TTL dm-trigger coordination keys (responded-seq, first-unresponded, last-activity, dm_responding, dm-trigger-explicit) alongside the ST keys. The st-evaluation job also re-checks the session is still active at start, so a job queued for an ended session no-ops.

Enforced ignorance

The gate and the director hold the secret-bearing sd_playbook freely — they are server-side infrastructure whose outputs that cross into the FT are exactly two: the direction and the standing text, both behavior-bound by the structural split and the prompt contract. The reasoning field and the gate verdict are logs only; the running summary stays FT-invisible (the FT's context type carries no summary). The st-evaluation worker defines its own narrow repo interface — the playbook read, the codec window, the roster read — rather than widening the FT-side TurnWorkerRepo, so the turn worker's dependency surface never gains a secret-bearing read.

The player-facing summary leak the audit nearly shipped — the running summary has a second exit: the suspend checkpoint folds it into sessions.st_running_summary, and GET /api/sessions/:campaignId/active used to return the full mapped Session row — that column included — to any campaign member. Inert while the summary was an empty stub, but the moment the ST writes rapport and ladder state, a member could read it with one REST call after any suspend. MYT-69 arms the ST, so MYT-69 ships the fix: the active-session route returns an explicit response allowlist (id / status / sessionNumber / timestamps — never stRunningSummary or any checkpoint material), pinned by a route test. See session transport.

Operating this piece

Watch a direction land on the next turn

  1. Bring up the data plane and both processes (pnpm db:up, pnpm dev, and pnpm --filter @mythrun/backend dev:worker — the worker hosts the st-evaluation worker). Start a session and fire DM turns (the fire-turn dev route, or real player chat through the trigger).
  2. After a turn flushes, watch the worker log for st-eval gate (with needed / confidence / skip) on a gated cycle, or a forced evaluation when the floor or wind-down arm fired.
  3. On an intervention, inspect the slots: GET session:{cId}:direction:oneshot holds the pending one-shot until the next turn GETDELs it; session:{cId}:direction:standing holds the standing text across turns. session:{cId}:summary reflects the rewritten running summary; session:{cId}:usage:st reflects the ST's accumulated token spend.
  4. Fire the next turn and confirm the prose visibly follows the direction — and grep the streamed text against the playbook's secret strings to confirm zero verbatim leak.

Diagnose an ST that never evaluates

  1. Confirm turns are flushing — the enqueue is gated on the flushed-success path, so a turn that converges or loses its lock never enqueues an evaluation. Check the st-evaluation queue depth.
  2. Check session:{cId}:turns-since-st. It INCRs every flushed turn and resets only when an Opus evaluation actually ran; a value ≥ ST_EVAL_FLOOR_TURNS that never resets means evaluations are being forced but failing — look for st-eval: director failed or a repair-discard warn.
  3. A job that no-ops with no matching active session means it was queued for a session that ended (or a new one started) before it ran — expected after a suspend. A standing wind-down directive that won't clear after a fresh session means the session-start key reset didn't run; verify resetSessionSpend + resetSessionKeys fired at /start.

Integration points

The Slow Thinker is the post-turn half of the session-turn pipeline: that worker enqueues the evaluation on its flushed-success path and, on the following turn, takes the one-shot and reads the standing directive into the Fast Thinker. Its gate and director call Opus and Haiku through the LLM client's generateObject; their schemas and prompts live alongside the client. The direction slots and the turns-since-ST counter are trigger-state keys; the running summary and the dedicated :usage:st counter are session-state keys. The worker is the sixth Worker registered in the worker process. Its secret-bearing reads — the sd_playbook and the PC roster — come from the repository layer through its own narrow interface. The running summary it owns is the session prep pipeline's sd_playbook rendered into play, and the Scribe's session-end input later.

Tuning constants (st-config.ts)

Constant Default Role
ST_MODEL / ST_GATE_MODEL OPUS / HAIKU The director's tier and the gate's tier — the architecture's assignment.
ST_EVAL_FLOOR_TURNS 5 Turns-since-the-last-ST-run that forces an evaluation, skipping the gate.
ST_GATE_CONFIDENCE_FLOOR 0.8 Only a confident "no" skips the Opus call. An empirical knob — the smoke tunes it.
ST_GATE_EXCHANGE_WINDOW / ST_EVAL_EXCHANGE_WINDOW 6 / 10 Recent-slice sizes; the gate sees a tighter window than the evaluation.
SESSION_TOKEN_BUDGET / WIND_DOWN_FRACTION 400000 / 0.9 The session-bound proxy and the fraction at which wind-down trips.
ST_EVAL_TIMEOUT_MS / ST_GATE_TIMEOUT_MS 120s / 30s Background-tolerant call budgets — nothing player-visible waits on them.
ST_EVAL_MAX_OUTPUT_TOKENS 4000 Reasoning + direction + a full summary rewrite is long; the SDK default truncates.
ST_SUMMARY_TARGET_WORDS 250 The rewrite-semantics target (prompt-instructed; no hard max enforced in code).

Key (under ${MYTHRUN_ENV}:${REGION_PREFIX}:) Shape / purpose
