Pipeline status

The campaign-scoped status surface — a JSON snapshot endpoint plus an SSE stream — that lets clients watch a campaign's world-gen and character-creation pipeline progress in real time. One Redis channel per campaign, one dedicated PSUBSCRIBE'd ioredis client per API process, and an in-memory fan-out from there to every attached SSE sink.

How it fits together

Two endpoints under /api/campaigns/:campaignId/* are the consumption surface: GET .../status is a one-shot read and GET .../status/stream is the long-lived SSE attachment. Both compute the same shape — a phase, a stages list, and the cumulative pipeline cost — from the same three sources: the campaign row, its world row, and the latest pipeline_runs entry per (stage, user_id) tuple. The stream variant delivers that shape as its first frame and then forwards live worker events for the rest of the connection.

Snapshot is the first SSE frame, not a separate fetch — a naive client that fetches GET /status and then opens GET /status/stream has a 50–200 ms window where worker events published between the two calls are lost. Sending the snapshot inside the SSE handler (after subscriber attachment but before live forwarding) closes that race. The standalone GET /status remains for callers that want a point-in-time read without holding a connection open.

The status surface itself is the consumption side: the worker (real processors landed across MYT-49 / MYT-51 / MYT-52) is what publishes events to Redis; this page documents how those events reach attached clients. The contract files backend/src/contract/pipeline-routes.ts and pipeline-events.ts declare the surface — two routes, sixteen event types. All sixteen arms have producers (six lifecycle from the processor, seven entity / edge from the streaming extractor + the post-COMMIT finalizedEvents pipe, three per-fact arms from coherence pass) AND a consumer in the dev tool's wire-log drawer. The bridge itself is type-blind: every JSON payload published on a campaign channel is forwarded to attached sinks unchanged. The WORLD / Status panel renders the snapshot's phase + stages list; the drawer renders all sixteen event arms as wire-data rows in chronological order.

The two endpoints

Method & path Auth Rate limit Response
GET /api/campaigns/:campaignId/status requireCampaignMember via the standard onboarded + access-control chain 60 / min per IP 200 { phase, stages[], cumulativeCostUsd }; 404 { code: 'campaign_not_found' } when the campaign or its world is gone.
GET /api/campaigns/:campaignId/status/stream Same — same membership semantics, same chain 10 / min per USER (keyGenerator reads requireDbUser(req).id; falls back to req.ip if the chain didn't attach dbUser) text/event-stream. First frame: event: snapshot\ndata: {...}\n\n (same shape as the snapshot endpoint). Subsequent frames: JSON-discriminated-union event payloads on the default message channel; periodic :keepalive\n\n comments; a terminal event: close\ndata: { reason }\n\n before the response ends.
Per-user rate-limit on the stream, per-IP on the snapshot — EventSource auto-reconnects (~3 s) on every close. A user on a flaky network or watching two campaigns at once burns through a per-IP 10/min cap and locks themselves out of the surface they need to see their pipeline progress. The threat model — "burst-open many connections to leak resources" — is per-user, not per-IP, and matches the ws-ticket route's existing precedent. The snapshot stays per-IP because cheap polling is the abuse shape there.
Route param is :campaignId, not :id — requireCampaignMember reads request.params.campaignId directly (matching the established sessions.ts ws-ticket convention). Using :id would 500 every request because the auth pre-handler couldn't resolve the param. The parent spec text says :id in §9; this implementation standardises on :campaignId for every campaign-scoped route going forward.

The pub/sub channel

Channel naming is {redisKeyPrefix}pipeline:campaign:{campaignId}. Concrete example: staging:use1:pipeline:campaign:01HABC.... The prefix is the ${MYTHRUN_ENV}:${REGION_PREFIX}: envelope every Redis-keyed subsystem prepends — see access control & WS ticket for the cross-cutting story. Staging and production share one ElastiCache cluster, so the prefix is what scopes channels by env; PSUBSCRIBE's pattern is {redisKeyPrefix}pipeline:campaign:*.

The channel is one-per-campaign, not one-per-stream-or-user. The worker publishes a single JSON payload per event after the corresponding pipeline_runs write COMMITs; the API's in-memory map fans that out to every SSE sink attached to the campaign. Campaign-id extraction in the pmessage handler is a suffix slice — channel.slice(channelPrefix.length) — not a split on ':', because the prefix itself contains colons while UUIDv7 campaign IDs do not.

One channel per campaign, not one per (campaign × user × stage) — a multi-axis channel scheme would let the API filter at the Redis layer, but at our cardinality (single-digit subscribers per campaign, low-tens of campaigns per task) the PSUBSCRIBE fan-out costs less than re-implementing routing in application code. If the wasted-message ratio documented below ever crosses ~50% sustained, swap PSUBSCRIBE for per-channel SUBSCRIBE/UNSUBSCRIBE on attach/detach behind the existing PipelineSubscriber interface. Trivially swappable.

Phase derivation

derivePhase is a pure function in backend/src/sse/derive-phase.ts. It takes { campaign, world, runs } and returns one of eight phase strings plus the ordered stages list and the cumulative cost. The route handler and (eventually) the worker's on-transition phase event share this one function as the source of truth for what state a campaign is in.

Phase Condition
complete campaigns.status = 'active'. Overrides every other check.
not_started No pipeline_runs rows at all for the campaign or its world.
world_gen Any worldgen stage is running or pending.
world_gen_failed worlds.status = 'failed', or any worldgen stage has a failed latest attempt with no later-stage progress.
world_snapshot_ready worlds.status = 'generating' AND stage 4 (entity_relationships) has a completed latest attempt. Stage 4b (entity_consolidation) and stages 5–7 may still be running. The myth-exac snapshot endpoint becomes fetchable in this phase; the SSE client uses the signal to fire its initial GET /world-snapshot. derivePhase surfaces this state from the stage-4 commit, so the route handler's initial-frame snapshot reports it immediately. The worker's published phase event for world_snapshot_ready fires one stage later — after stage 4b commits — so reconnecting subscribers see the signal once the phantom-reference reconciliation has fully landed (see world-gen / stage 4b).
post_creation The campaign-scoped post-creation stage character_integration (MYT-54) is running or pending. This is the single-pass party-into-world weave that fires after the owner clicks finalize. See character integration.
character_creation Any character-creation stage is running or pending.
failed Any character-creation or post-creation stage failed (post-worldgen failure; unrecoverable for now).
world_ready worlds.status = 'complete' and no later-stage activity. The "waiting-for-players" state.

The query that feeds derivePhase is listLatestForCampaign in backend/src/repo/pipeline-runs.ts. It unions rows keyed by campaign_id with rows keyed by the campaign's world_id (worldgen runs attach to the world; character-creation and post-creation runs attach to the campaign), then DISTINCT ON (stage, user_id) picks the most recent attempt per slot. A stage that was failed then retried to completed reports as completed; the previous failure isn't surfaced. cost_usd is NUMERIC(10,6) in the schema, which pg returns as a string by default; the query casts it ::float8 locally so the column lands in JS as number.

Latest-attempt wins, not run-history — clients want "where is the pipeline now," not "what happened in the past." History lives on the rows themselves; the snapshot is a present-tense projection. Surfacing every retry in the snapshot would make the dev tool unreadable on any campaign that exercised the worker's retry path.
Cumulative cost is DB-canonical — both the snapshot and the worker's cost-update event sum or report the same pipeline_runs.cost_usd column. The worker only publishes cost-update after the row COMMITs, so out-of-order arrival between snapshot and stream events is impossible within a single connection. Both surfaces report ABSOLUTE values, not deltas.

SSE plumbing

backend/src/sse/sse-connection.ts wraps a Fastify Reply into an SseSink with two methods: write(frame): boolean and close(reason). The first thing it does is reply.hijack() so Fastify stops trying to manage the response — no Content-Length, no onSend/onResponse hooks fire, the response lifecycle belongs to the sink from here on. Then it writes the SSE headers directly: Content-Type: text/event-stream, Cache-Control: no-cache, no-transform, X-Accel-Buffering: no. There is no Connection: keep-alive header — that's HTTP/1.1-specific and forbidden under HTTP/2, which the ALB terminates.

The sink arms two timers. A 25-second keepalive writes :keepalive\n\n (a comment frame the client ignores) and re-arms itself on a setTimeout rather than a setInterval — every real event-write resets the keepalive too, so a busy stream doesn't pay for useless ticks. A 30-minute idle timeout fires when no real event has been written for that long and closes the sink with reason: 'idle-timeout'.

25-second keepalive, 30-minute idle close — the ALB's idle timeout is 3600 s, but corporate VPNs and dev-loop proxies can be tighter. Six bytes every 25 s pre-empts every intermediate-proxy idle drop we'd otherwise see. The 30-minute server-side idle close is the recovery path for genuinely abandoned connections; clients reconnect via a fresh /status/stream and pick up where they left off via the snapshot frame.

Close emits a structured terminal frame: event: close\ndata: { "reason": "<reason>" }\n\n. The reason is one of:

  • idle-timeout — 30 minutes with no event written. The campaign is quiet; the client is welcome to reconnect.
  • server-shutdown — the API task is draining (SIGTERM from ECS). Clients should reconnect and the ALB will route them to a surviving task.
  • redis-resync-required — the dedicated subscriber reconnected to Redis after a blip. Attached sinks may have missed messages in the gap; the safe move is to close them and let clients re-fetch via a fresh stream (whose first frame is a fresh snapshot).
  • rate-limited — reserved for future per-event rate-limit eviction; not emitted by MYT-50.
  • back-pressure — the underlying reply.raw.write() returned false and the 'drain' event didn't fire within 5 seconds. Slow client; drop-and-let-them-reconnect is the recoverable path.
  • unknown — the upstream socket closed or a write threw. Catch-all.
Close-reason enum, not a free-form message — ops needs to distinguish "campaign is quiet" from "task scaled-in" from "Redis blipped" from "slow client dropped." A small typed enum gives the dev tool and (eventually) the SPA a structured signal to drive auto-reconnect decisions and gives operators a discriminator for log queries. Six values cover the lifecycle comprehensively.

Back-pressure handling protects the 768 MB Fargate heap. raw.write() returns false when the kernel send buffer is full; the sink arms a 5-second timer and waits for the 'drain' event. If drain fires, the timer clears. If it doesn't, the sink closes with back-pressure and detaches. MYT-52's entity-event flood and myth-imxg's per-fact events shipped on top of this gate, so a slow client on a busy campaign now sees the bound at one in-flight write plus the drain window rather than buffering megabytes per second.

Cleanup listens on BOTH request.raw 'close' AND reply.raw 'close' — Fastify 5 + Node 22 emit on either depending on which end of the socket closes first. The close path is idempotent (a closed flag short-circuits repeat calls), so wiring both is safe.

The dedicated subscriber client

backend/src/sse/pipeline-subscriber.ts owns the one Redis subscriber per API process. Critically, it does NOT use deps.redisRealtime directly. Instead it calls redis.duplicate({ retryStrategy, maxRetriesPerRequest: null, enableOfflineQueue: true }) to create a sibling ioredis client with the same URL/AUTH/TLS but a different retry policy.

Dedicated client, not a shared one — once an ioredis client issues SUBSCRIBE or PSUBSCRIBE it enters subscriber mode and rejects nearly every other command. The shared deps.redisRealtime is in command mode and serves the ws-ticket store, the @fastify/rate-limit backing store, and (forthcoming) the live-session metering surface. Reusing it for PSUBSCRIBE would silently break rate-limit and ws-ticket on every task with a single SSE connection attached — a credentialless DoS shape. The dedicated client makes the mode boundary explicit at the type and lifecycle level.
Override the retry policy on the dedicated client — the base factory at redis/client.ts disables retries (retryStrategy: () => null) because the boot probe wants fail-loud semantics. The subscriber is long-lived and needs the opposite: an exponential backoff up to 30 s with no per-request retry cap (maxRetriesPerRequest: null is required for pub/sub clients in ioredis). The .duplicate(...) call threads the override-specific options through.

The subscriber holds the channel-to-sinks map: Map<campaignId, Set<SseSink>>. On 'pmessage' it extracts the campaign-id, looks up the set, and writes the JSON payload to every attached sink as a data: {...}\n\n frame. Each sink.write() is wrapped in try/catch over a snapshot of the set so one stale sink can't wedge iteration over the others; on throw, the sink is closed with unknown and removed from the set.

Reconnection is the load-bearing operational behaviour. On the first 'ready' event (initial connect), nothing has been missed, so the subscriber just re-issues PSUBSCRIBE. On every subsequent 'ready' (post-disconnect), every attached sink gets a close('redis-resync-required') push and the map clears — events published while the client was disconnected may be lost, so the safe move is to evict and let clients reconnect via a fresh stream whose snapshot frame is the resync mechanism. A 'pmessage' arriving on a channel with zero attached sinks increments a wastedMessages counter surfaced in the 60-second log.

backend/src/sse/connection-counter.ts is the observability seam. Every 60 seconds it emits a single pino log line with event: 'sse.connections.active', the current count, the max-since-last-emission, the wasted-message count, and the ECS task revision. The setInterval handle is unref()'d so the periodic log never pins the event loop during shutdown.

Operating this piece

Diagnose a stale SSE connection

  1. In the client, read the last frame on the EventSource — a structured close emits event: close\ndata: {"reason":"..."}\n\n before the socket terminates. The dev tool's status panel renders this as phase: (server closed — reason: <reason>) in the phase row.
  2. Cross-reference the reason against the enum: idle-timeout means the campaign was quiet for 30 min, server-shutdown means an ECS rolling deploy or scale-in, redis-resync-required means a Redis blip, back-pressure means a slow consumer.
  3. In CloudWatch Logs Insights against the API task group, run the canonical query: fields @timestamp, count, max_since_last, wasted_msgs, taskRevision | filter event = 'sse.connections.active' | stats sum(count) as fleet_total, max(max_since_last) as peak by bin(1m). A growing fleet_total with flat traffic suggests a connection-leak bug — sinks aren't being detached on close.
  4. For back-pressure closes specifically, search for the pino 'sse write threw — closing connection' line; the surrounding context names the campaign and the underlying cause (kernel buffer full, socket reset, ECONNRESET).

Verify the subscriber survived a Redis blip

  1. A Redis blip emits the warn-level 'pipeline-subscriber reconnecting' log line. In Logs Insights: fields @timestamp, msg | filter msg like /pipeline-subscriber reconnecting/.
  2. The subsequent recovery is the warn-level 'pipeline-subscriber reconnected — closing attached sinks with redis-resync-required' line, which carries an attached field counting the sinks that were evicted. That count is "how many clients we forced to reconnect to recover from the blip"; zero means no clients were attached during the gap.
  3. On the client side, the surviving EventSources should have received an event: close\ndata: {"reason":"redis-resync-required"}\n\n frame. The dev tool's status panel auto-stops on close; production clients will auto-reconnect once that surface lands.
  4. Confirm PSUBSCRIBE re-attached: a successful reconnect emits no error log, and the next worker publish on any campaign channel reaches new SSE attachments. If publishes are arriving but no sink receives them, check the wasted_msgs field in the next sse.connections.active emission — a non-zero value with no attached sinks is the expected steady state for any channel with no current watchers.

Watch a campaign locally

  1. Bring up the backend and the dev tool per the Dev tool runbook: pnpm db:up, pnpm dev, pnpm dev:dev-tool.
  2. Create a campaign via the dev tool's CAMPAIGNS / Create panel (freeform mode is fastest — paste a 20+ character concept and submit). The 201 response carries the campaignId; CAMPAIGNS / My campaigns shows the new row.
  3. Click a row in My campaigns to set it as the active campaign. The shell's active-campaign store notifies the wire-log drawer, which opens an SSE connection to /api/campaigns/:campaignId/status/stream and starts streaming events into the right-side drawer. Open WORLD / Status to render the snapshot's phase + stages list.
  4. To smoke-test the live-event path without the worker, publish a fake event via redis-cli: redis-cli PUBLISH "development:use1:pipeline:campaign:<id>" '{"type":"phase","phase":"world_gen"}'. The drawer appends a phase row within a frame's RTT; the WORLD / Status panel reflects the new phase on its next refresh. Unknown event types silently fall through to the drawer's chronological log (rendered, but not interpreted by the status panel).

The worker side of the contract landed across MYT-49 (BullMQ shell + wrapStream middleware), MYT-51 (world-gen processor + lifecycle events), MYT-52 (streaming entity / edge events after COMMIT), MYT-53 (per-player character-creation processor), MYT-54 (campaign-scoped character integration), and myth-imxg (per-fact events from the coherence pass). Out of scope

JWT-expiry and membership-revocation eviction mid-stream are not handled. If a user is removed from a campaign while they're holding a stream open, they keep receiving events until the next close (idle, shutdown, or resync). The 30-minute idle timeout bounds the exposure window. A proper per-frame auth re-check is a post-launch hardening item.

The entity-removed arm is reserved in the contract but no current worker code path produces it — the streaming-stages repair chain preserves array length, so dropped entities don't reach the wire. The arm is in the contract so future repair-policy changes (e.g. a "drop unrepairable rows" mode) don't have to expand the wire format piecemeal. job-failed is similarly reserved — there's no current BullMQ-level terminal failure path that publishes it; transient failures route through stage-failed + retry instead.

Close-reason enum

Reason Cause Client action
idle-timeout 30 min no event written. Reconnect if still watching.
server-shutdown API task SIGTERM / drain. Reconnect; ALB routes to surviving task.
redis-resync-required Dedicated subscriber reconnected after a blip. Reconnect; fresh snapshot recovers state.
rate-limited Reserved for future per-event eviction. Back off; not emitted by MYT-50.
