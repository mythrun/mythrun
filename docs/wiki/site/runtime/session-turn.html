Session turn

The DM-turn execution engine: a transient SessionController that, per turn, acquires a per-session distributed lock, reconstructs the Fast Thinker's history from the durable session_messages transcript, runs the fixed ST → FT → Scribe macro sequence as deterministic code, persists the rendered turn as one atomic Postgres append, and releases the lock — surviving a mid-turn container crash by converging on the durable transcript or re-running from clean state. The Fast Thinker is now real (Sonnet); the Slow Thinker and Scribe remain stubs behind the same seams MYT-69 / 73 will fill.

How it fits together

A DM turn does not run inline on the WebSocket connection. It runs as a BullMQ job on a dedicated session-turn queue, processed by a fourth Worker in the worker process — never the API process. A trigger enqueues a job (enqueueTurn); the worker acquires the lock, drives a transient SessionController through the conductor, and publishes the streamed frames to the per-campaign Redis channel that the API containers' SessionHub already fans out to live sockets. MYT-66 adds the publisher on the worker side of the same publish → subscribe → fan-out path the transport built; the worker holds no socket of its own.

The turn runs in a BullMQ job in the worker process, not inline on the socket — two properties fall out for free. BullMQ's stalled-job redelivery gives per-job crash recovery (a worker dies → the job re-runs on another), which is exactly the recovery the turn needs; and running in the worker process means an API container crash — which drops WebSocket sockets — never takes an in-flight turn down with it, and the turn worker never shares a process with a live SessionHub. The cost is one enqueue → dequeue hop (tens of ms) before streaming begins, negligible against a multi-second LLM turn.

The worker process holds two Redis clients for this: the BullMQ-tuned batch client carries the session-turn queue, and a realtime client carries the lock, the turn-state reads/writes, and the frame publishing. The lock lives next to the session state it guards.

The transient SessionController

A SessionController exists for the life of one turn and is garbage-collected after — never long-lived. Its four-method lifecycle (loadFromRedis → processDmTurn → persistTurn → flushToRedis) is driven by the worker. It is a thin orchestration shell (Zero Framework Cognition): it makes no judgment calls. It hydrates the small turn state, reconstructs the FT history, sequences the tiers, persists the rendered turn, and flushes the residual state — every reasoning call lives behind an injected tier seam.

loadFromRedis reads only the small turn state: the running summary and the usage accumulator. The FT history is not in Redis — processDmTurn reconstructs it from session_messages in Postgres each turn (below). The participant roster, the FT prep context, and the world tone are not loaded here either; the worker resolves them per turn and injects them. Between load and persist the controller mutates only its in-memory copy.

The recovery invariant: the durability point is one atomic Postgres append — persistTurn encodes the rendered assistant message into DM-turn rows, allocates a seq per row, and writes them in a single, idempotent INSERT … ON CONFLICT (turn_id, turn_ordinal) DO NOTHING. That one statement is the only durable write the controller makes. flushToRedis afterward carries only the small {summary, usage} turn state. A crash before persistTurn leaves both Postgres and Redis at the pre-turn snapshot — nothing to undo; BullMQ redelivery re-runs the turn. A crash after the commit means the turn is durable, and the re-run converges to completion rather than re-rendering (the §5 decision order below). Streamed frames are not durable state — they are transport, deduplicated client-side by turnId.

The PG-direct transcript: one store, reconstructed each turn

The FT's history and the player transcript used to be two representations of the same artifact (a Redis ft_history hot cache and the durable session_messages table). MYT-68 unifies them: session_messages is the only transcript store. Player messages persist there on receipt; at turn end the conductor appends the DM turn's prose plus its roll events (dm_text / skill_check / dice_roll rows) as part of persistTurn. Each turn, processDmTurn reconstructs the FT's multi-part history from those rows via one repo read (listFtContextRows) and the transcript-codec — the one formatter that maps rows ↔ the Mythrun-owned multi-part ConversationMessage shape, both directions, so the round-trip is byte-stable by construction (which the prompt cache depends on).

Why retire the Redis hot cache — the transcript has exactly one reader, the FT itself on the next turn, so there is no fan-out for a cache to serve. The per-turn indexed scan is noise against the multi-second LLM call, and the expensive repeated read in this architecture is the input tokens, already handled by the prompt cache. A single store also eliminates dual-representation drift outright, and the reconstruction read sits behind one repo function, so a read-through cache is an afternoon's add if PG metrics ever demand it.
The single-piece read predicate — listFtContextRows(sessionId, maxConsumedSeq) returns player rows up to the consumed watermark unioned with all DM rows, ordered by seq. Player rows above the watermark (mid-turn arrivals) are excluded — they're the next turn's batch — but DM rows are always included regardless of seq, because a DM turn's rows can carry seqs above an early-arriving next-batch player message when chat races the turn's end, and a pure seq cutoff would silently drop the DM's own prior reply. This one read is the whole FT context; there is no separate batch append, so there is exactly one formatter by construction.
Recovery is the load path — crash loud on incoherence — with one store there is no cache to drift and no rarely-run rebuild branch: the rows→multi-part reconstruction runs on every turn, so a fidelity bug surfaces on turn 2 of a smoke, not at 3am. If session_messages is absent or incoherent for a session that should have history, the codec throws TranscriptCorruptError with a seq locator and the turn fails loud (turn_error) — it never silently truncates or degrades onto the running summary.

The conductor: deterministic code, never an LLM

processDmTurn is the conductor — the fixed macro sequence. Orchestration is code; reasoning is delegated to bounded tier specialists injected into the controller:

  1. Reconstruct the history from session_messages (above) into the in-memory multi-part history.
  2. ST evaluate — st.evaluate(ctx) returns an StEvaluation. Any summaryUpdate is appended to the running summary in-memory (decoupled from intervene); the ST's token usage is accumulated.
  3. FT render — when the ST chose to intervene with a direction, it is fused onto the last user message in the reconstructed history as a bracketed [DM direction: …] constraint, in-memory only. ft.render(ctx, emit) runs the Fast Thinker's tool loop, streaming text_delta / skill_check / dice_roll frames through the latched emitter, and returns a multi-part AssistantMessage; its token usage is accumulated. (The Slow Thinker is stubbed in MYT-68, so no direction is injected yet.)
  4. Scribe — scribe.extract(ctx) fires async and non-blocking; its errors are caught, logged, and never fail the turn.
The stage direction is a constraint, and the FT never learns why — when the ST intervenes, only the direction text reaches the FT, fused onto the player's last message. The FT renders prose under the constraint but is never told the ST intervened or why. This is enforced ignorance at the turn level: the FT's view is the public conversation plus a constraint, nothing about plot or intent.
Directions are per-turn ephemera, never transcript — the fused [DM direction: …] exists only in the in-memory messages assembled for that one turn's render; it is never written to session_messages (player rows persist at receipt, pre-fusion; DM rows are output only). So past directions never accumulate in the FT's reconstructed context and a direction can never leak into the player-visible transcript or reconnect replay — its narrative effect survives only through the prose it shaped. Under PG-direct, the FT's memory is exactly the public transcript plus the current turn's direction.
Scribe is fire-and-forget, behind a promise wrapper that also catches sync throws — the Scribe extracts world-state deltas off the critical path, so its failure must never fail the player's turn. The controller wraps the call in Promise.resolve().then(() => scribe.extract(ctx)).catch(...): the .then wrapper captures a synchronous throw (a non-async Scribe that throws before returning its promise) into the same .catch as a rejection, so neither escapes. The real per-turn Scribe (tripwire + working-set append) is MYT-73; MYT-66 only establishes the async-after-turn_end seam.

The tier seam, and structural enforced ignorance

The tier seam is defined once in tiers/types.ts. The FT (and, later, the ST) read an FtTurnContext — and that type is public by construction: every field on it (campaign id, the reconstructed conversation history, the participant roster, the enforced-ignorance-safe ftContext prep doc, usage counters, a reserved workingSet) is FT-safe. Secrets simply have nowhere to live on this type. MYT-68 strengthened the seam: it added the FT-safe ftContext field and removed the old runningSummary field — that was Slow-Thinker-authored, the FT never reads it, and an ST-authored field on the FT's context type is exactly what the boundary forbids. The ST gets the summary through its own widened view (TurnContext = FtTurnContext & StSecrets) in MYT-69.

Secrets reach the ST via constructor deps, never through TurnContext — enforced ignorance (CLAUDE.md non-negotiable #1) is made structural here, not a field-discipline convention. The ST's secret material (the sd_playbook, NPC secrets, narrative threads) is loaded from its constructor dependencies; the controller never threads it through the context the FT also reads. Adding a secret to the ST's view is then a compile-time-isolated change that cannot reach FastThinker.render — the type system is the boundary. If you ever feel the urge to add a plot field to FtTurnContext so the FT can "see a little more," that is the bug the type exists to prevent.

The controller takes its three tiers by constructor injection. As of MYT-68 the Fast Thinker is real — the worker constructs a fresh SonnetFastThinker per turn with that turn's scoped skill-check projection, resolved world tone, and the worker-latched emitter — while the Slow Thinker and Scribe remain stubs (a no-op ST that never intervenes, a no-op Scribe) until MYT-69. The seam is unchanged: a later issue swaps new StubSlowThinker() for new RealSlowThinker(deps) with no conductor change.

The distributed lock

session-lock.ts is a first-party per-session lock — one container drives a campaign's turn at a time. It implements Redis's documented distributed-lock pattern on the existing ioredis dependency: SET key <token> NX PX <ttl> to acquire (a random per-acquisition token), a Lua compare-and-PEXPIRE to extend, and a Lua compare-and-DEL to release. Both Lua bodies check the token before acting, atomically, so a handle can only ever touch its own lock.

A first-party lock, no new dependency — no third-party lock library cleared the repo's dependency bar (the well-known ones are abandoned betas or non-industry-standard small-org packages). The Redis-documented SET NX PX + Lua pattern on the ioredis client we already ship adds no package and keeps the correctness requirement (compare-before-delete) visible at the call site.
Single-instance is sufficient because this is coordination, not a safety-critical mutex — the consequence of a (rare) double-acquire under a pathological pause is bounded: two turns briefly streaming for one session, absorbed by the clean-retry / never-flush-on-crash design. We are not guarding a financial invariant, so the multi-instance Redlock guarantee (and its well-known criticisms) is irrelevant. Lock expiry is judged on the single Redis server clock, so worker-to-worker clock skew never affects it.
The lock's TTL + heartbeat is the liveness signal — there is no break-stale step — the worker extends the lock on a timer while the turn runs. A crashed holder simply stops extending; the lock atomically expires within its TTL; the next worker acquires the now-free key with a plain SET NX. A manual "break a stale lock" step would be a race window (two workers both observe "stale" and both break-then-acquire); atomic TTL expiry avoids it entirely. The lock — never the dm_responding flag — decides turn ownership; that flag is the DM trigger system's drain guard (MYT-67 sets it on acquire, clears it on release, so the trigger worker won't enqueue a colliding turn), not an ownership mutex.

The lock-fenced worker: the §5 decision order

processTurnJob is the BullMQ processor — the cluster-coordination shell around the controller. It acquires the lock, sets the dm_responding drain guard, starts a heartbeat, and then runs a three-way decision that holds whether the job is a fresh run or a BullMQ re-run:

  1. Converge a durable turn. If session_messages already holds rows for this turnId (turnRowsExist), the turn happened: advance the last-responded-seq watermark, publish turn_end, and return. Never turn_error — clients would discard prose the transcript keeps, and the stuck watermark would re-answer the same batch.
  2. Terminate a streamed-but-uncommitted turn. If frames were broadcast for this turnId but nothing committed (wasTurnEmitted set, no PG rows), a retry would re-stream divergent prose and re-roll dice under the same id. Publish turn_error via the cross-container SET NX claim and throw UnrecoverableError so BullMQ skips the remaining attempts. No render.
  3. Render fresh. Publish dm_thinking, resolve the per-turn context, construct the SessionController, and run load → process → persist → flush. The lock is re-checked before processDmTurn and again, critically, before the Postgres commit, so a lost lock stops the turn before persisting, never after. On success, advance the watermark and publish turn_end.
Converge or terminate — never re-stream under one turnId — the end-of-turn write order is: check lock liveness, then the atomic PG append (the turn is durable once it commits), then the Redis flush + watermark + turn_end. Every failure after the commit (Redis flush, watermark, BullMQ ack, a crash) re-runs the job, and the re-run must converge to completion, not turn_error — the rows prove the turn happened, so finishing the flush and publishing turn_end is the only correct outcome. A failure before the commit but after any frame shipped is terminal, because Sonnet is non-deterministic and the dice re-roll — a divergent re-stream is worse than a rare dead turn.
The emitted-anything latch is a Redis SET NX keyed by turnId, set before the first publish — it must be cross-container (a stalled-reclaim lands on any worker, so an in-memory latch only covers same-process retries) and set before the first frame goes out (set-after leaves a crash window that re-streams divergent prose under the same id). The latched emitter wraps the real one: the first emit of any kind marks the latch, then awaits, then publishes. So even a crash between mark and publish trips wasTurnEmitted on the re-run.

The fresh run resolves its per-turn context from the Redis :state blob: the FT prep context (ftContext) with a Postgres re-load fallback if the blob was evicted, the world tone, and — off one read of session_participants joined to characters — the FT prompt roster plus the userId→character-name attribution map.

The roster comes from session_participants, not the :state blob — the blob's participant list is a read-modify-write maintained on WS join, where two simultaneous joins can lose a name to last-write-wins. The skill-check resolver reads session_participants (the source of truth), so the worker resolves the roster and the attribution from the same place, in deterministic joined order. Attribution is the character name, not a display name, because the FT prompt tells the model to echo the attributed name into roll_skill_check.character_name, which resolves against session_participants — a display-name attribution fail-softed the first check live in the smoke.
On lock loss, abort quietly; on a real error, rethrow — a lost lock means a successor owns the continuation, so the worker returns without flushing (the recovery invariant leaves both stores at the pre-turn snapshot) and without publishing turn_error. A real error rethrows so BullMQ applies its retry policy; the terminal turn_error on attempts-exhaustion is published by the worker's failed-event handler, not here.
The heartbeat — not the TTL — is the primary double-run guard — three coordinated facts give the concurrency property. (1) A live worker keeps extending its lock every ~15 s, so even a spurious BullMQ redelivery of a still-alive worker's job fails its tryAcquire against the live-held lock. (2) A crashed worker stops extending, so the lock expires within its TTL; the TTL (45 s) is sized so the redelivered job's acquire succeeds on the first try rather than burning retry backoff. (3) A stalled-then-resumed worker that missed both its BullMQ job-lock renewal and the session-lock heartbeat finds the lock re-acquired; its next extend returns false, it aborts, and its frames are dropped at the publisher. The pinned inequality is bullmq.lockDuration (30 s) < sessionLockTtl (45 s) ≈ stalledInterval (30 s). Honest worst-case takeover after a crash is ~30–45 s (TTL expiry + redelivery), not instant.

Release, drain, and the post-turn re-mature

A finally block always clears the heartbeat, releases the lock (a compare-and-delete, so it only ever drops the worker's own token — safe even after lock loss), and clears dm_responding so the DM trigger worker can enqueue the next turn. It then runs two drains, each in its own try/catch so a hiccup never masks the turn outcome: an explicit drain (if an @dm landed mid-turn, takeExplicitPending enqueues one explicit follow-up immediately) and a post-turn re-mature.

The post-turn re-mature closes a quiet-table dead-end — a player message that arrives while a turn is in flight is swallowed by the trigger system (the evaluate job exits on dm_responding, and a dedup'd re-add during an in-flight evaluation is dropped). Without a re-arm it would sit unanswered until the next message — or forever, at a quiet table. So at turn end, if player rows still sit above the responded watermark (listAfterSeq), the worker re-arms the trigger's quiet window so the DM comes back for them. This was found live in the MYT-68 E2E smoke; it pairs with the DM trigger debounce fixes from the same session.

Cross-process frame publishing and the turnId fence

The worker has no in-memory socket registry, so it streams a turn by PUBLISHing the DM-turn frames — dm_thinking, text_delta, the MYT-68 mechanical frames skill_check / dice_roll, turn_end, and turn_error — to the per-campaign channel. The SessionHub in every API container PSUBSCRIBEs the pattern and fans each frame out to its locally-registered sockets. The FT streams through a TurnEmitter the worker builds — a small object (emitText / emitSkillCheck / emitDiceRoll) bound to one (campaign, turn) and wrapped by the emitted-anything latch. The tier seam stays frame-agnostic — it imports no wire-frame type; the publisher builds the wire frame around each emitted piece — so the contract module stays out of every tier implementation.

Both sides derive the channel string from one helper, so a wrong channel can't silently fan out to nobody — a Redis publish to a channel no one subscribes to returns 0 and throws nothing, so a drifted channel literal would be an invisible failure. The channel format ({keyPrefix}session:campaign:{campaignId}) is extracted into contract/session-channel.ts; both the SessionHub subscriber and the turn publisher derive it there. Because the prefix itself contains colons, campaign-id extraction is a suffix-slice, never a split-on-':'. The integration test round-trips a worker-published frame through a real SessionHub subscriber, so a wrong-channel regression fails loud.
A stable turnId rides every frame so an at-least-once re-stream dedups cleanly — the turnId is allocated once by the trigger at enqueue and lives in the job payload, so it is constant across a BullMQ redelivery (a redelivered job carries the same data). The client rule: a dm_thinking with a turnId already seen replaces the prior partial render for that turn. So a retried turn (or a stalled worker's late frames) dedups rather than double-rendering. The field is what makes the non-deterministic FT safe to retry — paired with the §5 decision order, which keeps a re-run from re-streaming under the same id at all.

Turn state and the residual Redis flush

After the PG-direct change, the only LLM-tier state in Redis is the running summary and the usage accumulator (:summary, :usage in the session-state module). The FT history key (:ft_history) and its periodic checkpoint are retired — the transcript is durable in Postgres. loadTurnState reads the summary + usage with a single read; flushTurnState writes them plus a TTL refresh in one MULTI after the transcript has already committed.

The flush is the cheap tail, not the durability point — durability is the atomic Postgres append in persistTurn; the Redis flush carries only the small summary/usage state. A flush failure after the commit re-runs the job, which converges (the rows exist) and finishes the flush — so the flush is never the all-or-nothing gate it was under the old Redis-history model. Usage is accumulated in the in-memory copy and persisted by this flush, so a converging re-run is usage-safe.

The producer and the dev fire-turn trigger

enqueueTurn is the thin BullMQ producer: it adds one job carrying { campaignId, sessionId, turnId, triggerMessages, maxConsumedSeq, trigger } with no custom jobId. The per-session mutex is the lock, not a jobId-dedup — so unlike the suspend queue, turns must each land as a distinct job rather than collapse onto a shared id. The session-turn queue handle is threaded through AppDeps (sessionTurnQueue) the same way the suspend queue is, built on redisBatch in server.ts and closed at shutdown.

The maxConsumedSeq and trigger fields are the MYT-67 additions. The DM trigger system populates them: maxConsumedSeq is the watermark this turn consumes up to (the worker advances last-responded-seq to it at flush, so the next batch starts at (maxConsumedSeq, …] and a deferred follow-up never replays stale messages); trigger.kind is the decision source (explicit / solo / auto) and the optional trigger.classification is the Haiku verdict for the auto path. Both are metadata only — they never cross the tier boundary into a Fast Thinker call. The classification is the skip-ST routing hint the Slow Thinker work (MYT-69) consumes; the FT never sees it.

The dev-only POST /api/dev/campaigns/:campaignId/fire-turn is the manual poke. It resolves the campaign's active session (no active session → 409 no_active_session, so a smoke caller starts one first), reads the durable MAX(seq) for maxConsumedSeq, allocates a turnId, enqueues a single fixed-identity trigger with trigger.kind: 'explicit', and returns 202 { turnId }. The real player-chat trigger path — the trigger modes, the typing-gated quiet window, and mapping a member to their messages — is the DM trigger system (MYT-67); this dev route stays as the deterministic manual poke.

The fire-turn route is gated twice, bypass-only — the plugin registers no route unless AUTH_MODE === 'bypass', and app.ts's wiring gates the register on the same condition (defense in depth, mirroring dev-credits.ts). A production boot never reaches the handler. The dev tool drives it from a fire-turn action panel on the System page.

Operating this piece

Fire a DM turn end-to-end locally

  1. Bring up the data plane and both processes: pnpm db:up, pnpm dev (API), and pnpm --filter @mythrun/backend dev:worker (the worker that hosts the turn worker).
  2. Start a session for the campaign first: POST /api/sessions/:campaignId/start (the fire-turn route 409s without an active session). Open a WebSocket to GET /ws/session/:sessionId so you can watch the frames.
  3. POST /api/dev/campaigns/:campaignId/fire-turn with { "triggerText": "…" }. Expect 202 { turnId }, then on the socket: dm_thinking → a stream of text_delta chunks (real Sonnet prose) — interleaved with skill_check / dice_roll frames if the FT calls a tool — → turn_end, all carrying that turnId.
  4. Confirm the turn is durable in Postgres: SELECT message_type, turn_ordinal FROM session_messages WHERE turn_id = '<turnId>' ORDER BY turn_ordinal shows the DM turn's dm_text (and any skill_check / dice_roll) rows. session:{campaignId}:lock is gone (released); :summary / :usage reflect the turn. There is no ft_history key — the transcript is in Postgres.

Diagnose a turn that never completes

  1. Check the lock key session:lock:{campaignId}. A present key with a live TTL means a worker holds the turn; a present key whose TTL is counting down with no frames arriving suggests a crashed holder — it will free within the TTL (≤45 s) and BullMQ will redeliver.
  2. Inspect the session-turn queue depth and the job's attemptsMade. A job retrying repeatedly with { ran: false } means it keeps losing the acquire race — another turn is in flight for the same session.
  3. A turn that threw and exhausted its attempts publishes a turn_error frame (the worker's failed-event handler, on the final attempt). The maxStalledCount-exhaustion terminal (a holder that crashes repeatedly) does not fire that JS handler — BullMQ transitions stalled → failed inside its own Lua script and emits only a broker-side event. MYT-67 closes that gap with a QueueEvents('session-turn') subscriber (on a dedicated blocking connection) that publishes the terminal turn_error too; both publishers guard on a shared SET NX latch (turn-error-published:{turnId}) so exactly one frame ships per terminal turn regardless of path or container. See the DM trigger page.
  4. If a job re-ran but session_messages already holds rows for its turnId, the worker converged — it published turn_end and advanced the watermark without re-rendering (look for the "turn already durable in PG; converging to turn_end" warn). That is the correct outcome for a crash after the commit; a turn that streamed frames but never committed instead terminates with turn_error.

Integration points

The turn worker is the fourth Worker registered in the worker process, on its own session-turn queue. It publishes through the per-campaign channel that session transport's SessionHub subscribes to — both deriving the channel from contract/session-channel.ts. The Fast Thinker tier it runs is documented on its own page; the Slow Thinker (MYT-69) and Scribe (MYT-73) seams are still stubs. The durable transcript it reconstructs and appends lives in session_messages through the repository layer, and the mechanical frames it streams (skill_check / dice_roll) join the dm_thinking / text_delta / turn_end / turn_error frames on the transport's wire contract — which also handles their reconnect replay from the persisted rows. The residual summary/usage turn state extends the session-state Redis module the transport owns. The dev tool drives the fire-turn trigger from the System page; the session-turn queue handle is threaded through the backend's AppDeps. Upstream, the DM trigger system decides when a turn fires and is what enqueues these jobs (other than the dev poke); this worker sets the dm_responding flag and records the last-responded-seq watermark that the trigger's drain logic depends on, and the trigger system's QueueEvents subscriber closes this worker's terminal-error gap.
