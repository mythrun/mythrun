Session turn

The DM-turn execution engine: a transient SessionController that, per turn, acquires a per-session distributed lock, loads turn state from Redis, runs the fixed ST → FT → Scribe macro sequence as deterministic code, flushes state back, and releases the lock — surviving a mid-turn container crash by re-running on another worker from clean state. The cognitive tiers are stubbed here behind stable interfaces; MYT-68 / 69 / 73 each swap one stub for a real Anthropic-backed implementation against the seams defined here.

How it fits together

A DM turn does not run inline on the WebSocket connection. It runs as a BullMQ job on a dedicated session-turn queue, processed by a fourth Worker in the worker process — never the API process. A trigger enqueues a job (enqueueTurn); the worker acquires the lock, drives a transient SessionController through the conductor, and publishes the streamed frames to the per-campaign Redis channel that the API containers' SessionHub already fans out to live sockets. MYT-66 adds the publisher on the worker side of the same publish → subscribe → fan-out path the transport built; the worker holds no socket of its own.

The turn runs in a BullMQ job in the worker process, not inline on the socket — two properties fall out for free. BullMQ's stalled-job redelivery gives per-job crash recovery (a worker dies → the job re-runs on another), which is exactly the recovery the turn needs; and running in the worker process means an API container crash — which drops WebSocket sockets — never takes an in-flight turn down with it, and the turn worker never shares a process with a live SessionHub. The cost is one enqueue → dequeue hop (tens of ms) before streaming begins, negligible against a multi-second LLM turn.

The worker process holds two Redis clients for this: the BullMQ-tuned batch client carries the session-turn queue, and a realtime client carries the lock, the turn-state reads/writes, and the frame publishing. The lock lives next to the session state it guards.

The transient SessionController

A SessionController exists for the life of one turn and is garbage-collected after — never long-lived. Its three-method lifecycle (loadFromRedis → processDmTurn → flushToRedis) is driven by the worker. It is a thin orchestration shell (Zero Framework Cognition): it makes no judgment calls. It loads the turn's in-memory state, sequences the tiers, and flushes the mutated state — every reasoning call lives behind an injected tier seam.

loadFromRedis performs one bulk read: the three LLM-tier keys (:ft_history, :summary, :usage) via a single MGET, plus the participant roster from the existing :state blob. Between load and flush the controller mutates only its in-memory copy — it issues no direct Redis writes of its own. flushToRedis is the single atomic write at the end.

The recovery invariant: nothing durable is written before flush — because the controller only ever mutates in-memory state until the final atomic flush, a crash mid-turn leaves Redis at the exact pre-turn snapshot. There is nothing to undo. A redelivered job re-runs the whole turn from clean state, and (with stub tiers) the re-run is byte-identical. This is what makes BullMQ's at-least-once delivery safe and deterministic here. Streamed text_delta frames are not durable state — they are transport, at-least-once, deduplicated client-side by turnId (see below).

The conductor: deterministic code, never an LLM

processDmTurn is the conductor — the fixed macro sequence. Orchestration is code; reasoning is delegated to bounded tier specialists injected into the controller:

  1. ST evaluate — st.evaluate(ctx) returns an StEvaluation. Any summaryUpdate is appended to the running summary in-memory (decoupled from intervene); the ST's token usage is accumulated.
  2. FT render — each trigger message is appended to ft_history as a user message. When the ST chose to intervene with a direction, that direction is fused onto the last trigger's content as a bracketed [DM direction: …] constraint. ft.render(ctx, emit) streams text_delta frames through emit and returns an AssistantMessage, which is appended to history. The controller then publishes turn_end.
  3. Scribe — scribe.extract(ctx) fires async and non-blocking after turn_end; its errors are caught, logged, and never fail the turn.
The stage direction is a constraint, and the FT never learns why — when the ST intervenes, only the direction text reaches the FT, fused onto the player's last message. The FT renders prose under the constraint but is never told the ST intervened or why. This is enforced ignorance at the turn level: the FT's view is the public conversation plus a constraint, nothing about plot or intent.
Scribe is fire-and-forget, behind a promise wrapper that also catches sync throws — the Scribe extracts world-state deltas off the critical path, so its failure must never fail the player's turn. The controller wraps the call in Promise.resolve().then(() => scribe.extract(ctx)).catch(...): the .then wrapper captures a synchronous throw (a non-async Scribe that throws before returning its promise) into the same .catch as a rejection, so neither escapes. The real per-turn Scribe (tripwire + working-set append) is MYT-73; MYT-66 only establishes the async-after-turn_end seam.

The tier-stub boundary, and structural enforced ignorance

The tier seam is defined once in tiers/types.ts and is the contract MYT-68 / 69 / 73 build against. The FT and ST both read an FtTurnContext — and that type is public by construction: every field on it (campaign id, trigger messages, conversation history, running summary, participant ids, usage counters, a reserved workingSet) is FT-safe. Secrets simply have nowhere to live on this type.

Secrets reach the ST via constructor deps, never through TurnContext — enforced ignorance (CLAUDE.md non-negotiable #1) is made structural here, not a field-discipline convention. The ST's secret material (the sd_playbook, NPC secrets, narrative threads) is loaded from its constructor dependencies; the controller never threads it through the context the FT also reads. Adding a secret to the ST's view is then a compile-time-isolated change that cannot reach FastThinker.render — the type system is the boundary. If you ever feel the urge to add a plot field to FtTurnContext so the FT can "see a little more," that is the bug the type exists to prevent.

The controller takes its three tiers by constructor injection, so a later issue swaps new StubSlowThinker() for new RealSlowThinker(deps) with no conductor change. The drop-in holds cleanly for the ST and Scribe; the FastThinker.render signature is flagged provisional — MYT-68's in-stream tool loop will add a tool-resolve callback and widen emit. The MYT-66 stubs make the whole pipeline run deterministically end-to-end without spending tokens: the ST never intervenes, the FT emits one canned text_delta ("(the DM considers the scene…)") then returns one canned line, the Scribe is a no-op. That is what lets the crash-recovery test assert a complete turn with no model calls.

The distributed lock

session-lock.ts is a first-party per-session lock — one container drives a campaign's turn at a time. It implements Redis's documented distributed-lock pattern on the existing ioredis dependency: SET key <token> NX PX <ttl> to acquire (a random per-acquisition token), a Lua compare-and-PEXPIRE to extend, and a Lua compare-and-DEL to release. Both Lua bodies check the token before acting, atomically, so a handle can only ever touch its own lock.

A first-party lock, no new dependency — no third-party lock library cleared the repo's dependency bar (the well-known ones are abandoned betas or non-industry-standard small-org packages). The Redis-documented SET NX PX + Lua pattern on the ioredis client we already ship adds no package and keeps the correctness requirement (compare-before-delete) visible at the call site.
Single-instance is sufficient because this is coordination, not a safety-critical mutex — the consequence of a (rare) double-acquire under a pathological pause is bounded: two turns briefly streaming for one session, absorbed by the clean-retry / never-flush-on-crash design. We are not guarding a financial invariant, so the multi-instance Redlock guarantee (and its well-known criticisms) is irrelevant. Lock expiry is judged on the single Redis server clock, so worker-to-worker clock skew never affects it.
The lock's TTL + heartbeat is the liveness signal — there is no break-stale step — the worker extends the lock on a timer while the turn runs. A crashed holder simply stops extending; the lock atomically expires within its TTL; the next worker acquires the now-free key with a plain SET NX. A manual "break a stale lock" step would be a race window (two workers both observe "stale" and both break-then-acquire); atomic TTL expiry avoids it entirely. The lock — never the dm_responding flag — decides turn ownership; that flag is the DM trigger system's drain guard (MYT-67 sets it on acquire, clears it on release, so the trigger worker won't enqueue a colliding turn), not an ownership mutex.

The lock-fenced worker and crash recovery

processTurnJob is the BullMQ processor — the cluster-coordination shell around the controller. It runs in five movements:

  1. tryAcquire the session lock. On null (a turn is already running for this session), return { ran: false }; the loser is re-driven by the DM trigger debounce, not by blind BullMQ attempts. On acquire, set the dm_responding flag (token = the lock token) so the trigger worker won't enqueue a colliding turn while this one runs (MYT-67 §4.7).
  2. Start a heartbeat (setInterval, every 15 s) that extends the lock. If an extend ever returns false — the lock expired and a successor re-acquired it — set a lockLost flag.
  3. Publish dm_thinking, construct the SessionController, and run load → process → flush. The lockLost flag is re-checked before processDmTurn and again before flushToRedis, so a lost lock stops the turn before the flush, never after. Only on a real (flushed) success does the worker advance the last-responded-seq watermark to the job's maxConsumedSeq — a lock-lost abort never flushes, so it must never advance the watermark.
  4. On a lock-lost abort, return without flushing or publishing turn_error — the winning container owns the continuation. On a real error, rethrow so BullMQ applies its retry policy.
  5. In a finally, clear the heartbeat, release the lock, then clear dm_responding so the trigger worker can enqueue the next turn. Release is a compare-and-delete, so it is safe even after lock loss — it can only ever drop the worker's own token, never a successor's. The finally also drains a pending explicit summon: if an @dm landed while this turn was in flight, takeExplicitPending enqueues one explicit follow-up immediately (in its own try/catch, so a drain hiccup never masks the turn outcome).
The heartbeat — not the TTL — is the primary double-run guard — three coordinated facts give the concurrency property. (1) A live worker keeps extending its lock every ~15 s, so even a spurious BullMQ redelivery of a still-alive worker's job fails its tryAcquire against the live-held lock. (2) A crashed worker stops extending, so the lock expires within its TTL; the TTL (45 s) is sized so the redelivered job's acquire succeeds on the first try rather than burning retry backoff. (3) A stalled-then-resumed worker that missed both its BullMQ job-lock renewal and the session-lock heartbeat finds the lock re-acquired; its next extend returns false, it aborts, and its frames are dropped at the publisher. The pinned inequality is bullmq.lockDuration (30 s) < sessionLockTtl (45 s) ≈ stalledInterval (30 s). Honest worst-case takeover after a crash is ~30–45 s (TTL expiry + redelivery), not instant.

Cross-process frame publishing and the turnId fence

The worker has no in-memory socket registry, so it streams a turn by PUBLISHing the DM-turn frames — dm_thinking, text_delta, turn_end, turn_error — to the per-campaign channel. The SessionHub in every API container PSUBSCRIBEs the pattern and fans each frame out to its locally-registered sockets. The FT streams through a TurnEmit closure the publisher binds to one (campaign, turn); the tier seam itself stays frame-agnostic (a plain (text) => Promise<void>), so MYT-68 can widen the emit without dragging the wire contract into every tier.

Both sides derive the channel string from one helper, so a wrong channel can't silently fan out to nobody — a Redis publish to a channel no one subscribes to returns 0 and throws nothing, so a drifted channel literal would be an invisible failure. The channel format ({keyPrefix}session:campaign:{campaignId}) is extracted into contract/session-channel.ts; both the SessionHub subscriber and the turn publisher derive it there. Because the prefix itself contains colons, campaign-id extraction is a suffix-slice, never a split-on-':'. The integration test round-trips a worker-published frame through a real SessionHub subscriber, so a wrong-channel regression fails loud.
A stable turnId rides every frame so an at-least-once re-stream dedups cleanly — the turnId is allocated once by the trigger at enqueue and lives in the job payload, so it is constant across a BullMQ redelivery (a redelivered job carries the same data). The client rule: a dm_thinking with a turnId already seen replaces the prior partial render for that turn. So a retried turn (or a stalled worker's late frames) dedups rather than double-rendering. With stub tiers the re-stream is byte-identical; the field is what makes MYT-68's non-deterministic FT safe to retry.

Turn state, the atomic flush, and the shared checkpoint envelope

The turn's LLM-tier state lives in three Redis keys added to the session-state module — :ft_history, :summary, :usage. loadTurnState bulk-reads them with a single MGET, JSON-parsing each with an empty default (an unset or corrupt key yields [] / '' / {input:0,output:0}). flushTurnState writes all three plus a TTL refresh in one MULTI.

Flush is one atomic MULTI, not a pipeline of independent SETs — a mid-flush failure across three separate writes could leave torn state (new history, stale usage) that a retry would then double-append. The single transaction makes the flush all-or-nothing. Usage is accumulated only in the in-memory copy and persisted solely by the flush, so a retry is usage-safe by contract.
MYT-66 writes a widened checkpoint envelope but builds no read-back — in-session crash recovery rides BullMQ redelivery + the never-flush invariant, which needs no checkpoint read. So MYT-66 does not yet deliver "recover turn state from Postgres after a full Redis loss" — that loader is a later issue. The envelope shares the sessions.st_running_summary column with the suspend writer: MYT-66 bumps the envelope kind to a superset the suspend reader still parses, the two writers are last-writer-wins, and the versioning discipline is fixed here once for the future ledger field (MYT-70).

The producer and the dev fire-turn trigger

enqueueTurn is the thin BullMQ producer: it adds one job carrying { campaignId, sessionId, turnId, triggerMessages, maxConsumedSeq, trigger } with no custom jobId. The per-session mutex is the lock, not a jobId-dedup — so unlike the suspend queue, turns must each land as a distinct job rather than collapse onto a shared id. The session-turn queue handle is threaded through AppDeps (sessionTurnQueue) the same way the suspend queue is, built on redisBatch in server.ts and closed at shutdown.

The maxConsumedSeq and trigger fields are the MYT-67 additions. The DM trigger system populates them: maxConsumedSeq is the watermark this turn consumes up to (the worker advances last-responded-seq to it at flush, so the next batch starts at (maxConsumedSeq, …] and a deferred follow-up never replays stale messages); trigger.kind is the decision source (explicit / solo / auto) and the optional trigger.classification is the Haiku verdict for the auto path. Both are metadata only — they never cross the tier boundary into a Fast Thinker call, and the stub conductor ignores them. MYT-68 / 69 read trigger.classification for the skip-ST routing.

The dev-only POST /api/dev/campaigns/:campaignId/fire-turn is the manual poke. It resolves the campaign's active session (no active session → 409 no_active_session, so a smoke caller starts one first), reads the durable MAX(seq) for maxConsumedSeq, allocates a turnId, enqueues a single fixed-identity trigger with trigger.kind: 'explicit', and returns 202 { turnId }. The real player-chat trigger path — the trigger modes, the typing-gated quiet window, and mapping a member to their messages — is the DM trigger system (MYT-67); this dev route stays as the deterministic manual poke.

The fire-turn route is gated twice, bypass-only — the plugin registers no route unless AUTH_MODE === 'bypass', and app.ts's wiring gates the register on the same condition (defense in depth, mirroring dev-credits.ts). A production boot never reaches the handler. The dev tool drives it from a fire-turn action panel on the System page.

Operating this piece

Fire a DM turn end-to-end locally

  1. Bring up the data plane and both processes: pnpm db:up, pnpm dev (API), and pnpm --filter @mythrun/backend dev:worker (the worker that hosts the turn worker).
  2. Start a session for the campaign first: POST /api/sessions/:campaignId/start (the fire-turn route 409s without an active session). Open a WebSocket to GET /ws/session/:sessionId so you can watch the frames.
  3. POST /api/dev/campaigns/:campaignId/fire-turn with { "triggerText": "…" }. Expect 202 { turnId }, then on the socket: dm_thinking → one text_delta (the canned stub line) → turn_end, all carrying that turnId.
  4. Confirm Redis turn state flushed: the session:{campaignId}:ft_history key now holds the trigger + the canned assistant line; session:lock:{campaignId} is gone (released).

Diagnose a turn that never completes

  1. Check the lock key session:lock:{campaignId}. A present key with a live TTL means a worker holds the turn; a present key whose TTL is counting down with no frames arriving suggests a crashed holder — it will free within the TTL (≤45 s) and BullMQ will redeliver.
  2. Inspect the session-turn queue depth and the job's attemptsMade. A job retrying repeatedly with { ran: false } means it keeps losing the acquire race — another turn is in flight for the same session.
  3. A turn that threw and exhausted its attempts publishes a turn_error frame (the worker's failed-event handler, on the final attempt). The maxStalledCount-exhaustion terminal (a holder that crashes repeatedly) does not fire that JS handler — BullMQ transitions stalled → failed inside its own Lua script and emits only a broker-side event. MYT-67 closes that gap with a QueueEvents('session-turn') subscriber (on a dedicated blocking connection) that publishes the terminal turn_error too; both publishers guard on a shared SET NX latch (turn-error-published:{turnId}) so exactly one frame ships per terminal turn regardless of path or container. See the DM trigger page.

Integration points

The turn worker is the fourth Worker registered in the worker process, on its own session-turn queue. It publishes through the per-campaign channel that session transport's SessionHub subscribes to — both deriving the channel from contract/session-channel.ts — and adds the dm_thinking / text_delta / turn_end / turn_error frames to that page's wire contract. Turn state extends the session-state Redis module the transport owns, and the checkpoint envelope is shared with its suspend writer. The dev tool drives the fire-turn trigger from the System page; the session-turn queue handle is threaded through the backend's AppDeps. The stubbed tiers are the seams the real Fast Thinker (MYT-68), Slow Thinker (MYT-69), and Scribe (MYT-73) implement. Upstream, the DM trigger system decides when a turn fires and is what enqueues these jobs (other than the dev poke); this worker sets the dm_responding flag and records the last-responded-seq watermark that the trigger's drain logic depends on, and the trigger system's QueueEvents subscriber closes this worker's terminal-error gap.

Server frames added (server → client only)

Frame Shape Meaning
dm_thinking { type, turnId } Turn start (the "DM is responding…" cue). No seq.
text_delta { type, turnId, text } One FT prose chunk — the only streamed content frame. No seq.
turn_end { type, turnId } Turn complete. No seq.
turn_error { type, turnId, message } Terminal failure after retries exhausted, so the client stops waiting. No seq.

Redis keys (realtime cluster)

Key (under ${MYTHRUN_ENV}:${REGION_PREFIX}:) Shape
session:lock:{campaignId} SET NX PX token (randomUUID), TTL 45 s; Lua compare-extend / compare-delete.
session:{campaignId}:ft_history The conversation the FT sees. JSON array; MGET load / MULTI flush.
session:{campaignId}:summary Running summary, maintained by the ST. JSON string.
session:{campaignId}:usage Accumulated token usage { input, output }.
session:campaign:{campaignId} (channel) Pub/sub channel the worker publishes frames to; the hub PSUBSCRIBEs the pattern.

Tuning constants (turn-worker.ts)

Constant Value Role
BullMQ lockDuration 30 s Held below the session-lock TTL so the session lock is the binding mutex.
BullMQ stalledInterval 30 s ≈ session-lock TTL so a stalled job is reclaimed after the lock has freed.
BullMQ maxStalledCount 3 Bounds retry storms on a repeatedly-crashing holder.
session-lock TTL 45 s A crashed holder's lock frees within this window.
heartbeat interval 15 s Comfortably under the TTL so a brief GC pause doesn't drop the lock.
concurrency 5 Turns processed in parallel by the worker (across distinct sessions).
