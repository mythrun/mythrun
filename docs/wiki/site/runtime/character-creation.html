Character creation

The per-player parallel character-creation surface. After world-gen completes and the wiki snapshot is fetchable, the owner picks one of the three generated starting situations for the entire party, and each member submits a character (a concept text plus a situation-grounding text). Every POST /characters commits one transaction that flips the player's character_concepts row to 'processing' AND seeds a character_concept recovery row in pipeline_runs, then — after that transaction commits — enqueues one character-creation job on the campaign-setup BullMQ queue. There is no separate owner fan-out step. Each job walks three stages (location_selection → character_concept → character_sheet) and ends with a populated characters row plus the structured concept_output JSONB blob the character integration pass consumes. The status panel and live-events feed render per-player progress via the existing campaign-scoped channel. Materializing the PC as an entities row, writing PC↔world facts and relationships, and weaving the party together happen later — in the single campaign-scoped Opus pass MYT-54 fires when the owner finalizes character creation.

How it fits together

Character creation is phase 4 of the campaign lifecycle. Phase 2 (world generation) and phase 3 (wiki read via GET /api/campaigns/:campaignId/world-snapshot) ship today. Phase 5 (cross-PC integration) shipped in MYT-54; phase 1 (pre-world-gen lobby retrofit) is a separate bead. MYT-53 owns the middle two steps — owner picks situation, members submit characters and the per-player pipeline auto-fires on submit — plus the three-stage worker pipeline that turns those submissions into characters ready for the campaign-scoped integration pass.

Strict order, not permissive — players cannot submit characters until the owner has chosen a starting situation. The strictness eliminates a class of edge cases ("what if a player submitted before the owner picked?") and makes the frontend trivial: the POST /characters route returns 409 'starting_situation_not_chosen' until campaigns.starting_situation_index is set, and the lobby displays a "waiting on owner" state. The owner choosing one situation for the entire party (not per-character) is the other half of the same simplification — different characters cannot have different starting situations and still play together. Once the situation is chosen, members no longer need an owner action to start their pipeline — submitting their character flips the row to processing (committed alongside a recovery row) and enqueues the job right after that transaction commits.

The two-prompt model

The character-submission body carries two load-bearing text fields, and the separation is what gives players agency on both axes:

  • conceptText (20–4000 chars): "Who is this character?" — identity, race, class, background, personality, backstory. Stage 2 (character_concept) consumes it.
  • situationGroundingText (20–2000 chars, always required): "Why is this character at this tavern?" — the player's framing of how their PC arrives at the owner-chosen opening. The MYT-54 integration pass consumes it when weaving the PC into the world.

Without the grounding prompt the integration pass has only a generic "introduce this PC to the world" instruction to work with; with it, the pass has the player's specific entry-point narrative to weave through the PC's facts and PC↔world relationships. The frontend reframes the grounding prompt for late joiners ("describe the situation the party is currently in and how your character fits") but the backend column is the same.

Both fields required in v1; guided-choices deferred to its own bead — the freeform path is the only consumer today, so the body schema is a two-field object with both strings required (20..4000 / 20..2000, mirroring the CHECK bounds in migration 016). The character_concepts.guided_choices JSONB column persists as the default {}; a future guided-character-creation bead lights up the picker UI, extends the body schema to accept a third field, and lights up the deterministic-assembly path in stages 2–3 without reshaping the route. Dropping the optional field today means a sharper 400 on bad bodies and one less branch to keep covered.

The eight routes

Method & path Auth Purpose
POST /api/campaigns/:campaignId/starting-situation Owner Sets campaigns.starting_situation_index to one of {0, 1, 2}. Idempotent while all character_concepts rows are still 'submitted' or absent.
POST /api/campaigns/:campaignId/archive Owner Soft-deletes the campaign by flipping campaigns.status to 'archived'.
POST /api/campaigns/:campaignId/characters Member In one transaction, UPSERTs the caller's character_concepts row with { conceptText, situationGroundingText }, atomically flips it from 'submitted' to 'processing', and seeds a 'pending' character_concept recovery row in pipeline_runs. After the transaction commits, it enqueues the per-player character-creation job on the campaign-setup queue. Returns 200 { conceptId, status: 'processing', jobId }. 409 'concept_locked' for 'processing' / 'completed'; 503 'queue_not_ready' if the queue connection is unhealthy. Re-POSTing while 'failed' resets the row and re-enqueues.
GET /api/campaigns/:campaignId/starting-situations Member Returns the three world-generated starting situations (worlds.starting_situation_entries) plus the chosen index, if any.
GET /api/campaigns/:campaignId/characters Member Per-member roster: userId, display name, concept status (none | submitted | processing | completed | failed), and characterId once the row exists.
GET /api/campaigns/:campaignId/characters/:charId Member The portable character — narrative half + mechanics + the four sub-tables (skills, features, equipment, spells).
GET /api/campaigns/:campaignId/hierarchy Member Tier-filtered entity hierarchy for the campaign's world (known-only by default; dev bypass widens). Mirrors the world-snapshot tier semantics.
GET /api/campaigns/:campaignId/random-tables Member The world-gen stage-6 output — the world's per-domain random tables, surfaced to members so the dev tool and any future session-runtime UI can render them.

All eight routes carry config.pipelineRoute = true and are registered in backend/src/contract/pipeline-routes.ts, so the boot-time route-audit invariant keeps the plugin, the contract, and the dev tool honest in lockstep. The character-creation job kind is registered in backend/src/contract/pipeline-jobs.ts with the deterministic id cc-<campaignId>-<userId> so a duplicate POST while a job is in flight becomes a no-op at the queue layer.

Why character_concepts is its own table, not a column on campaign_members — campaign_members is a join table; concept input is conceptually separate from membership. One row per (campaign_id, user_id) matches campaign_members's grain exactly, and a composite FK to (campaign_members.campaign_id, campaign_members.user_id) means removing a member cascades the concept row out. The concept lifecycle (status, error JSON, resubmit edits) stays self-contained rather than mixing with membership state.

The three stages

The processor in backend/src/llm/prep/character-creation-processor.ts mirrors the world-gen processor's outer loop: it claims each stage atomically, runs the LLM call outside any transaction, and marks the row completed or failed on the pool. Each stage handler owns its own persist transaction — the character_sheet stage opens one client and runs the whole sheet (character row + four satellite tables) under a single BEGIN/COMMIT, rolling back on any constraint failure. The atomic-claim helper from world-gen is parameterised on an optional userId, so character-creation rows in pipeline_runs are keyed on (world_id, stage, user_id) rather than (world_id, stage, NULL) — N players run N concurrent rows per stage without colliding. Per-player failure does not abort other parallel jobs. The fourth stage (character_integration) sketched in earlier drafts was retired in MYT-54 — its job moved to the campaign-scoped single-pass the owner triggers when every player's row reaches completed.

Stage Model Latency Cost (lower bound) Persists
location_selection none ~0.1s $0 Resolves campaigns.starting_situation_index → worlds.starting_situation_entries[index].locationEntityId. Validates the location entity still exists. Defers the actual fact write to stage 4 (the PC entity doesn't exist until then); stage 4 re-derives the same id from the same source records.

character_sheet Sonnet generateObject ~10–20s ~$0.04 Ability scores, HP / max HP / AC / proficiency bonus, plus the four sub-tables (character_skills, character_features, character_equipment, character_spells) and (MYT-70) the live ledger's opening state: starting_gold, the hit-dice pool, the caster spellcasting_progression, and the code-derived character_spell_slots rows. Single transaction: INSERT into characters (narrative + mechanics together) + INSERT into campaign_characters + bulk-INSERT into the sub-tables. characters.entity_id stays NULL until the MYT-54 integration pass backfills it.

The sheet co-evolved with the live ledger (MYT-70)

The character sheet is also the seed for the live character ledger the Rules Lawyer debits during play, so the character_sheet stage's schema and prompt grew to emit the ledger's structure. The model now produces starting_gold, a hit_die size, a spellcasting_progression archetype (full | half | third | pact | none), and per-row flags: consumable on equipment, ritual on spells, and a max_uses + recharge pair on limited features. Spell slots themselves are not asked of the model — code derives them from (progression, level) against the SRD slot tables and writes the per-level character_spell_slots rows at finalize.

The model emits one structured judgment, code derives the slots (ZFC) — the free-text class name is never string-matched. The model picks the progression archetype; the deterministic SRD tables turn (progression, level) into the slot grid. The stage also gained a coherence loop: a sheet that is Zod-valid but mechanically incoherent against those tables (a level-9 spell on a level-1 caster) triggers a full regeneration, bounded by a max attempt count, then terminal-fails loud rather than persisting a brickable character.
The prepared pin and the dedupe-merge are load-bearing for the tools — the Rules Lawyer keys casting on prepared ("currently castable," not "uses the prepare mechanic"), so the prompt is explicit that always-castable casters (sorcerers) emit all leveled spells prepared: true. And because the ledger matches items/features/spells by normalized name under a unique index, the stage mechanically dedupe-merges the model's output before insert (equipment sums quantities; features and spells keep-first) so an LLM duplicate can't terminal-fail the insert or corrupt a debit's rowcount math. The detail lives on the character ledger page.

The table's per-stage costs are the lower-bound point estimate (2K input / 1–2K output per Sonnet call, 2K input / 1K output for Opus). Realistic per-player cost is $0.20–$0.50 once the world snapshot input (8–15K tokens for a full world) and the player's grounding text reach normal sizes. A cost-cap circuit breaker receives settings.character_creation_cost_cap_usd (default $5.00) as injected CharacterCreationDeps.costCapUsd — read once by server.ts at process boot via readCostCapsAtBoot and held for the worker's lifetime. Each per-player job compares cumulative cost against the injected cap; over-cap aborts the player's stages with character_creation_cost_cap_exceeded, leaving other parallel jobs untouched. The $5 default covers ~10 players at the realistic upper bound, with headroom for the multiplayer concurrency target of 5–8 per party. An operator-edited cap requires a worker restart to take effect — by design, since the cap is global policy and worker process lifetime is the natural enforcement window.

Stages 2–3 are Sonnet — the parent pipeline spec sketched all character-creation stages as Opus. Stages 2–3 produce bounded structured output (a portable-character payload, D&D 5e SRD-compliant mechanical rows); Sonnet handles that reliably and is ~3× cheaper input, 5× cheaper output. The load-bearing PC↔world integration is Opus, but it runs out of band — see the campaign-scoped integration pass.

Lifecycle and late joiners

A member can submit a character as soon as two gates are satisfied: worlds.status = 'complete' and campaigns.starting_situation_index IS NOT NULL. Until both gates hold, POST /characters returns 409 with the specific gate code (world_not_complete or starting_situation_not_chosen). Once a row exists in 'submitted', the player can re-POST to update the prose; the route refuses updates while the row is 'processing' or 'completed' (409 concept_locked).

Enqueue after commit, with a recovery row inside the commit — the queue.add sits AFTER the submit transaction commits, never inside BEGIN. A queue.add wrapped in BEGIN/COMMIT is the "enqueued but the commit rolled back" zombie-job shape this refactor exists to eliminate. The trade is the opposite window: a Redis blip between COMMIT and queue.add could leave a concept stranded at 'processing' with no job ever running. The fix is to seed a 'pending' character_concept row in pipeline_runs inside the same transaction (mirroring world-gen's seed-row contract). A missed enqueue therefore leaves a resumable trace: derivePhase maps the 'pending' character_concept row to 'character_creation', and the worker's campaign-user atomic claim re-arms that pending row to 'running' via ON CONFLICT rather than double-inserting.

The flow is symmetric for late joiners — members who accept invites after the rest of the party has submitted — since the per-player job fires on the member's own POST, not an owner action:

  1. Late member accepts an invite. Their campaign_members row exists; no character_concepts row yet.
  2. Late member POSTs /characters. One transaction creates the row, flips it to 'processing', and seeds the recovery row; the per-player job is enqueued right after that transaction commits. No owner action required. Other members' 'completed' rows are untouched.
  3. Late-joiner's character creation runs in parallel with any other in-flight jobs.

Failure handling is per-player and resubmittable. On terminal stage failure the processor sets character_concepts.status='failed' and writes the error JSON; the player re-POSTs /characters, which commits the reset-row + recovery-row transaction and then re-enqueues the job after commit (no separate owner trigger). The processor's re-run is idempotent at the stage boundary, not delete-and-recreate: stage 3 detects an existing characters row for (campaign_id, user_id) and UPDATEs rather than INSERTs (TRUNCATE-then-INSERT on the four sub-tables). The frontend reframes the second prompt for late joiners ("describe the situation the party is currently in and how your character fits") but both forms map to the same situation_grounding_text column.

Resubmit-after-failure is idempotent on stage outputs, not a clean slate — the alternative (DELETE the partial character row on failure) would force the player to re-enter their prose just because a Sonnet call timed out once. Idempotent re-runs let a transient Anthropic 503 self-heal without losing the player's input or the work stage 2 already completed. The UNIQUE(campaign_id, user_id) on campaign_characters would otherwise turn the re-run into a constraint violation. Players who genuinely want a clean slate (different name, race, class) re-roll through an admin path — there is no member-facing DELETE in v1.

Cross-PC integration moved to MYT-54

The per-player pipeline now ends at stage 3 (character_sheet). MYT-54 retired the per-player character_integration stage 4 outright: PCs no longer become entities rows from the per-player pass. Instead, MYT-53's stage 2 (character_concept) persists its structured output to the new character_concepts.concept_output JSONB column, and the owner-triggered character integration pass reads every PC's concept output plus the world inventory in one Opus call and writes every PC entity, fact, and relationship (including PC↔PC edges) in a single transaction.

Two consequences for the per-player surface this page documents:

  • A character_concepts row reaches status='completed' after stage 3 finishes. The fifth lifecycle state, 'integrated', is set by the MYT-54 integration handler, not by anything on this page.
  • The cost-cap budget (character_creation_cost_cap_usd) covers both the per-player character_concept + character_sheet rows and the campaign-scoped character_integration row — one budget across all character-creation spend.

Operating this piece

Exercise the routes end-to-end

The Characters workflow page in the dev tool composes the per-player panels inline: starting situations (read-only list), situation pick (owner), submit character concept (member), creation progress, roster, character view, members, and finalize-character-creation. Switching identities via the dev-tool's identity switcher lets one operator impersonate every player against a single campaign and walk the full submit → processing → completed flow (no manual fan-out step — each submit enqueues its own job). Direct psql + curl remain useful for shape verification — concept rows in character_concepts, PC rows in entities, the four sub-table rows in character_* — but the page is the primary driver. The route-audit contract test (backend/src/contract/__tests__/pipeline-routes.test.ts) verifies registration drift as a side-effect of any backend type-check.

Integration points

Upstream: world gen populates worlds.starting_situation_entries (extended in MYT-53 + myth-k1ee) — stage starting_situation emits a structured three-entry array alongside the existing prose blob, with each entry carrying a title (LLM-emitted, 5–60 chars) and a locationName (worker-resolved from entities.name via locationEntityId). GET /starting-situations passes the JSONB through verbatim so older worlds without the new fields keep rendering. Downstream: the pipeline status surface carries per-player events on the same campaign-scoped channel (pipeline:campaign:{campaignId}) — each event payload carries user_id so subscribers can route per-player. The dev tool's live-events panel renders character-creation lifecycle and entity / edge events the same way it renders world-gen events.

Appendix: schema additions

Migration 016_character_concepts.sql adds one new table, two new columns, and one extended CHECK:

  • character_concepts — one row per (campaign_id, user_id). Carries concept_text, situation_grounding_text, guided_choices JSONB (reserved for the guided-mode follow-on; the route never writes it in v1), status (submitted | processing | completed | failed), and an error JSONB. Composite FK to campaign_members(campaign_id, user_id) ON DELETE CASCADE.
  • campaigns.starting_situation_index SMALLINT — CHECKed to NULL or {0, 1, 2}.
  • worlds.starting_situation_entries JSONB NOT NULL DEFAULT '[]' — the structured array of three { index, locationEntityId, prose } entries the world-gen starting_situation stage now also emits.
  • entities.entity_type CHECK extended to allow 'pc' — PCs are conceptually distinct from NPCs (one is owned by a real user, the other is purely game-fiction), so reusing 'npc' would force every "list NPCs" path to add a PC-exclusion filter.

The migration also seeds settings('character_creation_cost_cap_usd', '5.00'); server.ts's readCostCapsAtBoot helper reads it once on startup and injects the value as CharacterCreationDeps.costCapUsd. The sumCharacterCreationStageCosts(campaignId) aggregation in cost-cap.ts still runs per-job — filtered on WHERE campaign_id = $1 AND user_id IS NOT NULL AND status = 'completed' — so character-creation costs and world-gen costs are budgeted separately. Only the cap value moved to boot-time read; the cumulative-cost lookup is per-job by necessity.
