Worker

The async-execution half of the backend. A second ECS Fargate service running node dist/worker.js with ten BullMQ Workers — world-gen (concurrency 3), campaign-setup (concurrency 5), session-prep (concurrency 3), the MYT-66 session-turn worker (concurrency 5), the MYT-67 dm-trigger worker (concurrency 5), the MYT-69 st-evaluation worker (concurrency 2), the MYT-73 scribe worker (concurrency 2), the MYT-74a session-reconcile worker (concurrency 1), the MYT-74b session-analysis worker (concurrency 1), and the LLM outage-resilience llm-health-probe worker (concurrency 1, a repeatable 60s cycle) — all consuming from redisBatch, plus four QueueEvents subscribers on dedicated blocking connections: session-turn and, since the outage-resilience feature, the three prep queues. Phase 0 shipped stub processors that logged job receipt and marked complete. The real prep-stage processors landed across MYT-51 (world-gen), MYT-52 (streaming entity / edge events), MYT-53 (per-player character creation), MYT-54 (campaign-scoped character integration), and MYT-61 (session prep); the session-turn worker — the lock-fenced DM-turn conductor — joined in MYT-66, the dm-trigger decision worker in MYT-67, the post-hoc Slow Thinker's st-evaluation worker in MYT-69, the post-turn Scribe's scribe worker in MYT-73, the end-of-session reconcile worker in MYT-74a, and the post-session analysis worker in MYT-74b. The shape locked in at Phase 0 so each later stage was a coverage edit, not a service-topology change. The stub-processor file was retired in MYT-55 once the dedicated worker container caught up to the same wiring the API container already used.

How it fits together

The prep pipeline is long-running by nature: an Opus call inside the world-generation stage holds a streaming HTTP connection open for tens of seconds, and a single campaign-setup run chains multiple such calls. Running those calls inside the API service would tie up event-loop time the HTTP and WebSocket handlers need, and an OOM in a stage would kill in-flight player requests. The worker is the other side of that split: a separate service, on a separate ECS task, scaling independently from queue depth, with its own failure blast radius.

Separate service, not a sidecar — packing the worker into the API container would couple their resource limits (CPU, memory, file descriptors) and their deploy lifecycles. An Opus-heavy worker run that approached the task's memory ceiling would page-trap the API threads. Independent ECS services means the worker can be sized for batch (more memory, fewer vCPU) while the API stays sized for steady-state HTTP.

The worker entrypoint is backend/src/worker.ts. It reads the same loadEnv() contract the API does, opens connections to the same Postgres + two-Redis data plane, and then registers ten BullMQ Worker instances against redisBatch: QUEUE_WORLD_GEN (world-gen, concurrency 3), QUEUE_CAMPAIGN_SETUP (campaign-setup, concurrency 5), QUEUE_SESSION_PREP (session-prep, concurrency 3, added in MYT-61), QUEUE_SESSION_TURN (session-turn, concurrency 5, added in MYT-66), QUEUE_DM_TRIGGER (dm-trigger, concurrency 5, added in MYT-67), QUEUE_ST_EVAL (st-evaluation, concurrency 2, added in MYT-69), QUEUE_SCRIBE (scribe, concurrency 2, added in MYT-73), QUEUE_SESSION_RECONCILE (session-reconcile, concurrency 1, added in MYT-74a), QUEUE_SESSION_ANALYSIS (session-analysis, concurrency 1, added in MYT-74b), and QUEUE_LLM_HEALTH_PROBE (llm-health-probe, concurrency 1, added by the outage-resilience feature). Queue names and concurrency caps for the prep workers live in backend/src/worker/bullmq-config.ts — the single source of truth so the API-side Queue producers and the worker-side Worker consumers can't drift; the session-turn, dm-trigger, st-evaluation, scribe, session-reconcile, and session-analysis workers' own queue names and tuning constants live alongside their processors in session/turn-worker.ts, session/dm-trigger-config.ts, session/st-eval-queue.ts / session/st-config.ts, session/scribe-queue.ts / session/scribe-config.ts, session/session-reconcile.ts, and session/post-session-analysis.ts. Since myth-y2qfi the three inline prep processors register wrapped in containProcessor — the containment boundary described in Job containment below.

After the Postgres wait and before the workers register, the boot sequence runs the Voyage boot probe — one real embedQuery that asserts the embeddings provider is reachable and returning 512-dim vectors. A configuration error (bad key, wrong model or dimension) crashloops the worker so a misconfigured key can't ship and leave every world silently un-embedded; a transient Voyage outage logs loud and boots degraded (world-gen content still works; embeddings backfill on recovery). The API server runs the same probe.

The dm-trigger worker is the DM trigger system's decision half — it runs when a per-campaign quiet-window debounce matures and decides whether the AI DM takes a turn. Like the turn worker it builds its own repo over the pg Pool and reads coordination state on redisRealtime, with its producers riding the shared redisBatch; its decision logic lives wholly on its own page. worker.ts also constructs the MYT-67 QueueEvents('session-turn') subscriber — the broker-side terminal turn_error publisher that closes the maxStalledCount-exhaustion gap the per-worker on('failed') listener can't see.

The st-evaluation worker (buildStEvaluationWorker) is the post-hoc Slow Thinker — the omniscient narrative director, off the hot path. The turn worker enqueues an evaluation on its flushed-success path; this worker runs policy → Haiku gate → Opus director → write, landing stage directions in Redis slots the next turn consumes. Like the turn worker it takes the pg Pool (building its own narrow secret-bearing repo) and both Redis connections; its producer rides redisBatch. Its decision logic lives wholly on its own page. Its concurrency is the lowest in the process (2) because each job can hold an Opus call open for minutes — and its BullMQ lock sits comfortably above the evaluation timeout so a live job is never reclaimed mid-Opus.

The scribe worker (buildScribeWorker) is the post-turn Scribe — the reconciler that turns the Fast Thinker's improvisation into in-session canon and guards the secret boundary, off the hot path. The turn worker enqueues one job per flushed turn; this worker embeds the turn's proposed facts into the working set, runs the Haiku secret tripwire over the FT prose, and on a core-secret breach authors (Opus) a secret-preserving retcon and delivers it through a player-less correction turn. Like the turn and st-evaluation workers it takes both Redis connections — redisBatch for its own BullMQ queue plus the session-turn producer it enqueues corrections onto, redisRealtime for the working-set list — and builds its own narrow secret-bearing repo over the pg Pool. It also takes the boot-probed Voyage embedder (the working-set embed-on-append). Its decision logic lives wholly on its own page; its concurrency (2) and 90-second lock mirror the st-evaluation worker because a retcon job can hold an Opus call open.

The session-reconcile worker (buildReconcileWorker) is the end-of-session reconciler — it folds a closed session's improvised working set into durable canon (load the working set → retrieve canon candidates → one holistic Opus reconcile → a pure structural-and-policy validate → Voyage embed → one gated commit transaction → clear the working set), off the hot path. It is fired by the end_session WS frame or the turn worker's context-ceiling auto-end, not by a per-turn enqueue, so unlike the other session workers it has no producer inside the worker process — the API server and the turn worker are the producers. It takes both Redis connections (redisBatch for its queue, redisRealtime for the per-session lock and the working-set list), builds its own narrow secret-bearing repo over the pg Pool, and shares the boot-probed Voyage embedder for the candidate-similarity search and the fact embeds. Its decision logic lives wholly on its own page. It is the only worker that is not total: it throws on transient failure so BullMQ retries, and its idempotency rests on the commit's conditional reconciled_at gate, not on raw concurrency — which is why its concurrency is the lowest in the process (1) and its lock (180s) sits above the worst-case Opus + Voyage + commit wall-clock so a live reconcile is never stalled-reclaimed into a second run.

The session-analysis worker (buildPostSessionAnalysisWorker) is the second end-of-session closeout — the post-session analysis that reads a closed session's transcript tail, prep sd_playbook, and running summary through one Opus call, mechanically verifies the handoff's verbatim excerpts, and writes the recap + handoff. Like reconcile it is fired at finalize (not a per-turn enqueue), is not total (it throws on transient failure so BullMQ retries, idempotent on the summary IS NULL write gate), and runs at concurrency 1 with a 180s lock. Unlike reconcile it takes no embedder — analysis doesn't embed. It builds its own repo over the pg Pool and reads the running summary on redisRealtime.

worker.ts also wires the MYT-74b finalize backstop: it constructs a finalizeEndedSession closure (over its own repo + reconcile/analysis producers built through the policy queue builders, so the backstop's enqueues carry the same retry policy — plus, myth-x4ca4, a realtime-side SessionState so the finalize can release the session's :ending fence: a backstop finalize must clear a fence its crashed winner never got to) and passes it into the QueueEvents('session-turn') subscriber. That subscriber runs the finalize from the broker side when a farewell turn fails terminally (maxStalledCount-exhaustion) — the path the in-worker finally can't cover. Those two backstop producer handles are distinct Queue objects, so they're closed explicitly at shutdown (after the workers drain) — redisBatch.quit() doesn't reach them, and skipping the close would leak two Redis clients per deploy.

The outage-resilience feature added three pieces of wiring here. First, boot binds the LLM health sink: setLlmHealthSink(tracker.report) connects ai.ts's connectivity-failure reports to the Redis-shared outage tracker — without this call the sink stays a no-op and the outage detector never arms from this process (the API server binds the same sink for its inline workers). Second, the llm-health-probe worker: a repeatable 60-second job registered via idempotent upsertJobScheduler (every boot re-asserts the same scheduler rather than stacking duplicates) whose cycle probes implicated models while degraded and promotes parked prep jobs on recovery. The promote scan needs producer handles on the three prep queues (a BullMQ Worker can't list delayed jobs), so the worker also constructs three scan-side Queue clients — closed explicitly at shutdown like the finalize producers. Third, buildPrepQueueEvents subscribes QueueEvents on world-gen, campaign-setup, and session-prep — the broker-side terminal net that recovers a parked run whose wake died terminally, operating from the event's jobId alone; each subscriber holds its own dedicated blocking connection with an explicit shutdown close.

The QueueEvents subscriber needs explicit shutdown; the workers don't leak — the subscriber duplicate()s redisBatch for a dedicated BRPOP blocking connection, which redisBatch.quit() does not cover. So its close() is added to the SIGTERM teardown explicitly — skipping it would leak one Redis connection per deploy. (MYT-74b adds two more explicit closes for the same reason — the finalize-backstop producer handles — and the outage-resilience feature adds seven more: three prep QueueEvents subscribers, the probe producer, and three promote-scan queue handles.) The ten Workers each share or own connections the existing quit() calls already drain.

The session-turn worker is built by buildSessionTurnWorker and is shaped differently from the three prep workers. It is the only one that needs two Redis sides at once: it reuses the already-probed redisBatch as its BullMQ connection (no new client, no second ping-probe) and constructs its per-session lock, session-state I/O, and frame publisher on redisRealtime. The full story — the transient SessionController, the deterministic single-tier (FT) conductor (the in-turn ST seam was retired in MYT-69 and the on-path Scribe seam in MYT-73 — both now run as their own post-turn workers), the distributed lock, and the crash-recovery model — lives on the session turn page; this worker is where it is registered to run.

The turn worker runs here, not in the API process — the prep workers and the turn worker share the same crash-isolation rationale, but the turn worker has an extra one. A DM turn streams to live WebSocket sockets the API process owns; running the turn in the API process would couple a mid-turn crash to the sockets it streams to. Keeping the turn in the dedicated worker means an API container crash drops sockets without killing the turn, and the turn worker never shares a process with a live SessionHub. It publishes frames cross-process to the per-campaign Redis channel the API containers fan out.
A queue per stage, not one shared queue — world-generation, campaign-setup, and session-prep have different cost-per-job, different SLAs (interactive vs. batch), and different retry semantics. Sharing one queue would let a slow world-gen run starve a quick campaign-setup of worker slots, or a long session-prep Opus stream starve both. Separate queues with independent concurrency caps let each stage be tuned in isolation — which is why session prep got its own queue rather than a slot on campaign-setup.

Boot is sequential and fail-fast. Its very first act — before any connection, queue, or worker exists — is binding the health port, which doubles as the same-host duplicate-worker guard (below). Only once that socket is claimed does anything else start. Then createBullmqRedisClient(env.redisBatchUrl) returns an ioredis client configured for BullMQ; immediately ping()'d (through waitFor) so a misconfigured URL surfaces at startup rather than first-job time. Boot is where the client fails loud; at runtime it does the opposite — both clients now share the bounded backoff-with-jitter reconnect strategy, so a mid-run ElastiCache blip self-heals (the workers reconnect and BullMQ reclaims any job stalled during the gap) instead of severing the process until a rollover. That config-vs- transient split, and what an operator sees in the logs during a blip, live on Redis reconnection. createRedisClient(env.redisRealtimeUrl) opens the second Redis (the realtime side, used by MYT-52's streaming entity / edge PUBLISH path, myth-imxg's per-fact events, and MYT-62's session-prep phase + prose deltas — all feeding the pipeline status SSE bridge, the prep deltas over the separate dev-only prep channel). createPgPool(env.databaseUrl, { max: 4 }) with SELECT 1 follows. The escape guard goes in next, after every probe has passed and immediately before the first queue consumer registers (why that exact spot). Only once every dependency is up and all ten workers are registered is the already-bound health server armed with its probes — arming, not binding, is what flips the task from starting to healthy at the ECS level.

The boot gate

A boot-phase failure is always fatal here. There is no degraded worker worth running: one that comes up without its queues consumes nothing, so the only honest signal is a non-zero exit that ECS turns into a visible crash-loop, and that a local pnpm dev:worker surfaces immediately rather than hanging half-alive. So main() is a thin gate around bootWorker: every handle is registered into a BootPartials bag as it comes up, and a throw at any step closes whatever exists — health socket, pg pool, both Redis clients, the escape guard — and exits 1. Closes go through allSettled so one failed close cannot mask the others, or the boot error itself. It mirrors the API server's closePartials, with two extra members the worker owns: the bound health socket (releasing it is what lets a restart rebind) and the escape-guard disposer.

The gate does no classification — the probes already did — whether a failure is configuration (a bad Voyage key) or transient (Redis not up yet) is decided inside the individual probes, which is where the knowledge lives. By the time a throw reaches the gate the verdict is already "do not run", so the gate's whole job is to clean up and exit honestly.
A second ioredis factory for BullMQ — BullMQ requires maxRetriesPerRequest: null on its Redis client (blocking commands depend on unlimited retries). The general createRedisClient sets it to 1 for fast-fail in the request path. A separate createBullmqRedisClient factory at backend/src/redis/bullmq-client.ts keeps that requirement explicit at the call site instead of hiding it behind a config flag — when a future contributor wires another Redis-backed background system, the factory name signals which one to pick.

Job containment: one bad job cannot kill the process

The worker long carried a latent assumption: a job that fails, fails alone. Playtest session s10 falsified it. A session-prep Opus response hit the output-token cap; the resulting structured-output error was re-thrown inside a detached promise chain in the LLM client's streaming-repair path — no awaiter had attached yet, so the rejection escaped the job's await chain entirely, and under Node's default --unhandled-rejections=throw policy the process died. All nine queues, every in-flight job, from one bad LLM response. The fix (myth-y2qfi) is three complementary layers, each catching what the previous one cannot.

The root fix lives in the LLM client. streamObject creates its wrapped .object promise eagerly, but consumers typically drain partialObjectStream first and await .object later — or, on a stream error path, never — so a repair-chain rejection could fire before any awaiter attached and detach from every job boundary. The client now marks that promise handled at birth; real awaiters still observe the rejection. That closes the one known escape route — the details live on the LLM client page. The worker's two layers exist because "the one known escape route" is not the same as "the last escape route".

Layer two is the processor boundary. The three inline prep processors — world-gen, campaign-setup, session-prep — register through containProcessor (backend/src/queue/job-containment.ts), an async wrapper that turns any throw in the processor's await chain, synchronous or asynchronous, into a logged job.contained_failure and re-throws so BullMQ still marks the job failed and applies its retry policy. Containment means "this job fails", never "swallow silently". One throw passes the boundary untouched: BullMQ's DelayedError, the control signal a parked prep job throws after moveToDelayed-ing itself — a sanctioned self-delay, not a failure, so the boundary rethrows it as-is and logs job.parked at info (an error-level contained_failure here would page on every routine park rung). The six session workers are not wrapped: their builders own their failure semantics (the turn worker is total by design; reconcile and analysis throw deliberately so BullMQ retries), documented on their own pages.

Layer three is the process boundary. createProcessEscapeGuard registers unhandledRejection / uncaughtException handlers — because a floating rejection detached from every await chain (the exact incident shape) is invisible to both layers above. Each escape is logged as process.escape and the process stays alive. The keep-alive posture is bounded by a storm hatch: more than 25 escapes inside a rolling 60-second window logs process.escape_storm and exits 1, so ECS restarts the task and the failure surfaces as a crash-loop that alarms fire on. During graceful shutdown the guard no-ops and is detached, so a rejection racing teardown can't re-trigger the fail-fast exit.

The guard installs after the probes, not before them — and that placement is the whole fix — it used to be the first act of main(), which sounded maximally safe and was the opposite. The guard is keep-alive by default, so covering boot meant every boot failure — bad Voyage key, unreachable Redis — became a swallowed rejection and a half-live, silent process: health bound but never armed, zero consumers, no crash, no signal. It now sits after the last probe and immediately before the first queue consumer registers, so it covers steady state (where keep-alive is right) and not boot (where exiting is right). The one await between that line and health.arm() — the probe scheduler upsert — runs with the guard already installed, so a job that starts during it is covered, while its own throw still propagates to the boot gate (awaited rejections never reach the guard).
Keep-alive per escape, crash on a storm — generic Node advice says always exit on uncaughtException because process state may be corrupt. The worker deliberately departs: an escaped LLM-parse failure doesn't corrupt the process-scoped state (the pg pool, the Redis clients, the BullMQ workers), and exiting would orphan nine healthy queues to punish one — the exact blast radius the incident proved unacceptable. The residual risk is the zombie: a systemic bug escaping on every job while /health stays green (isRunning() is true — jobs are failing, not stuck). The storm hatch resolves that tradeoff: isolated escapes survive; a storm becomes a loud crash-loop instead of a silent log trickle. The threshold sits well above one bad response (a single escape) and well below every-job-escapes.
The containment log is secret-free — the boundary logs errors thrown from LLM-adjacent code, and the typed LLM errors carry diagnostic.rawTextSnippet: verbatim model output, which for session-prep is sd_playbook text — NPC secrets. So the boundary never hands a logger the raw error. describeErrorForLog keeps only the stable scalars (class name, .code, the terminal flag, a hard-capped message) and drops diagnostic, cause, and stack entirely. Enforced ignorance extends to CloudWatch.

The module carries one more primitive, withJobTimeout (myth-3u4a0) — a hard wall-clock bound on a single external await that throws the terminal { terminal: true } shape on trip, freeing the BullMQ lock and the worker slot instead of renewing the lock forever on a hung await. Its consumer today is the character-creation processor; that story lives on the character creation page.

The health endpoint, and the duplicate-worker guard

GET http://127.0.0.1:3001/health probes the four moving parts: the pg pool (SELECT 1), redisBatch.ping(), redisRealtime.ping(), and each registered Worker's isRunning() state (all ten). Each probe is given a 1-second timeout via Promise.race. A 200 response means all probes passed; a 503 response carries a failed[] array of probe names so operators can see at a glance which dependency tripped. The endpoint binds 127.0.0.1 only — it's task-internal, consumed by the ECS container healthCheck block in infra/modules/serving/main.tf, which curls it every 30 seconds.

It comes up in two phases. startHealthServer(port) binds the socket at the very top of boot; arm(deps) supplies the runtime probes at the very bottom. Between the two, /health answers 503 with failed: ['boot'] — the same "not ready" signal ECS used to get from the port simply not listening yet — so an un-armed worker can never report green.

Binding first is what stops a second local worker stealing jobs — BullMQ consumers compete, so a stray second pnpm dev:worker on the same host quietly takes half the session turns, and its tsx watch reloads kill them mid-run. Nothing about that is visible; jobs just disappear. Because the bind now happens before a single queue consumer is registered, a duplicate dies on EADDRINUSE with an actionable message instead of falling through into a hidden competing consumer. The split exists purely to move the bind earlier without reporting healthy earlier.
Deliberately a same-host guard, not a distributed lock — production runs the worker as an ECS service whose rolling deploys run old and new tasks concurrently, and competing consumers are the intended scale-out story. A Redis lock would break both. Under awsvpc each task has its own network namespace, so every replica binds its own 127.0.0.1:3001 and this check never sees a sibling. WORKER_HEALTH_PORT remains the escape hatch for a deliberate second local instance.
Probe the workers, not just the connections — a healthy Redis client paired with a wedged BullMQ Worker (Node-side state machine stuck on a crashed job) would otherwise pass an "are sockets open" probe and silently miss jobs. isRunning() is the actual liveness signal the ECS-level circuit breaker needs.

Graceful shutdown

ECS sends SIGTERM and waits up to stopTimeout = 120s before SIGKILL. The handler in worker.ts flips the shutting-down flag and detaches the process escape guard first — a rejection racing teardown must not re-trigger the storm hatch's fail-fast exit — then closes the health server (stops new probes from going green during teardown), then runs worker.close() on all ten BullMQ Workers in parallel with a 100-second deadline each. Any worker that misses the deadline is force-closed via worker.close(true), which leaves in-flight jobs as stalled for another worker to pick up — BullMQ's stall recovery is the safety net here. For the session-turn worker that stall recovery is not just a shutdown nicety but the load-bearing crash-recovery path (a force-closed turn re-runs on another worker from clean state). The QueueEvents('session-turn') subscriber is then closed explicitly (its dedicated blocking connection isn't covered by the redisBatch.quit() below), followed by the three prep-queue QueueEvents subscribers (same dedicated-connection reason), the two MYT-74b finalize-backstop producer handles, and the four outage-resilience queue handles (the llm-health-probe producer plus the three promote-scan clients) — all distinct Queue objects on redisBatch, closed after the workers drain so an in-flight backstop finalize or probe cycle can still finish. After the workers, the subscribers, and the producers close, pg.end() and the two redis.quit() calls finish out, then process.exit(0).

100s graceful close under a 120s stopTimeout — the 20-second remainder is the budget for pg + Redis cleanup plus any final log flushes. If a job legitimately takes longer than 100 seconds it's a misshaped job, not a shutdown problem; the stall recovery path is the right tool, not a longer grace.

The wrapStream middleware

The worker is the first consumer of streaming LLM calls. The LLM layer's existing wrapGenerate middleware logs and normalizes errors for one-shot calls; this issue adds wrapStream with the same contract for the streaming side. Both live in backend/src/llm/middleware.ts and the worker registers them when constructing its model handles.

Streaming has six terminal states. The middleware logs exactly one line per call, governed by a terminated closure flag so an in-stream error chunk followed by stream close doesn't double-log:

Terminal state Trigger Log line Caller behavior
Success type === 'finish' event: 'llm.call' Stream closes
Provider-graceful error finishReason === 'error' event: 'llm.call' Stream closes
In-stream error part type === 'error' event: 'llm.error' controller.error(mapToMythrunError(part.error))
Truncation Stream closes without finish or error event: 'llm.error', reason: 'truncated' controller.error(LlmStructuredOutputError)
Cancellation Stream's cancel() handler fires event: 'llm.error', reason: 'cancelled' (no rethrow)
Open-time error doStream() throws event: 'llm.error' wrapStream throws the mapped error
Truncation is treated as a typed error, not a quiet close — a stream that closes without a finish part means the model output didn't satisfy the structured schema. The caller needs a typed signal (LlmStructuredOutputError) it can branch on for retry, not an ambiguous "stream ended."

Callers attribute cost by passing providerOptions.mythrun = { worldId, campaignId?, userId?, stage } on the call; the middleware threads those into the log line so the cost-attribution path from MYT-43 can join against pipeline_runs. Mythrun-typed errors propagate to the caller in every failure case — parity with wrapGenerate is the explicit contract.

The deploy mechanism

The worker service is provisioned in Terraform with desired_count = 0 and lifecycle.ignore_changes = [desired_count, task_definition] — Terraform creates the service and the initial task-def revision, but CI owns both the running count and revision pinning thereafter. The pattern matches the API service (see Serving) so both deploy through the same shape.

TF registers, CI deploys — Terraform pins task-def images to :placeholder; the GitHub Actions deploy job swaps in the real ECR digest at push-to-main time. After a TF env-var or secret change the right move is gh workflow run Deploy, never force-rollover onto the TF-owned revision.

The deploy-staging-worker job in .github/workflows/deploy.yml is a parallel peer of deploy-staging with its own concurrency group. On every push to main it fetches the current task definition, renders it with the new image via aws-actions/amazon-ecs-render-task-definition, deploys via aws-actions/amazon-ecs-deploy-task-definition with wait-for-service-stability: true, then flips desired_count to 1 (a no-op after the first deploy), then polls rolloutState for two minutes to catch a circuit-breaker rollback the action's wait wouldn't otherwise surface.

Operating this piece

Bring up the worker locally

  1. Bring up the local data plane and backend: pnpm db:up, then pnpm dev in one terminal (see backend).
  2. In a second terminal: pnpm --filter @mythrun/backend dev:worker. The process binds :3001 for /health and logs event: 'worker.started' with the queue names.
  3. Curl http://127.0.0.1:3001/health. A 200 with { "status": "ok" } means pg + both Redises + all ten BullMQ workers are healthy. A 503 carrying failed: ['boot'] means the socket is bound but boot hasn't finished arming — either still coming up, or stuck on a probe.
  4. worker.health_port_in_use means another worker already owns :3001 on this host. It refuses to start rather than becoming a competing consumer — stop the other one, or set WORKER_HEALTH_PORT for a deliberate second instance. worker.boot_failed means a probe rejected: the partial clients were closed and the process exited non-zero, so read the preceding probe log for the cause.

Deploy the worker to staging

  1. Push to main. The deploy-staging-worker job in .github/workflows/deploy.yml fires alongside deploy-staging.
  2. The job builds + pushes the image to ECR, renders the new task definition, deploys with wait-for-service-stability, flips desired_count = 1, and polls rolloutState for two minutes.
  3. On a circuit-breaker rollback (rolloutState != COMPLETED at the two-minute mark), the job fails red. Inspect the ECS service events tab and the most recent task's CloudWatch log group to diagnose.

Roll the worker after a TF env or secret change

  1. Apply the Terraform change. Confirm the new task-def revision was registered (revision number bumps; image stays pinned to :placeholder).
  2. gh workflow run Deploy from the repo root, targeting main. Do not manually force-rollover the service onto the TF revision — the image is a placeholder. The Deploy run renders the real image digest onto the new revision.
  3. Confirm the new revision shows up in aws ecs describe-services and the worker pod's logs reflect the new config.

Diagnose a worker crash-loop from the escape-storm hatch

  1. Confirm the signature: the worker service is restart-looping in ECS, and the last CloudWatch lines before each exit show event: 'process.escape_storm' preceded by a burst of event: 'process.escape' lines. This is the guard's deliberate exit(1) — a systemic defect escaping on many jobs, never one bad job (a single escape is logged and survived).
  2. Read the err descriptor on the process.escape lines — class name, code, terminal, capped message. It is secret-free by construction, so it is safe to paste into an issue. Correlate with any event: 'job.contained_failure' lines (which carry queue and jobId) to identify which queue's jobs are escaping.
  3. Find what changed: a deploy just before the loop started, a provider incident (the escapes are usually LLM-shaped), or a config change. The threshold is >25 escapes in a rolling 60s window — nothing job-isolated trips it.
  4. Fix or roll back the defect. No manual reset is needed: ECS keeps restarting the task, and once jobs stop escaping the loop settles on its own. Jobs that failed during the storm follow their normal BullMQ retry policy; check the affected queue for jobs that exhausted retries.

Integration points

The worker shares the backend codebase, the repository layer, and the LLM client with the API. Its task definition and service are provisioned by the serving module alongside the API service. Job names live in backend/src/contract/pipeline-jobs.ts — the same contract file the dev tool's ship gate enforces coverage against. The session-prep worker is the third Worker registered here, on its own queue; the session-turn worker is the fourth, the only one whose stalled-job recovery is a load-bearing product behavior rather than a teardown safety net; the dm-trigger worker is the fifth, the DM trigger system's decision half; the st-evaluation worker is the sixth, the post-hoc narrative director; the scribe worker is the seventh, the post-turn in-session reconciler; the session-reconcile worker is the eighth, the end-of-session reconciler that folds the working set into durable canon; and the session-analysis worker is the ninth, the end-of-session narrative closeout that writes the recap + handoff; and the llm-health-probe worker is the tenth, the outage-recovery cycle that probes implicated models and wakes parked prep jobs. The session-turn, dm-trigger, st-evaluation, scribe, session-reconcile, and session-analysis workers all read and write redisRealtime (the per-session lock, turn / trigger / direction state, the working set, the running summary, and DM-turn frame publishing) on top of the shared redisBatch queues — the dm-trigger worker makes the real Haiku classifier call, the st-evaluation worker the Haiku gate + Opus director calls, the scribe worker the Haiku tripwire + Opus retcon calls, the session-reconcile worker the single Opus reconcile call, and the session-analysis worker the single Opus analysis call, through the LLM client (the scribe and session-reconcile workers also share the boot-probed Voyage embedder — the scribe for the working-set embed-on-append, the reconciler for candidate similarity search and fact embeds; the analysis worker takes no embedder). The QueueEvents('session-turn') subscriber registered alongside them publishes the terminal turn_error the JS listener can't. Streaming-cost attribution joins to the pipeline_runs table introduced in MYT-43. The job-containment module's root-fix counterpart — the eagerly-created streamObject .object promise, marked handled at birth — lives in the LLM client; its withJobTimeout primitive is consumed by the character-creation processor.
