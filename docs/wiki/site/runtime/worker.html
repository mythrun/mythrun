Worker

The async-execution half of the backend. A second ECS Fargate service running node dist/worker.js with three BullMQ Workers — world-gen (concurrency 3), campaign-setup (concurrency 5), and session-prep (concurrency 3) — all consuming from redisBatch. Phase 0 shipped stub processors that logged job receipt and marked complete. The real prep-stage processors landed across MYT-51 (world-gen), MYT-52 (streaming entity / edge events), MYT-53 (per-player character creation), MYT-54 (campaign-scoped character integration), and MYT-61 (session prep). The shape locked in at Phase 0 so each later stage was a coverage edit, not a service-topology change. The stub-processor file was retired in MYT-55 once the dedicated worker container caught up to the same wiring the API container already used.

How it fits together

The prep pipeline is long-running by nature: an Opus call inside the world-generation stage holds a streaming HTTP connection open for tens of seconds, and a single campaign-setup run chains multiple such calls. Running those calls inside the API service would tie up event-loop time the HTTP and WebSocket handlers need, and an OOM in a stage would kill in-flight player requests. The worker is the other side of that split: a separate service, on a separate ECS task, scaling independently from queue depth, with its own failure blast radius.

Separate service, not a sidecar — packing the worker into the API container would couple their resource limits (CPU, memory, file descriptors) and their deploy lifecycles. An Opus-heavy worker run that approached the task's memory ceiling would page-trap the API threads. Independent ECS services means the worker can be sized for batch (more memory, fewer vCPU) while the API stays sized for steady-state HTTP.

The worker entrypoint is backend/src/worker.ts. It reads the same loadEnv() contract the API does, opens connections to the same Postgres + two-Redis data plane, and then registers three BullMQ Worker instances against redisBatch: QUEUE_WORLD_GEN (world-gen, concurrency 3), QUEUE_CAMPAIGN_SETUP (campaign-setup, concurrency 5), and QUEUE_SESSION_PREP (session-prep, concurrency 3, added in MYT-61). Queue names and concurrency caps live in backend/src/worker/bullmq-config.ts — the single source of truth so the API-side Queue producers and the worker-side Worker consumers can't drift.

A queue per stage, not one shared queue — world-generation, campaign-setup, and session-prep have different cost-per-job, different SLAs (interactive vs. batch), and different retry semantics. Sharing one queue would let a slow world-gen run starve a quick campaign-setup of worker slots, or a long session-prep Opus stream starve both. Separate queues with independent concurrency caps let each stage be tuned in isolation — which is why session prep got its own queue rather than a slot on campaign-setup.

Boot is sequential and fail-fast. createBullmqRedisClient(env.redisBatchUrl) returns an ioredis client configured for BullMQ; immediately ping()'d so a misconfigured URL surfaces at startup rather than first-job time. createRedisClient(env.redisRealtimeUrl) opens the second Redis (the realtime side, used by MYT-52's streaming entity / edge PUBLISH path, myth-imxg's per-fact events, and MYT-62's session-prep phase + prose deltas — all feeding the pipeline status SSE bridge, the prep deltas over the separate dev-only prep channel). createPgPool(env.databaseUrl, { max: 4 }) with SELECT 1 follows. Only once every dependency is up does startHealthServer bind Fastify on 127.0.0.1:3001 — the order matters because that bind is what flips the task from starting to healthy at the ECS level.

A second ioredis factory for BullMQ — BullMQ requires maxRetriesPerRequest: null on its Redis client (blocking commands depend on unlimited retries). The general createRedisClient sets it to 1 for fast-fail in the request path. A separate createBullmqRedisClient factory at backend/src/redis/bullmq-client.ts keeps that requirement explicit at the call site instead of hiding it behind a config flag — when a future contributor wires another Redis-backed background system, the factory name signals which one to pick.

The health endpoint

GET http://127.0.0.1:3001/health probes the four moving parts: the pg pool (SELECT 1), redisBatch.ping(), redisRealtime.ping(), and each registered Worker's isRunning() state. Each probe is given a 1-second timeout via Promise.race. A 200 response means all probes passed; a 503 response carries a failed[] array of probe names so operators can see at a glance which dependency tripped. The endpoint binds 127.0.0.1 only — it's task-internal, consumed by the ECS container healthCheck block in infra/modules/serving/main.tf, which curls it every 30 seconds.

Probe the workers, not just the connections — a healthy Redis client paired with a wedged BullMQ Worker (Node-side state machine stuck on a crashed job) would otherwise pass an "are sockets open" probe and silently miss jobs. isRunning() is the actual liveness signal the ECS-level circuit breaker needs.

Graceful shutdown

ECS sends SIGTERM and waits up to stopTimeout = 120s before SIGKILL. The handler in worker.ts closes the health server first (stops new probes from going green during teardown), then runs worker.close() on all three BullMQ Workers in parallel with a 100-second deadline each. Any worker that misses the deadline is force-closed via worker.close(true), which leaves in-flight jobs as stalled for another worker to pick up — BullMQ's stall recovery is the safety net here. After both close, pg.end() and the two redis.quit() calls finish out, then process.exit(0).

100s graceful close under a 120s stopTimeout — the 20-second remainder is the budget for pg + Redis cleanup plus any final log flushes. If a job legitimately takes longer than 100 seconds it's a misshaped job, not a shutdown problem; the stall recovery path is the right tool, not a longer grace.

The wrapStream middleware

The worker is the first consumer of streaming LLM calls. The LLM layer's existing wrapGenerate middleware logs and normalizes errors for one-shot calls; this issue adds wrapStream with the same contract for the streaming side. Both live in backend/src/llm/middleware.ts and the worker registers them when constructing its model handles.

Streaming has six terminal states. The middleware logs exactly one line per call, governed by a terminated closure flag so an in-stream error chunk followed by stream close doesn't double-log:

Terminal state Trigger Log line Caller behavior
Success type === 'finish' event: 'llm.call' Stream closes
Provider-graceful error finishReason === 'error' event: 'llm.call' Stream closes
In-stream error part type === 'error' event: 'llm.error' controller.error(mapToMythrunError(part.error))
Truncation Stream closes without finish or error event: 'llm.error', reason: 'truncated' controller.error(LlmStructuredOutputError)
Cancellation Stream's cancel() handler fires event: 'llm.error', reason: 'cancelled' (no rethrow)
Open-time error doStream() throws event: 'llm.error' wrapStream throws the mapped error
Truncation is treated as a typed error, not a quiet close — a stream that closes without a finish part means the model output didn't satisfy the structured schema. The caller needs a typed signal (LlmStructuredOutputError) it can branch on for retry, not an ambiguous "stream ended."

Callers attribute cost by passing providerOptions.mythrun = { worldId, campaignId?, userId?, stage } on the call; the middleware threads those into the log line so the cost-attribution path from MYT-43 can join against pipeline_runs. Mythrun-typed errors propagate to the caller in every failure case — parity with wrapGenerate is the explicit contract.

The deploy mechanism

The worker service is provisioned in Terraform with desired_count = 0 and lifecycle.ignore_changes = [desired_count, task_definition] — Terraform creates the service and the initial task-def revision, but CI owns both the running count and revision pinning thereafter. The pattern matches the API service (see Serving) so both deploy through the same shape.

TF registers, CI deploys — Terraform pins task-def images to :placeholder; the GitHub Actions deploy job swaps in the real ECR digest at push-to-main time. After a TF env-var or secret change the right move is gh workflow run Deploy, never force-rollover onto the TF-owned revision.

The deploy-staging-worker job in .github/workflows/deploy.yml is a parallel peer of deploy-staging with its own concurrency group. On every push to main it fetches the current task definition, renders it with the new image via aws-actions/amazon-ecs-render-task-definition, deploys via aws-actions/amazon-ecs-deploy-task-definition with wait-for-service-stability: true, then flips desired_count to 1 (a no-op after the first deploy), then polls rolloutState for two minutes to catch a circuit-breaker rollback the action's wait wouldn't otherwise surface.

Operating this piece

Bring up the worker locally

  1. Bring up the local data plane and backend: pnpm db:up, then pnpm dev in one terminal (see backend).
  2. In a second terminal: pnpm --filter @mythrun/backend dev:worker. The process binds :3001 for /health and logs event: 'worker.started' with the queue names.
  3. Curl http://127.0.0.1:3001/health. A 200 with { "status": "ok" } means pg + both Redises + both BullMQ workers are healthy.

Deploy the worker to staging

  1. Push to main. The deploy-staging-worker job in .github/workflows/deploy.yml fires alongside deploy-staging.
  2. The job builds + pushes the image to ECR, renders the new task definition, deploys with wait-for-service-stability, flips desired_count = 1, and polls rolloutState for two minutes.
  3. On a circuit-breaker rollback (rolloutState != COMPLETED at the two-minute mark), the job fails red. Inspect the ECS service events tab and the most recent task's CloudWatch log group to diagnose.

Roll the worker after a TF env or secret change

  1. Apply the Terraform change. Confirm the new task-def revision was registered (revision number bumps; image stays pinned to :placeholder).
  2. gh workflow run Deploy from the repo root, targeting main. Do not manually force-rollover the service onto the TF revision — the image is a placeholder. The Deploy run renders the real image digest onto the new revision.
  3. Confirm the new revision shows up in aws ecs describe-services and the worker pod's logs reflect the new config.

Integration points

The worker shares the backend codebase, the repository layer, and the LLM client with the API. Its task definition and service are provisioned by the serving module alongside the API service. Job names live in backend/src/contract/pipeline-jobs.ts — the same contract file the dev tool's ship gate enforces coverage against. The session-prep worker is the third Worker registered here, on its own queue. Streaming-cost attribution joins to the pipeline_runs table introduced in MYT-43.
