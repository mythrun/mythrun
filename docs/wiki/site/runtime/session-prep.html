Session prep

Before a session can run, one Opus call produces the two prep documents that session needs — a Fast-Thinker-safe ft_context and a secrets-bearing sd_playbook — and a dedicated BullMQ worker persists them to session_preps. The job is keyed on (campaign_id, session_number), so re-enqueuing the same session is a resume, not a duplicate. A prep failure is session-scoped: it never fails the campaign. The Opus call streams, so two parallel signals come off it: phase events (a player's "the DM is preparing tonight's session" loading screen) and the live prose itself (a dev-only inspector). Those two signals ride two different Redis channels — and that split is what makes enforced ignorance structural rather than a runtime filter.

How it fits together

The generation primitive — generateSessionPrep — shipped first, ahead of any caller. This piece is the orchestration around it: a session-prep BullMQ job, a processor that owns the job's pipeline_runs lifecycle, a dedicated queue and worker, and a repo.sessionPreps binder that lands the result. The shape mirrors character integration — claim a stage, do the LLM work outside any transaction, persist, mark completed with cost — but differs in two deliberate ways the rest of this page calls out: there is no cost cap, and a failure does not touch the campaign.

The enqueue side — the play-runtime route that calls queue.add with jobId = sp-{campaignId}-{sessionNumber} — lands in a later ticket. This piece wires the consumer end (the worker) and the queue's lifecycle (created at boot, drained at shutdown). The job carries a two-field payload: campaignId and sessionNumber.

The dedicated queue and worker

Session prep gets its own queue (QUEUE_SESSION_PREP = 'session-prep') and its own Worker at CONCURRENCY_SESSION_PREP = 3, alongside the existing world-gen and campaign-setup pair in backend/src/worker/bullmq-config.ts. Both the dedicated worker container and the API process register the same processor against this queue — the API side is wired so the queue's connection bookkeeping exists and is closed cleanly at shutdown even before the enqueue route lands.

A third queue, not a slot on campaign-setup — session prep is a single long Opus stream (the slowest call in the system, see below). Folding it onto the campaign-setup queue would let one in-flight prep starve the per-player character-creation jobs of worker slots, and vice versa. A separate queue with its own concurrency cap keeps each stage's saturation independent — the same reasoning that split world-gen from campaign-setup in the first place.

The queue's job options match world-gen's: attempts: 2 with exponential backoff (30s), and removeOnComplete / removeOnFail both pruning terminal jobs so a future re-enqueue with the same jobId isn't silently swallowed by a leftover completed record. At shutdown the worker is closed before the queue (an in-flight Opus prep gets to finish, then the queue's Redis bookkeeping is released), ahead of the rest of the boot chain.

Claim, generate, persist, mark

The processor (session-prep-processor.ts) walks the same per-stage lifecycle the other prep processors use. It claims a pipeline_runs row via atomicClaimStage on (campaign, stage) — but the stage string embeds the session number: session-prep:{sessionNumber}. That's what gives each session its own claim row on a table that keys on (campaign, stage). A claim that comes back completed is an idempotent re-entry (BullMQ retried an already-done job) and returns cleanly; a lost-race result means another worker won and also returns cleanly.

Session number in the stage string, not a new table key — pipeline_runs already keys claims on (campaign, stage). Putting the session number inside the stage label (session-prep:3) reuses that machinery to give session 3 a claim row distinct from session 4's, without a schema change. The atomic claim is what makes re-enqueue a resume: a second job for an already-completed session no-ops at claim time.

With the claim held, the processor publishes a prep-started phase event, resolves the campaign's world_id, and calls generateSessionPrep — one Opus streamObject producing the two prose documents. That call runs against the raw pool, outside any open transaction: it is the slowest single call in the system (a 9-minute timeout, two long markdown documents), and holding a pooled connection for its full duration would starve the rest of the worker. The LLM client page covers the generation primitive — the omniscient serializer, the maxOutputTokens ceiling, the enforced-ignorance split that lives inside the prompt, and the optional onProseDelta callback the processor threads in to capture the stream as it lands.

On success the processor persists the two artifacts to session_preps through repo.sessionPreps.insert (ON CONFLICT (campaign_id, session_number) DO NOTHING — the first persisted row wins), then marks the pipeline_runs row completed with the call's cost and publishes a prep-ready event carrying the recorded costUsd. On any error it publishes prep-failed with the terminal flag instead. These three prep-* arms are the entire player-visible signal — they ride the campaign's pipeline channel, never the prose.

Dedicated prep-* arms, not the generic stage-* events — an earlier cut of this processor reused the pipeline's generic stage-completed / stage-failed arms, but their shapes drifted (they expect a userId and a durationMs the session-prep job has no use for, and carried a free-form message the contract doesn't define). The three purpose-built arms — prep-started { sessionNumber }, prep-ready { sessionNumber, costUsd }, prep-failed { sessionNumber, terminal } — carry exactly the fields a prep loading screen needs and nothing a Fast Thinker could mistake for narrative. They're added to the pipeline event contract alongside the world-gen and character-creation arms.

Two channels off one stream

generateSessionPrep already streamed its result under the hood — the original code just awaited the final object and threw the intermediate chunks away. The processor now passes an onProseDelta(field, text) callback into the stage, so consuming the partial stream costs no extra LLM tokens: the same bytes that were being discarded are now forwarded as they arrive. (The stage page covers the delta mechanics — per-field length-diff, the mid-escape resync.) What the processor does with those deltas is the load-bearing design choice on this page.

The processor holds two publishers, both built by makePipelinePublishers in backend/src/worker/publishers.ts, and they write to two different Redis channels:

  • publishEvent → {redisKeyPrefix}pipeline:campaign:{id} — the existing player-facing channel. The three prep-* phase events go here. This is what the player's prep-status loading screen reads.
  • publishProse → {redisKeyPrefix}prep:campaign:{id} — a new, parallel channel that exists only to carry prep-delta prose. The onProseDelta callback wraps each delta in a prep-delta event and publishes it here. The only consumer is the dev-only prose route the dev tool subscribes to.
Prose rides its own channel exposed only in dev — structural enforced ignorance — the sd_playbook half of the stream is, by design, full of secrets: clues, revelation conditions, what the depth markers in ft_context are pointing at. There is no runtime leak guard on prep prose (the Haiku leak-classifier idea was descoped), so the channel split is the control. Phase events ("preparing… ready") are the only thing a player's surface can subscribe to. The prose never touches the player channel — it's published to prep:campaign:, and the single route that serves that channel is registered only when AUTH_MODE=bypass, so it is literally absent in a production boot. A player has no route to reach prep prose; leaking sd_playbook would require building one that doesn't exist.
Why the boundary holds even if someone wires it wrong — the split is defended at three independent layers, so no single mistake leaks prose. Compile-time: prep-delta is a ProseEvent, deliberately not a member of the PipelineEvent union, and publishEvent only accepts PipelineEvent — so publishEvent(id, prepDelta) doesn't type-check. Runtime: the pipeline channel's subscriber carries a type tripwire that drops any message whose type isn't a known pipeline event before it reaches a sink — so even a stray prep-delta hand-published onto pipeline: is discarded. Topology: in production no prose route and no prose subscriber are constructed at all. Defeating enforced ignorance would mean changing the types, removing the tripwire, AND registering the dev route in prod — none of which happens by accident.

A publishProse failure is swallowed: the onProseDelta callback is fire-and-forget (a rejected publish is caught and dropped), and the stage wraps the callback in its own try/catch so a throwing sink can never abort generation. Prose is cosmetic, dev-only telemetry; the persisted documents and the prep-* phase events are the durable output, and neither depends on a prose delta landing.

Cost is recorded, not capped

The processor prices the Opus call via computeCostUsd and writes it onto the pipeline_runs row — the same observability every prep stage carries. Unlike world generation and character integration, there is no cost-cap pre-flight and no credit debit here.

No cost cap, no credit debit at prep time — the world-gen and character-creation caps exist to bound an open-ended pipeline that can chain many calls. Session prep is a single call whose cost is structurally bounded by its maxOutputTokens ceiling (16384 tokens) — there is no runaway loop to fence. The recorded cost is for attribution and dashboards, not a gate. And no credit moves here: the session credit is debited later, at the /start path in Session Runtime, through credits.tryDebitForSession. Prep is preparatory work the runtime pays for when the session actually begins.

A prep failure is session-scoped

On any error the processor classifies it with isTerminalError, marks the pipeline_runs row failed, and publishes a prep-failed event carrying the terminal flag. A non-terminal error is re-thrown so BullMQ retries with backoff; a terminal error returns cleanly so BullMQ marks the job done (retrying the same payload wouldn't help). What it deliberately does not do — on either path — is call repo.campaigns.setFailed.

Why a prep failure does not fail the campaign — character integration flips the campaign to failed on a terminal error because integration is a one-time bring-up step: if it can't complete, the campaign genuinely can't go live. Session prep is different — it runs once per session, repeatedly over a campaign's life. A failed prep for session 5 says nothing about the campaign's health; the campaign stays at its current status and a later attempt can succeed. Resume is sound because the (campaign_id, session_number) claim row and the session_preps unique constraint together make re-enqueue idempotent: a retry either finds the prior row completed (no-op) or re-runs into the same ON CONFLICT DO NOTHING landing.

The persistence row and its unique constraint

session_preps holds one row per prepared session: ft_context, sd_playbook, an optional snapshot_id (the world snapshot a session is pinned to, populated by Session Runtime), and the usual id + timestamp. Migration 022 adds a named UNIQUE (campaign_id, session_number) constraint — the original schema had only a non-unique index. That constraint is what makes the processor's INSERT … ON CONFLICT resume sound: without it, a retried job could write a second prep for the same session. The repo.sessionPreps binder exposes insert (the ON-CONFLICT landing), existsFor (the resume existence check), and getBy (the read Session Runtime will use to load the docs at session start).

Operating this piece

Re-run a failed session prep

  1. Check the failure mode for the session in pipeline_runs:

    SELECT status, error, cost_usd, completed_at
  FROM pipeline_runs
 WHERE campaign_id = '<id>'
   AND stage = 'session-prep:<n>'
   AND user_id IS NULL;

    A failed row carries the classified error. The campaign's own status is untouched — a failed prep never moves it.

  2. Re-enqueue the same (campaign, session_number) job. The atomic claim re-arms from the prior failed row, the prep re-runs, and the ON CONFLICT (campaign_id, session_number) DO NOTHING insert keeps the run idempotent. If a prior attempt already persisted a session_preps row, the claim comes back completed and the job no-ops.

  3. Watch the attempt on the campaign's SSE stream. A clean run opens with one prep-started and ends with one prep-ready event carrying the recorded costUsd; a failure publishes prep-failed with its terminal flag. To watch the prose stream itself, attach the dev tool's prose pane (dev-only — see the dev tool page).

Confirm a session prep landed

  1. Read the persisted docs for a session:

    SELECT id, session_number, length(ft_context), length(sd_playbook), snapshot_id, created_at
  FROM session_preps
 WHERE campaign_id = '<id>'
   AND session_number = '<n>';

    Exactly one row per (campaign, session) — the UNIQUE constraint guarantees it. No row means prep hasn't completed; check pipeline_runs for an in-flight or failed stage.

Integration points

Upstream: the generation primitive on the LLM client page — the omniscient serializer, the two-field schema, the maxOutputTokens ceiling, the onProseDelta streaming seam, and the in-prompt enforced-ignorance split that keeps discoverable / secret material out of ft_context. Sideways: the worker registers this queue's Worker as a third peer and is one of the two entrypoints that wire publishProse (the other is the API container's in-process worker); the repository layer holds the sessionPreps binder; the session-prep job name lives in backend/src/contract/pipeline-jobs.ts and is now a fully dev-tool-covered job (the prose pane is its driver). The two SSE consumption surfaces live elsewhere: the player-facing prep-status route reads the phase channel, and the dev-only prose route + its prose subscriber are documented on pipeline status alongside the rest of the SSE plumbing. Downstream: Session Runtime will read session_preps at /start, debit the session credit, and feed ft_context to the Fast Thinker and sd_playbook to the Slow Thinker.

Appendix: inputs and outputs

Job payload

Field Type Notes
campaignId string (UUID) The campaign the session belongs to.
sessionNumber number 1-based session ordinal. Combined into the claim stage label session-prep:{n} and the jobId sp-{campaignId}-{n}.

Queue configuration

Constant Value
QUEUE_SESSION_PREP 'session-prep'
CONCURRENCY_SESSION_PREP 3
Job options attempts: 2, exponential backoff 30s, removeOnComplete/removeOnFail: { count: 0 }.

session_preps columns

Column Notes
id UUIDv7, app-side generated.
campaign_id, session_number The UNIQUE pair (migration 022) — one prep per session; backs the resume ON CONFLICT.
ft_context Fast-Thinker-facing context, enforced-ignorance safe.
sd_playbook Slow-Thinker stage-direction playbook; carries secrets, clues, revelation conditions.
snapshot_id Nullable; the pinned world_snapshots row, populated by Session Runtime.
created_at Insert timestamp.
