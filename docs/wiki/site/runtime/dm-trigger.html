DM trigger

The system that decides when the AI DM responds — and enqueues exactly one DM turn per decision. A typing-gated quiet window: the DM fires only after the table has gone quiet (no one typing, no new message) for a few seconds, so it never cuts a player off mid-thought. The window is a cross-container BullMQ debounce job; on maturity a dedicated worker re-validates the quiet, builds the unresponded-message batch, and decides three ways — respond, sit back, or step in — via a real Haiku classifier, with explicit summons, solo games, and a dead-air ceiling as deterministic short-circuits around it.

How it fits together

This page owns the decision — whether and when a turn fires. The session turn page owns the execution — the lock-fenced conductor that runs a turn once one is enqueued. The two are deliberately separate queues: dm-trigger (decide) and session-turn (execute). The trigger system never touches the lock or the conductor; it only ever lands at most one session-turn job.

The whole design rests on one model: the trigger is gated on "is anyone still composing?", not on raw message arrival. Two concerns ride the same client activity — typing heartbeats and player messages. First, a per-member typing display state (who is typing), a Redis key with a TTL. Second, the quiet-window trigger timer, a resettable BullMQ debounce job per campaign. Both live in Redis / BullMQ, so they are correct no matter which API container a player is connected to.

"Stopped typing" is a timeout, not an event — and there are no in-process timers — every robust chat system (XEP-0085, Matrix, Ably, Stream, Discord, Slack) treats the end of typing as a server-side TTL, never a client-sent "stop", because a client can crash mid-compose and never send the final frame. A periodic client heartbeat keeps the indicator alive; the indicator dies by TTL expiry. Mythrun adopts that and extends it: the same activity that refreshes the typing key also resets the server-authoritative quiet-window timer that fires the DM. The timer is a shared BullMQ job, not a setTimeout on one container — so there is no leader election and no "owner death strands the timer" failure mode. A worker restart mid-window leaves the delayed job in Redis; it still matures exactly once.

The server side: observe activity, reschedule the debounce

The transport's inbound handler is the single ingestion point — each frame arrives at exactly one container (the player's own connection), so there is no double-scheduling. On a typing_start heartbeat or a player_message, the handler writes the trigger state (markTyping, stampActivity, armFirstUnresponded) and then reschedules the per-campaign debounce — rescheduleQuietWindow in ws-trigger-actions.ts. A player_message also clears the sender's typing key (a send implies "done"), so the common path starts the quiet window immediately on send.

The reschedule runs after persist + broadcast, and a failure logs at warn — the durable message is the source of truth, so it is written and fanned out before the trigger side effects. A debounce reschedule that fails (a queue outage) is logged at warn and swallowed — never thrown — because the message is already safe; but it is logged, not silently dropped like a malformed frame, so a sustained outage is observable rather than a silent never-fires.

The debounce itself is one BullMQ delayed job per campaign in replace-mode deduplication (rescheduleDebounce in dm-trigger-queue.ts). Every add with the stable per-campaign dedup id dm-trigger:{campaignId} removes the still-delayed job and re-adds a fresh one, resetting the countdown. So a burst of player messages collapses onto a single evaluation that fires only after QUIET_WINDOW_MS of quiet.

No dedup TTL — the key must die with the job — an earlier design gave the dedup key an explicit TTL (intended to span the whole window). That was a latent bug, surfaced live by the MYT-68 real-LLM smoke: with an explicit TTL, BullMQ's finalization does not clear the key (it only deletes keys with no TTL), and replace-mode cannot displace a job that has already left the delayed state — so every reschedule for roughly a minute after an evaluation fired was silently swallowed and the DM went untriggerable after each turn. Without a TTL the key dies with the job at finalization, so post-evaluation messages schedule fresh. The reset is driven purely by replace: true — verified against BullMQ's Lua; the recurring-scheduler surface (upsertJobScheduler) is deliberately avoided as a known-buggy path.
A self-re-arm from inside the evaluate job must clear its own dedup key first — the evaluate job's own re-arms (the not-quiet boundary re-arm, the sit-back-toward-dead-air re-arm) add through the same dedup id while their own job still holds the key. A running job cannot be replaced, so a plain dedup'd add from inside the evaluate is swallowed by its own key — both re-arm paths had been dead in effect since they shipped. The worker-side reschedule binding now calls removeDeduplicationKey before re-adding; the server-side producer keeps the narrow add-only surface (removing the key there would defeat the debounce). The residual swallow window — an add while the evaluate runs, or while a turn is in flight — is closed by the turn worker's post-turn re-mature.
A max-wait ceiling, so one idle typer can't starve the table — a single player who holds a typing indicator alive (idle in the compose box, a laggy client) would otherwise reset the debounce forever and starve everyone of any DM response. armFirstUnresponded stamps the first activity after a turn (SET NX, first-writer-wins), and clampQuietDelay clamps every reschedule so the job matures no later than firstUnresponded + MAX_QUIET_EXTENSION_MS (30s) regardless of ongoing typing. This caps a continuous-typing hold; the separate dead-air ceiling handles total silence.

The worker side: re-validate, batch, decide, drain-guard

When the debounce matures, the dm-trigger worker — processDmTriggerJob in dm-trigger-worker.ts, the fifth Worker in the worker process — runs an ordered decision shell. It is pure orchestration (Zero Framework Cognition): every reasoning call is delegated to the Haiku classifier, and the rest is mechanical re-validation, batch assembly, and policy short-circuits. It takes all dependencies as injected params, so the whole decision tree is unit-testable with plain fakes.

  1. Re-validate quiet. Read last-activity; if a reset landed in the narrow window after the job promoted to active but before the worker ran (sinceLastActivity < QUIET_WINDOW_MS), the worker matured too early. It re-arms the debounce for the remaining quiet and exits — never a bare exit.
  2. Build the batch. Resolve the active session (none → exit, closing the session-ended-mid-window race) and the responded-seq watermark, then build the (lastRespondedSeq, maxSeq] slice of player messages from turn-batch.ts. An empty batch exits.
  3. Decide, in order: the dead-air ceiling, an explicit-pending summon, a solo game, then the auto classifier.
  4. Drain-guard and enqueue. If a turn is already in flight (dm_responding set), do not enqueue — the post-turn re-mature drains it. Otherwise enqueue one session-turn carrying the freshly-built batch and structured-log the decision.
The empty-batch exit is the no-monologue guard — the same batch is both the classifier input and the turn's triggerMessages, so decision and execution can never diverge. And because a proactive open (drift re-grounding, or the dead-air ceiling) can only fire when an unresponded player message exists, once a turn consumes the batch the watermark advances and the DM can never step in twice with no intervening player message. The guard is what makes "keep the table alive" safe — the DM never monologues.
Re-arm on the maturity-boundary race, never a bare exit — if an activity pulse arrives after the delayed job promoted but before the worker ran, BullMQ's replace finds nothing to remove and the new add is dropped, creating no fresh job. The re-validation guard catches the resulting too-early fire — and on catching it the worker re-arms the debounce for the remaining quiet. A bare exit there would strand the trigger until the next activity, silently swallowing a DM beat when the player then goes quiet.

The three short-circuits and the classifier

The decision runs four branches in order. The first three are mechanical / policy short-circuits that skip the Haiku call; only the fourth is a model judgment.

  • Dead-air ceiling. If the table has been totally silent — no message or typing — for DEAD_AIR_MS (≈60s), open a proactive turn without the classifier. A 60s dead-air step-in is a deterministic policy threshold, like a rate limit. The Fast Thinker authors the actual beat (any Slow Thinker direction usually isn't ready for a proactive open — the ST refines on a following beat). The non-empty batch is the no-monologue guard, so this can't fire back-to-back.
  • Explicit pending. An @dm / dm_invoke that landed while a turn was in flight set a flag; takeExplicitPending (a GETDEL) drains it once, forcing a respond.
  • Solo. A campaign with exactly one accepted member always gets a DM beat, no classifier. The count uses countAcceptedMembers (invite_accepted = true only) — a pending invite does not make a solo game multiplayer.
  • Auto. The default in multiplayer — call the real Haiku classifier over the public table context.

The classifier (dm-trigger-classifier.ts) is a real Anthropic Haiku call through the single LLM abstraction (model from config, never hardcoded) — ZFC: the "should the DM take a turn, and how heavy" judgment is delegated to a model, never a heuristic. Its decision is three-way, the "make the DM feel alive" requirement:

  • Respond — a player addressed the DM, addressed an NPC, or took an action the world should answer ("I check the stall's wares", "I try to pick the lock"). Open a turn reactively.
  • Sit back — grounded, engaged player-to-player roleplay advancing a scene. Stay out of the way; good RP is not an interruption opportunity. No turn.
  • Step in — the players are still talking among themselves but the scene has drifted (gone in circles, turned meta, gone slack). Open a turn proactively so the DM can re-ground them.
The classifier opens the door; it never decides what the DM says — the sit-back-vs-step-in call is a coarse read. The classifier only decides to open a turn; the Slow Thinker makes the fine intervene-or-stay-silent call — but post-hoc, after the turn, not in-line. A proactive step-in's stage direction usually doesn't exist yet (player-only chat produces no DM turns, hence no evaluations), so the Fast Thinker improvises the intrusion and the ST refines on the following beat. The quality of the read (telling good RP from drift) is an eval-harness concern; the smoke verifies a proactive open can fire.
The classifier input is public by construction — enforced ignorance (CLAUDE.md non-negotiable #1) is structural here, not field discipline. The DmTriggerContext type carries only table-visible material: the attributed player-message batch, the DM's last player-facing line, two pacing counters (turnsSinceLastDmBeat / secondsSinceLastDmBeat), and an optional scene-grounding line — the running summary, used for both the last-DM-output and scene-grounding slots. Crucially, the classifier's output (shouldRespond / intent / complexity) is consumed by code only — it never reaches a player or the Fast Thinker, exactly like the Slow Thinker's Haiku gate. So the classifier is ST-side-adjacent infrastructure.
The summary input is secret-adjacent after MYT-69 — and that is acceptable here — MYT-65 framed the classifier's summary input as "public table material only." Once the Slow Thinker owns the running summary, it deliberately carries secret-adjacent state (NPC rapport, reveal-ladder progress). That would break a "public-only" input contract — but the contract is superseded, not violated: there is no output path from this call to a player-facing surface, so grounding the respond/sit-back/step-in call on rapport state leaks nothing. The reframed rule is "no output path to a player-facing surface," not "public-only input."

On a shouldRespond=false verdict, the worker re-arms the debounce to the dead-air mark (delay = DEAD_AIR_MS − sinceLastActivity) so the 60s backstop still fires if the silence persists; any new activity reschedules it back to the normal quiet window. The verdict's intent (reactive vs proactive) and complexity (low vs high) ride the turn payload as metadata; the confidence anchors the CONFIDENCE_FLOOR (0.8) escalation. The free-prose reason is debug-only — it is structured-logged, never plumbed onto the payload and never sent to a player.

The classification is not the post-hoc ST's spend gate — it was once framed as a skip-ST routing hint, but the Slow Thinker runs after the turn in its own worker and reads neither this payload (persisted nowhere it can reach) nor a classification that is ill-defined under its job collapse. The ST makes its own spend decision via its own Haiku gate. The classification stays useful only as turn-payload metadata and a dev signal.
Fail-closed, no fail-open fallback — a classifier failure (timeout, transient, auth, malformed parse) means no turn this cycle, re-driven on the next activity, with a metric distinguishable from a normal shouldRespond:false for diagnosis. There is no "default to firing" fallback: a sustained Haiku failure is an Anthropic-API outage, in which case the FT / ST turn the classifier would trigger is down too (same API) — firing anyway would only enqueue a turn that immediately fails into turn_error. Because the schema is trivially small and the posture is fail-closed, the classifier skips the Sonnet repair's fail-open default and lets a malformed parse fall straight to the fail-closed path.

The explicit summon: an immediate hard preempt

An @dm-prefixed message or a dm_invoke frame is the "everyone be quiet, I have a question for the DM" gesture — it deliberately ices out the room and must fire as fast as possible. It bypasses the dm-trigger queue entirely. runExplicitTrigger (ws-trigger-actions.ts) rate-limits the summon per campaign + user, then — if no turn is in flight — allocates the turnId, broadcasts dm_thinking immediately so every client greys its input ahead of any enqueue or lock latency, builds the batch from the watermark (frozen at invoke), and enqueues the session-turn directly. If a turn is in flight, it instead sets the explicit-pending flag, drained the instant the current turn releases.

The @dm prefix and dm_invoke are structural, not semantic — detecting the summon is a literal prefix check and a frame-type check, both mechanical (the ZFC structural carve-out). The rate limit is policy enforcement, another carve-out: the explicit path is the first WS frame that triggers real LLM spend, so an unbounded @dm is a cost and griefing surface. Over the ceiling, the summon is dropped and logged. None of this is the classifier — the classifier judges only the auto path.

Collision and drain: the lock is the mutex

The invariant is at most one session-turn in flight per campaign, and triggers arriving during a turn produce at most one coherent follow-up — never a backlog of stale replies. The coordination is the dm_responding flag plus the session lock, not a queue-level dedup id: the session-turn queue keeps its no-dedup, lock-is-the-mutex contract unchanged.

The session-turn worker sets dm_responding while a turn runs and records last-responded-seq = the max consumed seq at flush, then clears the flag on release. The dm-trigger worker checks dm_responding before enqueuing; in-flight, it does not enqueue. But a message that arrived during the turn is swallowed (the evaluate job exits on dm_responding, and a dedup'd re-add during an in-flight evaluation is dropped) — so on release the turn worker runs a post-turn re-mature: if player rows still sit above the responded watermark, it re-arms the quiet window so the DM comes back for them. If players were quiet during the turn, no follow-up fires — correct, nothing new to say.

The debounce is the queued trigger; the post-turn re-mature is the drain — the runtime spec's "if lock held, queue the trigger; on release, drain the queue" is realized without a literal queue. The active re-arm (rather than waiting passively for the next player message) is what keeps a quiet table from stranding the DM after a turn — without it, a message sent mid-turn would sit unanswered until someone spoke again. The lock serializes any residual race (two enqueues slipping past the flag check); the loser returns { ran: false } and is re-driven by the debounce, not by blind BullMQ attempts. The one exception is an explicit summon during an in-flight turn: the session-turn worker checks the explicit-pending flag on release and enqueues the follow-up immediately, so the summon is honored the instant the current turn ends.

The terminal turn_error subscriber

MYT-67 also closes a gap left in the turn worker: a turn whose holder crashes terminally (maxStalledCount exhausted) was failed by BullMQ inside a Lua script, emitting only a broker-side event — never the per-worker on('failed') JS event — so the player's client would wait forever on a turn that will never complete. session-turn-queue-events.ts adds a QueueEvents('session-turn') subscriber that listens for the broker failed event and publishes the terminal turn_error.

A dedicated blocking connection and a cross-container idempotency latch — QueueEvents BRPOPs a Redis stream, so it gets its own duplicate()d ioredis connection, never the BullMQ Worker's (a blocking command would stall every command multiplexed onto a shared connection). And because both publishers — the in-process JS listener and the broker-side QueueEvents, which fires on every worker container — could publish, each guards on a shared SET NX latch (turn-error-published:{turnId}) before publishing, so exactly one turn_error goes out per terminal turn regardless of path or container count. The subscriber's connection is torn down on SIGTERM, so no connection leaks per deploy.

MYT-74b gives the same subscriber a second job. When the terminally-stalled turn is the player-less farewell turn (the end-of-session send-off), the in-worker finally that would normally finalize the session never ran — the holder crashed before it. So the subscriber, after publishing turn_error, also runs the idempotent finalizeEndedSession for that session (flip to ended, enqueue reconcile + analysis, broadcast session_end). Without it a crashed farewell would leave a session that never ends. A double-fire with the in-worker finalize is harmless — the conditional flip broadcasts exactly once. The worker process wires the finalize closure into the subscriber.

Observability: a dev signal, never the player transport

The trigger decision is surfaced for debugging as a structured pino log — { kind, shouldRespond, intent?, confidence?, reason?, campaignId, at }. It is deliberately not a player-facing frame: dm_trigger is not in the transport's server-frame union, because the hub fans every published frame to all player sockets with no audience filter — a dm_trigger frame there would leak the classifier's reason and confidence to players. The player-visible signal that a turn fired is the existing dm_thinking frame.

Operating this piece

Watch a DM trigger decision fire locally

  1. Bring up the data plane and both processes — pnpm db:up, pnpm dev (API), and pnpm --filter @mythrun/backend dev:worker (the worker that hosts the dm-trigger worker). Start a session (POST /api/sessions/:campaignId/start) and open a WebSocket.
  2. Send a typing_start heartbeat, then a player_message. Watch the worker log: after QUIET_WINDOW_MS of quiet the debounce matures and the worker emits a dm-trigger decision log line with kind, shouldRespond, and (for auto) the classifier's intent / confidence / reason.
  3. On a respond / step-in / solo / explicit decision, a dm_thinking frame appears on the socket — the turn fired. A sit-back decision logs shouldRespond:false and re-arms toward the dead-air mark, no dm_thinking.
  4. Send { "type": "dm_invoke" } (or a message starting @dm): the dm_thinking frame appears immediately, bypassing the quiet window and the classifier.

Diagnose a DM that never fires (or fires too eagerly)

  1. Inspect the dm-trigger queue for a delayed job (dedup id dm-trigger:{campaignId}). A present delayed job means a quiet window is counting down; its absence after activity means either it matured already or a reschedule failed — grep the API logs for ws-session debounce reschedule failed (the warn on a queue outage).
  2. Check the trigger-state keys for the campaign: last-activity (the re-validation stamp), responded-seq (the batch watermark — an unexpectedly high value means the next batch starts past recent messages), dm_responding (a turn is in flight, so the worker is gating enqueues), and first-unresponded (the max-wait anchor). A lingering dm_responding with no live turn lapses on its own (TTL ≈ lock TTL).
  3. A DM that fires on a sustained-typing hold confirms the max-wait ceiling: the debounce matured at first-unresponded + MAX_QUIET_EXTENSION_MS despite ongoing typing. That is by design.

Integration points

The server side lives in the session transport's inbound handler, which writes the typing / activity state and reschedules the debounce — and adds the dm_invoke client frame to the wire contract. The worker side is the fifth Worker in the worker process, alongside the QueueEvents subscriber that closes the turn worker's terminal-error gap. A decision enqueues a session-turn job that the session turn page's lock-fenced conductor executes; that worker in turn sets dm_responding and records the last-responded-seq watermark this page's drain logic depends on. The classifier runs through the LLM client's single abstraction with the Haiku model from config. Member counts come from the repository layer's countAcceptedMembers.
