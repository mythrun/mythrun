Fast Thinker

The player-facing prose tier — a Sonnet model driving an interleaved agentic tool loop: it streams narration, calls deterministic tools (roll_dice, roll_skill_check) when the scene needs mechanical truth, and writes prose informed by each tool's result rather than deciding the outcome itself. It runs under enforced ignorance by construction — its context type carries only public facts, so plot and NPC secrets have nowhere to live. The session-turn conductor calls it once per DM turn; everything the player reads is its output.

How it fits together

A DM turn's Fast Thinker pass is a multi-step generation, not a single prompt. The SessionController calls SonnetFastThinker.render(ctx, emit); the FT builds its prompt, runs the Vercel AI SDK's tool loop on Sonnet, and consumes the resulting stream. The model alternates between writing prose and calling tools: it narrates, decides a check is needed, calls roll_skill_check, receives the resolved outcome as a constraint, and continues narrating around that outcome — all inside one render call. The loop ends when the model stops calling tools or the per-turn cap fires.

The SDK's tool loop, not a hand-rolled one — streamText + tool() + stopWhen + prepareStep + the typed fullStream (text-delta / tool-call / tool-result / error / abort parts) + per-message cache breakpoints cover every requirement, including the cap's graceful prose close. The SDK's deterministic tool loop is plumbing — like BullMQ — not delegated reasoning, so using it does not cross the Zero-Framework-Cognition line: the prose is the model's job, the dice and skill math are deterministic code, and re-implementing the loop would be strictly more bug surface for no capability gain.

The wrapper: streamTextWithTools

The FT never reaches into the 'ai' package directly (a lint rule forbids it). It calls streamTextWithTools, the net-new streaming-with-tools primitive added to the LLM client's ai.ts alongside generateObject / streamObject / generateText. The wrapper exposes the fullStream plus two distinct usage promises — the final step's usage (the context-fill signal) and the cumulative totalUsage across all steps (the spend number) — and threads the per-turn timeout through the SDK's native timeout.

Errors and timeouts arrive as in-band stream parts, not throws — verified against the installed SDK: when the provider errors mid-stream or the per-turn timeout fires, streamText enqueues an error / abort part and closes the stream gracefully — the for await does not throw on its own. So the consume loop must throw on both, or a truncated turn ends "normally" and gets persisted as canon. There is also no mid-turn retry: the SDK's internal retry only fires on raw retryable API errors, which the middleware has already mapped away. A divergent re-stream under one turn is worse than a rare dead turn, so a failure after any frame has shipped is terminal — see the turn lifecycle.
Final-step usage and total usage are different numbers — the SDK's per-call usage is the final step only; cumulative spend is totalUsage. A five-step turn billed off the final step would under-count four Sonnet passes, so the wrapper names both explicitly. The usage promises are also pre-handled: on a zero-step failure they reject, and the wrapper attaches no-op catches so an FT that throws out of its consume loop never leaves an unhandled rejection to kill the worker.

The consume loop: the single emission point

render iterates fullStream and emits player-visible frames in stream-part order: a text-delta becomes a text_delta frame, a tool-result becomes a skill_check or dice_roll frame built from the result and its call args. Tools never emit — all emission happens here, in one place. As it consumes, the loop also assembles the returned multi-part AssistantMessage directly from the stream parts (text deltas coalesce into text parts split at tool boundaries; tool-call and tool-result parts append at their positions), so the persisted turn is Mythrun-owned and never coupled to the SDK's own message shape.

Why emit from the consume loop and not from inside a tool — the SDK executes tools at its internal pipeline pace, ahead of the consumer, so an emit from inside a tool's execute could hit the wire before the prose deltas that preceded the tool call in the model's output. fullStream interleaves tool-call / tool-result parts at their true positions, so part-order emission is model-output order. It also serializes the player-visible frames of parallel same-step tool calls (a full-party "everyone roll Perception") deterministically, even though the SDK may run those resolvers concurrently. Frames carry no sequence number, so arrival order is the only ordering — which makes this invariant load-bearing.

The cap and the prose close

FT_MAX_TOOL_STEPS (5) bounds the loop via stopWhen: stepCountIs(...): up to four tool-calling steps plus one prose-close step. A full-party group check fits in a single step through parallel tool calls, so the cap is rarely the binding limit.

The forced close is an injected instruction, not toolChoice: 'none' — verified against the Anthropic provider: toolChoice: 'none' strips the tools param entirely, and an Anthropic request whose history holds tool blocks but defines no tools is rejected with a 400 — exactly on the turns that hit the cap. So prepareStep on the final step keeps tools defined and appends a close instruction ("wrap up in prose, do not call tools"). If the model defies it and emits a tool call on the final step, that dangling call has no result; it is dropped from the persisted turn (and logged), so the rebuilt history stays clean and never 400s the next turn.

The tool registry: pure resolvers

ft-tools.ts (buildFtTools) is the extension point — the place tools register as their resolvers land. MYT-68 wired two (roll_dice, roll_skill_check); MYT-70 added the six Rules Lawyer ledger tools (cast_spell, spend_resource, acquire_resource, adjust_hp, update_condition, take_rest); world_fact_lookup and combat tools stay deferred. Tools are pure resolvers: their execute returns data only, never emits a frame, and the SDK feeds each result back to the model as the next step's input.

The ledger tools return a structured constraint, never throw, never emit — each ledger tool's execute delegates to a total Rules Lawyer resolver and returns its LedgerResolution as data. On ok:true the consume loop emits a ledger_update frame the same way it emits a skill_check; on ok:false the constraint object surfaces unchanged and the model narrates how the attempt falls short. The SDK-assigned toolCallId threads into the resolver as the journal idempotency key. The tools' model-facing schemas are deliberately flat z.objects with a kind enum, not discriminated unions: the Anthropic tool API requires every input_schema to have a root "type": "object", and Zod's discriminated union emits a root oneOf with no top-level type — which the API rejects. The per-kind requirements are enforced in execute + the resolver instead. This was found by the MYT-70 smoke, not by typecheck.
  • roll_dice — { count, sides } over the standard die set; returns { results, total }. The bounds are enforced in code (Zod plus a defensive clamp in the engine) — an unbounded count would stall the worker, which holds the session lock. For non-skill rolls (damage, wild magic). No modifier param: a "2d6+3" total would be LLM arithmetic, acceptable here and never treated as mechanical truth (authoritative damage math is the combat engine's job, later).
  • roll_skill_check — { character_name, skill, context, advantage?, disadvantage? }; the full pre-generated-DC-table flow below. character_name resolves against the session roster, a closed known set, never a free-text DB key.
The resolver's injected dependency is a scoped projection, not the whole repo — the tool loop adds a third inbound channel to the FT (tool results), which has no type-level enforced-ignorance bound. The discipline is held by scope: the skill-check resolver receives only a narrow mechanical-reads projection (findSessionParticipantCharacterByName), not the full repository, so no future tool can casually return a repo-fetched secret-tier string. world_fact_lookup stays Slow-Thinker-gated for exactly this reason. The MYT-70 ledger tools take the same shape: they receive the scoped LedgerOps surface and a per-turn transaction runner, not the whole repository.

The dice engine (Principle #4)

dice/engine.ts is pure functions over crypto.randomInt — the LLM never generates a random number. rollD20WithType returns the kept roll for advantage/disadvantage (roll twice, keep higher/lower), rollDice sums a pool with a defensive bound, calculateModifier is floor((score − 10) / 2), and resolveRollType applies the 5e rule that advantage and disadvantage cancel to a normal roll. An injectable RNG makes every path deterministically unit-testable.

The skill-check resolver (Principle #5)

skill-check.ts is the pre-generated-DC-table flow — and it is total: every failure arm returns a structured error constraint rather than throwing, because an uncaught throw would surface as a tool-error part the loop continues past, letting the model narrate an outcome with no roll. The steps:

  1. Resolve the roller from the session roster (session_participants joined to characters). The name is normalized (trim + case-fold) and matched exactly against the closed participant set — structural validation, no fuzzy matching. No match or an ambiguous name → an error constraint, never a throw.
  2. Compute the modifier — the ability modifier from the character's score plus the per-skill proficiency bonus, read from character_skills.proficiency_level: none → +0, proficient → +PB, expertise → +2×PB, using the authoritative characters.proficiency_bonus column. Both sides of the skill join are normalized (the stored skill name is itself unconstrained LLM output), and an absent row defaults to none.
  3. Pre-generate the DC table — one Haiku call returns { dc, outcomes: { fail, success, great_success } }, the outcomes authored as narrative constraints, not dialogue. The FT turn's abort signal is threaded into this nested call so a turn timeout cancels the in-flight DC generation with no orphaned spend.
  4. Roll and match — rollD20WithType + the modifier → total; the tier is total ≥ dc+5 → great_success, ≥ dc → success, else fail. The matched outcome string is the constraint. No nat-1 / nat-20 crit on ability checks — that is RAW only for attack rolls.
Roll, then match — never prose pre-written for an outcome — this is CLAUDE.md non-negotiable #5. Haiku generates the DC and three outcome descriptions before the roll; code rolls deterministically; the matched tier is injected as a constraint the FT narrates around. The model writes how a check fails or succeeds, informed by the outcome — it never decides the outcome. The frame and the persisted row both carry character_name, because in multiplayer every client must see whose check fired.
Fail-soft, so the turn never dies on a bad check — if the Haiku DC call fails or aborts, the resolver falls back to a fixed moderate DC with tier-neutral outcome templates, and the deterministic roll + tier match still run against it, so "roll then match" still holds. An unknown character, an ambiguous name, or an unmapped skill each returns an error constraint and the ft-system prompt instructs the model not to invent a result. roll_dice out of range returns a tool-error the model narrates around. Every arm is logged.

Enforced ignorance and the prompt

The FT's grounding is two things: the curated, enforced-ignorance-safe prep document (session_preps.ft_context, loaded into FtTurnContext.ftContext — see the conductor), and the full verbatim session transcript reconstructed each turn from session_messages. It is never a summary. The ft-system.txt prompt is a multiplayer rewrite of the prototype's single-player one: it encodes the participant roster + character-name attribution, the tool protocol ("call the tool, then narrate the returned constraint; never decide an outcome; never roll yourself"), enforced ignorance (never reveal what a character can't know), and how to handle an error constraint without inventing a result. MYT-70 added a Resources & The Ledger section: it teaches the six ledger tools, the rock principle (improvised objects are narrated, never spent), the three-branch reasoning for a not-found debit (environmental → narrate; fiction already granted → acquire_resource first; never established → correct gently), that binding constraints are authoritative outcomes, actor-scoping (mutate only the acting player's character), and that the [Party ledger: …] tail names resources canonically — reuse those names exactly.

MYT-69 added the NPC-authenticity half of the prompt — the FT's side of the Slow Thinker's social clock. NPCs are normal people, not quest dispensers: a stranger gets weather, prices, and wary politeness, not the NPC's troubles or secrets; small talk is the texture of the world, played in full; trust is earned across a conversation, and what an NPC has to share, the story tells the FT when it is time — via a direction. Two craft rules ride alongside: the check-frequency rule carves out genuine no-stakes chat (checks gate attempts to change a mind, deceive, or read what's hidden — never ordinary conversation), and a successful social check against an NPC whose depths the FT doesn't know yields demeanor or plausible public content, never invented hidden plot.

The FT cannot plot-dump what it does not know — that is the authenticity engine — these prompt rules only hold because enforced ignorance is structural. The FT has no playbook, no secrets, no plot in its context, so it genuinely cannot hand a stranger a quest hook. The Slow Thinker holds the secrets and the social clock and decides, post-hoc, when a conversation has earned a reveal — portioning out exactly what an NPC entrusts via a stage direction. Without the split, the carve-out would be a prompting suggestion the model could ignore; with it, the FT's ignorance is the boundary.
The running summary is the Slow Thinker's tool, not the FT's memory — the FT never reads the running summary. It holds the literal full transcript every turn, so there is no compressed history to hallucinate around. The summary is the Slow Thinker's own compression and the Scribe's session-end input; it plays no role in FT grounding or recovery. Removing it from the FT's context type is what makes "secrets have nowhere to live" structural rather than a convention.

Prompt caching: the cost lever

Holding the full transcript every turn is only affordable with prompt caching, so the FT attaches an ephemeral cache_control breakpoint to the system message (which carries the immutable ft_context head — the ideal anchor) and to the last settled history message (the end of the prior turn). Each of the up-to-five steps then re-uses the cached prefix rather than re-paying full input price on the accumulating tool-result tail.

Cache breakpoints ride per-message provider options, never the call level — verified against the provider: the Anthropic provider reads cache_control only from a message's or part's providerOptions, never from the call-level providerOptions.anthropic. A top-level setting is silently inert — no error, just full input price on every step of every turn. That is why the system prompt is passed as a system-role message (not the SDK's system: param) and why the middleware logs cacheReadTokens: a mis-placed breakpoint is otherwise invisible. The smoke asserts cache reads are non-zero on turn ≥ 2.
The standing directive is a raw tail message after the breakpoints — when the Slow Thinker has a live standing directive, the worker reads it from its Redis slot and threads it onto FtTurnContext.standingDirective; buildModelMessages appends it as one raw [DM direction: …] user message after placing the cache breakpoints. The MYT-70 [Party ledger: …] snapshot tail rides the same always-uncached zone, appended in pinned order (the ledger tail first, then the directive). Both ride past the last breakpoint, so neither perturbs the cached prefix and neither shifts the sliding-breakpoint index. It is render-only: never persisted, never pushed into ftHistory (which would render through the codec's attribution as a phantom "Player"). A one-shot direction, by contrast, is fused onto the last user message by the conductor before this assembly runs — fuse-then-append, so the one-shot lands on the real player message, not the ephemeral tail.

Integration points

The Fast Thinker is the player-facing cognitive tier behind the session-turn conductor's tier seam; the Scribe remains a stub until MYT-73, and the Slow Thinker now runs off the turn path — its stage directions reach the FT as a fused one-shot (on the player's last message) and a standing tail message, both consumed silently. It runs through the LLM client's streamTextWithTools wrapper (Sonnet) and its skill-check resolver makes a nested Haiku call through the same abstraction. Its roller resolution and per-skill proficiency reads come from the repository layer's characters.findSessionParticipantCharacterByName. The frames it emits (skill_check, dice_roll, plus the streamed text_delta) flow through the worker-latched emitter to the session transport's wire contract, and the multi-part assistant message it returns is persisted to the PG-direct transcript by the conductor.
