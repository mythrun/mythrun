End-of-session reconciliation

What happens when a session ends. The in-session working set — every fact the Fast Thinker improvised this session, tier- and provenance-annotated by the Scribe — is folded into durable canon: entities, append-only facts, relationship edges, and embeddings. One holistic Opus pass makes every match-vs-mint and contradiction judgment; deterministic code validates it and commits it in a single transaction.

How it fits together

Through a live session the Scribe accumulates the session's improvisation into a Redis working set — an append-only list of facts the Fast Thinker invented, each stamped with its tier (known / discoverable / secret) and provenance (objective ground truth, or an NPC's attributed claim). That working set is ephemeral: it lives in Redis (ridden onto the durable 5-minute Postgres checkpoint) and it never touches the world store while the session is live. Reconciliation is the closing step that makes the session's discoveries permanent — it turns the working set into canon the next session, the next prep, and the wiki can read.

Two pieces make that happen, both new in MYT-74a: a session-end lifecycle that detects a session is over and fences off the still-draining turn loop, and a reconcile pass — an eighth BullMQ worker — that does the actual fold off the hot path. The diagram traces both: the two end triggers converging on endSession at the left, and the worker's retrieve → reconcile → validate → commit pipeline on the right.

Why a holistic Opus plan, not a per-subject loop — the obvious shape is "for each working-set subject, decide match-or-mint and append its facts." But two working-set items can name the same brand-new entity; a per-subject loop would mint it twice. One Opus call that sees the whole working set at once gives the best cross-subject coherence — it can collapse two mentions into one mint, resolve a contradiction against the live canon it was shown, and omit a restatement that already matches existing canon. This is also the Zero Framework Cognition line: the match/mint/contradiction judgment is the model's; the application code does mechanical candidate retrieval and deterministic commit, never a similarity-threshold auto-match (that would hardcode a judgment ZFC delegates to the model).

The session-end lifecycle

There was no session-end flow before MYT-74a. MYT-65 built suspend (all players disconnect, the session checkpoints but stays status='active'); the sessions.summary / handoff columns sat unpopulated. This piece builds the trigger and the orchestration shell so a session can structurally end and commit its canon.

Two triggers converge on one flow, endSession in session/session-end.ts:

  • Explicit — a player sends an end_session WebSocket frame (a bare summon, no payload, like the dm_invoke "@DM button"). The session transport route resolves the world id and runs the orchestration.
  • Budget auto-end — the token budget reaches 100%. The turn worker observes the crossing on its post-flush success phase (the same place the ST-evaluation floor is bumped) and fires the same end flow. The Fast-Thinker context bound is the real session-length cap; when cumulative usage reaches it, the session has to end because the FT can hold no more transcript.
A SET-NX ending flag makes the two triggers idempotent — the explicit frame and the budget auto-end can race (a player taps end on the same turn that crosses 100%). endSession's first act is to claim a once-only session:{cId}:ending flag; the loser of the race short-circuits there. So the status flip, the reconcile enqueue, and the session_end broadcast each run exactly once no matter how many triggers fire.

The flow is ordered to fence the reconcile against still-draining in-flight work:

  1. Quiesce. Set the ending flag and cancel any pending suspend (an uncancelled suspend would later re-checkpoint an ended session — a lost update on the very checkpoint reconcile reads). The inbound WS handler then drops every frame except a redundant end_session, so no new turn is enqueued after end.
  2. Fence the in-flight turn. Acquire the per-session lock — the same lock the turn worker holds while rendering. Acquiring it means no turn is mid-render; the working set won't be mutated out from under the reconcile.
  3. Flip + enqueue. Transition the row to status='ended', ended_at=now() (reconciled_at stays NULL — only a successful commit sets it). Enqueue one reconcile job, with a per-session jobId (reconcile-{sessionId}) so a double-trigger collapses to a single broker job.
  4. Close. Broadcast a structural session_end frame to every client.
A contended lock proceeds anyway — the worker re-fences — if the lock is held (a turn is genuinely mid-flight), endSession still flips the row and enqueues. It doesn't block. The reconcile worker re-acquires the same lock itself before it reads the working set, so the fence is enforced there regardless. The lock-fence is the load-bearing part; the final turn's trailing post-turn jobs (Scribe, ledger) drain on their own queues.

The cross-session start interlock

The working set is keyed by campaign (session:{cId}:workingset — one live session per campaign), and the idx_sessions_one_active index frees the active slot the instant status flips to ended. Without a guard, a new session could start on the same campaign, append onto the same Redis list, and have the prior session's still-pending reconcile load the polluted list and clear() it — silently destroying the new session's working set on a perfectly normal flow (budget auto-end of session 1 → start session 2).

The fix is an interlock at POST /api/sessions/:campaignId/start: it returns 409 reconcile_pending while the campaign's most-recent session is ended_at IS NOT NULL AND reconciled_at IS NULL. No new session starts until the prior one's canon is committed and its working set cleared. Reconcile is fast (async, seconds to tens of seconds), so the block is brief in the happy path.

The tri-state is the reader contract — ended_at set with reconciled_at NULL means "ended, reconcile pending or failed." Consumers must not treat such a session's canon as complete. reconciled_at set means canon is committed. A terminal reconcile failure therefore surfaces as a stuck campaign plus an alarm — observable-stuck, not silent canon loss. That is the correct failure mode for a canon write path: better to block the next session than to lose what happened in this one.

The reconcile pass

The worker body in session/session-reconcile.ts is ZFC-shaped: a deterministic retrieve, one LLM judgment, a deterministic commit. The world id is resolved once (session → campaign → world). The worker is not total — unlike the post-turn Scribe job, it throws on transient failure so BullMQ retries, and every retry is idempotent (the commit gate, below, keeps a re-run from double-writing).

1. Retrieve (deterministic)

Load the working set. For each distinct subject, call findSimilarEntities to pull the top-K canon entity candidates, then load those candidates' live facts (superseded_by IS NULL) so the reconciler sees current canon, never a fact a prior session already corrected away. findSimilarEntities throws on failure (it is on the canon write path — a swallowed embed blip would make the reconciler think no similar entity exists and mint a duplicate), so a retrieval failure propagates and the job retries. This fan-out — the per-subject query embeddings, batched through Voyage, and the candidate reads — is the dominant latency, not the single Opus call.

2. Reconcile (one holistic Opus call)

llm/session-reconciler.ts is one Opus call through the standard generateObject boundary. Its input is the full working set (each item's subject name, content, kind, tier, provenance, source, optional parent name), the retrieved candidates and their live facts, and the world tone. Its output is a structured plan: entity match/mint ops, fact appends (each optionally superseding a live fact), and relationship edges. The model owns every judgment — it decides match vs mint per subject, resolves contradictions by absorb (canonize the improvised version) or supersede (append the canonical version and point the old fact's superseded_by at it), bakes an NPC's attribution into an attributed claim's content, and omits any restatement that already matches live canon so a stable entity doesn't accrete a duplicate fact every session.

The output ceiling is pinned, and redactRawText is on — the budget auto-end fires on the largest sessions, so the call sizes its maxOutputTokens for the worst case (an unpinned cap risks mid-JSON truncation → a terminal fail). And because the reconciler reasons over secret-tier items, a malformed response must never spill a secret into the repair log or the rethrown error's diagnostic — redactRawText: true nulls the raw snippet, exactly the posture the secret-tripwire and retcon-author calls use. A sonnet repair strategy is acceptable only because the validator (next) re-checks every id post-repair — repair fixes JSON shape, never the match/mint judgment.

3. Validate (deterministic — structural + policy)

session/reconcile/validate.ts is pure (no I/O) and security-critical. It builds the load-bearing subject-name → entity-id map (matched canon ids plus minted ids) and resolves every fact and relationship op through it. The arms: every match points at a live candidate; every minted type is legal (npc | location | faction | item); every fact subject and every relationship endpoint resolves to an entity op (else it is a dangling ref → reject); a supersede target is a live fact. There is no semantic re-judgment here — the validator enforces structure and policy, not meaning.

Reject the plan, don't silently fix it — a dangling reference or a tier downgrade is a model bug worth surfacing. The validator returns the first failure as a structural reason code and the worker throws, so the non-deterministic Opus call is retried (the attempts cap bounds a persistently-failing one). A partial commit never happens — validation runs entirely before the transaction opens.

4. Commit (deterministic, transactional)

session/reconcile/commit.ts folds the validated plan into canon in one transaction. It mints entities (created_in='session:<id>', marked touched-by-play), appends facts, sets superseded_by / superseded_at pointers on corrected facts (and NULLs the superseded fact's embedding so it leaves the HNSW index rather than burning recall budget), inserts relationship edges and any sub-faction hierarchy edges, and writes the new facts' embeddings. The Voyage re-embed call runs before the transaction opens — slow I/O never sits inside a BEGIN — and the resulting vectors are written inside the transaction, so embeddings are atomic with the facts and can't desync across a retry. On a clean commit the worker clears the working set.

The conditional reconciled_at update is the idempotency mutex — the commit's last in-transaction statement is UPDATE sessions SET reconciled_at = now() WHERE id = $1 AND reconciled_at IS NULL. Zero rows updated means another execution already reconciled this session → roll the whole transaction back, so no duplicate canon lands. A plain unconditional write would not be a guard: two executions that both read NULL on entry (the candidate retrieval and the seconds-long Opus call sit between the entry check and BEGIN) would both commit a full duplicate of the working set. The conditional WHERE serializes them; the on-entry check is just a cheap early-out.

The append-only fact log

Migration 027 makes facts append-only for corrections. A correction never edits a row's content — it appends a new fact and points the old fact's superseded_by at it (with a superseded_at stamp). Live canon is superseded_by IS NULL; the full history is the supersede chain. The same migration adds sessions.reconciled_at — the completion marker and the idempotency gate. A partial index idx_facts_live_by_entity on (entity_id, access_level) WHERE superseded_by IS NULL matches the live-canon snapshot predicate.

ON DELETE SET NULL on the supersede FK is deliberate — the FK from a live fact to the superseded fact it replaced is declared ON DELETE SET NULL, not the bare default. entities → facts is ON DELETE CASCADE, so a world-regen wipe that deletes an entity whose superseded fact is pointed-to by a live fact would otherwise FK-abort the cascade. Setting the pointer to NULL on delete lets the wipe proceed.

Reconcile-committed facts carry three code-stamped columns: source='session' (the provenance marker distinguishing session-improvised canon from prep canon), narrative_status='delivered' (these facts were shown to players this session), and a topic the model emits per fact (it drives later grouping and retrieval, so a constant stamp would degrade it). A session-committed secret fact is indistinguishable at read time from a prep secret fact and inherits the same Slow-Thinker over-pull gate.

The live-only read filter

An append-only log means every canon-fact reader must default to live-only, or a corrected-away fact would surface beside its correction. The read defaults to superseded_by IS NULL through a binder flag (so a future history/audit reader can opt into the full chain — a durable shape, not a hardcoded WHERE per call site). The reader set that now filters live-only: the world-retrieval searchFacts (the Fast Thinker's search_lore arm), the member-facing world-snapshot view, the prep/coherence composite read, the embed-write backfill (skip superseded rows — don't re-embed dead canon), and the reconciler's own candidate-fact read (else a superseded secret could re-enter a later reconcile and un-retcon itself).

Enforced ignorance

The reconciler reasons over secret-tier working-set items and secret-cleared candidate facts, so the validated plan legitimately contains secret prose — a secret fact's content is the secret, and this call is allowed to write it into canon. The boundary here is therefore not "no player-facing surface." There are two real surfaces, and both are mechanical, not prompt-trusted.

The log/alert surface is the actual leak vector. The validated plan object is never logged or broadcast (the session_end frame is structural; the plan is not in it), and every alert payload — a validator reject, a terminal failure — carries structural facts only: op counts, a reject reason code, ids, sessionId, never content prose or the working-set snapshot. A reject reason is a structural code (dangling_match, tier_downgrade, …), never a string that echoes a fact.

Tier and attribution are preserved on commit, by mechanical guard. Tier and attribution preservation is policy enforcement — the explicit ZFC exception — so the validator enforces it structurally, not by trusting the prompt:

  • Tier floor. Each plan fact carries the originating working-set item's subject name (the key the Scribe stamped, not the model-rephrasable entity name). The validator joins each fact to its item by subject name and rejects the plan if a fact's access level is weaker than its item's tier. Per-fact, not per-entity (entity granularity would wrongly bury a secret entity's legitimately-known facts); reject-not-edit (a downgrade is a model bug worth surfacing).
  • Attribution arm. Each plan fact carries claimedBy — the NPC name for an attributed claim, else null. The validator rejects a fact whose working-set item is provenance: attributed but whose claimedBy is null (the model dropped the attribution → would canonize a hearsay claim as objective truth). claimedBy is the structural signal the validator checks; the prompt also bakes the attribution into the fact content, but the structural arm is what's tested deterministically.
Why the structural claimedBy, not just prose attribution — an attributed working-set item ("Marsh the Fishmonger claims the harbor answers to smugglers") must canonize as a claim, never as ground truth, so an NPC's lie or partial knowledge can't silently become canon. Baking the attribution into the prose alone (D6) is invisible to a test; the claimedBy field is the structural signal the validator checks and the leak matrix exercises with a mocked model — restoring the structural-and-tested posture the Scribe established.

Operating this piece

Recover a stuck reconcile_pending campaign

  1. Symptom: POST /api/sessions/:campaignId/start returns 409 reconcile_pending and stays that way. The campaign's most-recent session is ended_at set, reconciled_at NULL — the reconcile never completed.
  2. Confirm the worker exhausted its retries: look for a reconcile_plan_rejected or a transient-failure log line for that sessionId in the worker service logs (structural fields only — no plan content).
  3. The working set is not lost — it survives on the durable 5-minute Postgres checkpoint. The correct recovery is to re-drive the reconcile job for that session (the conditional gate makes a re-run idempotent); a persistent rejection means a real plan bug to fix before re-driving.

End a session by hand (dev)

  1. With a live session open over the WebSocket, send an end_session frame. The server flips the row to ended, broadcasts session_end, and enqueues the reconcile job.
  2. Watch the worker logs for reconcile_committed (carries op counts only). Then inspect sessions.reconciled_at (now set) and the new facts rows (source='session') for the world.

Integration points

This page picks up where the Scribe leaves off: the Scribe builds the tier- and provenance-annotated working set during the session; reconciliation commits it at the end. The end lifecycle lives at the session transport seam (the end_session / session_end frames, the inbound ending-gate, the start interlock) and is also fired by the turn worker's budget auto-end. The reconcile worker is the eighth BullMQ worker. It retrieves candidates through the world-store retrieval resolvers and writes through the repository layer's facts, entities, relationships, and entityHierarchy namespaces; the append-only superseded_by / superseded_at columns and sessions.reconciled_at are on the schema. Downstream gating stays intact — the wiki-data refresh (a later piece) reads only known facts; secret tiers stay behind the Slow-Thinker gate.

The reconcile plan (Zod root)

Op group Shape
entities[] op (match | mint), subjectName, canonEntityId (set when matching), name, entityType, accessLevel.
facts[] subjectName (the tier-floor join key), topic, content (no .max() — a secret's content is the secret), accessLevel, claimedBy (the structural attribution signal), supersedesFactId.
relationships[] fromSubjectName, toSubjectName, relationshipType, description.

Validator reject reasons (structural codes)

Reason Meaning
dangling_match A match op's canonEntityId is null or not a live candidate.
dangling_fact_subject A fact's subjectName resolves to no entity op.
dangling_relationship_endpoint A relationship endpoint resolves to no entity op.
supersede_target_not_live A supersedesFactId is not a live canon fact.
tier_downgrade A fact's access level is weaker than its working-set item's tier.
attribution_dropped An attributed item's fact has claimedBy: null.
