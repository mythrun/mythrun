End-of-session reconciliation

What happens when a session ends. First the table gets a live send-off — a player-less farewell turn the Fast Thinker renders in its own voice. Then two off-the-hot-path jobs fire. Reconcile folds the in-session working set — every fact the Fast Thinker improvised this session, tier- and provenance-annotated by the Scribe — into durable canon: entities, append-only facts, relationship edges, and embeddings, via one holistic Opus match / mint / supersede / promote pass. Promotion is what makes the party's campaign wiki grow with play: a discoverable or secret canon fact the party surfaced this session is flipped up to known, after which it appears in the member-readable wiki read. Post-session analysis reads the transcript and writes the next session's narrative state — a player-facing recap plus a secret-aware handoff that primes the prep engine (including verbatim NPC voice lines that keep characterization consistent across sessions). Both closeout jobs also read the farewell's durable closing narration — the player-less farewell skips the Scribe, so the send-off prose is the only place the session's final beats live — and fold it in as the authoritative account of how the session ended.

How it fits together

Through a live session the Scribe accumulates the session's improvisation into a Redis working set — an append-only list of facts the Fast Thinker invented, each stamped with its tier (known / discoverable / secret) and provenance (objective ground truth, an NPC's attributed claim, or a dice-earned grant). That working set is ephemeral: it lives in Redis (ridden onto the durable 5-minute Postgres checkpoint) and it never touches the world store while the session is live. Reconciliation is the closing step that makes the session's discoveries permanent — it turns the working set into canon the next session, the next prep, and the wiki can read.

The pieces, layered across MYT-74a and MYT-74b: a session-end lifecycle that detects a session is over, gives the table a live farewell, and fences off the still-draining turn loop; a reconcile pass that folds the working set into canon off the hot path (MYT-74a); and a post-session analysis pass that reads the transcript and writes the next session's narrative state — recap plus handoff (MYT-74b). The diagram traces all of it: the two end triggers beginning the end at the left, the farewell turn and the finalize that fires the two closeout jobs in the middle — with the durable closing narration the farewell leaves behind for both jobs to read — and each worker's pipeline on the right.

Why a holistic Opus plan, not a per-subject loop — the obvious shape is "for each working-set subject, decide match-or-mint and append its facts." But two working-set items can name the same brand-new entity; a per-subject loop would mint it twice. One Opus call that sees the whole working set at once gives the best cross-subject coherence — it can collapse two mentions into one mint, resolve a contradiction against the live canon it was shown, and omit a restatement that already matches existing canon. This is also the Zero Framework Cognition line: the match/mint/contradiction judgment is the model's; the application code does mechanical candidate retrieval and deterministic commit, never a similarity-threshold auto-match (that would hardcode a judgment ZFC delegates to the model).

The session-end lifecycle

There was no session-end flow before MYT-74a. MYT-65 built suspend (all players disconnect, the session checkpoints but stays status='active'); the sessions.summary / handoff columns sat unpopulated. This piece builds the trigger and the orchestration shell so a session can structurally end and commit its canon.

Two triggers converge on the begin phase, endSession in session/session-end.ts:

  • Explicit — a player sends an end_session WebSocket frame (a bare summon, no payload, like the dm_invoke "@DM button"). The session transport route resolves the world id and runs the orchestration.
  • Context-ceiling auto-end — the session reaches 100% of its length bound. The turn worker observes the crossing on its post-flush success phase (the same place the ST-evaluation floor is bumped) and fires the same begin flow. The bound is the Fast Thinker's context window: it re-sends the whole transcript on every call with no compaction, so when its fill reaches SESSION_FT_CONTEXT_BUDGET the session has to end — the next turn would not fit. It is a length bound and not a spend cap; myth-zd6pn retired the cumulative-token ceiling that used to fire here, which counted cache reads against a pre-caching budget and ended sessions roughly ten times too early.

Begin: a farewell, not an inline finalize

MYT-74b split the end into a begin phase and a complete phase so the table gets a live send-off before the session is structurally over. endSession only begins it. It does four things and stops:

  1. Claim the flag. Set the once-only session:{cId}:ending flag (SET-NX). The loser of an explicit-frame-vs-auto-end race short-circuits here.
  2. Cancel the pending suspend. An uncancelled all-disconnected suspend would later re-checkpoint an ending session — a lost update keeping status='active', undoing the end. cancelSuspend is a no-op when nothing is pending.
  3. Read the watermark. Read the responded-seq watermark and thread it onto the farewell payload as maxConsumedSeq — a player-less turn must not advance past unresponded player seqs.
  4. Enqueue ONE farewell turn. A player-less trigger.kind: 'farewell' turn, jobId farewell-{sessionId}, carrying the resolved worldId so the finalize needs no campaign→world read of its own.
A SET-NX ending flag makes the two triggers idempotent — the explicit frame and the auto-end can race (a player taps end on the same turn that crosses 100%). endSession's first act is to claim the flag; the loser short-circuits there. So exactly one farewell turn is enqueued no matter how many triggers fire — and the farewell-{sessionId} jobId is a broker-level dedup backstop beyond the flag.

The farewell turn is rendered by the turn worker like any other turn, but player-less. Its direction (a fixed "bring the scene to a natural close" cue) rides the single-bracket [DM direction:] silent-consume seam — the same seam the MYT-73 correction turn established — so the Fast Thinker writes the send-off in its own voice rather than quoting a marker. It joins the correction turn under a shared isPlayerless predicate in the turn worker: neither advances the watermark, enqueues the Scribe, nor runs the auto-end. The Scribe skip has a consequence the closeout jobs must answer for: whatever the send-off establishes — an NPC departing, an object reaching its finished form — never enters the working set. The farewell's prose is still persisted like any turn's, as durable dm_text rows stamped trigger_kind='farewell', and those rows land at persistTurn, before the finalize enqueues the closeout jobs. Both jobs read them back as the closing narration (below). The turn page covers the render seam and the gates.

Complete: the unconditional finalize

finalizeEndedSession is the complete phase, run from the farewell turn's finally after the render — so the table sees the DM's send-off, then the session_end frame. finally always runs, so a thrown farewell render still finalizes: a session always ends. It does four things:

  1. Flip, conditionally. markEnded sets status='ended', ended_at=now() only when the row isn't already ended, returning the rowCount (reconciled_at and summary both stay NULL — those are the reconcile and analysis completion markers).
  2. Enqueue the two closeout jobs. One reconcile job (reconcile-{sessionId}) and one analysis job (analysis-{sessionId}), both per-session jobIds so a re-enqueue collapses to the existing broker job.
  3. Broadcast, once. Only the finalize that won the flip (rowCount 1) broadcasts the structural session_end frame; a later finalize (rowCount 0) skips it.
  4. Release the ending fence. clearEnding — an idempotent DEL, run on both arms — drops the session:{cId}:ending flag now that the row is durably ended: from here the /start active-session and reconcile_pending preconditions own every later window.
The conditional flip is what makes session_end fire exactly once — the finalize is callable from two places: the farewell turn's finally (the normal path) and a QueueEvents backstop (the terminal-stall path, below). Both call the same idempotent function. The reconcile and analysis enqueues collapse on their jobIds, but the broadcast would double-fire without a gate — so markEnded returns the rowCount and only the winner broadcasts. A second finalize is otherwise harmless.
The fence is released at finalize; its TTL is only the crash backstop (myth-x4ca4) — the ending flag's two jobs (fence the end orchestration; drop inbound frames while the row is still active) both expire the moment markEnded flips the row. Nothing originally cleared it, so after every clean end the campaign's next /start answered 409 session_ending until the full 1h TTL reaped the flag — "session over, come back in an hour," found live with session-2 prep ready and 40 minutes left on the fence. The DEL runs on both finalize arms because the noop arm's caller may be the QueueEvents backstop finishing a crashed winner's cleanup — a fence its winner never got to release. The TTL remains as the last resort for a session whose finalize never runs at all.
Why a farewell turn, not an inline flip-and-broadcast — MYT-74a's endSession flipped the row and broadcast session_end inline. That ended the session abruptly: the client saw "session over" with no narrative close. Routing the end through a real (player-less) turn lets the Fast Thinker render a send-off first, and the finalize rides the turn's existing lock + finally — so the turn loop is already quiesced when the row flips, no separate lock-fence needed. The reconcile worker still re-acquires the per-session lock itself before reading the working set, so the fence is enforced there regardless.
A QueueEvents backstop covers the terminal stall — the in-worker finally covers a clean render and a thrown render, but not a worker that crashes mid-flight: BullMQ retries the job maxStalledCount times, then fails it inside a Lua script that emits only a broker-side event — never the per-worker finally. The session-turn QueueEvents subscriber listens for that broker failed event and, for a farewell turn, runs finalizeEndedSession itself. Idempotent, so a double-fire with the in-worker path is safe. Without it a crashed farewell would leave a session that never finalizes — the table waiting forever.
The finalize logger keeps its pino binding (MYT-92) — the turn worker hands finalizeEndedSession a logger, and the finalize logs at info after each step. Pino's methods read instance internals through this, so plucking them into a plain object literal ({ info: logger.info, … }) detaches the binding and every finalize log call throws — after the flip, the enqueues, and the broadcast have already landed. That late throw marks the whole farewell turn job failed, so BullMQ retries it and the table gets a second send-off for a session that already ended. bindFinalizeLogger wraps the source logger in delegating arrows that keep each call on the original instance (a fake logger with no info falls back to warn), so the finalize's logging can't fail a turn that otherwise succeeded. Caught live by the play screen's end-to-end session run.

The cross-session start interlock

The working set is keyed by campaign (session:{cId}:workingset — one live session per campaign), and the idx_sessions_one_active index frees the active slot the instant status flips to ended. Without a guard, a new session could start on the same campaign, append onto the same Redis list, and have the prior session's still-pending reconcile load the polluted list and clear() it — silently destroying the new session's working set on a perfectly normal flow (auto-end of session 1 → start session 2).

The fix is a two-part interlock at POST /api/sessions/:campaignId/start. It returns 409 reconcile_pending while the campaign's most-recent session is ended_at IS NOT NULL AND reconciled_at IS NULL — no new session starts until the prior one's canon is committed and its working set cleared. And it returns 409 session_ending while the ending flag is set.

Why session_ending needs its own guard — MYT-74b moved the status flip to the finalize, which runs after the farewell renders. During that render the row is still status='active' with ended_at NULL, so the reconcile_pending interlock (which reads ended_at) can't see the end yet. The ending flag is set at the very start of the begin phase, so the second guard fences the whole window from begin-of-end through finalize — and the finalize releases it (clearEnding, myth-x4ca4), so the guard covers exactly that window, never the hour its TTL would imply. Reconcile is fast (seconds to tens of seconds), so the combined block is brief in the happy path.
The tri-state is the reader contract — ended_at set with reconciled_at NULL means "ended, reconcile pending or failed." Consumers must not treat such a session's canon as complete. reconciled_at set means canon is committed. A terminal reconcile failure therefore surfaces as a stuck campaign plus an alarm — observable-stuck, not silent canon loss. That is the correct failure mode for a canon write path: better to block the next session than to lose what happened in this one.

The reconcile pass

The worker body in session/session-reconcile.ts is ZFC-shaped: a deterministic retrieve, one LLM judgment, a deterministic commit. The world id is resolved once (session → campaign → world). The worker is not total — unlike the post-turn Scribe job, it throws on transient failure so BullMQ retries, and every retry is idempotent (the commit gate, below, keeps a re-run from double-writing).

1. Retrieve (deterministic)

Load the working set — and the farewell turn's closing narration (listFarewellNarration: the durable trigger_kind='farewell' dm_text rows, joined in seq order). The farewell is player-less, so the post-turn Scribe never ran on it: its closing beats live only in those rows. Before myth-8mom0 the reconcile read only the working set, so canon committed the session's pre-farewell state and the next session's prep re-serialized it — a carving the send-off finished reverted to half-done; an NPC the send-off walked out of town was back at the bar. Both were live reproductions.

Read the durable prose; don't un-gate the Scribe (myth-8mom0) — the obvious fix is to let the Scribe run on the farewell so its facts enter the working set like every other turn's. But the Scribe is an async post-turn job, and the reconcile is enqueued in the same finally that follows the farewell render — un-gating would open a race at exactly the boundary this fix exists to close (the Scribe's working-set append landing after the reconcile loads, or worse, clears the set), and closing it would mean new sequencing machinery. The durable rows need none of that: they are persisted at persistTurn, before the finalize enqueues either closeout job, so by the time a worker runs, the narration is already there — race-free by construction, no ordering change. And the isPlayerless Scribe gate keeps its other job untouched: the correction turn must stay Scribe-skipped (a retcon line points at the buried secret it exists to bury).

A session with an empty working set and no closing narration takes a shortcut: run the commit with an empty plan, so the reconciled_at gate still fires through the same conditional path and the start interlock releases consistently. Both inputs must be empty.

The empty-working-set shortcut must not skip a farewell session — a quiet session can end with an empty working set (nothing improvised worth extracting) and still land real facts in its send-off, and because the farewell is Scribe-skipped, those are precisely the sessions whose only canon-worthy material lives in the closing narration. The pre-myth-8mom0 shortcut keyed on the working set alone, so such a session was waved past the reconciler and its close dropped entirely — the bug class this fix closes, in its purest form.

For each distinct working-set subject — plus, when there is one, the whole closing narration as one more query — call findSimilarEntities to pull the top-K canon entity candidates, then load those candidates' live facts (superseded_by IS NULL) so the reconciler sees current canon, never a fact a prior session already corrected away. findSimilarEntities throws on failure (it is on the canon write path — a swallowed embed blip would make the reconciler think no similar entity exists and mint a duplicate), so a retrieval failure propagates and the job retries. This fan-out — the query embeddings, batched through Voyage, and the candidate reads — is the dominant latency, not the single Opus call.

Candidate retrieval runs over the closing text too — the closing narration's subjects are not working-set subjects, so the per-subject fan-out would pull no candidates for them. The reconciler would then see a farewell beat about an entity it was shown no canon row for, and a subject the farewell merely updates (the carver whose piece is finished in the send-off) would be minted as a duplicate entity instead of matching — and superseding into — its existing canon row. One extra semantic query over the whole closing text pulls those candidates into the same dedup'd pool, so an end-state beat resolves onto the entity it is about.

2. Reconcile (one holistic Opus call)

llm/session-reconciler.ts is one Opus call through the standard generateObject boundary. Its input is the full working set (each item's subject name, content, kind, tier, provenance, source, optional parent name), the retrieved candidates and their live facts, the world tone, and — when the session had one — the closing narration, threaded as an authoritative end-state block. Its output is a structured plan: entity match/mint ops, fact appends (each optionally superseding a live fact), relationship edges, and a promotions list. The model owns every judgment — it decides match vs mint per subject, resolves contradictions by absorb (canonize the improvised version) or supersede (append the canonical version and point the old fact's superseded_by at it), bakes an NPC's attribution into an attributed claim's content, and omits any restatement that already matches live canon so a stable entity doesn't accrete a duplicate fact every session.

A dice-earned item is rendered as canon-on-grant, not as one more claim — the working set carries a third provenance alongside objective and attributed: dice_outcome, stamped on facts asserted in a turn whose skill check actually passed. The reconciler's rendering says so in as many words — "dice-earned (tier on a resolved roll — canon-on-grant; the world conforms to it)" — because the model otherwise has no way to tell a reward the system itself granted from an improvisation that happens to collide with prep material, and would resolve the collision by discarding the grant. The direction of reconciliation is the opposite: the world conforms to play. A collision steers future turns; it does not retract something a player earned at the table.

The prompt makes the closing narration authoritative for how the session ended: any canon-worthy end-state it establishes is folded, matched onto an existing candidate rather than minted fresh, and where the close contradicts a live candidate fact — the half-finished carving that is now complete, the NPC who was present and has now left — the final version supersedes the stale one, never both. A closing-narration fact is player-witnessed prose, so it lands at known unless it refines a higher-tier candidate; a close that merely restates canon is omitted like any other restatement.

The fourth branch: promote (MYT-74c)

Per working-set item the reconciler already retrieves the canon candidates and their live facts at every tier — and the candidates render with their factId and accessLevel. So the model has everything it needs to make one more per-item decision after match/mint/supersede: promotion. When a working-set item matches an existing candidate fact that is discoverable or secret — the same underlying fact, surfaced in play this session — the reconciler puts that candidate's factId in promotions rather than minting a near-duplicate known fact. A match against an already-known candidate is omitted as before (already public); a genuinely new item is minted at its tier; a refinement supersedes — and a superseded fact is never also promoted (it is dead canon). Promotion needs no new discovery signal, no registry, no per-secret-to-fact linkage: the working-set match is the discovery signal.

Promotion is a branch of the match the reconciler already makes, not a new mechanism — the obvious alternative is a real-time "fact was revealed" hook firing mid-session, or a side-table mapping each [SECRET-n] to the fact it guards. Both are machinery the reconcile pass doesn't need: it already does a read-then-write that decides, per working-set item, whether it matches existing canon. "Matched a non-known candidate the party surfaced" is the same trusted judgment the reconciler makes for every canon write — promotion is just the fourth outcome of it. The residual risk (a spurious match promoting a fact that wasn't really discovered) is exactly the residual match-quality risk of any reconcile write, bounded by the same eval, and — critically — never reaches a player except through the known-tier, no-bypass, member-scoped wiki read.
The output ceiling is pinned, and redactRawText is on — the budget auto-end fires on the largest sessions, so the call sizes its maxOutputTokens for the worst case (an unpinned cap risks mid-JSON truncation → a terminal fail). And because the reconciler reasons over secret-tier items, a malformed response must never spill a secret into the repair log or the rethrown error's diagnostic — redactRawText: true nulls the raw snippet, exactly the posture the secret-tripwire and retcon-author calls use. A sonnet repair strategy is acceptable only because the validator (next) re-checks every id post-repair — repair fixes JSON shape, never the match/mint judgment.

3. Validate (deterministic — structural + policy)

session/reconcile/validate.ts is pure (no I/O) and security-critical. It builds the load-bearing subject-name → entity-id map (matched canon ids plus minted ids) and resolves every fact and relationship op through it. Entity-op resolution is total — every match op lands in the map, through a resolution chain that heals rather than rejects. Id-bind: the claimed canonEntityId is a live candidate → bind as claimed. Name-rebind: a non-binding id (null, hallucinated, or a mis-transcribed UUID) whose claimed name uniquely identifies one live candidate → rebind to that candidate. A name carried by more than one candidate is excluded from the rebind map at construction — an ambiguous rebind would be a guess. Mint-degrade is the floor: a match that neither binds nor rebinds mints a new entity instead of failing the plan. Heals surface on the ok result as rebinds and demotions, and the worker warn-logs them (reconcile_entity_ops_healed) as entity names and ids only — never fact prose.

Between the Opus call and the validator, the worker runs a canon-by-name pre-pass: for each match op that would neither id-bind nor name-rebind, one indexed entities.findIdByWorldAndNormalizedName lookup asks whether the claimed name is real canon the top-K-per-subject retrieval simply never surfaced. A hit joins the rebind map and the live-candidate set, so the validator heals it as a rebind rather than demoting a genuinely canonical entity to a duplicate mint.

Entity ops heal or mint — they never reject (myth-ejsp5) — the original posture rejected the whole plan when a match's canonEntityId didn't bind (dangling_match). Live, that was a brick: Opus reliably names entities and unreliably transcribes UUIDs, and it emitted match-with-null-id in two shapes — naming real canon the per-subject candidate retrieval never surfaced ("Maret Varden", canon since session 1), and match-where-mint-was-meant for genuinely new entities. Five consecutive plans rejected (each rejection re-spends the whole Opus reconcile, ~$0.50), the exhausted job vanished (removeOnFail), and the campaign stuck at reconcile_pending forever. Each entity op is independently healable, so failing the whole plan bought nothing — and mint-degrade is a safe floor because the canon-by-name pre-pass sits in front of it: a wrong mint now requires a name genuinely absent from canon, and a near-duplicate entity is a wart a later reconcile can match against, where a bricked campaign is an outage. dangling_match left the reject union entirely — it is unreachable.

The remaining arms still reject: every fact subject and every relationship endpoint resolves to an entity op (else it is a dangling ref → reject); a supersede target is a live fact; and — MYT-74c — every promotions id is a live candidate fact (dangling_promotion otherwise). There is no semantic re-judgment here — the validator enforces structure and policy, not meaning.

Promotion is a distinct op — it does NOT pass the tier-floor — the tier_downgrade arm guards fact-add ops: a minted/superseded fact may never land weaker than its working-set item's tier (that would bury a secret as public). A promotion is the sanctioned upgrade of an existing canon fact, so routing it through the same floor would be backwards. Its check is its own: the id must be in liveFactIds — the same live-candidate set that backs the supersede arm, so no new validator input is needed. The reject reason stays a structural code with no content, per the log rule below.
The remaining arms reject, not silently fix — a dangling fact subject, a dead supersede target, a tier downgrade, or a dropped attribution is a model bug worth surfacing, and unlike an entity-op miss none of them has a deterministic heal that preserves meaning: rebinding a fact to a guessed subject would hang prose on the wrong entity, and auto-raising a downgraded tier would paper over a policy violation the retry usually fixes. The validator returns the first failure as a structural reason code and the worker throws, so the non-deterministic Opus call is retried (the attempts cap bounds a persistently-failing one). A partial commit never happens — validation runs entirely before the transaction opens.

4. Commit (deterministic, transactional)

session/reconcile/commit.ts folds the validated plan into canon in one transaction. It mints entities (created_in='session:<id>', marked touched-by-play), appends facts, sets superseded_by / superseded_at pointers on corrected facts (and NULLs the superseded fact's embedding so it leaves the HNSW index rather than burning recall budget), inserts relationship edges and any sub-faction hierarchy edges, and writes the new facts' embeddings. The Voyage re-embed call runs before the transaction opens — slow I/O never sits inside a BEGIN — and the resulting vectors are written inside the transaction, so embeddings are atomic with the facts and can't desync across a retry. After the play-marking and before the markReconciled gate, it applies the promotions: facts.promoteToKnown flips each matched candidate to known and returns the distinct owning entity ids it actually flipped, then entities.promoteToKnown flips those entities too. On a clean commit the worker clears the working set.

Entity follows fact, deterministically — the wiki filters entities by tier first, then loads their known facts. A fact promoted to known on a still-discoverable entity would be orphaned out of the view — the fact is public but its owning entity is hidden, so the read never reaches it. So the commit auto-promotes the owning entity of every promoted fact (this is mechanical bookkeeping, not LLM judgment — the explicit ZFC exception). Revealing one fact reveals the entity's existence plus that fact only: the entity's other non-known facts stay tier-filtered, and the wire carries no prose kernel for it, so no characterization blob leaks with the reveal. Promotion is a metadata flip — access_level changes, content does not — so there is no supersede and no re-embed: the content-derived embedding is already live and simply starts passing the known filter. Both repo UPDATEs guard access_level <> 'known' (and facts.promoteToKnown also superseded_by IS NULL), so a re-run is idempotent and a dead fact is never resurrected. The whole step lives inside the reconcile transaction, so a gated re-run rolls the promotions back with everything else.
The conditional reconciled_at update is the idempotency mutex — the commit's last in-transaction statement is UPDATE sessions SET reconciled_at = now() WHERE id = $1 AND reconciled_at IS NULL. Zero rows updated means another execution already reconciled this session → roll the whole transaction back, so no duplicate canon lands. A plain unconditional write would not be a guard: two executions that both read NULL on entry (the candidate retrieval and the seconds-long Opus call sit between the entry check and BEGIN) would both commit a full duplicate of the working set. The conditional WHERE serializes them; the on-entry check is just a cheap early-out.

Post-session analysis and the handoff

Reconcile commits facts. The second closeout job, in session/post-session-analysis.ts, writes narrative state — what the session was about and where it left things. It is the same ZFC shape as reconcile: a deterministic read, one Opus judgment, a deterministic verify-and-write. It is not total — it throws on transient failure so BullMQ retries, gated idempotent on summary IS NULL. It runs on its own worker (concurrency 1, 180s lock) and takes no embedder — analysis doesn't embed.

The job reads five durable inputs, all safe to read after the WebSocket closes: the bounded transcript tail (the latest 160 rows — the late tail is where evolved relationships and voice live), the prep sd_playbook, the Slow-Thinker running summary from Redis, the PC roster, and the farewell's closing narration (the same listFarewellNarration read the reconcile makes). llm/post-session-analysis.ts feeds them to one Opus call that emits a { summary, emergingThreads, handoff } object.

  • summary / emergingThreads — the player-facing recap. Secret-free by construction: the prompt's hard rule is that these describe only what the players witnessed at the table. They land in sessions.summary as a JSON wrapper, and reach players through the recap route.
  • handoff — the SessionHandoff, which may be secret-aware (it feeds the next session's prep pipeline, not any player surface). It carries the party's end-of-session positions and conditions, the in-world time, the unresolved threads (most-urgent first), per-NPC state (a paraphrasable disposition) and voice (verbatim late-session lines), and per-location atmosphere. It lands in sessions.handoff.

The closing narration lands in the prompt as a distinct authoritative block: the summary and every end-state field of the handoff — party positions and conditions, timeOfDay, each NPC's state, the unresolved threads — must reflect the session's closing state, not an earlier mid-session moment. That is the analysis half of the myth-8mom0 carry: the close reaches the next session through the surfaces that already exist (the recap, and the handoff's "Where We Left Off" anchor in prep), so a departed NPC stays departed in the next session's opening. It composes cleanly with the containment verifier (below): the farewell is authoritative for the paraphrasable end-state and simultaneously banned as a verbatim voice or atmosphere source — two different channels, and the prompt holds both rules at once.

The recap is paragraphed, and the paragraphs are structural only — a session with three distinct movements compressed into one dense block reads as a wall, so the prompt now asks for one to four short paragraphs broken where the session broke: a discovery, a confrontation, a journey, a retreat. A session that was one continuous scene stays one paragraph. Same words, same register — only the breaks are new, and they pass through as blank lines inside the same single summary string, so the wire contract and the recap route are unchanged. The prompt also pulls in shared/prose-register for summary and emergingThreads, and explicitly exempts the handoff's voice and atmosphere fields: those are quoted verbatim from the transcript, and restyling a quote would destroy the thing that makes it useful.
Verbatim NPC voice is the point of the handoff — the recurring failure across sessions is an NPC whose voice resets: the smuggler who was wry and conspiratorial by the end of session 3 greets the party in session 4 with a generic "coin first, stories after." The handoff carries a few of each major NPC's actual late-session lines, quoted exactly, and the prep engine concatenates them into the next ft_context verbatim (never paraphrased). The array length is bounded (it's a static budget the FT carries every turn), but the individual strings carry no length cap — a real line must survive at its real length.

The containment verifier

Between the Opus call and the write sits a pure mechanical gate, session/analysis/containment.ts. It drops any handoff voice excerpt or location atmosphere snippet that is not a verbatim substring of a non-correction, non-farewell transcript row. Normalization is forgiving on whitespace and case (JSON re-emission drifts those) but not on meaning: a semantic, non-substring difference is dropped.

The containment verifier is an enforced-ignorance boundary, not a quality filter — a verbatim excerpt that the next session's ft_context will carry must never be sourced from a correction turn (a MYT-73 retcon line points at the buried secret it spent an Opus call to bury) or a farewell line (meta-closure, not characterization). The migration-028 trigger_kind column records each DM row's originating turn trigger, so the verifier can structurally exclude those rows from the source set. The [[DM CORRECTION:]] marker doesn't survive into persisted content and message_type is the row kind, not the trigger — so the trigger had to be recorded explicitly. A drop is logged by count only, never the dropped prose, so the alert surface can't echo the secret the verifier exists to gate.

The verified handoff and the recap then go through repo.sessions.writeAnalysis, a conditional write gated on summary IS NULL — the same idempotency-mutex shape as the reconcile commit. A retry or a concurrent execution that finds summary already set no-ops. The worker logs structural counts only (drop counts, NPC and location counts, the write rowCount), never summary, handoff, or excerpt content — the analysis reasons over secrets, so the log surface is the leak vector, and it carries none.

How prep consumes the handoff

The handoff is written for one reader: the next session's prep. When prep runs, it reads the campaign's prior ended sessions (newest-first, capped) via getPriorContextForPrep and splits them two ways. The summary strings become a chronological recap fed to the prep prompt, and the latest session's handoff renders a "Where We Left Off" anchor — party positions, time of day, unresolved threads, returning-NPC dispositions — so the prep opens on where the table actually is: since myth-8mom0, where the farewell left it, not a mid-session snapshot. That part is a paraphrasable prompt input.

Verbatim voice is concatenated onto ft_context, not run through the prep LLM — the disposition lines (state) are fine to paraphrase, so they go into the prompt. But the whole value of the verbatim voice lines is that they're exact; routing them through the prep LLM would let it reword them, defeating the cross-session consistency they exist for. So the prep processor builds a fixed "Returning characters and places" section from the handoff's voice and atmosphere excerpts and appends it to ft_context deterministically after generation. All parsing of the prior rows is tolerant (a malformed or legacy row degrades to omission, never a throw mid-prep) — the analysis is transcript-derived narrative state, independent of canon commit, so it is not reconcile-gated.

The append-only fact log

Migration 027 makes facts append-only for corrections. A correction never edits a row's content — it appends a new fact and points the old fact's superseded_by at it (with a superseded_at stamp). Live canon is superseded_by IS NULL; the full history is the supersede chain. The same migration adds sessions.reconciled_at — the completion marker and the idempotency gate. A partial index idx_facts_live_by_entity on (entity_id, access_level) WHERE superseded_by IS NULL matches the live-canon snapshot predicate.

ON DELETE SET NULL on the supersede FK is deliberate — the FK from a live fact to the superseded fact it replaced is declared ON DELETE SET NULL, not the bare default. entities → facts is ON DELETE CASCADE, so a world-regen wipe that deletes an entity whose superseded fact is pointed-to by a live fact would otherwise FK-abort the cascade. Setting the pointer to NULL on delete lets the wipe proceed.

Reconcile-committed facts carry three code-stamped columns: source='session' (the provenance marker distinguishing session-improvised canon from prep canon), narrative_status='delivered' (these facts were shown to players this session), and a topic the model emits per fact (it drives later grouping and retrieval, so a constant stamp would degrade it). A session-committed secret fact is indistinguishable at read time from a prep secret fact and inherits the same Slow-Thinker over-pull gate.

The live-only read filter

An append-only log means every canon-fact reader must default to live-only, or a corrected-away fact would surface beside its correction. The read defaults to superseded_by IS NULL through a binder flag (so a future history/audit reader can opt into the full chain — a durable shape, not a hardcoded WHERE per call site). The reader set that now filters live-only: the world-retrieval searchFacts (the Fast Thinker's search_lore arm), the member-facing world-snapshot view, the prep/coherence composite read, the embed-write backfill (skip superseded rows — don't re-embed dead canon), and the reconciler's own candidate-fact read (else a superseded secret could re-enter a later reconcile and un-retcon itself).

The access-tier promotion state machine

Promotion only makes sense once you read access_level as a one-way state machine, not a per-player visibility flag. Every fact and entity sits at one of three tiers, and play moves them in one direction — toward public:

  • known — public baseline the world ships with, or something the party has learned through play. This is what the wiki shows. Available from session 1 so players can browse the world they're dropped into.
  • discoverable — unknown to the players but easy to learn (a skill check, a conversation). Not behind enforced ignorance: the Fast Thinker may freely know and use a discoverable fact before it is formally revealed. On discovery (a working-set item matches it this session) → promoted to known.
  • secret — core plot material, the enforced-ignorance line. The FT never sees it unsanctioned. Revealed only when the Slow Thinker sanctions it — the ST-vet relays it, or the ST director stages it. On reveal → promoted to known.
The promotion direction is what keeps secret-promotion safe — a secret fact can only be promoted when a working-set item matches it, and a secret reaches the working set only when the ST already sanctioned surfacing it: a tier:'secret' working-set item comes solely from the ST-vet's relay (st_injection source), and a director-staged reveal lands as a known ft_delta the FT delivered. The FT cannot author a secret-tier working-set item itself. So the ST sanction is the floor that populates the working set, the working-set match is the gate that promotes, and the wiki read is the final fence (known-only, no bypass, member-scoped). The reconciler never free-scans the secret candidates looking for things to promote.

The player campaign wiki

Promotion exists to feed one reader: the campaign wiki. This is the players' view of the world they are playing — a member-readable, known-tier read that starts at the world's baseline public knowledge and grows every time a session promotes something. The route is GET /api/campaigns/:campaignId/wiki in routes/campaigns.ts; repo/campaign-wiki-view.ts composes the body.

The composition is deliberately narrow — a sibling of the fuller world-snapshot, not a re-pointing of it. It carries: a narrow world summary (worlds.getWikiSummary — name, tone, themes, era, plus the known-filtered vocabulary registry); the known entities (name + type only); their live known facts; and the known-tier relationships among them. It carries no prose kernels and no stat blocks.

Relationships are tier-filtered by their own access_level, not their endpoints (MYT-89) — relationships.listAmong is passed ['known'] here, and the filter reads the relationship's tier, not its endpoints'. Once relationships became player-facing, the both-endpoints-known predicate was no longer enough: a secret connection between two known entities would have surfaced. The relationship's own tier is what closes that deterministic leak — see relationship tiering for where the tier is assigned.
A purpose-built projection, not the snapshot's composition — the obvious shortcut is to point the player wiki at the existing worldSnapshotView. Both reads now share the same plot-safe world summary (each re-projects to WikiWorldSummary, so the owner's raw freeform concept seed is on neither member-readable wire since myth-0xwos), but the snapshot still attaches per-entity prose kernels and stat blocks — FT-facing generation artifacts that are not tier-gated, a play-promoted secret entity's kernel being its full characterization blob. So the wiki gets its own narrower composition — the getWikiSummary summary plus known entities, facts, and relationships, with no kernels and no stat blocks. The two reads are distinct surfaces for distinct moments in a campaign's life; the split is composition, not audience.
Member-readable, no bypass, per-user rate-limited — the snapshot is requireCampaignMember(repo, 'owner'); the wiki is requireCampaignMember(repo) — any party member. Its dev-mode tier bypass is hardcoded off: there is no knob to widen it past known, so the structural guarantee is the narrow projection itself, not a flag a future caller could flip. Readiness gates on stage 4 (entity_relationships) — 409 wiki_not_ready before it, 404 campaign_not_found on a null world id. The owner snapshot's own gate moved one stage later to world_introduction (myth-zaqxh — its reveal now waits for the intro page), so the member wiki, which has no intro to wait for, becomes readable a stage before the owner snapshot. It is rate-limited per-user (60/min, the member-poll precedent), not per-IP like the owner snapshot — a whole party fanning the same read shouldn't share one IP bucket. Because it is a player route with no dev-tool panel, it sits in the dev-tool contract's EXEMPT_ROUTES.

Enforced ignorance

The reconciler reasons over secret-tier working-set items and secret-cleared candidate facts, so the validated plan legitimately contains secret prose — a secret fact's content is the secret, and this call is allowed to write it into canon. The boundary here is therefore not "no player-facing surface." There are three real surfaces — the log/alert path, the tier/attribution guard, and now the wiki read — and all three are mechanical, not prompt-trusted.

The log/alert surface is the actual leak vector. The validated plan object is never logged or broadcast (the session_end frame is structural; the plan is not in it), and every alert payload — a validator reject, a terminal failure — carries structural facts only: op counts, a reject reason code, ids, sessionId, never content prose or the working-set snapshot. A reject reason is a structural code (tier_downgrade, dangling_promotion, …), never a string that echoes a fact. The entity-op heal warn (reconcile_entity_ops_healed) carries rebound and demoted entity names and ids only — an entity's name is the least-secret thing about it; its facts are the secret — never working-set or fact prose. The success and reject logs carry promotions.length as a count — never the promoted fact ids or content.

The wiki read is the third surface, and it is known-only by construction. A player cannot receive a discoverable or secret fact, the owner's raw concept seed, or a play-promoted entity's prose kernel — the projection structurally cannot carry them and the bypass is hardcoded off. Secret promotion is upstream-gated by the ST sanction that is the only way a secret reaches the working set at all, so the only thing the wiki ever shows from a former secret is a fact the Slow Thinker already chose to reveal at the table.

Tier and attribution are preserved on commit, by mechanical guard. Tier and attribution preservation is policy enforcement — the explicit ZFC exception — so the validator enforces it structurally, not by trusting the prompt:

  • Tier floor. Each plan fact carries the originating working-set item's subject name (the key the Scribe stamped, not the model-rephrasable entity name). The validator joins each fact to its item by subject name and rejects the plan if a fact's access level is weaker than its item's tier. Per-fact, not per-entity (entity granularity would wrongly bury a secret entity's legitimately-known facts); reject-not-edit (a downgrade is a model bug worth surfacing).
  • Attribution arm. Each plan fact carries claimedBy — the NPC name for an attributed claim, else null. The validator rejects a fact whose working-set item is provenance: attributed but whose claimedBy is null (the model dropped the attribution → would canonize a hearsay claim as objective truth). claimedBy is the structural signal the validator checks; the prompt also bakes the attribution into the fact content, but the structural arm is what's tested deterministically.
Why the structural claimedBy, not just prose attribution — an attributed working-set item ("Marsh the Fishmonger claims the harbor answers to smugglers") must canonize as a claim, never as ground truth, so an NPC's lie or partial knowledge can't silently become canon. Baking the attribution into the prose alone (D6) is invisible to a test; the claimedBy field is the structural signal the validator checks and the leak matrix exercises with a mocked model — restoring the structural-and-tested posture the Scribe established.

Operating this piece

Recover a stuck reconcile_pending campaign

  1. Symptom: POST /api/sessions/:campaignId/start returns 409 reconcile_pending and stays that way. The campaign's most-recent session is ended_at set, reconciled_at NULL — the reconcile never completed.
  2. Confirm the worker exhausted its retries: look for a reconcile_plan_rejected or a transient-failure log line for that sessionId in the worker service logs (structural fields only — no plan content). A reconcile_entity_ops_healed warn is a benign heal (rebinds/demotions), not a failure — since myth-ejsp5 entity ops cannot reject a plan, so a persistent rejection points at a fact, relationship, or policy arm.
  3. The working set is not lost — it survives on the durable 5-minute Postgres checkpoint. The correct recovery is to re-drive the reconcile job for that session (the conditional gate makes a re-run idempotent); a persistent rejection means a real plan bug to fix before re-driving.

End a session by hand (dev)

  1. With a live session open over the WebSocket, send an end_session frame. The server claims the ending flag and enqueues a player-less farewell turn.
  2. Watch the session channel for the farewell turn's prose, then the structural session_end frame (in that order — the live send-off precedes the close).
  3. Watch the worker logs for session_finalized, then reconcile_committed and analysis_written (all carry counts only — a nonzero promotions count means facts were promoted this session). Then inspect sessions.reconciled_at (now set), sessions.summary / sessions.handoff (now populated), and the new facts rows (source='session') for the world.

Confirm a promotion reached the campaign wiki

  1. Before the session, note a discoverable or (ST-revealed) secret fact: SELECT id, access_level FROM facts WHERE entity_id = $1 AND superseded_by IS NULL. It is absent from GET /api/campaigns/:campaignId/wiki (the read is known-only).
  2. Run a session that surfaces that fact, then end it (above). The reconcile commit's promotions log count should be ≥ 1.
  3. Re-query: the fact (and its owning entity) now read back access_level='known', and the same GET …/wiki call now returns the entity and the fact. A fact the party did not surface stays at its old tier and absent — that is the over-promotion guard working, not a bug.

Re-run a stuck post-session analysis

  1. Symptom: a session has ended_at set but summary stays NULL. The analysis job exhausted its retries (a persistently-failing Opus call) or never landed.
  2. Confirm in the worker logs for that sessionId: a transient-failure line, or an analysis_excerpts_dropped_not_in_transcript warn (count only — expected, not a failure). The session's canon is unaffected — analysis and reconcile are independent jobs.
  3. Re-enqueue the analysis job for the session. The summary IS NULL gate makes a re-run idempotent; a persistent failure means a real prompt/schema bug to fix before re-driving. Until summary lands, the next session's prep simply opens without a "Where We Left Off" anchor — it never blocks.

Integration points

This page picks up where the Scribe leaves off: the Scribe builds the tier- and provenance-annotated working set during the session; reconciliation commits it at the end. The end lifecycle lives at the session transport seam (the end_session / session_end frames, the inbound ending-gate, the two start-interlock 409s) and is also fired by the turn worker's auto-end; the farewell turn itself is rendered by that turn worker, and the QueueEvents backstop is its terminal-stall net. The reconcile and analysis workers are the eighth and ninth BullMQ workers. Reconcile retrieves candidates through the world-store retrieval resolvers and writes through the repository layer's facts, entities, relationships, and entityHierarchy namespaces; analysis writes sessions.summary / sessions.handoff via writeAnalysis. The append-only superseded_by / superseded_at columns, sessions.reconciled_at, and the migration-028 session_messages.trigger_kind column are on the schema. The reconcile commit's promoteToKnown tier flips and the player wiki's campaignWikiView + getWikiSummary composition also live in the repository layer; the wiki read is a deliberately narrow sibling of world-gen's fuller world-snapshot (which shares the known / discoverable / secret tier model). Downstream, the next session's prep reads the handoff and the prior summaries; secret tiers stay behind the Slow-Thinker gate, whose sanction is also what lets a secret be promoted into the wiki at all. The farewell carry runs one direction only — into canon (reconcile) and the next session's prep (the analysis handoff), never back into the Fast Thinker's own in-session window; the complementary context filter that keeps farewell prose out of the FT's window lives on the Fast Thinker page.
