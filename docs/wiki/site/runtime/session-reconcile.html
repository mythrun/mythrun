End-of-session reconciliation

What happens when a session ends. First the table gets a live send-off — a player-less farewell turn the Fast Thinker renders in its own voice. Then two off-the-hot-path jobs fire. Reconcile folds the in-session working set — every fact the Fast Thinker improvised this session, tier- and provenance-annotated by the Scribe — into durable canon: entities, append-only facts, relationship edges, and embeddings, via one holistic Opus match-vs-mint pass. Post-session analysis reads the transcript and writes the next session's narrative state — a player-facing recap plus a secret-aware handoff that primes the prep engine (including verbatim NPC voice lines that keep characterization consistent across sessions).

How it fits together

Through a live session the Scribe accumulates the session's improvisation into a Redis working set — an append-only list of facts the Fast Thinker invented, each stamped with its tier (known / discoverable / secret) and provenance (objective ground truth, or an NPC's attributed claim). That working set is ephemeral: it lives in Redis (ridden onto the durable 5-minute Postgres checkpoint) and it never touches the world store while the session is live. Reconciliation is the closing step that makes the session's discoveries permanent — it turns the working set into canon the next session, the next prep, and the wiki can read.

The pieces, layered across MYT-74a and MYT-74b: a session-end lifecycle that detects a session is over, gives the table a live farewell, and fences off the still-draining turn loop; a reconcile pass that folds the working set into canon off the hot path (MYT-74a); and a post-session analysis pass that reads the transcript and writes the next session's narrative state — recap plus handoff (MYT-74b). The diagram traces all of it: the two end triggers beginning the end at the left, the farewell turn and the finalize that fires the two closeout jobs in the middle, and each worker's pipeline on the right.

Why a holistic Opus plan, not a per-subject loop — the obvious shape is "for each working-set subject, decide match-or-mint and append its facts." But two working-set items can name the same brand-new entity; a per-subject loop would mint it twice. One Opus call that sees the whole working set at once gives the best cross-subject coherence — it can collapse two mentions into one mint, resolve a contradiction against the live canon it was shown, and omit a restatement that already matches existing canon. This is also the Zero Framework Cognition line: the match/mint/contradiction judgment is the model's; the application code does mechanical candidate retrieval and deterministic commit, never a similarity-threshold auto-match (that would hardcode a judgment ZFC delegates to the model).

The session-end lifecycle

There was no session-end flow before MYT-74a. MYT-65 built suspend (all players disconnect, the session checkpoints but stays status='active'); the sessions.summary / handoff columns sat unpopulated. This piece builds the trigger and the orchestration shell so a session can structurally end and commit its canon.

Two triggers converge on the begin phase, endSession in session/session-end.ts:

  • Explicit — a player sends an end_session WebSocket frame (a bare summon, no payload, like the dm_invoke "@DM button"). The session transport route resolves the world id and runs the orchestration.
  • Budget auto-end — the token budget reaches 100%. The turn worker observes the crossing on its post-flush success phase (the same place the ST-evaluation floor is bumped) and fires the same begin flow. The Fast-Thinker context bound is the real session-length cap; when cumulative usage reaches it, the session has to end because the FT can hold no more transcript.

Begin: a farewell, not an inline finalize

MYT-74b split the end into a begin phase and a complete phase so the table gets a live send-off before the session is structurally over. endSession only begins it. It does four things and stops:

  1. Claim the flag. Set the once-only session:{cId}:ending flag (SET-NX). The loser of an explicit-frame-vs-auto-end race short-circuits here.
  2. Cancel the pending suspend. An uncancelled all-disconnected suspend would later re-checkpoint an ending session — a lost update keeping status='active', undoing the end. cancelSuspend is a no-op when nothing is pending.
  3. Read the watermark. Read the responded-seq watermark and thread it onto the farewell payload as maxConsumedSeq — a player-less turn must not advance past unresponded player seqs.
  4. Enqueue ONE farewell turn. A player-less trigger.kind: 'farewell' turn, jobId farewell-{sessionId}, carrying the resolved worldId so the finalize needs no campaign→world read of its own.
A SET-NX ending flag makes the two triggers idempotent — the explicit frame and the budget auto-end can race (a player taps end on the same turn that crosses 100%). endSession's first act is to claim the flag; the loser short-circuits there. So exactly one farewell turn is enqueued no matter how many triggers fire — and the farewell-{sessionId} jobId is a broker-level dedup backstop beyond the flag.

The farewell turn is rendered by the turn worker like any other turn, but player-less. Its direction (a fixed "bring the scene to a natural close" cue) rides the single-bracket [DM direction:] silent-consume seam — the same seam the MYT-73 correction turn established — so the Fast Thinker writes the send-off in its own voice rather than quoting a marker. It joins the correction turn under a shared isPlayerless predicate in the turn worker: neither advances the watermark, enqueues the Scribe, nor runs the budget auto-end. The turn page covers the render seam and the gates.

Complete: the unconditional finalize

finalizeEndedSession is the complete phase, run from the farewell turn's finally after the render — so the table sees the DM's send-off, then the session_end frame. finally always runs, so a thrown farewell render still finalizes: a session always ends. It does three things:

  1. Flip, conditionally. markEnded sets status='ended', ended_at=now() only when the row isn't already ended, returning the rowCount (reconciled_at and summary both stay NULL — those are the reconcile and analysis completion markers).
  2. Enqueue the two closeout jobs. One reconcile job (reconcile-{sessionId}) and one analysis job (analysis-{sessionId}), both per-session jobIds so a re-enqueue collapses to the existing broker job.
  3. Broadcast, once. Only the finalize that won the flip (rowCount 1) broadcasts the structural session_end frame; a later finalize (rowCount 0) skips it.
The conditional flip is what makes session_end fire exactly once — the finalize is callable from two places: the farewell turn's finally (the normal path) and a QueueEvents backstop (the terminal-stall path, below). Both call the same idempotent function. The reconcile and analysis enqueues collapse on their jobIds, but the broadcast would double-fire without a gate — so markEnded returns the rowCount and only the winner broadcasts. A second finalize is otherwise harmless.
Why a farewell turn, not an inline flip-and-broadcast — MYT-74a's endSession flipped the row and broadcast session_end inline. That ended the session abruptly: the client saw "session over" with no narrative close. Routing the end through a real (player-less) turn lets the Fast Thinker render a send-off first, and the finalize rides the turn's existing lock + finally — so the turn loop is already quiesced when the row flips, no separate lock-fence needed. The reconcile worker still re-acquires the per-session lock itself before reading the working set, so the fence is enforced there regardless.
A QueueEvents backstop covers the terminal stall — the in-worker finally covers a clean render and a thrown render, but not a worker that crashes mid-flight: BullMQ retries the job maxStalledCount times, then fails it inside a Lua script that emits only a broker-side event — never the per-worker finally. The session-turn QueueEvents subscriber listens for that broker failed event and, for a farewell turn, runs finalizeEndedSession itself. Idempotent, so a double-fire with the in-worker path is safe. Without it a crashed farewell would leave a session that never finalizes — the table waiting forever.

The cross-session start interlock

The working set is keyed by campaign (session:{cId}:workingset — one live session per campaign), and the idx_sessions_one_active index frees the active slot the instant status flips to ended. Without a guard, a new session could start on the same campaign, append onto the same Redis list, and have the prior session's still-pending reconcile load the polluted list and clear() it — silently destroying the new session's working set on a perfectly normal flow (budget auto-end of session 1 → start session 2).

The fix is a two-part interlock at POST /api/sessions/:campaignId/start. It returns 409 reconcile_pending while the campaign's most-recent session is ended_at IS NOT NULL AND reconciled_at IS NULL — no new session starts until the prior one's canon is committed and its working set cleared. And it returns 409 session_ending while the ending flag is set.

Why session_ending needs its own guard — MYT-74b moved the status flip to the finalize, which runs after the farewell renders. During that render the row is still status='active' with ended_at NULL, so the reconcile_pending interlock (which reads ended_at) can't see the end yet. The ending flag is set at the very start of the begin phase, so the second guard fences the whole window from begin-of-end through finalize. Reconcile is fast (seconds to tens of seconds), so the combined block is brief in the happy path.
The tri-state is the reader contract — ended_at set with reconciled_at NULL means "ended, reconcile pending or failed." Consumers must not treat such a session's canon as complete. reconciled_at set means canon is committed. A terminal reconcile failure therefore surfaces as a stuck campaign plus an alarm — observable-stuck, not silent canon loss. That is the correct failure mode for a canon write path: better to block the next session than to lose what happened in this one.

The reconcile pass

The worker body in session/session-reconcile.ts is ZFC-shaped: a deterministic retrieve, one LLM judgment, a deterministic commit. The world id is resolved once (session → campaign → world). The worker is not total — unlike the post-turn Scribe job, it throws on transient failure so BullMQ retries, and every retry is idempotent (the commit gate, below, keeps a re-run from double-writing).

1. Retrieve (deterministic)

Load the working set. For each distinct subject, call findSimilarEntities to pull the top-K canon entity candidates, then load those candidates' live facts (superseded_by IS NULL) so the reconciler sees current canon, never a fact a prior session already corrected away. findSimilarEntities throws on failure (it is on the canon write path — a swallowed embed blip would make the reconciler think no similar entity exists and mint a duplicate), so a retrieval failure propagates and the job retries. This fan-out — the per-subject query embeddings, batched through Voyage, and the candidate reads — is the dominant latency, not the single Opus call.

2. Reconcile (one holistic Opus call)

llm/session-reconciler.ts is one Opus call through the standard generateObject boundary. Its input is the full working set (each item's subject name, content, kind, tier, provenance, source, optional parent name), the retrieved candidates and their live facts, and the world tone. Its output is a structured plan: entity match/mint ops, fact appends (each optionally superseding a live fact), and relationship edges. The model owns every judgment — it decides match vs mint per subject, resolves contradictions by absorb (canonize the improvised version) or supersede (append the canonical version and point the old fact's superseded_by at it), bakes an NPC's attribution into an attributed claim's content, and omits any restatement that already matches live canon so a stable entity doesn't accrete a duplicate fact every session.

The output ceiling is pinned, and redactRawText is on — the budget auto-end fires on the largest sessions, so the call sizes its maxOutputTokens for the worst case (an unpinned cap risks mid-JSON truncation → a terminal fail). And because the reconciler reasons over secret-tier items, a malformed response must never spill a secret into the repair log or the rethrown error's diagnostic — redactRawText: true nulls the raw snippet, exactly the posture the secret-tripwire and retcon-author calls use. A sonnet repair strategy is acceptable only because the validator (next) re-checks every id post-repair — repair fixes JSON shape, never the match/mint judgment.

3. Validate (deterministic — structural + policy)

session/reconcile/validate.ts is pure (no I/O) and security-critical. It builds the load-bearing subject-name → entity-id map (matched canon ids plus minted ids) and resolves every fact and relationship op through it. The arms: every match points at a live candidate; every minted type is legal (npc | location | faction | item); every fact subject and every relationship endpoint resolves to an entity op (else it is a dangling ref → reject); a supersede target is a live fact. There is no semantic re-judgment here — the validator enforces structure and policy, not meaning.

Reject the plan, don't silently fix it — a dangling reference or a tier downgrade is a model bug worth surfacing. The validator returns the first failure as a structural reason code and the worker throws, so the non-deterministic Opus call is retried (the attempts cap bounds a persistently-failing one). A partial commit never happens — validation runs entirely before the transaction opens.

4. Commit (deterministic, transactional)

session/reconcile/commit.ts folds the validated plan into canon in one transaction. It mints entities (created_in='session:<id>', marked touched-by-play), appends facts, sets superseded_by / superseded_at pointers on corrected facts (and NULLs the superseded fact's embedding so it leaves the HNSW index rather than burning recall budget), inserts relationship edges and any sub-faction hierarchy edges, and writes the new facts' embeddings. The Voyage re-embed call runs before the transaction opens — slow I/O never sits inside a BEGIN — and the resulting vectors are written inside the transaction, so embeddings are atomic with the facts and can't desync across a retry. On a clean commit the worker clears the working set.

The conditional reconciled_at update is the idempotency mutex — the commit's last in-transaction statement is UPDATE sessions SET reconciled_at = now() WHERE id = $1 AND reconciled_at IS NULL. Zero rows updated means another execution already reconciled this session → roll the whole transaction back, so no duplicate canon lands. A plain unconditional write would not be a guard: two executions that both read NULL on entry (the candidate retrieval and the seconds-long Opus call sit between the entry check and BEGIN) would both commit a full duplicate of the working set. The conditional WHERE serializes them; the on-entry check is just a cheap early-out.

Post-session analysis and the handoff

Reconcile commits facts. The second closeout job, in session/post-session-analysis.ts, writes narrative state — what the session was about and where it left things. It is the same ZFC shape as reconcile: a deterministic read, one Opus judgment, a deterministic verify-and-write. It is not total — it throws on transient failure so BullMQ retries, gated idempotent on summary IS NULL. It runs on its own worker (concurrency 1, 180s lock) and takes no embedder — analysis doesn't embed.

The job reads four durable inputs, all safe to read after the WebSocket closes: the bounded transcript tail (the latest 160 rows — the late tail is where evolved relationships and voice live), the prep sd_playbook, the Slow-Thinker running summary from Redis, and the PC roster. llm/post-session-analysis.ts feeds them to one Opus call that emits a { summary, emergingThreads, handoff } object.

  • summary / emergingThreads — the player-facing recap. Secret-free by construction: the prompt's hard rule is that these describe only what the players witnessed at the table. They land in sessions.summary as a JSON wrapper.
  • handoff — the SessionHandoff, which may be secret-aware (it feeds the next session's prep pipeline, not any player surface). It carries the party's end-of-session positions and conditions, the in-world time, the unresolved threads (most-urgent first), per-NPC state (a paraphrasable disposition) and voice (verbatim late-session lines), and per-location atmosphere. It lands in sessions.handoff.
Verbatim NPC voice is the point of the handoff — the recurring failure across sessions is an NPC whose voice resets: the smuggler who was wry and conspiratorial by the end of session 3 greets the party in session 4 with a generic "coin first, stories after." The handoff carries a few of each major NPC's actual late-session lines, quoted exactly, and the prep engine concatenates them into the next ft_context verbatim (never paraphrased). The array length is bounded (it's a static budget the FT carries every turn), but the individual strings carry no length cap — a real line must survive at its real length.

The containment verifier

Between the Opus call and the write sits a pure mechanical gate, session/analysis/containment.ts. It drops any handoff voice excerpt or location atmosphere snippet that is not a verbatim substring of a non-correction, non-farewell transcript row. Normalization is forgiving on whitespace and case (JSON re-emission drifts those) but not on meaning: a semantic, non-substring difference is dropped.

The containment verifier is an enforced-ignorance boundary, not a quality filter — a verbatim excerpt that the next session's ft_context will carry must never be sourced from a correction turn (a MYT-73 retcon line points at the buried secret it spent an Opus call to bury) or a farewell line (meta-closure, not characterization). The migration-028 trigger_kind column records each DM row's originating turn trigger, so the verifier can structurally exclude those rows from the source set. The [[DM CORRECTION:]] marker doesn't survive into persisted content and message_type is the row kind, not the trigger — so the trigger had to be recorded explicitly. A drop is logged by count only, never the dropped prose, so the alert surface can't echo the secret the verifier exists to gate.

The verified handoff and the recap then go through repo.sessions.writeAnalysis, a conditional write gated on summary IS NULL — the same idempotency-mutex shape as the reconcile commit. A retry or a concurrent execution that finds summary already set no-ops. The worker logs structural counts only (drop counts, NPC and location counts, the write rowCount), never summary, handoff, or excerpt content — the analysis reasons over secrets, so the log surface is the leak vector, and it carries none.

How prep consumes the handoff

The handoff is written for one reader: the next session's prep. When prep runs, it reads the campaign's prior ended sessions (newest-first, capped) via getPriorContextForPrep and splits them two ways. The summary strings become a chronological recap fed to the prep prompt, and the latest session's handoff renders a "Where We Left Off" anchor — party positions, time of day, unresolved threads, returning-NPC dispositions — so the prep opens on where the table actually is. That part is a paraphrasable prompt input.

Verbatim voice is concatenated onto ft_context, not run through the prep LLM — the disposition lines (state) are fine to paraphrase, so they go into the prompt. But the whole value of the verbatim voice lines is that they're exact; routing them through the prep LLM would let it reword them, defeating the cross-session consistency they exist for. So the prep processor builds a fixed "Returning characters and places" section from the handoff's voice and atmosphere excerpts and appends it to ft_context deterministically after generation. All parsing of the prior rows is tolerant (a malformed or legacy row degrades to omission, never a throw mid-prep) — the analysis is transcript-derived narrative state, independent of canon commit, so it is not reconcile-gated.

The append-only fact log

Migration 027 makes facts append-only for corrections. A correction never edits a row's content — it appends a new fact and points the old fact's superseded_by at it (with a superseded_at stamp). Live canon is superseded_by IS NULL; the full history is the supersede chain. The same migration adds sessions.reconciled_at — the completion marker and the idempotency gate. A partial index idx_facts_live_by_entity on (entity_id, access_level) WHERE superseded_by IS NULL matches the live-canon snapshot predicate.

ON DELETE SET NULL on the supersede FK is deliberate — the FK from a live fact to the superseded fact it replaced is declared ON DELETE SET NULL, not the bare default. entities → facts is ON DELETE CASCADE, so a world-regen wipe that deletes an entity whose superseded fact is pointed-to by a live fact would otherwise FK-abort the cascade. Setting the pointer to NULL on delete lets the wipe proceed.

Reconcile-committed facts carry three code-stamped columns: source='session' (the provenance marker distinguishing session-improvised canon from prep canon), narrative_status='delivered' (these facts were shown to players this session), and a topic the model emits per fact (it drives later grouping and retrieval, so a constant stamp would degrade it). A session-committed secret fact is indistinguishable at read time from a prep secret fact and inherits the same Slow-Thinker over-pull gate.

The live-only read filter

An append-only log means every canon-fact reader must default to live-only, or a corrected-away fact would surface beside its correction. The read defaults to superseded_by IS NULL through a binder flag (so a future history/audit reader can opt into the full chain — a durable shape, not a hardcoded WHERE per call site). The reader set that now filters live-only: the world-retrieval searchFacts (the Fast Thinker's search_lore arm), the member-facing world-snapshot view, the prep/coherence composite read, the embed-write backfill (skip superseded rows — don't re-embed dead canon), and the reconciler's own candidate-fact read (else a superseded secret could re-enter a later reconcile and un-retcon itself).

Enforced ignorance

The reconciler reasons over secret-tier working-set items and secret-cleared candidate facts, so the validated plan legitimately contains secret prose — a secret fact's content is the secret, and this call is allowed to write it into canon. The boundary here is therefore not "no player-facing surface." There are two real surfaces, and both are mechanical, not prompt-trusted.

The log/alert surface is the actual leak vector. The validated plan object is never logged or broadcast (the session_end frame is structural; the plan is not in it), and every alert payload — a validator reject, a terminal failure — carries structural facts only: op counts, a reject reason code, ids, sessionId, never content prose or the working-set snapshot. A reject reason is a structural code (dangling_match, tier_downgrade, …), never a string that echoes a fact.

Tier and attribution are preserved on commit, by mechanical guard. Tier and attribution preservation is policy enforcement — the explicit ZFC exception — so the validator enforces it structurally, not by trusting the prompt:

  • Tier floor. Each plan fact carries the originating working-set item's subject name (the key the Scribe stamped, not the model-rephrasable entity name). The validator joins each fact to its item by subject name and rejects the plan if a fact's access level is weaker than its item's tier. Per-fact, not per-entity (entity granularity would wrongly bury a secret entity's legitimately-known facts); reject-not-edit (a downgrade is a model bug worth surfacing).
  • Attribution arm. Each plan fact carries claimedBy — the NPC name for an attributed claim, else null. The validator rejects a fact whose working-set item is provenance: attributed but whose claimedBy is null (the model dropped the attribution → would canonize a hearsay claim as objective truth). claimedBy is the structural signal the validator checks; the prompt also bakes the attribution into the fact content, but the structural arm is what's tested deterministically.
Why the structural claimedBy, not just prose attribution — an attributed working-set item ("Marsh the Fishmonger claims the harbor answers to smugglers") must canonize as a claim, never as ground truth, so an NPC's lie or partial knowledge can't silently become canon. Baking the attribution into the prose alone (D6) is invisible to a test; the claimedBy field is the structural signal the validator checks and the leak matrix exercises with a mocked model — restoring the structural-and-tested posture the Scribe established.

Operating this piece

Recover a stuck reconcile_pending campaign

  1. Symptom: POST /api/sessions/:campaignId/start returns 409 reconcile_pending and stays that way. The campaign's most-recent session is ended_at set, reconciled_at NULL — the reconcile never completed.
  2. Confirm the worker exhausted its retries: look for a reconcile_plan_rejected or a transient-failure log line for that sessionId in the worker service logs (structural fields only — no plan content).
  3. The working set is not lost — it survives on the durable 5-minute Postgres checkpoint. The correct recovery is to re-drive the reconcile job for that session (the conditional gate makes a re-run idempotent); a persistent rejection means a real plan bug to fix before re-driving.

End a session by hand (dev)

  1. With a live session open over the WebSocket, send an end_session frame. The server claims the ending flag and enqueues a player-less farewell turn.
  2. Watch the session channel for the farewell turn's prose, then the structural session_end frame (in that order — the live send-off precedes the close).
  3. Watch the worker logs for session_finalized, then reconcile_committed and analysis_written (all carry counts only). Then inspect sessions.reconciled_at (now set), sessions.summary / sessions.handoff (now populated), and the new facts rows (source='session') for the world.

Re-run a stuck post-session analysis

  1. Symptom: a session has ended_at set but summary stays NULL. The analysis job exhausted its retries (a persistently-failing Opus call) or never landed.
  2. Confirm in the worker logs for that sessionId: a transient-failure line, or an analysis_excerpts_dropped_not_in_transcript warn (count only — expected, not a failure). The session's canon is unaffected — analysis and reconcile are independent jobs.
  3. Re-enqueue the analysis job for the session. The summary IS NULL gate makes a re-run idempotent; a persistent failure means a real prompt/schema bug to fix before re-driving. Until summary lands, the next session's prep simply opens without a "Where We Left Off" anchor — it never blocks.

Integration points

This page picks up where the Scribe leaves off: the Scribe builds the tier- and provenance-annotated working set during the session; reconciliation commits it at the end. The end lifecycle lives at the session transport seam (the end_session / session_end frames, the inbound ending-gate, the two start-interlock 409s) and is also fired by the turn worker's budget auto-end; the farewell turn itself is rendered by that turn worker, and the QueueEvents backstop is its terminal-stall net. The reconcile and analysis workers are the eighth and ninth BullMQ workers. Reconcile retrieves candidates through the world-store retrieval resolvers and writes through the repository layer's facts, entities, relationships, and entityHierarchy namespaces; analysis writes sessions.summary / sessions.handoff via writeAnalysis. The append-only superseded_by / superseded_at columns, sessions.reconciled_at, and the migration-028 session_messages.trigger_kind column are on the schema. Downstream, the next session's prep reads the handoff and the prior summaries; secret tiers stay behind the Slow-Thinker gate.
