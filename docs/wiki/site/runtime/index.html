Backend

The Node.js server the cognitive tiers will live in. A pnpm workspace, a Fastify app with a dependency-injected data layer, a retry-then-fail-loud boot gate gated behind BOOT_GATE_ENABLED, and a local docker-compose stack (Postgres + two Redis instances) the dev loop probes on start.

How it fits together

The repository is a pnpm monorepo. The root package.json pins pnpm@10.30.3 via packageManager and node >= 24 via engines; pnpm-workspace.yaml declares two workspace packages today — backend/ and docs/wiki/ — and the root exposes the single-word verbs (pnpm test, pnpm typecheck, pnpm lint, pnpm build) that fan out across every workspace via pnpm -r. A second cluster of root scripts (pnpm db:up, pnpm db:down, pnpm db:reset) wraps the docker-compose local data stack.

Monorepo from day one, not a polyrepo — the backend, the wiki, and every future piece (prep worker, frontend, Terraform-companion tools) share a lockfile, a TypeScript version, and a single CI run. A second repo would double tooling for no real isolation: all of these deploy together.

The backend/ workspace is @mythrun/backend. Production dependencies are fastify, pg, and ioredis; dev dependencies are tsx, typescript, and vitest. The source tree is shallow but no longer flat: app.ts / server.ts / app-deps.ts at the root, with one-file subdirectories for boot/, config/, db/, and redis/. Each subdirectory has a colocated __tests__/.

The app factory and the dependency-injection shape

app.ts exports buildApp(deps: AppDeps) — a pure factory that returns a Fastify instance with GET /health registered — and createShutdown(app, clients), a pure function that returns a signal handler. AppDeps lives in app-deps.ts and declares the injection shape: { pg: Pool, redisRealtime: Redis, redisBatch: Redis }. Nothing in app.ts has side effects on import — no listener, no signal hooks, no connection opens. The deps parameter is unused by the single /health route today; Backend Core's first plugin will add app.decorate('pg', deps.pg) and the matching declare module 'fastify' augmentation.

Factory-with-deps before any plugin needs them — establishing the AppDeps contract now means every subsequent plugin lands a decorator onto a shape that already exists in every build and test harness. The alternative — buildApp() no- arg today, refactor when schema lands — would churn every test in the Backend Core PR.

createShutdown produces a signal handler that drains in a fixed order: Fastify's app.close() first (stops accepting connections, waits for in-flight requests), then pg.end(), then redisRealtime.quit() and redisBatch.quit(). The handler yields once via setImmediate before closing so pino's async log queue can flush the "shutting down" line.

Drain order: HTTP → pg → redis — closing Fastify first guarantees no new query hits the pool while it's draining. pg.end() waits for in-flight queries to settle. Redis quit() (not disconnect()) flushes in-flight commands gracefully instead of ripping the socket; any commands already written to the wire complete.
SIGTERM handling matters on ECS — ECS sends SIGTERM when it deregisters a task for any reason (rolling deploy, service scale-down, capacity rebalance). Without a handler, Node exits on the default kernel disposition and in-flight requests and queries get truncated. The 120-second stopTimeout on the task definition gives LLM calls time to finish before ECS sends SIGKILL.

The boot gate and its opt-in flag

server.ts has two startup paths. BOOT_GATE_ENABLED=1 (or true) runs the full boot gate: load + validate env, open a pg Pool and two Redis clients, probe each sequentially with retry-backoff, then app.listen. Anything else — including the default when the var is unset — runs fallbackStart: no env validation, no client creation, stub deps passed to buildApp, listen immediately. The dev .env.development sets the flag to 1; the staging ECS task definition does not set it, so the deployed binary stays at /health-only with the full data-layer code path dormant.

Boot gate off by default in production — staging's RDS is bootstrapped with a placeholder password until Backend Core lands schema + migrations and bootstrap-databases.sh sets the real per-env password. A default-on boot gate would crash the ECS task on every deploy with password authentication failed and trip the deployment circuit breaker. Keeping the gate opt-in lets the data-layer code ship (exercised by tests and by pnpm dev) while production remains on the MYT-28 entrypoint until a single env-var flip enables it.

Inside the gate, signal handlers are installed before any resource creation — installSignalHandlers in boot/signal-handlers.ts attaches SIGINT/SIGTERM listeners to an AbortController. That signal is threaded through every waitFor probe, so a Ctrl-C during retry backoff aborts the sleep immediately instead of waiting out the current delay.

boot/wait-for.ts is the retry helper. It runs the probe once, then retries after [200, 500, 1000, 2000] ms — five total attempts, ~3.7-second budget — and rethrows a labeled error naming which service failed. Probes are sequential, not parallel: three local services starting under docker compose up -d --wait reach healthy at the same moment, so serial vs parallel produce identical wall time and the serial shape gives a clean "the Postgres probe failed" error instead of a collapsed-Promise.all mess.

Fail loud, don't retry forever — ioredis defaults to infinite retry and would keep a process alive until its operator noticed. A bounded retry budget plus process.exitCode = 1 plus a 5-second watchdog setTimeout().unref() means a broken boot becomes a crash-loop the container orchestrator can see and alert on.

If any probe exhausts its retries, the catch block runs closePartials (Promise.allSettled over whichever clients were created), logs the labeled error, sets process.exitCode = 1, and arms the watchdog. The watchdog force-exits after five seconds if any client's socket kept the event loop alive past cleanup; unref() ensures it doesn't block exit when cleanup succeeds.

The pg pool and its sslmode trick

db/postgres.ts exports createPgPool(url). Naively handing a postgresql://...?sslmode=require URL to node-postgres does not produce a working RDS connection: pg's URL parser sets ssl: true (which defaults to rejectUnauthorized: true) and then doesn't reliably honor an explicit ssl override passed alongside the URL. RDS presents a chain rooted in Amazon's RSA CA which Node's default trust store does not include, so the handshake fails with SELF_SIGNED_CERT_IN_CHAIN even though sslmode=require only asks for encryption, not chain validation.

Strip sslmode from the URL, set ssl ourselves — this is the only shape where one call site handles dev (no sslmode → no TLS), staging/prod sslmode=require (encryption-only, rejectUnauthorized: false), and the future verify-ca/verify-full modes (rejectUnauthorized: true plus a ca bundle, not yet enabled). Letting pg's URL parser pick wins no clarity and loses prod.

The redis client and its retry policy

redis/client.ts exports createRedisClient(url), constructing an ioredis Redis with lazyConnect: true, maxRetriesPerRequest: 1, retryStrategy: () => null, and enableOfflineQueue: false. A noop 'error' listener is attached so the process doesn't log "Unhandled error event" noise during closePartials if the client never successfully connected.

ioredis retries disabled; all retry policy in waitFor — ioredis's default is aggressive auto-connect plus infinite retry, which fights the boot gate's bounded retry loop (the client would keep trying to reconnect after closePartials and keep the event loop alive, blocking process exit). Disabling ioredis retry puts the whole retry policy in one place: wait-for.ts.

The env loader accepts two shapes

config/env.ts exports loadEnv() returning a frozen Env { databaseUrl, redisRealtimeUrl, redisBatchUrl, port }. Dev .env.development provides DATABASE_URL, REDIS_REALTIME_URL, and REDIS_BATCH_URL directly. Production's ECS task definition sets the component form instead — DB_HOST, DB_PORT, DB_USER, DB_NAME, DB_PASSWORD, REDIS_HOST, REDIS_PORT, REDIS_AUTH_TOKEN — and the loader constructs the URLs from those components.

Two shapes because ECS already speaks component-form — the serving module's Terraform wires component env vars and secrets into the task definition well before the app existed to consume them. Rewriting the task definition to match a URL-form-only loader would touch a dozen Terraform resources; teaching the loader to accept either shape touches one file and leaves the deploy pipeline alone.

Component-form Postgres URLs always get ?sslmode=require appended (RDS enforces TLS and createPgPool knows how to handle it). Component-form Redis URLs use rediss:// with the auth token when one is set, plain redis:// otherwise. Production currently runs a single Redis cluster shared between realtime and batch; both URLs point at the same instance until the two-cluster split ships.

The local dev loop

The repo-root docker-compose.yml declares three services — postgres (Postgres 16 on 127.0.0.1:5432), redis-realtime (Redis 7.2 on 127.0.0.1:6379), and redis-batch (Redis 7.2 on 127.0.0.1:6380). Each has a healthcheck, 10 MB × 3-file log rotation, and binds only to the loopback interface. Postgres has a named pgdata volume; the Redis services run with --save "" --appendonly no so they're pure in-memory and docker compose down resets them cleanly. pnpm db:up wraps docker compose up -d --wait; pnpm db:reset wipes the Postgres volume.

Two Redis containers locally, even though prod is one — the production two-cluster split is a future ticket, but keeping the dev topology two-clustered exercises the code path that opens and probes two clients. A single-Redis local stack would let a bug in that code path hide until it shipped.
127.0.0.1 binding, not default 0.0.0.0 — Compose's default ports shape binds the container to every interface on the host. A laptop on an untrusted network would then expose a passwordless Postgres to anything on that network. Pinning to loopback is free and closes that hole.

backend/.env.development.example is committed as the template; backend/.env.development is gitignored. Values there match the compose stack's ports/credentials and include BOOT_GATE_ENABLED=1 and sentinel placeholders for external-service keys (REPLACE_ME_dev_only — obviously-fake strings that won't trip GitHub's secret-scanning if the file is accidentally committed). backend/package.json's dev script is tsx watch --env-file=.env.development src/server.ts, using Node's native --env-file flag rather than a dotenv dependency. docker-compose.override.yml is also gitignored; docker-compose.override.yml.example is the template, used when a developer needs to remap host ports (e.g. a Homebrew Postgres already bound to 5432).

TypeScript, lint, and the container image

The backend's tsconfig.json turns on every strictness knob that changes code — strict, noUncheckedIndexedAccess, exactOptionalPropertyTypes — with ES2023/NodeNext module resolution. tsconfig.build.json extends it and excludes __tests__/ so the built dist/ carries only runtime code. ESLint sits at the repo root and runs against every workspace: typescript-eslint strict + stylistic type-checked presets, a repo-specific ban on default exports, a 400-line module cap, a 50-line function cap, and any/non-null-assertion bans. eslint-config-prettier is applied last so Prettier owns formatting.

backend/Dockerfile is two stages on top of node:24-alpine. Both stage FROM lines resolve via a BASE_IMAGE_REGISTRY ARG: CI passes --build-arg BASE_IMAGE_REGISTRY=$REGISTRY (the account-specific ECR host) so the base image is pulled through the pull-through cache. When the ARG is unset (local builds), FROM resolves to ecr-public/docker/library/node:24-alpine, which does not exist on Docker Hub — local builds must pass the build-arg or keep a one-off backend/Dockerfile.local pointing at docker.io/library/node:24-alpine. The builder stage installs with pnpm install --frozen-lockfile --filter @mythrun/backend, builds, then runs pnpm --filter @mythrun/backend deploy --prod /app/deploy; the runtime stage copies that directory in, adds dumb-init, runs as a non-root mythrun user, and executes dumb-init node dist/server.js.

pnpm deploy instead of copying node_modules — a workspace's node_modules is a forest of symlinks pointing back into the pnpm store and sibling packages. Copying that across a stage gives you dangling symlinks. pnpm deploy materializes a proper single-package tree suitable for the runtime image. inject-workspace-packages=true in .npmrc is the supported pnpm-10 way to make deploy bundle workspace dependencies without the deprecated --legacy flag.
dumb-init + non-root mythrun user — Node doesn't reap zombies or forward signals correctly as PID 1 under Docker; dumb-init (~20 KB) fixes both and costs nothing at idle. The non-root user exists only to own /app and sidesteps container-scanner findings for running as root.

The image declares a container-level HEALTHCHECK that hits http://localhost:3000/health every 30 s through Node's own http module. Two .dockerignore files work together — the root one is authoritative for repo-root build contexts, backend/.dockerignore is a narrower duplicate kept alongside the Dockerfile as a readable hint.

Operating this piece

Run the backend locally

  1. From the repo root: pnpm install.
  2. Copy backend/.env.development.example to backend/.env.development. Replace the REPLACE_ME_dev_only sentinels with real keys only if you're exercising those integrations; the boot gate itself doesn't need them.
  3. pnpm db:up — brings up Postgres + both Redis containers and waits until every healthcheck passes.
  4. pnpm dev — starts the backend under tsx watch. Expect three ✓ ready lines (Postgres, Redis realtime, Redis batch) before app.listen logs. Reloads on source changes.
  5. curl localhost:3000/health should return {"status":"ok"}.

Reset the local data stack

  1. pnpm db:down stops the containers without touching the named pgdata volume; next pnpm db:up keeps existing Postgres data.
  2. pnpm db:reset wipes the Postgres volume and brings the stack back up clean. Redis is volumeless, so db:down/db:up already resets it.

Remap local ports when something on the host conflicts

  1. Copy docker-compose.override.yml.example to docker-compose.override.yml (gitignored). Compose merges it on top of docker-compose.yml automatically.
  2. Edit the host-side of each port mapping (e.g. 127.0.0.1:15432:5432). Leave the container-side alone.
  3. Update backend/.env.development so DATABASE_URL / REDIS_REALTIME_URL / REDIS_BATCH_URL point at the remapped host ports.

Diagnose a failed boot gate

  1. The error line names the probe that exhausted retries, e.g. waitFor(Redis (realtime)): exhausted 5 attempts; last error: ....
  2. For a Postgres failure, verify pnpm db:up succeeded and that DATABASE_URL in .env.development matches the compose credentials (defaults: user mythrun, password mythrun_dev, db mythrun).
  3. For a Redis failure, note that redis-cli ping inside the container does not exercise auth; a passing compose healthcheck with a failing app probe suggests the REDIS_*_URL is wrong or points at the other Redis instance.
  4. If the process hangs instead of exiting after the error, upgrade ioredis/pg or check whether a new Redis option is keeping a socket alive past quit(). The 5-second watchdog force-exits either way.

Run the full verification suite

  1. pnpm install && pnpm test && pnpm typecheck && pnpm lint — the "done when" of every implementation ticket. All four must exit 0.
  2. Each command fans out across every workspace via pnpm -r; a failure in any workspace fails the root command. Tests mock the probe functions, not the clients themselves, so the suite does not require pnpm db:up.

Build and run the container image locally

  1. The default FROM path in backend/Dockerfile expects the ECR pull-through cache and won't resolve on a laptop. For local builds, keep a one-off backend/Dockerfile.local whose FROM lines point at docker.io/library/node:24-alpine, or rewrite FROM in place while iterating.
  2. From the repo root: docker build -t mythrun -f backend/Dockerfile.local . — build context is the repo root so the lockfile, .npmrc, and pnpm-workspace.yaml are visible.
  3. docker run -p 3000:3000 mythrun.
  4. curl localhost:3000/health should return {"status":"ok"}. The container runs with BOOT_GATE_ENABLED unset, so it uses the fallback start and does not need a reachable Postgres or Redis.

Add a new workspace package

  1. Create the directory with its own package.json (scoped @mythrun/*).
  2. Add the directory to pnpm-workspace.yaml. Root pnpm -r commands pick it up automatically.
  3. Add the scripts the root commands fan out to (test, typecheck, lint, optionally build). Workspaces without a given script are silently skipped.
  4. pnpm install from the root to materialize dependencies and update the lockfile.

Integration points

The data plane owns the Postgres and Redis endpoints production connects to; the network module owns the ecs security group the container launches into. The serving module wires the prod env vars and secrets that loadEnv's component-form branch consumes and that the boot gate — once enabled — probes. Cognitive-tier code (Fast Thinker, Slow Thinker, Scribe, DM Trigger) lands as additional modules under backend/src/; they'll share this server's lifecycle, AppDeps shape, and Dockerfile.
