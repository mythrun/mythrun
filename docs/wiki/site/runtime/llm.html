LLM client

The thin shell every Mythrun LLM call sits on top of. Three tier-named model constants (HAIKU, SONNET, OPUS), a logging + error-normalization middleware that handles both generateText and streamObject / streamText call shapes, a typed error taxonomy (nine classes including the terminal LlmContentFilteredError), and a file-based prompt loader. The streamObject / generateObject wrappers also accept an optional maxOutputTokens ceiling so a long-prose call can lift the SDK default before it truncates, an optional redactRawText flag (generateObject only) for a call whose raw output reasons over secrets, and a blocks option that splits a prompt into cacheable spans. Consumers include the onboarding profanity classifier, the world-gen input gate, the paint-job validator, the world-gen stage handlers (concept_intake, world_color, vocabulary_intake, world_and_factions, locations_and_npcs, entity_relationships, world_introduction, entity_consolidation, starting_situation, random_tables, coherence_pass), the structured-output repair chain plus its companion per-item drop-on-fail gate on the streaming stages, the session-prep generation stage, the DM-trigger classifier (a cheap Haiku generateObject deciding whether the AI DM should take a turn), the Slow Thinker's two calls (a Haiku spend gate and an Opus director — both generateObject, the director with the haiku-then-sonnet repair chain and an explicit maxOutputTokens), and — newest — the Fast Thinker's world-knowledge lookups: a Haiku contextual recall-gate and the synchronous Opus ST-vet (the one call that sets redactRawText), and the Haiku turn-audit gate that classifies each Fast-Thinker render for behavioral violations (authored PC speech, an inline correction, a faked session end) before it reaches the table. Everything heavier (provider mechanics, structured-output validation) is delegated to Vercel AI SDK v6 — with one deliberate exception: retries for budget-shaped prep calls are now wrapper-owned, part of the LLM outage resilience layer that also gives every Anthropic request a per-mode transport timeout and classifies every failure at this boundary.

How it fits together

Mythrun's cognitive tiers (Fast Thinker, Slow Thinker, Scribe, DM Trigger Classifier, prep engine) all need to call Anthropic models, with a consistent error shape, consistent token + latency logging, and zero hardcoded model IDs sprinkled across call sites. Rather than write that abstraction from scratch, the LLM layer wraps the Vercel AI SDK (ai + @ai-sdk/anthropic) and adds the Mythrun-specific seams the SDK leaves open.

The provider package must KNOW the pinned models — @ai-sdk/anthropic carries a per-model capability table, and a model id it does not recognize silently falls back to maxOutputTokens: 4096 and supportsStructuredOutput: false. On the Claude 5 line, where thinking is on by default and shares the output ceiling, that fallback is a time bomb: any uncapped structured call can spend the whole 4096 thinking and produce no tool-call output at all (AI_NoOutputGeneratedError) — intermittently, because it depends on how long the model thinks. This bit for real on 2026-07-29: provider 3.0.76 predated claude-sonnet-5/claude-opus-5 and a live world build died in vocabulary_intake; 3.0.103 knows both models (128K ceiling, native structured output). A model-id bump in models.ts is therefore not complete until the provider version demonstrably recognizes the new ids — check its getModelCapabilities before trusting a green unit suite, because short-prompt smokes think briefly and slip under the fallback ceiling.
Vercel SDK, not a hand-rolled adapter — the next two consumers in the queue are Fast Thinker (streaming) and Slow Thinker (tool use). Both are exactly what Vercel's SDK is built for. An own-adapter approach would push 2-3 days of streaming + tool-use plumbing into the Session Runtime tickets that the SDK handles natively. The provider-agnostic shape is a free durability win on top: adding OpenAI or Gemini becomes pnpm add @ai-sdk/<provider> + a new wrapped model constant, no call-site changes. We aren't locked in either — callers use Vercel's public functions (generateText, etc.) directly, so a future swap to direct Anthropic SDK calls is a per-file mechanical refactor.

The core Mythrun-owned files sit under backend/src/llm/: models.ts defines the three tier constants, middleware.ts wraps each with logging + error normalization, errors.ts defines the typed error taxonomy and the Vercel-to-Mythrun mapper, prompts.ts is the file-based template loader, ai.ts is the canonical wrapper for schema-validated calls (repair chain, diagnostics, and the outage-layer attempt loop), and profanity.ts is the original call site. The outage-resilience siblings — llm-fetch.ts, classify-llm-error.ts, llm-health.ts, llm-health-probe.ts — have their own page. Two more directories hold the data shapes: schemas/ for Zod schemas describing structured-output responses, and prompts/ for the .txt system-prompt templates the loader reads.

Tier-named model constants

models.ts exports three constants — HAIKU, SONNET, OPUS — each constructed from a shared createAnthropic({ fetch }) provider and wrapped by wrapLanguageModel with the logging middleware. The custom fetch is the outage-resilience transport: every Anthropic request routes through per-mode undici dispatchers so a hung connection fails with a classifiable UND_ERR_* code instead of hanging indefinitely. The IDs are pinned in this file and this file alone: claude-haiku-4-5-20251001, claude-sonnet-5, claude-opus-5. Every other call site in the codebase imports a tier constant by name; no file outside models.ts mentions a model ID string.

Tier names, not task names — PROFANITY_CLASSIFIER, FAST_THINKER, SCRIBE were considered. They'd add an indirection that lets a config swap one task's model without touching call sites. The use case for that hasn't materialized — model assignments are stable and align with cost tiers (Haiku for routing / classification, Sonnet for player-facing prose, Opus for reasoning-heavy work). Tier names today; task aliases when the need shows up.

Callers reach the SDK through Vercel's public surface — generateText with output: Output.object({ schema }) for structured output, plain generateText for prose, streamText for streaming when that lands. They pass a tier constant as model and the wrap is invisible from their perspective: the middleware fires automatically inside the SDK call frame.

Logging + error normalization, as middleware

middleware.ts exports logAndNormalizeMiddleware(modelId) — a LanguageModelV3Middleware factory that wraps doGenerate. On success it records start-to-finish wall time, pulls token counts and finish reason out of the SDK result, and emits a single event: 'llm.call' log line at info level with { model, mode, inputTokens, outputTokens, totalTokens, cacheReadTokens?, cacheWriteTokens?, latencyMs, finishReason, sessionId?, userId? }. On failure it emits event: 'llm.error' at error level with the original error preserved as err, then runs the original through mapToMythrunError before rethrowing.

Middleware seam, not a wrapper function — Vercel's wrapLanguageModel is the supported extension point: the middleware fires inside the SDK's call stack, so SDK-level retries, response parsing, and tool-use protocols all run on top of our instrumentation. A wrapper function would either shadow the SDK's API (re-implementing every public function) or sit outside it (and miss retries that completed successfully on the second attempt). The middleware shape lets Vercel keep owning the call path while we own the observability.

Two pieces are deliberately not in the log line. Cost isn't logged here because Anthropic exposes no programmatic pricing API to query at runtime; hardcoding rates here would create a second source of truth that drifts from the billing-metering MODEL_PRICING map. Downstream consumers — the recordUsage writer, the CloudWatch dashboards — compute cost from tokens × ratePerMillion against the rate map at backend/src/billing/model-pricing.ts, which is itself kept honest by the daily LLM price-check workflow. The model field on each log line is the discriminator that lets retrospective analysis split spend across Haiku / Sonnet / Opus correctly. Provider-specific finish-reason detail is also dropped — the SDK exposes finishReason as { unified, raw }, and the middleware logs only unified (one of stop / length / content-filter / tool-calls / error / other). Log queries stay grep-friendly across providers; debugging sessions that need the raw value pull it from the SDK directly.

The two cache counters are what make the line priceable at all. The SDK's inputTokens is a sum — fresh input plus cache reads plus cache writes — so pricing it directly against the input rate overstates a healthy cached call by 3–5×. Anything deriving dollars from these lines subtracts first: base input is inputTokens − cacheReadTokens − cacheWriteTokens, reads bill at a tenth of the input rate, writes at 1.25×. The cost-measurement harness is the one place that derivation lives.

MythrunContext rides through providerOptions.mythrun on every outgoing call. Five fields are read: sessionId, userId, worldId, campaignId, and stage. The middleware reads them out of the params namespace and includes them on every log line; calls without the context fields just have undefined for those keys (pino omits undefined). The mythrun namespace inside providerOptions avoids collision with provider-specific options like providerOptions.anthropic.cacheControl.

Five fields, not just sessionId/userId — the prep pipeline runs jobs that don't have a session yet (a world generation kicks off before any campaign is bound to it), so a session-only attribution model wouldn't slice prep costs. Adding worldId, campaignId, and a free-form stage label ('world-gen.intro', 'campaign-setup.factions', etc.) gives the spend-attribution writer enough discriminator to split costs across world creation, campaign bring-up, and live-play turns without changing schemas later.

Those fields are only useful if every call site sets them, and for a long time most did not. The cost-harness work closed that: each of the ~30 call sites across src/llm/ and src/session/ now stamps a stable stage label plus whichever ids are genuinely in scope — sessionId on the per-turn calls, campaignId (and worldId where it exists) on the prep and world-gen stages. A call-versus-stamp sweep over both trees is what found the last holdouts: the paint-job validator's Opus generator and Sonnet judge, the retcon author, and the combat outcome table, none of which had ever been attributable. Two call sites stay deliberately id-less — synthesizeConcept and reviseConcept run at preview time, before any campaign row exists to point at.

An unstamped call is worse than an unmeasured one — a line with no ids does not merely go uncounted, it goes uncounted silently: cost tooling scopes by id, so an unattributable call simply vanishes from the totals and every derived number looks plausibly smaller. That is why the sweep compares LLM-call count against stamp count per module rather than spot-checking, and why the harness reports what it dropped instead of quietly filtering.

Streaming via wrapStream

Beyond wrapGenerate, the middleware also implements wrapStream — the SDK hook that fires for streamText calls (Fast Thinker prose, eventually the prep-stage interactive narration). Streaming is more demanding to observe than non-streaming: exactly one terminal log line per call, regardless of how the stream ends, with the right bindings on the right level. The middleware uses a terminated flag closed over the stream wrapper to guarantee that.

Seven terminal states are possible; each produces exactly one log entry:

State Trigger Log line Surfaces to caller as
Success upstream emits a type === 'finish' part llm.call (info) stream closes naturally
Provider-graceful error finish part with finishReason.unified === 'error' llm.call (info, with the unified reason) stream closes naturally — provider already shaped the error
Content-policy filter finish part with finishReason.unified === 'content-filter' llm.error (error, reason: 'content-filter') LlmContentFilteredError raised through the controller — terminal, no retry
In-stream error upstream emits a type === 'error' part mid-stream llm.error (error) controller.error(mapped) — consumer's iterator throws
Truncation upstream closes with no finish or error event llm.error (error) LlmStructuredOutputError is raised through the controller
Cancellation downstream cancel() handler fires llm.error (error, reason: 'cancelled') nothing — cancellation is consumer intent, no rethrow
Open-time error doStream() rejects before any chunk arrives llm.error (error) wrapStream throws the mapped error to the caller
Content-policy filter is distinct from provider-graceful error — Anthropic's finishReason.unified distinguishes error (the model itself failed partway through and the provider shaped the error gracefully) from content-filter (the safety classifier terminated generation because the prompt or its continuation tripped content policy). Treating them the same would mean an output-quality failure (retryable) and a policy failure (terminal — retrying the same payload hits the same filter) flow through the same code path. The middleware's wrapGenerate also detects content-filter on its non-streaming side and raises LlmContentFilteredError, even though the SDK reports the call as a success. The error maps to HTTP 422 with no Retry-After — the right next action is the user adjusting their input.
Terminate-once via closure flag, not per-state idempotency — every state needs to coordinate with the others (cancel after a finish is a no-op, error after a cancel is a no-op, truncation after an in-stream error is a no-op). Tracking "did this stream already terminate?" via one mutable flag in the wrapper closure is dramatically simpler than guarding each emission site against the other five states independently. The flag flips the first time any terminal event fires, and every subsequent emission site short-circuits.

Every log line — both modes — now carries a mode field ('generate' | 'stream') so retrospective queries can split spend across one-shot and streaming calls without inferring from finishReason. The unified LogBindings shape is declared in middleware.ts so a typo on a new callsite is a TS compile error rather than a silently-malformed log entry. The llm.call completion line also records cacheReadTokens — the count of input tokens served from the Anthropic prompt cache.

cacheReadTokens makes a cache regression visible — the Fast Thinker holds the full session transcript every turn, which is only affordable while prompt-cache reads stay high on turn ≥ 2. A mis-placed cache breakpoint is otherwise silent — no error, just full input price on every step of every turn — so the middleware surfaces the per-call cache-read count for retrospective queries and the smoke asserts it is non-zero after the first turn.

The Fast Thinker tool loop: streamTextWithTools

ai.ts exposes generateText / generateObject / streamObject but had no streaming-with-tools surface. MYT-68 adds streamTextWithTools — the net-new primitive the Fast Thinker drives its interleaved tool loop with. It wraps the SDK's streamText + tool() + stopWhen + prepareStep on a wrapped (middleware-carrying) model, exposes the typed fullStream, and returns two distinct usage promises: the final step's usage (the context-fill signal) and the cumulative totalUsage across all steps (spend attribution). The same lint rule that forbids reaching into 'ai' directly is why the wrapper also re-exports the SDK types callers need (tool, ToolSet, ModelMessage, stepCountIs, …).

No repair chain; errors and timeouts are in-band, not throws — the wrapper deliberately wires no output-repair (that is generateObject's concern; this is prose, and a malformed tool input surfaces as a tool-error part the model recovers from). The per-turn timeout is the SDK's native timeout, which — like a provider error mid-stream — surfaces as an in-band abort / error fullStream part and closes the stream gracefully; the for await does not throw on its own. The consumer owns converting both to thrown Mythrun errors, so a truncated turn never ends "normally." The usage promises are pre-handled (no-op catches) so an FT that throws out of its consume loop never leaves an unhandled rejection to kill the worker. Because the wrapper never throws, it also carries an error/abort-part observer for the outage detector: each in-band error part is classified and reported before it yields through to the consumer.

Concurrency and rate-limit ceilings

Two independent ceilings shape what the LLM client can drive at peak. The first is our self-imposed BullMQ worker concurrency caps, declared in backend/src/worker/bullmq-config.ts: CONCURRENCY_WORLD_GEN = 3 + CONCURRENCY_CAMPAIGN_SETUP = 5 = 8 in-flight Anthropic streams at full saturation. The second is Anthropic's per-account ceiling on our API key — Tier 2 at the time of writing, ~50 requests/minute and ~800k tokens/minute on the input side. The two ceilings exist for different reasons (ours protects the data plane and the bill; theirs protects their fleet), and we sit comfortably under the lower one with substantial headroom.

Ceiling Value today Owner What it protects
BullMQ world-gen concurrency 3 worker/bullmq-config.ts Opus-heavy world-creation streams; each holds a pg client + Vercel SDK stream buffer.
BullMQ campaign-setup concurrency 5 worker/bullmq-config.ts Per-player character-creation jobs; Sonnet-weight, lighter per-slot.
Peak concurrent Anthropic streams 8 derived Both queues saturated simultaneously.
Anthropic Tier 2 RPM ~50 requests/min Anthropic console Their per-account fairness ceiling.
Anthropic Tier 2 TPM (input) ~800k tokens/min Anthropic console Their per-account fairness ceiling.

The cap of 8 is not arbitrary; it's the sum of a small constraint stack. Each in-flight job holds a Postgres client from a pool sized around 10, leaving headroom for the health probe and the worker's own SELECTs. Each Anthropic streaming call buffers JSON repair state in the Vercel AI SDK, which competes for the 2 GB the worker task is sized at. Node is single-threaded for parse + repair, so raising concurrency past the CPU's ability to interleave parse work degrades total throughput. The cap also functions as a passive billing-burst rate-limiter — one buggy LLM loop can drain credits an order of magnitude faster than the cap allows. Finally, higher concurrency drives more atomic-claim contention on pipeline_runs (see Worker) and rollback storms are always worse than waiting in a queue.

Why we don't just raise the cap to match Anthropic Tier 2 — the ceiling isn't the bottleneck at launch traffic shape. Prep work (world generation, character creation) is bursty-but-rare — a single launch-day campaign creation touches each queue for a few minutes and goes idle. The ratio of long-tail idle time to active time means a higher cap would only matter during a synchronized creation spike, and the surrounding constraints (pg pool, task memory, billing safety) bind first anyway. When live-play traffic shape replaces prep-traffic shape, the calculus changes; until then, the budget headroom is the win.

Scaling levers, in order of preference. Horizontal: run more ECS worker tasks (the BullMQ workers are stateless; desiredCount + maxCapacity sit on the serving module ready to be increased). Each task adds a full 3 + 5 = 8 slots at the same per-slot footprint, and the underlying pg + Redis fleet has plenty of headroom for >1 task. Vertical: raise the per-queue concurrency caps in bullmq-config.ts, increase the pg pool max, and re-size the ECS task's cpu/memory — this is harder to undo and binds the resource ratio tighter than the horizontal lever.

Three trigger signals would warrant raising the caps (any one is enough to start the conversation): pg connection-pool utilization above 80% during a sustained peak; worker queue depth above 50 for more than five minutes; observed LlmRateLimitedError spikes in production that aren't traceable to a runaway loop. None of these are tripping today — the cap is set conservatively against a future where they might.

The prep-pipeline smoke is the running proof point. The smoke-testing page covers the operator surface; the short version is that aws ecs run-task --cluster mythrun --task-definition mythrun-staging-smoke-prep-pipeline ... drives three concurrent owner-creates-campaign flows with three players each — saturating both queues. Absence of LlmRateLimitedError entries during the run, combined with completion inside the 10-minute wall-clock budget and total cost under $5, is the running verification that the ceiling-stack survives a real burst. A green smoke is the artifact that justifies leaving the caps where they are; a red one with 429s is the trigger to revisit.

The error taxonomy

errors.ts defines nine typed classes and a single mapper: LlmRateLimitedError (429), LlmOverloadedError (529 — Anthropic-specific upstream-busy), LlmUpstreamError (a provider-side 500-class failure surfaced as an in-band api_error event on an open stream — transient, same retry posture as its 529 sibling), LlmAuthError (401 / 403), LlmContextTooLongError (400 + context-window message match), LlmInvalidRequestError (other 4xx), LlmTimeoutError (AbortError), LlmStructuredOutputError (AI_NoObjectGeneratedError — the SDK exhausted its retries trying to coerce the model into a schema-valid response), and LlmContentFilteredError (Anthropic's content-policy filter terminated generation — the call returned with finishReason.unified === 'content-filter').

mapToMythrunError pattern-matches the incoming error: DOMException with name AbortError, plain Error with name AI_NoObjectGeneratedError (matched by name to avoid a brittle deep-import), or APICallError with status code dispatch. Unknown errors pass through unchanged so Fastify's default error handler still catches them as 500. Every mapped error preserves the original as cause for stack-trace forensics. The middleware's wrapGenerate also detects finishReason.unified === 'content-filter' on otherwise-successful calls and raises LlmContentFilteredError from there — the call doesn't reject from the SDK, but the response is unusable, so the middleware shapes it into the taxonomy at call-frame edge. The stream side carries one more deliberate mapping: mid-stream Anthropic error events on an open stream arrive as raw JSON payloads, not Error instances, and the in-stream arm maps overloaded_error → LlmOverloadedError and api_error → LlmUpstreamError with the raw payload preserved as cause — without it the generic fallback mints Error("[object Object]") and a partial overload on the streaming path dies unclassified by the outage taxonomy.

Route handlers catch only Mythrun classes. The HTTP-status mapping happens at the route layer: rate-limited → 429, overloaded → 503, timeout → 504, auth-failed → 503 (server misconfigured, not the caller's fault), context-too-long → 400, invalid-request → 400, structured-output → 502 (provider returned unparseable output), content-filtered → 422 (the prompt itself was rejected; retrying with the same payload hits the same filter, so the response carries code: 'content_filtered' with no Retry-After).

The prompt loader

prompts.ts is a tiny file utility with no SDK dependency. loadPrompt(area, name, vars?) reads backend/src/llm/prompts/<area>/<name>.txt, caches the raw template on first read, and substitutes {{variable}} placeholders from the optional vars map. Unmatched placeholders are left intact so a missing variable surfaces visibly in the rendered output (and on inspection of the LLM call). Cache is process-scoped so a deploy starts fresh.

File templates, not inline string literals — prompts are versioned content the prototype iterated on for months; treating them as code and committing each one as a .txt file means git history captures each prompt revision discretely. Inline string literals would mix prompt changes into adjacent code diffs and lose that signal. The area/name directory shape (auth/profanity, fast-thinker/turn, etc.) keeps them organized as the cognitive-tier modules grow.

Prompt blocks and cache breakpoints

A flat prompt string is one opaque payload, and Anthropic's prompt cache needs to be told where the reusable part of a prompt ends. The blocks option is that seam. In place of prompt / system, a call site can pass an ordered list of { role, text, cacheBreakpoint? } pieces; ai.ts compiles them into the SDK's message form and attaches providerOptions.anthropic.cacheControl to exactly the blocks that asked for it. Everything above a breakpoint becomes a cacheable prefix: written once, then read back at a tenth of the input price on every subsequent call that shares those bytes.

The compiler is strict about the shapes that would otherwise fail at the wire. Blocks and prompt/system together throw, as do more than four breakpoints (the provider's ceiling), a block list with no user-role entry, and a system block sitting after a user block — that last one is subtle, because the provider quietly accepts it by switching on a model-gated beta header that then 400s on Haiku and Sonnet. Legacy flat-prompt callers are untouched: their requests are byte-identical to what they sent before the seam existed, pinned by snapshots captured against the pre-seam code.

Breakpoints belong on messages, not on the call — passing cacheControl at the top level of providerOptions.anthropic looks like it should work and is not rejected, but the installed provider maps it to a different feature (whole-prompt auto-caching) rather than a prefix boundary. Nothing errors; the cache just does something other than what the call site meant. Compiling breakpoints down to per-message annotations inside the wrapper keeps that mistake unavailable to call sites.

Caching only pays when the cached span is genuinely stable, which makes prompt ordering a cost decision. Templates that want caching are written stable-first: instructions, rosters, and playbooks above the breakpoint; per-turn state below it. A single volatile byte above the boundary silently zeroes every hit — no error, just full price — so the templates that were reordered for caching carry tests pinning the compiled prefix byte-identical across assemblies that vary every volatile input. Two more constraints shape where this is worth doing: a cached prefix must clear the model's minimum cacheable length (4,096 tokens on Haiku, 1,024 on Sonnet and Opus), and the entry lives for five minutes from the moment its call is processed, not from when it finished. See the Slow Thinker and Scribe for the three prompts currently annotated this way.

The first call site: classifyProfanity

profanity.ts is one function, ten lines of body, and the prototype for every structured-output call site that follows. It loads the system prompt from prompts/auth/profanity.txt, calls generateText with output: Output.object({ schema: ProfanitySchema }) against HAIKU, and returns the parsed object verbatim. The schema (schemas/profanity.ts) is a small Zod object: { profane: boolean, reason?: 'offensive' | 'impersonation' }.

generateText + Output.object, not generateObject — Vercel SDK v6 deprecated generateObject in favor of the unified generateText + output shape, which supports tool-calling and structured output through the same call. Writing new code against the deprecated function would mean rewriting it inside a year. The Output helper lives in ai and validates on the SDK side; AI_NoObjectGeneratedError still surfaces from a schema mismatch and the middleware still maps it to LlmStructuredOutputError.
Zero local heuristics — full ZFC delegation — the previous MYT-38 stub kept a static RESERVED_USERNAMES set and a Shutterstock LDNOOBW seed list. Both were pattern-matching shortcuts (substring scans on the username), exactly the style of cognition CLAUDE.md's Zero Framework Cognition principle says to delegate to AI. The single Haiku call covers offensive content (profanity, slurs, sexual content, hate speech, violence) and impersonation (system roles, Mythrun brand or staff, technical identifiers) in one prompt; the fallback static lists are gone. Cost is trivial: ~50 input + ~10 output tokens per call, ~$0.0001 per username registration at Haiku pricing. 10K registrations/month is ~$1.

The function name is now a slight misnomer — it does both impersonation and offensive checks, not just profanity. Renaming was deferred from the MYT-44 scope; whoever owns the next bead in the area can decide.

The session-prep generation stage

llm/prep/stages/session-prep.ts is the first consumer of the maxOutputTokens seam, and the first call site that builds for a tier the live game hasn't reached yet. generateSessionPrep(repo, { campaignId, worldId, sessionNumber }) produces the three prep documents a session needs before play starts: ft_context — the Fast-Thinker-facing context, enforced-ignorance safe — sd_playbook — the Slow-Thinker's stage-direction playbook carrying every secret, clue, and revelation condition — and (MYT-101) opening, the short player-facing DM introduction the table opens on, read aloud at session start. It serializes the omniscient world state (llm/prep/serialize-world-state-for-prep.ts), renders the prompts/prep/session-prep.txt template against it, and runs one streamObject call on OPUS against a three-string Zod schema (sessionPrepSchema: { ft_context, sd_playbook, opening } with presence/length floors — opening carries a 100-character floor). Like ft_context, the opening is player-facing prose an all-seeing model wrote, so the session-prep processor runs it through the secret tripwire before persisting: this primitive produces the opening, the processor vets it. The call returns the parsed object plus its token usage.

The generation primitive, wired into a job — this page documents generateSessionPrep as a building block. The orchestration around it — a session-prep BullMQ job, a processor that tripwire-vets the opening, persists the three documents to session_preps, and records cost, a dedicated queue and worker — ships on the session prep page. The /start path in Session Runtime reads the persisted prep and feeds ft_context to the Fast Thinker and delivers the opening as the session's first DM row (MYT-101). There is no runtime leak guard on ft_context and there will not be one — see the omniscient-serializer note below for how enforced ignorance is achieved instead.
Long prose docs in one structured object → an explicit maxOutputTokens — the call asks Opus for two long markdown documents (a ~2,000–3,000-word context plus a ~1,000–2,000-word playbook), alongside the short 150–350-word opening, inside a single structured response. The two long docs are what drive the ceiling. The SDK's default output ceiling truncates that mid-document, which a schema-presence floor can't recover from — the reason the maxOutputTokens opt was added to the wrapper at all. The stage pins it to OPUS_MAX_OUTPUT_TOKENS (128k, the model's real output ceiling) as a backstop, not the routine wall: a low fixed cap (the original 16384) truncated prep mid-schema around session ~10 as accumulated campaign canon grew the output, so the session-prep orchestration bounds the growth at the source (working-set input tiering plus an in-prompt output budget with a single graceful overflow-retry) and the raised cap only ever catches a genuine runaway. It also sets the codebase's largest LLM timeout (9 minutes) because two long Opus documents over a streamed object is the slowest single call in the system.
Read await result.object, not runStreamingStage — the world-gen streaming stages key on arrays (regions, relationships) and use the partial-tree iterator to emit per-entry events as the LLM writes them. Session prep emits a flat two-string object with no array to walk, so it reads the validated result directly via await result.object — the array-keyed runStreamingStage would emit nothing here. The call sets maxRetries: 0 at the SDK layer on purpose: the haiku-then-sonnet repair chain owns schema-validation recovery and the stage's parking ladder owns transport recovery, so a third hidden SDK retry layer would only multiply cost. The call threads providerOptions.mythrun.stage = 'session_prep' for log attribution — one of the stage labels the wrapper now recognizes alongside the world-gen stages.

generateSessionPrepArgs carries an optional onProseDelta(field, text) callback. When a caller supplies it — the session-prep processor does, to push the prose live to the dev tool — the stage drains result.partialObjectStream before reading the final object, emitting the newly-appended substring of each long field as it streams (the delta stream carries the two long docs, ft_context and sd_playbook; the short opening is finalized with the object, not streamed). The three-string object is still finalized through await result.object afterward (consuming the partial stream doesn't consume the object or usage promises), so the persisted documents and the token usage are unchanged. When the callback is absent (the stage's own unit tests, a direct-call smoke), the drain is skipped entirely and the result is identical.

Streaming the prose costs no extra tokens — streamObject was already streaming under the hood; the original code just awaited the final object and threw the intermediate chunks away. Forwarding them through onProseDelta reuses bytes that were already on the wire — there is no second LLM call and no added cost. The diff is a simple per-field length comparison: when a field's streamed value strictly extends its prior value, emit the tail; when it doesn't (the SDK's partial-JSON parser briefly rewrites an in-flight escape sequence — a dangling \ resolving to \n — so the prefix diverges for one tick), resync silently and emit nothing. The callback is wrapped in try/catch: it is fire-and-forget cosmetic telemetry, so a throwing sink must never abort generation. Field attribution is correct regardless of emission order because each field is diffed independently against its own retained value — do not "simplify" this by assuming the fields fill in order.
The wrapped .object promise is handled at birth — a consumer that drains partialObjectStream reads the stream first and awaits result.object only afterward (or, on a stream-error path, never). The wrapper builds that object promise eagerly, so if the haiku-then-sonnet repair chain rejects before any awaiter has attached, the rejection is detached — and under the worker's --unhandled-rejections=throw policy a detached rejection kills the whole process, every queue, not just the failing job. That is exactly how a session-prep output-token overflow once took down all nine worker queues at once. The wrapper attaches a no-op .catch() at construction so the rejection is always observed; a real await result.object still sees the error. It is the same discipline the tool-loop wrapper applies to its usage promises, and the worker's job-containment layer is the second line of defence behind it.

The serializer is async and omniscient by design. It hops campaign → world_id, loads the full world inventory (all access tiers, secrets included — this is a Slow-Thinker-tier artifact, not a Fast-Thinker read), renders it with the omniscient world dump, and appends the world concept, the party (each character with their known-tier facts only, batched in one query — never N+1), and the chosen starting situation. Two forward-compat seams are present but unexercised: a swappable inventory-source function so a later session-N caller can feed evolved state, and an optional prior-session-context block. The enforced-ignorance split happens inside the prompt, not the serializer: the serializer hands Opus the whole truth with authoritative [access_level] markers, and the template's hard exclusions are what keep discoverable and secret material out of ft_context.

Omniscient serializer + in-prompt exclusion, not a pre-filtered input — the Slow Thinker needs to see every secret to write the playbook and to decide what a depth marker in the Fast-Thinker context is pointing at. Pre-filtering the input to known-tier would blind the playbook. So the serializer is deliberately omniscient and the access markers ride through verbatim; the model is instructed to route known-tier-only into ft_context and everything else into sd_playbook. There is no separate, code-level leak guard on the produced ft_context, and one is not planned. Enforced ignorance rests on two things: the Opus author writes a watertight ft_context under the template's hard exclusions (omitting discoverable / secret material), and the access-tier separation means only known facts are ever Fast-Thinker-safe in the first place. A weaker per-document checker run after the fact couldn't out-judge the omniscient author on subtle leaks, and would risk redacting the deliberate foreshadowing (depth markers) the author put there on purpose. Systemic assurance is the launch red-team, not a runtime gate.

Configuration: ANTHROPIC_API_KEY

config/env.ts validates ANTHROPIC_API_KEY at boot — required, must start with sk-ant- (the prefix common to test and live keys). The @ai-sdk/anthropic provider reads the env var directly; no explicit factory call in models.ts. Local dev populates from Anthropic Console into backend/.env.development; staging and production read from AWS Secrets Manager (mythrun/staging/anthropic-api-key, mythrun/prod/anthropic-api-key), exposed as the same env var by the ECS task definition's secrets: block.

Prefix check at env-load, not at first call — pasting a Stripe key, a half-rotated value, or an empty string from a missing secret would otherwise surface as a runtime 401 from the Anthropic SDK on the first LLM call — minutes or hours after boot, depending on traffic. Validating the prefix at loadEnv() makes the failure mode loud, immediate, and obvious during deploy.

Operating this piece

Add a new structured-output call site

  1. Define the response shape in backend/src/llm/schemas/<area>.ts as a Zod object. Keep the schema small — Anthropic models match well-bounded enums and short strings; deeply nested or open-ended shapes drive up the chance of an AI_NoObjectGeneratedError.
  2. Write the system prompt as backend/src/llm/prompts/<area>/<name>.txt. Use {{vars}} placeholders for any per-call interpolation and resolve them in the caller via loadPrompt('area', 'name', { vars }).
  3. In a per-area module under backend/src/llm/, call generateText({ model: HAIKU | SONNET | OPUS, output: Output.object({ schema }), system, prompt, maxRetries: 3 }) and return result.output. Pick the tier that matches the task — Haiku for classification / routing, Sonnet for prose, Opus for reasoning-heavy work.
  4. Mock at the SDK boundary in tests: vi.mock('ai', ...) with a stubbed generateText returning the desired fixture. Tests don't hit the network; the middleware doesn't fire under the mock either.

Thread session / user context into the log line

  1. Pass providerOptions: { mythrun: { sessionId, userId } } on the generateText call. The values flow through the SDK and surface as fields on the middleware's log line — useful for spend attribution and per-session debugging.
  2. The mythrun namespace coexists with provider-specific entries (e.g. providerOptions: { mythrun: {...}, anthropic: { cacheControl: { type: 'ephemeral' } } }); the middleware ignores anything outside the mythrun key.

Rotate the Anthropic API key

  1. Mint a fresh key in Anthropic Console; mark the new key with the same mythrun-staging / mythrun-prod tag the old one carried.
  2. aws secretsmanager update-secret --secret-id mythrun/<env>/anthropic-api-key --secret-string <new-key>. The task definition reads the secret on every task start, so deploys after this point pick up the new value automatically.
  3. Force a service rollover (aws ecs update-service ... --force-new-deployment) to cycle existing tasks onto the new key.
  4. Revoke the old key in Anthropic Console once the rollover completes.

Diagnose an llm.error log spike

  1. Filter CloudWatch on event: 'llm.error'. The err.name field discriminates by class.
  2. LlmRateLimitedError spikes mean Anthropic's per-key rate limit is biting; either rate-limit the upstream caller or open a support ticket to raise the limit. LlmOverloadedError spikes are Anthropic-side capacity issues; the route layer returns 503, retries are bounded, no Mythrun-side action.
  3. LlmAuthError in production is usually the wrong key being deployed (stale rotation, env mismatch); cross-check the secret value against the Anthropic Console.
  4. LlmStructuredOutputError spikes on a specific call site mean the schema is too open-ended for the model — tighten the enum, narrow the field shape, or move to a stronger tier.

Integration points

The onboarding surface's POST /api/users/register and GET /api/users/check-username are the current consumers of classifyProfanity. The backend runtime page describes config/env.ts loading ANTHROPIC_API_KEY alongside the rest of the env contract. The live-play cognitive tiers now use this same surface: the Fast Thinker drives its tool loop through streamTextWithTools, the Slow Thinker's gate and director call generateObject, and the post-turn Scribe's secret tripwire (Haiku) and retcon-author (Opus) do too. The Fast Thinker's world-knowledge lookups add two more generateObject consumers — a Haiku recall-gate and a synchronous Opus ST-vet. Three of these set redactRawText because their raw output reasons over the secret playbook: the ST-vet, the Scribe's tripwire, and the Scribe's retcon-author. All call Vercel's surface against tier constants, threading providerOptions.mythrun = { sessionId, userId, worldId, campaignId, stage } for log attribution. The streaming half of the middleware lands ahead of those consumers via MYT-49 — the worker's prep-stage processors will be the first callers to exercise wrapStream end-to-end. The billing-metering data plane consumes the token counts the SDK surfaces — its recordUsage writer turns them into a durable per-session estimated_cost_usd using the MODEL_PRICING rate map. The rate map lives there, not here. One sibling under backend/src/llm/ is not an Anthropic call: embed.ts is the Voyage embeddings client that powers world-store retrieval — Anthropic ships no embeddings endpoint, so semantic search uses a second provider with its own key, boot probe, and page. The LLM outage resilience page owns the story of what happens when calls through this layer fail: the transport dispatchers, the failure taxonomy, the Redis outage state and recovery probe, and prep-pipeline parking.
