Session transport

The live multiplayer layer: a ticket-authed WebSocket per player, a cross-container fan-out hub modeled on the SSE pipeline subscriber, ordered persist-then-broadcast chat, sequence-based reconnection replay, and a crash-safe TTL-presence model that suspends an empty session through a self-validating BullMQ job. This is the transport floor the DM-turn pipeline builds on: it carries player chat and presence frames, and its SessionHub fan-out is also the path the turn worker streams dm_thinking / text_delta / turn_end frames through.

How it fits together

A session is a live play room scoped to one campaign — at most one active at a time. Three HTTP routes bracket its lifecycle (routes/sessions.ts): POST /api/sessions/:campaignId/start creates the row, debits a credit, and resets the per-session Redis state (below); GET /api/sessions/:campaignId/active returns a field-allowlisted view of the live row or null; GET /api/sessions/:sessionId/messages replays the persisted transcript for REST gap-fill. The live transport itself is a single WebSocket route — GET /ws/session/:sessionId, registered by wsSessionRoutes over @fastify/websocket — that a player upgrades into after minting a ws-ticket. Once connected, every player message flows through the same path: a server-assigned sequence number, an append to session_messages, then a fan-out across every API container via Redis pub/sub.

One active session per campaign, enforced in the schema — the idx_sessions_one_active partial-unique index (a campaign can hold exactly one row with status = 'active') is what makes the campaignId a stable key for all the Redis transport state below (session:{campaignId}:…). Two players racing /start can't both win — the second INSERT raises a 23505 the route maps to a clean 409 session_already_active rather than a 500. Keying live state on campaignId rather than sessionId means a reconnect after a suspend/resume cold-starts against the same Redis keyspace without threading the new sessionId everywhere.

Starting a session: the atomicity-critical ordering

POST /:campaignId/start is member-guarded but the campaign owner pays. After three preconditions (campaign is active, a session prep exists for the next session number, no session already active), the handler runs a fixed four-step sequence whose ordering is load-bearing:

  1. Mint the sessionId up front, so the credit debit's idempotency key (= sessionId) is known before either the INSERT or the debit.
  2. INSERT the session row first. A concurrent /start that already took the idx_sessions_one_active slot surfaces here as a 23505 → 409 (closing the race; never 500).
  3. Debit one session credit from the owner — self-managing transaction, idempotent on sessionId. Insufficient credits → deleteById the just-created row (it must not occupy the one-active slot unpaid) → 402.
  4. Initialize the Redis :state blob, parking the FastThinker's prep context (ftContext, from session_preps.ft_context) and the world tone alongside the participant list — so the turn worker reads them per turn without a Postgres round-trip. A fresh session leaves the :seq counter unset, so the first nextSeq returns 1.
The FT context is loaded once at session start, fail-soft on a missing prep — the prep doc is immutable per session, so it is read once into the hot :state blob rather than per turn. A session whose prep stage never ran (or whose row was deleted in the narrow window between the precondition check and this read) still starts — the FastThinker degrades to transcript-only grounding, logged loudly at warn, never a 409. The world tone is read with a tier-neutral minimal accessor (getToneAndEra), not the plot-bearing world record, so the enforced-ignorance boundary holds even on this turn-worker-facing path. If the blob is later evicted mid-session, the turn worker re-loads ftContext from Postgres rather than silently losing the canon.
Row-before-debit, with a delete-on-failure rollback — the debit and the row insert can't share one Postgres transaction: the debit runs its own transaction against the credit ledger. So the row goes in first to win the one-active slot, then the debit runs; if it fails on no-credits, the row is deleted so the campaign isn't left with an unpaid active session wedging the slot. The delete is itself wrapped — a cleanup failure logs and still returns 402, never a 500, because the money invariant already holds (no debit happened, and the active-session guard blocks a double-charge on retry). The only fallout of a failed cleanup is a stranded row, diagnosable from the logged line.

The upgrade handshake is the enforced-ignorance boundary's entry point

GET /ws/session/:sessionId opts out of the JWT chain (config.auth: 'public') because a browser-native WebSocket can't send an Authorization header — but "public" here means "no JWT," not "unauthenticated." The auth boundary is the route's preHandler, wsSessionAuth, which @fastify/websocket v11 runs before the upgrade completes: any reply.code(…).send() it issues rejects the handshake with no socket opening at all. The handshake runs five checks in order:

  1. No ?ticket query param → 401 ws_ticket_missing.
  2. consumeWsTicket (an atomic GETDEL). A null return (consumed / expired / missing) → 401 ws_ticket_invalid; a throw (a transient Redis fault on the GETDEL itself) → 503 ws_ticket_store_unavailable.
  3. Ticket's sessionId must equal the path's :sessionId → else 401 ws_ticket_session_mismatch.
  4. Load the session row: not found → 404; not active → 409 session_not_active.
  5. Re-check campaign membership against the session row's campaignId (never the ticket's claimed value), with the same "pending invite is not a member" predicate as requireCampaignMember → else 403 not_campaign_member.
The campaignId the handler trusts comes from the loaded session row, not the ticket — a successful consumeWsTicket only proves some member minted a ticket in the last 30 seconds. It does not prove membership at upgrade time, and it must not be trusted to name the campaign: binding the upgrade to the ticket's claimed campaignId against a different URL session would let a ticket minted for session A authorize a socket on session B. So the handshake loads the session, reads its campaignId, and re-queries campaign_members. The ws-ticket page's "five load-bearing assertions for the future handler" are all honored here — this is that handler.
401 vs 503 on ticket consume, fail-closed either way — the SPA's reconnect logic differentiates: a 401 means the ticket is dead, so re-mint and retry; a 503 means Redis is wobbling, so back off and retry. Collapsing both into a generic 500 would make the client back off on a transient that should retry immediately, or hammer on a dead ticket. Both paths reject the handshake with no socket — the boundary fails closed.

Connect: presence, registration, then the first frame

Past the handshake, handleConnection resolves the participant's character and writes the session_participants row (sessionParticipants.join resolves the character server-side — the client never supplies a character_id, and a member with no integrated character surfaces as a typed NoCharacterForParticipantError that closes the socket cleanly rather than a raw FK violation). It then records presence and registers the socket before broadcasting the join, so the new socket is in the registry when the fan-out comes back around. On join it also appends the character name to the :state participant roster (the list the FT system prompt uses) — covering mid-session joins by construction, and never removed on leave (a departed character is still in the scene).

The :state roster is the FT prompt's, not the skill-check resolver's source of truth — the roster update is a read-modify-write on the hot blob, so two simultaneous joins can lose a name to last-write-wins until the next join. That is acceptable here because the skill-check resolver resolves rollers against session_participants (the authoritative row store), not this list — correctness never depends on the blob roster, and the turn worker reads the roster for the FT prompt from session_participants in deterministic order anyway.

The first server frame is deterministic. A fresh connect (no ?lastSeq) broadcasts a player_joined and sends session_ready. A reconnect (?lastSeq=N) instead builds a session_reconnect replay frame and sends it directly on the socket — a synchronous send that reaches this socket ahead of the player_joined (which only arrives after a Redis pub/sub round-trip).

register-before-replay, so live frames during the DB read aren't lost — the socket is registered with the hub before the reconnect replay reads session_messages. Any frame published live during that DB read is then delivered to this socket too; the client's seq-dedup drops the overlap with the replay batch. A read-then-register ordering would drop exactly that gap. This is the same ordering discipline the hub-resync path relies on.

Inbound chat: persist-then-broadcast with a server-assigned seq

Every inbound frame is parsed and classified at the transport boundary (parseClientFrame + classifyClientFrame): non-JSON, a missing type, or a type not on the CLIENT_FRAME_TYPES allowlist (player_message, typing_start, typing_stop, and the MYT-67 dm_invoke summon) is silently dropped. A typing_* frame broadcasts immediately with no sequence and no persistence. A player_message goes through persist-then-broadcast: assign a server-ordered seq via Redis INCR, append it to session_messages, then publish the frame through the hub.

The inbound handler is also the server side of the DM trigger system. Past the persist-and-broadcast, it writes the per-campaign trigger state (the typing key, the last-activity stamp, the max-wait anchor) and reschedules the quiet-window debounce that decides when the DM responds — after the message is persisted and broadcast, so a queue failure logs at warn and never loses the message. A dm_invoke frame (or an @dm-prefixed message) is the explicit summon: it carries no chat text, is never persisted, and fires the DM immediately rather than waiting on the window. The mechanics of all of that live on the DM trigger page; this transport is where the frames are observed.

Only player_message carries a seq; presence frames never do — clients render the seq stream in seq order, not arrival order, and gap-detect to trigger a reconnect replay. Presence and control frames (player_joined, player_left, typing_*, session_ready, error) are out-of-band: they're never persisted to session_messages and are absent from the replay, so they must never carry a seq a client could gap-detect on — that would corrupt reconnect-replay ordering. The first player_message is therefore seq 1.
Persist before broadcast, and a unique index that fails loud — the durable transcript is the source of truth for replay, so a message is written before it's fanned out. Migration 023 adds UNIQUE(session_id, seq): a re-used number (a reseed race after a crash-recovery counter bump) raises a 23505 rather than silently corrupting the ordering. The route catches that one violation, re-INCRs once, and retries; a second collision re-throws as the pathological state it is. If the broadcast throws after the append succeeds, the message is still durable — the client gap-detects the missing seq and REST-backfills via GET …/messages.
A bad inbound frame drops; it never kills the socket — the whole inbound path is a per-frame error boundary. A malformed frame, an oversized text (capped at 4 KB of untrusted input, distinct from the no-max rule on LLM-generated prose), or a transient Redis fault on persist/publish drops that one frame and keeps the connection alive. The worst case is one lost message, logged. A library-level maxPayload (16 KB) rejects oversized frames before the handler even runs; the in-handler text cap is the second line of defense.

The SessionHub: cross-container fan-out

The transport runs across many ECS tasks, and two players in the same campaign may be connected to different containers. The SessionHub bridges them with Redis pub/sub — one channel per campaign, session:campaign:{campaignId}, derived from the shared contract/session-channel.ts helper (the same helper the turn worker's publisher consumes, so a worker in another process can't publish to a channel the hub doesn't subscribe to). Each API process holds one dedicated PSUBSCRIBE'd Redis client (a duplicate() of redisRealtime) and an in-memory writable registry, Map<campaignId, Map<userId, socket>>. When any container publishes a frame, every container's subscriber receives the pmessage and sends it to its own locally-registered sockets for that campaign. This is structurally the SSE pipeline subscriber with two WS-specific differences: the registry holds writable sockets keyed per user (not a set of read-only SSE sinks), and a resync teardown closes the socket rather than ending a sink.

A dedicated subscriber client, not the shared realtime one — once an ioredis client enters subscriber mode it rejects almost all other commands, so the PSUBSCRIBE client must be separate from the one the route (or the cross-process turn worker) uses to publish, INCR, and rate-limit. The same split the pipeline subscriber makes. The initial psubscribe is awaited before createSessionHub returns, so a publish immediately after construction is reliably delivered.
Reconnect → close every socket → clients replay — if the subscriber drops and reconnects, it may have missed messages published during the gap. Rather than try to reconcile, the hub closes every registered socket with WS code 1011 (redis-resync-required); clients reconnect and pull a fresh session_reconnect replay, which is the canonical recovery path anyway. The very first ready event is the initial connect (nothing missed yet) and is exempt — only a later reconnect triggers the teardown. A single dead socket whose send throws is evicted from the registry in place so it can't wedge the others.

Reconnection replay

A client that drops reconnects with ?lastSeq=N — the highest seq it has rendered. buildReconnectFrame returns a session_reconnect carrying every persisted row with seq > N, the current participant list, and the session mode. As of MYT-68 that includes the DM-turn rows: a player_message row replays as a player_message frame; a dm_text row replays as a consolidated dm_message frame; skill_check / dice_roll rows are reconstructed from their stored JSON content into their respective frames; and the six MYT-70 ledger-tool rows reconstruct into ledger_update frame(s) from the row's persisted LedgerResolution. So a reconnecting client sees the prior DM turns, not just the player chat. Author display and character names are resolved through two in-memory maps built once from campaign-wide reads — no per-message DB lookup. An author who has since left the campaign falls back to a stable "Former player" byline; their prose history still replays intact.

A corrupt DM row drops one frame, never breaks the reconnect — the DM-row replay reconstruction reads the stored JSON through narrow accessors, not a schema that fails loud. This is a transport-replay path, so a malformed or unknown-type row yields null and is dropped (logged), and the rest of the replay still ships. That differs deliberately from the turn worker's history reconstruction, which does fail loud on an incoherent transcript — there, an incoherent row is a persistence-layer invariant violation that must crash the turn; here, it is one missing frame in a best-effort replay.
A ledger row replays as 0, 1, or N frames — and ok:false is silent — the Rules Lawyer persists a row for every adjudicated call, including rejections, but only a successful mutation has a player-visible delta to replay. So the reconstructor discriminates on the stored output's ok field first: an ok:false rejection replays as an empty array with no warning (it is expected, not corruption); an ok:true single payload replays as one frame; and a take_rest row, whose payload is an array (one entry per rested character), replays as one frame each. A genuinely malformed row still warns and drops, as above.
lastSeq is structurally validated at the boundary — parseLastSeq accepts only a non-negative integer; absent, empty, negative, or non-integer input is treated as a fresh connect (null → session_ready). This is a transport-layer structural check (the ZFC structural-validation exception), mirroring the drop-on-malformed posture of the inbound frame parser. The REST GET …/messages?afterSeq=N route applies the same discipline more strictly — a /^\d+$/ match so '', -1, 1.5, and hex don't silently coerce — returning 400 bad_after_seq on anything malformed.

Presence, heartbeat, and crash-safe suspend

Presence is not a counter — it's one TTL key per live connection, session:{campaignId}:conn:{containerId}:{userId}, set with a 60-second expiry. The heartbeat pings every 30 seconds (terminating a socket that hasn't ponged within a 10-second grace) and refreshes the presence key on each ping, so a live connection never lapses. countPresence walks the keys with SCAN (never KEYS, which blocks the single-threaded Redis event loop on a shared cluster).

TTL keys keyed by containerId, not an INCR/DECR counter — a bare counter leaks or goes negative under failure. A container that crashes skips its socket close handlers and would never decrement, leaving a session that looks permanently occupied; a double-fire would push it negative. Per-connection TTL keys self-heal: a crashed container's presence simply lapses after 60 seconds. The containerId (a per-process UUID generated once at boot) namespaces the keys so two containers' presence for the same user don't collide.

When the last player disconnects (countPresence == 0), handleDisconnect schedules a delayed BullMQ suspend job — a five-minute grace window keyed suspend-{sessionId}. A returning player cancels the pending job on connect. The processor (processSuspendJob) is idempotent and self-validating: on fire it re-reads live presence and only suspends when it's genuinely zero. Suspend flushes the live :state to a Postgres checkpoint, keeps status = 'active' (suspend is not end), and holds the Redis transport keys for ~2 hours so a quick reconnect cold-starts from live Redis rather than the checkpoint.

The presence re-read is the guarantee; the cancel is only an optimization — a player can reconnect during the grace window and the cancel can race the fire (the job transitioning delayed→active just as the cancel's remove lands), and BullMQ's jobId-dedup can in principle leave a phantom job. Neither matters: the processor re-reads presence and bails if anyone is connected, so an over-schedule is inert. The handler also fails safe — if countPresence itself throws on disconnect, it schedules the suspend anyway, because the processor's re-read gates the actual suspend. An over-schedule wastes a wakeup; an under-schedule would strand an empty session live forever.
The checkpoint target is a documented overload, pending a real column — the sessions table has no dedicated checkpoint column yet, and adding one is a schema migration this transport task didn't own. So the checkpoint writes a self-describing { kind: 'myt65-checkpoint', maxSeq, state } envelope into the existing st_running_summary TEXT column through repo.sessions.update. The kind discriminator lets a future reader tell a MYT-65 checkpoint apart from any other use of the column. The maxSeq recorded is the durable MAX(session_messages.seq) — never the raw :seq counter (which sits one ahead between INCR and the row insert) — so a crash-recovery reseed never re-hands-out a number a message already used. A dedicated session_checkpoints row is the long-term home. The envelope's kind bumped to myt69-checkpoint when the turn flush shrank to usage-only, so the recovery reader fails loud on the old shape rather than reading a stale flush contract.
The active-session route returns a response allowlist — the summary must not leak — the checkpoint folds the running summary into sessions.st_running_summary, and GET /api/sessions/:campaignId/active used to return the full mapped Session row — that column included — to any campaign member. Inert while the summary was an empty stub, but the moment the Slow Thinker writes rapport and reveal-ladder state into it (MYT-69), a member could read secret-adjacent narrative state with one REST call after any suspend. So the route now returns an explicit allowlist (id / status / sessionNumber / timestamps — never stRunningSummary or any checkpoint material), pinned by a route test. The persist into the column stays — it is the crash-recovery cold-start input; the fix is at the read boundary, not the write.

The wire contract scope

contract/session-events.ts is the declarative wire contract — a client-frame allowlist, a server-frame allowlist, and discriminated-union payload types per direction, mirroring pipeline-events.ts. MYT-65 shipped the player-chat-and-presence subset. MYT-66 adds the first DM-turn frames as server → client only: dm_thinking, text_delta, turn_end, and turn_error, each carrying a turnId and no seq. The turn worker publishes them; this transport's hub fans them out. MYT-67 adds one client → server frame, dm_invoke (the explicit "@DM button" summon, no payload fields) — and deliberately adds no server frame: the trigger decision rides a dev-only structured log, never the player transport, because the hub fans every published frame to all sockets with no audience filter and a dm_trigger frame would leak the classifier's reasoning to players (see DM trigger). MYT-68 adds the DM-turn mechanical frames the FT tool loop emits — skill_check and dice_roll (server → client), live-streamed during a turn with no seq and replayed from the persisted rows on reconnect (then carrying the row seq), plus dm_message, a replay-only frame for the consolidated DM prose row (live prose streams as text_delta). MYT-70 adds one more server → client frame, ledger_update — the Rules Lawyer's character-sheet delta, one flat member whose kind discriminates which post-mutation value fields are populated, on the same live-then-replayed lifecycle as the mechanical frames. The rest — combat_*, session_end, st_evaluation, scribe_result, and the rest — is still deliberately absent until its surface is built.

The contract grows only as handlers ship, so unbuilt frames can't be broadcast — the classifyClientFrame tripwire rejects any client frame type not in CLIENT_FRAME_TYPES at the transport boundary. The server-frame allowlist plays the same role on the outbound side: a frame type is added only when something produces it. MYT-66 added the four DM-turn streaming frames and MYT-68 the mechanical frames precisely because the turn worker now produces them. roll_complete is deliberately not added to the client allowlist — no server handler consumes it yet; it lands with the frontend roll-animation issue. Adding it early would make the transport accept a frame nothing handles. Same structural-gate discipline the pipeline subscriber uses (ZFC structural exception — not LLM cognition).
Roll-reveal gating is client-side, not a server-held buffer — the worker emits the skill_check / dice_roll frame then the dependent narration deltas, in order; the frontend (a later milestone) plays the dice animation and reveals the buffered narration locally. This is a deliberate amendment to the earlier server-synchronized-reveal model: a cross-process session lock cannot be held pending a human animation ack without stalling the worker and the queue. The tradeoff is that reveal timing becomes per-client — the roll result is identical for everyone (resolved once, deterministically); only the animation beat desyncs — and turn_end now fires at model speed, before a client finishes animating.

Operating this piece

Trace a failed WS upgrade

  1. The HTTP status on the rejected handshake discriminates the cause: 401 ws_ticket_missing (no ?ticket), 401 ws_ticket_invalid (consumed / expired / unknown ticket), 401 ws_ticket_session_mismatch (ticket minted for a different session), 404 session_not_found, 409 session_not_active, 403 not_campaign_member, or 503 ws_ticket_store_unavailable (transient Redis fault).
  2. A repeating 401 ws_ticket_invalid from one client usually means the SPA isn't minting a fresh ticket per upgrade attempt — tickets are single-use. Confirm the mint route returns 201 just before each upgrade.
  3. A 503 points at ElastiCache. Check for a failover; the ticket consume is a single GETDEL with no retry layer between the handshake and Redis.

Diagnose a session that won't suspend (or suspends too eagerly)

  1. Count live presence keys for the campaign: SCAN for ${MYTHRUN_ENV}:${REGION_PREFIX}:session:{campaignId}:conn:*. A non-empty match means at least one connection is still considered live (or a crashed container's key hasn't lapsed yet — the keys carry a 60-second TTL).
  2. Inspect the delayed suspend job in BullMQ: jobId suspend-{sessionId} on the session-suspend queue. A present delayed job means a suspend is pending; its absence after the last disconnect means either a reconnect cancelled it or it already fired.
  3. The processor logs its observed presence count and whether it suspended. A job that fires and finds presence > 0 bails by design — that's the cancel racing the fire, not a bug.

Read a suspended session's checkpoint

  1. The checkpoint envelope lives in sessions.st_running_summary as JSON with kind: 'myt65-checkpoint'. maxSeq is the durable last-persisted sequence; state is the live :state blob at suspend time.
  2. Suspend leaves status = 'active' — a suspended session is still active, just unoccupied. Do not treat a populated checkpoint as an ended-session signal.

Integration points

Upstream: a player earns the credential on the access control & WS ticket page — POST /api/sessions/:id/ws-ticket mints the single-use ticket this route's handshake consumes. The backend runtime registers @fastify/websocket, constructs the SessionHub (closed in createShutdown before app.close), generates the per-process containerId, and builds the session-suspend BullMQ Worker on a dedicated connection — the same shape as the prep workers, with the mandatory waitFor ping-probe before new Worker(...). The fan-out mirrors the pipeline status SSE subscriber. Durable state lives in sessions, session_messages, and session_participants through the repository layer; see the schema for those tables. The DM-turn pipeline extends the wire contract with the server-streamed turn frames and publishes them through this transport's SessionHub; it also adds the per-turn LLM-tier keys to the session-state module documented here. As of MYT-69 that module's :summary key is owned by the Slow Thinker job (the turn flush is usage-only, and setRunningSummary is the summary's only writer), the ST's spend tracks on a dedicated :usage:st counter summed at every read, and the session-start route resets the spend + summary keys (resetSessionSpend). The DM trigger system hangs off this inbound handler: it observes the typing and message frames here, writes its own trigger-state Redis keys, and reschedules the quiet-window debounce that decides when a DM turn fires — and adds the dm_invoke client frame to the contract.
