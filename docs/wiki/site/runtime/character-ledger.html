Character ledger & the Rules Lawyer

The shared live per-character ledger — HP, spell slots, gold, inventory, limited-feature uses, and conditions, held PG-direct in characters and its satellite tables — and the Rules Lawyer, the deterministic adjudication service that debits and credits it when the Fast Thinker calls a resource tool. Casting a spell decrements a slot; an over-spend is rejected with an authoritative constraint the FT narrates; every applied mutation persists. It is plain code, not an LLM tier: scarce numbers are moved by a guard-predicate UPDATE, never by a model's say-so.

How it fits together

The ledger is the mutable companion to character creation's static sheet. When the character-sheet stage finalizes a PC it seeds the opening balances — gold, a hit-dice pool, caster progression, the SRD-derived spell slots — and from then on the only thing that moves those numbers out of combat is the Rules Lawyer. The FT's tool belt (built by buildFtTools) gained six ledger tools alongside the dice and skill-check tools:

  • cast_spell — spend a slot for a known, prepared spell (cantrips + rituals skip the slot).
  • spend_resource — debit gold, a tracked item, or a limited-feature use.
  • acquire_resource — credit gold or an item the fiction granted.
  • adjust_hp — damage or heal, dice rolled in the resolver.
  • update_condition — apply or clear a 5e condition.
  • take_rest — short or long rest for the whole party.

Each tool's execute delegates to a resolver and returns its result as data; the resolver does the whole job — resolve the actor, run the guarded mutation, write the journal row, and hand back a LedgerResolution. On success the conductor's consume loop emits a ledger_update frame; on a rejection the structured constraint flows back to the model unchanged, and the FT narrates how the attempt falls short — never a frame, never a throw.

PG-direct, not a Redis cache

The ledger lives in Postgres and is read and written directly there. There is no Redis projection of character state to keep coherent — a debit is a single UPDATE against characters (or a satellite table), and the per-turn snapshot the FT sees is a fresh read.

PG-direct over a Redis mirror — the ledger holds money and scarce resources, so it is exactly the kind of state where a stale cached copy is a correctness bug, not a latency win. The same logic that retired the FT transcript's Redis hot cache applies: there is no fan-out for a cache to serve (the resolver reads its own writes within a turn), and the expensive repeated cost in a turn is LLM tokens, not an indexed row read. Keeping the authoritative numbers in one store means the combat engine and the out-of-combat Rules Lawyer share one source of truth rather than reconciling two.

Binding vs. informational: the rock principle

Every rejection a resolver returns is one of two kinds, and the distinction is the heart of the design. A binding rejection means a scarce, tracked resource was exhausted or insufficient — not enough gold, no castable slot, the spell is known but unprepared, a feature's uses are spent. The constraint is authoritative: the FT narrates how the attempt falls short, the same posture as a failed skill check. An informational miss means there was no row to debit — the named item or feature simply isn't on the sheet. That is non-binding, and the constraint hands the FT a three-branch choice it reasons over.

Scarcity is what makes a constraint binding — the rock is free — a player who picks up a rock to throw should never be told "you don't have a rock." Improvised and environmental objects are narrative, not ledger state, so spend_resource on an absent item returns an informational miss, and the ft-system prompt tells the model: a plausibly-at-hand object → narrate it freely; a thing the transcript shows the fiction already granted → call acquire_resource now, then proceed; a never-established claim → correct the player gently. Only things that genuinely run out — gold, slots, charges, HP — produce a binding rejection. An unknown spell always takes the correction branch: there is no environmental fireball.

The journal is checked first — and that is what makes idempotency safe

Every applied mutation writes one row to ledger_events, an append-only journal keyed uniquely on (turn_id, tool_call_id, character_id), in the same transaction as the mutation. The shared helper applyWithJournal opens that transaction and, before touching any mutable column, asks the journal whether this exact tool call already committed (findLedgerEvent). If it has, the resolver short-circuits to a replay builder that reports the current post-mutation state and mutates nothing.

Check the journal FIRST, not the journal's ON CONFLICT alone — the obvious idempotency design is "write the mutation, let the journal's unique constraint reject the duplicate." It double-spends. A BullMQ redelivery of an in-flight turn job would re-run the guarded debit, and the debit commits before the journal's ON CONFLICT can fire — two slots gone for one cast. Checking the journal as the first statement inside the transaction makes a replay a true no-op: it returns the current state and never re-runs the guard. The ON CONFLICT DO NOTHING on the journal write remains as the belt-and-suspenders backstop.

The resolvers are total: every game-rule failure arm returns a structured constraint rather than throwing. An uncaught throw would surface to the SDK as a tool-error part the FT loop continues past — letting the model narrate an outcome that no adjudication produced, a Principle #4/#5 violation. Infrastructure failures (Postgres down, a transaction throw) follow the skill-check fail-soft precedent: a generic "could not be resolved" constraint that tells the FT not to narrate a definite outcome, logged for the operator.

Guard-predicate writes: rowcount is the adjudication

The LedgerOps projection (charactersLedgerNs, a sibling binder composed into repo.characters) is where the scarce-resource discipline lives. Every debit is a single guard-predicate statement — UPDATE … SET col = col - $n WHERE id = $1 AND col >= $n RETURNING col. A returned row means the debit applied; zero rows means the guard failed, which is the rejection. There is no SELECT-then-UPDATE anywhere on the success path: the check and the write are one atomic statement, so two concurrent debits can't both read "enough" and both spend. The credit side is a single ON CONFLICT upsert against the functional name index.

One guard statement, not read-then-write — a SELECT balance followed by a decision followed by an UPDATE is the classic TOCTOU race; it is the same trap the credit ledger avoids by locking the user row. Here the guard predicate is the lock: Postgres evaluates col >= $n and the decrement in one statement under the row's write lock, so rowcount-0 is a serialized rejection, not a lost-update. The one extra read on the rejection path (to report the current balance in the binding constraint) never runs on the success path.

Two cross-cutting invariants are pinned to single owners so inlined copies can't drift. The §5a HP↔unconscious pair — clamping HP to [0, max] and syncing the HP-derived unconscious condition (apply at 0, clear above 0) — runs through one helper, applyHpAndSyncUnconscious, that adjust_hp, the short-rest heal, and the long-rest restore all call. Clearing unconscious by hand while a character sits at 0 HP is a binding rejection: the condition is HP-derived; heal them first.

Dice are rolled inside the resolver

When adjust_hp takes a dice expression ("2d4+2") or a short rest spends hit dice, the numbers are rolled by the deterministic dice engine inside the resolver — never invented by the model (Principle #4). The dice expression is parsed by a structural regex (mechanical computation, ZFC-exempt), rolled over crypto.randomInt, and the rolled faces ride the payload so the FT can narrate the specific result.

Prep co-evolution: the ledger is seeded, structured, and de-duplicated at creation

The Rules Lawyer can only debit what character creation laid down coherently, so the character-sheet stage grew to emit the ledger's structure. The schema now asks the model for starting_gold, a hit_die size, a spellcasting_progression enum (full | half | third | pact | none), and per-row flags: consumable on equipment, ritual on spells, a max_uses + recharge pair on limited features. Spell slots are not asked of the model — code derives them from (progression, level) against the SRD slot tables in spell-slots.ts and writes the full per-level rows at finalize.

The model emits structure; code derives the slots (ZFC) — the free-text class name is never string-matched. The model makes one bounded judgment — which of five progression archetypes this character is — and the deterministic SRD tables turn (progression, level) into the slot grid. A generated sheet that is Zod-valid but mechanically incoherent (a level-9 spell on a level-1 caster) is caught by a coherence check that triggers a full regeneration, up to a bounded number of attempts, then terminal-fails loud rather than persisting a brickable character.
The prepared pin means "currently castable," not "uses the prepare mechanic" — the Rules Lawyer keys casting on prepared, so the prep prompt is explicit that a sorcerer (which never "prepares") must emit all known leveled spells as prepared: true. Emitting them false because "sorcerers don't prepare" would brick every leveled cast. Prepare-casters emit a sensible daily list; cantrips are always castable regardless of the flag.
Dedupe-merge before insert, because the name index is the mutation key — the Rules Lawyer matches items, features, and spells by normalized name, so migration 025 puts a unique index on (character_id, lower(btrim(name))). That index is load-bearing: a debit UPDATE that matched two rows of the same item would read "rowcount 2" as success while only the guard intended one, and the acquire upsert would have no conflict target. So prep mechanically dedupe-merges the model's output first — equipment stacks SUM quantities, features and spells keep-first — so an LLM duplicate can't terminal-fail the insert or corrupt the debit math.

The party-ledger snapshot: numbers AND nouns

Once per turn the worker reads readPartyLedgerSnapshot — every session participant's full mechanical state — and the Fast Thinker renders it as a [Party ledger: …] tail message: HP, hit dice, gold, the slot ledger, active conditions, tracked features with uses, spells grouped by level with castable/ritual flags, and the full equipment list with consumables flagged.

The nouns are the showstopper, not a nicety — an early shape carried only the numbers (HP, gold, slot counts). That silently breaks the tools: the FT can't call cast_spell("fear spell") or spend_resource on an item it can't name, so slot enforcement never engages and the player's paraphrase has nothing to resolve against. The snapshot therefore lists the canonical names, and the prompt tells the model to reuse them exactly. The block is turn-start state: within a turn the tool-result payloads are the live truth, not this tail.
The snapshot rides after the cache breakpoints, before the standing directive — like the standing directive, the ledger tail is a render-only message appended after the FT's per-message cache breakpoints, so it sits in the always-uncached zone and never perturbs the cached prefix or shifts the sliding-breakpoint index. The merge order (ledger tail, then directive tail) is pinned. It is never persisted to the transcript and never pushed into the FT history.

The frame and its replay

A successful mutation emits a ledger_update frame — one flat wire member whose kind discriminates which value fields are populated (hp+maxHp, slotLevel+ slotsRemaining, and so on), plus an always-present human-readable summary. It is persisted as one of six DM-turn row types (one per tool) by the transcript codec and live-streamed during the turn (no seq). On reconnect the transport rebuilds the frame from the persisted row's stored LedgerResolution.

A persisted ok:false row replays as nothing — silently — a rejection is real adjudication and is journaled, but it produced no player-visible state change, so the reconnect path skips it with no warning. A take_rest row, by contrast, carries an array payload (one entry per character) and replays as one frame each. Only a genuinely corrupt row warns; an expected rejection is not a corruption.

Operating this piece

Drive a ledger mutation end-to-end

  1. Bring up the data plane and both processes (pnpm db:up, pnpm dev, the worker), start a session, and open a WebSocket — the same setup as firing a DM turn.
  2. Drive a turn whose prose warrants a cast or a spend (e.g. a player declares they cast a known, prepared leveled spell). Watch for a ledger_update frame on the socket alongside the text_delta stream.
  3. Confirm the mutation is durable: SELECT slots_remaining FROM character_spell_slots WHERE character_id = '<id>' shows the decremented slot, and SELECT tool, delta FROM ledger_events WHERE turn_id = '<turnId>' shows the journal row.
  4. To see a binding rejection, drive an over-spend (cast with no slot left, spend more gold than the character has). Expect no ledger_update frame and FT prose that narrates the shortfall — the constraint is the outcome.

Integration points

The Rules Lawyer is invoked entirely through the Fast Thinker's tool belt — buildFtTools wires the six ledger tools beside the dice and skill-check tools, threading the scoped LedgerOps surface and a per-turn transaction runner from the turn worker. The repository layer owns the LedgerOps binder (characters-ledger.ts, composed into repo.characters); the migration that adds the ledger substrate is 025. The opening balances are seeded by character creation's sheet stage, whose schema and prompt co-evolved to emit the ledger's structure. The ledger_update frame joins the mechanical frames on the transport's wire contract and replays from the persisted DM rows. The same per-character state is the contract the combat engine (later) shares.
