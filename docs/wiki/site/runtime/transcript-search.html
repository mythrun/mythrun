Transcript search

A player-facing lookback over the campaign's play transcript — "what did Bram say about the ledger," "what happened with the harbourmaster" — answered by Postgres full-text search over the prose-bearing session_messages rows, relevance-ranked, with a highlighted snippet per hit. It is a sibling player-read surface to the campaign wiki, but a different corpus: the wiki reads canon at the known tier; search reads the raw transcript, which is public by construction.

How it fits together

The transcript is the session_messages log the session transport writes — every player line and every Fast-Thinker narration row, in seq order, across all of a campaign's sessions. Search is a single member-readable route, GET /api/campaigns/:campaignId/transcript/search in routes/campaigns.ts, backed by one repo read, searchTranscript in repo/transcript-search.ts, over a full-text index added in migration 029. There is no AI in the path: the player's raw query is parsed mechanically and matched against a Postgres tsvector. The diagram traces the whole request — the member, the route's auth-and-parse, the FTS read against the index, the speaker attribution, and the shaped result.

Full-text search, not embeddings — the canon retrieval stack already runs Voyage embeddings + pgvector, so the obvious move is to reuse it for the transcript. But the transcript is the largest corpus in the system (thousands of prose rows per campaign, growing every turn), and the use case is literal recall — a name, an item, a place, a line someone said. Postgres FTS answers that exactly, with no per-message embedding cost and no embedding pipeline to run on the hot append path. Semantic transcript search is a documented later enhancement, not a v1 gap; the canon stack stays embeddings-based because canon retrieval is a semantic-similarity problem, and the transcript search is not.

The corpus is the prose-bearing rows only

session_messages holds two shapes of row. The prose-bearing types — Fast-Thinker narration (dm_text) and player messages (player_message) — store human-readable text. The mechanical types (skill_check, dice_roll, world_fact_lookup, and the party-ledger tool rows) store JSON.stringify blobs — a tool call's input and output, not prose. Search indexes and returns only the prose-bearing types; a constant SEARCHABLE_MESSAGE_TYPES in the repo names them.

Why the mechanical JSON rows are excluded — indexing a JSON blob would tokenize field names and UUIDs as spurious match terms, and a hit would return an un-renderable highlighted-JSON snippet — the opposite of a "what did X say" lookback. Nothing is lost: the readable narration of a roll or a ledger change already lives in the adjacent dm_text prose, which is indexed. So the exclusion keeps the index lean and guarantees every returned content and snippet is human-readable.

This exclusion is enforced in two places that must stay in lockstep: migration 029's partial GIN index carries a WHERE message_type IN ('dm_text', 'player_message') predicate, and the query repeats the same literal in its WHERE. The literal is duplicated deliberately — a parameterised = ANY($n) would not match the partial-index predicate, so the planner would fall back to a sequential scan. A repo test EXPLAINs the query and asserts a bitmap index scan on idx_session_messages_content_tsv, pinning the coupling so a drift surfaces as a failing test rather than a production latency cliff.

The index: a generated tsvector column

Migration 029 adds a content_tsv tsvector column to session_messages, GENERATED ALWAYS AS (to_tsvector('english', content)) STORED. Postgres maintains it on insert, so there is no application write-path change — append and appendDmTurn are untouched. The 'english' config stems and tokenizes prose; proper nouns ("Bram", "the Obsidian Cabal") tokenize fine. A partial GIN index over the column, restricted to the prose-bearing rows, answers the membership predicate.

A STORED generated column, not a trigger or an application write — the transcript is append-only, so a generated-stored column carries no update churn: each row's content_tsv is computed once at insert and never recomputed. A trigger would be more machinery for the same result, and computing the tsvector in application code would put it on the hot append path the transport keeps lean. The migration lands pre-launch against an empty table, so the column add (a full table rewrite) and the GIN build are effectively free; the spec notes that a comparable column-add against a populated production table would need an online backfill instead — this in-transaction form is safe only because the table is empty here.

The read: rank, paginate, then highlight

searchTranscript is one SQL statement. It binds websearch_to_tsquery('english', $q) once through a CROSS JOIN LATERAL row source, joins sessions to scope by campaign_id and surface the session_number, filters to the prose-bearing rows that match the query, ranks by ts_rank, and paginates. The expensive ts_headline snippet — the <mark>-wrapped highlight that shows why a row matched — is computed in an outer query over the already-paginated inner result, so it runs only for the rows actually returned, never for the full match set.

The ORDER BY is a total order, or pagination silently corrupts — appendDmTurn writes every row of one DM turn in a single multi-VALUES INSERT, so those rows share one created_at; equal-length terse rows tie on ts_rank to the digit. rank DESC, created_at DESC alone is therefore not a total order, and LIMIT/OFFSET over a non-total order can skip or duplicate rows across pages. Adding session_id, seq DESC — the (session_id, seq) pair is unique — makes the sort total, so paging through with increasing offset returns every row exactly once. The inner query ranks-filters-paginates and the outer re-applies the same total order before adding the headline.

Search is campaign-wide by default — "what happened with the harbourmaster" spans sessions — with an optional sessionId to narrow to one session's in-session lookback. It intentionally ignores sessions.status: an ended or crashed session's transcript is part of "the story so far" and stays searchable. (That differs from the WebSocket connect path, which gates on status = 'active' — the lookback has no such gate.)

Parsing the query is mechanical retrieval, not cognition (ZFC) — websearch_to_tsquery handles phrases ("obsidian cabal"), exclusions (-term), and or from the player's raw string, mechanically. Search is structural retrieval — the same Zero Framework Cognition mechanical-computation exception as dice math or movement ranges — so there is no Haiku query-reformulation step. It also means no fuzzy or prefix matching: a partial name or a misspelling returns nothing, which is the accepted literal-recall v1 scope (consistent with the embeddings deferral).

Speaker attribution is shared with the replay path

A hit's raw user_id is not useful to a player — they want a name. The route resolves each hit to a speaker through resolveSpeaker in session/attribution.ts, the one source of truth for "who said it," built once from the campaign's userId → character name map (characters.listForCampaign). Because the corpus is now dm_text + player_message only, there are exactly three cases:

  • a null user_id (a DM-authored dm_text row) → "DM";
  • a user_id present in the map (a player_message from an active member) → the speaking character's name;
  • a user_id absent from the map — a player who has since left the campaign, so they dropped out of listForCampaign — → the "Former player" placeholder.
A departed author is "Former player," never "DM" — collapsing a departed player's line into "DM" is a "who said it" mis-attribution: it would put words in the Dungeon Master's mouth that a player actually said. The DEPARTED_AUTHOR_NAME constant was already the WebSocket reconnect replay's fallback byline; MYT-74d extracted resolveSpeaker into session/attribution.ts so both the replay path and search resolve speakers through one tested helper rather than two parallel copies (the ws-session.ts change was a behaviour-preserving import swap).

Enforced ignorance: nothing to tier-filter

The campaign wiki is a carefully tier-gated read — it must filter to known canon and drop every secret. Transcript search has no such filter, and deliberately so: the transcript corpus is public by construction. The Fast Thinker operates under enforced ignorance and never narrates a secret; the Slow Thinker's sanctioned reveals are public the moment they are narrated; and the [[DM CORRECTION:]] marker that buries a leak is an FT input direction that never persists into the FT's output content (the persisted row is the rendered retcon prose). There is no access_level on session_messages, and the debug Slow-Thinker / Scribe streams are not in the table at all. So search has nothing it could leak.

The one real guard is the campaign join — the surface this read does introduce is cross-campaign bleed, and it is closed structurally: the s.campaign_id = $1 join restricts every result to the caller's own campaign, and requireCampaignMember proves the caller is a member of it. A sessionId that belongs to another campaign, passed with this campaign's id, returns zero rows — the AND-ed predicates can only narrow within the campaign. There is no tier-bypass parameter on the route, because there is no tier to widen. Two defense-in-depth repo tests pin the property the feature rests on: the prose-only corpus (a mechanical JSON row is never returned) and a correction-derived row (it returns the player-facing retcon prose, never the literal marker).

Operating this piece

Run a transcript search by hand

  1. As a campaign member, call GET /api/campaigns/:campaignId/transcript/search?q=harbourmaster. The response is { hits, query, limit, offset }; each hit carries a speaker, a <mark>-highlighted snippet, the full content, and the locators sessionNumber / sessionId / seq / createdAt.
  2. Narrow to one session by adding &sessionId=<uuid>; page with &limit= (≤ 50) and &offset= (≤ 500). An empty or whitespace-only q returns 400 invalid_query; a non-member returns 403; a fresh campaign with no sessions returns 200 { hits: [] }, not an error.

Confirm a search uses the partial index

  1. If campaign-wide search ever feels slow, the first check is whether the query is hitting the partial GIN index. EXPLAIN the search SQL and confirm a Bitmap Index Scan on idx_session_messages_content_tsv — a sequential scan means the repo's message_type literal has drifted from migration 029's partial-index predicate.
  2. The repo's EXPLAIN test exists to catch exactly this in CI; a red one points at the lockstep between SEARCHABLE_MESSAGE_TYPES and the migration's WHERE.

Integration points

The corpus is the session_messages transcript the session transport writes through persist-then-broadcast; the content_tsv column and its partial GIN index are on the schema (migration 029). Speaker attribution shares the resolveSpeaker helper with the transport's reconnect-replay byline. This is a sibling player-read surface to the campaign wiki — both are member-readable, campaign-scoped, per-user rate-limited routes in routes/campaigns.ts with no dev-tool panel (each sits in the dev-tool contract's EXEMPT_ROUTES) — but search reads the raw transcript, not promoted canon, so unlike the wiki it is not a pipeline route and has no stage gate. The read goes through the repository layer's new transcriptSearch namespace. The search box itself is a Frontend ticket; 74d is the data and API layer.

Appendix: surface

The route (GET /api/campaigns/:campaignId/transcript/search)

Facet Value
Auth requireCampaignMember(repo) — any party member.
Querystring q (required, trimmed-non-empty → else 400 invalid_query); sessionId? (uuid); limit? (default 20, ≤ 50); offset? (default 0, ≤ 500).
Rate limit 30/min, keyed per-user (IP fallback) — heavier than the 60/min member polls (an O(matches) rank-sort plus a per-returned-row ts_headline).
Response 200 { hits, query, limit, offset }; each hit is { sessionId, sessionNumber, seq, messageType, speaker, content, snippet, createdAt }. 400 invalid_query · 403 (non-member).
Contract In contract/backend-routes.ts and the dev-tool verify-registry.ts EXEMPT_ROUTES. Not in dev-tool/coverage.json or pipeline-routes.ts — those are pipeline-only, and this is not a pipeline route.

The hit (TranscriptHit → shaped wire result)

Field Source
speaker resolveSpeaker(userId, map) — "DM" / character name / "Former player". The raw userId is dropped at the route.
snippet ts_headline highlight — <mark>…</mark>, up to 2 fragments, computed only for the returned page.
content The full prose row (always human-readable — mechanical JSON rows are not in the corpus).
sessionNumber / sessionId / seq / createdAt Locators — the UI jumps to full context via the existing message replay on click.

Storage (migration 029)

Object Shape
session_messages.content_tsv tsvector GENERATED ALWAYS AS (to_tsvector('english', content)) STORED — auto-maintained, no app write path.
idx_session_messages_content_tsv Partial GIN over content_tsv, WHERE message_type IN ('dm_text', 'player_message') — in lockstep with SEARCHABLE_MESSAGE_TYPES.
