World gen

The campaign-scoped world-generation pipeline. POST /api/campaigns validates a concept (two creation modes — freeform prose or three guided picks synthesized by Sonnet), runs a 3-axis Sonnet input gate, debits one world_gen credit inside an advisory-locked transaction, and enqueues a BullMQ job. The worker walks seven stages — three non-streaming Sonnet calls (concept_intake, starting_situation, random_tables), three streaming stages with live entity emission (world_and_factions Opus, locations_and_npcs Opus, entity_relationships Sonnet), and a final non-streaming Sonnet coherence_pass. A non-streaming Sonnet vocabulary_intake stage runs between concept_intake and world_and_factions — it generates the world's distinctive lexicon (the vocabulary registry) and every downstream stage injects the rendered registry into its system prompt. After stage 4 commits the pipeline fires a world_snapshot_ready phase; the persisted world becomes fetchable through GET /api/campaigns/:campaignId/world-snapshot while stages 5–7 are still running, and stage 7's edits flow on the same SSE channel as post-snapshot deltas. Each stage handler returns a unified StageDispatchResult { costUsd, tokens, finalizedEvents, capExhausted }; the outer scope owns BEGIN/COMMIT and publishes the finalized events only after COMMIT. A cost-cap circuit breaker reads settings.world_gen_cost_cap_usd at the start of each stage; over-cap refunds the credit and marks the world failed — except at stage 7, where cap-fire marks the world COMPLETE (coherence is best-effort polish).

How it fits together

Seven routes form the consumption surface — all under /api/campaigns, all listed in the PIPELINE_ROUTES contract so the boot-time enforcer keeps the dev tool, the route registrations, and the contract honest in lockstep. POST /api/campaigns is the create flow described above. GET /api/campaigns/:campaignId returns the campaign row, the world row, and the member list for a campaign the caller is a member of. GET /api/campaigns/mine lists every campaign the caller created or joined. POST /api/campaigns/:campaignId/resume is the recovery surface: a polymorphic switch over the nine phases derivePhase reports (see pipeline status) that re-enqueues, 409s, or 422s depending on where the pipeline got stuck. DELETE /api/campaigns/:campaignId is the hard-delete cleanup path — owner-only, refuses while generating, cascades through the FK chain to remove the world + every dependent row. PATCH /api/campaigns/:campaignId/name is the rename path for owners: concept_intake auto-names the campaign from the LLM-synthesized world name, and this is how the owner overrides that default. GET /api/campaigns/:campaignId/world-snapshot is the owner-only known-tier view of the persisted world, fetchable once the new world_snapshot_ready phase has fired (after stage 4 commits).

Campaign-id is the user-facing handle, not world-id — a campaign owns at most one world, but the user always interacts with the campaign (its name, its membership, its session history). World-id is an internal join key. The route surface, the status SSE channel (pipeline:campaign:{campaignId}), and the BullMQ jobId all key on campaignId; the 201 response from the create flow returns only campaignId. The create transaction seeds a pipeline_runs row keyed on world_id + stage = 'concept_intake' with status = 'pending' so a Redis blip between COMMIT and queue.add presents as world_gen_failed via the existing derivePhase rules instead of not_started, which the resume route's world_gen_failed arm can recover from cleanly.

The body shape is discriminated from day one. The outer discriminator is kind with one functional arm ('new') and a future arm reserved for joining an existing world (not stubbed at launch — an unknown kind produces a standard 400 from Zod, not 501). Inside kind: 'new', an inner discriminator on source.mode selects either 'freeform' (a 20–4000-character free-text concept) or 'guided' (exactly three { title, whyILikeIt } picks the user assembled in a chooser UI). The synthesizer fires only in the guided arm; both arms then converge on the input gate. The body carries no campaign name — concept_intake auto-names the world (and propagates that name to the campaign), and the owner overrides later via PATCH /api/campaigns/:campaignId/name.

Per-user rate-limit on POST + resume, per-IP on the GETs — the writes are tied to cost (an LLM call, a queue add) and the abuse shape is per-identity. The reads are cheap and a shared NAT (corporate VPN, lab network) might legitimately have several active users; per-IP ceilings are enough there.

The pre-credit validation pipeline

Five pre-checks fire BEFORE the create transaction, in cheap-to-expensive order. Concurrent-gen guard (one Postgres query) rejects with 409 if the caller already has a world in status = 'generating'. Rejection-storm cooldown (one Redis GET) rejects with 429 if the user has been rejected by the input gate more than three times in the past hour. Credit balance peek (one Postgres SUM, no lock) rejects with 403 if the world_gen balance is < 1. Queue-depth admission (one BullMQ getJobCounts) rejects with 503 if waiting + active + delayed exceeds 20.

Cheap checks first, LLM calls last — every gate that can run without an LLM call runs first, so an adversarial caller burning rejection-storm credits or hammering the queue can't drive Sonnet cost. The synthesizer (guided mode only — one Sonnet call) and the input gate (one Sonnet call, always) run after every cheap rejection path has had a chance to short-circuit.

Then the synthesizer fires if the body is guided-mode. It's one generateText call with temperature: 0.9 against the prompt template at backend/src/llm/prompts/prep/synthesize-concept.txt, structured-output against the SynthesizerOutput schema: { concept: string, intentSummary: { aesthetics[], themes[], sourcesInternal[] } }. The concept field is what the input gate (and later stages) see as the user's freeform-equivalent input; intentSummary is the structured trace of what aesthetic / thematic moves the synthesizer made. sourcesInternal is the synthesizer's list of works it drew from — opaque downstream, never echoed to the user, never appended to concept_intake's prompt; the input gate DOES receive it so clone-intent judgement isn't bypassed via prompt injection in the user's picks.

The input gate is a single Sonnet call against three axes — srd_compat (does this fit D&D 5e SRD-compatible mechanics?), clone_intent (is this a recognizable intellectual-property clone?), inappropriate (does this trip the content-safety policy?). Each axis returns a boolean and (where the model is calibrated to it) a confidence score on [0, 1]. The verdict is computed in TypeScript from the structured output, not prose-matched:

  • Primary threshold (0.85) — any axis flag with confidence above this rejects on that axis alone.
  • Aggregate rule (≥ 0.7 on both srd_compat AND clone_intent) — two near-miss signals together reject as srd_incompat. Catches the "borderline-on-each-axis but obviously off-spec when read together" case the per-axis check would otherwise pass.
  • inappropriate is treated as a binary flag with no confidence threshold — when set, rejection is unconditional.
Verdict logic in code, not in the prompt — having the model emit per-axis signals and computing the rejection rule in TypeScript means the rule is testable, auditable, and changeable without re-tuning a prompt. The model's job is to score; the policy lives in code.

On rejection, the route increments the rejection-storm counter, logs the model's reasoning server-side (never returned in the HTTP response — leaking it would let an adversary iterate against the gate's reasoning), and returns 422 with { code: 'concept_rejected', reason, rejectionMessage }. Guided-mode rejections additionally include synthesizedConcept in the response so the user can see exactly what the synthesizer produced before the gate rejected it.

The paint-job validator

Stage 1 (concept_intake) wraps its generator call in validateAndGenerateConcept — a judge-and-retry loop in backend/src/llm/prep/paint-job-validator.ts. For each attempt: one Sonnet call generates a structured WorldConcept; a SECOND Sonnet call (distinct prompt, fresh context, temperature: 0.1) judges whether the draft mirrors a recognizable copyrighted work; on flag (confidence > 0.85), the loop discards the draft entirely and retries with a fresh-direction amendment built from the judge's structured { mirroredWork, specificDriftAxes } output, plus a temperature bump to 1.0. Max 3 attempts total (1 original + 2 retries). On exhaustion the loop throws PaintJobLoopExhaustedError, which the worker treats as a stage failure.

Distinct judge prompt, not a self-check — the SDK's structured-output retry policy is set to maxRetries: 1 on the inner generator call so the SDK's policy and the validator's outer loop don't multiply into 12 worst-case Sonnet calls. The validator is the sole retry authority. The judge is a fresh Sonnet call (separate prompt template, separate context) because asking the same model to grade its own output produces measurably worse calibration than asking a fresh instance.

The credit gate transaction

Once the input gate allows the concept, the route opens a Postgres connection and runs the create transaction. The shape (in order, all inside BEGIN ... COMMIT):

  1. SET LOCAL lock_timeout = '5s' + SET LOCAL statement_timeout = '10s'. Bounds the tx's wall time so a hung lock can't pin a pool connection.
  2. pg_advisory_xact_lock(hashtextextended(userId::text, 0)). Serializes per-user create attempts so concurrent calls can't double-spend a credit. hashtextextended sidesteps pg's lack of a direct uuid→bigint cast.
  3. Re-read the world_gen balance under lock. If < 1, ROLLBACK + 403 — the peek at step 2d above was an optimization, not a guarantee.
  4. INSERT worlds (status = 'generating', name = 'Untitled'), INSERT campaigns (status = 'setup', name = 'Untitled'), INSERT campaign_members (role = 'owner', invite_accepted = true). The create body never carries a name; stage 1 (concept_intake) backfills both worlds.name and campaigns.name from the LLM-synthesized world name once it lands (UPDATE campaigns SET name = $2 WHERE world_id = $1 AND name = 'Untitled', which keeps an in-flight user rename from being clobbered). Users override later via PATCH /api/campaigns/:campaignId/name.
  5. INSERT credit_ledger — a -1 debit. source_type = 'debit', source_id = worldId (satisfies migration 004's credit_ledger_debit_has_source_chk), both FK columns NULL.
  6. Seed pipeline_runs (stage = 'concept_intake', status = 'pending', started_at = NULL). The seed row is what makes the Redis-blip recovery path work — see the resume table below.
  7. COMMIT.

After commit, the route resets the rejection-storm counter (a user who proves they can produce a passing concept gets a clean slate), calls worldGenQueue.add('world-gen', { campaignId }, { jobId: campaignId }), and returns 201 { campaignId }.

BullMQ job options are the load-bearing operational contract — the world-gen queue is constructed with attempts: 2 + backoff: { type: 'exponential', delay: 30000 } + removeOnComplete: { count: 0 } + removeOnFail: { count: 0 } in server.ts's buildWorldGenQueue. The two retries are what makes every "BullMQ retries the stage" recovery path in the §7.2 error matrix real rather than fictional — without attempts: 2, transient Anthropic 503s or persistence-COMMIT failures would surface as terminal stage failures instead of self-healing. The removeOn*: { count: 0 } pair prunes terminal jobs so the resume flow's queue.add with { jobId: campaignId } doesn't silently no-op on a previously-completed run.

The seven stages

The processor in backend/src/llm/prep/world-gen-processor.ts runs on the worker service at concurrency 3. WORLD_GEN_STAGES is the ordered tuple concept_intake, vocabulary_intake, world_and_factions, locations_and_npcs, entity_relationships, starting_situation, random_tables, coherence_pass. The list grew by one entry — vocabulary_intake is the new stage 1.5 that generates the per-world vocabulary registry before any downstream prose-bearing stage runs. Counting prose continues to call the streaming Opus + Sonnet block "the seven stages" because vocabulary_intake is a structured pre-pass with no entity emission; section headings and the cost-cap discussion treat it as a cheap setup call. Every iteration enforces the same per-stage invariant:

  1. Atomic claim. An INSERT … ON CONFLICT (...) DO UPDATE … WHERE pipeline_runs.status IN ('pending', 'failed') RETURNING id either creates the row or flips a pending/failed row to running. If RETURNING is empty, another worker won the race OR the row is already completed — skip the stage in either case. The unique index keys on (COALESCE(world_id, campaign_id), stage, COALESCE(user_id, sentinel)); world-gen rows have user_id = NULL.
  2. Stuck-stage reset. If the conflict branch found a running row, the processor tries an UPDATE-with-WHERE on (status = 'running' AND started_at < now() - INTERVAL '5 minutes'). Zero rows affected means another worker raced and won the reset; this worker bails.
  3. runStage wraps the handler in BEGIN/COMMIT. The outer scope acquires a PoolClient, runs BEGIN, dispatches to the per-stage handler, and on success COMMITs and publishes every event in the handler's returned finalizedEvents array. On handler throw it runs ROLLBACK and publishes stage-reset — the signal that any mid-flight entity-added / entity-updated events for this stage are invalidated.
  4. Cost-cap check. After the COMMIT, sumCompletedStageCosts reads every completed pipeline_runs row for this world; if > cap, issueCostCapRefund fires (refund row + worlds.status='failed') and the loop exits. Stage 7 is the documented exception: if the handler returns capExhausted: true, the world is marked complete instead — coherence is best-effort polish, not a correctness gate.
  5. On stage failure. Write a sanitized error JSON to pipeline_runs.error (strict allowlist — only { code, message } survive; raw provider error chains with embedded API keys or response bodies are dropped) and publish stage-failed. StageNotImplementedError is treated as an expected stop (publish phase = world_gen_failed and return; no BullMQ retry); every other thrown error rethrows so BullMQ's retry policy fires.
Read the cost cap once per stage, not once per job — a long-running world-gen job that started under an old cap and crossed a config-change boundary mid-run should observe the new cap on its next stage. The read is a single Postgres query against the settings table; the cost of ~7 reads per run is negligible against the LLM-call cost inside each stage.

The unified stage-handler contract

Every wave-4 handler — world_and_factions, locations_and_npcs, entity_relationships, coherence_pass — takes (client: PoolClient, args) and returns StageDispatchResult { costUsd, inputTokens, outputTokens, finalizedEvents, capExhausted }. The contract is what lets runStage own the transaction lifecycle from outside the handler: handlers don't BEGIN, they don't COMMIT, they don't ROLLBACK, and they don't publish post-COMMIT events. They write to the passed client and accumulate finalized events; runStage publishes those events only after its COMMIT has landed, so a ROLLBACK on a partially-streamed stage can't leave the client with a finalized event pointing at an entity_id that doesn't exist.

Mid-stream entity events fire from the streaming extractor, not from the handler's return value — entity-added / entity-updated / edge-added are emitted by streaming-extractor.ts as the partial-tree iteration crosses the "entity is emittable" boundary, BEFORE the handler reaches its INSERT phase. Those are speculative — they tell the client "we see a region named Karadon taking shape." If the repair chain exhausts or the persistence COMMIT fails, the outer stage-reset event invalidates them. finalized events are different: they fire only after the persist COMMIT, so they carry the real entityId and the client can trust them. The wire-format split is deliberate.

Legacy stages — concept_intake, starting_situation, random_tables — were authored before the unified contract under a simpler StageCost return type. wrapLegacyStage in the processor lifts each to the new shape by setting finalizedEvents: [] and capExhausted: false. No call-site changes; the contract is uniform downstream.

Vocabulary registry

Every world has a vocabulary registry — a per-world glossary of distinctive terms generated at stage 1.5 (vocabulary_intake) and injected into the system prompt of every downstream world-gen stage. The registry's primary purpose is to give each world its own distinctive voice across whatever vocabulary domains its premise demands (calendar terms, pantheon names, honorifics, in-world slang, named concepts). IP-drift defense (avoiding verbatim use of franchise-iconic neologisms like Statute of Secrecy or Mystra) falls out as a consequence: stage 1.5 identifies which fiction franchises the world is adjacent to and generates the world's own term for each iconic neologism, recording the IP term in the entry's avoids field.

The registry is stored as worlds.vocabulary_registry jsonb with shape {entries: [...], adjacent_franchises: [...]} (migration 015, NOT NULL DEFAULT '{"entries": [], "adjacent_franchises": []}' with a CHECK constraint pinning the top-level shape). Each entry carries {term, definition, avoids?, usage_notes?, source, access_level}. Downstream stages 2-7 render the registry as deterministic prose via renderVocabularyRegistry() and substitute it into a {{vocabularyRegistry}} placeholder at the top of their prompt templates. Anthropic prompt caching keeps the per-stage cost negligible since the registry is stable across a single world's stages.

The GET /api/campaigns/:campaignId/world-snapshot endpoint exposes the registry on the WorldSummary as vocabularyRegistry, filtered by the same access_level tier list as entities and facts: without dev bypass only known-tier entries surface; adjacent_franchises is metadata (not player-secret content) and always surfaces.

A consolidation pass that appends terms surfaced during world-gen and character creation is designed but deferred (bead myth-1uw6). The per-player character-creation pipeline landed in MYT-53 (see Character creation), but the consolidation hook is not yet wired in — that's the deferred bead's scope. The vocabulary registry's data shape, append-only semantics, and source tag on each entry are designed to support both that consolidation pass and a future Scribe runtime write-back.

Streaming stages and the partial-tree iterator

Stages 2, 3, and 4 all share runStreamingStage in streaming-extractor.ts. The LLM emits a JSON tree via Vercel SDK's streamObject; the SDK exposes a partialObjectStream async iterable that yields successive partial tree snapshots as more tokens arrive. The extractor walks each snapshot, looks at the configured arrays (regions + factions for stage 2, locations + npcs for stage 3, relationships for stage 4), and emits exactly one identity-only event per array entry once the LLM has finished writing it:

  • For entity entries (stages 2 + 3), the extractor fires entity-added { synthKey, kind, name } the first time the array length advances past that entry's index — i.e. when the LLM has moved on to the next sibling, which is when the closed entry is in hand. The last entry of each array closes in a post-loop pass after the for await exits.
  • For edge entries (stage 4), the extractor fires edge-added { synthKey, from, to, relationship } on the same closed-entry boundary.
  • Mid-stream entity-updated events do NOT fire from the extractor. Field-level deltas during streaming are NOT on the wire — the client receives an identity-only signal that "an entity with this name and kind is now persisted-bound," nothing more. Prose, facts, and statblocks for the entity arrive through the post-stage-4 snapshot fetch, not through deltas.
Identity-only mid-stream + a known-tier snapshot at stage 4, not field-level deltas — the previous wire format streamed every partial field of every entity as successive entity-updated patches. That meant the client saw plot-bearing prose before the access-tier classification of the entity was even known (the LLM emits access_level as one of the last fields it writes), creating a window where discoverable / secret material could leak through the stream. Narrowing mid-stream to identity only and persisting the body through a tier-filtered snapshot at the stage-4 boundary closes that window: the client never sees a field it isn't entitled to, even transiently, because tier-aware fields don't flow on the wire at all.

Every emitted event carries a synthKey of the form ${stage}/${arrayPath}/${index} — e.g. world_and_factions/regions/2. The synthKey is stable for the duration of the stream and is what the post-COMMIT finalized event uses to bind the speculative key to the real entityId: { type: 'finalized', synthKey, entityId }. The client's inventory reducer (in the dev tool's live-events panel) carries forward the entityId on finalize and lets the dev tool show the real UUID alongside the entity's name once persistence lands.

Closed-entry gate, not "name plus one other field" — the earlier emit gate fired entity-added the moment name and one neighbouring field had been written, then streamed every subsequent field as an entity-updated. After myth-exac the wire format no longer carries entity bodies at all, so the previous trigger would race the access-tier classification (the LLM writes access_level late in the entry) and leak identity for entities that will be filtered out at persistence time. The current gate waits until the LLM has finished the entire entry — detected by the array advancing past that index, or by the post-loop pass for the last entry of each array — at which point access_level is in hand and the tier-filter decision can be made before any byte hits the channel.

Stage 3's three-pass parent resolver

Stage 3 (locations_and_npcs) is the one streaming stage with a non-trivial persistence shape, because location entries have an optional parent_location: string | null field naming their parent — and the LLM names parents by string, not by ID. The handler runs three passes against the caller's transaction:

  1. Pass 1 — insert everything. Walk locations, then NPCs; INSERT each entity, its prose kernel, and its facts. Collect (synthKey, entityId) pairs into a finalized list, and for every location whose parent_location is non-null, collect an unresolved-ref { synthKey, childEntityId, parentName }.
  2. Pass 2 — build a name → entityId map. Query entities.listByWorld, filter to entity_type = 'location', and pick the OLDER entry on name collision (lowest UUIDv7, which is the earlier insert because UUIDv7 is time-ordered). This is the "stage 2 wins on collision" rule from §D8 — if stage 3 names a city the same as a stage-2 region, the region is the parent candidate.
  3. Pass 3 — resolve or null out. For each unresolved ref, look up the parent name. Resolvable → INSERT entity_hierarchy { parent, child }. Unresolvable → collect the synthKey for a post-COMMIT entity-updated { synthKey, patch: { parent_location: null } } event in finalizedEvents. The client sees the parent get cleared only AFTER the row actually lands; if the transaction ROLLBACKs, the patch event never publishes and the client's inventory falls back to whatever stage-reset tells it.
Resolve by name in code, not by ID in the prompt — passing entity UUIDs into the LLM context would let the LLM emit them in the parent_location field. The failure mode is a hallucinated UUID — the LLM invents a plausible-looking ID that doesn't exist in entities, the INSERT fails with an FK violation, the transaction ROLLBACKs. Names are LLM-native: the LLM has seen them in the stage-2 + stage-3 context windows and won't hallucinate them in the same way. The cost is the resolver pass and the "parent we can't find" edge case; the benefit is durability against LLM ID hallucination.

Stage 4's UUID pre-filter

entity_relationships is the one stage that DOES feed entity UUIDs into the prompt — relationships are inherently between identified entities and naming them by string here would create ambiguity stage 3's resolver doesn't have to deal with. The handler loads entities.listByWorld at stage start and renders the inventory as - ${uuid} [${kind}] ${name} lines in the prompt. The LLM is instructed to use real UUIDs only.

The LLM does hallucinate occasionally — emitting a UUID that's plausible-shaped but doesn't exist in the world. The handler defends with a pre-INSERT filter: build a Set<entityId> from the loaded inventory, drop every relationship row whose from or to isn't in the set (WARN-logged but not thrown — it's a known LLM failure mode, dropping doesn't corrupt the world). The same filter applies to any hierarchy-straggler rows stage 4 emits as a fallback for stage 3's misses.

Stage 4 also handles retry idempotency: the very first DB action is relationships.deleteByWorld(client, worldId). If a previous attempt partial-wrote relationships and the stage retried, the next run starts from a clean slate. Stage 3's entity_hierarchy rows are not deleted on retry — the schema's UNIQUE(child_entity_id) means a re-INSERT of the same child would conflict, so stage 4's straggler path pre-filters against the existing hierarchy table and skips already-parented children (the "stage 3 wins" collision rule).

The structured-output repair chain

Every streaming stage validates its final tree with the stage's Zod schema; if validation fails, repairStructuredOutput in structured-output-repair.ts tries to repair it. The chain is fixed: Haiku first, Sonnet if Haiku fails. Each repair call sends the broken tree plus a serialized list of the Zod errors to the model with the prompt template at backend/src/llm/prompts/prep/repair.txt, structured against the same schema. If Sonnet also fails, the stage throws and the outer scope ROLLBACKs + publishes stage-reset; BullMQ's attempts: 2 picks up one more try.

The repair prompt enforces array length and ordering — the repair model is given the broken tree and told to fix shape violations WITHOUT adding or dropping entries from any array. Mythrun has no truth about how many regions a world "should" have; the streaming Opus call is the source of truth on cardinality, and the repair pass is purely about coercing field-level shape to match the schema. A repair that helpfully added a missing region would be invisibly synthesizing world content under Haiku — a quality-degrading silent failure.

Repair costs flow back to the caller through the stage's StageDispatchResult.costUsd: the handler sums (a) the streaming model's reported usage, (b) the Haiku repair call's usage if invoked, and (c) the Sonnet repair call's usage if Haiku failed. The cost lands in pipeline_runs.cost_usd with the same row the stage's success commits, so the cost-cap check sees the total.

Coherence pass and its cap-fire exception

Stage 7 (coherence_pass) is non-streaming Sonnet plus a mechanical apply path. The Sonnet call reads a compact dump of the world (entities, prose, facts, relationships) and returns a list of discriminated-union patches:

  • fix_fact { fact_id, new_content } — UPDATE one facts.content by id.
  • fix_prose { entity_id, new_content } — UPDATE one entity's prose_kernels.content; emits entity-updated.
  • fix_relationship { relationship_id, new_type, new_description } — DELETE the existing row, INSERT a replacement with the new fields. Emits edge-removed + edge-added.
  • rename_entity { entity_id, new_name } — UPDATE entities.name; emits entity-updated { patch: { name } }.
  • delete_relationship { relationship_id } — DELETE one row; emits edge-removed.

There is no drop_entity patch type. Coherence never deletes entities — that would invalidate any prose, fact, or relationship the client has already seen referencing that entity. If coherence references a UUID that doesn't exist (an LLM hallucination), the patch is WARN-logged and skipped silently; other patches in the same batch still apply. The world isn't broken, the LLM was just imprecise.

Cap-fire at stage 7 marks the world complete, not failed — stages 1–6 produce load-bearing content. If the cap fires before stage 6 finishes, the world is missing things the player will notice and the right answer is refund + restart. Stage 7 is best-effort polish: the world functions without it. So coherence-pass.ts checks sumCompletedStageCosts > cap on entry; if true, it returns { capExhausted: true, finalizedEvents: [{ type: 'phase', phase: 'complete' }] } with zero cost. The processor's runStage loop sees the flag, flips worlds.status = 'complete' in lieu of the cap-fire refund, and returns. The trade-off is consistent with the §D5 design intent: the user got a usable world, the cap held, no credit refund was owed.

The cost-cap circuit breaker

backend/src/llm/prep/cost-cap.ts owns three functions: readCostCap(pool) fails loudly on a missing or unparseable settings.world_gen_cost_cap_usd row (a misconfigured cap is an operator-fix, never silently degraded to "no cap"). sumCompletedStageCosts(pool, worldId) sums cost_usd from pipeline_runs where status = 'completed' and user_id IS NULL — running / failed rows don't count toward the cap. issueCostCapRefund(pool, { userId, worldId }) runs a transaction that flips worlds.status = 'failed' and inserts a credit_ledger row with source_type = 'cost_cap_refund', amount = +1, both FK columns NULL.

Migration 011 added 'cost_cap_refund' to the credit_ledger source-type whitelist and the table-level FK-shape CASE. The polarity check from migration 004 — (source_type = 'debit') = (amount < 0) — passes naturally because a refund is positive and not a debit. The resume route's world_gen_failed arm sniffs the latest failed pipeline_runs.error for the string world_gen_cost_cap_exceeded and 409s with code: 'world_gen_capped' instead of re-enqueueing (a re-run would just burn cap again).

Pipeline events on the wire

The processor and its stage handlers publish to {redisKeyPrefix}pipeline:campaign:{campaignId}, the channel format the pipeline status surface listens on. Thirteen event arms are declared in PIPELINE_SSE_EVENTS — six lifecycle arms plus seven entity / edge arms. Every arm is now rendered by the dev tool's live-events panel; the contract has zero exempt entries.

stage-completed After COMMIT, with stage cost and duration. Processor

The snapshot phase and the world-snapshot endpoint

The pipeline ends with three non-streaming stages (5–7) that, in the old shape, finished before any consumer could read the world. Two facts changed with myth-exac: stage 7 (coherence_pass) edits prose and renames entities, so the persisted state isn't fully settled until it finishes; and the dev tool's wiki-style inspector wants the persisted world the moment it's coherent — well before stages 5/6/7 add their finishing touches. Both pull in the same direction: the pipeline now emits a world_snapshot_ready phase the moment stage 4 (entity_relationships) commits.

derivePhase in backend/src/sse/derive-phase.ts returns world_snapshot_ready when the world is still generating but a stage-4 completed row exists; the worker publishes the phase event directly from world-gen-processor.ts immediately after stage 4 commits (and on idempotent re-entry past a completed stage-4 row, so a reconnecting subscriber catches up). Stages 5 + 6 + 7 then continue under this phase. When stage 7 commits and worlds.status flips to complete, the phase advances to world_ready; if the cost cap fires the world ends at complete (stage 7's cap-fire exception) or failed (any earlier stage).

GET /api/campaigns/:campaignId/world-snapshot is the read side. It is owner-only, rate-limited per IP, and serves a 409 snapshot_not_ready until the pre-readiness check (pipelineRunsRepo.isStageCompleted(worldId, 'entity_relationships')) passes. The response is a WorldSnapshot: a WorldSummary projection of the worlds row, the entities, their prose kernels and facts, the relationships among them, the entity hierarchy rows for resolved parents, and stat blocks for entities that have them. Seven read queries — most run in parallel — make up the composition; world-snapshot-view.ts owns it.

An explicit WorldSummary projection, not SELECT * — the worlds table holds plot-bearing columns the Fast Thinker must never see: key_tensions, political_summary, starting_situations, follow_up_questions, geography_summary, world_overview, and (notably) dev_bypass_access_filter. The snapshot view explicitly selects id, name, concept, tone, themes, era, and vocabulary_registry — the registry is the one jsonb column that does cross the wire, with its entries tier-filtered against the same access-level list as entities and facts before they're attached to WorldSummary.vocabularyRegistry. New columns added to the worlds table never reach the wire automatically — adding a column requires authoring a deliberate addition to the projection. This is the inverse of the usual repo-mapper default: most repos return the row shape; this one returns an allowlist.

Three-tier access classification

Facts and entities carry an access_level column with three values: known, discoverable, secret. The classification is grounded in D&D-mechanic semantics — known is no-roll player knowledge (the things anyone in this city would casually know), discoverable is roll-required information (the kind of thing an Investigation or Insight check would surface), secret is actively-hidden plot material the player must earn through play. Migration 014 renamed facts.access_level from the old (public, private, secret) vocabulary, added the same column to entities with NOT NULL DEFAULT 'known', and added a covering index (world_id, access_level) for the snapshot endpoint's primary filter.

The snapshot endpoint filters every read by tier. Without bypass, only access_level = 'known' rows surface — known-tier entities, known-tier facts of those entities, relationships where both endpoints are known-tier, prose kernels for known entities only, hierarchy rows whose parent and child are both known, stat blocks referenced by known entities only. The streaming extractor applies the same filter to the wire format: it consults the entry's access_level at the closed-entry gate and only fires entity-added for known-tier entities. Stage 4's edge emit checks both endpoints against the world's endpointTierMap and skips edges that cross into the hidden tiers. Stage 7's coherence patches do the same — a fix_prose patch targeting a discoverable-tier entity persists silently in the database but does not fire an entity-updated on the wire.

Prose-tier consistency at the prompt level — tier filtering on the wire isn't enough on its own. If the LLM writes "The Saltwind Coast is famous for its fish markets; the smugglers' tunnels under the market square…" into a known-tier region's prose, the smuggler detail leaks the second the region's entity-added ships, because the entity is known-tier and its prose travels with it through the snapshot endpoint. The generation prompts for stages 2, 3, and 7 carry a prose-tier consistency constraint: the prose and fact content of a tier-T entity may only reveal information that is itself tier-T or lower (less hidden). Discoverable facts about a known entity belong on a discoverable-tier fact, not woven into the entity's known-tier prose. Each tier is a separate "what-can-be-said-here" boundary. Filtering content on the wire enforces the shape; the prompt constraint enforces the meaning.

Post-snapshot deltas on the same channel

After the snapshot is fetched, the SSE stream stays open and stage 7's coherence pass emits its patches as deltas on the same channel. The client applies each delta in place against its local copy of the snapshot — entity-updated patches replace top-level keys (RFC 7396 merge-patch semantics) on the named entity, edge-added appends a new relationship, edge-removed drops one. The delta channel reuses the same event arms the streaming extractor uses; the discriminator is the phase the client is in, not the event shape. Coherence doesn't delete entities — there's no entity-removed on the post-snapshot path today.

Reconnect recovery is fetch-and-replace, not replay. EventSource auto-reconnects on transport failure; on re-open, if the phase is at or past world_snapshot_ready, the client re-fetches the snapshot and discards its local copy. Any in-flight coherence deltas that arrive between the snapshot fetch and steady state re-apply harmlessly — the fresh snapshot already reflects them. The pattern avoids the need for an event cursor / replay log; the authoritative snapshot is cheap enough to refetch outright.

Replace, not merge, on reconnect — a missed edge-removed during a disconnect would otherwise leave a stale edge in the client's local state forever. The fetch-and-replace pattern evicts whatever the client thought was true and resyncs to the authoritative server state. Idempotent, no out-of-order risk, and the only cost is a few extra read queries on the rare reconnect — well worth not having to ship a per-client cursor.

Dev-mode access-filter bypass

worlds.dev_bypass_access_filter is a per-world boolean that opts a single world out of the tier filter. When set, the streaming extractor publishes entity-added / edge-added for entries of any tier, stage 7's coherence pass emits deltas for any tier it patches, and the snapshot endpoint widens its tier filter to ['known', 'discoverable', 'secret']. The wire-shape stays narrow — identity-only events, allowlist-projection snapshot — but the set of which events fire and which rows the snapshot includes grows.

The flag is set at world-creation time. The dev tool's campaign-create panel surfaces an opt-in checkbox; when checked, the POST body carries devBypassAccessFilter: true, and the create route writes true into the new world's column. Production users can't reach this code path: the route gates the body field on AUTH_MODE === 'bypass' plus NODE_ENV being development or test, and the six-layer-defense bypass plugin (see JWT middleware) refuses to load anywhere else.

Defense-in-depth at the snapshot endpoint, not just at create — the world's flag is necessary but not sufficient. The snapshot handler additionally checks that the requesting user is in bypass-auth mode (the bypass plugin attaches a scopes: ['bypass'] hint). A dev-tool-created world's secrets must not leak to a prod-auth requester, even if the world's column says yes. Both axes — world flag and user scope — have to align for the wider tier set to surface.

POST /api/campaigns/:campaignId/resume dispatches off derivePhase's nine phases via an exhaustive switch with an assertNever default. Most arms 409 with a typed code; two have real recovery logic.

Phase Resume action

world_snapshot_ready 409 world_gen_in_progress + Retry-After: 30. Stage 4 has committed (the snapshot is fetchable) but stages 5–7 are still running; from the resume-policy perspective the job is still in flight.
world_gen_failed Read the latest failed pipeline_runs.error. If it contains stage_not_implemented → 409 phase_not_yet_implementable with the stuck stage name. The dev tool surface

Five panels in the dev tool drive and observe the world-gen pipeline. The campaign-create form (freeform / guided sub-forms) posts to POST /api/campaigns and exposes a "Bypass access tiers" opt-in checkbox that flips the world's dev_bypass_access_filter column at create time. The campaign-details panel loads a campaign by id and exposes a Resume button. The live-events panel attaches to the SSE stream and renders every event arm — see the live-events inspector section. The new world-snapshot panel attaches to the same SSE stream, waits for world_snapshot_ready, fetches the snapshot endpoint, and renders it as a tree-of-entities-by-kind + per-entity detail card; stage 7's coherence deltas apply in place so the user watches the world settle without a refetch. The credit-ledger panel maintains an in-session log of grants and force-grants via the dev-only POST /api/dev/credits/grant.

Both dev-only routes — POST /api/dev/credits/grant and the read-side GET /api/dev/credits/me (balance + the last 20 ledger entries) — register only when AUTH_MODE === 'bypass' and live behind the same six-layer bypass-plugin defense as the rest of the dev surface. Both routes resolve identity from request.user.sub — the bypass plugin sets that from the x-mythrun-dev-sub header (the dev-tool's identity dropdown), so a grant lands on the currently-active dev-user-N identity, not a pinned sub.

The dev tool's coverage.json ship-gate keeps the contract honest: every entry in PIPELINE_ROUTES, PIPELINE_SSE_EVENTS, and PIPELINE_JOBS must either be driven by a panel or carry a typed exempt reason. With MYT-52 landed, the exempt list is empty — the live-events panel renders all thirteen event arms. Adding a new pipeline route or job is a four-file change in a single PR — contract, handler, dev-tool panel, coverage entry — and pnpm dev-tool:check red-CI's the merge otherwise.

Operating this piece

Diagnose a stuck world-gen

  1. Get the campaign's phase from the snapshot endpoint: GET /api/campaigns/:campaignId/status. world_gen_failed is the most common stuck state; world_gen for > 5 minutes usually means a wedged worker.
  2. Query pipeline_runs for the world: SELECT stage, status, started_at, completed_at, error FROM pipeline_runs WHERE world_id = $1 ORDER BY started_at DESC. The latest failed row's error column is JSON — read the code field.
  3. Map error.code to action: stage_not_implemented → expected (resume will 409 phase_not_yet_implementable); world_gen_cost_cap_exceeded → the cap fired (refund row exists in credit_ledger; resume will 409 world_gen_capped); any code matching content_filtered → Anthropic content-policy filter rejected this prompt (resume will 409 content_filtered — the user must adjust the source concept); any other code → transient infra blip, resume re-enqueues. BullMQ's attempts: 2 means most transient errors self-heal before the user sees world_gen_failed.
  4. For a world_gen-stuck-running case, the worker's atomic-claim path will self-recover after 5 minutes (the stuck-stage reset UPDATE flips a started_at < now() - INTERVAL '5 minutes' running row back to claimable). If it doesn't, the worker pod's CloudWatch logs name the cause.

Watch the cost-cap fire (stages 1–6)

  1. Set the cap low against the local Postgres: UPDATE settings SET value = '0.001' WHERE key = 'world_gen_cost_cap_usd';. The worker re-reads the cap at the start of every stage, so no restart is needed.
  2. Create a campaign via the dev tool. Stage 1 (concept_intake) runs to completion (the cap check fires AFTER stage commit, not before LLM call), then the cap check sees cumulative cost > 0.001 USD.
  3. Confirm the breaker fired: the worlds row's status column is 'failed'; a row exists in credit_ledger with source_type = 'cost_cap_refund', amount = 1, user_id matching the campaign owner. The pipeline_runs row's error JSON contains code: 'world_gen_cost_cap_exceeded'.
  4. Try to resume from the dev tool: the resume route returns 409 { code: 'world_gen_capped' } — there's no point re-running, the cap will fire on the next stage too. Reset the cap to a sensible value before trying again.

Watch the stage-7 cap-fire exception

  1. Run a full world-gen to completion against the standard cap. Note the cumulative cost from the final cost-update event in the live-events panel.
  2. Lower the cap to a value below that cumulative figure but above the sum of stages 1–6: UPDATE settings SET value = '<value>' WHERE key = 'world_gen_cost_cap_usd';.
  3. Create a fresh campaign. Stages 1–6 run; stage 7 reads sumCompletedStageCosts on entry, sees the value already over cap, and returns { capExhausted: true } with a single { type: 'phase', phase: 'complete' } in finalizedEvents.
  4. Confirm worlds.status = 'complete' (NOT failed); no refund row in credit_ledger; pipeline_runs for stage 7 shows completed with zero cost. The user got a polished-minus-coherence world; the cap held without the refund-and-restart cycle.

Force a paint-job rejection

  1. Submit a freeform concept that's a recognizable clone — "A school of magic on a hidden castle where young wizards learn spells" is the canonical test input. The synthesizer is bypassed in freeform mode; the input gate's clone_intent axis will likely flag it first and return 422 concept_rejected before the paint-job validator gets a chance.
  2. To exercise the paint-job validator specifically, submit a concept that's BORDERLINE on clone-intent (the input gate's primary threshold is 0.85; aim for the 0.5–0.8 range). The gate lets it through; stage 1 generates a draft; the judge fires; on flag, the loop discards and retries with a fresh-direction amendment.
  3. The dev tool's live-events panel will show concept_intake running for ~30–60 seconds longer than usual when the validator retries (up to 3 attempts × 2 Sonnet calls per attempt). On exhaustion, the stage fails with code: 'concept_intake_paint_job_loop_exhausted' and the phase flips to world_gen_failed.
  4. Resume re-enqueues (the loop-exhausted error isn't in the terminal-class list); a fresh attempt rolls a fresh judge call and may succeed. If it doesn't, the user is asked to refine the concept.

Trigger the repair chain on a streaming stage

  1. Streaming stages emit JSON via streamObject. The deterministic way to force a Zod failure is to corrupt the schema in code (don't ship): in backend/src/llm/schemas/world-and-factions.ts, tighten a field — e.g. require a z.string().regex(/^[A-Z]/) name. Most LLM-generated regions will fail. Run a world-gen and watch the live-events panel.
  2. On stage 2's stream completion, the handler's validateOrRepair calls Haiku with the broken tree + Zod errors. The Haiku call surfaces in CloudWatch logs as event: 'llm.call' with stage: 'world_and_factions' and model = claude-haiku-4-5-20251001.
  3. Cost flows back through StageDispatchResult.costUsd; the pipeline_runs.cost_usd for stage 2 carries the Opus stream cost PLUS the Haiku repair cost. The cost-update event after stage 2 reflects the total.
  4. If Haiku also fails the schema, Sonnet fires next; if Sonnet fails, the handler throws and runStage ROLLBACKs + publishes stage-reset. BullMQ's attempts: 2 means the stage gets one more shot before terminal failure.
  5. Revert the schema change. The intended production path is "repair fires occasionally on real LLM output quirks"; the deliberate-schema-break is a forcing function for debugging the chain.

Recover a Redis-blip orphan

  1. Find the orphaned campaign via GET /api/campaigns/:campaignId/status — phase will be world_gen_failed (the create transaction seeds a pending pipeline_runs row, which presents as failed when no worker ever claims it) or, very rarely, not_started if the seed row is missing.
  2. Inspect the latest failed pipeline_runs row's error column. If it's NULL or the code isn't in the terminal-class list (stage_not_implemented, world_gen_cost_cap_exceeded, content_filtered), the resume route will re-enqueue cleanly.
  3. From the dev tool's campaign details panel (or via direct POST /api/campaigns/:campaignId/resume), click Resume. The response is 202 { campaignId, action: 'world-gen-re-enqueued' } on the world_gen_failed path or ... 'world-gen-enqueued-after-orphan-recovery' } on the rarer not_started path.
  4. Confirm the worker picked up the job: the pipeline:campaign:{campaignId} Redis channel emits phase = world_gen and stage-started events almost immediately. If the resume returns a non-recoverable code (409 world_gen_capped, 409 content_filtered, 409 phase_not_yet_implementable), the failure isn't a Redis blip — see the diagnose-a-stuck-world-gen runbook.

Integration with the status surface

The processor and its handlers publish JSON event payloads on {redisKeyPrefix}pipeline:campaign:{campaignId} — the channel format the pipeline status surface listens on. All thirteen arms in PIPELINE_SSE_EVENTS are now in use: the six lifecycle arms from MYT-50 plus the seven entity / edge arms wired by MYT-52 (stage-reset, entity-added, entity-updated, entity-removed, edge-added, edge-removed, finalized). The SSE bridge is type-blind — every JSON payload published on a campaign channel is forwarded to attached sinks unchanged. The dev tool's live-events panel renders every arm.

Out of scope

  • Resume for the character_creation phase. MYT-53 landed the per-player character-creation pipeline on the campaign-setup queue (see Character creation), but the POST /resume endpoint here in world-gen still returns 422 phase_resume_not_yet_implemented when the campaign has advanced into the character_creation phase — resume support for that phase is a follow-up bead.
  • Automatic refunds beyond the cost cap. Stage failures that aren't cost-cap fires don't refund — the user can resume and the worker re-runs failed stages within the cap. Manual refunds for genuine infrastructure failures are an operator action, not an automated path; a proper user-facing refund surface is a post-launch hardening item.
  • The future kind: 'existing' body arm (joining an existing world) is reserved in the discriminated body shape but not stubbed at launch. An unknown kind produces a Zod 400, not a 501.
  • Repair-chain entity drops. The contract reserves entity-removed { reason: 'repair_dropped' } but no current code path produces it — the repair prompt is constrained to preserve array length. The arm is in the contract so future repair-policy changes don't have to expand the wire format piecemeal.
