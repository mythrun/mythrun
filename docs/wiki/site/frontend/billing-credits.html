Billing & credits

The player's side of the money. The Sessions & billing screen at /billing shows both credit balances, the subscription tiers, and a purchase ledger; the app header carries the live session-credit count with a quiet quick-buy; a drained owner meets a purchase prompt at session start; and a checkout return waits for the credit to land. It's a thin client over the shipped billing routes — every purchase routes to a Stripe redirect that grants nothing synchronously, because the credit lands only through the webhook.

How it fits together

The client-core/api/billing.ts slice wraps the shipped endpoints: getBalance (self-scoped { session, world_gen, active_subscription }), getSkus (the public pricing catalogue), getHistory (the unified purchase feed), and the three mutations — createCheckout, upgradeTier, openPortal — each returning only a Stripe redirect URL. On top sit pure client-core view-models (client-core/billing/) that shape those reads for the screen, and the mythrunUI components that render them. The one hard rule that shapes every surface: credits land only via the webhook, never from a mutation's response, so the client polls rather than assumes.

Two credit buckets, never one number

Session credits and world-gen credits are independent, and no surface ever shows a conflated sum. balanceView passes each bucket through unchanged; the settings screen's CreditBalance itemizes both, while the play-adjacent chrome — the header count and the campaign card's low-credit line — tracks session credits only. Starting a session spends a session credit; generating a world spends a world-gen credit; the two are different currencies and the UI keeps them apart. The header readout is where that discipline is under the most pressure: a bare number in the app's most-seen chrome silently equalled one bucket and taught the wrong model, so MYT-99 labelled it "session credits". The navbar redesign then tersened the visible label to "Credits" as part of the bar's quieter chrome — the readout still tracks the session bucket only, and the label's final wording is flagged for the end-of-frontend copy pass; this itemized surface remains where the two currencies are actually taught.

Keeping them apart is necessary but not sufficient — a number a player can't interpret is not much better than a wrong one. Each bucket therefore renders as its own bounded tile carrying its count plus two lines of its own: what one credit buys, and what running out means. Those explainers are required props on the component, not optional decoration.

The explainer lives with its number, and the contract forces it — the first version rendered each bucket as a full-width justified row, which at desktop width put the label most of a screen away from its count with nothing binding them, and neither count said what the currency was. A bounded tile fixes the association; making the explainers required in CreditBalanceProps is what stops the next surface from shipping a bare number again. These are the product's only two economic units, so the cost of teaching them is two lines each, and they must never be readable against the wrong bucket.

The subscription CTA gate — the double-subscribe guard

Every subscription tier renders a CTA, and subscriptionCta decides which one from the viewer's active_subscription and the target tier's price rank (read off the shared catalogue, so this layer never re-sums prices):

  • No active subscription → subscribe (Checkout, mode subscription).
  • Active, target higher → upgrade (POST /upgrade-tier, prorated).
  • Active, target same or lower, or unresolvable → manage (Customer Portal).
subscribe is returned only when there is no active subscription — this is a required acceptance criterion, not chrome — Stripe will happily create a second live subscription for a user who already has one; it does not dedupe. So a plain subscription-checkout CTA presented to an already-subscribed user double-charges them. The gate makes that state unreachable: an active subscriber's every tile routes to upgrade or manage, and the defensive arm sends even an unresolvable tier (an active sub whose tier the catalogue no longer lists) to the Portal rather than to a second subscribe. This is the showstopper the blind review flagged; the guard is what keeps the pin total. A pending upgrade (409 upgrade_already_pending) renders a calm "your upgrade is processing" arm, never an error.

The purchase moment — the owner pays

Starting a session debits the campaign owner's session credit regardless of who pressed Start, so the play screen's 402 arm fires on the owner's shortfall. The PurchaseSeam splits on who is looking:

  • The owner gets an inline PurchasePrompt with the buy path — à-la-carte session credits through Checkout, a quantity control with terse presets (1 / 4 / 8) — returning through the /billing/return poll.
  • A non-owner member gets a calm notice: the campaign's owner is out of session credits. No buy CTA.
A non-owner is shown no buy button because buying would credit the wrong ledger — the session debits the owner's balance, and a member's purchase credits the member's own ledger, which does nothing to unblock the session. Offering a member a buy CTA would take their money and leave the session just as stuck. So the seam's non-owner variant is a calm explanation with no action, and the campaign-card low-credit line is owner-only for the same reason — there is no member-visible read of the owner's balance, and one must not be added. "Trial-end" as a distinct surface is dropped: the trial is a non-expiring starter credit with no trial flag on any read, so the out-of-credits prompt is the one moment.

Checkout return — the webhook is the truth

Stripe redirects a completed checkout to /billing/return, but the grant rides the async checkout.session.completed webhook, so the balance can't be confirmed synchronously. useCheckoutReturn snapshots the balance on its first poll and polls until it changes (→ settled, and it invalidates the cached balance) or the budget expires (→ processing — a calm, non-error beat pointing at the settings history, never a failure claim for a completed payment). A cancelled checkout lands on a separate calm /billing/cancelled route.

The "arrived" signal keys off an observed balance change, not the pre-redirect baseline — the natural check is "did the balance go up from what it was before I left for Stripe?" But that pre-redirect baseline doesn't survive the full-page Stripe round-trip. So the hook captures its baseline on the first poll after return and watches for a change from there. The cost is a known, accepted fallback: a webhook that landed before the first poll makes the already-updated balance the baseline, so it never appears to change and the return lands on the calm processing beat — correct and non-alarming, just not the celebratory "settled" copy.
The forwarded-webhook gotcha the billing smoke must clear — because the grant depends entirely on the webhook, a local billing smoke needs the Stripe CLI forwarder running. But the forwarder currently delivers events at an API version that doesn't match the SDK pin, and the dispatcher fail-closes on that mismatch — records the event, returns 200, grants nothing. So a dev checkout can complete and the return route will sit on processing forever with no credit. The current behavior and the parallel production risk are documented on the billing webhook page (filed as myth-e3ary).

The billing surface and its components

/billing is the Sessions & billing screen: SessionsBilling reads the balance, skus, and history suspense queries and hands each to a component. The screen originally shipped at /settings; the navbar redesign renamed the route to what the surface actually is (the app has no general settings — the page is entirely billing), keeping a legacy redirect inside the auth gate that forwards /settings to /billing with its search and hash intact, using replace semantics so the dead path never lands in history. The header's Add-credits actions deep-link to /billing#buy: the screen scrolls its purchase section into view from a ref once the suspense reads resolve, with a scroll margin that clears the sticky bar.

  • CreditBalance — both buckets, itemized, never summed, each an explained tile.
  • PackList — the price-ordered subscription tiers by their brand names (Wayfarer / Sojourner / Mythwright), each with its gated CTA and its grant ledger, over the à-la-carte packs with a quantity control (presets 1 / 4 / 8 / 16). Both sections carry a heading and a one-line note on how their credits behave.
  • PurchaseHistory — a terse mono ledger.
  • PurchasePrompt — the owner/non-owner purchase-moment variants (used by the play seam).
The tiers differentiate on the ledger, never on a nudge — three cards carrying only a name and a price cannot be used to make a billing decision, which is the one job a pricing screen has. So every tier and pack states its per-cycle grants as label·value rows: sessions, then worlds, in that fixed order in every card, so the reader scans across rather than re-reading each one. A zero grant renders no row at all — an empty "worlds: 0" line is noise, not data. What is still absent is any "recommended" / "best value" / "most popular" marker: the register constraint holds, and the product states what each tier gives and lets the reader choose. The one state the vocabulary does mark is the tier the viewer is already on, and it marks it with a mono label line plus a raised paper surface — typography and surface tier, not a chip.
The grant numbers come from the SKU payload, not a frontend table — the catalogue is served from the Stripe-probed SKU cache, so composing each ledger from the payload's own granted counts is what keeps the pricing UI from drifting off Stripe. A frontend constant listing "the Sojourner gives eight sessions" would be a second source of truth for a number Stripe already owns, and it would be wrong the first time a tier is re-sized. The shell formats those counts; the design system receives finished strings and never formats a count itself. (Prices are formatted the same way, and drop the trailing .00 on a whole amount — a decimal on a round consumer price is a developer tell.)
No "best value" labels, and a pack row can't name a credit count — the tier names are server data carried through verbatim. And the history feed carries lookup_key only for subscription invoice rows — an à-la-carte pack row has none — so the view-model can never resolve a tier name or promise per-item credit detail for a pack. Its prose is "Purchase — $X.XX", because the webhook (not the client) is the authority on what a purchase granted.

Header chrome and the low-credit card line

The AppFrame header carries the live session-credit count with a quiet quick-buy path to the purchase surface: since the navbar redesign, a labelled "Add credits" action beside the readout on desktop and an item of the header menu on phones, both deep-linking to /billing#buy (and standing down to menu-only on the full-bleed play stage). The campaign card shows an owner-only low-credit line, driven by useLowSessionCredits.

Because that readout lives in chrome that never remounts, it needs an explicit refresh contract: useInvalidateBalance marks the shared ['billing','balance'] cache stale and lets every active reader refetch in the background. The header calls it on route navigation, and the live play shell calls it when a session's shell mounts, since starting a session is where the debit actually happens.

A chrome-level refresh contract beats asking every spender to remember — the alternative is for each credit-spending mutation site to invalidate the balance itself, which is one more thing to forget at every future call site and fails silently when forgotten (a stale number is not an error). Invalidating on navigation makes "the header is never stale across a navigation" a property of the chrome instead. It is stale-while-revalidate, so the number updates in place — suspense only ever gates the first load — and the cost is one cheap GET per navigation. The session-start invalidation exists for the case navigation can't cover: the debit happens while the player sits on the play route, and the end-of-session confirm states in the past tense that the credit is already spent, so the two must not disagree.
useLowSessionCredits fails open — the low-credit nudge is decorative chrome on the hub, so it must never let a billing blip degrade the shelf. The hook is a non-suspense query with retries off: while loading, on error, or with no data it reports false, so the nudge simply doesn't appear rather than tearing down the card or showing a spurious warning. It shares the same ['billing','balance'] cache the header warms, so it costs no extra fetch. The shipped resilience contract already isolates a failed balance read to the credits slot; this keeps the card on the safe side of that line.
One closed SKU set, pinned across the wire by a test — the frontend keys its tier/pack logic off the contract's LookupKeySchema enum (tier_wayfarer/sojourner/mythwright, sku_session/sku_world); the backend keys its Stripe wiring off its own LOOKUP_KEYS. These are two hand-maintained copies of the same closed set, so a drift-pin test asserts them equal in both directions — a key added on either side fails that test rather than drifting into a runtime mismatch (a contract enum that rejects a real backend lookup key, or the reverse).

Operating this piece

Run the billing smoke (dev, Stripe test mode)

  1. Precondition: the Stripe CLI webhook forwarder must be running — without it, credits never land and the smoke should fail the precondition check, not hang. Note the api-version gotcha: the forwarder's events must also carry the pinned API version, or the dispatcher records-and-acks them without granting.
  2. Open /billing (the legacy /settings path redirects there): both balance tiles render with their explainers, every tier and pack shows its grant ledger in the same row order, the tiers show their gated CTAs, and history lists real rows. As a new subscriber, the subscription CTA is subscribe; as an already-subscribed test user, the same tiles render upgrade / manage — never a second checkout — and the active tier carries the current marker.
  3. Buy an à-la-carte pack: Checkout → /billing/return polls until the credited balance changes (settled) or the budget expires (processing). Confirm the ledger reflects it.
  4. Drain the owner's session credits and press Start on a session: the owner sees the inline purchase prompt; a non-owner member sees the calm "owner is out of credits" notice.

Integration points

This surface consumes the billing routes and the SKU catalogue; every credit grant lands through the billing webhook (whose current api-version behavior is the reason the checkout-return sits on processing in dev). The live 402 purchase moment belongs to the play flow; the header credit chrome edits the app frame; the owner-only low-credit line rides the campaign card. Every visible element is a mythrunUI component over the DOM-free client brain, and each checkout/upgrade/portal action navigates the browser to the returned Stripe URL through the platform navigation seam (a screen never touches window).

Appendix: the modules

Client-core — the brain (client-core/billing + api/billing.ts)

Module Role
api/billing.ts The slices — getBalance/useBalance, useSkus, useHistory, createCheckout, openPortal, upgradeTier, the fail-open useLowSessionCredits, and useInvalidateBalance (the shared-cache refresh the persistent chrome calls).
billing/balance-view-model.ts The two independent buckets + the resolved subscription tier name (never a sum).
billing/tier-catalogue.ts subscriptionTiers / aLaCarteSkus / tierRank — price-ordered derivations over the SKU listing.
billing/subscription-cta.ts The subscribe/upgrade/manage gate (the double-subscribe guard).
billing/insufficient-credits.ts The 402 guard + purchasePromptModel (owner / non-owner variant).
billing/purchase-history-view-model.ts The unified feed → ledger rows; packs name no credit count.
billing/use-checkout-return.ts The post-redirect balance poll → settled / processing.
contract/rest/billing.ts The wire schemas + the closed LookupKeySchema (the drift-pinned SKU set).

Web — the screens

Module Role
routes/billing.tsx · routes/billing/sessions-billing.tsx The Sessions & billing surface (balance tiles + tiers + à-la-carte + history + portal); it also composes each card's grant ledger and formats every price and count, so the design system receives finished strings.
routes/billing/checkout-return.tsx · checkout-cancelled.tsx The pinned post-checkout terminal states.
routes/play/purchase-seam.tsx The live 402 purchase moment (owner buy / member hold) — shared with the play flow.
ui/…/CreditBalance · PackList · PurchaseHistory · PurchasePrompt The four presentational billing components.
