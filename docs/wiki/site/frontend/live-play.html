Live play

The table itself: /campaigns/:id/play, where the party and the AI DM run a session. An atmospheric prep beat gives way to a Start that debits the owner's session credit, then the screen becomes a streamed multiplayer transcript — the DM's prose arrives token by token, the humans' messages post the instant they're typed, a mid-session joiner sees the full backlog, a dropped connection resyncs without double-rendering the turn it dropped during, and a skill check arrives as an in-stream dice card the player rolls before the outcome prose unfolds. Beside the transcript sits a knowledge sidebar — a browsable world wiki, a relationship graph, and the player's live character sheet — and recognized names in the DM's settled prose highlight into terse knowledge cards, every surface showing only what the character already knows. The route is a thin composition; all the reasoning — the start classifier, the transcript reducer, the reveal gate, the transport view-model, the one-snapshot knowledge cache — lives in the platform-neutral client brain.

The screen adds no frame type and no read surface — enforced ignorance holds here by construction, not by prompt discipline. The play screen only ever renders frames the session transport hands it; it introduces no new WebSocket frame, no new backend read. There is deliberately no Slow-Thinker stage-direction frame anywhere in the client, and nothing on this screen may add one — the reason the DM intervened is never on the wire the player consumes. MYT-93's dice moment holds the same line: the reveal drives entirely off the skill_check/dice_roll frames already on the wire, and the client→server roll_complete frame was deliberately excluded — pressing Roll sends nothing, because the number is already server-resolved.

How it fits together

PlayRoute (routes/play.tsx) is the router-mounted entry, and because the router mounts it directly — not through CampaignPage, which feeds the character surface a campaign prop — it resolves its own identity signals first. usePlayViewer loads two reads it already has slices for: getMe (the viewer's DB id — the reconcile key the server stamps on this player's message echoes — plus the display name) and the same GET /api/campaigns/mine payload the hub renders, found by id. From the campaign it derives ownership (creator === null ⟹ owner, the same signal character creation uses) and the party roster (userId → displayName). A campaign the viewer can't see resolves to a calm error — you can't play a session you're not a member of.

With the viewer resolved, PlaySession owns the rest. It calls start() once on mount and renders by the start flow's phase: the short connecting beat while the attempt is in flight, the prep beat, the live session shell, the purchase seam, or a calm retry notice. The route file itself stays a thin shell — the client-core hooks (the start classifier, the prep SSE fold, the transport view-model) carry every judgment, and each is an injectable seam so a test drives any phase deterministically without a live transport.

The start flow — one classifier, five arms

POST /api/sessions/:campaignId/start debits the campaign owner's session credit regardless of who pressed Start, and answers with one of several shapes that each mean a different next screen. classifyStartError (in client-core/session/start-flow.ts) maps a caught error to a discriminated StartOutcome, keying only on the contract-blessed status/code/body — never on prose (the ZFC line: pure orchestration, no pattern-matching). The useSessionStart hook resolves each outcome to a render phase:

  • 200 → ready{sessionId}: mount the live shell.
  • 409 session_already_active → the join path. The 409 body carries no sessionId, so the hook calls GET …/active to resolve the running session's id, then mounts the shell against it. This is the mid-session join.
  • 409 prep_not_ready → the prep beat (below), which resolves upward: when prep completes it re-attempts start().
  • 402 insufficient_credits → the purchase moment, carrying the owner-vs-member split.
  • 409 campaign_not_active / reconcile_pending / session_ending → a calm, retryable "blocked" notice; anything unrecognized is a generic retry.
The join arm and the prep arm are only distinguishable because the backend reordered its preconditions (MYT-92) — the start flow drives the atmospheric prep beat on prep_not_ready and the join path on session_already_active, so the two must be told apart truthfully. Until the play E2E caught it, a member whose /start raced an already-running session got prep_not_ready — because maxSessionNumber counts the live session, so the "next" prep legitimately doesn't exist — and pinned forever on the prep beat. The fix moved the active-session guard ahead of the prep guard on the server; the client relies on that discrimination.
Seed lastSeq = 0 on the very first connect — the view-model connects with seedLastSeq: 0, which asks the transport for a full-history replay. A fresh connect would otherwise get a session_ready with no messages, and only a reconnect replays the backlog. Seeding zero makes the owner's first connect, a reload, and the 409-join / mid-session joiner all rebuild the whole transcript from one session_reconnect batch — one code path covers every entry into a running session.

The prep beat (PrepBeat + useSessionPrep) is the "the DM is preparing tonight's session…" experience. It rides the shipped prep-status SSE (the campaign-scoped channel, distinct from world-gen), seeds its coarse bit off the connect-time snapshot, and advances on the live prep-started/prep-ready/prep-failed events. On ready it re-attempts start. It latches a failure: because a reconnect re-snapshots generating (the prep row's existence is the snapshot's only signal), the beat holds a seen failure on the calm retry rather than re-arming the atmospheric wait off a post-failure re-snapshot.

The transcript reducer — the reconnect-safe core

Once a session is ready, SessionShell drives useSession, the view-model over the shipped WS session client (a dumb typed pipe with production-grade reconnection). Every inbound frame folds through reduceFrameReconciling — the pure transcript-reducer.ts wrapped in the optimistic own-echo layer. The reducer models the transcript as an ordered list of TranscriptItems and owns transcript content only: the streamed DM prose (text_delta accumulates into one dm item per turnId, settling on turn_end), the confirmed player messages (deduped on seq), and every mechanical frame.

Every mechanical frame is a first-class item, so the rendering can grow without touching the reducer — skill_check, dice_roll, ledger_update, mode_change, and the two combat_* frames each become a typed transcript item carrying the whole frame, not a flattened string. MYT-92 rendered every one as a terse mono system line and froze the reducer's shape as the wave-2 shared contract; MYT-93 then did exactly what that freeze was for — it extended the rendering of skill_check and dice_roll into the RollCard dice moment (MessageStream's item dispatch) without adding a field to the reducer. MYT-94 did the same again from the other side: it reads the ledger_update item — still rendered as a mono line in the transcript — and folds it into the live character-sheet overlay in the knowledge sidebar, again without touching the reducer. mode_change and the combat_* frames still render as mono lines until their own surfaces land.
Whole-turn replace, so a reconnect can't double-render the turn it dropped during — a client that drops mid-turn has a partial dm item built from live text_deltas. On reconnect the transport replays that same turn as seq-bearing rows. If the reducer merely appended them, the turn would render twice. So applyReconnect — an explicit folder seam, not a hidden branch — first prunes every existing DM/mechanical item whose turnId the replay batch carries, then re-folds the batch so each turn rebuilds settled. Player items (turnId null) survive the prune and dedup on seq instead. The seam is a separate exported function precisely so the optimistic layer can re-fold the same batch through a reconciling folder (below) rather than the raw one.

Optimistic own-messages

A player's own message appears the instant it's typed — addPending appends a player item with pending: true and no seq, keyed by a stable local id so React reuses the same node when the server echo confirms it in place. reduceFrameReconciling wraps the raw reducer: an inbound own player_message reconciles the first matching pending item — settling it and adopting the server's authoritative seq — instead of appending a duplicate. Because that confirmation happens outside the raw append path, it records the seq in the dedup ledger itself, or a redelivery would slip past. On a reconnecting → connected transition the hook arms a resend that fires after the replay batch settles: the replay confirms the messages that landed, and every still-pending one is re-sent.

The resend can duplicate, and that residual is accepted on purpose — the wire protocol carries no client message id, so reconciliation matches on (viewerUserId, text) in FIFO order. If a pending message actually landed but fell outside the transport's filtered replay window, the reconnect resend duplicates it. Adding a client message id is out of MYT-92 scope, so the residual is annotated in the code rather than hidden — the two dominant paths (a first-join backlog and a single in-flight-turn reconnect) are exact, and a rare duplicate on a lossy reconnect is the accepted cost of an input that never feels laggy.

Presence, and the parts the reducer won't touch

The reducer deliberately ignores the out-of-band control and presence frames; useSession folds those into a separate SessionPresence state through foldOutOfBand. The thinking indicator opens on dm_thinking and clears on the first text_delta/turn_end/turn_error for that turn; the typing set tracks typing_start/typing_stop; the ended flag flips on session_end. A session_reconnect resets the thinking indicator, so a stuck "DM is thinking…" can't survive a drop — a turn genuinely still running re-arms it with a fresh live frame. The route maps the transport's own connection status (reconnecting/failed) to a quiet system line pinned under the transcript, and resolves the presence typing userIds to display names through the party roster (unknown ids are omitted, never shown raw).

The dice moment — a reveal gate over an already-resolved roll

When the DM calls for a check, the backend rolls the die deterministically and sends the whole result in one skill_check frame — the natural roll, the modifier, the total, the DC, and the matched outcome tier. The player never rolls anything real. So MYT-93's dice moment is pure presentation: it delays the display of a number the client already holds and gates the outcome prose behind an explicit Continue, so a check feels like a roll instead of arriving pre-decided. useSession is untouched — the reveal is a render gate layered over the transcript the reducer already produces, not a hold-back inside it.

The roll is server-resolved; the card sends nothing back — the number is generated in deterministic backend code (the LLM never rolls), so the whole result is on the wire before the card mounts. Pressing Roll therefore fires no request: there is no client→server roll_complete frame, deliberately excluded from the contract. This keeps the screen's no-new-frame boundary intact and means a reload or a mid-session joiner can reconstruct every roll from the persisted frames alone — the theater is a local flourish, never a source of truth.

The reveal state lives in a tiny separate reducer, roll-reveal.ts, exposed as useRollReveal. It tracks only the two committed interactions — which card keys have been rolled and which continued — as two sets. A card's phase is derived, never stored per frame: cardPhase reads idle (show a Roll button) → revealed (numbers land, show Continue) → released (the outcome prose opens). A card whose frame carries a persisted seq — a backlog row or a reconnect replay — is history, and derives straight to released: no theater on anything the player has already lived through, the same history-has-no-theater rule the reconnect-safe reducer follows.

The gate itself is one pure selector. buildRevealView(items, state) walks the transcript and returns a plain view — phaseByKey (each card's derived phase) and gatedTurnIds (the set of turns whose outcome prose is still held). MessageStream renders a dm item as nothing while its turnId is in gatedTurnIds, so the DM's post-check narration stays hidden until the check that provoked it is continued. A turn with two checks stays gated until both are continued; a lead-in line the DM wrote before the check folds into the same gated turn item and is held with it. A dice_roll is the flavor variant — it reveals a number but never gates prose.

The constraint field is never rendered — a skill_check frame carries the outcome constraint the DM's prose is written from (the pre-generated fail/success/great-success seed). Painting it on the card would pre-empt the very narration the gate exists to hold back — the player would read the outcome before the DM voiced it. So the card renders the mechanical readout (die, modifier, total, DC, tier) and nothing else; the constraint is threaded nowhere on the client. An E2E check asserts the constraint text is absent from the DOM at every phase.

All of this is computed route-side. SessionShell runs useRollReveal, derives the view with buildRevealView, and resolves the [ph:] label bundle, then hands MessageStream plain data and neutral callbacks. The mythrunUI layer holds no reveal runtime — RollCard's phase arrives as a prop, its only local state the DieSpin transition (portability rule R1: the DOM layer imports no client-core logic). A pending, un-continued card does not lock the composer — the player may keep typing while a card waits, the calm default the spec leaves open.

The card and the die

RollCard is the in-stream dice moment made visible: a square, flat-1-bit paper card that reads as a mechanical interjection in the DM's serif transcript. It composes the skill and character and any advantage/disadvantage posture, a DieSpin in the centre, a Roll button while idle, then the modifier→total→DC readout and a Continue button once revealed. Every mechanical value is --font-ui mono, and — matching the brand's no-status-chips register — the outcome tier is carried by typographic weight (a heavier word for a better result), never a coloured badge. There are no circles anywhere on it.

DieSpin is a flat 2D outlined d20, authored here as a new mark because no pixelarticons die exists. It spins in a stepped rotation — eight discrete 45° steps over roughly a second, the motion analog of the brand's stepped Bayer dither, never a smooth CSS interpolation — and stamps the used die's numeral upright in its centre when it lands. Under prefers-reduced-motion it does not spin: it lands instantly and reveals. Because motion is never the only signal, the die glyph is aria-hidden decoration and the landed result is announced through a polite live region, so a screen reader hears the number the sighted player watches settle.

A stepped die, not a smooth one — the UX spec called for a smooth spin, but the brand register is 1-bit and pixel-honest, so the die jumps in discrete steps the same way the Dither bands rather than blending. This is the brand-overrides-UX rule applied to motion. The step count and die geometry are story-tuned placeholders pending the end-of-milestone visual pass; the structure (stepped, ~1s, reduced-motion-instant, mono numeral) is what's fixed now.

The stage — six components, two registers

SessionShell composes six mythrunUI components into a full-height flex column: the scroller, the thinking line, and the input, beside the knowledge sidebar. The register split is the meaning — the DM speaks in narrative, the humans at the table speak in the mechanical voice:

  • MessageStream — the transcript scroller. Auto-follows the tail with a "jump to now" affordance, and positions instantly under prefers-reduced-motion (no smooth-scroll vestibular trigger). It dispatches each transcript item to its renderer — dm to DmMessage, player to PlayerMessage, skill_check/dice_roll to the RollCard, the rest to a mono system line — holds a gated turn's DM prose off-screen, and carries the connection system line.
  • DmMessage — the DM's prose in Source Serif 4 (--font-body), on a paper tint, appended token-wise as text_deltas arrive and settling on turn_end. Once a turn settles, recognized entity names in the prose highlight into knowledge cards; the streaming path is byte-unchanged.
  • PlayerMessage — a human utterance in IBM Plex Mono (--font-ui), a distinct tint, on its own paper band. There is no bubbles-and-avatars chat idiom; the mono voice marks the players as the mechanical register against the DM's narrative one.
  • SessionInput — the composer, with a prominent @DM summon. The summon uses the explicit-text path: it composes the visible @dm token into the sent message, which persists and broadcasts as an ordinary player_message the backend's explicit-trigger path recognizes — so the whole table sees the summon. The invisible dm_invoke frame is deliberately not used.
  • SessionStartBeat — the 1-bit loading-beat family, with two labeled phases: the SSE-driven atmospheric prep wait and the short socket-connect boundary. Reduced-motion lands instantly.
  • ThinkingIndicator — "DM is thinking…" on the thinking bit, player typing on the typing set.
The @DM summon is explicit text, not an invisible control frame — the transport supports a payload-free dm_invoke summon, but the play screen composes a visible @dm token into a normal message instead. A summon is a social act at the table; routing it through the visible transcript means the other players see who called the DM and why, rather than the DM answering an invisible prod. composeSummon is a deterministic string helper (a protocol token, not user copy, so it is not an i18n key).

The full-bleed frame

The play route escapes the app frame's padded content box: it carries a fullBleed route handle that AppFrame reads to render header-plus-stage as exactly one viewport, so the transcript scrolls inside its column and the page never scrolls. The unbroken min-h-0 flex-scroll chain (the full-bleed AppFrame root → the play route root → the transcript column → MessageStream) is the one place the play routes use a raw layout element — the layout scaffold isn't expressible through mythrunUI Stack props (which ban className), so it takes the sanctioned, reasoned no-ad-hoc-ui escape hatch, while every piece of visible content composes the design system.

A route handle, not ad-hoc negative margins — and a declared shared file — the full-bleed breakout is owned by the play route as an explicit AppFrame variant because MYT-95's header credit chrome edits the same AppFrame. The two changes were declared up front so neither worktree rewrote the frame wholesale: the play route owns the content full-bleed variant, the billing work owns the header. A pile of negative margins on the screen would have collided; a route-handle variant keeps the frame's one composition root intact.

Session end lands on the recap route

When session_end arrives the shell shows a brief "session complete" transition and navigates to /campaigns/:id/recap. That is where MYT-92 stops.

The recap is a stub route, deliberately — not silently dropped — the session's summary exists in the database (post-session analysis writes sessions.summary), but there is no player-facing recap read yet. So MYT-92's done-when was softened to "session end lands on the recap route," with the real recap screen and a minimal recap read filed as a follow-up bead (which also resolves the campaignId-vs-sessionId param question). The UX-spec recap experience is explicitly deferred, not quietly abandoned.

The knowledge layer — what the character knows, beside the table

MYT-94 fills the sidebar seam MYT-92 left collapsed. Beside the transcript sits a three-tab knowledge sidebar — a browsable World Wiki, an interactive Relationship Graph, and the player's live Character Sheet — and the DM's settled prose gains entity highlighting: a recognized name in the narration becomes a quiet underline that opens a terse knowledge card. Every surface renders only what the character knows. This is the first player-facing read of the world store during play, and it holds the enforced-ignorance line the same way the transcript does — by construction, not by prompt discipline.

The knowledge layer adds no backend read surface — the whole sidebar and the highlighter are built from ONE snapshot: the member-readable, known-tier world-snapshot the world-gen reveal already fetches. The server filters it to the known tier before it crosses the wire; the client adds no tier logic of its own, invents no new endpoint, and — the load-bearing pin — no session frame ever promotes what the cache holds. A player can only ever see, in the wiki, the graph, or a popover, exactly what the server already decided they know.

One snapshot, three projections

useKnowledgeCache (client-core/session/knowledge-cache.ts) is the spine. It fetches the world snapshot once and derives all three views from that single read: the wiki view model (toWikiViewModel), the relationship-graph seed (the canonical snapshotToGraph), and the entity index the highlighter matches against (buildEntityIndex). The cache refetches quietly — the current projections stay on screen until a fresh snapshot resolves, and a refetch failure keeps the prior cache with no error flash — and it refetches on exactly one trigger: a session boundary (the mount, or a WS reconnecting → connected transition), threaded in as a bumped refreshToken.

The no-frame-promotes-the-cache invariant is executable, not a comment — enforced ignorance (spec §6) means no live session frame may carry pre-flip or tier-promotion content into the cache. The module encodes that as code a test pins: CACHE_PROMOTION_FRAME_TYPES is the empty set and frameRefetchesCache returns false for every frame type. Opening a frame-driven promotion path would mean adding a type to that set — a single, reviewed, test-visible change, never a silent drift. Until then the only way knowledge grows on screen is a boundary refetch of a snapshot the server re-filtered.

The three tabs

KnowledgeSidebar is pure wiring over three shipped primitives, one per tab:

  • World Wiki — the shipped WorldWiki over cache.wiki, with client-side search. There are no stat blocks: the WorldSnapshotSchema strips prose kernels and stat blocks server-side, so the model carries only names, known facts, related entities, and the world introduction — the wiki structurally cannot surface a mechanical secret.
  • Relationship Graph — the same WorldGenGraph the world-gen reveal uses, mounted drained (its shown count equals its total, so the fog field empties and never animates) and interactive for node selection. It renders known-tier edges only.
  • Character Sheet — the in-session SessionSheet (below): the player's own curated sheet with a live HP/condition overlay.

The graph↔wiki bridge is a first-class seam: one selectedEntityId feeds both the wiki and the graph, so a pick on either side highlights the other, and tapping a graph node also switches the active tab to the wiki so the tap lands on that entity's page. A chat-highlight click drives the same seam from the transcript.

The graph renders exactly the snapshot's edges and synthesizes none — the structural secret-edge pin — a relationship between two known entities can still itself be secret (a hidden pact between two people the player has both met). The server already drops those: the snapshot's relationships are filtered to access_level = 'known' with both endpoints in the known set. The canonical snapshotToGraph adapter — shared with the world-gen reveal's rehydration, so there is one known-tier projection rather than a divergent second one — maps each snapshot edge to a graph edge and invents nothing, so a secret edge the server withheld can never reappear on the client. The live E2E seeds a secret known↔known edge and asserts it is absent from the rendered graph.

Entity highlighting in settled prose

When a DM turn settles, DmMessage swaps its plain paragraph for HighlightedProse, which runs the cache's entity index over the text and wraps each recognized name in an EntityMention (a quiet resting underline; hover or focus reveals a small leading type glyph) inside an EntityPopover (a terse card — the name, its type, its first known fact, and an "open in wiki" action that drives the graph↔wiki bridge). The streaming path is byte-unchanged: highlighting only ever applies to settled text, so nothing reflows mid-stream, and segmentation is memoized once per settled row rather than recomputed on every render.

Matching is mechanical and names-only — ZFC, not classification — the matcher (client-core/session/entity-index.ts) is a longest-first, Unicode-boundary-anchored substring match over the known entities' names. It runs no model, classifies nothing, and never pattern-matches on the prose — the narration is displayed verbatim; only the names are matched, against a data-derived index. Only world-lore kinds highlight (npc / location / faction); the player's own name and inventory items fall through unmarked. The type glyph is monochrome — it conveys kind by shape alone, never a colour (spec §6) — so the register stays paper-and-ink, not a tag cloud.

The in-session sheet and its live overlay

The Character Sheet tab is the player's own sheet, curated for play. useSessionSheet resolves the viewer's character off the party roster, fetches the existing member-readable character read, and adapts it to the same curated shape the creation reveal renders — reusing the raw→curated adapter promoted into client-core for exactly this second consumer. Over that static base it lays a live overlay folded from the session's ledger_update frames: the HP readout shows the current hit points the instant an adjust_hp or rest frame lands, and a quiet line logs recent condition changes.

The overlay SETS authoritative values, it doesn't apply deltas — a ledger_update frame carries post-mutation values, not a change amount (an adjust_hp frame sends the new HP; a rest frame also sends the restored HP). So reduceLedger folds by field presence — any frame carrying hp/maxHp/gold sets it — which makes re-applying a frame idempotent, so a reconnect replay of the same frame is harmless. Conditions are the exception: the frame boundary drops the apply/clear flag, so a deterministic active-condition set isn't derivable without parsing prose (a ZFC violation). The overlay therefore keeps a chronological condition log and renders it as recent changes; a maintained active set is a filed follow-up that needs a wire flag. The live E2E confirmed the full ledger_update → reduceLedger → data-live path against a real damage frame.

The rail, the drawer, and one structural mount

usePlayKnowledge is the route brain: it owns the cache, the sheet view-model, and the shared sidebar state (active tab, selection, wiki query, open) that both the chat highlighter and the sidebar read. KnowledgePanel presents it two ways from a single mount — a collapsible ~30% desktop rail (default open) above the lg step, the shipped mount-persistent Drawer below it — chosen by the useViewportBelowLg breakpoint hook.

A JS breakpoint flip, not a pair of CSS Shows — the usual responsive idiom is two sibling Shows, one hidden with display:none. That fails here twice over: the narrow branch is the Drawer, whose content is portaled to <body> — a display:none wrapper can't hide portaled content — and rendering both branches would mount two WorldGenGraph canvases. So the rail↔drawer choice is one structural mount driven by useViewportBelowLg, a design-system hook that flips at the same lg (1024px) boundary the CSS uses, so the JS regime and any lg: styling can never disagree.

Operating this piece

Walk a live session end-to-end (dev)

  1. Bring up the stack (pnpm db:up, pnpm dev for backend + worker, the web app), sign in, and take a campaign through character creation to the play entry. A real session needs live Anthropic credentials.
  2. Enter /campaigns/:id/play. If prep hasn't run you land on the atmospheric prep beat; when it completes, Start debits the owner's session credit and the transcript opens. Type a message — it posts instantly (optimistic), then settles when its seq echo returns — and watch the DM's prose stream in token by token.
  3. Open the same campaign as a second identity mid-session: it should rebuild the full backlog (the lastSeq = 0 seed), then stream live and show typing presence. Press @DM — the summon is visible to both tables and draws a response.
  4. Open the knowledge sidebar (default-open on desktop, the edge-handle Drawer on a ~375px viewport). The World Wiki lists the known entities and its search narrows client-side; the Relationship Graph renders drained (no fog) with known-tier edges only; the Character Sheet shows your own sheet, and an adjust_hp turn moves its HP readout live. Reload — the sidebar reopens and the Network panel shows exactly one world-snapshot GET. To prove enforced ignorance, seed a secret-tier relationship between two known entities and confirm it never appears in the graph.
  5. Kill and restore the connection mid-turn: the turn resyncs without double-rendering. Then end the session (the end_session summon) — the DM renders a send-off, then the screen lands on the recap route.
  6. To inspect the wire, watch the WS frames and the session_messages / credit_ledger rows — the server side is on the session transport page.

Integration points

This screen is the client half of the session transport: it consumes that transport's frames through the shipped WS session client and prep-status SSE, and every start arm maps to a backend precondition documented there. The 402 arm hands off to the billing & credits purchase moment; the full-bleed frame is a declared shared edit with that work on the app shell's AppFrame. The play entry itself is reached from character creation once the party finalizes, and every visible element is a mythrunUI component over the DOM-free client brain. The dice moment (MYT-93) is the first surface built on this reducer's first-class item shape; the knowledge layer (MYT-94) is the next consumer, reading the ledger_update item into its live sheet overlay. That layer reuses the world-gen reveal's WorldWiki and WorldGenGraph and its canonical snapshot→graph adapter, and the creation reveal's curated-sheet adapter, both fed by the one member-readable world snapshot the server filters to the known tier. The session-end recap read is still the outstanding consumer of the reducer's shape.

mythrunUI — the play components

Component Register / behavior
MessageStream The scroller — auto-follow + jump-to-now; instant positioning under reduced motion. Dispatches each item to its renderer and holds a gated turn's DM prose off-screen.
DmMessage · HighlightedProse Serif (--font-body), paper tint, token-streamed, settles on turn end. Settled rows swap in HighlightedProse — entity mentions over the once-per-row segmentation; the streaming path stays byte-identical.
PlayerMessage Mono (--font-ui), own paper band — the mechanical register, no bubbles.
SessionInput Compose + send + the visible @DM explicit-text summon.
SessionStartBeat The 1-bit beat — prep phase (SSE) + connect phase; reduced-motion instant.
ThinkingIndicator DM-thinking + player-typing presence line.
RollCard The in-stream dice moment — skill + posture → Roll → readout → Continue; tier as typographic weight, the constraint never rendered; phase passed in (no reveal runtime).
DieSpin The stepped 2D outlined d20 — eight 45° steps, reduced-motion instant land, result announced via a polite live region.
EntityMention · EntityPopover The in-prose mention (a quiet underline + a monochrome type glyph on hover/focus) and the terse popover card it anchors — name, type, first known fact, "open in wiki".
SessionSheet The in-session curated sheet — the creation-reveal body without the confirm/start-over chrome, with a live HP data-live overlay and a quiet recent-conditions line.
KnowledgeSidebar The three-tab panel (World Wiki · Relationship Graph, drained · Character Sheet) over one snapshot; the graph↔wiki bridge is a first-class seam. Pure wiring — the route owns the state.
