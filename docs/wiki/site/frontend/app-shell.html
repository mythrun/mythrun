App shell & data layer

The application skeleton every flow hangs on: a typed REST data layer, a four-state session gate, the live OAuth sign-in flow, and the React-Router shell — built so the whole client ports to true-native later without an extraction refactor. A new shared package (@mythrun/contract) is the single typed wire source both the backend and the client validate against; the client brain (@mythrun/client-core) owns every backend call, the session store, and the platform interfaces; the web app (@mythrun/web) is a thin shell of route screens plus the web implementations of those interfaces.

Everything that isn't a pixel lives in client-core — the load-bearing constraint. The API client, the React-Query hooks, the session store, the platform interfaces, and the i18n catalog all live in the DOM-free brain; @mythrun/web holds only the router shell, thin screens, and the web implementations of those interfaces under platform/web/**. The native port later re-fills platform/web → platform/native and swaps @mythrun/ui → @mythrun/ui-native; client-core and @mythrun/contract are untouched. There is never a later "lift the data layer out of the app" refactor because it was never in the app.

The shape — four packages, the brain in the middle

The frontend now has four packages, and the dependency arrow points one way: contract ← {backend, client-core} ← @mythrun/ui ← @mythrun/web. @mythrun/contract is the typed wire — the only package the backend consumes. @mythrun/client-core is the platform-agnostic client brain (the component contract and token data from MYT-82, now joined by the data/state/transport layer). @mythrun/ui is the web design system. @mythrun/web is the app — and it stays thin: a route screen composes client-core hooks, @mythrun/ui components, and i18n keys, nothing else (the R5 import boundary).

Two different "contracts," one import-path apart — @mythrun/contract (this new package: Zod wire schemas) is a distinct concept from @mythrun/client-core's src/contract/ (the mythrunUI component prop contracts gated by api-purity). They sit one import-path apart and the new package carries its own minimal Zod-only ESLint config so the two enforcement scopes never collide.

The typed wire — @mythrun/contract

The wire contract is the single typed source of truth for what crosses the network. It carries two kinds of artifact, with deliberately different guarantees.

REST schemas are Zod, and they are authored, not extracted. The two endpoints the home-hub smoke needs had no response schema (both routes reply.send'd a raw repo row), so MYT-83 authors them: MeResponseSchema for GET /api/users/me and CampaignSummarySchema / MyCampaignsResponseSchema for GET /api/campaigns/mine. They model the over-the-wire shape, not the in-memory domain type: a Campaign.createdAt is a Date server-side but JSON-serializes to an ISO-8601 string, so the schema types it z.iso.datetime() (a string validator), never z.date(). /me is a deliberate public projection — it omits cognitoSub, stripeCustomerId, and suspendedAt, so billing-internal fields can never leak over the wire. The backend types its handler return against the schema's inferred type, and client-core derives its types via z.infer from the same schema and validates the response body at runtime.

Zod single source, validated on the client — the alternative (hand-written client types, or codegen) lets the client's idea of a payload drift silently from the server's until a field is quietly wrong in production. Here a single schema is the contract: the backend's return is tsc-linked to it at compile time, and the client parses every response through it at runtime, so a shape drift fails loudly in dev as a ContractValidationError rather than rendering subtly-wrong data. Backend outbound validation is intentionally out of scope (it would risk a live 5xx on a mismatch); the client-side parse is the drift catch.

The realtime event unions moved here as-is. The WebSocket session-transport frames (session-events) and the prep-pipeline SSE event unions (pipeline-events) relocated from backend/src/contract/ so the frontend can consume the same frames the backend produces — setting up the realtime client (MYT-85). These are hand-written TypeScript discriminated unions plus runtime classify* helpers, not Zod, so the move gives the client type safety but no runtime frame validation — and MYT-85's realtime clients consume them exactly that way, as a dumb typed pipe (type-safe, deliberately not re-parsed per frame on the hot streaming path). The backend keeps a one-line re-export shim at the old paths so its existing import sites — and the drift-tested route list — don't churn. The session transport and pipeline status pages tell the server-side protocol stories, and the realtime transport page the client that consumes them; this is just where the unions are now authored.

@mythrun/contract is a built package, not source-.ts — the backend takes its first cross-package runtime dependency here, and it resolves modules with NodeNext, which cannot import a .ts file across a package boundary. A source-only package would typecheck green and then crash the container on import at runtime. So @mythrun/contract emits compiled .js + .d.ts through an exports map, the backend Dockerfile copies and builds it before the backend, and the CI workflows and the pre-push hook build it first as their gate 0. (client-core, on Bundler resolution, can consume either source or built; only the backend forces built.)

The data layer — one seam to the backend

Every backend call is built through a single typed primitive, defineEndpoint. It takes a method, a typed path builder, an optional request schema, and a required response schema — all Zod, from the contract — and compiles to a function (input, ctx) => Promise<Res>. The returned function builds the URL, attaches auth headers, calls universal fetch, maps a non-2xx response to an error, and parses the body against the response schema before handing back typed data. Because request/response are typed as Zod schemas, an endpoint cannot be declared without a contract schema — the conformance lever.

defineEndpoint throws three discriminated error kinds so callers branch on what actually failed instead of parsing a message string:

  • HttpError (carries status) — a non-2xx response. A 401 is special-cased: defineEndpoint first awaits the single-flight token refresh and retries the call once. Only a 401 that survives the refresh surfaces as an HttpError — which then drives the session store + the auth gate, not the generic error screen.
  • ContractValidationError — the response (or a request) failed Zod parse: a backend shape drift, loud in dev.
  • NetworkError — fetch itself rejected (a transport failure).

On top of the primitive sit thin slice hooks — useMe, useMyCampaigns, useBalance — each a one-liner that reads the ambient ApiContext from a client-core React context and hands the endpoint to React-Query's useSuspenseQuery. The hooks are React, not DOM, so they stay R1-clean and a native shell reuses them verbatim. A flow ticket adds its endpoint's schema to the contract and its slice to client-core/api; the pattern never changes — the campaign hub added the useBalance (billing) slice and widened the /mine contract this way, and the play/invite/billing wave added whole slice families the same way — the play-session start/active slices, the invite create/list/revoke/preview/accept slices, and the billing balance/skus/history reads plus the checkout/upgrade-tier/portal mutations (the mutations follow the imperative (ctx, body) shape, not the suspense-hook shape).

fetch directly, no transport interface — fetch is universal (web and React Native both have it) and is explicitly allowed by R1, so it lives in the brain rather than behind a platform interface. The platform-divergent streaming transports (SSE/WS) are a different matter, and ship in MYT-85: the SSE read crosses a StreamingFetch platform seam and the WebSocket is a web global, both on the realtime transport page.

The session gate — four states

The backend distinguishes two authenticated rejections the client must tell apart: 401 unauthenticated (no/invalid token) and 403 username_required (authenticated but not yet onboarded). The session store — a tiny DOM-free Zustand store in client-core/stores — resolves those into the player's auth lifecycle, now four states in lifecycle order:

  • initializing — the boot state. The on-load token refresh has not settled yet (jwt mode), so the client does not yet know who the player is. <RequireAuth> shows a neutral splash here, not a redirect.
  • unauthenticated — no identity (logged out, pre-login, or a failed refresh).
  • onboarding-required — identity known, profile not yet finalized.
  • ready — fully provisioned; the app is playable.

A separate suspended boolean rides alongside the status: an account_suspended rejection lands the player back at unauthenticated but raises the flag, so the sign-in screen can surface a suspension notice instead of silently bouncing. The <RequireAuth> gate reads only the status and resolves it to one of four outcomes — render the splash, bounce to sign-in, bounce to onboarding, or render the matched route — with no token parsing, no backend call, no local intelligence.

A pre-decision initializing state, not a redirect-flash — the three auth-decision states (unauthenticated / onboarding-required / ready) were baked in early so the gate never needed reshaping when acquisition landed. MYT-84 adds the fourth as a distinct pre-decision state. On a fresh load the access token is gone (it lives in memory; see below) and the refresh round-trip is in flight, so the gate has no answer yet. A two-bucket "authed or not" model would read that gap as unauthenticated and flash the player to sign-in for the split second before the refresh resolves them back to ready. initializing plus a splash holds the gate until the boot bootstrap settles it, so a redirect only ever fires on a real answer. (The dev bypass seam, always authenticated, seeds ready directly at boot and never passes through initializing.)

The access token, in memory

Auth headers ride an injected getAuthHeaders() built once from a mode flag, then invoked per request: dev (bypass) sends a static x-mythrun-dev-sub header; prod (jwt) reads the current Cognito access token and sends it as a Bearer (an empty header set before one is acquired). The token itself lives in a module-scoped token manager in client-core/auth — held in a plain variable, in memory only. It is never written to localStorage or sessionStorage, so it is lost on reload and re-acquired from the refresh cookie.

Access token in memory, refresh token in an httpOnly cookie — the standard SPA defense against token theft. A token in localStorage is readable by any script on the page, so a single XSS payload can exfiltrate it; an in-memory variable is not reachable that way and evaporates when the tab closes. The durable half — the long-lived refresh token — is the backend's httpOnly mythrun_refresh cookie, which JavaScript cannot read at all; the client only ever asks the backend to spend it. That server side (the BFF that mints the cookie and the access token) is the Identity page's story; this page covers the client half.

Because the access token is short-lived and lost on reload, a backend call routinely meets a 401. defineEndpoint handles it in one place: on a 401 it awaits runRefresh(), and if the refresh succeeds it rebuilds the request init — so getAuthHeaders re-reads the now-fresh token rather than resending the dead Bearer — and retries the call exactly once. Only if the refresh fails does the 401 fall through to the typed HttpError that resets the session. runRefresh is single-flight: one in-flight POST /api/auth/refresh coalesces N concurrent 401s, so a burst of parallel calls triggers exactly one refresh round-trip and every call retries behind it.

The refresh transport is injected, not imported — the token manager performs the refresh through a function handed to it at boot (configureTokenRefresh), never by importing the session API slice. The 401 retry lives in defineEndpoint, which the auth slices are built from, so a direct import would close the loop endpoint → session → endpoint. Injection keeps the import graph acyclic. The auth endpoints themselves carry skipAuthRetry so a failing refresh cannot recurse through the refresh call, and credentials:'include' is threaded into those cookie-bearing fetches so the browser actually sends and receives the mythrun_refresh cookie on the same-origin /api/auth/* calls.

Acquiring identity — the OAuth sign-in flow

Sign-in is a Cognito Hosted-UI OAuth flow with PKCE, driven entirely from the client brain's auth module and realized by three screens. The sign-in screen (routes/signin.tsx) is the genesis title composition: the stacked brand Lockup over a dithered crown, with two secondary Buttons — Continue with Google, Continue with Discord — each carrying its provider mark in the native icon slot. It reads the session store's suspended flag to show an account-suspended notice when one is pending.

Pressing a provider button begins the flow through the OAuth helper (auth/oauth.ts), the canonical PKCE API: createPkce draws a 256-bit verifier from the platform CSPRNG and S256-hashes it into a challenge; createAuthState mints a random opaque state and persists the {provider, returnTo, verifier} triple single-use, returning {state, challenge}; buildAuthorizeUrl assembles the Hosted-UI authorize URL; and the screen redirects the browser to it through the platform/web navigation helper (screens never touch window.location themselves). The returnTo — the invite hand-off target — is run through an isLocalPath open-redirect guard before it ever rides the round-trip.

The OAuth state store is a platform port — the single-use state triple has to survive the full-page redirect to Cognito and back, but the DOM-free brain cannot reach sessionStorage itself (R1). So OAuthStateStore is a platform-capability interface in client-core/platform — the same pattern as SecureStorage — with a sessionStorage-backed web impl under platform/web, injected at boot via configureOAuth alongside the Cognito config. Its take is a single-use read-and-delete: spending the state exactly once is the CSRF + replay defense. The Cognito config is the public VITE_COGNITO_* build env (the Hosted-UI domain + the public app-client id) bundled into the SPA — PKCE means there is no client secret to hide.

Cognito returns to the callback screen (routes/callback.tsx), which parses code + state (a parse-only step — it never consumes the store itself), verifies the state against the stashed triple, exchanges {code, codeVerifier} for a session by POSTing to the backend BFF (POST /api/auth/session, an Identity endpoint), sets the returned access token in the in-memory token manager, and runs the session adapter. A ready result navigates to the returnTo; an onboarding-required result detours to the onboard screen carrying the pre-fill name.

The onboard screen (routes/onboard.tsx) is the display-name moment: one serif question, one pre-filled Input, one primary Button. deriveUsername turns the provider-supplied name into a backend-valid handle candidate (regex-valid by construction), and a small register error taxonomy maps the backend's 409s — already_onboarded (treat as done), username_taken (re-mutate the candidate and retry, bounded) — plus a 400 display_name_invalid to an inline field error, so a collision resolves without bouncing the player.

Both the callback and the on-load boot funnel through one session adapter (auth/session-adapter.ts). applyMe does a single GET /me and maps the result to the store: 200 → ready, 403 username_required → onboarding-required, 403 account_suspended → suspended, anything else → unauthenticated. bootstrapSession is the boot path: it runs the on-load refresh, then applyMe on success or unauthenticated on failure. The on-load probe is the reason /api/auth/refresh answers 200 with a null token (not a 401) when there is no session: the token manager reads that null as "no session" and the boot settles to unauthenticated without logging a console error on the sign-in screen. The sub the store records is read structurally from the access token's sub claim (jwt-claims.ts — a mechanical base64url decode, no verification; the backend is the verifier).

The adapter settles the store before the Hub's useMe runs — onboarding status is discovered once, at the seam that already knows it (the callback / the boot bootstrap), not lazily inside the first authed screen. By the time <RequireAuth> clears and the home hub's useMe fires, the store is already ready or onboarding-required — so useMe is never the place a player discovers they still need to onboard, and the gate never has to unwind a half-rendered authed tree.

Conformance by construction

The pattern can't be quietly skipped — it is structural, enforced by three rails working together. The defineEndpoint type signature forces a contract schema on every endpoint. The R5 feature import boundary bans bare fetch and @tanstack/react-query inside routes/**, so a screen can't sidestep the primitive by calling useQuery/fetch directly — it imports hooks from client-core only. And the R1 no-restricted-globals lint bans document, window, localStorage, location, navigator, EventSource in client-core and in web outside platform/web/**, keeping the brain DOM-free. Each ships with positive-and-negative wiring tests (a banned global fails; a platform/web use and the lint-exempt app entry pass).

The one allowed DOM touch — frontend/src/main.tsx's document.getElementById('root') mount is the single unavoidable web-only global, and it is lint-exempt the same way vite.config.ts is. The native entry is entirely different, so the exemption is on the entry file, not a pattern that could spread.

Platform interfaces — the native seam

A platform-capability interface lets the brain reach a device capability through a contract rather than a web global. MYT-83 defines exactly one — SecureStorage (the token store), an all-async get/set/remove interface in client-core/platform — and its first web implementation, a localStorage adapter under frontend/src/platform/web/. That single interface-plus-impl establishes the platform/web convention: the brain declares the capability, the web layer realizes it, and the provider root injects the impl so the brain never touches a web global itself. A later native impl (Keychain/Keystore) satisfies the same surface. MYT-85 adds the second one, StreamingFetch — the SSE status client's streamed-read seam (see realtime transport); further interfaces (Share, Push, …) stay deferred — we do not define an interface with no consumer.

The shell — routing, the quiet frame, and the dithered 404

The route tree is a plain RouteObject[] (so tests drive the same array through a memory router) with two branches under one error boundary. The public branch resolves pre-auth — landing, the auth screens, the invite-join link, the shareable recap. The authed branch sits behind <RequireAuth> and renders inside the quiet brand frame: a minimal Parchment-&-Ink header (wordmark · display name · credit balance · a gear settings affordance) wrapping the content <Outlet/>, composed from mythrunUI only. The frame recedes so the narrative/combat content is the focus. The public auth screens — sign-in, callback, onboard — are now wired end-to-end (the OAuth flow above); the remaining player-facing screens are thin i18n'd stubs the flow tickets fill, except the campaign hub, since built out into the app's first full screen — a shelf of book-cover campaign cards with the header's credit balance wired live — and the public landing page (MYT-86), the first public-branch screen built out from a stub. The play/invite/billing wave then filled most of the rest: the live play screen and its full-bleed variant of the frame, the public join route on the public branch, and the Sessions & Billing settings screen and checkout-return routes — and it made the header's credit balance a real quick-buy into that billing surface rather than an interim stub.

The header stays one quiet row at phone width — MYT-83's mobile audit deferred a real bug: at 375px the header overflowed sideways and shoved the settings affordance off-screen, because the layout had no shrink/wrap/truncate to fall back on. MYT-97 fixed it without breaking the brand's single-row frame. The display name is the only flexible item — it truncates and absorbs the row's shrink; the wordmark and credit balance are noShrink so they hold their width instead of squeezing into a spill; and the settings affordance became an icon-only gear IconButton (shrink-0) so a long display name can never push a text label past the edge. Every piece is a responsive mythrunUI primitive, so the fix lives in the design system, not in raw CSS on the frame.
A full-bleed content variant driven by a route handle, not per-screen margins — most screens render inside the frame's padded content box, but the live play screen needs the whole viewport so its transcript scrolls internally. So the play route carries a fullBleed route handle the frame reads to drop the content padding, rather than the screen cancelling it with negative margins. This edit and MYT-95's header credit chrome were declared shared edits to AppFrame up front — the play work owns the content variant, the billing work owns the header — so two parallel worktrees never both restructured the frame's one composition root.
The viewport floor is unconditional now (MYT-102) — the frame used to apply its minHeight="screen" floor only on fullBleed routes. A staging audit found short content (the world-gen loading beat, the calm "setting up the table" holds) leaving the app 626px tall, exposing the page background beneath the app's own surface. The frame now floors to the viewport on every route, and its padded content region carries the new Box grow variant so that region — not the page behind it — absorbs the slack; fullBleed still governs only whether the content padding is dropped.

A route-level error boundary catches any thrown render/loader failure and branches on the typed errors above: a 401 HttpError resets the session to unauthenticated and bounces to sign-in; a ContractValidationError shows a dev-facing "contract drift" message; everything else falls through to a generic retryable screen with a retry affordance. The 404 is the brand's stepped Bayer Dither in its first product use — a full-screen dark dead end where the Dither is a real transition (the cream page-top grading down into a reversed dark surface that fills the viewport), not decoration.

The 404 floor uses 100dvh, not 100vh — a mobile-audit fix. The full-screen dark surface is a reversed Box with a new minHeight="screen" variant that maps to min-h-dvh (the dynamic viewport), deliberately not 100vh. On mobile, 100vh is the height with the URL bar retracted, so a 100vh root is shorter than the page once the bar hides on scroll and leaves a strip of the cream page canvas showing below the dark field. dvh tracks the actually-visible viewport, so the surface fills the screen on mobile and desktop alike. The reversed dark surface itself is the other new Box variant (surface="reversed"); both are mythrunUI additions documented on the Design system page.

The provider stack is the web shell's one composition root: the ThemeProvider, a single QueryClient, the resolved ApiContext (base URL + the injected getAuthHeaders), and the i18n runtime, in that nesting order. An effect inside it re-binds the token manager's refresh transport to the resolved ApiContext whenever that context changes — the steady-state 401-retry path reaches configureTokenRefresh through here.

The on-load boot, though, runs before any of that renders — at module scope in main.tsx, in a fixed order. In jwt mode it calls configureOAuth (web state-store impl + Cognito config), then configureTokenRefresh to bind the refresh transport, and only then kicks off bootstrapSession — so the store starts initializing and the splash covers the gap until the refresh settles it. configureStreamingFetch is wired here too — unconditionally, in both auth modes — binding the SSE transport seam the realtime transport page covers. It is config-driven — main.tsx builds the concrete config from the environment and the web platform impls once at module scope and passes it in — so the shell is testable with fakes and an explicit auth mode. In dev (bypass) main.tsx instead seeds the session store ready once, so the dev app lands on the authed side of the gate against the always-authenticated bypass backend.

The refresh transport is wired at module scope, before bootstrapSession — the on-load refresh is the token manager's single-flight call, and that call is a silent no-op until its transport is injected: with no refreshFn set, performRefresh returns false without ever hitting /api/auth/refresh. The transport used to be wired only in the provider effect above, which runs after the module-scope bootstrapSession — so on every reload the boot refresh fired against a null transport, silently failed, and bounced the user to sign-in, with no /refresh ever reaching the server. Wiring it in main.tsx ahead of the bootstrap is what makes a reload actually re-hydrate the session; the provider effect still re-binds it for the in-app lifecycle (MYT-84).

The landing page

The first real screen on the public branch — the marketing front door, built out from the i18n'd stub the shell shipped with (MYT-86). It is composed entirely from mythrunUI: a nav landmark (the horizontal brand lockup, an inline theme toggle, and a Sign-in button), a centered hero (the stacked lockup, a one-line tagline, the primary call-to-action, and a transparent pricing line), and a theme-inverting footer (terms / privacy / a contact link). The three landmarks are real nav/main/footer elements via the Box as prop, not raw DOM. All copy is [ph_*] i18n placeholder — the brand prose is Miklos's to write — and the CTA and the nav Sign-in both route to /auth/signin through the SPA router, the OAuth flow's entry point.

Visually the page grades into its footer: a page→footer Dither sits between the hero and the footer, and because the footer uses the surface="inverted" field — dark on a light page, light on a dark page — the Dither's direction flips with the theme so it always grades the page into its opposite. The footer-inversion mechanism is a design-system concern; this screen is its first consumer.

The hero centers, the footer pins — a grow spacer, not a fixed footer — the page root is a minHeight="screen" Stack, but a min-height column with no growing child collapses to its content and floats the footer mid-page on a tall desktop. So the hero is wrapped in a Stack grow justify="center": the spacer absorbs the slack, optically centering the hero while the footer settles at the bottom edge. The fix is the same layout-primitive vocabulary the rest of the app uses — no fixed-position footer, no viewport-unit math on the screen itself. (Miklos's visual audit caught the floating footer; the per-component DOM tests could not, since the gap only shows at a viewport taller than the content.)

Gating the screens at phone width

The app-frame header bug lived in the composition layer — not in any one primitive, but in how a screen assembles them — so isolated component stories could never have caught it. MYT-97 closes that gap with a screen-level arm of the mobile-viewport overflow gate: every player-facing screen ships a Storybook story that renders the real route tree through a seeded ScreenHarness, so the 375/1280 sweep measures assembled screens, not just leaves. The harness mounts the actual routes array in a memory router at a seeded entry, pre-seeds the session store to ready (so authed screens clear <RequireAuth>) and the React-Query cache (so a suspense hook resolves without a network call), and can override an i18n key to feed an adversarial-length display name. A screen-story-coverage forcing function (frontend/scripts/screen-story-coverage.mjs) fails CI if any routes/* screen — or the assembled app-frame / 404 screen — lacks a co-located story, so a new screen can't dodge the gate.

A router-bearing seeded harness, not an isolated render — the bug was a composition bug, so the gate has to drive the composition. Seeding the session and cache up front means the authed screens actually render their content; a bad seed shape would hang a suspense query forever, so each story's play asserts the screen's root testid and fails loud instead of timing out as a flake. And because the display name is an i18n key rather than a prop, the only way to exercise a too-long name is to override the key — which is exactly what the adversarial home-hub story does, reproducing the original overflow and proving the gate would have caught it.

Talking to the API

In the deployed build the SPA and the API share one origin: the data layer fetches staging.mythrun.com/api/* — the SPA's own host — and the CloudFront /api/* proxy forwards those to the API. Same-origin is what lets the BFF's refresh cookie be first-party (Safari refuses to store a cross-origin Set-Cookie). Local dev is the one cross-origin case — localhost:5173 calling localhost:3030, which the browser preflights — and the backend's CORS plugin (single allowed origin = the already-validated frontend origin) stays as defense-in-depth either way. That topology, and why the dev proxy pattern stays confined to the internal dev tool, lives on the Backend page.

Operating this piece

Add a REST endpoint to the data layer

  1. Author the response (and any request) Zod schema in frontend/contract/src/rest/, modeling the wire shape (ISO strings for dates, an explicit public projection — never a raw row mirror). Export it from the rest barrel.
  2. Type the backend handler's return against the schema's inferred type (z.infer), so tsc links the two sides.
  3. Add the slice in frontend/client-core/src/api/: a defineEndpoint with the schema, plus a thin useSuspenseQuery hook. Re-export both (and any domain type) from the client-core barrel.
  4. Render it from a screen through the hook only — never a bare fetch or useQuery (the R5 boundary fails the lint otherwise).
  5. Build the contract first (pnpm --filter @mythrun/contract build), then run the frontend-check chain. A fresh tree can't resolve @mythrun/contract/rest until dist/ exists.

Add a player-facing screen

  1. Add the screen (frontend/src/routes/<name>.tsx, or an assembled src/app/ screen) and wire it into the routes array.
  2. Add a co-located <name>.stories.tsx that renders it through ScreenHarness — seed the session status, and the ['campaigns','mine'] cache if it reads a suspense hook — with an expectScreen play that asserts the root testid. The screen-story-coverage gate fails without the story.
  3. Compose mythrunUI primitives and i18n keys only (R5 + no-ad-hoc-ui), then pnpm --filter @mythrun/web build-storybook and test-storybook so the screen clears the 375/1280 overflow gate.

Trace a sign-in end-to-end

  1. Open the sign-in screen and press a provider button. The browser leaves for the Cognito Hosted UI — confirm the authorize URL carries code_challenge_method=S256, the expected identity_provider, and an opaque state.
  2. After the provider, the callback lands at /auth/callback?code=…&state=…. In DevTools, watch POST /api/auth/session succeed and set the mythrun_refresh cookie (httpOnly — visible in the Network response, never in document.cookie). The access token never appears in storage; it lives in memory.
  3. A first-time identity routes to /auth/onboard; an existing one lands on the return-to (the home hub). Reload the page: the store starts initializing, the splash shows, POST /api/auth/refresh fires once, and the session resolves back to ready without a sign-in bounce.
  4. To exercise the refresh-retry, let an access token expire (or clear it) and trigger an authed call: one 401 → one coalesced POST /api/auth/refresh → the call retried once with the fresh Bearer. The server side (the BFF endpoints + the cookie) is covered on the Identity page.
