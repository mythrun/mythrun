Realtime transport

The client half of the live wire: a bidirectional WebSocket session client and a unidirectional SSE status client, both dumb typed pipes with production-grade reconnection, built on one shared connection primitive in the DOM-free brain. The flows (play, world-gen, session-prep) consume frames and a connection-state surface; the transport carries bytes and reconnects — it never interprets a frame or decides a flow's lifecycle. The matching server halves are the Session transport and Pipeline status pages; this is what the SPA runs against them.

Dumb typed pipe, not a frame interpreter — the transport's whole job is delivery: carry frames in order, survive a drop, expose "connecting / reconnecting / failed" for the UI. It deliberately holds no flow knowledge — no turn state, no pipeline state, no idea what a session_end or a finalized frame means. That lives in the flow reducers a later ticket builds. Keeping the seam here a pure pipe is what lets three different flows (play, world-gen, session-prep) reuse the same two clients unchanged, and what keeps the reconnection logic testable in isolation from any one flow's semantics.

Two clients, one connection primitive

Both clients are built on connection.ts — the shared backoff/ceiling state machine. The rule it enforces is shared code, per-instance state: the machine lives once, but each client factory mints its own store via createConnection(), never a module-level singleton, so a live play session and a world-gen status stream hold independent connection state. It owns three things the WS and SSE clients both lean on: the ConnectionState store (connecting → connected → reconnecting{n} → closed, or failed{denied|exhausted}), the backoff schedule (1s → 2s → 4s → 8s → 30s capped, ±10% jitter), and a monotonic generation token for single-flight connects.

The generation token is how a superseded socket self-ignores — every connect attempt takes nextGeneration() and captures the number. A socket's late onclose/onmessage callback compares its captured token to the current generation() and bails if it has been superseded — by a newer reconnect, or by an explicit close(). Without it, a backoff reopen racing a slow close handler could double-open, or a torn-down client could still route a stale frame. The counter is the one place that race is resolved, so neither client re-implements it.

The attempt counter resets on a successful open, so cumulative drops over a long session never trip the ceiling — only consecutive failures do. At the ceiling (≈10 straight), the next drop yields failed{exhausted}, which is re-armable: a flow may call the client's connect()/open() again to start a fresh cycle. The React read seam is useConnectionState(client) — it subscribes a component to the client's store so flows and the harness render "Reconnecting…" without importing zustand directly.

The backoff timer lives in the client, not the primitive — the connection module defines the schedule (nextDelayMs()) and the ceiling decision (recordDrop()), but the actual setTimeout handle is owned by each client. That client MUST clear it before any markClosed()/reset() and in close(), so a pending reopen can never fire into a torn-down client. The primitive documents the contract; the client holds the timer it has to be able to cancel.

The WebSocket session client — the bidirectional play pipe

createWsSessionClient(ctx) is the play transport. A connect(sessionId) runs a fixed sequence: a pre-flight runRefresh() (refresh the access token before anything), then mintWsTicket — POST /api/sessions/:id/ws-ticket — then new WebSocket(wss://…/ws/session/:id?ticket=…). The access token never rides in the WS URL; the single-use ticket gates the upgrade instead. Inbound frames are JSON-decoded and dispatched to onFrame subscribers; send(frame) writes a client frame back but returns false (no write, no throw) unless the live socket is OPEN, so a flow can retry an unsent frame rather than lose it silently.

A ticket in the URL, because a browser WebSocket can't send an Authorization header — the native WebSocket constructor takes a URL and (optionally) a subprotocol, nothing else; there is no header API. So auth can't ride the upgrade as a Bearer. The SPA mints a short-lived single-use ticket over authenticated REST first (the mint inherits defineEndpoint's 401 refresh-retry), then passes it as the ?ticket query param. The server handshake consumes it atomically pre-upgrade. A fresh ticket is minted on every (re)connect — tickets are single-use, so a reconnect can't replay the last one.

The reconnection is the production-grade part, and it has two moving pieces beyond the shared primitive: seq dedup and whole-turn replay. The client tracks a lastSeenSeq high-water mark, advanced per emitted seq-bearing frame in seq order (never batch-set to the max). On a transient drop, the backoff reopen connects with ?lastSeq=<high-water>, and the server replies with a session_reconnect replay batch. The client filters that batch — discarding any row at or below the high-water mark (the load-bearing register-before-replay overlap) — and emits the filtered batch. It does not interpret the batch further: the whole-turn (turnId) replace over those rows is the flow reducer's job downstream. The transport does the mechanical seq filter and nothing more.

Close-routing is on readable signals only — every socket close is transient — the client treats every WebSocket close code (1006 abnormal, 1011 any reason) as a transient drop that earns a backoff reconnect, because the readable terminal signals live elsewhere: a session_end data frame self-closes the client to closed, and a ticket-POST 403/404 (no session / not a member) routes straight to failed{denied}. A 401/429/503 or a network error on the ticket POST is transient, not terminal — a 401 has already exhausted defineEndpoint's own refresh-retry, and the lossy refresh boolean must not be allowed to strand a recoverable hiccup as a permanent failure. So the only two ways to leave the reconnect loop for good are an explicit denial or a data-frame end — a dropped tunnel always retries.

A DEV-only __simulateDrop() closes the live socket to exercise the reconnect-replay path by hand; its body dead-code-eliminates from the production bundle (Vite inlines import.meta.env.DEV), so it ships nothing to players. It is what the /dev/transport harness drives.

The SSE status client — the unidirectional status pipe

createSseStatusClient(ctx) drives a status UI — world-gen and session-prep both stream their pipeline progress as Server-Sent Events. open(path) starts the cycle; subscribers attach via onEvent (decoded PipelineEvents) and onSnapshot (the raw first-frame snapshot, which is not a PipelineEvent). All the framing, decoding, and reconnection lives in the brain: it reassembles blank-line-delimited SSE frames across chunk boundaries, strips the leading-space-after-colon, joins multi-line data: fields, and skips comment keepalives. The transport never auto-closes on a data frame — a finalized event is per-entity, not terminal — so the consuming flow calls close() on its own terminal event.

fetch + a ReadableStream, never EventSource — the native EventSource has the same blind spot as the raw WebSocket: it can't set an Authorization header, so it can't carry the SPA's Bearer. The SSE stream therefore rides an authenticated fetch whose body is read as a stream. EventSource is a banned global in the brain (R1) precisely so this can't be quietly reintroduced. This mirrors the dev tool's own sse-client.ts openSse(), which solved the same problem the same way.

Open-status routing is the only observable signal the client branches on: a 403/ 404 is terminal failed{denied} (no session / not a member); any other non-200 (401, 429, 503, or a CloudFront-generated 502/504) is transient and earns a backoff reconnect; and a stream that simply ends — a clean end, an event: close frame, or a mid-read error (the wifi-drop case) — is also transient. The ceiling bounds the retries to failed{exhausted}, re-armable by a fresh open().

The StreamingFetch seam — the one platform-divergent piece

Everything above is platform-neutral and lives in @mythrun/client-core. The single exception is the actual streamed HTTP read, which needs fetch + ReadableStream + a streaming TextDecoder. The brain reaches it through a one-method port, StreamingFetch: given a URL and { headers, signal }, it resolves once the response head is available (not once the body completes) with { status, chunks } — the open status so the brain's non-200 routing is observable, and an async-iterable of raw decoded text chunks (the SSE client owns the framing). The web implementation, createWebStreamingFetch, lives under frontend/src/platform/web/ — the sanctioned web-globals carve-out — and is ctx-free: the brain computes auth and hands it mode-correct headers; the impl just applies them.

Injected at boot, unconditionally, both auth modes — the seam is wired with configureStreamingFetch() at module scope in main.tsx, the same injection pattern as configureTokenRefresh — so the brain never imports the web impl and the import graph stays acyclic. Unlike the token-refresh seam (jwt-mode only), this wiring is unconditional: a streamed read is the same shape in dev-bypass and jwt mode, only the headers differ. getStreamingFetch() throws if the boot wiring never ran — a wiring bug should fail loud, not be a runtime condition the brain branches on.
The frames are typed, but not Zod-validated at runtime — the relocated contract event unions give the client compile-time ServerFrame/PipelineEvent types, but the transport does not parse each frame through a runtime schema (unlike a defineEndpoint REST response, which always does). A dumb typed pipe trusts the wire: the backend validates every outbound frame against the contract before it sends, so a second client-side parse on a hot streaming path would buy little and cost per-frame CPU. The one Zod schema here is WsTicketResponse — a single short REST body on the cold connect path, where the validation is cheap and the contract guarantee is worth it.

Operating this piece

Drive the realtime transport by hand (/dev/transport)

  1. Run the SPA in dev (pnpm --filter @mythrun/web dev) and open /dev/transport. The route is registered React.lazy over a DEV-only import, so the harness chunk is excluded from the production bundle entirely — it is not a player-facing screen.
  2. In the WebSocket panel, enter an active session id and press Connect. Watch the status chip go connecting → connected and a session_ready frame land in the inbound log. Send a player_message; it round-trips back.
  3. Press Simulate drop to fire __simulateDrop(). The chip flips to reconnecting with a climbing attempt count, then back to connected, and a session_reconnect replay batch arrives — the production reconnection path, exercised against the real wire.
  4. In the SSE panel, open a status path (a world-gen or session-prep stream) and watch decoded events accrue in its log; Close tears the stream down to closed.

Integration points

The server halves this client talks to are the Session transport (the ticket handshake, the SessionHub fan-out, the session_reconnect replay this client dedups) and the Pipeline status SSE subscriber. The ticket itself is minted on the access control & WS ticket route. The wire ServerFrame/ClientFrame and PipelineEvent unions, plus the WsTicketResponse REST schema, are authored in @mythrun/contract, and the mintWsTicket endpoint is a defineEndpoint slice from that page's data layer (inheriting its 401 refresh-retry). In the deployed build the ticket mint rides the CloudFront /api/* behavior and the WS upgrade rides the /ws/* behavior — both on the SPA's own origin — which is also where the 60s origin-read timeout that keeps an idle socket alive past the heartbeat lives. The whole transport is verified against staging by the WS-transport smoke.
