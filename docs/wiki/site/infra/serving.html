Serving

The compute platform that runs the API and the Worker. A shared ECR repo, an ECS cluster, and the ALB on one side; per-env task definitions, services, target groups, and the GitHub-Actions deploy role on the other.

How it fits together

Serving splits along the same shared-vs-per-env line the rest of the infra does. The shared workspace owns the resources that would be wasteful or confusing to duplicate — one ECR repo, one GitHub OIDC provider, one ECS cluster, one ALB, one HTTPS listener. The per-env workspace (today only staging/) consumes those through terraform_remote_state and adds everything that has to exist twice by nature: task definitions, services, a target group, a listener rule, a DNS A-alias, a scoped GitHub Actions IAM role, and an SNS alerts topic.

Shared compute platform

The ECR repo is named mythrun and is shared by both the API and the Worker container definitions — same image, different command. Scan-on-push is enabled. The lifecycle policy expires untagged images after a day and keeps only the 20 most recent tagged images.

MUTABLE tag mutability, not IMMUTABLE — CI pushes the same image under two tags (:latest alongside :$GIT_SHA), and an immutable repo would reject every second :latest push. Git-SHA immutability is instead a CI-discipline concern: never re-push the same SHA tag.

One aws_iam_openid_connect_provider for token.actions.githubusercontent.com lives in the shared workspace. Both the staging role and the future production role will trust this same provider. The thumbprint_list is omitted — AWS has done native JWK discovery for GitHub's OIDC endpoint since 2023, and the field is optional in the v6 provider.

The ECS cluster is named mythrun and offers only Fargate as a capacity provider. Container Insights is disabled to save the per-task fee; first-deploy debugging relies on raw CloudWatch Logs and describe-tasks.

The ALB is a single internet-facing application load balancer in the public subnets with the shared alb security group. It has HTTP/2 on, invalid-header dropping on, a 3600-second idle timeout for WebSocket tolerance, and deletion protection on. Two listeners hang off it: :80 permanently redirects to :443; the :443 HTTPS listener terminates TLS with the wildcard ACM cert from the DNS module and uses ELBSecurityPolicy-TLS13-1-2-2021-06. Its default action is a plain 404; matching traffic is routed by per-env listener rules attached from the serving module.

Deletion protection on the shared ALB — the ALB serves both staging and the future production environment. Any terraform destroy accident that took it out would cut both at once. Flipping the flag to false is a deliberate, separately-reviewed change.

Per-env task definitions and services

The serving module produces the per-env surface: two CloudWatch log groups (/mythrun/<env>/api, /mythrun/<env>/worker), two IAM roles, two task definitions, a target group, a listener rule, two ECS services, and a Route 53 A-alias record. Every resource is named mythrun-<env>-* so staging and production never collide.

Two IAM roles sit behind each task: the task-execution role is what ECS uses before the container starts — pulling the image, fetching secrets from Secrets Manager, shipping the first log line. The task role is what the app assumes at runtime; today it only grants cloudwatch:PutMetricData under the Mythrun/<env> namespace. Both use the AmazonECSTaskExecutionRolePolicy baseline plus an explicit per-ARN secrets policy.

Per-ARN secrets list, not a wildcard — a naive mythrun/<env>/* wildcard would miss the one secret whose path doesn't match the env prefix: mythrun/shared/redis-auth. Enumerating ARNs makes that boundary explicit. The RDS master secret (rds!db-*) is deliberately absent — the app runs as the per-env mythrun_<env> user, not the master.
No explicit kms:Decrypt statement — all six referenced secrets use the AWS-managed aws/secretsmanager key, for which AmazonECSTaskExecutionRolePolicy already allows decrypt transparently. The day any secret moves to a customer-managed CMK, that ResourceInitializationError becomes a readable signal to add a scoped statement.

Task definitions are registered pointing at ecr_repository_url:placeholder — a tag that doesn't exist. Registration is pure metadata and does not pull the image; with desired_count = 0 on both services, ECS never tries. CI replaces both pieces on first deploy: it registers a new task-def revision pointing at the real :<git-sha> tag and flips desired_count to 1 via update-service. A lifecycle.ignore_changes = [desired_count, task_definition] on each service keeps Terraform permanently out of CI's way afterwards.

Services are owned by Terraform, revisions are owned by CI — Terraform creates the service once and hands off desired_count and task_definition forever. Any other shape (Terraform re-creates the service on every deploy, or CI creates the service) either produces zero-downtime-breaking replacements or splits ownership so state and reality drift apart.

The API's container definition exposes 3000, runs node --max-old-space-size=768 dist/server.js, declares a container-level HEALTHCHECK that curls http://localhost:3000/health through Node's own http module, and has a 120-second stopTimeout. The Worker mirrors the API but omits the port mapping and the container healthcheck — the worker doesn't exist yet, and the internal BullMQ-pingable HTTP server on :3001 that the spec calls for is deferred to the Prep Pipeline milestone.

Both task definitions pull the same six secrets: ANTHROPIC_API_KEY, STRIPE_SECRET_KEY, STRIPE_WEBHOOK_SECRET, COGNITO_CLIENT_SECRET, DB_PASSWORD, REDIS_AUTH_TOKEN. The first four are per-env manual shells (values set in the AWS console out-of-band); DB_PASSWORD is the per-env RDS secret that bootstrap-databases.sh populates; REDIS_AUTH_TOKEN is the cross-env mythrun/shared/redis-auth. Environment variables (DB_HOST, REDIS_HOST, NODE_ENV, PORT, and friends) are plain values the app composes into a DATABASE_URL at startup.

DB_PASSWORD has no :password:: suffix on valueFrom — bootstrap-databases.sh writes the secret value as a plain string (--secret-string "$pw"), not as a JSON object. The moment it becomes JSON, the valueFrom needs a JSON-path suffix.

ALB routing and DNS

The per-env target group is a Fargate-compatible (target_type = "ip") group that health-checks /health on :3000. healthy_threshold is 2 (AWS rejects the spec's original value of 1); the deregistration_delay of 120 seconds matches the container stopTimeout so in-flight LLM calls get grace during rolling deploys; stickiness is off because session state lives in Redis; slow-start is explicitly disabled.

A single host-based listener rule routes staging-api.mythrun.com (or api.mythrun.com in production) to that target group. Priority is reserved in the 100-299 band: production = 100, staging = 200. Production wins if hosts ever accidentally collide.

A Route 53 A-alias record in the shared zone points <env>-api.mythrun.com at the ALB's DNS name. The alias uses the ALB's own hosted zone ID, not the Route 53 zone ID, and disables Route 53 health-checking since the ALB already owns it.

The GitHub Actions deploy role

mythrun-github-actions-staging is the role CI assumes to push images and update services. Its trust policy is deliberately boring: every condition is StringEquals, never StringLike. The federated principal is the shared OIDC provider; five conditions narrow who can assume it.

  • aud = sts.amazonaws.com — the standard audience check.
  • repository = mythrun/mythrun — only this repo.
  • repository_owner_id = 274691930 — the numeric org ID, immune to rename or reclaim attacks.
  • environment = staging — requires the GitHub Environment named staging (configured separately in repo settings).
  • ref = refs/heads/main — belt-and-suspenders on top of the Environment's own branch protection.
  • sub = repo:mythrun/mythrun:environment:staging — redundant with the above, but AWS IAM rejects CreateRole unless :sub is pinned explicitly.
All StringEquals, no StringLike — the two operators would behave identically today because none of the values contain wildcards, but swapping to StringLike invites a future refactor that introduces a real wildcard to silently broaden who can assume the role. Keeping the operator strict is free insurance.

The permissions policy grants exactly what a deploy needs: an account-wide ecr:GetAuthorizationToken (AWS doesn't let it be ARN-scoped), the ECR push/pull verbs scoped to the mythrun repo, ECS UpdateService / DescribeServices / DescribeTasks / ListTasks conditioned on the mythrun cluster, RegisterTaskDefinition and DeregisterTaskDefinition scoped to the mythrun-staging-* family, and iam:PassRole on the two task roles conditioned on iam:PassedToService = ecs-tasks.amazonaws.com. Production snapshot permissions (rds:CreateDBSnapshot) are deliberately absent; they belong to the future production role.

SNS alerts topic

mythrun-staging-alerts is the SNS topic that CloudWatch alarms will eventually publish to. It lands with a single email subscription to miklos@mythrun.com and is encrypted at rest with the AWS-managed alias/aws/sns key. The email subscription starts in PendingConfirmation and stays there until the recipient clicks the AWS-sent confirmation link — that confirmation is not a Terraform-managed attribute, so re-running apply while pending is a no-op.

Topic now, alarms later — MYT-30 stops at the topic and subscription so first-deploy surfaces (ECS CircuitBreaker rollbacks, task failures) have a destination the day they're wired up. The actual alarm resources live in the Observability milestone.

Operating this piece

Confirm the alerts email subscription

  1. Run aws sns list-subscriptions-by-topic --topic-arn <mythrun-staging-alerts ARN> --query 'Subscriptions[0].SubscriptionArn'.
  2. If it prints PendingConfirmation, open the inbox for the alerts_email address (miklos@mythrun.com by default) and click the AWS confirmation link.
  3. Re-run the same command; the ARN should now be the full subscription ARN.

Rotate a manual secret value

  1. Manual secrets (anthropic-api-key, stripe-secret-key, stripe-webhook-secret, cognito-client-secret) have ignore_changes = [secret_string] on their Terraform version — safe to update out-of-band.
  2. aws secretsmanager put-secret-value --secret-id mythrun/<env>/<name> --secret-string <value>.
  3. Roll the ECS service so running tasks pick up the new version: aws ecs update-service --cluster mythrun --service mythrun-<env>-api --force-new-deployment.

Deregister an old task-definition revision

  1. AWS never deletes task-def revisions, only marks them INACTIVE. Old revisions accumulate but cost nothing.
  2. To prune: aws ecs list-task-definitions --family-prefix mythrun-<env>-api then aws ecs deregister-task-definition --task-definition mythrun-<env>-api:<N>.
  3. Do not deregister the revision currently pinned to a running service — describe the service first to confirm the revision numbers don't overlap.

Integration points

ECS tasks launch into the network module's private subnets under the ecs security group. Task definitions read secrets from the data plane (per-env rds-password, shared redis-auth) and the manual per-env secret shells. The ALB uses the wildcard ACM cert from the DNS module, and the per-env A-alias is published into the same Route 53 zone. The Backend image built from backend/Dockerfile is what gets pushed to ECR and pointed at by task definitions on every deploy.
