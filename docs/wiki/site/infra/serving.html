Serving

The compute platform that runs the API and the Worker. A shared ECR repo, an ECS cluster, the ALB and the GitHub-Actions build role on one side; per-env task definitions, services, target groups, the scoped deploy role, the alerts topic, and the alarms that watch this environment on the other.

How it fits together

Serving splits along the same shared-vs-per-env line the rest of the infra does. The shared workspace owns the resources that would be wasteful or confusing to duplicate — one ECR repo, one GitHub OIDC provider, one ECS cluster, one ALB, one HTTPS listener, one image-build IAM role. The per-env workspace (today only staging/) consumes those through terraform_remote_state and adds everything that has to exist twice by nature: task definitions, services, a target group, a listener rule, a DNS A-alias, a scoped GitHub Actions deploy role, an SNS alerts topic, and the alarms whose subject is this environment.

Shared compute platform

The ECR repo is named mythrun and is shared by both the API and the Worker container definitions — same image, different command. Scan-on-push is enabled. The lifecycle policy expires untagged images after a day and keeps only the 50 most recent tagged images.

50-image retention, not 20 — CI pushes :$GIT_SHA and :latest on every deploy to main, so each deploy consumes two of the retention slots. Twenty would give roughly ten deploys of rollback headroom; fifty gives about twenty-five. Storage cost is negligible at backend-image size.

Alongside the mythrun repo, the shared workspace declares an aws_ecr_pull_through_cache_rule whose upstream is public.ecr.aws. Base-image pulls (node:24-alpine and friends) route through this cache instead of Docker Hub directly: CI's docker build passes --build-arg BASE_IMAGE_REGISTRY=$REGISTRY and the Dockerfile's FROM resolves to <account>.dkr.ecr.<region>.amazonaws.com/ecr-public/docker/library/node:24-alpine. Cache repos under the ecr-public/* prefix are auto-created on first pull.

Upstream is ECR Public, not registry-1.docker.io — AWS's pull-through cache for Docker Hub proper now requires Secrets Manager-stored auth credentials (policy change, 2026). public.ecr.aws is AWS's official auth-free mirror of Docker Hub's Library namespace. Same images, no credentials path, no rate-limit exposure.
MUTABLE tag mutability, not IMMUTABLE — CI pushes the same image under two tags (:latest alongside :$GIT_SHA), and an immutable repo would reject every second :latest push. Git-SHA immutability is instead a CI-discipline concern: never re-push the same SHA tag.

One aws_iam_openid_connect_provider for token.actions.githubusercontent.com lives in the shared workspace. Both the staging role and the future production role will trust this same provider. The thumbprint_list is omitted — AWS has done native JWK discovery for GitHub's OIDC endpoint since 2023, and the field is optional in the v6 provider.

The ECS cluster is named mythrun and offers only Fargate as a capacity provider. Container Insights is disabled to save the per-task fee; first-deploy debugging relies on raw CloudWatch Logs and describe-tasks.

The ALB is a single internet-facing application load balancer in the public subnets with the shared alb security group. It has HTTP/2 on, invalid-header dropping on, a 3600-second idle timeout for WebSocket tolerance, and deletion protection on. Two listeners hang off it: :80 permanently redirects to :443; the :443 HTTPS listener terminates TLS with the wildcard ACM cert from the DNS module and uses ELBSecurityPolicy-TLS13-1-2-2021-06. Its default action is a plain 404; matching traffic is routed by per-env listener rules attached from the serving module.

Deletion protection on the shared ALB — the ALB serves both staging and the future production environment. Any terraform destroy accident that took it out would cut both at once. Flipping the flag to false is a deliberate, separately-reviewed change.

Per-env task definitions and services

The serving module produces the per-env surface: two CloudWatch log groups (/mythrun/<env>/api, /mythrun/<env>/worker), two IAM roles, two task definitions, a target group, a listener rule, two ECS services, a Route 53 A-alias record, and the alarms that watch them. Every resource is named mythrun-<env>-* so staging and production never collide.

Staging keeps 30 days of logs, not the module's 14 — two weeks is shorter than the interval at which a subtle bug gets noticed, so an incident that opens with “when did this start?” runs out of logs before it runs out of questions. At roughly a gigabyte a month the difference is cents; the production composition should pass 90. The 14-day default stays as the conservative floor for a bring-up, and the staging workspace holds its value in one local so a future bump moves every log group it owns together. The migrate task's group is deliberately outside that: its lifetime is a schema history, not an incident window.

Two IAM roles sit behind each task: the task-execution role is what ECS uses before the container starts — pulling the image, fetching secrets from Secrets Manager, shipping the first log line. The task role is what the app assumes at runtime; today it only grants cloudwatch:PutMetricData under the Mythrun/<env> namespace. Both use the AmazonECSTaskExecutionRolePolicy baseline plus an explicit per-ARN secrets policy.

Per-ARN secrets list, not a wildcard — a naive mythrun/<env>/* wildcard would miss the one secret whose path doesn't match the env prefix: mythrun/shared/redis-auth. Enumerating ARNs makes that boundary explicit. The RDS master secret (rds!db-*) is deliberately absent — the app runs as the per-env mythrun_<env> user, not the master.
No explicit kms:Decrypt statement — all seven referenced secrets use the AWS-managed aws/secretsmanager key, for which AmazonECSTaskExecutionRolePolicy already allows decrypt transparently. The day any secret moves to a customer-managed CMK, that ResourceInitializationError becomes a readable signal to add a scoped statement.

Task definitions are registered pointing at ecr_repository_url:placeholder — a tag that doesn't exist. Registration is pure metadata and does not pull the image; with desired_count = 0 on both services, ECS never tries. The CI/CD pipeline replaces both pieces on first deploy: it registers a new task-def revision pointing at the image's digest and flips desired_count to 1 via update-service. A lifecycle.ignore_changes = [desired_count, task_definition] on each service keeps Terraform permanently out of CI's way afterwards. Both task-definition resources also carry lifecycle { create_before_destroy = true } so argument changes (env var edits, memory resizes, log-group renames) register the new revision before deregistering the old, instead of tearing the service's revision out from under it.

Services are owned by Terraform, revisions are owned by CI — Terraform creates the service once and hands off desired_count and task_definition forever. Any other shape (Terraform re-creates the service on every deploy, or CI creates the service) either produces zero-downtime-breaking replacements or splits ownership so state and reality drift apart.
The flip side: TF env-var changes don't roll the service — because of ignore_changes = [task_definition], a terraform apply that adds an env var or rotates a secret reference REGISTERS a new task-def revision but the live service keeps pointing at whatever CI last deployed. Engaging the new revision needs a CI run (which re-renders the real ECR digest into a fresh revision and calls update-service). See CI/CD for why force-rolling onto the TF-registered revision directly is the wrong move.
create_before_destroy on task defs — Terraform-initiated destroy-and-replace fires on any task-def argument change that can't be modified in place. Without the lifecycle flag, that sequence deregisters the currently-live revision before the replacement exists, and ECS momentarily has no revision to fall back to if a concurrent auto-scaling event runs. With the flag, the new revision is registered first and the old one deregistered only after.

Today, after the first CI deploy, both mythrun-staging-api and mythrun-staging-worker run at desired_count=1 on real git-SHA-addressed revisions. MYT-49 closed the worker's Phase 0: the worker service ships a BullMQ-aware entrypoint with stub processors and a /health Fastify probe, and CI's deploy-staging-worker job flips it to desired_count=1 on first deploy the same way the API job does.

The API's container definition exposes 3000, runs node --max-old-space-size=768 dist/server.js, declares a container-level HEALTHCHECK that curls http://localhost:3000/health through Node's own http module, and has a 120-second stopTimeout. The Worker mirrors that shape: it runs node --max-old-space-size=768 dist/worker.js, declares portMappings = [{ containerPort = 3001, protocol = "tcp" }] for the internal Fastify /health server, and carries its own container-level healthCheck block that curls http://localhost:3001/health on the same cadence as the API (interval 30s, timeout 5s, retries 3, startPeriod 60s). The :3001 port is task-internal — there is no target group, no ALB listener — the endpoint exists solely so ECS can probe BullMQ + Redis + pg liveness from inside the task.

60-second startPeriod on the worker healthCheck — worker cold boot is heavier than the API's: BullMQ loads its Lua scripts into Redis, both Redis clients ping() in sequence, pg SELECT 1 runs, then Fastify binds on 3001. The same value as the API leaves enough slack for an Opus-tier dependency hiccup without trading off fast recovery once the task is up. The .on('error', ...) branch on the Node curl command is what catches connection-refused during boot — without it, the healthcheck would flap from "unknown" straight to "unhealthy" before the grace expires.

The worker service also carries health_check_grace_period_seconds = 120 on the ECS service itself — first-deploy cold-start headroom for image pull + Node boot + Redis × 2 + pg + Fastify binding all happening before the first healthCheck probes fire. The API service uses the same value for the same reason.

Both task definitions pull the same seven secrets: ANTHROPIC_API_KEY, VOYAGE_API_KEY, STRIPE_SECRET_KEY, STRIPE_WEBHOOK_SECRET, COGNITO_CLIENT_SECRET, DB_PASSWORD, REDIS_AUTH_TOKEN. The first four are per-env manual shells (values set in the AWS console out-of-band — see the Voyage key runbook for the one that ships as a placeholder); DB_PASSWORD is the per-env RDS secret that bootstrap-databases.sh populates; REDIS_AUTH_TOKEN is the cross-env mythrun/shared/redis-auth. Environment variables (DB_HOST, REDIS_HOST, NODE_ENV, PORT, REGION_PREFIX, MYTHRUN_ENV, and friends) are plain values the app composes into a DATABASE_URL at startup. MYTHRUN_ENV is wired from var.environment and feeds the Redis key prefix the app concatenates as ${MYTHRUN_ENV}:${REGION_PREFIX}: — load-bearing because staging and production share one ElastiCache cluster and would otherwise collide in keyspace. A per-env extra_env input on the module appends additional name/value pairs onto common_env — staging passes BOOT_GATE_ENABLED=1 through it; production will set the same when its workspace lands at Launch.

extra_env is per-env, not a module-default — the boot gate is a per-environment switch, not a module-shape decision. Threading it through a typed list(object({name,value})) input keeps the module locals clean and forces every consumer workspace to be explicit. The downside is the default-[] footgun: a future env that forgets to set the flag silently launches with the gate OFF and all data-layer code dormant. A follow-up bead tracks a guard.
DB_PASSWORD has no :password:: suffix on valueFrom — bootstrap-databases.sh writes the secret value as a plain string (--secret-string "$pw"), not as a JSON object. The moment it becomes JSON, the valueFrom needs a JSON-path suffix.

ALB routing and DNS

The per-env target group is a Fargate-compatible (target_type = "ip") group that health-checks /health/ready on :3000 — the backend's readiness route, which probes the data layer (pg + both Redis instances) on every check. healthy_threshold is 2 (AWS rejects the spec's original value of 1); the deregistration_delay of 120 seconds matches the container stopTimeout so in-flight LLM calls get grace during rolling deploys; stickiness is off because session state lives in Redis; slow-start is explicitly disabled.

ALB on /health/ready, container HEALTHCHECK on /health — a Redis blip should drop the task out of the ALB rotation while it self-heals, not trigger an ECS task replacement and a cold start. Liveness (process is alive) and readiness (process can serve right now) want different recovery paths, so they get different endpoints and different watchers.

A single host-based listener rule routes staging-api.mythrun.com (or api.mythrun.com in production) to that target group. Priority is reserved in the 100-299 band: production = 100, staging = 200. Production wins if hosts ever accidentally collide.

A Route 53 A-alias record in the shared zone points <env>-api.mythrun.com at the ALB's DNS name. The alias uses the ALB's own hosted zone ID, not the Route 53 zone ID, and disables Route 53 health-checking since the ALB already owns it.

The GitHub Actions roles

mythrun-github-actions-staging is the role CI assumes to push images and update services. Its trust policy is deliberately boring: every condition is StringEquals, never StringLike. The federated principal is the shared OIDC provider; five conditions narrow who can assume it.

  • aud = sts.amazonaws.com — the standard audience check.
  • repository = mythrun/mythrun — only this repo.
  • repository_id = 1216403029 — the numeric repo ID, immutable across org or repo renames, strictly stronger than pinning owner-only.
  • environment = staging — requires the GitHub Environment named staging (configured separately in repo settings).
  • ref = refs/heads/main — belt-and-suspenders on top of the Environment's own branch protection.
  • sub = repo:mythrun/mythrun:environment:staging — redundant with the above, but AWS IAM rejects CreateRole unless :sub is pinned explicitly.
repository_id, not repository_owner_id — AWS's IAM allowlist of supported GitHub OIDC condition keys does not include repository_owner_id; sts:AssumeRoleWithWebIdentity silently fails with an opaque error when that key is used. repository_id is on the allowlist and achieves the same rename-resistance — pinning a specific repo ID implies a specific owner.
All StringEquals, no StringLike — the two operators would behave identically today because none of the values contain wildcards, but swapping to StringLike invites a future refactor that introduces a real wildcard to silently broaden who can assume the role. Keeping the operator strict is free insurance.

A sixth condition is written but switched off. pin_job_workflow_ref adds a job_workflow_ref equality check against an enumerated list of workflow files, so only those files can assume the role rather than anything merged to main inside the staging environment. The list is derived from every workflow that names the staging role — today deploy.yml, the reusable _db-migrate-job.yml, deploy-frontend.yml, and bootstrap-db-build.yml.

The workflow pin defaults to off — a wrong ref string doesn't degrade, it locks every deploy job out of AWS until someone reverts, and the claim's exact value can't be confirmed from outside a real workflow run. The safe order is: decode the OIDC token in a throwaway workflow step, compare it against the enumerated list, then flip and watch the next run. A reusable workflow is the subtle case — its jobs report their own file as job_workflow_ref, not the caller's, so the caller's entry does not cover it.

The build / deploy split

The image-build half of CI has its own role, mythrun-github-actions-build, declared in the shared workspace. It can authenticate to ECR, push to the mythrun and mythrun-bootstrap-db repositories, and create + import through the ecr-public/* pull-through cache prefix. It has no ECS authority and no iam:PassRole at all.

A compromised build should be able to push an image and nothing more — the build job's whole purpose is to run third-party code with AWS credentials in the environment: a pinned action, a pnpm postinstall script, a Dockerfile's RUN lines. On the single-role shape, anything that compromises one of those steps inherits the authority to roll a new task definition into the running cluster. Split, a compromised build produces a bad image and something still has to choose to deploy it. For staging alone the blast radius made the single role acceptable; for production it does not, which is why the split lands before the production deploy job is enabled.
The build role is shared, the deploy roles are per-env — it is environment-agnostic by construction: it pushes to the two shared ECR repositories, and the images it produces are the same images every environment deploys. Declaring it in the shared workspace means the production composition inherits one build role instead of minting a second with identical permissions.

The cutover is deliberately sequenced and gated rather than done in one commit, because it spans Terraform, GitHub settings, and workflow files. Applying the shared workspace creates the role and changes nothing — no workflow assumes it yet. A build GitHub Environment has to exist (with its own AWS_ACCOUNT_ID variable, since variables are environment-scoped and come back empty under a new one), the build jobs have to point at the new role and go green, and only then does github_build_role_cutover = true on the staging workspace strip ECR write from the deploy role. Doing those out of order breaks every image push, which is what the gate variable exists to keep separately revertible.

The deploy role's permissions policy grants exactly what a deploy needs: an account-wide ecr:GetAuthorizationToken (AWS doesn't let it be ARN-scoped), ECR read on the mythrun and mythrun-bootstrap-db repositories, ECS UpdateService / DescribeServices / DescribeTasks / ListTasks conditioned on the mythrun cluster, RegisterTaskDefinition and DeregisterTaskDefinition scoped to the mythrun-staging-* family, and iam:PassRole on the two task roles conditioned on iam:PassedToService = ecs-tasks.amazonaws.com. Two further statements (added with the frontend-hosting module) let the same role drive the frontend deploy: S3 object verbs scoped to the mythrun-staging-frontend bucket ARN and its /*, and cloudfront:Create/GetInvalidation scoped to the distribution ARN. The ECR write and pull-through-cache statements are still on this role today, wrapped in the cutover gate, and move wholesale to the build role when it flips. Production snapshot permissions (rds:CreateDBSnapshot) are deliberately absent; they belong to the future production role.

ECR read stays on the deploy role after the cutover — the deploy jobs don't pull images themselves (the task-execution role does that), but the migrate workflow resolves a SHA to a digest before running its task, and an operator debugging a deploy shouldn't be blocked on a role they don't hold. Read is not the permission that made the single role uncomfortable.

SNS alerts topic

mythrun-staging-alerts is the SNS topic this environment's alarms publish to: the billing and retrieval log-metric alarms from the serving module, the API health and 5xx alarms, and the Cognito throttling alarms from the auth module. Alarms on resources every environment shares — the RDS instance, Redis, the ALB itself, the wildcard certificate, the NAT gateway — go to a separate mythrun-shared-alerts topic in the shared workspace instead, so a future production composition inherits one alarm per shared resource rather than a second copy of each. Both topics carry a single email subscription to dev@mythrun.com, which starts in PendingConfirmation and stays there until the recipient clicks the AWS-sent confirmation link — that confirmation is not a Terraform-managed attribute, so re-running apply while pending is a no-op.

A customer-managed KMS key, not alias/aws/sns — the AWS-managed key looks like the free, obvious choice, and it silently breaks every alarm. Encrypting a published message requires the publisher to reach kms:GenerateDataKey, and the AWS-managed key's policy grants that only to principals inside the account. A CloudWatch alarm publishes as the service principal cloudwatch.amazonaws.com, which is not one, and an AWS-managed key's policy cannot be edited to add it. The alarm still turns red; the notification is simply never delivered, leaving one line in the alarm's History tab as the only evidence. Both topics therefore use the customer-managed alias/mythrun-alerts key from the shared workspace, whose policy names both cloudwatch.amazonaws.com and budgets.amazonaws.com.

The topic also carries an explicit resource policy. SNS's default policy allows sns:Publish from any principal in the account; declaring a policy replaces it outright, leaving only cloudwatch.amazonaws.com and budgets.amazonaws.com able to publish from the resource side. Nothing about administration changes — same-account access is satisfied by an identity policy or a resource policy, so Terraform and anyone holding sns:* continue to manage the topic normally.

Budgets is pre-authorized even though nothing publishes budget notifications here — the account cost budget notifies by email today. AWS Budgets fails closed and silently against a policy that omits it: notifications simply stop, with no error surfaced anywhere. Granting it up front turns a future wiring change into one that works rather than one that appears to. The two statements carry different conditions on purpose — the Budgets one is AWS-published verbatim (including a region-less arn:aws:budgets:: source-ARN pattern), while the CloudWatch one carries only aws:SourceAccount, because pinning a source ARN is undocumented for CloudWatch and an unpopulated condition key denies the publish, producing exactly the silent non-delivery this hardening exists to prevent.

Because a green apply proves nothing about delivery, each topic is smoke-tested once after it is wired: aws cloudwatch set-alarm-state --alarm-name mythrun-staging-api-down --state-value ALARM --state-reason "delivery smoke test" should produce an email.

What watches this environment

The serving module carries its own alarms, in three files beside the resources they watch. Two are metric alarms on the ALB's view of this environment's target group; the other two files are log-metric-filters over the API and worker log groups, turning structured pino events into CloudWatch metrics with alarms on top. All of them publish to alerts_topic_arn, and all of them are skipped entirely when that input is empty, so a fresh environment can apply before its topic exists.

Alarms live in the module, not the environment root — they sit beside the log group or target group they watch, so a future production composition inherits them by construction. An alarm that has to be remembered per-environment is an alarm that will be missing in the environment that matters. The counterpart rule holds too: alarms whose subject is a shared resource live in the shared workspace, so one database gets one alarm rather than one per environment.

mythrun-<env>-api-down watches HealthyHostCount on the target group, firing when no load-balancer node can see a healthy target for a minute. It is the only liveness signal available without Container Insights, and it is the better one anyway: it reports whether the API is answering /health/ready, not merely whether a container process exists. It wires an OK action as well as an alarm action — recovery is exactly the edge an operator mid-incident wants confirmed.

Missing data is breaching, and the statistic is Maximum — a target group with zero registered targets stops emitting HealthyHostCount altogether rather than emitting a zero, so “no data” is the outage; any other setting sleeps through the worst case. Maximum reads backwards until you know Min/Max here are computed across the load balancer's nodes, not across time: Minimum would page whenever any single node briefly reports zero, while Maximum below one means no node can see a healthy target anywhere. A partial failure surfaces through the 5xx alarm instead of as a false “everything is down” at 3am.

mythrun-<env>-api-target-5xx fires on more than fifty HTTPCode_Target_5XX_Count responses in five minutes — errors the application produced. The load balancer's own 502/503/504s are a property of the shared ALB and are alarmed once in the shared workspace. Both exist because they point at different people: one at the code, one at the platform.

The retrieval alarms cover the Voyage embedding dependency after boot. The boot probe already makes deploy-time misconfiguration loud — the task crashloops and ECS rolls the deploy back — but it cannot cover a key revoked, re-scoped, or dimension-changed while tasks are already running. In that window nothing crashes: world-gen keeps producing content and leaves every embedding NULL, so retrieval quietly degrades to whatever was embedded before the break. Two alarms split it by operator response: a misconfigured class that never self-heals and needs a corrected key or realigned model, and an unavailable class that is usually transient.

Both log groups feed the same metric, and the transient alarm needs two windows — the API task runs the boot probe, but only the worker runs the world-gen and character-integration pipelines where the runtime embed events come from, so two filters write one metric name in one namespace. That is deliberate: one metric, one alarm, one page, whichever task noticed first; triage by log group and event name from there. The unavailable alarm requires two of three five-minute windows because a single failed embed during a Voyage blip is expected and self-heals, and the partial-degradation event that the backfill recovers on its own is excluded from the filter entirely — alarming on it would page for the system working as designed.

The billing alarms are the fourth group, described with their metric filters in the appendix below.

Operating this piece

Confirm the alerts email subscription

  1. Run aws sns list-subscriptions-by-topic --topic-arn <mythrun-staging-alerts ARN> --query 'Subscriptions[0].SubscriptionArn'.
  2. If it prints PendingConfirmation, open the inbox for the alerts_email address (dev@mythrun.com by default) and click the AWS confirmation link.
  3. Re-run the same command; the ARN should now be the full subscription ARN.

Cut CI over to the ECR-push-only build role

Four steps, in this order. Each is separately revertible; doing them out of order breaks every image push.

  1. Apply the shared workspace. mythrun-github-actions-build appears and nothing changes — CI keeps using the staging role.
  2. In GitHub, create an Environment named build. No required reviewers (it gates nothing; it exists to scope the OIDC environment claim). Restrict its deployment branch to main and add an AWS_ACCOUNT_ID variable — environment variables are environment-scoped, so a new environment that lacks it hands the job an empty string.
  3. Point the build jobs at the new environment and role: the build job in deploy.yml and build-and-push in bootstrap-db-build.yml. Push and confirm a real run goes green.
  4. Only now set github_build_role_cutover = true on the staging workspace and apply. That strips ECR write and pull-through-cache creation from the deploy role.

Pin the OIDC trust to specific workflow files

  1. Add a temporary step to one workflow that fetches and base64-decodes the OIDC token ($ACTIONS_ID_TOKEN_REQUEST_URL with audience=sts.amazonaws.com), and read the real job_workflow_ref off a live run. The value cannot be confirmed any other way.
  2. Compare it against local.staging_job_workflow_refs in the staging workspace (and the equivalent list in github-actions-build-role.tf). Every workflow that names the role must appear, reusable workflows included — a reusable workflow's jobs report their own file, not the caller's.
  3. Set pin_job_workflow_ref = true, apply, and watch the next run. If deploys start failing at the role assume, revert the variable and re-apply; nothing else is affected.

Rotate a manual secret value

  1. Manual secrets (anthropic-api-key, voyage-api-key, stripe-secret-key, stripe-webhook-secret, cognito-client-secret) have ignore_changes = [secret_string] on their Terraform version — safe to update out-of-band.
  2. aws secretsmanager put-secret-value --secret-id mythrun/<env>/<name> --secret-string <value>.
  3. Roll the ECS service so running tasks pick up the new version: aws ecs update-service --cluster mythrun --service mythrun-<env>-api --force-new-deployment.

Prune orphan task-definition revisions (quarterly)

Revisions accumulate from two directions and are never adopted from one of them. Every CI deploy registers a revision and points its service at it; every Terraform edit that touches a task definition registers one too, but ignore_changes = [task_definition] on the services means Terraform's revision sits unused until the next CI deploy supersedes it. ECR has a lifecycle policy for images; task definitions have no equivalent, so nothing prunes them. They cost nothing and break nothing — this is housekeeping, run about once a quarter, not an incident response.

  1. For each family — api, worker, migrate, smoke-prep-pipeline, bootstrap-db — find what is actually in use. Service-backed families answer directly: aws ecs describe-services --cluster mythrun --services mythrun-<env>-api --query 'services[].taskDefinition'.
  2. The families with no service (migrate, smoke-prep-pipeline, bootstrap-db) are invoked by run-task against whatever revision is latest at invocation time, so keep the newest and treat the rest as prunable.
  3. List the active revisions: aws ecs list-task-definitions --family-prefix mythrun-<env>-api --status ACTIVE.
  4. Deregister each revision that is neither in use nor the newest: aws ecs deregister-task-definition --task-definition mythrun-<env>-api:<N>. Keep a few recent ones — they are the fastest rollback path if a deploy goes bad.
  5. Never deregister the revision a running service is pinned to. ECS will not stop the running tasks, but the service can no longer scale or replace them, and the failure surfaces later as an unexplained inability to recover.
  6. Deregistering is reversible in effect but not in identity: revisions go INACTIVE rather than being deleted, and AWS does eventually remove INACTIVE revisions on its own schedule. Do not plan to re-activate one.

Integration points

ECS tasks launch into the network module's private subnets under the ecs security group. Task definitions read secrets from the data plane (per-env rds-password, shared redis-auth) and the manual per-env secret shells. The ALB uses the wildcard ACM cert from the DNS module, and the per-env A-alias is published into the same Route 53 zone. The Backend image built from backend/Dockerfile is what gets pushed to ECR and pointed at by both task definitions on every deploy — see Worker for the worker container's BullMQ + health-server runtime, and CI/CD for how each deploy is executed (the API and worker get separate deploy jobs sharing the same build).

Billing alarms

billing-alarms.tf holds four CloudWatch log-metric-filters over the API log group and an alarm on each, publishing to the SNS topic passed in as alerts_topic_arn (staging wires aws_sns_topic.alerts). Everything matches structured pino fields — $.event for the boot probe's events, $.msg for the dispatcher's, since that one logs through Fastify's request logger where the event name is the message key. Metrics land in the Mythrun/<env>/Billing namespace.

Alarm Fires on Response
billing-probe-config-failure billing.probe_failed, billing.probe_portal_failed, billing.probe_webhook_version_failed Stripe config drifted; the task is crashlooping and ECS is rolling back. Fix the Dashboard.
billing-probe-auth-failure billing.probe_auth_failed Rotate or re-scope STRIPE_SECRET_KEY.
billing-probe-transient-failure billing.probe_transient_failed, billing.probe_portal_transient_failed Stripe unreachable. Check status.stripe.com and the task's egress path.
stripe-webhook-api-version-mismatch stripe_webhook_api_version_mismatch Revenue incident — paid customers are not being credited. Realign the endpoint's version, then replay the dropped events.
Every metric transformation sets default_value = 0 — without it a log-derived metric emits nothing in a quiet window, and the alarm parks in INSUFFICIENT_DATA instead of holding a real OK state. Zero-filling means these alarms self-recover and their green is meaningful.
