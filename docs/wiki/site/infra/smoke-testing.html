Smoke testing

How we exercise the deployed staging API end-to-end. Two smokes today: the narrow check-username smoke (one bash script, one Cognito user) that proves the cognitive stack is reachable; and the multi-campaign prep-pipeline smoke (one TypeScript driver, four Cognito users, one in-VPC ECS task family) that exercises the full prep flow under burst concurrency. Both share the same provisioning shape: native Cognito users created by Terraform, credentials in Secrets Manager, and an operator-facing one-command entry point.

How it fits together

infra/modules/auth/smoke-test.tf provisions four native (non-federated) Cognito users gated by smoke_test_user_enabled = true in the staging composition: one owner (mythrun-staging-smoke-owner@example.com) and three players (mythrun-staging-smoke-player-1..player-3@example.com). Each user gets a Terraform-generated 32-character password that meets Cognito's policy, stored in its own Secrets Manager entry at mythrun/staging/smoke-test-{owner,player_1,player_2,player_3}-credentials as a JSON-encoded {username, password} object. The four secret ARNs surface back as a map output (module.auth.smoke_test_credentials_secret_arns) the staging composition wires into IAM grants without reaching across module boundaries.

Two smoke surfaces consume those credentials. The narrow pnpm smoke:staging path (backend/scripts/smoke/staging.sh) reads the owner secret, authenticates via Cognito's USER_AUTH flow with a PASSWORD challenge inline (single API call, no challenge round-trip), and hits the API with the resulting access token. The broader prep-pipeline smoke (backend/scripts/smoke/prep-pipeline.ts) reads all four secrets, authenticates each user in parallel, and drives three concurrent owner-creates-campaign / three-players-each-submit-character flows end-to-end against the deployed staging API. Both surfaces hold no IAM write permissions on Cognito; users are pre-provisioned and the smokes only need secretsmanager:GetSecretValue on the credential secrets and cognito-idp:InitiateAuth (which the public App Client allows by design).

Native Cognito users, not federated — we don't have Mythrun-controlled Google or Discord test accounts and don't want to depend on a third-party provider for our smokes. Native users give us end-to-end ownership of the credentials. The user pool's username_attributes = ["email"] requires each username be a valid email shape; no actual mailbox exists at the @example.com addresses, but email_verified = true is set at provisioning so Cognito doesn't try to validate.
Four users, not one — the prep-pipeline smoke saturates the worker concurrency caps (3 world-gen + 5 campaign-setup) by driving three concurrent campaigns with three players each. A single user serialized across campaigns would defeat the burst-concurrency assertion. The for_each map keyed by role (owner, player_1, player_2, player_3) yields zero resources when smoke_test_user_enabled = false, so the production composition stays clean.
Pre-provisioned, not throwaway-per-run — the alternative is to have the smokes create fresh users each run. That requires IAM write permissions on Cognito (admin-create-user + admin-set-user-password + admin-delete-user). Pre-provisioned users with read-only-secret access keep the smokes' IAM footprint tight and avoid burning Cognito's account-level sign-up quota on every run.
Why we use null_resource for user CRUD — the hashicorp/aws Terraform provider doesn't have an aws_cognito_user_pool_user resource. Cognito user CRUD is SDK-only. We use a null_resource with a local-exec provisioner that runs aws cognito-idp admin-create-user + admin-set-user-password --permanent per user (looped via the same for_each map). The provisioner is idempotent: admin-create-user errors with UsernameExistsException on re-runs, which we swallow via grep -v UsernameExistsException || true; the password set always succeeds. Triggers re-run on either user-id change or password rotation.

What the narrow smoke verifies

Five HTTP requests against the live deployed API, exercising both the classifyProfanity call site (Haiku reachability) and the underlying users repository:

  1. GET /health/ready returns 200 (the container is serving traffic on the new revision).
  2. POST /api/users/register with a generated smoketester$$ username. First run: 201 fresh path. Subsequent runs: 409 idempotent (same Cognito sub returns the existing user record per MYT-38 spec). Either way, classifyProfanity fires twice (once on the username, once on the display name).
  3. GET /api/users/check-username?username=gandalf$$ returns {available: true} — Haiku classifies non-profane and the route reaches users.getByUsername, which finds nothing.
  4. GET /api/users/check-username?username=fucknugget returns {available: false, reason: 'offensive'} — Haiku classifies the offensive name and the route emits the rejection.
  5. GET /api/users/check-username?username=mythrun_admin returns {available: false, reason: 'impersonation'} — Haiku classifies the impersonation attempt.

Five Haiku calls show up in CloudWatch as structured log lines emitted by the LLM middleware: event: 'llm.call' with model: 'claude-haiku-4-5-20251001', token counts, and latency. Total cost per smoke run is ~$0.0005 at current Haiku pricing.

Why the smokes aren't yet on a cron — both are manual today (pnpm smoke:staging + the prep-pipeline run-task command). Scheduled GitHub Actions runs are the obvious next step but need CloudWatch alarm wiring before they're worth automating; an unwatched green/red signal is operational noise. Until alarms exist, the scripts live where any human or agent can run them on demand: pre-deploy, post-deploy, after a flaky-feeling outage, or during a billing-rate change to verify spend is what we expect.

The prep-pipeline smoke (MYT-55)

The prep-pipeline smoke is the wider verification artifact: a multi-campaign creation burst that saturates the worker concurrency caps and proves the cognitive stack survives Tier-2 Anthropic load without degrading. It runs as a one-shot ECS Fargate task family rather than from a developer laptop because staging RDS is publicly_accessible = false (correctly) and the smoke's in-DB assertions + teardown need direct database reach.

Task family mythrun-staging-smoke-prep-pipeline is defined in infra/environments/staging/main.tf. It reuses the existing backend ECR image (which carries tsx and the smoke script source under /app/backend) and runs tsx scripts/smoke/prep-pipeline.ts with task definition cpu 1024 / memory 2048 — sized for 8 in-flight Anthropic streams plus 3 concurrent campaign drivers per the concurrency-ceilings analysis on the LLM client page. The task carries its own task-execution role (ECR pull + log writes + the rds-password secret) and its own task role (per-ARN secretsmanager:GetSecretValue on the four smoke-user secrets only), kept separate from the API and bootstrap-db roles for blast-radius isolation. Logs land in /ecs/mythrun-staging-smoke-prep-pipeline with 14-day retention.

Sibling task family, not a serving-module addition — the smoke isn't an API or worker process; it's a one-shot driver that mirrors the bootstrap-db task-family pattern (separate roles, dedicated log group, paste-ready run-task command). Folding it into modules/serving would entangle a long-running service's lifecycle with an invoked-on-demand task. The shared shape gives future cron + post-deploy-gate uses a 15-line EventBridge addition instead of a rewrite.
SG reuse, not a fresh one — the smoke's network needs are exactly the bootstrap-db's: 443 egress to AWS APIs (Cognito, Secrets Manager, the staging API ALB via the NAT path) and 5432 egress to RDS. The task definition's smoke_prep_pipeline_run_task_command output pins module.bootstrap_db.security_group_id rather than provisioning a duplicate SG with identical rules. Two smokes, one SG identity to audit.

Operator invocation lives behind a Terraform output. The full paste-ready aws ecs run-task command (cluster, task definition, launch type, subnets, security group) surfaces as smoke_prep_pipeline_run_task_command on the staging workspace; eval "$(terraform output -raw smoke_prep_pipeline_run_task_command)" launches one task, and aws logs tail /ecs/mythrun-staging-smoke-prep-pipeline --follow surfaces the structured JSON output line by line. The script prints a final summary record with verdict: PASS | FAIL, total cost, wall-clock, and per-campaign stats.

What the prep-pipeline smoke verifies

Three layers of assertion, all must pass for verdict PASS:

  • Phase completeness — each campaign reaches status='active', each world reaches status='complete', every pipeline_runs row is completed (zero failed, zero running), every campaign has exactly 3 character rows, total entity-PC count is 9 across 3 worlds.
  • Per-concept floors — entity count, relationship count, and average facts/entity each meet a per-concept floor calibrated from a real reference run. Floors absorb LLM variance without flaking.
  • Session-prep gate — once a campaign reaches active, the smoke POSTs to its session-prep route, reads the prep-status SSE through to prep-ready (accepting the connect-time snapshot: {status:'ready'} frame as already-done, since the route emits that snapshot but does not replay prep-ready), then asserts a session_preps row with non-empty ft_context and sd_playbook. This makes the prep-pipeline smoke the first real-LLM exercise of the session-prep flow against staging. Leak-cleanliness is deliberately not asserted here — that's eval / red-team territory, not a plumbing assertion.
  • Global gates — total cost across all 3 campaigns ≤ $8; wall-clock ≤ 35 minutes; zero LlmRateLimitedError entries observed during the run. The rate-limit gate is what makes this smoke also the concurrency-ceilings verification.
$8 cap, not $5 — the prior $5 cap covered three-campaign world-gen + character creation. Appending one session-prep stream per campaign adds three measured ~$0.52 streams (~$1.56), so the cap rose to $8 with headroom for LLM cost variance. The wall-clock budget stayed at 35 minutes: session-prep (~3.4 min) appends to each campaign's parallel chain, adding to the slowest campaign once rather than three times.

Teardown is leave-on-failure, clean-on-success. PASS cascade-deletes every campaign, world, session-prep row, and credit-ledger entry the run created. The session_preps row and its session-prep:1 pipeline run cascade with the campaign, so the teardown needed no new DELETE. The run sanity-checks DB_NAME contains staging before any DELETE — the staging RDS hostname is anonymized, the database name is the env signal; FAIL prints the campaign + world IDs and exits non-zero for forensic inspection. The smoke also runs a pre-run state reset at startup (after auth + user-materialize, before campaign creation) that DELETEs any campaigns currently owned by the four smoke users — otherwise the per-owner concurrency gate 409s every retry after a FAIL. Forensics from prior runs live in CloudWatch logs (full campaign IDs and assertion diagnostics from the FAIL summary), so the audit trail is preserved without the DB carrying state across runs. The smoke does NOT seed credits at runtime — that's the bootstrap-db's --seed-smoke-credits mode, run once after first auth materializes the users in the application DB.

Bootstrap-db --seed-smoke-credits mode

The smoke users need world_gen + session credits to create campaigns (1 credit per campaign creation). Trial registration grants 1 session credit per user — not enough to drive three concurrent campaigns per smoke run. infra/scripts/bootstrap-databases.sh --seed-smoke-credits grants 1,000,000 of each credit type to each of the four smoke users, idempotent on a deterministic source_id hash so re-runs are no-ops. At 1 credit per campaign that's effectively forever — ~333,000 smoke runs of headroom.

The seed mode is wired into the existing bootstrap-db task family rather than as a new task: the bootstrap module gains two staging-only inputs (cognito_user_pool_id and a smoke_user_emails map), and the staging composition passes module.auth.user_pool_id through with the four email values that mirror local.smoke_test_users. When the inputs are set, the bootstrap task carries COGNITO_USER_POOL_ID + SMOKE_USER_EMAIL_* env vars and gains an ARN-pinned cognito-idp:AdminGetUser IAM grant. The script's seed branch resolves email → cognito_sub at runtime, then INSERTs the admin grants keyed by (user_id, credit_type). Production composition leaves both inputs empty — no Cognito surface gets bound to the bootstrap role outside staging.

Why credits are seeded out-of-band, not at smoke runtime — runtime seeding would force the smoke script to hold DB credentials and admin-grant SQL execution privileges. The pre-seed mode keeps the smoke's IAM footprint narrow (Secrets Manager + API calls only) and turns credit-grant into a one-time operator action: run the bootstrap-db task once after Cognito users land and first auth materializes them. Re-running it is idempotent. This decouples credit pool size from smoke-script complexity.

Operator invocation: eval "$(terraform output -raw bootstrap_db_run_task_seed_smoke_credits)" prints PASS / FAIL inline; the output is empty string when staging-only seeding isn't wired in this environment, so production callers can reference it unconditionally.

Operating this piece

Run the narrow staging smoke

  1. From the repo root, run pnpm smoke:staging. Expected output: green checkmarks on each step and a final “Smoke passed” line.
  2. If a step fails, the script exits non-zero and prints the request body that didn't match expectations. CloudWatch /mythrun/staging/api has the corresponding server-side log line.

Run the prep-pipeline smoke

  1. From infra/environments/staging/, fetch the paste-ready command: aws_cmd=$(terraform output -raw smoke_prep_pipeline_run_task_command), then eval "$aws_cmd". The eval wrapper is required because the --network-configuration 'awsvpc...' segment is single-quote-wrapped inside the string and needs a shell re-parse.
  2. Tail the run as it executes: aws logs tail /ecs/mythrun-staging-smoke-prep-pipeline --follow. Each significant step emits a structured JSON line; the final summary record carries the verdict.
  3. On FAIL the smoke leaves all created campaigns + worlds in place for forensic inspection; inspect the IDs in the summary record. On PASS the cascade-delete teardown runs and the DB returns to its pre-run state (modulo credit-ledger debits, which are intentionally retained for cost analysis).

Seed smoke-user credits (once per Cognito user materialization)

  1. Each smoke user must have at least one POST /api/users/register against the staging API to materialize a users row keyed by their Cognito sub. The first prep-pipeline smoke run does this automatically on its first attempt; the seed mode is deferred until after.
  2. From infra/environments/staging/: eval "$(terraform output -raw bootstrap_db_run_task_seed_smoke_credits)". The bootstrap-db task resolves email → cognito_sub at runtime and INSERTs admin grants of 1,000,000 world_gen + 1,000,000 session credits per user. Idempotent on re-runs.
  3. Verify with aws logs tail /ecs/mythrun-staging-bootstrap-db --since 5m; the task logs one line per inserted (or skipped) credit row.

Rotate the smoke-test credentials

  1. From infra/environments/staging/, target the desired user-key: terraform apply -replace='module.auth.random_password.smoke_test["owner"]' (or player_1 / player_2 / player_3).
  2. Terraform regenerates the password, updates the user's Secrets Manager entry, and runs the null_resource provisioner to set the new password as permanent on the Cognito user.
  3. Re-run the affected smoke surface (pnpm smoke:staging if the owner rotated; prep-pipeline if any of the four).

Integration points

The smokes exercise the LLM client through the onboarding routes wired up in Onboarding & invites and, for the prep-pipeline smoke, the world-gen and character-creation processors on the worker service. The Cognito user pool itself is documented under Identity; the four smoke-test users sit alongside the federated users that flow in via Google and Discord. The Bootstrap database page covers the --seed-smoke-credits mode in the broader context of the bootstrap-db task family, and the concurrency-ceilings section on the LLM client page explains why the prep-pipeline smoke's absence of LlmRateLimitedError is also the running proof that our caps + Anthropic's Tier 2 limits survive a real burst.

Appendix: configuration

Knob Where Default Purpose
smoke_test_user_enabled module "auth" input false Gates all smoke-test resources (four users + four Secrets Manager entries). Staging sets true; production composition leaves the default.
cognito_user_pool_id / smoke_user_emails module "bootstrap_db" inputs "" / {} Enables --seed-smoke-credits on the bootstrap-db task family. Staging passes module.auth.user_pool_id + the four email values; production leaves them empty so no Cognito surface is bound to the bootstrap role.
API_BASE Both smokes' env https://staging-api.mythrun.com Override to run against a different deployment.
OFFENSIVE_USERNAME / IMPERSONATION_USERNAME staging.sh env fucknugget / mythrun_admin Test inputs for the offensive + impersonation classification paths. Both must be inputs Haiku will reliably classify into the expected reason.
SMOKE_WALL_CLOCK_BUDGET_MS Prep-pipeline task env 2100000 (35 min) Hard ceiling on a single smoke run; over-budget triggers FAIL. Absorbs the slowest campaign's full pipeline plus its appended session-prep stream and repair-chain headroom.
SMOKE_COST_CAP_USD Prep-pipeline task env 8.00 Cumulative cost across all three campaigns. Calibrated against the myth-imxg reference run (~$1.20 per world, with headroom for character creation + integration), plus three measured ~$0.52 session-prep streams added by MYT-64.
