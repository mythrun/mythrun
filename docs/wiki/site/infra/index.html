Infra

Everything Mythrun runs on: a single AWS account in us-east-1, carved into Terraform modules and composed by per-environment workspaces.

How it fits together

Infrastructure lives in the infra/ directory as a small set of modules and a handful of environment workspaces. Modules describe a single piece of AWS surface area; workspaces decide which modules to compose and with which inputs.

The modules shipped so far:

  • Network — VPC, public/private subnets across two AZs, NAT, security groups.
  • Data — RDS Postgres, ElastiCache Redis, and the Secrets Manager entries that front them.
  • DNS — Route 53 hosted zone for mythrun.com, Google Workspace email records, and the wildcard ACM certificate.
  • Serving — ECS task definitions, services, target group, listener rule, DNS A-alias, IAM task roles, and the GitHub Actions deploy role.
  • Frontend hosting — private S3 + CloudFront serving the SPA at staging.mythrun.com behind a fail-closed Basic-Auth gate.
  • CI/CD — the push-to-deploy pipeline: two-job GitHub Actions workflow, ECR pull-through cache, digest-pinned task-def revisions, rollout verification, a separate frontend deploy workflow, and Dependabot for SHA-pinned actions.

Two workspaces consume those modules: shared/ creates the single cross-environment footprint (VPC, ALB, ECS cluster, ECR repo, GitHub OIDC provider, RDS, Redis, DNS zone + wildcard cert — resources we don't double up per env), and staging/ creates per-env resources that read shared outputs via terraform_remote_state: task defs and services, per-env secret shells, the scoped GitHub Actions IAM role, and an SNS alerts topic.

The shared workspace also carries the account-level pieces that belong to no single module: the image-build IAM role, the KMS key that encrypts both alerts topics, the cost budget, and the alarms whose subject is a shared resource. See Alerting and spend below.

Shared vs per-env split — a second Postgres or VPC would double cost without buying anything real in staging. Sensitive boundaries (per-env databases, per-env app users, per-env IAM roles) sit inside the shared infrastructure; noisy-neighbor and blast-radius concerns are revisited before production traffic lands.

State and bootstrap

Terraform state lives in the mythrun-terraform-state S3 bucket — one key per workspace. bootstrap.sh creates the bucket itself: SSE-S3 encryption, versioning, public-access block, TLS-only bucket policy, 90-day noncurrent expiration. Native S3 state locking (use_lockfile = true) replaces DynamoDB; every backend declares required_version >= 1.10 to pin that feature on.

No DynamoDB lock table — Terraform 1.10 added native object-lock based state locking. It's one less resource to provision, one less bill, and the lock semantics are simpler to reason about.

Alerting and spend

Every alarm in the account lands in one of two SNS topics, and which one it lands in follows a single rule: the topic belongs to whoever owns the resource being watched. Alarms on shared infrastructure — the RDS instance, the Redis replication group, the ALB, the wildcard certificate, the NAT gateway — publish to mythrun-shared-alerts in the shared workspace. Alarms whose subject is one environment — the API's health and 5xx rate, the log-derived billing and retrieval alarms, Cognito throttling — publish to that environment's own topic, and live in the module that owns the resource so a production composition inherits them rather than re-declaring them. Both topics carry a single email subscription today, which starts in PendingConfirmation until the recipient clicks the AWS link.

Two topics, because the dependency arrow only runs one way — the staging workspace reads shared's remote state, never the reverse, so a shared-resource alarm cannot publish to the staging topic without inverting that. The alternative, declaring the shared alarms inside each environment, means a production composition either duplicates every one of them (two pages for one database) or silently omits them. One shared resource, one alarm, one topic that belongs to nobody's environment.
A customer-managed KMS key, not alias/aws/sns — the AWS-managed key is free and looks like the obvious choice, and it silently disarms every alarm on the topic. Publishing an encrypted message requires the publisher to reach kms:GenerateDataKey, which the AWS-managed key's policy grants only to IAM principals in the account. A CloudWatch alarm publishes as the service principal cloudwatch.amazonaws.com, and an AWS-managed key's policy cannot be edited to add it. The alarm still turns red and the console still looks right; the notification is simply never sent, and the only evidence is one line in the alarm's History tab. One customer-managed key (alias/mythrun-alerts) therefore encrypts both topics, and each topic is smoke-tested once after wiring with aws cloudwatch set-alarm-state — a green apply proves nothing about delivery here.

Account spend is watched separately, by AWS Budgets rather than a CloudWatch alarm: a monthly cost budget with three layered notifications — 85% actual, 100% forecasted, 100% actual. The forecast usually fires first on a sharp ramp, which is exactly the case worth catching early, because a runaway LLM spend doesn't creep, it steps. The budget predates its Terraform declaration and is therefore imported rather than applied; the name is half the import ID, so renaming it destroys and recreates it.

Budgets, not an alarm on AWS/Billing EstimatedCharges — that metric doesn't exist in this account. It is published only once the “Receive Billing Alerts” account preference is switched on, and only ever into us-east-1. Budgets needs no such preference, evaluates forecasts as well as actuals, and is what AWS itself now points at.

Operating this piece

Create the state bucket in a new AWS account

  1. Configure AWS credentials for the target account.
  2. Verify terraform >= 1.10 and jq are on the PATH.
  3. Run bash infra/scripts/bootstrap.sh.
  4. The script is idempotent — re-running against an existing bucket reconciles its settings without recreating it.

Verify an alerts topic actually delivers

Do this once per topic, after wiring and after any change to the topic's encryption or policy. A green terraform apply proves the alarm exists, not that a notification reaches anyone.

  1. Confirm the email subscription is out of PendingConfirmation: aws sns list-subscriptions-by-topic --topic-arn <arn> --query 'Subscriptions[0].SubscriptionArn'.
  2. Force one alarm into ALARM: aws cloudwatch set-alarm-state --alarm-name mythrun-staging-api-down --state-value ALARM --state-reason "delivery smoke test".
  3. Check the inbox. Then let the alarm settle back on its own, or set it to OK.
  4. If no email arrives while the console shows the alarm red, read the alarm's History tab. A “Failed to execute action … does not have authorization to access the SNS topic encryption key” line means the topic is on the wrong KMS key. SNS's own NumberOfNotificationsFailed will show nothing — the publish is rejected before the message enters SNS.

Integration points

The Network page drills into the VPC. The Data page covers RDS, Redis, and the bootstrap script that creates per-env databases inside the shared RDS instance. Serving carries the per-environment half of the alerting story — the alarms declared inside the serving module, the environment's own topic, and its policy.

Workspace State key Contents

Shared-resource alarms

Declared in the shared workspace, publishing to mythrun-shared-alerts. Per-environment alarms are listed on the Serving page.

Alarm Condition Why it matters
mythrun-rds-cpu-high CPU > 90% The one Postgres instance every environment shares.
mythrun-rds-storage-low Free storage < 2 GiB Autoscaling has a ceiling; this is the warning before it.
mythrun-redis-<n>-memory-high Node memory > 80% for 5 min maxmemory-policy is noeviction, so a full node rejects writes rather than shedding load — every job enqueue starts failing. One alarm per node.
mythrun-alb-5xx > 50 ELB-generated 5xx in 5 min The load balancer's own 502/503/504 — the platform's view, not the application's.
mythrun-acm-wildcard-expiry < 30 days to expiry; missing data breaches ACM auto-renews at ~60 days, so reaching 30 means renewal has been failing. The cert fronts every hostname we serve.
mythrun-nat-port-allocation-errors Any ErrorPortAllocation Source-port exhaustion toward one destination (~55k concurrent connections). Surfaces in the app as scattered, hard-to-diagnose connection failures under load.

Worker liveness is deliberately absent. Container Insights is off by design, so RunningTaskCount isn't published, and the worker has no target group to borrow HealthyHostCount from. The two honest options are enabling Container Insights at Launch or having the worker emit its own heartbeat metric — the task role already carries cloudwatch:PutMetricData for the Mythrun/<env> namespace — and both cost something, so neither is taken silently.
