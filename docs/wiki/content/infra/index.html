Infra

Everything Mythrun runs on: a single AWS account in us-east-1, carved into Terraform modules and composed by per-environment workspaces.

How it fits together

Infrastructure lives in the infra/ directory as a small set of modules and a handful of environment workspaces. Modules describe a single piece of AWS surface area; workspaces decide which modules to compose and with which inputs.

The modules shipped so far:

  • Network — VPC, public/private subnets across two AZs, NAT, security groups.
  • Data — RDS Postgres, ElastiCache Redis, and the Secrets Manager entries that front them.
  • DNS — Route 53 hosted zone for mythrun.com, Google Workspace email records, and the wildcard ACM certificate.
  • Serving — ECS task definitions, services, target group, listener rule, DNS A-alias, IAM task roles, and the GitHub Actions deploy role.
  • CI/CD — the push-to-deploy pipeline: two-job GitHub Actions workflow, ECR pull-through cache, digest-pinned task-def revisions, rollout verification, and Dependabot for SHA-pinned actions.

Two workspaces consume those modules: shared/ creates the single cross-environment footprint (VPC, ALB, ECS cluster, ECR repo, GitHub OIDC provider, RDS, Redis, DNS zone + wildcard cert — resources we don't double up per env), and staging/ creates per-env resources that read shared outputs via terraform_remote_state: task defs and services, per-env secret shells, the scoped GitHub Actions IAM role, and an SNS alerts topic.

Shared vs per-env split — a second Postgres or VPC would double cost without buying anything real in staging. Sensitive boundaries (per-env databases, per-env app users, per-env IAM roles) sit inside the shared infrastructure; noisy-neighbor and blast-radius concerns are revisited before production traffic lands.

State and bootstrap

Terraform state lives in the mythrun-terraform-state S3 bucket — one key per workspace. bootstrap.sh creates the bucket itself: SSE-S3 encryption, versioning, public-access block, TLS-only bucket policy, 90-day noncurrent expiration. Native S3 state locking (use_lockfile = true) replaces DynamoDB; every backend declares required_version >= 1.10 to pin that feature on.

No DynamoDB lock table — Terraform 1.10 added native object-lock based state locking. It's one less resource to provision, one less bill, and the lock semantics are simpler to reason about.

Operating this piece

Create the state bucket in a new AWS account

  1. Configure AWS credentials for the target account.
  2. Verify terraform >= 1.10 and jq are on the PATH.
  3. Run bash infra/scripts/bootstrap.sh.
  4. The script is idempotent — re-running against an existing bucket reconciles its settings without recreating it.

State bucket

Setting Value
Name mythrun-terraform-state
Region us-east-1
Encryption SSE-S3 (AES256), bucket key enabled
Versioning Enabled; noncurrent expires after 90 days
Public access Blocked (all four controls)
Transport TLS-only (aws:SecureTransport=false denied)
Locking Native S3 object lock (use_lockfile)
