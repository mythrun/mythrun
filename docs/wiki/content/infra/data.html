Data plane

RDS Postgres and ElastiCache Redis, both in the private subnets, and the Secrets Manager entries that hold every credential the app will ever read.

How it fits together

The data module provisions two stateful engines — one Postgres instance and one Redis replication group — plus the secrets that front them. Both are shared across environments; isolation happens one layer in (per-env databases and per-env users inside the single RDS instance, per-env secret paths in Secrets Manager).

One RDS, many databases — a second RDS instance for staging would roughly double the data-plane bill without buying real isolation: staging and prod traffic never touch the same database anyway. Per-env app users with GRANT ALL only on their own database provide the boundary that matters. The day load or compliance demands physical separation, the production workspace gets its own data module.

Postgres

Postgres 16 on db.t4g.micro, Single-AZ, 20 GB gp3 with autoscale to 50. Encrypted at rest, TLS-required on the wire (rds.force_ssl = 1), and not publicly accessible. The parameter group sets query-safety knobs up front: 30-second statement_timeout, 1-minute idle_in_transaction_session_timeout, slow-query logging at 1 s, log_parameter_max_length = 0 so parameter values never hit the logs.

AWS manages the master password — manage_master_user_password = true puts the mythrun_admin password in an AWS-managed Secrets Manager entry that Terraform never sees. The password is never in state, never in plan output, never in a tfvars file. Rotations are an AWS-side concern.

db_name is intentionally unset on the instance. Per-env databases (mythrun_staging, mythrun_production) and app users (mythrun_staging, mythrun_production) are created by bootstrap-databases.sh after the network path from ECS to RDS exists.

Static parameters carry apply_method = "pending-reboot" — AWS classifies max_connections, shared_buffers, and rds.force_ssl as static; leaving the apply method at its default of immediate produces a perpetual no-op diff because Terraform asks AWS to apply immediately and AWS silently defers.

Redis

Redis 7.1 on cache.t4g.micro, single-node replication group. Encrypted at rest, TLS required on the wire (transit_encryption_mode = required), AUTH token required on every connection. maxmemory-policy is volatile-lru — the app is expected to set TTLs on anything cacheable and leave session state without TTL so it isn't evicted.

No rename-commands hardening — the MYT-25 apply tried three variants (renaming CONFIG/DEBUG, renaming to empty strings). ElastiCache already platform-blocks the dangerous admin commands (CONFIG, DEBUG, SHUTDOWN, REPLICAOF, SAVE, BGSAVE, MIGRATE, SYNC) and rejects renaming them; it also rejects empty-string aliases. Defense-in-depth falls to AUTH token, transit TLS, ECS-only SG ingress, and the private subnet placement.

AUTH token rotation contract

The AUTH token is generated by Terraform (random_password) and written into both mythrun/shared/redis-auth and the Redis replication group on initial create. After that, both sides opt out of Terraform-driven updates via ignore_changes. The Rotate Redis AUTH runbook is the only path that keeps the secret and the replication group in sync.

Secrets Manager layout

Three groups of secrets, each with a different write path:

  • AWS-managed RDS master secret — auto-created by the RDS instance; never read by the app. Used only by bootstrap-databases.sh.
  • mythrun/shared/redis-auth — written once by Terraform, then opted out via ignore_changes. Shared across environments because Redis itself is shared.
  • Per-env secret shells — mythrun/{env}/anthropic-api-key, stripe-secret-key, stripe-webhook-secret, cognito-client-secret, and rds-password. Created by the env workspace as empty shells; values written out-of-band. The rds-password shell has no Terraform-managed version, so terraform apply -replace can never overwrite the real password with a placeholder.

Operating this piece

Bootstrap databases for an environment

  1. Run from inside the VPC — RDS isn't publicly accessible. A one-shot ECS task on the shared cluster is the supported path.
  2. Pass --env staging or --env production. The task role needs secretsmanager:GetSecretValue on the RDS master secret ARN and secretsmanager:PutSecretValue on mythrun/{env}/rds-password.
  3. With no other flags, the script verifies current state and creates whatever is missing. Modes cover the partial-failure cases: --verify, --user-only, --secret-only, --reset-password.
  4. Revoke the task role after the bootstrap completes.

Rotate Redis AUTH token

  1. Generate a new token and write it to mythrun/shared/redis-auth in Secrets Manager.
  2. Apply the new token to Redis: aws elasticache modify-replication-group --auth-token-update-strategy SET (or the AWS console).
  3. Do not taint the Terraform random_password resource and re-apply — both the secret version and the replication group have ignore_changes, so the new Terraform value never propagates.
  4. Roll ECS tasks so they pick up the new secret version.

Recover from a partial bootstrap

  1. Run bootstrap-databases.sh --env <env> --verify.
  2. The script prints one of OK, DB_ONLY, SECRET_MISSING, or MISSING.
  3. MISSING → run with no flags. DB_ONLY → run with --user-only. SECRET_MISSING → run with --secret-only (rotates the password via ALTER USER and writes the new value).

Integration points

The Network module provides the private subnets and the rds/redis security groups this module attaches to. The app's repository layer (not yet built) reads the per-env rds-password secret and the shared redis-auth secret to connect.
