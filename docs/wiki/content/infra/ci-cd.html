CI/CD

The push-to-deploy pipeline. A two-job GitHub Actions workflow that on every push to main builds the backend image through an ECR pull-through cache, assumes the staging GitHub Actions role via OIDC, registers a new task-def revision pinned to the image digest, rolls the ECS service, polls for circuit-breaker rollback, and smoke-tests the public /health URL.

How it fits together

The workflow lives at .github/workflows/deploy.yml. It triggers on pushes to main whose paths include application code — doc-only and tracker-only commits (docs/**, .beads/**, **/*.md, wiki/**) skip the run. workflow_dispatch is on so a deploy can be re-run by hand from the Actions tab without pushing a no-op commit.

One concurrency group per ECS service, not per branch — a future branch-based preview deploy or the eventual prod append won't share a queue with staging. Two simultaneous pushes to main serialize against deploy-mythrun-staging-api; cancel-in-progress is off so a mid-roll deploy finishes before the next one starts.

The build job

The build job checks out the repo, sets up pnpm + Node from .nvmrc, and runs pnpm install --frozen-lockfile --filter @mythrun/backend.... The @mythrun/backend... filter scopes install to the backend and its transitive workspace dependencies so a broken sibling workspace (say @mythrun/wiki) can't red-light a backend deploy. --frozen-lockfile still validates the whole lockfile, so lockfile drift is caught regardless of the filter. After install, the job runs lint, typecheck, and test against the backend package — the same four verbs the Backend page documents, scoped to the workspace being shipped.

pnpm install runs before the OIDC role assume — npm lifecycle scripts execute at install time. Running them before AWS credentials are in the environment means a compromised transitive dependency can't exfiltrate the deploy role's STS token. This ordering is load-bearing; do not hoist the assume step.

After the verification gates pass, the job assumes the mythrun-github-actions-staging IAM role through the shared GitHub OIDC provider, logs in to ECR, and runs docker build. The build passes --build-arg BASE_IMAGE_REGISTRY=$REGISTRY — the account-specific ECR host — so the backend Dockerfile resolves its FROM through the ECR pull-through cache instead of Docker Hub directly.

Pull-through cache, not Docker Hub direct — GitHub-hosted runner IP pools collectively hit Docker Hub's 100-pulls-per-6h anonymous rate limit at team scale, and direct pulls add transit latency to every cold build. Routing through aws_ecr_pull_through_cache_rule.ecr_public keeps pulls in-region and auth-free. Upstream is public.ecr.aws (AWS's official mirror of the Docker Hub Library namespace), not registry-1.docker.io directly — Docker-Hub-proper pull-through now requires Secrets Manager-stored credentials, which the ECR Public path sidesteps.

The build step tags the image twice — :$GIT_SHA and :latest — and pushes both. OCI image labels carry the source URL, the revision SHA, the build timestamp, and a pair of com.mythrun.workflow_run* labels that make the pushed image clickable back to the originating run in registries that render OCI annotations. The final build step resolves the image's content-addressable digest by reading Docker's local RepoDigests array via docker inspect --format='{{index .RepoDigests 0}}' and publishes it as the job output.

Local docker inspect, not aws ecr describe-images — calling ECR after the push introduces a TOCTOU window: an attacker with ECR push could re-tag :$GIT_SHA to point at a different image between our push and our describe, and the deploy would silently pin to the attacker's digest. Reading Docker's own record of the push closes that window — the digest is whatever docker just uploaded.

The deploy-staging job

The deploy job reassumes the same role (jobs don't share credentials) and walks the task definition through a render-update-verify cycle. It calls aws ecs describe-task-definition --task-definition mythrun-staging-api to grab the current revision, runs amazon-ecs-render-task-definition to swap the container image for the digest-addressed URI from the build job's output, and then amazon-ecs-deploy-task-definition registers the new revision and calls update-service. wait-for-service-stability: true blocks until ECS reports the deployment settled, with a 15-minute ceiling.

Digest-pinned image, not :$GIT_SHA — ECS task definitions resolve tags at task-launch time. A tag-pinned task def would revisit the registry on every placement and be vulnerable to the same re-tag attack the docker inspect step defends against. A digest-pinned task def is immutable by construction.

After the deploy action returns, the job runs update-service --desired-count 1. On the very first deploy this flips the service from 0 → 1 (task definitions get registered at :placeholder with desired_count=0 — see the Serving page); on every deploy after, it's a no-op. Ordering matters: the desired-count flip runs after the deploy action, so ECS never attempts to place on the :placeholder revision.

The wait-for-stability flag alone isn't enough to catch a failed deploy — AWS's services-stable waiter returns SUCCESS even after a circuit-breaker rollback. The next step polls describe-services directly every 10 seconds for up to two minutes, reading deployments[].rolloutState on the PRIMARY deployment. On COMPLETED with running == desired and zero failed tasks, the step passes; on FAILED, the step fails immediately with a pointer to the recovery runbook; a two-minute no-progress window also fails the job.

Explicit rolloutState poll, not just the waiter — the ECS deployment circuit breaker rolls the service back to the previous task-def revision when a new revision's tasks repeatedly fail to reach healthy. The waiter observes the service settled, doesn't notice it settled at the old revision. Reading rolloutState is the only way to distinguish a real success from a rollback-that-settled.

The final step smoke-tests https://staging-api.mythrun.com/health. It retries three times with a 10-second pause between attempts and demands both a 200 response and a JSON body matching .status == "ok". Body-matching guards against the ALB's default-action 404 succeeding by accident: a listener-rule misconfiguration would still return 200 from something, but not {"status":"ok"} from the backend.

Dependabot for SHA-pinned actions

Every third-party action in the workflow is pinned by commit SHA, not by tag, because tag mutations upstream are the dominant supply-chain threat vector for CI. .github/dependabot.yml schedules weekly bump PRs against the github-actions ecosystem and caps concurrent open PRs at five. Bumps are reviewed by hand — never auto-merged — because each SHA change is a fresh opportunity to audit what the action is doing.

GitHub Environment configuration

Both jobs declare environment: staging. The GitHub Environment named staging is configured in the repo UI, not in Terraform — environments are a GitHub construct. Two settings matter: deployment-branches is restricted to main (belt-and-suspenders on top of the trust policy's :ref condition), and AWS_ACCOUNT_ID is set as an environment variable, not a secret. The account ID is not a credential, and variables render in logs where a secret would be masked — useful when debugging a trust-policy mismatch.

Operating this piece

Rerun a failed deploy

  1. Go to the Actions tab, click the failing run, and use the Re-run failed jobs button. The concurrency group serializes the retry behind any in-flight deploy.
  2. If the failure was in the rolloutState poll, the deploy may have already rolled back by itself — confirm with aws ecs describe-services --cluster mythrun --services mythrun-staging-api --query 'services[0].deployments' before pushing a fix.
  3. If the smoke test failed but rolloutState was COMPLETED, the new revision reached RUNNING but /health didn't come back clean. Tail CloudWatch (/mythrun/staging/api) before re-rolling.

Trigger a manual deploy (no new commit)

  1. In the Actions tab, select the Deploy workflow and use Run workflow against the main branch.
  2. This rebuilds and redeploys the same SHA that's currently on main. Useful when the image in ECR needs to be rolled forward for a base-image refresh without a source change.

Roll back to a previous revision

  1. List the task-def family: aws ecs list-task-definitions --family-prefix mythrun-staging-api.
  2. Point the service at an earlier revision: aws ecs update-service --cluster mythrun --service mythrun-staging-api --task-definition mythrun-staging-api:<N>. The circuit breaker is on, so if the old revision is itself broken the service will roll forward again, not leave you at zero tasks.
  3. Push a revert commit to main to keep the next CI run from re-deploying the bad revision on top.

Recover from a pull-through cache cold start

  1. The first build after the cache rule is created (or after a new upstream image hasn't been pulled in 30+ days) takes noticeably longer while ECR fetches from public.ecr.aws. This is expected — no action needed.
  2. If the build fails with an ECR authorization error on ecr-public/docker/library/*, the GH Actions role is missing ecr:CreateRepository or ecr:BatchImportUpstreamImage on the ecr-public/* prefix — see the Serving page's IAM notes.

Integration points

The workflow consumes the Serving module's GitHub Actions role, ECR repo, ECS cluster, and the staging API service. The image it builds is produced by the backend Dockerfile, which reads the BASE_IMAGE_REGISTRY ARG this workflow sets. The pull-through cache itself is a shared-workspace resource — see the Serving page's shared-platform section. Post-launch, a sibling prod job will be appended to this same workflow, assuming a separate mythrun-github-actions-production role (Serving, follow-up bead).
