CI/CD

The push-to-deploy pipeline. A four-job GitHub Actions workflow that on every push to main builds the backend image through an ECR pull-through cache, assumes the staging GitHub Actions role via OIDC, registers a new task-def revision pinned to the image digest, and rolls the two ECS services in parallel — deploy-staging-api against the API service (with a public /health smoke test) and deploy-staging-worker against the worker service (task-internal probe via the ECS container healthCheck). Both deploy jobs poll rolloutState independently so a circuit-breaker rollback on either surface fails the run loudly.

How it fits together

The workflow lives at .github/workflows/deploy.yml. It triggers on pushes to main whose paths include application code — doc-only and tracker-only commits (docs/**, .beads/**, **/*.md, wiki/**) skip the run. workflow_dispatch is on so a deploy can be re-run by hand from the Actions tab without pushing a no-op commit.

One concurrency group per ECS service, not per branch — a future branch-based preview deploy or the eventual prod append won't share a queue with staging. Two simultaneous pushes to main serialize against deploy-mythrun-staging-api; cancel-in-progress is off so a mid-roll deploy finishes before the next one starts.

The build job

The build job checks out the repo, sets up pnpm + Node from .nvmrc, and runs pnpm install --frozen-lockfile --filter @mythrun/backend.... The @mythrun/backend... filter scopes install to the backend and its transitive workspace dependencies so a broken sibling workspace (say @mythrun/wiki) can't red-light a backend deploy. --frozen-lockfile still validates the whole lockfile, so lockfile drift is caught regardless of the filter. After install, the job runs lint, typecheck, and test against the backend package — the same four verbs the Backend page documents, scoped to the workspace being shipped.

pnpm install runs before the OIDC role assume — npm lifecycle scripts execute at install time. Running them before AWS credentials are in the environment means a compromised transitive dependency can't exfiltrate the deploy role's STS token. This ordering is load-bearing; do not hoist the assume step.

After the verification gates pass, the job assumes the mythrun-github-actions-staging IAM role through the shared GitHub OIDC provider, logs in to ECR, and runs docker build. The build passes --build-arg BASE_IMAGE_REGISTRY=$REGISTRY — the account-specific ECR host — so the backend Dockerfile resolves its FROM through the ECR pull-through cache instead of Docker Hub directly.

Pull-through cache, not Docker Hub direct — GitHub-hosted runner IP pools collectively hit Docker Hub's 100-pulls-per-6h anonymous rate limit at team scale, and direct pulls add transit latency to every cold build. Routing through aws_ecr_pull_through_cache_rule.ecr_public keeps pulls in-region and auth-free. Upstream is public.ecr.aws (AWS's official mirror of the Docker Hub Library namespace), not registry-1.docker.io directly — Docker-Hub-proper pull-through now requires Secrets Manager-stored credentials, which the ECR Public path sidesteps.

The build step tags the image twice — :$GIT_SHA and :latest — and pushes both. OCI image labels carry the source URL, the revision SHA, the build timestamp, and a pair of com.mythrun.workflow_run* labels that make the pushed image clickable back to the originating run in registries that render OCI annotations. The final build step resolves the image's content-addressable digest by reading Docker's local RepoDigests array via docker inspect --format='{{index .RepoDigests 0}}' and publishes it as the job output.

Local docker inspect, not aws ecr describe-images — calling ECR after the push introduces a TOCTOU window: an attacker with ECR push could re-tag :$GIT_SHA to point at a different image between our push and our describe, and the deploy would silently pin to the attacker's digest. Reading Docker's own record of the push closes that window — the digest is whatever docker just uploaded.

The deploy-staging job

The deploy job reassumes the same role (jobs don't share credentials) and walks the task definition through a render-update-verify cycle. It calls aws ecs describe-task-definition --task-definition mythrun-staging-api to grab the current revision, runs amazon-ecs-render-task-definition to swap the container image for the digest-addressed URI from the build job's output, and then amazon-ecs-deploy-task-definition registers the new revision and calls update-service. wait-for-service-stability: true blocks until ECS reports the deployment settled, with a 15-minute ceiling.

Digest-pinned image, not :$GIT_SHA — ECS task definitions resolve tags at task-launch time. A tag-pinned task def would revisit the registry on every placement and be vulnerable to the same re-tag attack the docker inspect step defends against. A digest-pinned task def is immutable by construction.

After the deploy action returns, the job runs update-service --desired-count 1. On the very first deploy this flips the service from 0 → 1 (task definitions get registered at :placeholder with desired_count=0 — see the Serving page); on every deploy after, it's a no-op. Ordering matters: the desired-count flip runs after the deploy action, so ECS never attempts to place on the :placeholder revision.

The wait-for-stability flag alone isn't enough to catch a failed deploy — AWS's services-stable waiter returns SUCCESS even after a circuit-breaker rollback. The next step polls describe-services directly every 10 seconds for up to two minutes, reading deployments[].rolloutState on the PRIMARY deployment. On COMPLETED with running == desired and zero failed tasks, the step passes; on FAILED, the step fails immediately with a pointer to the recovery runbook; a two-minute no-progress window also fails the job.

Explicit rolloutState poll, not just the waiter — the ECS deployment circuit breaker rolls the service back to the previous task-def revision when a new revision's tasks repeatedly fail to reach healthy. The waiter observes the service settled, doesn't notice it settled at the old revision. Reading rolloutState is the only way to distinguish a real success from a rollback-that-settled.

The final step smoke-tests https://staging-api.mythrun.com/health. It retries three times with a 10-second pause between attempts and demands both a 200 response and a JSON body matching .status == "ok". Body-matching guards against the ALB's default-action 404 succeeding by accident: a listener-rule misconfiguration would still return 200 from something, but not {"status":"ok"} from the backend.

The deploy-staging-worker job

The worker deploy job is a near-mirror of the API job, with three deliberate differences. It reuses the same digest from the build job's output (one build feeds both deploys), but it targets mythrun-staging-worker as the family / service / container name, runs in a separate concurrency group (deploy-mythrun-staging-worker) so a worker-only redeploy doesn't queue behind an API deploy and vice versa, and omits the public HTTPS smoke test — the worker has no ALB listener. The worker's own internal health endpoint on :3001 is task-internal and probed by the ECS container healthCheck block, which the rolloutState poll already gates on.

Two jobs, not one matrix — a matrix: over [api, worker] was the obvious shape, but each surface has subtly different verification (the API needs a public smoke test; the worker needs a CloudWatch follow-up if logs are interesting). Concurrency groups also have to differ. Two explicit jobs are 20% more YAML and 100% more readable: each can be re-run, re-failed, or extended independently in the Actions UI.

Job ordering: needs: [build, db-migrate] — the same dependency the API job carries, so both deploy surfaces wait for migrations to finish before they roll. The build job runs once and feeds both. Each deploy job assumes the GH Actions role fresh (jobs don't share credentials), pulls the current task-def, renders the image digest in, calls amazon-ecs-deploy-task-definition with wait-for-service-stability: true, flips desired-count to 1 (no-op after the first deploy), and polls describe-services for up to two minutes looking for rolloutState == COMPLETED with running == desired and zero failed tasks. The rolloutState poll catches a circuit-breaker rollback that the stability waiter alone misses — same defense as the API job, same shape.

Why Terraform env-var changes need a CI run

The serving module's ECS services ignore changes to task_definition. That split — Terraform owns the service, CI owns the revision — is what keeps the two systems out of each other's way during normal deploys, but it has a non-obvious operational consequence: a terraform apply that changes an env var or a secret reference REGISTERS a new task-def revision and then the live service quietly stays on whatever CI last deployed. To engage the change, run CI.

Don't force-roll onto a TF-registered revision — TF's task-def template pins the container image to :placeholder because Terraform doesn't know the real ECR digest. CI's amazon-ecs-render-task-definition step is what fetches the latest active revision (the one TF just registered with the new env var) and renders the real digest into a fresh revision before update-service. aws ecs update-service --task-definition mythrun-staging-api:<TF-rev> --force-new-deployment attempts to pull :placeholder and fails with CannotPullContainerError; the live service stays on the old (no-env-var) revision while the new deployment loops on the pull error. The MYT-35 boot-gate rollout caught this in production-of-staging; the fix is always "trigger CI, don't manually roll the service onto the TF rev."

In practice, after a TF apply that changes env vars or secret references on the serving module: gh workflow run Deploy, watch the run, confirm the deployed task-def revision is strictly greater than the TF-registered one (CI adds a fresh revision rather than reusing TF's :placeholder-image revision). The same pattern applies to the emergency-rollback path described on the Backend page.

Dependabot for SHA-pinned actions

Every third-party action in the workflow is pinned by commit SHA, not by tag, because tag mutations upstream are the dominant supply-chain threat vector for CI. .github/dependabot.yml schedules weekly bump PRs against the github-actions ecosystem and caps concurrent open PRs at five. Bumps are reviewed by hand — never auto-merged — because each SHA change is a fresh opportunity to audit what the action is doing.

The db-migrate workflow

Code and schema ship through two complementary pipelines. deploy.yml handles the code path — rolls a new image onto the ECS API service. .github/workflows/db-migrate.yml handles the schema path — applies the SQL files in backend/migrations/ to staging RDS. The pair is held in tension by a container boot-gate that refuses to start the API on a schema-mismatched DB, so a code roll cannot race ahead of its required schema change.

Two workflows, one interlock — early drafts considered baking the migration step into deploy.yml directly. The separate-workflow shape (with the boot-gate as the safety net) keeps each surface focused: db-migrate is the canonical "apply pending migrations" trigger, decoupled from any specific code roll. Operators can rerun migrations without redeploying. If db-migrate doesn't run for any reason, the next Deploy hits the boot-gate, ECS circuit-breaker rolls back, and the failure is loud at the right surface. See 2026-05-11 migration runner design §2 D3.

Triggers: push to main with path filter backend/migrations/*.sql, or manual workflow_dispatch. Both Deploy and db-migrate auto-fire on a paired commit (migration + code in the same push); they run concurrently with no cross-workflow ordering. If Deploy reaches the boot-gate before db-migrate finishes, the deploy fails on rolloutState=FAILED, ECS rolls back, the previous image continues serving, and the operator re-triggers Deploy after db-migrate is green.

The workflow itself follows deploy.yml's pattern exactly: describe-task-definition → amazon-ecs-render-task-definition with the image swapped to mythrun:<github.sha> → explicit register-task-definition → run-task against the new revision → wait tasks-stopped. The image is pinned by commit SHA (not :latest) to defeat the race where a parallel Deploy retags :latest before db-migrate reads it. The log-stream name is derived from the task ARN (deterministic) so the “tail logs” step never picks up a sibling run's stream. Failures distinguish task-failed-to-start (exitCode == null, stoppedReason set) from task-failed-during-run (exitCode != 0, logs available).

Separate migrate DB role with rds_superuser + app-user membership — the migrate task connects as a dedicated mythrun_staging_migrate user, distinct from the API's mythrun_staging. rds_superuser grants the role CREATE EXTENSION for the RDS-allowed list (pgcrypto, pgvector, uuid-ossp). It is not a true Postgres SUPERUSER and cannot bypass object ACLs on its own, so the role also gets membership in mythrun_staging via GRANT mythrun_staging TO mythrun_staging_migrate — that inherits ALTER/DROP rights on the existing app-owned tables. Bootstrap-db provisions the user + populates a {username, password} JSON secret at mythrun/staging/migrate-db-credentials in Secrets Manager; the ECS task fetches :password:: at task launch.

The pre-push hook (local mirror of CI)

Every push to main from a developer's machine first passes through .husky/pre-push, a six-stage gate that mirrors what CI is going to re-assert on the push it just accepted. The hook runs in cheapest-first order — a one-second grep, a ~3 s typecheck, a ~10 s lint, the ~3 min coverage suite, a ~2 s wiki source-hash diff, and (when the diff touches the dev-tool surface) a ~30 s JSDOM verifier run. Any non-zero step refuses the push and prints the diagnostic the operator needs.

Hook locally, re-assert in CI — never trust the hook alone — a developer can always --no-verify their way past Husky. The hook exists so red CI is impossible from this machine in the normal flow, but every gate it runs is duplicated in lint-auth.yml + deploy.yml so the production gate is the workflow, not the local hook. The point of the hook is fast feedback (catch a typo in 3 s instead of 6 min of CI queue), not coverage on its own.

The six stages, in order:

  1. Auth-narrowing pattern check. A single grep -rEn 'request\.user[!?]\.|request\.user as ' against backend/src/, excluding __tests__/ and backend/src/auth/. Any match aborts with a pointer to the assign-then-check pattern or requireUser(request). Mirrors .github/workflows/lint-auth.yml exactly.
  2. Backend typecheck. pnpm --filter @mythrun/backend typecheck.
  3. Backend lint. pnpm --filter @mythrun/backend lint. Exits non-zero on errors, not warnings — the 21 outstanding max-lines warnings on a handful of files are intentional and not gated.
  4. Backend coverage suite. pnpm --filter @mythrun/backend test:coverage. Vitest is configured with hard thresholds at 100% lines, 100% branches, 100% functions, 100% statements; anything below fails the run.
  5. Wiki source-hash freshness. Sources backend/.env.development so DATABASE_URL is set for the schema fragment build, then runs pnpm wiki:check — a hash diff of every page's declared sources against the live tree. ~2 s. Mirrors the Wiki CI workflow. Added 2026-05-14 after three consecutive red CI runs from wave-3/wave-4 source additions that the earlier four-gate hook didn't catch.
  6. Dev-tool verifier. Conditional — only runs when the diff touches backend/dev-tool/** or backend/src/contract/{backend-routes,pipeline-routes}.ts. Invokes pnpm dev-tool:verify, which boots a JSDOM environment per panel, identity- bootstraps a dev sub, mounts each panel against the live backend, and asserts the panel reaches its declared data-state ready / error / idle / loaded marker. Catches the bug class that vitest unit tests miss (real-backend contract drift) — see the dev tool page for the verifier + AUTHORING.md contract. Added 2026-05-15 (myth-e5mn) after three dev-tool bugs shipped to the user despite green unit tests + green dev-tool:check.
100% coverage as a hard threshold, not a soft target — Mythrun's production code path goes through the boot-gate-managed connections (Postgres, Redis), the typed-error taxonomy, and the auth + billing surfaces. Soft coverage targets let untested error arms accumulate silently; the gate flips that — every new branch either has a test or carries a /* c8 ignore */ marker with a one-line rationale for why it's structurally unreachable (e.g., INSERT … RETURNING's never-empty rows, defense-in-depth type-narrowing of pg's QueryResult.rowCount). The ignore markers are reviewed in PR like any other code change.

backend/vitest.config.ts carries the threshold config and the exclusion list (COVERAGE_EXCLUDES). Excluded files are scripts and process entrypoints that vitest can't reach — src/server.ts and src/worker.ts (they exit the process), src/db/migrate.ts (one-shot CLI exercised by every integration test's beforeAll), src/scripts/** (standalone debug tools), src/repo/index.ts (re-export barrel), and a handful of pure-type files. Each entry in COVERAGE_EXCLUDES carries a one-line justification; adding to the list is a design decision, not a place to hide untested work.

Order: cheapest first, slowest last — a one-second grep gives the operator feedback on the auth-narrowing violation before the 3-minute coverage suite even starts. If the grep finds an offender, the typecheck never runs. This keeps the hook fast for the dominant case (clean push) and fast-fail for the common-error case (lint or pattern violation).

GitHub Environment configuration

Both jobs declare environment: staging. The GitHub Environment named staging is configured in the repo UI, not in Terraform — environments are a GitHub construct. Two settings matter: deployment-branches is restricted to main (belt-and-suspenders on top of the trust policy's :ref condition), and AWS_ACCOUNT_ID is set as an environment variable, not a secret. The account ID is not a credential, and variables render in logs where a secret would be masked — useful when debugging a trust-policy mismatch.

Operating this piece

Rerun a failed deploy

  1. Go to the Actions tab, click the failing run, and use the Re-run failed jobs button. The concurrency group serializes the retry behind any in-flight deploy.
  2. If the failure was in the rolloutState poll, the deploy may have already rolled back by itself — confirm with aws ecs describe-services --cluster mythrun --services mythrun-staging-api --query 'services[0].deployments' before pushing a fix.
  3. If the smoke test failed but rolloutState was COMPLETED, the new revision reached RUNNING but /health didn't come back clean. Tail CloudWatch (/mythrun/staging/api) before re-rolling.

Trigger a manual deploy (no new commit)

  1. In the Actions tab, select the Deploy workflow and use Run workflow against the main branch.
  2. This rebuilds and redeploys the same SHA that's currently on main. Useful when the image in ECR needs to be rolled forward for a base-image refresh without a source change.

Roll back to a previous revision

  1. List the task-def family: aws ecs list-task-definitions --family-prefix mythrun-staging-api.
  2. Point the service at an earlier revision: aws ecs update-service --cluster mythrun --service mythrun-staging-api --task-definition mythrun-staging-api:<N>. The circuit breaker is on, so if the old revision is itself broken the service will roll forward again, not leave you at zero tasks.
  3. Push a revert commit to main to keep the next CI run from re-deploying the bad revision on top.

Bootstrap a new ECS service from :placeholder

Terraform creates each ECS service with desired_count = 0 and image = ":placeholder", then ignores changes to desired_count and task_definition. This decouples infra from the first deploy — Terraform sets the service shape, CI does the first revision flip. Today's deploy.yml workflow automates the sequence below; the steps are documented for future prod bring-up and for any future scenario where a service has been reset to :placeholder.

  1. Build and push the image tagged with the git SHA: docker push $REGISTRY/mythrun:<sha> and docker push $REGISTRY/mythrun:latest.
  2. Fetch the current task definition (revision 1, with the :placeholder image): aws ecs describe-task-definition --task-definition mythrun-staging-api --query 'taskDefinition'.
  3. Patch containerDefinitions[0].image to point at the real SHA. Strip the read-only fields the API rejects on register: taskDefinitionArn, revision, status, requiresAttributes, compatibilities, registeredAt, registeredBy. The aws-actions/amazon-ecs-deploy-task-definition action handles this field-stripping correctly — prefer it over hand-rolled jq.
  4. Register the patched definition: aws ecs register-task-definition --cli-input-json file://patched.json. This produces revision 2.
  5. Point the service at the new revision AND scale up: aws ecs update-service --cluster mythrun --service mythrun-staging-api --task-definition mythrun-staging-api:2 --desired-count 1 --force-new-deployment.
Why --task-definition is load-bearing — without it, the service keeps the :placeholder revision and only forces a new deployment of that broken image. --force-new-deployment on its own does NOT switch revisions; it just rolls the current one. The first deploy of a fresh service must always combine --task-definition, --desired-count 1, and the force flag.

Roll a TF env-var or secret-reference change into the live service

  1. Edit the serving-module input or per-env workspace (e.g. add a key to extra_env), terraform plan, terraform apply. Expect a +/- aws_ecs_task_definition.api replacement (and the worker analogue) — TF registers a new revision with the change and a :placeholder image; the live service does not roll because of ignore_changes = [task_definition].
  2. Confirm no Deploy workflow is in flight: gh run list --workflow Deploy --status in_progress --limit 5. A concurrent CI run could land a revision that bypasses the TF change.
  3. Trigger CI: gh workflow run Deploy. CI's describe-task-definition returns the latest ACTIVE revision (the one TF just registered), render-task-definition renders the real ECR digest into a fresh revision, and update-service rolls the service onto it.
  4. Confirm the live service moved to a revision strictly greater than the TF-registered one: aws ecs describe-services --cluster mythrun --services mythrun-staging-api --query 'services[0].taskDefinition'.
Never aws ecs update-service --task-definition mythrun-…:<TF-rev> --force-new-deployment — TF revisions carry the :placeholder image. That command attempts to pull a non-existent tag, fails with CannotPullContainerError, and the failed deployment loops while the live service stays on the previous (real-image, no-change) revision. CI is the only path that pairs the new env var with a real image digest.

Recover from a pull-through cache cold start

  1. The first build after the cache rule is created (or after a new upstream image hasn't been pulled in 30+ days) takes noticeably longer while ECR fetches from public.ecr.aws. This is expected — no action needed.
  2. If the build fails with an ECR authorization error on ecr-public/docker/library/*, the GH Actions role is missing ecr:CreateRepository or ecr:BatchImportUpstreamImage on the ecr-public/* prefix — see the Serving page's IAM notes.

Integration points

The workflow consumes the Serving module's GitHub Actions role, ECR repo, ECS cluster, and the staging API service. The image it builds is produced by the backend Dockerfile, which reads the BASE_IMAGE_REGISTRY ARG this workflow sets. The pull-through cache itself is a shared-workspace resource — see the Serving page's shared-platform section. Post-launch, a sibling prod job will be appended to this same workflow, assuming a separate mythrun-github-actions-production role (Serving, follow-up bead).
