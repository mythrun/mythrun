Smoke testing

How we exercise the deployed staging API end-to-end. A single Cognito test user provisioned by Terraform, credentials in Secrets Manager, and a bash script that authenticates and hits a small set of routes that prove the cognitive stack is reachable. Designed for a daily-cron shape: one command, no operator typing, idempotent re-runs.

How it fits together

Three pieces compose the staging smoke. infra/modules/auth/smoke-test.tf provisions a native (non-federated) Cognito user smoke-test@mythrun.com with a Terraform-generated 32-character password that meets Cognito's policy. The password lives in Secrets Manager at mythrun/staging/smoke-test-credentials as a JSON-encoded {username, password} object. backend/scripts/smoke/staging.sh reads the secret, authenticates against Cognito via the USER_AUTH flow with a PASSWORD challenge inline (single API call, no challenge round-trip), and then hits the API with the resulting access token. pnpm smoke:staging at the repo root is the operator-facing entry point.

Native Cognito user, not federated — we don't have Mythrun-controlled Google or Discord test accounts and don't want to depend on a third-party provider for our smoke. A native user gives us end-to-end ownership of the credential. The user pool's username_attributes = ["email"] requires the username be a valid email shape; no actual mailbox exists at smoke-test@mythrun.com, but email_verified = true is set at provisioning so Cognito doesn't try to validate.
Pre-provisioned, not throwaway-per-run — the alternative is to have the smoke script create a fresh user each run. That requires the script to hold IAM write permissions on Cognito (admin-create-user + admin-set-user-password + admin-delete-user). A pre-provisioned user with read-only-secret access keeps the smoke's IAM footprint tight: it only needs secretsmanager:GetSecretValue on the credentials secret and cognito-idp:InitiateAuth (which the public client allows by design).
Why we use null_resource for user CRUD — the hashicorp/aws Terraform provider doesn't have an aws_cognito_user_pool_user resource. Cognito user CRUD is SDK-only. We use a null_resource with a local-exec provisioner that runs aws cognito-idp admin-create-user + admin-set-user-password --permanent. The provisioner is idempotent: admin-create-user errors with UsernameExistsException on re-runs, which we swallow via grep -v UsernameExistsException || true; the password set always succeeds. Triggers re-run on either user-id change or password rotation.

What the script verifies

Five HTTP requests against the live deployed API, exercising both the classifyProfanity call site (Haiku reachability) and the underlying users repository:

  1. GET /health/ready returns 200 (the container is serving traffic on the new revision).
  2. POST /api/users/register with a generated smoketester$$ username. First run: 201 fresh path. Subsequent runs: 409 idempotent (same Cognito sub returns the existing user record per MYT-38 spec). Either way, classifyProfanity fires twice (once on the username, once on the display name).
  3. GET /api/users/check-username?username=gandalf$$ returns {available: true} — Haiku classifies non-profane and the route reaches users.getByUsername, which finds nothing.
  4. GET /api/users/check-username?username=fucknugget returns {available: false, reason: 'offensive'} — Haiku classifies the offensive name and the route emits the rejection.
  5. GET /api/users/check-username?username=mythrun_admin returns {available: false, reason: 'impersonation'} — Haiku classifies the impersonation attempt.

Five Haiku calls show up in CloudWatch as structured log lines emitted by the LLM middleware: event: 'llm.call' with model: 'claude-haiku-4-5-20251001', token counts, and latency. Total cost per smoke run is ~$0.0005 at current Haiku pricing.

Why the smoke is not yet on a cron — today it's manual: pnpm smoke:staging. A scheduled GitHub Actions run is the obvious next step but needs CloudWatch alarm wiring before it's worth automating; an unwatched green/red signal is operational noise. Until alarms exist, the script lives where any human or agent can run it on demand: pre-deploy, post-deploy, after a flaky-feeling outage, or during a billing-rate change to verify spend is what we expect.

Operating this piece

Run the staging smoke

  1. From the repo root, run pnpm smoke:staging. Expected output: green checkmarks on each step and a final “Smoke passed” line.
  2. If a step fails, the script exits non-zero and prints the request body that didn't match expectations. CloudWatch /mythrun/staging/api has the corresponding server-side log line.

Rotate the smoke-test credentials

  1. From infra/environments/staging/, run terraform apply -replace=module.auth.random_password.smoke_test[0].
  2. Terraform regenerates the password, updates Secrets Manager, and runs the null_resource provisioner to set the new password as permanent on the Cognito user.
  3. Re-run pnpm smoke:staging to confirm the new credentials work.

Integration points

The smoke exercises the LLM client through the onboarding routes wired up in Onboarding & invites. The Cognito user pool itself is documented under Identity; the smoke test user is one extra row alongside the federated users that flow in via Google and Discord.
