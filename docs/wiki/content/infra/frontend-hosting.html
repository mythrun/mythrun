Frontend hosting

Where the built React app lands in staging: a private S3 bucket behind a CloudFront distribution at staging.mythrun.com, with a fail-closed HTTP Basic-Auth gate that keeps the pre-launch site off the open internet while still reachable from any network.

How it fits together

frontend-hosting is a single reusable Terraform module composed by the staging/ workspace. It owns four pieces of AWS surface: a private S3 bucket that holds the compiled SPA, a CloudFront distribution that fronts it, a CloudFront Function that gates access, and the Route 53 records that point the domain at the distribution. The Deploy Frontend workflow is what fills the bucket; this module is the standing infrastructure that serves it.

The private bucket and Origin Access Control

The artifact bucket (mythrun-staging-frontend) is private end-to-end: all four public-access-block controls are on, and the only principal allowed to read it is CloudFront. The bucket policy grants s3:GetObject (and nothing else) to the cloudfront.amazonaws.com service principal, conditioned on AWS:SourceArn equal to this exact distribution. CloudFront reaches the origin through an Origin Access Control with signing_behavior = "always", so every origin request is SigV4-signed and the bucket never needs a public path.

OAC overwrites the viewer's Authorization header — the Basic-Auth gate (below) sends an Authorization: Basic … header. With signing_behavior = "always", CloudFront replaces that header with its own SigV4 signature on the origin request, so the Basic credential never reaches S3 and origin signing still works. The managed CachingOptimized policy is load-bearing here too: it does not forward Authorization into the cache key or the origin request. Attaching an origin-request policy that forwarded it would break SigV4 signing — a module invariant.

The CloudFront distribution

The distribution serves a single alias, staging.mythrun.com, over the shared *.mythrun.com wildcard cert from the DNS module — no new certificate. It is dual-stack (is_ipv6_enabled), compresses responses, redirects http to https, allows only GET/HEAD, and uses the AWS-managed CachingOptimized cache policy. PriceClass_100 limits the edge footprint to North America and Europe.

Reuse the wildcard cert, not a per-distribution cert — CloudFront requires its ACM cert in us-east-1, which the whole Mythrun stack already is. The shared *.mythrun.com cert already covers staging.mythrun.com, so the module takes the cert ARN as an input rather than minting and validating its own.

Two custom error responses map both 403 and 404 from the origin to /index.html with a 200 — the SPA fallback that lets client-side routes resolve on a deep link or a hard refresh.

403 → index.html, not just 404 — a private OAC bucket with GetObject-only (no ListBucket) returns 403 Forbidden, not 404, for a key that doesn't exist. A missing deep-link path like /campaigns/abc is a non-existent key, so without the 403 mapping every client-side route would surface as Access Denied. The Basic-Auth 401 is emitted by the gate function before the origin is ever consulted, so it is unaffected by these origin-error rules.

The Basic-Auth gate

The site must not be publicly reachable before launch, but it must be reachable from Miklos's laptop on any network. The mechanism is a CloudFront Function bound to the distribution's viewer-request event. It reads a single expected value — the literal Basic <base64(user:pass)> header — from an associated KeyValueStore and compares it to the request's Authorization header. Only the exact-match path returns the request; every other branch returns a 401 with a WWW-Authenticate: Basic challenge, so the browser shows its native login prompt.

A CloudFront Function, not WAF or Lambda@Edge — a WAF IP-allowlist ties access to a network location, which breaks the moment Miklos is on mobile, a café, or a VPN; a shared password works from anywhere. Lambda@Edge would do the job but is heavier and pricier — a full Lambda replicated to every edge, with cold starts — for what is a single string comparison. A CloudFront Function runs in sub-millisecond edge compute, costs a fraction, and its one real limitation (no general network calls) doesn't bite because the only state it needs is the KVS, which Functions can read natively.
The password lives in the KVS, set out-of-band — never in git or state — Terraform creates the KeyValueStore empty. The expected header is written afterward with the AWS CLI (see the runbook below). Threading the password through a Terraform variable would persist it plaintext in the state bucket and almost certainly in git history; keeping it in the KVS means rotation never touches Terraform and the secret never lands in version control.
Fail closed in every branch — the function denies by default: a missing Authorization header, a KVS read that throws, an unset key (the value comes back null), or a mismatch all return 401. The only path that passes traffic through is a present-and-equal comparison. So a half-finished bring-up — distribution live but password not yet set — denies access rather than briefly exposing the site. A node:test suite in the module exercises all four deny branches plus the pass-through.
The gate is a perimeter, not the app's auth — behind the Basic-Auth wall the SPA still runs its real JWT login flow against the staging API. Gating at the edge means no part of the pre-launch app is exposed — not the login page, not static assets, not unauthenticated routes — while the staging experience stays realistic: you still sign in with a real account. At launch the gate is removed and the app's own auth is the only boundary.

Route 53 and environment parameterization

Two alias records — an A and an AAAA — point staging.mythrun.com at the distribution. Both are needed: the distribution is dual-stack, so an IPv6-only client must be able to resolve the name. The aliases target CloudFront's fixed global hosted-zone ID (Z2FDTNDATAQYW2), not the Route 53 zone ID.

The module is environment-parameterized so production can reuse it unchanged at Launch. The site_domain input is a bare FQDN (so the prod apex mythrun.com is expressible, not just a subdomain), and enable_basic_auth toggles the whole gate — the Function, the KeyValueStore, and the viewer-request association are all count-gated on it. Production reuses the module with the apex domain and enable_basic_auth = false; staging passes true.

Operating this piece

Stand up the gated staging site

  1. terraform apply in infra/environments/staging/. This creates the bucket, the distribution, the empty KeyValueStore, the Function, and the Route 53 aliases. CloudFront propagation takes a few minutes.
  2. Read the deploy identifiers Terraform now exports: terraform output -raw frontend_bucket_name and terraform output -raw frontend_distribution_id.
  3. Set them as GitHub Environment variables on the staging environment — STAGING_FRONTEND_BUCKET and STAGING_FRONTEND_DISTRIBUTION_ID. The Deploy Frontend workflow pre-flight fails loudly if either is missing.
  4. Set the Basic-Auth password (next runbook). Until it is set, the gate fails closed and the site answers 401 to everyone.
  5. Push a frontend/** change to main (or run the workflow by hand) to publish the first build.

Set or rotate the Basic-Auth password

  1. Grab the KeyValueStore ARN: terraform output -raw frontend_kvs_arn.
  2. Compute the expected header from the chosen credentials: printf 'Basic %s' "$(printf 'user:pass' | base64)".
  3. The data-plane API needs the current ETag for a conditional write: aws cloudfront-keyvaluestore describe-key-value-store --kvs-arn <arn> and read ETag.
  4. Write the value under the fixed key the function reads: aws cloudfront-keyvaluestore put-key --kvs-arn <arn> --key staging-basic-auth --value "<Basic header>" --if-match <ETag>. The change is live at the edge within seconds — no redeploy.
  5. Verify: curl -s -o /dev/null -w '%{http_code}' https://staging.mythrun.com/ returns 401 with no header and 200 with -u user:pass.

Open the site at launch

  1. Set enable_basic_auth = false on the module block and terraform apply. This destroys the Function, the KeyValueStore, and the viewer-request association; the distribution stays up and now serves the SPA to the public.
  2. Confirm the app's own JWT auth is now the only boundary — every protected route should still require a real login.

Integration points

The distribution serves the SPA built by the frontend app and reuses the wildcard cert and hosted zone from the DNS module. The Deploy Frontend workflow uploads each build and invalidates /index.html; the GitHub Actions deploy role carries the scoped S3 and CloudFront-invalidation grants that workflow uses. The built app points at the staging API at staging-api.mythrun.com.

Appendix: inputs & outputs

Module inputs

Variable Default Notes
site_domain — Bare FQDN. Drives the CloudFront alias, the Route 53 record name, and the URL output.
acm_certificate_arn — us-east-1 cert covering site_domain. The shared wildcard cert.
hosted_zone_id — Route 53 zone for mythrun.com (shared dns_zone_id).
environment — One of staging, production. Naming and tags only.
enable_basic_auth true Toggles the whole gate (Function + KVS + association). false at launch.

Module outputs

Output Notes
bucket_name Set as GH var STAGING_FRONTEND_BUCKET.
distribution_id Set as GH var STAGING_FRONTEND_DISTRIBUTION_ID; used for invalidation.
distribution_arn Consumed by the OIDC role's cloudfront:CreateInvalidation grant.
url https://staging.mythrun.com.
kvs_arn Basic-Auth KeyValueStore ARN for the out-of-band password set/rotate. Null when disabled.
