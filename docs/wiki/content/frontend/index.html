Frontend

The frontend workspace and the lint rails that gate it. Two pnpm packages — @mythrun/web (the React app) and @mythrun/ui (the design system) — plus three "rules of the road" turned into CI lints before any real UI is built. As of today this is an empty-but-enforced skeleton: it builds, the rails bite, and the gates run. No real components, tokens, or flows yet — those land in later issues.

Rails before track — the foundation ships the enforcement, not the UI. Once the rails are wired, a hardcoded string or an ad-hoc element in feature code is a CI failure from the first real component onward. Putting the gates down first means the team never has to retrofit discipline onto a pile of already-written markup.

The two-package workspace

pnpm-workspace.yaml lists two new packages alongside the backend and the wiki. frontend/ is @mythrun/web — the React app: routes, features, flows. frontend/ui/ is @mythrun/ui — the mythrunUI design system. The app declares "@mythrun/ui": "workspace:*" and pnpm symlinks the package directory.

@mythrun/web imports the library as source, not a built bundle. @mythrun/ui's package.json points its exports map at ./src/index.ts, and the consumer's moduleResolution: "Bundler" permits importing .ts/.tsx source directly. So import { Text } from '@mythrun/ui' resolves to the library's TypeScript, with no intermediate compile step. The library has no build script; root pnpm -r build builds @mythrun/web (via Vite) and intentionally skips @mythrun/ui.

Source-consumed library, no publish step — both packages live in this repo and deploy together; there is no external consumer that needs a versioned, pre-built @mythrun/ui artifact. Skipping the build step keeps the library editable in place — a change to a primitive is visible in the app on the next Vite reload, with no rebuild-and-relink dance. The cost (the app's bundler must understand TypeScript source) is already paid: Vite compiles the app's own .tsx anyway.

The scaffold is Vite + React 19 + TypeScript (strict) + Tailwind v4. The tsconfig.json mirrors the dev-tool package, not the backend: module: ESNext, moduleResolution: Bundler, jsx: react-jsx, with strict, noUncheckedIndexedAccess, and exactOptionalPropertyTypes all on. Tailwind is wired CSS-first through @tailwindcss/vite — a single src/index.css with @import "tailwindcss" and an empty @theme {} block; the real OKLCH brand tokens land in a later issue. The library today is one trivial <Text> primitive — the boundary anchor that makes the lint rails testable on day one.

Mirrors dev-tool, not backend — the backend uses moduleResolution: NodeNext, but Vite and Vitest config files default-export, which the repo-wide ESLint config bans, and a bundler-style resolution is what lets the app import library .ts source. The backend/dev-tool package already solved exactly this shape — a per-package config with Bundler resolution — so the frontend follows that precedent rather than the backend one.

The three rules of the road

Three conventions govern all frontend code. Each is enforced as a lint, not left as a style guide — the third rule is that anything the team cares about becomes a CI lint.

Rule 1 — no hardcoded user-facing strings

Every user-visible string is an i18n key, never inline text. The off-the-shelf i18next/no-literal-string rule enforces it, set to error in mode: 'jsx-only' over feature code. That mode flags string literals in JSX text and in JSX attributes — the attribute case is load-bearing because mythrunUI props (<Text label="…" />) carry most user-facing text, and the plugin's weaker default would let those through. Non-user-facing attributes (data-testid, aria-*, role, id) are exempted so they don't trip the rule.

A known gap, carried forward deliberately — eslint-plugin-i18next allowlists bare JSX text inside PascalCase arrow-const components (const X = () => <Text>hi</Text> is not flagged — it treats the uppercase const like a constant). All attribute literals and JSX text inside function Comp() {} declarations still fail, and a raw element there still fails the no-ad-hoc-UI rail. Closing the arrow-const text gap belongs to the i18n-runtime issue, which also adds the typed t() provider and a callee allow-list. The gap is documented in the config so nobody mistakes it for a hole.

Rule 2 — no ad-hoc UI

Feature code composes @mythrun/ui components only — never raw DOM. The custom mythrun-ui/no-ad-hoc-ui rule (authored at frontend/eslint-rules/no-ad-hoc-ui.js) reports three AST shapes: an intrinsic lowercase JSX element (<div>, <button>, …), a style attribute, and a className attribute. It is pure AST shape — no type information needed. JSX fragments (<>…</>) and component elements (capitalized identifiers) are allowed; they carry no raw markup or styling.

The rule lives in the frontend config, not the root mythrun plugin — it is scoped to where it applies (frontend/src/**) and uses a distinct mythrun-ui/ plugin namespace, leaving the root mythrun namespace for backend rules. The rule file is a .js ESM module imported by both the ESLint config and its Vitest test, so it is instrumented by Vitest and counts toward the coverage gate — unlike the backend's .cjs rule files, which Vitest excludes.

The boundary is asymmetric. In the library zone (frontend/ui/**) the rule is off — raw elements, className, and Tailwind utilities legitimately live there, because that is where the primitives wrapping them are built. The jsx-a11y accessibility rails ride alongside, applying effectively only in the library, since intrinsic elements exist nowhere else. Accessible-element authoring is, by design, a library responsibility.

Rule 3 — the rules are CI lints, with a lint-enforced escape hatch

A true one-off escapes the no-ad-hoc-UI rail with // eslint-disable-next-line mythrun-ui/no-ad-hoc-ui -- <reason>. The escape hatch is itself enforced so it can't decay into a free-for-all. The frontend config sets reportUnusedDisableDirectives: 'error' (a disable that no longer suppresses anything is a CI error) and @eslint-community/eslint-comments/require-description: 'error' (a disable without a trailing -- reason is a CI error). A bare disable fails; only a disable that names its reason — and still suppresses a real violation — passes.

The hatch enforcement is added, not inherited — ESLint does not natively require a -- reason, and the root config does not set reportUnusedDisableDirectives at error severity. The frontend config adds both. This is what makes the escape hatch a deliberate, reviewed act (a named reason in the diff) rather than a silent bypass.

Coverage and the wiring tests

Frontend Vitest enforces 100% on the logic surface — lines, branches, functions, statements — while presentational code is excluded from the percentage (rendered in tests, not %-gated). Today the only logic is the custom lint rule; coverage.include is eslint-rules/**, to be extended with src/lib/**, src/hooks/**, and the future API/transport clients as they land. The convention that keeps this honest: logic lives in .ts, never .tsx, so the .tsx exclusion can't launder untested logic.

Two test files supply the acceptance evidence that the rails are real. The RuleTester suite for no-ad-hoc-ui drives the rule with inline code strings — invalid (<div>, style=, className=), valid (<Text/>, fragments) — and is what instruments the rule to 100%. The config-wiring test uses ESLint.calculateConfigForFile to assert both rails are error for a src/** path and no-ad-hoc-ui is off for a ui/** path, then lints inline strings to prove the rails actually fire. The wiring test runs under the plain test script (and is gated in CI) but is excluded from the coverage run, where loading the rule through ESLint's own loader corrupts the v8 map.

The gates

Both rails run in two places — a CI workflow and the pre-push hook — so a violation is caught before it can land. .github/workflows/frontend-check.yml is the frontend's required status check; .husky/pre-push gains a diff-scoped section that runs the same chain locally when a push touches the frontend. Both are documented in detail on the CI/CD page — including why frontend-check runs unconditionally (so it never blocks merges Pending on backend-only PRs) and why the pre-push section diffs on origin/main...HEAD rather than the staging area. The companion change: deploy.yml adds frontend/** to its paths-ignore, so a frontend-only push skips the backend image build and ECS deploy entirely.
