Frontend

The frontend foundation: the workspace, the lint rails that gate it, the i18n layer every string flows through, and the design tokens every component consumes. Three pnpm packages — @mythrun/web (the React app), @mythrun/ui (the design system), and @mythrun/client-core (the platform-neutral brain) — plus the "rules of the road" turned into CI lints before any real UI is built. The substrate is in place and enforced: the rails bite, every string is a typed key, and the brand's Parchment & Ink palette is importable in CSS and Tailwind. The component library those rails protect — mythrunUI — is the subject of its own page, the Design system; this page is the foundation it stands on.

Rails before track — the foundation ships the enforcement, not the UI. Once the rails are wired, a hardcoded string or an ad-hoc element in feature code is a CI failure from the first real component onward. Putting the gates down first means the team never has to retrofit discipline onto a pile of already-written markup.

The frontend workspace

pnpm-workspace.yaml lists three frontend packages alongside the backend and the wiki. frontend/ is @mythrun/web — the React app: routes, features, flows. frontend/ui/ is @mythrun/ui — the mythrunUI design system. frontend/client-core/ is @mythrun/client-core — the platform-neutral brain that holds the component contract and the token data (added in MYT-82; see the Design system page). The app declares "@mythrun/ui": "workspace:*" and pnpm symlinks the package directory; the same for client-core, which @mythrun/ui depends on.

@mythrun/web imports the library as source, not a built bundle. @mythrun/ui's package.json points its exports map at ./src/index.ts, and the consumer's moduleResolution: "Bundler" permits importing .ts/.tsx source directly. So import { Text } from '@mythrun/ui' resolves to the library's TypeScript, with no intermediate compile step. The library has no build script; root pnpm -r build builds @mythrun/web (via Vite) and intentionally skips @mythrun/ui.

Source-consumed library, no publish step — both packages live in this repo and deploy together; there is no external consumer that needs a versioned, pre-built @mythrun/ui artifact. Skipping the build step keeps the library editable in place — a change to a primitive is visible in the app on the next Vite reload, with no rebuild-and-relink dance. The cost (the app's bundler must understand TypeScript source) is already paid: Vite compiles the app's own .tsx anyway.

The scaffold is Vite + React 19 + TypeScript (strict) + Tailwind v4. The tsconfig.json mirrors the dev-tool package, not the backend: module: ESNext, moduleResolution: Bundler, jsx: react-jsx, with strict, noUncheckedIndexedAccess, and exactOptionalPropertyTypes all on. Tailwind is wired CSS-first through @tailwindcss/vite — a single src/index.css that does @import "tailwindcss" then @import "@mythrun/ui/styles.css" to pull in the token layer (below). Because Tailwind v4 doesn't scan node_modules, the same file adds @source "../ui/src" so utility classes used inside the library are detected. The library began as one trivial <Text> primitive — the boundary anchor that made the lint rails testable on day one — and is now the full mythrunUI component set, documented on the Design system page.

Mirrors dev-tool, not backend — the backend uses moduleResolution: NodeNext, but Vite and Vitest config files default-export, which the repo-wide ESLint config bans, and a bundler-style resolution is what lets the app import library .ts source. The backend/dev-tool package already solved exactly this shape — a per-package config with Bundler resolution — so the frontend follows that precedent rather than the backend one.

The three rules of the road

Three conventions govern all frontend code. Each is enforced as a lint, not left as a style guide — the third rule is that anything the team cares about becomes a CI lint.

Rule 1 — no hardcoded user-facing strings

Every user-visible string is an i18n key, never inline text. The rail is split across two cooperating rules because no single off-the-shelf rule covers both places a string can hide. JSX child text — the words between tags — is owned by a custom rule, mythrun-ui/no-untranslated-jsx-text. JSX attribute literals (<Text label="…" />, which is where most mythrunUI copy actually lives) are owned by the off-the-shelf i18next/no-literal-string, now scoped to attributes only. Both are error on feature code under src/**.

The custom rule is the authoritative JSX-child rail. It reports bare non-whitespace text, a string literal inside a child {…} expression, and a template literal with static text — and exempts numeric/expression children, interpolation-only templates, and anything inside a <Trans> element. The escape valve is the same one Rule 3 governs: a named // eslint-disable-next-line mythrun-ui/no-untranslated-jsx-text -- <reason>.

A custom child-text rail, not the plugin's — eslint-plugin-i18next has two holes on JSX children. It allowlists bare text inside PascalCase arrow-const components (it treats the uppercase const like a constant), and its should-validate-template:false default skips template-literal children entirely. The MYT-79 page documented the arrow-const gap as a known limitation; MYT-80 closed it for real by writing a purpose-built rule that covers every component shape and the template-literal case. The plugin keeps the attribute job, where it has no equivalent blind spot.
jsx-attributes.exclude, not ignoreAttribute — the attribute rail allowlists non-user-facing attributes (className, style, type, id, data-testid, aria-*, role, …) so they don't trip the rule. MYT-79 inherited an ignoreAttribute key here that is not a real plugin option — a silent no-op that allowlisted nothing. MYT-80 replaced it with the plugin's real jsx-attributes.exclude array. Because that array replaces the plugin defaults rather than extending them, the defaults are re-listed alongside the additions.

Rule 2 — no ad-hoc UI

Feature code composes @mythrun/ui components only — never raw DOM. The custom mythrun-ui/no-ad-hoc-ui rule (authored at frontend/eslint-rules/no-ad-hoc-ui.js) reports three AST shapes: an intrinsic lowercase JSX element (<div>, <button>, …), a style attribute, and a className attribute. It is pure AST shape — no type information needed. JSX fragments (<>…</>) and component elements (capitalized identifiers) are allowed; they carry no raw markup or styling.

The rule lives in the frontend config, not the root mythrun plugin — it is scoped to where it applies (frontend/src/**) and uses a distinct mythrun-ui/ plugin namespace, leaving the root mythrun namespace for backend rules. The rule file is a .js ESM module imported by both the ESLint config and its Vitest test, so it is instrumented by Vitest and counts toward the coverage gate — unlike the backend's .cjs rule files, which Vitest excludes.

The boundary is asymmetric. In the library zone (frontend/ui/**) the rule is off — raw elements, className, and Tailwind utilities legitimately live there, because that is where the primitives wrapping them are built. The jsx-a11y accessibility rails ride alongside, applying effectively only in the library, since intrinsic elements exist nowhere else. Accessible-element authoring is, by design, a library responsibility.

Rule 3 — the rules are CI lints, with a lint-enforced escape hatch

A true one-off escapes the no-ad-hoc-UI rail with // eslint-disable-next-line mythrun-ui/no-ad-hoc-ui -- <reason>. The escape hatch is itself enforced so it can't decay into a free-for-all. The frontend config sets reportUnusedDisableDirectives: 'error' (a disable that no longer suppresses anything is a CI error) and @eslint-community/eslint-comments/require-description: 'error' (a disable without a trailing -- reason is a CI error). A bare disable fails; only a disable that names its reason — and still suppresses a real violation — passes.

The hatch enforcement is added, not inherited — ESLint does not natively require a -- reason, and the root config does not set reportUnusedDisableDirectives at error severity. The frontend config adds both. This is what makes the escape hatch a deliberate, reviewed act (a named reason in the diff) rather than a silent bypass.

Coverage and the wiring tests

Frontend Vitest enforces 100% on the logic surface — lines, branches, functions, statements — while presentational code is excluded from the percentage (rendered in tests, not %-gated). The logic surface is the two custom lint rules plus the palette generator; coverage.include spans eslint-rules/** and the generator, to be extended with src/lib/**, src/hooks/**, and the future API/transport clients as they land. The convention that keeps this honest: logic lives in .ts, never .tsx, so the .tsx exclusion can't launder untested logic.

The test files supply the acceptance evidence that the rails are real. A RuleTester suite drives each custom rule with inline code strings — invalid (<div>, bare child text, template-literal children) and valid (<Text/>, fragments, {t('k')}, <Trans> descendants) — and is what instruments the rules to 100%. The config-wiring test uses ESLint.calculateConfigForFile to assert the rails are error for a src/** path and no-ad-hoc-ui is off for a ui/** path, then lints inline strings to prove they actually fire. The wiring test runs under the plain test script (and is gated in CI) but is excluded from the coverage run, where loading a rule through ESLint's own loader corrupts the v8 map. The token layer is covered separately — a manifest-driven presence test and a structural guard, both described under design tokens below.

The gates

Both rails run in two places — a CI workflow and the pre-push hook — so a violation is caught before it can land. .github/workflows/frontend-check.yml is the frontend's required status check; .husky/pre-push gains a diff-scoped section that runs the same chain locally when a push touches the frontend. Both are documented in detail on the CI/CD page — including why frontend-check runs unconditionally (so it never blocks merges Pending on backend-only PRs) and why the pre-push section diffs on origin/main...HEAD rather than the staging area. The companion change: deploy.yml adds frontend/** to its paths-ignore, so a frontend-only push skips the backend image build and ECS deploy entirely.

The i18n layer

Rule 1 says no hardcoded strings; the i18n layer is where they go instead. It is react-i18next on top of i18next, initialized once in src/i18n/config.ts and provided at the app root in main.tsx via <I18nextProvider>. Strings live in per-namespace locale files under src/i18n/locales/en/ — today a single common namespace — and components read them through t('key'). The config is wired against the diagram's i18n layer cluster: config.ts binds the typed-keys augmentation and the locale resources.

Synchronous init, no Suspense — config.ts calls init() with inline resources and no init callback. That combination is load-bearing: an init callback re-triggers i18next's internal setTimeout deferral, and an async backend would leave the first render before strings are loaded. With neither, init() loads synchronously and sets isInitialized before returning, so useTranslation()'s ready is true on first render — no flash-of-keys and no need for a <Suspense> boundary. Adding a callback or an async backend later would require reintroducing Suspense.

Keys are typed. src/i18n/i18next.d.ts augments the i18next module's CustomTypeOptions with the actual resource shape, so t('back') compiles and t('not.a.key') is a type error. A guard file (typed-keys.guard.ts) is typechecked but never imported: it holds a @ts-expect-error over a known-bad key, so if typed keys ever regress to plain string, the directive goes unused and pnpm typecheck fails loudly.

Typed keys via the i18next module augmentation — the alternative is a hand-kept union of key strings that drifts from the locale files. Augmenting CustomTypeOptions with typeof resources makes the locale JSON itself the source of truth: add a key to common.json and it is callable; remove one and every stale t() call fails to compile. The compiler enforces the catalog with zero hand-maintained list.

Prose copy is Miklos's to write, so most values ship as a [placeholder for <purpose>] string rather than guessed text — only generic chrome (Back, nav labels) gets a real value on day one. The pnpm i18n:todo script JSON-walks every locale file and lists each value still holding a placeholder, so unwritten copy is findable instead of silently shipping a bracketed string. It walks values structurally, so it survives nested keys and _one/_other plural shapes.

Design tokens

Every component consumes the same visual vocabulary: the brand's Parchment & Ink palette plus type, motion, and shadow scales. The tokens live in @mythrun/ui under src/styles/ and are pulled into the app through the single @import "@mythrun/ui/styles.css" in src/index.css. That entry file imports four layers in order — the generated palette, the @theme scales, the semantic aliases, and the base reset — matching the diagram's design tokens cluster.

The palette is 60 colors: six ten-step ramps (paper, ember, and the success/warning/danger/info semantics). The paper and ember anchors are the brand's hand-picked hexes, copied verbatim. The 36 other steps are generated: generate-palette.mjs uses culori to read each semantic anchor in OKLCH, then interpolates the rest of the ramp by borrowing ember's perceptual lightness curve and scaling chroma to the anchor — writing colors.generated.css (a @theme block of --color-* tokens), a tokens.manifest.json, and a tokens.html audit page. MYT-82 relocated the generator (and the raw token-scale data) into @mythrun/client-core/src/tokens/ — the platform-neutral home — leaving the web CSS emission in @mythrun/ui, which runs the generator at build time. That relocation and the completed token scales it brought are covered on the Design system page.

A generator for the 36 steps, not 36 hand-picked hexes — hand-tuning forty intermediate swatches by eye produces ramps that drift in lightness and read inconsistently against each other. Anchoring each semantic ramp to ember's OKLCH lightness curve makes every ramp perceptually parallel by construction, and the generator asserts strict monotonic lightness so a bad interpolation fails the build rather than shipping a muddy step. The brand's chosen anchors are still authoritative — they're emitted verbatim; only the in-between steps are computed.

On top of the raw palette sit semantic aliases — --bg, --surface, --ink, --accent, and the rest — that name a role rather than a color. These are what dark mode flips: a .dark class remaps each alias to a different paper/ember step (a true warm dark, not a second palette), and because the aliases are plain CSS custom properties in :root/.dark, the cascade does the flipping. A small @theme inline block then surfaces each alias as a Tailwind utility (bg-bg, text-ink) that references the var at runtime.

Why @theme inline for the dark flip — a plain Tailwind v4 @theme alias resolves its value once, at :root, and bakes it in — so a later .dark override never reaches the utility and the theme can't flip. Declaring the alias inline emits --color-bg: var(--bg) instead of the resolved paper hex, so the utility reads --bg live and the .dark remap cascades through. A token gate guards this: a structural test asserts semantic.css still maps --color-bg to var(--bg), so a well-meaning "simplification" to a plain alias fails CI rather than silently breaking dark mode.

The type scale is the brand's narrative-serif / machine-mono split — Source Serif 4 for body and narrative, IBM Plex Mono for UI and data — both self-hosted via @fontsource (imported in main.tsx), not pulled from a CDN. The @theme scales also carry the type-size, motion-duration, and shadow tokens, and the base layer adds a prefers-reduced-motion reset that collapses animation and transition durations for users who ask for less motion. The token gate's other half is a manifest-driven presence test: it reads tokens.manifest.json and asserts every declared color token actually appears in the source CSS, and that every semantic alias has both a :root and a .dark value.
