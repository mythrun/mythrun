Live play

The table itself: /campaigns/:id/play, where the party and the AI DM run a session. An atmospheric prep beat gives way to a Start that debits the owner's session credit, then the screen becomes a streamed multiplayer transcript — the DM's prose arrives token by token, the humans' messages post the instant they're typed, a mid-session joiner sees the full backlog, and a dropped connection resyncs without double-rendering the turn it dropped during. The route is a thin composition; all the reasoning — the start classifier, the transcript reducer, the transport view-model — lives in the platform-neutral client brain.

The screen adds no frame type and no read surface — enforced ignorance holds here by construction, not by prompt discipline. The play screen only ever renders frames the session transport hands it; it introduces no new WebSocket frame, no new backend read. There is deliberately no Slow-Thinker stage-direction frame anywhere in the client, and nothing on this screen may add one — the reason the DM intervened is never on the wire the player consumes.

How it fits together

PlayRoute (routes/play.tsx) is the router-mounted entry, and because the router mounts it directly — not through CampaignPage, which feeds the character surface a campaign prop — it resolves its own identity signals first. usePlayViewer loads two reads it already has slices for: getMe (the viewer's DB id — the reconcile key the server stamps on this player's message echoes — plus the display name) and the same GET /api/campaigns/mine payload the hub renders, found by id. From the campaign it derives ownership (creator === null ⟹ owner, the same signal character creation uses) and the party roster (userId → displayName). A campaign the viewer can't see resolves to a calm error — you can't play a session you're not a member of.

With the viewer resolved, PlaySession owns the rest. It calls start() once on mount and renders by the start flow's phase: the short connecting beat while the attempt is in flight, the prep beat, the live session shell, the purchase seam, or a calm retry notice. The route file itself stays a thin shell — the client-core hooks (the start classifier, the prep SSE fold, the transport view-model) carry every judgment, and each is an injectable seam so a test drives any phase deterministically without a live transport.

The start flow — one classifier, five arms

POST /api/sessions/:campaignId/start debits the campaign owner's session credit regardless of who pressed Start, and answers with one of several shapes that each mean a different next screen. classifyStartError (in client-core/session/start-flow.ts) maps a caught error to a discriminated StartOutcome, keying only on the contract-blessed status/code/body — never on prose (the ZFC line: pure orchestration, no pattern-matching). The useSessionStart hook resolves each outcome to a render phase:

  • 200 → ready{sessionId}: mount the live shell.
  • 409 session_already_active → the join path. The 409 body carries no sessionId, so the hook calls GET …/active to resolve the running session's id, then mounts the shell against it. This is the mid-session join.
  • 409 prep_not_ready → the prep beat (below), which resolves upward: when prep completes it re-attempts start().
  • 402 insufficient_credits → the purchase moment, carrying the owner-vs-member split.
  • 409 campaign_not_active / reconcile_pending / session_ending → a calm, retryable "blocked" notice; anything unrecognized is a generic retry.
The join arm and the prep arm are only distinguishable because the backend reordered its preconditions (MYT-92) — the start flow drives the atmospheric prep beat on prep_not_ready and the join path on session_already_active, so the two must be told apart truthfully. Until the play E2E caught it, a member whose /start raced an already-running session got prep_not_ready — because maxSessionNumber counts the live session, so the "next" prep legitimately doesn't exist — and pinned forever on the prep beat. The fix moved the active-session guard ahead of the prep guard on the server; the client relies on that discrimination.
Seed lastSeq = 0 on the very first connect — the view-model connects with seedLastSeq: 0, which asks the transport for a full-history replay. A fresh connect would otherwise get a session_ready with no messages, and only a reconnect replays the backlog. Seeding zero makes the owner's first connect, a reload, and the 409-join / mid-session joiner all rebuild the whole transcript from one session_reconnect batch — one code path covers every entry into a running session.

The prep beat (PrepBeat + useSessionPrep) is the "the DM is preparing tonight's session…" experience. It rides the shipped prep-status SSE (the campaign-scoped channel, distinct from world-gen), seeds its coarse bit off the connect-time snapshot, and advances on the live prep-started/prep-ready/prep-failed events. On ready it re-attempts start. It latches a failure: because a reconnect re-snapshots generating (the prep row's existence is the snapshot's only signal), the beat holds a seen failure on the calm retry rather than re-arming the atmospheric wait off a post-failure re-snapshot.

The transcript reducer — the reconnect-safe core

Once a session is ready, SessionShell drives useSession, the view-model over the shipped WS session client (a dumb typed pipe with production-grade reconnection). Every inbound frame folds through reduceFrameReconciling — the pure transcript-reducer.ts wrapped in the optimistic own-echo layer. The reducer models the transcript as an ordered list of TranscriptItems and owns transcript content only: the streamed DM prose (text_delta accumulates into one dm item per turnId, settling on turn_end), the confirmed player messages (deduped on seq), and every mechanical frame.

Every mechanical frame is a first-class item, even though MYT-92 renders it as one mono line — skill_check, dice_roll, ledger_update, mode_change, and the two combat_* frames each become a typed transcript item carrying the whole frame, not a flattened string. MYT-92 renders each as a terse system line, but modeling them fully now is the wave-2 shared contract: the dice-and-skill-checks and knowledge-sidebar issues extend the rendering (MessageStream's item dispatch), never the reducer's shape. The reducer is wave-2-final so two parallel issues can build on it without touching it.
Whole-turn replace, so a reconnect can't double-render the turn it dropped during — a client that drops mid-turn has a partial dm item built from live text_deltas. On reconnect the transport replays that same turn as seq-bearing rows. If the reducer merely appended them, the turn would render twice. So applyReconnect — an explicit folder seam, not a hidden branch — first prunes every existing DM/mechanical item whose turnId the replay batch carries, then re-folds the batch so each turn rebuilds settled. Player items (turnId null) survive the prune and dedup on seq instead. The seam is a separate exported function precisely so the optimistic layer can re-fold the same batch through a reconciling folder (below) rather than the raw one.

Optimistic own-messages

A player's own message appears the instant it's typed — addPending appends a player item with pending: true and no seq, keyed by a stable local id so React reuses the same node when the server echo confirms it in place. reduceFrameReconciling wraps the raw reducer: an inbound own player_message reconciles the first matching pending item — settling it and adopting the server's authoritative seq — instead of appending a duplicate. Because that confirmation happens outside the raw append path, it records the seq in the dedup ledger itself, or a redelivery would slip past. On a reconnecting → connected transition the hook arms a resend that fires after the replay batch settles: the replay confirms the messages that landed, and every still-pending one is re-sent.

The resend can duplicate, and that residual is accepted on purpose — the wire protocol carries no client message id, so reconciliation matches on (viewerUserId, text) in FIFO order. If a pending message actually landed but fell outside the transport's filtered replay window, the reconnect resend duplicates it. Adding a client message id is out of MYT-92 scope, so the residual is annotated in the code rather than hidden — the two dominant paths (a first-join backlog and a single in-flight-turn reconnect) are exact, and a rare duplicate on a lossy reconnect is the accepted cost of an input that never feels laggy.

Presence, and the parts the reducer won't touch

The reducer deliberately ignores the out-of-band control and presence frames; useSession folds those into a separate SessionPresence state through foldOutOfBand. The thinking indicator opens on dm_thinking and clears on the first text_delta/turn_end/turn_error for that turn; the typing set tracks typing_start/typing_stop; the ended flag flips on session_end. A session_reconnect resets the thinking indicator, so a stuck "DM is thinking…" can't survive a drop — a turn genuinely still running re-arms it with a fresh live frame. The route maps the transport's own connection status (reconnecting/failed) to a quiet system line pinned under the transcript, and resolves the presence typing userIds to display names through the party roster (unknown ids are omitted, never shown raw).

The stage — six components, two registers

SessionShell composes six mythrunUI components into a full-height flex column: the scroller, the thinking line, and the input, beside a desktop-only sidebar seam. The register split is the meaning — the DM speaks in narrative, the humans at the table speak in the mechanical voice:

  • MessageStream — the transcript scroller. Auto-follows the tail with a "jump to now" affordance, and positions instantly under prefers-reduced-motion (no smooth-scroll vestibular trigger). It dispatches each transcript item to its renderer and carries the connection system line.
  • DmMessage — the DM's prose in Source Serif 4 (--font-body), on a paper tint, appended token-wise as text_deltas arrive and settling on turn_end.
  • PlayerMessage — a human utterance in IBM Plex Mono (--font-ui), a distinct tint, on its own paper band. There is no bubbles-and-avatars chat idiom; the mono voice marks the players as the mechanical register against the DM's narrative one.
  • SessionInput — the composer, with a prominent @DM summon. The summon uses the explicit-text path: it composes the visible @dm token into the sent message, which persists and broadcasts as an ordinary player_message the backend's explicit-trigger path recognizes — so the whole table sees the summon. The invisible dm_invoke frame is deliberately not used.
  • SessionStartBeat — the 1-bit loading-beat family, with two labeled phases: the SSE-driven atmospheric prep wait and the short socket-connect boundary. Reduced-motion lands instantly.
  • ThinkingIndicator — "DM is thinking…" on the thinking bit, player typing on the typing set.
The @DM summon is explicit text, not an invisible control frame — the transport supports a payload-free dm_invoke summon, but the play screen composes a visible @dm token into a normal message instead. A summon is a social act at the table; routing it through the visible transcript means the other players see who called the DM and why, rather than the DM answering an invisible prod. composeSummon is a deterministic string helper (a protocol token, not user copy, so it is not an i18n key).

The full-bleed frame

The play route escapes the app frame's padded content box: it carries a fullBleed route handle that AppFrame reads to render header-plus-stage as exactly one viewport, so the transcript scrolls inside its column and the page never scrolls. The unbroken min-h-0 flex-scroll chain (the full-bleed AppFrame root → the play route root → the transcript column → MessageStream) is the one place the play routes use a raw layout element — the layout scaffold isn't expressible through mythrunUI Stack props (which ban className), so it takes the sanctioned, reasoned no-ad-hoc-ui escape hatch, while every piece of visible content composes the design system.

A route handle, not ad-hoc negative margins — and a declared shared file — the full-bleed breakout is owned by the play route as an explicit AppFrame variant because MYT-95's header credit chrome edits the same AppFrame. The two changes were declared up front so neither worktree rewrote the frame wholesale: the play route owns the content full-bleed variant, the billing work owns the header. A pile of negative margins on the screen would have collided; a route-handle variant keeps the frame's one composition root intact.

Session end lands on the recap route

When session_end arrives the shell shows a brief "session complete" transition and navigates to /campaigns/:id/recap. That is where MYT-92 stops.

The recap is a stub route, deliberately — not silently dropped — the session's summary exists in the database (post-session analysis writes sessions.summary), but there is no player-facing recap read yet. So MYT-92's done-when was softened to "session end lands on the recap route," with the real recap screen and a minimal recap read filed as a follow-up bead (which also resolves the campaignId-vs-sessionId param question). The UX-spec recap experience is explicitly deferred, not quietly abandoned.

Operating this piece

Walk a live session end-to-end (dev)

  1. Bring up the stack (pnpm db:up, pnpm dev for backend + worker, the web app), sign in, and take a campaign through character creation to the play entry. A real session needs live Anthropic credentials.
  2. Enter /campaigns/:id/play. If prep hasn't run you land on the atmospheric prep beat; when it completes, Start debits the owner's session credit and the transcript opens. Type a message — it posts instantly (optimistic), then settles when its seq echo returns — and watch the DM's prose stream in token by token.
  3. Open the same campaign as a second identity mid-session: it should rebuild the full backlog (the lastSeq = 0 seed), then stream live and show typing presence. Press @DM — the summon is visible to both tables and draws a response.
  4. Kill and restore the connection mid-turn: the turn resyncs without double-rendering. Then end the session (the end_session summon) — the DM renders a send-off, then the screen lands on the recap route.
  5. To inspect the wire, watch the WS frames and the session_messages / credit_ledger rows — the server side is on the session transport page.

Integration points

This screen is the client half of the session transport: it consumes that transport's frames through the shipped WS session client and prep-status SSE, and every start arm maps to a backend precondition documented there. The 402 arm hands off to the billing & credits purchase moment; the full-bleed frame is a declared shared edit with that work on the app shell's AppFrame. The play entry itself is reached from character creation once the party finalizes, and every visible element is a mythrunUI component over the DOM-free client brain. The session-end recap read and the wave-2 mechanical- frame rendering (dice cards, the knowledge sidebar) build on this reducer's first-class item shape.
