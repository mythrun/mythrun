Live play

The table itself: /campaigns/:id/play, where the party and the AI DM run a session. Start debits the owner's session credit — a return to an already-running game instead joins silently off a read-only probe, and the between-sessions gap is a calm preparing hold while the flow backoff-polls for readiness — then the screen becomes a streamed multiplayer transcript: the DM's prose arrives token by token, the humans' messages post the instant they're typed, a mid-session joiner sees the full backlog, a dropped connection resyncs without double-rendering the turn it dropped during, a skill check arrives as an in-stream dice card the player rolls before the outcome prose unfolds, and the DM's rare self-correction lands as a set-apart errata slip. A quiet line says roughly how much evening is left, and near the end — only near the end — the table is offered the choice to land it deliberately. Beside the transcript sits a knowledge sidebar — a browsable world wiki, a relationship graph, and the player's live character sheet — and recognized names in the DM's settled prose highlight into terse knowledge cards, every surface showing only what the character already knows. When the session closes, the screen lands on a recap of what happened. The route is a thin composition; all the reasoning — the start flow, the transcript reducer, the reveal gate, the display order, the progress band, the transport view-model, the one-snapshot knowledge cache — lives in the platform-neutral client brain.

The screen adds no frame type and no read surface — enforced ignorance holds here by construction, not by prompt discipline. The play screen only ever renders frames the session transport hands it; it introduces no new WebSocket frame, no new backend read. There is deliberately no Slow-Thinker stage-direction frame anywhere in the client, and nothing on this screen may add one — the reason the DM intervened is never on the wire the player consumes. MYT-93's dice moment holds the same line: the reveal drives entirely off the skill_check/dice_roll frames already on the wire, and the client→server roll_complete frame was deliberately excluded — pressing Roll sends nothing, because the number is already server-resolved. The session-progress signal is the same discipline applied to a harder case: it is the one progress number a player sees, and it carries nothing but mechanics.

How it fits together

PlayRoute (routes/play.tsx) is the router-mounted entry, and because the router mounts it directly — not through CampaignPage, which feeds the character surface a campaign prop — it resolves its own identity signals first. usePlayViewer loads two reads it already has slices for: getMe (the viewer's DB id — the reconcile key the server stamps on this player's message echoes — plus the display name) and the same GET /api/campaigns/mine payload the hub renders, found by id. From the campaign it derives ownership (creator === null ⟹ owner, the same signal character creation uses) and the party roster (userId → displayName). A campaign the viewer can't see resolves to a calm error — you can't play a session you're not a member of.

With the viewer resolved, PlaySession owns the rest. It calls start() once on mount and renders by the start flow's phase: the short connecting beat while the attempt is in flight, the between-sessions preparing hold, the live session shell, the purchase seam, or a calm retry notice. The route file itself stays a thin shell — the client-core hooks (the start flow, the prep SSE fold, the transport view-model) carry every judgment, and each is an injectable seam so a test drives any phase deterministically without a live transport.

The start flow — probe first, then one classifier

An initial or manual attempt POSTs nothing at first. It probes GET …/active — a read-only lookup, no debit — and if a session is already running it mounts the shell against that id directly: returning to a live game issues no POST /start and no 409 at all. Only when nothing is running (or the probe fails — it is a best-effort short-circuit, never a gate) does the flow fall through to POST /api/sessions/:campaignId/start, which debits the campaign owner's session credit regardless of who pressed Start and answers with one of several shapes that each mean a different next screen.

Probe GET /active before POST /start — a handled 409 still paints the console red — the flow originally POSTed first and treated 409 session_already_active as the join signal. The classifier handled it cleanly, but every return to a running game logged a red "Failed to load resource" line, and that line is the browser's own network log — no app-level handler can suppress it. The only real fix is not issuing the 409: the probe joins silently, and the 409 join arm survives only for the rare race where a session starts between the probe and the POST.

classifyStartError (in client-core/session/start-flow.ts) maps a caught error to a discriminated StartOutcome, keying only on the contract-blessed status/code/body — never on prose (the ZFC line: pure orchestration, no pattern-matching). The useSessionStart hook resolves each outcome to a render phase:

  • 200 → ready{sessionId}: mount the live shell.
  • 409 session_already_active → the join arm — now only the probe↔POST race, since the probe covers the common return-to-a-running-game path. The 409 body carries no sessionId, so the hook re-resolves it via GET …/active, then mounts the shell against it.
  • 409 prep_not_ready / reconcile_pending / session_ending → one waiting phase — the calm between-sessions hold (below). These codes are transient by contract (the next session's prep is running, the last one is reconciling or ending — all resolve on their own), so the hook backoff-polls /start from inside the phase rather than surfacing a retry.
  • 402 insufficient_credits → the purchase moment, carrying the owner-vs-member split.
  • 409 members_without_characters → the blocked hold, but naming names: the 409 body lists every confirmed member still without an integrated character, so the hold reads "waiting on Bryn, Sana" rather than an unexplained refusal. Not transient — someone has to finish creation — so no auto-poll; a malformed body degrades to the bare blocked hold, never a crash.
  • 409 campaign_not_active (and any off-contract 409) → a calm, manually retryable "blocked" notice — not transient, so no auto-poll; anything unrecognized is a generic retry.
The silent-lockout fix has two faces (myth-mnik3) — a member with no integrated character used to fall into ambient quiet: the owner's /start succeeded and left that member staring at a table that never spoke. The fix closes both sides. The owner who starts now gets a 409 members_without_characters that names who is missing a character (the blocked hold above), so the table knows who to nudge. The member without a character who opens the session has their socket closed 4404 no_character by the transport and lands on an explicit "make a character" notice (below), never a silent shell. The guard's server predicate is the exact character-row join the WS connect resolves against, so the two signals can't disagree.
One backoff-polled waiting phase, not an SSE-driven re-start — the retry storm is impossible by construction — the old prep beat re-attempted start() the instant its prep SSE reported ready, with zero backoff. In the between-sessions window (a session just ended, the next prep isn't ready, reconcile still running) a stale or flapping ready re-fired the attempt in a tight loop — ten POSTs in half a second — that hit the /start rate limit (10/min) and 429'd the player right after every session close. The fix removes the re-start trigger entirely rather than damping it: the three transient codes collapse into one waiting phase, and the hook itself polls /start on an exponential, jittered ramp (2s → 4s → 8s → ~12s cap, ≈5 polls/min at the cap — never near the limit), staying in waiting across polls so the screen doesn't thrash. The poll is the readiness probe; there is no second signal left to storm on.
The join arm and the waiting arm are only distinguishable because the backend reordered its preconditions (MYT-92) — the start flow drives the between-sessions hold on prep_not_ready and the join path on session_already_active, so the two must be told apart truthfully. Until the play E2E caught it, a member whose /start raced an already-running session got prep_not_ready — because maxSessionNumber counts the live session, so the "next" prep legitimately doesn't exist — and pinned forever on the prep wait. The fix moved the active-session guard ahead of the prep guard on the server; the client relies on that discrimination.
Seed lastSeq = 0 on the very first connect — the view-model connects with seedLastSeq: 0, which asks the transport for a full-history replay. A fresh connect would otherwise get a session_ready with no messages, and only a reconnect replays the backlog. Seeding zero makes the owner's first connect, a reload, and the probe-join / mid-session joiner all rebuild the whole transcript from one session_reconnect batch — one code path covers every entry into a running session.

The preparing hold (PreparingHold + the mythrunUI SessionPreparing beat) is the waiting phase made visible: "the DM is preparing the next session…" over the shared BeatFigure — an ambient square of hard 1-bit Bayer cells whose density swells and ebbs as a slow traveling breath, its only sign of life, frozen to a still frame under prefers-reduced-motion — with the same whisper ledger the world-gen wait uses, plus a coarse estimate of the remaining wait, and with aria-busy and a polite live region carrying the line for assistive tech. The hold still owns no retry timing: the hook polls behind it, and when a poll finally answers 200 the phase flips to ready on its own. The prep-status SSE (useSessionPrep) is kept for exactly one job — latching a terminal prep failure into the calm dead-end fast, a definitive "tonight didn't come together" instead of polling forever behind an atmospheric wait. The latch still holds against re-snapshots: a post-failure reconnect re-reports generating (the prep row's existence is the snapshot's only signal), which must not re-arm the wait. During reconcile_pending / session_ending the prep bit reads ready — prep isn't the blocker — so the latch never false-fires there.

The estimate is a historical baseline minus elapsed, because there is nothing finer to use — session prep is a single pipeline stage and the prep-status channel only surfaces a coarse generating → ready/failed lifecycle, so unlike world gen there are no per-stage completions to re-estimate against. The honest fallback is a baseline: average the historical session-prep timings (the stage string embeds the session number, so the aggregate is fragmented across per-session-number rows and averaging them gives one typical duration — coarse by design, which is all a minute-granular display needs) and subtract the elapsed wall clock. The origin is the moment the player entered the hold, so the estimate errs long: prep may have started slightly earlier server-side, and finishing early is the safe direction to be wrong in. It then feeds the same shared wait brain as every other long wait, so an overrun degrades to the stalled line rather than sitting on a dead zero, and with no history at all there is simply no number — after a flat window the stalled line still answers "has this broken?"

The transcript reducer — the reconnect-safe core

Once a session is ready, SessionShell drives useSession, the view-model over the shipped WS session client (a dumb typed pipe with production-grade reconnection). Every inbound frame folds through reduceFrameReconciling — the pure transcript-reducer.ts wrapped in the optimistic own-echo layer. The reducer models the transcript as an ordered list of TranscriptItems and owns transcript content only: the streamed DM prose (text_delta accumulates into one dm item per turnId, settling on turn_end), the confirmed player messages (deduped on seq), and every mechanical frame.

Every mechanical frame is a first-class item, so the rendering can grow without touching the reducer — skill_check, dice_roll, ledger_update, mode_change, and the two combat_* frames each become a typed transcript item carrying the whole frame, not a flattened string. MYT-92 rendered every one as a terse mono system line and froze the reducer's shape as the wave-2 shared contract; MYT-93 then did exactly what that freeze was for — it extended the rendering of skill_check and dice_roll into the RollCard dice moment (MessageStream's item dispatch) without adding a field to the reducer. MYT-94 did the same again from the other side: it reads the ledger_update item — still rendered as a mono line in the transcript — and folds it into the live character-sheet overlay in the knowledge sidebar, again without touching the reducer. mode_change and the combat_* frames still render as mono lines until their own surfaces land.
Whole-turn replace, so a reconnect can't double-render the turn it dropped during — a client that drops mid-turn has a partial dm item built from live text_deltas. On reconnect the transport replays that same turn as seq-bearing rows. If the reducer merely appended them, the turn would render twice. So applyReconnect — an explicit folder seam, not a hidden branch — first prunes every existing DM/mechanical item whose turnId the replay batch carries, then re-folds the batch so each turn rebuilds settled. Player items (turnId null) survive the prune and dedup on seq instead. The seam is a separate exported function precisely so the optimistic layer can re-fold the same batch through a reconciling folder (below) rather than the raw one.

The errata slip — when the DM amends the record

The wire already carried the DM's rare self-correction: a dm_correction frame the Fast Thinker emits when something previously narrated needs amending — broadcast live within the turn, and replayed on reconnect from its persisted row. The client now renders it. The reducer folds the frame into its own dm_correction item — a content kind deliberately distinct from dm, so a correction can never read as the fiction it corrects — carrying its own emission turnId (the turn the DM issued it in, not the corrected turn's), so it rides whole-turn-replace exactly like every other row. MessageStream dispatches the item to DmCorrection, the errata slip: square and unfilled on the ambient transcript ground (never the narration's warm paper lift), ruled with a heavy ink left margin, the mono face set against the DM's serif, under a terse uppercase eyebrow. The eyebrow is resolved [ph:] chrome the route threads in; the correction text is DM data, never an i18n key. The slip's register at the design-system altitude — why it reads as a record amendment, not an alarm — is on the design-system page.

The live frame and the replay row must render identically — the reducer is the single source — a correction reaches a client two ways: live, as a seq-less frame inside the turn, and on reconnect, as a seq-bearing row in the replay batch. Both fold through the same reducer arm into the same item shape, so the player who watched the amendment land and the player who reconnected past it read the identical slip. There is no separate replay renderer to drift — and there must not be: if the two ever looked different, the record itself would appear revised depending on when you looked, which is exactly what an errata register exists to prevent.

Optimistic own-messages

A player's own message appears the instant it's typed — addPending appends a player item with pending: true and no seq, keyed by a stable local id so React reuses the same node when the server echo confirms it in place. reduceFrameReconciling wraps the raw reducer: an inbound own player_message reconciles the first matching pending item — settling it and adopting the server's authoritative seq — instead of appending a duplicate. Because that confirmation happens outside the raw append path, it records the seq in the dedup ledger itself, or a redelivery would slip past. On a reconnecting → connected transition the hook arms a resend that fires after the replay batch settles: the replay confirms the messages that landed, and every still-pending one is re-sent.

The resend can duplicate, and that residual is accepted on purpose — the wire protocol carries no client message id, so reconciliation matches on (viewerUserId, text) in FIFO order. If a pending message actually landed but fell outside the transport's filtered replay window, the reconnect resend duplicates it. Adding a client message id is out of MYT-92 scope, so the residual is annotated in the code rather than hidden — the two dominant paths (a first-join backlog and a single in-flight-turn reconnect) are exact, and a rare duplicate on a lossy reconnect is the accepted cost of an input that never feels laggy.

Presence, and the parts the reducer won't touch

The reducer deliberately ignores the out-of-band control and presence frames; useSession folds those into a separate SessionPresence state through foldOutOfBand. The thinking indicator opens on dm_thinking and clears on the first text_delta/turn_end/turn_error for that turn; the typing set tracks typing_start/typing_stop; the ended flag flips on session_end. A session_reconnect resets the thinking indicator, so a stuck "DM is thinking…" can't survive a drop — a turn genuinely still running re-arms it with a fresh live frame. The route maps the transport's own connection status (reconnecting/failed) to a quiet system line pinned under the transcript, and resolves the presence typing userIds to display names through the party roster (unknown ids are omitted, never shown raw). One terminal failure is the exception: failed{no_character} — the transport closed 4404 because the viewer has no integrated character — makes SessionShell render a full NoCharacterNotice (an explicit "you don't have a character here yet" hold with a CTA into creation) instead of the live stage, because reconnecting can't help. failed{denied} and failed{exhausted} still fall through to the shell's quiet connection line — those are recoverable or already covered by the disabled composer.

The transcript as a record — display order and table talk

The transcript is not only a live feed; it is the durable artifact the table rereads and the product's memory is built on. Two pure derivations, computed route-side and handed to the stream as plain data, keep it honest as a record. Both live in transcript-presentation.ts and neither touches the reducer.

Causal order. The Fast Thinker may stream prose before it issues its roll tool call, so a check card can arrive after the prose it caused — read back later, the roll happens after its consequences. Once a card is released (its theater done, its gate lifted) it files into its causal slot: immediately before its own turn's first prose. Un-released cards keep arrival order, so the live gesture — the card as the tail centerpiece while the prose behind it is gated invisible — is untouched.

Only the display moves; the gate keeps reading arrival order — the reveal gate, the composer gate, and the reducer all continue to read the raw item list. Reordering the underlying transcript would mean the reducer's reconnect-safe identity and the gate's derivations both had to reason about a list that rearranges itself as cards are continued. The reorder is a projection for the stream and nothing else, and it returns the input array unchanged when nothing moves, so it costs no render churn in the common case.

Table talk. An @DM exchange is out-of-character, and the durable transcript has to keep that boundary. The question and its answering turn group into one block the stream wraps in a marked frame — a terse uppercase eyebrow over a ruled slip, the sibling of the errata slip's register. The rows inside keep their own faces (the question in the players' mono, the answer in the DM's serif, which stays readable at answer length); the boundary lives on the frame, not the faces. The grouping is keyed off the explicit @dm token — a UI command, the sanctioned ZFC exception — so nothing semantic is inspected.

The frame marks the way in, not just the way out — before it, an out-of-character answer rendered in the narration serif with no marking at all, so the record discarded a boundary the system knew with certainty at authorship. Marking only the answer's sign-off would be a door on the way out; the eyebrow is the door on the way in. The grouping is deterministic and replay-stable — the question opens a pending exchange, the next DM segment claims it and pins the answering turn, further segments of that turn join, and any other item closes it — so a mid-answer roll never gets swallowed into the block and the same items always group the same way on reread.

The dice moment — a reveal gate over an already-resolved roll

When the DM calls for a check, the backend rolls the die deterministically and sends the whole result in one skill_check frame — the natural roll, the modifier, the total, the DC, and the matched outcome tier. The player never rolls anything real. So MYT-93's dice moment is pure presentation: it delays the display of a number the client already holds and gates the outcome prose behind an explicit Continue, so a check feels like a roll instead of arriving pre-decided. useSession is untouched — the reveal is a render gate layered over the transcript the reducer already produces, not a hold-back inside it.

The roll is server-resolved; the card sends nothing back — the number is generated in deterministic backend code (the LLM never rolls), so the whole result is on the wire before the card mounts. Pressing Roll therefore fires no request: there is no client→server roll_complete frame, deliberately excluded from the contract. This keeps the screen's no-new-frame boundary intact and means a reload or a mid-session joiner can reconstruct every roll from the persisted frames alone — the theater is a local flourish, never a source of truth.

The reveal state lives in a tiny separate reducer, roll-reveal.ts, exposed as useRollReveal. It tracks only the two committed interactions — which card keys have been rolled and which continued — as two sets. A card's phase is derived, never stored per frame: cardPhase reads idle (show a Roll button) → revealed (numbers land, show Continue) → released (the outcome prose opens). A card whose frame carries a persisted seq — a backlog row or a reconnect replay — is history, and derives straight to released: no theater on anything the player has already lived through, the same history-has-no-theater rule the reconnect-safe reducer follows.

The gate itself is one pure selector. buildRevealView(items, state) walks the transcript and returns a plain view — phaseByKey (each card's derived phase) and gatedTurnIds (the set of turns whose outcome prose is still held). MessageStream renders a dm item as nothing while its turnId is in gatedTurnIds, so the DM's post-check narration stays hidden until the check that provoked it is continued. A turn with two checks stays gated until both are continued; a lead-in line the DM wrote before the check folds into the same gated turn item and is held with it. A dice_roll is the flavor variant — it reveals a number but never gates prose.

The constraint field is never rendered — a skill_check frame carries the outcome constraint the DM's prose is written from (the pre-generated fail/success/great-success seed). Painting it on the card would pre-empt the very narration the gate exists to hold back — the player would read the outcome before the DM voiced it. So the card renders the mechanical readout (die, modifier, total, DC, tier) and nothing else; the constraint is threaded nowhere on the client. An E2E check asserts the constraint text is absent from the DOM at every phase.

All of this is computed route-side. SessionShell runs useRollReveal, derives the view with buildRevealView, and resolves the [ph:] label bundle, then hands MessageStream plain data and neutral callbacks. The mythrunUI layer holds no reveal runtime — RollCard's phase arrives as a prop, its only local state the DieSpin transition (portability rule R1: the DOM layer imports no client-core logic). A pending, un-continued card does not lock the composer — the player may keep typing while a card waits, the calm default the spec leaves open.

The card and the die

RollCard is the in-stream dice moment made visible: a square, flat-1-bit paper card that reads as a mechanical interjection in the DM's serif transcript. It composes the skill and character and any advantage/disadvantage posture, a DieSpin in the centre, a Roll button while idle, then the readout and a Continue button once revealed. Every mechanical value is --font-ui mono, and — matching the brand's no-status-chips register — the outcome tier is carried by typographic weight, never a coloured badge. There are no circles anywhere on it.

The card is also where a player who has never played D&D learns how a check works, so it reads as one causal sentence. Before the roll it shows the skill and the player's own modifier — their competence, theirs to weigh ("I need a 7 or better") — under a single quiet framing line that turns the stat fragment into a sentence. Only the DC stays hidden. After, the readout runs die → arithmetic → comparison → verdict: the whole equation with the die's own numeral as its left operand, then the explicit pass/fail against the now-revealed DC, then the outcome word promoted to the card's typographic peak. A natural 20 — the die's face, not the modified total — takes the system's own "loud": the inverted plate, ink field with paper letters, at display size. Theme-aware, no colour, one move.

The equation repeats the die's number rather than pointing at it — a readout reading "+6 = 16" asks the reader to reach back up into the die to reconstruct where 16 came from. Writing it whole ("10 + 6 = 16") costs three characters and makes the card self-contained. The modifier moves above the die for the same reason it is revealed early: it is the player's own number and knowing it is what makes the roll suspenseful rather than arbitrary. The outcome word is promoted because it is the card's whole point and it had been rendering at footnote size — weight still carries the tier, it just carries it at a size worth reading.

Once a card is released — Continue pressed, or replayed history — the theater is over, and the full card sitting below fresh narration would file the roll after its consequences. So it collapses to a compact one-line receipt: skill, the whole equation, the verdict against the DC, on a quiet hairline rather than the card's stronger edge. The receipt recedes; the prose around it is the point. The causal order above is what files it back between the player's message and the outcome prose.

DieSpin is a faceted d20, authored here as a new mark because no pixelarticons die exists: the pointy-top hexagonal silhouette with the icosahedron's full interior fan drawn — a central triangular face plus the edges tying it to every silhouette vertex, the classic front-face-with-a-number construction. The central face is drawn a touch larger than the true projection so the numeral stamps cleanly inside it at any value, single- or two-digit. The geometry stays open (no knockout plate) because the die renders both on the page ground standalone and on a card surface inside RollCard, and a filled plate would mismatch one of them. The same construction language extends to the other dice: a flavour roll threads its own sides and gets its own silhouette — triangle, square, rhombus, kite, pentagon — each unmistakable by outline, with the numeral always stamping at the same centre. It spins in a stepped rotation — eight discrete 45° steps, the motion analog of the brand's stepped Bayer dither, never a smooth CSS interpolation — and stamps the used die's numeral upright in its centre when it lands. The easing lives in time, not the angle: the per-step dwell ramps (~50 → 220 ms) so the die visibly decelerates into the landing, and the final step to upright carries a single scale-pop recoil frame before it snaps to rest and holds still — the stillness is what sells the landing. Under prefers-reduced-motion it does not spin: it lands instantly and reveals. Because motion is never the only signal, the die glyph is aria-hidden decoration and the landed result is announced through a polite live region, so a screen reader hears the number the sighted player watches settle.

A stepped die, decelerating in the dwell — the UX spec called for a smooth spin, but the brand register is 1-bit and pixel-honest, so the die jumps in discrete 45° steps the same way the Dither bands rather than blending — the brand-overrides-UX rule applied to motion. The refinement a design-lead pass landed is where the easing lives: the angle never interpolates, so deceleration is carried entirely by a ramping dwell schedule (each step held longer than the last) capped by one discrete recoil frame — the same "quantization is the easing" grammar the shared BeatFigure engine uses. The dwell ramp is the tuned result of that pass, not a placeholder.
The facet-band hexagon read as a hex nut — an earlier cut drew only the two pole facets and left the equator open, which solved the numeral-clearance problem and lost the die: at a glance it was a hexagonal fastener, not an icosahedron. Drawing the full interior fan makes it unmistakably a d20 both at rest and at its result, and enlarging the central face past its true projection recovers the clearance the open band existed for. The landed numeral also carries reveal weight — bold, a step larger than the equation below it — because the roll is the one moment of chance in the loop: the number lands before the arithmetic explains it.

Where the session is, and what that permits

The wire carries one number saying how far through its mechanical ceiling the session is: a fraction the server computes from the Fast Thinker's context fill against its usable window — one ceiling, because the session ends when that window can no longer take another turn. It is monotonic and coarse by the server's own guarantee, and it rides three frames — turn_end (the once-per-turn beat, after persist and flush), session_reconnect, and session_ready. The client reads all three identically, holds the raw value, and derives exactly two things from it.

The fraction is purely mechanical, and that is the enforced-ignorance argument — this is the one progress number the player sees, so under enforced ignorance it may never encode plot state, NPC secrets, or any narrative judgment about how close the story is to an ending. How full a context window is carries none of that; there is nothing narrative in it to leak. The narrative side of a session converging lives with the Slow Thinker, on the secret side of the boundary, and never rides this field.
In practice it arrives on session_reconnect, not session_ready — the shipped client connects with seedLastSeq: 0, so the server always takes the reconnect branch and session_ready never reaches a real browser. Carrying the fraction on only the two frames one would naively pin would have left every real join blank until the first turn completed. The field is optional and additive everywhere, and absence means "no statement," not "reset to zero" — the corrected-turn whole-turn replace reuses the reconnect frame and deliberately carries no progress, so an audit-corrected retry must not blank the readout. The client validates the payload structurally on the way in, exactly as it does any parsed network JSON, and takes no second opinion about the value: monotonicity and coarseness are the server's, and a second opinion is how two surfaces start disagreeing.

A word, never a number

The fraction collapses into four coarse bands — early, middle, late, close — and only the band's word reaches the screen, as one quiet line of chrome above the transcript. There is no numeric variant and no meter. Emphasis is typographic: the line's ink lifts as the session closes, quiet while there is room and full ink when the landing is near, which is the register's only emphasis channel and means the last stretch reads without ever becoming an alarm. It is a polite live region, not decoration — a band change is rare (three per session at most) and is exactly the thing a player needs told.

A percentage would be a spend meter parked over the fiction — the signal is cost-derived, so "62%" reads as "62% of your money used," which is both the wrong thing to hold in mind mid-scene and squarely outside a paper-y, un-gamified register that already bans bars, chips, badges, and dots. What the player actually needs is narrative room — how much evening is left to plan a landing in — which is forward-looking where a spent percentage is backward-looking. Four bands are enough to pace a story and too few to watch tick. The number never reaches the component at all: the surface bands it and passes a word, so there is no numeric prop to regress into.

The voluntary end, gated

The same signal decides whether the table may end the session on purpose. A Mythrun session is a play unit, not a sitting: leaving is free, rejoining is the normal case, and the credit is debited at session start. So the end control does not mount at all until the session is genuinely near its end — and with no signal at all (a pre-first-turn join, an older frame) it stays absent, the safe default for something that cannot be undone.

Early, ending is pure value destruction; late, it is craft — because the credit is already spent and the session can be resumed indefinitely, ending early refunds nothing and throws away what the player paid for. An always-available end control is therefore a footgun. Near the end the calculus inverts: "end here, on this beat" lets the player pick the landing instead of letting the budget cliff pick a random mid-scene moment. That is one threshold, and the late band starts at the same place, single-sourced, so the line that says the end is near and the control that offers to take it can never disagree.

Pressing it opens a one-beat inline confirm — no modal — with two bordered controls and the consequence stated under the question, before the decision rather than under the buttons. The disclosure leads with what ending forecloses: the session cannot be resumed. The cost is stated second, as record.

The disclosure had to stop reading as a receipt — an earlier version disclosed only the cost, in the past tense ("this session used one credit"), which is the most reassuring possible framing for the most destructive action on the screen. And because a session is a play unit, a player can quite reasonably read "end" as banking the remainder for later. It is not. Leading with irreversibility is what makes the confirm informative rather than ceremonial. It sits under the question because, placed under the buttons, it parsed as a consequence of confirming ("ending will cost a credit") rather than the statement of record it is.

A second, gentler exit hangs off the long rest the rules engine already detects: a dismissible wind-down offer — a night's rest is the most natural session boundary the genre has. It keys off the structured rest discriminator on the ledger frame, never the human-readable summary prose, and only on a live frame: a long rest replayed from an hour ago must not re-pop the offer. It carries the same near-the-end gate as the control, because it ends the session too — a long rest at 15% would otherwise be an invitation to destroy a paid session at the one moment it feels most natural to accept.

Confirming either one sets a local ending latch immediately, before the farewell turn's first frame arrives, so the end can't be double-fired and the screen stops asking for input at once. The whole between-turns chrome row is then swept: a stale question with one dead button must not keep asking. The composer goes inert rather than merely send-gated, and the one end-transition signal — the DM is closing the session — lives at the live edge in place of the generic turn indicator. One signal, one place.

The stage — two registers

SessionShell composes the mythrunUI play components into a viewport-bounded flex column: the between-turns chrome row on top, the scroller filling the middle, the thinking line and the input pinned below, beside the knowledge sidebar. The register split is the meaning — the DM speaks in narrative, the humans at the table speak in the mechanical voice:

  • MessageStream — the transcript scroller. Auto-follows the tail, and positions instantly under prefers-reduced-motion (no smooth-scroll vestibular trigger). It dispatches each transcript item to its renderer — dm to DmMessage, player to PlayerMessage, skill_check/dice_roll to the RollCard, dm_correction to the DmCorrection errata slip, the rest to a mono system line — folds a table-talk block into its marked frame, holds a gated turn's DM prose off-screen, and carries the connection system line. Scroll up and a labelled pill appears at the bottom centre; once content lands below the fold it swaps to the new-messages label and announces through a polite live region.
  • DmMessage — the DM's prose in Source Serif 4 (--font-body), on a paper tint, appended token-wise as text_deltas arrive and settling on turn_end. Once a turn settles, recognized entity names in the prose highlight into knowledge cards; the streaming path is byte-unchanged.
  • PlayerMessage — a human utterance in IBM Plex Mono (--font-ui), a distinct tint, on its own paper band. There is no bubbles-and-avatars chat idiom; the mono voice marks the players as the mechanical register against the DM's narrative one.
  • SessionInput — the composer. The field wears the serif prose face and the branded caret, the one face a player's own writing wears, so the authorship moment shares the world's voice instead of reading as an unfinished form control. Its two actions are grouped together at the right of one row rather than pinned to opposite ends, and the in-world / out-of-character split rides the variant hierarchy: Send is the accent primary — the character's in-world action — and the @DM summon is the bordered secondary beside it, prominent but quiet. The summon uses the explicit-text path: it composes the visible @dm token into the sent message, which persists and broadcasts as an ordinary player_message the backend's explicit-trigger path recognizes — so the whole table sees the summon. The invisible dm_invoke frame is deliberately not used. Hovering or focusing the summon shifts the empty field's placeholder to the out-of-character line, disclosing that the same box is action via Send and question via the summon. The composer also hard-caps its length at a client mirror of the server's MAX_MESSAGE_TEXT_LEN (a native maxLength that blocks typing and paste past the cap, plus a send guard for a programmatically over-cap value), so an over-long message can't optimistically render and then be silently dropped by the server — or exceed the WS payload cap and trigger a reconnect storm. The transport enforces the same 4 KB bound server-side; the client cap keeps the failure from ever reaching the wire.
  • SessionStartBeat — the 1-bit loading beat for the short socket-connect boundary, rebuilt on the shared BeatFigure in fill mode: a full-width Bayer band whose threshold-sweep front rises to the current phase level. (Its atmospheric prep phase is retired from this route — the between-sessions wait is the SessionPreparing hold above, its cadence owned by the start-flow hook, not an SSE.) Reduced-motion lands the front instantly.
  • ThinkingIndicator — "DM is thinking…" on the thinking bit, player typing on the typing set.
The @DM summon is explicit text, not an invisible control frame — the transport supports a payload-free dm_invoke summon, but the play screen composes a visible @dm token into a normal message instead. A summon is a social act at the table; routing it through the visible transcript means the other players see who called the DM and why, rather than the DM answering an invisible prod. composeSummon is a deterministic string helper (a protocol token, not user copy, so it is not an i18n key) — and since the table-talk grouping keys on the same token, the definition lives in client-core with the route wire re-exporting it, so the composer and the grouping can never disagree about what a summon is.

The composer says who the game is waiting on

Sending is not always the expected next action, and the composer now says so. One derivation, composerGate, produces the state — and the status line, the Send disable, and the roll card all read that same derivation, so they cannot disagree at any point of the turn state machine. It names the blocking party: an end in flight gates everything; then the player-blocking states (a check awaiting Roll, a revealed check awaiting Continue) outrank the DM-blocking one (a turn visibly in flight). Each carries a quiet caption naming why, in a polite live region so the reason is announced rather than swallowed.

A check pending must outrank "the DM is writing" — with a check on screen the post-check prose is already streaming, invisibly, behind the reveal gate. Reading the raw streaming flag would put "the DM is writing…" on the screen while the game is in fact waiting on the player to press Roll — telling the one person who can unblock it to sit still. So the DM-writing test excludes gated turns, and the player-blocking states win the precedence.
Busy is not disabled, and the visual has to agree with the functional — the worst bug the first play run produced was a Send button that looked live during a stream and silently no-op'd, so a player typed, pressed, and lost their turn to nothing. The fix is two states, not one. busy is transient: the field stays typeable so drafting ahead is preserved, but both send paths gate (including the Enter key, so a keyboard send can't slip past the gated button) and a caption says who is being waited on. disabled is terminal — the session ended, or the player has confirmed an end — and hard-gates the field itself. Crucially the appearance follows: while gated, the field drops to the muted treatment and its visible placeholder blanks (the caption carries the reason; the accessible name is unaffected), and Send stands down from the solid accent to a quiet ghost. The accent fill stays the exclusive mark of a pressable Send, so the gate lifting is a decisive flip rather than a state the player has to test by clicking.

The full-bleed frame

The play route escapes the app frame's padded content box: it carries a fullBleed route handle that AppFrame reads, so the transcript scrolls inside its column and the page never scrolls. The stage row also takes a hard height ceiling — the dynamic viewport minus the header's allowance — which is what makes the row two independent scroll regions. The unbroken min-h-0 flex-scroll chain (the stage root → the transcript column → MessageStream) is the one place the play routes use a raw layout element: the scaffold isn't expressible through mythrunUI Stack props (which ban className), so it takes the sanctioned, reasoned no-ad-hoc-ui escape hatch, while every piece of visible content composes the design system.

A viewport floor without a ceiling lets the whole page scroll — the app frame's root is a minimum height, so with only that in place the stage grew past the viewport and the page itself scrolled: the sidebar rode away, the composer sank off the bottom, and the live edge sat beside a dead right gutter. Adding the ceiling pins the composer, keeps the transcript scrolling inside its own column, and holds the sidebar at every scroll position — the same allowance the sidebar rail already used, so the two halves agree. The chrome above and below the stream shares the stream's own horizontal inset, so the position line, the transcript cards, the status line, and the composer all sit on one left grid line instead of three near-misses.
A route handle, not ad-hoc negative margins — and a declared shared file — the full-bleed breakout is owned by the play route as an explicit AppFrame variant because MYT-95's header credit chrome edits the same AppFrame. The two changes were declared up front so neither worktree rewrote the frame wholesale: the play route owns the content full-bleed variant, the billing work owns the header. A pile of negative margins on the screen would have collided; a route-handle variant keeps the frame's one composition root intact.

Session end lands on the recap

When session_end arrives the shell shows a brief transition and navigates to /campaigns/:id/recap, which is now a real screen over a real read. The recap is shaped as a document, not a scoreboard: an identity header (the campaign, the session number, a muted date and party record), the summary set as the writer's own paragraphs, the open threads as a numbered index with hanging indent and mono markers so they are referable at the table, and a quiet copy-link exit beside the way back to the campaign. The credit receipt is a footnote below the button, so the document never ends on billing. There is no transcript dump and no fanfare — closure, not a score.

The analysis behind it is asynchronous — an Opus job writes it seconds to minutes after finalize — so the read answers pending with facts only until the prose lands, and the route polls. The pending beat makes the wait a contract ("you don't have to stay") and seats itself in the upper third, with the empty page below the rule reading as the recap's future home; the poll streams the finished document into it.

Enforced ignorance holds at the wire, not at the renderer — a session's row also carries the secret-aware handoff and the Slow Thinker's running summary. The recap schema does not model them and the endpoint does not read the column they live in, so there is no filtering step for a future change to get wrong and nothing for a renderer to remember to hide. What crosses is the secret-free summary and open threads the post-session analysis writes from player-witnessed material. The route itself moved into the authed branch for the matching reason: the read is membership-gated, so it belongs inside the frame. A public share link would be a separate tokenized surface, not this campaign-id read.

The knowledge layer — what the character knows, beside the table

MYT-94 fills the sidebar seam MYT-92 left collapsed. Beside the transcript sits a three-tab knowledge sidebar — a browsable World Wiki, an interactive Relationship Graph, and the player's live Character Sheet — and the DM's settled prose gains entity highlighting: a recognized name in the narration becomes a quiet underline that opens a terse knowledge card. Every surface renders only what the character knows. This is the first player-facing read of the world store during play, and it holds the enforced-ignorance line the same way the transcript does — by construction, not by prompt discipline.

The knowledge layer adds no backend read surface — the whole sidebar and the highlighter are built from ONE snapshot: the member-readable, known-tier world-snapshot the world-gen reveal already fetches. The server filters it to the known tier before it crosses the wire; the client adds no tier logic of its own, invents no new endpoint, and — the load-bearing pin — no session frame ever promotes what the cache holds. A player can only ever see, in the wiki, the graph, or a popover, exactly what the server already decided they know.

One snapshot, three projections

useKnowledgeCache (client-core/session/knowledge-cache.ts) is the spine. It fetches the world snapshot once and derives all three views from that single read: the wiki view model (toWikiViewModel), the relationship-graph seed (the canonical snapshotToGraph), and the entity index the highlighter matches against (buildEntityIndex). The cache refetches quietly — the current projections stay on screen until a fresh snapshot resolves, and a refetch failure keeps the prior cache with no error flash — and it refetches on exactly one trigger: a session boundary (the mount, or a WS reconnecting → connected transition), threaded in as a bumped refreshToken.

The no-frame-promotes-the-cache invariant is executable, not a comment — enforced ignorance (spec §6) means no live session frame may carry pre-flip or tier-promotion content into the cache. The module encodes that as code a test pins: CACHE_PROMOTION_FRAME_TYPES is the empty set and frameRefetchesCache returns false for every frame type. Opening a frame-driven promotion path would mean adding a type to that set — a single, reviewed, test-visible change, never a silent drift. Until then the only way knowledge grows on screen is a boundary refetch of a snapshot the server re-filtered.

The three tabs

KnowledgeSidebar is pure wiring over three shipped primitives, one per tab:

  • World Wiki — the shipped WorldWiki over cache.wiki, with client-side search. Its browse groups lead with the people and places this session has actually named, so the scene's antagonist and a session-one shopkeeper are not rendered as alphabetical equals. There are no stat blocks: the WorldSnapshotSchema strips stat blocks server-side, so the model carries only names, known facts, related entities, the entity prose kernels, and the world introduction — the wiki structurally cannot surface a mechanical secret.
  • Relationship Graph — the same WorldGenGraph the world-gen reveal uses, mounted drained (its shown count equals its total, so the fog field empties and never animates) and interactive for node selection. It renders known-tier edges only.
  • Character Sheet — the in-session SessionSheet (below): the player's own curated sheet with a live HP/condition overlay.

The graph↔wiki bridge is a first-class seam: one selectedEntityId feeds both the wiki and the graph, so a pick on either side highlights the other, and tapping a graph node also switches the active tab to the wiki so the tap lands on that entity's page. A chat-highlight click drives the same seam from the transcript.

"Named this session" is the matcher's output, not a judgment — the transcript already knows which entities the session has mentioned, because the same mechanical name matcher that underlines them in the prose has been running over every settled DM row. The sidebar just asks it: accumulateNamedEntities folds each not-yet-scanned settled row through the matcher and keeps the ids it hit, in first-named order, and each browse group splits into those and the rest. Nothing is classified, ranked, or scored, and membership is cumulative and never decays — an entity named in turn one still counts at turn forty. Decay would need a notion of "the current scene," and nothing on the wire marks a scene boundary; inventing one is exactly the local intelligence ZFC forbids. Only settled prose is scanned, so a growing turn neither churns the scan nor matches a half-typed name.
The graph renders exactly the snapshot's edges and synthesizes none — the structural secret-edge pin — a relationship between two known entities can still itself be secret (a hidden pact between two people the player has both met). The server already drops those: the snapshot's relationships are filtered to access_level = 'known' with both endpoints in the known set. The canonical snapshotToGraph adapter — shared with the world-gen reveal's rehydration, so there is one known-tier projection rather than a divergent second one — maps each snapshot edge to a graph edge and invents nothing, so a secret edge the server withheld can never reappear on the client. The live E2E seeds a secret known↔known edge and asserts it is absent from the rendered graph.

Entity highlighting in settled prose

When a DM turn settles, DmMessage swaps its plain paragraph for HighlightedProse, which runs the cache's entity index over the text and wraps each recognized name in an EntityMention (a quiet resting underline; hover or focus reveals a small leading type glyph) inside an EntityPopover (a terse card — the name, its type, a one-line lead, and an "open in wiki" action that drives the graph↔wiki bridge). Since MYT-102 the lead prefers the entity's prose-kernel first sentence (the line that says what the thing is), falling back to its lowest-id known fact only when there is no kernel — a mechanical first-sentence split, no summarization. The streaming path is byte-unchanged: highlighting only ever applies to settled text, so nothing reflows mid-stream, and segmentation is memoized once per settled row rather than recomputed on every render.

Matching is mechanical and names-only — ZFC, not classification — the matcher (client-core/session/entity-index.ts) is a longest-first, Unicode-boundary-anchored substring match over the known entities' names. It runs no model, classifies nothing, and never pattern-matches on the prose — the narration is displayed verbatim; only the names are matched, against a data-derived index. Only world-lore kinds highlight (npc / location / faction); the player's own name and inventory items fall through unmarked. The type glyph is monochrome — it conveys kind by shape alone, never a colour (spec §6) — so the register stays paper-and-ink, not a tag cloud.

The in-session sheet and its live overlay

The Character Sheet tab is the player's own sheet, curated for play. useSessionSheet resolves the viewer's character off the party roster, fetches the existing member-readable character read, and adapts it to the same curated shape the creation reveal renders — reusing the raw→curated adapter promoted into client-core for exactly this second consumer. Over that static base it lays a live overlay folded from the session's ledger_update frames: the HP readout shows the current hit points the instant an adjust_hp or rest frame lands, and a quiet line logs recent condition changes.

The overlay SETS authoritative values, it doesn't apply deltas — a ledger_update frame carries post-mutation values, not a change amount (an adjust_hp frame sends the new HP; a rest frame also sends the restored HP). So reduceLedger folds by field presence — any frame carrying hp/maxHp/gold sets it — which makes re-applying a frame idempotent, so a reconnect replay of the same frame is harmless. The live E2E confirmed the full ledger_update → reduceLedger → data-live path against a real damage frame.

Conditions used to be the exception to that rule, and are no longer. The frame now carries the character's full post-mutation condition set — each condition with its level, for the one condition that tracks one — as authoritative data alongside the HP and gold post-values, so the overlay sets it by the same presence fold. The overlay keeps both: the chronological condition log the sheet renders as recent changes, and the maintained active set. Rendering that set is a still-open design call — the paper register bans chips, badges, and dots, so state is prose — so the sheet reads the log today and the data is folded and ready.

The full set, not a direction flag — and absent is not empty — the obvious wire fix was a per-frame apply/clear flag, and it cannot work: a long rest mutates two conditions in one operation (clearing unconscious via the HP-to-max write while decrementing exhaustion) yet emits a single rest frame, and every HP write silently syncs the HP-derived unconscious row while emitting only an HP frame. One condition-plus-direction pair per frame can express neither. A full list can, which is why it rides the HP and rest frames too and not just the condition frame. Three states matter and confusing two of them silently wipes a player's conditions on every gold spend: a frame whose tool cannot touch conditions omits the field, which means "no statement" and holds the last known set; an empty array is a statement — this character has none — and clears it; and a null overlay means no frame has spoken yet, so the base sheet stands. Carrying the exhaustion level as structured data rather than leaving it in the prose summary is the same argument: re-parsing prose to recover mechanics is precisely the local intelligence the architecture bans.

The rail, the drawer, and one structural mount

usePlayKnowledge is the route brain: it owns the cache, the sheet view-model, and the shared sidebar state (active tab, selection, wiki query, open) that both the chat highlighter and the sidebar read. KnowledgePanel presents it two ways from a single mount — a collapsible ~30% desktop rail (default open) above the lg step, the shipped mount-persistent Drawer below it — chosen by the useViewportBelowLg breakpoint hook.

A JS breakpoint flip, not a pair of CSS Shows — the usual responsive idiom is two sibling Shows, one hidden with display:none. That fails here twice over: the narrow branch is the Drawer, whose content is portaled to <body> — a display:none wrapper can't hide portaled content — and rendering both branches would mount two WorldGenGraph canvases. So the rail↔drawer choice is one structural mount driven by useViewportBelowLg, a design-system hook that flips at the same lg (1024px) boundary the CSS uses, so the JS regime and any lg: styling can never disagree.

Operating this piece

Walk a live session end-to-end (dev)

  1. Bring up the stack (pnpm db:up, pnpm dev for backend + worker, the web app), sign in, and take a campaign through character creation to the play entry. A real session needs live Anthropic credentials.
  2. Enter /campaigns/:id/play. If prep hasn't run you land on the calm preparing hold — watch the Network panel: the flow backoff-polls /start at a widening 2s→~12s cadence, and when prep completes a poll answers 200, debits the owner's session credit, and opens the transcript. Type a message — it posts instantly (optimistic), then settles when its seq echo returns — and watch the DM's prose stream in token by token. Reload mid-session: the return joins off the GET /active probe — no POST /start, and no red 409 line in the console.
  3. Open the same campaign as a second identity mid-session: it should rebuild the full backlog (the lastSeq = 0 seed), then stream live and show typing presence. Press @DM — the summon is visible to both tables and draws a response.
  4. Open the knowledge sidebar (default-open on desktop, the edge-handle Drawer on a ~375px viewport). The World Wiki lists the known entities and its search narrows client-side; the Relationship Graph renders drained (no fog) with known-tier edges only; the Character Sheet shows your own sheet, and an adjust_hp turn moves its HP readout live. Reload — the sidebar reopens and the Network panel shows exactly one world-snapshot GET. To prove enforced ignorance, seed a secret-tier relationship between two known entities and confirm it never appears in the graph.
  5. Watch the between-turns chrome: the position line appears once a turn has completed and lifts its ink as the session runs on, and the end control does not mount until the session is genuinely near its end. Press it and the confirm should lead with irreversibility, not cost; confirming should sweep the whole row, go the composer inert, and leave one closing signal at the live edge.
  6. Kill and restore the connection mid-turn: the turn resyncs without double-rendering, and the position line holds its last value rather than blanking. Then end the session — the DM renders a send-off, then the screen lands on the recap, which shows its pending beat until the analysis job writes the summary and then streams the document in.
  7. To inspect the wire, watch the WS frames and the session_messages / credit_ledger rows — the server side is on the session transport page.

Integration points

This screen is the client half of the session transport: it consumes that transport's frames through the shipped WS session client and prep-status SSE, every start arm maps to a backend precondition documented there, and the dm_correction frame the errata slip renders is emitted by the Fast Thinker's correction tool on the server side. The 402 arm hands off to the billing & credits purchase moment; the full-bleed frame is a declared shared edit with that work on the app shell's AppFrame. The play entry itself is reached from character creation once the party finalizes, and every visible element is a mythrunUI component over the DOM-free client brain. The dice moment (MYT-93) is the first surface built on this reducer's first-class item shape; the knowledge layer (MYT-94) is the next consumer, reading the ledger_update item into its live sheet overlay. The between-sessions hold and the session-position chrome both read shared brains — the wait vocabulary and the transport's own progress field — rather than deriving second opinions. That layer reuses the world-gen reveal's WorldWiki and WorldGenGraph and its canonical snapshot→graph adapter, and the creation reveal's curated-sheet adapter, both fed by the one member-readable world snapshot the server filters to the known tier. The session-end recap read is still the outstanding consumer of the reducer's shape.
