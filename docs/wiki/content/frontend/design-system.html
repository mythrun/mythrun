Design system

mythrunUI — the brand-aligned, token-driven component library the whole app composes. The system before the app: ~27 primitives (layout, type, controls, overlays, feedback, display) each typed against a platform-neutral contract, styled from a single token vocabulary, documented in Storybook, and held in place by lint and CI gates. Two packages carry it — @mythrun/client-core (the platform-neutral brain: the component contract + the token data) and @mythrun/ui (the web implementation that turns the contract into DOM).

Why a contract layer at all — Mythrun ships web first, then ports to true-native iOS/Android later (not React-Native-Web, not Capacitor). For that port to be a mechanical translation rather than a rewrite, the component API has to be platform-neutral from day one. So the prop/variant types (ButtonProps, …) live in a DOM-free package and the web implementation is typed against them. A future @mythrun/ui-native implements the same contract; tsc catches any prop-surface drift between the two. This is the frontend's portability rule R2 made structural — the contract layer and the api-purity lint (below) are how that rule is enforced in code.

Three packages, one direction

The dependency arrow points one way: client-core ← ui ← web. @mythrun/client-core is the base — born in this issue, it holds only platform-neutral things and imports nothing but react (for ReactNode in a child slot) and culori (in the build-time token generator). @mythrun/ui is the web design system: it implements the contract with DOM, Radix, and Tailwind, and it owns all web CSS. @mythrun/web is the app — it composes the library's public components and never reaches past them.

@mythrun/ui consumes the contract via import type — erased at compile time, so there is no runtime coupling and no circular import as @mythrun/client-core later grows stores and transport (MYT-83). It invokes the token generator only in its build script, never in shipped component code. The seam stays thin on purpose.

The contract — a typed seam enforced as a pair

The contract is the set of exported *Props types under client-core/src/contract/, surfaced as a type-only subpath, @mythrun/client-core/contract. ButtonProps, InputProps, SelectProps, … — prop shapes and variant unions, nothing else. The barrel (contract/index.ts) re-exports them all with export type only, so the package root stays free of runtime values; a test asserts that property.

Each web component is typed (props: ButtonProps) against its contract type. tsc then checks that the implementation's prop surface satisfies the contract — so when the native impl is written and typed the same way, prop-surface drift is a compile error. But tsc checks prop shape, not behavior, and does not by itself forbid a web-only excess prop: a stray className? passthrough can structurally satisfy (props: ButtonProps). That gap is closed by the second half of the pair.

Conformance = tsc (satisfies) + API-purity lint (does not exceed) — the phrase "tsc guarantees parity" is deliberately avoided. tsc proves the impl is at least the contract; the API-purity lint (below) proves it is at most the contract — no DOM-only props leaked onto the public surface. Together they pin the API to exactly the platform-neutral contract. Behavioral parity is documented in the contract and verified by each component's tests, not claimed by the compiler.

So the native impl is a mechanical translation, the contract fixes a few cross-cutting conventions once: ref forwarding on every component; a single controlled/uncontrolled signature shape (value / defaultValue / onChange) across all inputs; and polymorphism expressed neutrally — a Button-as-Link routes through the Link primitive, never Radix's DOM-coupled asChild (which has no native analog and would fail API-purity). asChild / Slot stays an internal web-impl detail. Contract changes are recorded in client-core/CHANGELOG.md — a breaking change is a deliberate, reviewed event, because a second consumer will implement the same contract later.

The token foundation, relocated

The design tokens were born in @mythrun/ui (MYT-81). This issue relocates the platform-neutral half of them into client-core: the OKLCH palette generator (generate-palette.mjs, with its culori dependency) and the raw token-scale data (scales.ts — spacing, radius, control/icon sizes, z-index, motion, typography roles, weights, tracking, measure, breakpoints, and the twelve curated avatar pigments). These are exposed as the build-time subpath @mythrun/client-core/tokens. No CSS moves.

Generator moves, web CSS stays — the token values are platform-neutral data (a native impl emits the same numbers into NativeWind). But the web @theme emission — the :root/.dark flip, @theme inline, semantic.css, base.css — is a web-face concern and must not live in the DOM-free base layer. So only the generator + scale data + manifest (JS/JSON) move; @mythrun/ui imports the generator and runs it at build time (pnpm --filter @mythrun/ui build → build:tokens) to emit colors.generated.css back into its own src/styles/. A round-trip test asserts the relocated generator reproduces the committed CSS byte-for-byte — the real idempotency check that the move changed nothing.

The MYT-82 token work also completes the foundation MYT-81 left partial: it adds the spacing, sizing, border, surface-tier, focus, interaction-state, status-intent, z-index, and motion scales the components consume, and it settles the design language (below) by removing the soft-shadow tokens. Static scales live as typed data in scales.ts and are mirrored into theme.css by hand; a drift-guard test asserts the two never diverge. Theme-aware tokens (focus ring, --border-strong, surface tiers, status intents) stay in semantic.css because they flip per theme.

The design language — flat 1-bit

The brand's "Parchment & Ink / Obra Dinn" register, taken seriously. This is where the visual identity finally settles, in the brand's favor over the older UX spec's "light, airy, soft shadows."

  • Radius: 0px everywhere. Sharp corners match the pixel-art icons.
  • Depth via borders and paper-tier surfaces, not shadows. The MYT-81 soft-shadow tokens are removed. Interactive control boundaries use --border-strong (≥3:1 contrast); faint --border is reserved for decorative dividers.
  • Focus ring: 2px hard square outline, 2px offset, no glow — and theme-aware. --focus-ring-color: var(--accent) resolves to ember-600 in light and ember-400 in dark, so it clears WCAG 3:1 on both surfaces.
  • Interaction states are token-swaps (discrete steps), never translucent overlays.
Theme-aware focus ring — a fixed ember-600 ring fails the 3:1 non-text-contrast floor against dark surfaces. Binding the ring to the --accent alias lets the .dark remap swap in ember-400, which passes. The token-contrast gate (below) checks this claim at the token level, since axe does not verify the ring color against its background.

The build stack

The widely-adopted "shadcn pattern," chosen partly because it ports cleanly. Behavior and accessibility come from Radix (the unified radix-ui package): unstyled primitives supply focus-trap, focus-return, keyboard navigation, portals, and ARIA wiring; we style them 100% from our tokens. Variants are CVA (class-variance-authority) — but the variant→class mapping is internal to the web impl, never crossing the contract. Classes are merged through a single cn() util (clsx + tailwind-merge). Icons are pixelarticons per-icon component imports behind a swappable Icon API. The brand's one sanctioned gradient is the Dither — a locked 4×4-Bayer two-color band, for committed high-contrast transitions only, never a smooth gradient.

The unified radix-ui package, not individual @radix-ui/react-* — shadcn migrated to the single package in early 2026; the individual packages risk a React-19 peer-dependency skew that pnpm's strict resolution hard-fails. The native mirror is rn-primitives (same API) — the seam the native impl swaps behind. CVA is the recorded swap target's predecessor: if it stalls (single-maintainer), tailwind-variants is the pre-chosen replacement, and because CVA never crosses the contract the swap is contained.

The primitive set

Each primitive lands in @mythrun/ui/src/components/<Name>/ with its web impl, a Storybook story, and a Vitest + RTL + axe test, typed against a contract type in client-core. The set reads as cognitive layers, leaves first:

  • Layout — Stack, Box, Grid, Divider. These expose a token-typed style vocabulary (gap: SpaceToken), so they pass API-purity by construction.
  • Typography — Text, Heading, Link (router-aware, i18n), VisuallyHidden.
  • Leaves — Icon, Spinner — composed by the controls (Button's loading state, IconButton).
  • Controls — Button (incl. loading), IconButton (requires an accessible name), Input, TextArea (autosizing), Select, Checkbox, Radio/RadioGroup, Switch, and SeamlessInput — the borderless ghost field for one-question creation flows.
  • Forms — FormField (label + helper + error + required/invalid) and Label. The error string is an i18n key, so the error-rendering contract — including server/LLM-rejection messages routed inline — is designed once, not improvised per field.
  • Containers & overlays — Card (header/body/footer slots), Modal, Popover, Tooltip, Tabs, Menu.
  • Feedback — Banner (inline, persistent), Toast (transient, global), Spinner.
  • Display — Avatar/AvatarGroup (image-with-initials fallback, twelve curated pigments), Badge, Dither.
Banner vs Toast — inline vs subsystem — a Banner is a leaf: inline, contextual, persistent, rendered where the message belongs. A Toast is a subsystem: an app-root provider and portal, a queue (max-visible + dedupe), aria-live politeness, auto-dismiss that respects prefers-reduced-motion, and an imperative toast() API callable from anywhere. toast() is the one runtime value the library exports that isn't a component — it ships from @mythrun/ui, not the type-only contract barrel.

Feature-specific composites — campaign cards, roll cards, chat messages, the character sheet — are deliberately out of scope here. They get built into mythrunUI inside their own feature issues, never ad-hoc, so the system grows with the app rather than ahead of it.

Storybook

Storybook 9 (Vite builder) is the visual catalogue and the authoring surface. Each component's story follows a doc template the story-coverage gate can assert: an autodocs props table, the all-states matrix (default / hover / active / focus-visible / disabled / loading / invalid / read-only / selected, the relevant subset per component), a11y notes, do/don't, and content/i18n guidance. A foundation story renders the token specimens; a patterns story shows a composed Character-Creation flow. A light/warm-dark toggle exercises both themes.

Tailwind v4 needs explicit Storybook wiring — Storybook builds its preview through its own Vite config, separate from the app's. Without pushing @tailwindcss/vite into that config via viteFinal in .storybook/main.ts, the @import "tailwindcss" never compiles and every story renders unstyled. That one line is load-bearing.

Enforcement — rules as CI gates

The methodology rule is that every reusable component lives in mythrunUI and has a story, and that anything the team cares about becomes a CI gate rather than a style note. MYT-82 stands up the gates that keep the system from rotting, each registered in the correct package's config and each shipped with a positive-and-negative wiring test (a rule that silently no-ops is worse than no rule).

API-purity (R2)

api-purity.js keeps the public *Props surface platform-neutral: it flags a className/style member, a DOM mouse/pointer/drag event handler, a CSSProperties-typed member, or an exported *Props that extends an HTML-attribute base. Pure AST — no type-checker. The rule lives in client-core (the base layer) so both packages can register it without inverting the dependency direction: client-core applies it to the contract types themselves; @mythrun/ui imports the same rule and applies it to component prop-widening (a (props: ButtonProps & { className?: string }) that would smuggle a DOM prop past the contract). Only exported *Props are the public surface — a non-exported helper interface is the carve-out for internal Radix plumbing.

no-ad-hoc-color (R3)

no-ad-hoc-color.js keeps color in the token layer: it flags a raw hex or rgb()/hsl()/oklch() literal, a Tailwind arbitrary-value color utility (bg-[#abc]), and an inline style color. It scans every string literal and template quasi under src/components/**, not just JSX attributes — because in the CVA pattern the color classes live inside cva({...}) / cn(...) call arguments, where a JSXAttribute-only matcher would miss them. A var(--…) reference is a token and always passes. Component .css is covered separately by a Stylelint pass (excluding the generated colors.generated.css).

Story-coverage

story-coverage.mjs globs the immediate child directories of src/components/ and fails CI if any lacks a *.stories.tsx. The directory-per-component convention is the discriminator — type-only, util, hook, and foundation files aren't under components/<Name>/, so they are exempt by construction. Alongside it, the CI workflow runs a full Storybook production build, which catches story/MDX breakage the existence check can't.

Import boundary (R5)

Feature code composes the library's public surface only. A no-restricted-imports path-ban in @mythrun/web's config forbids feature code from importing the library's internal building blocks (radix-ui, CVA, tailwind-merge/clsx, the icon set) and from deep-importing @mythrun/ui's source — features import from the package root @mythrun/ui (plus React, client-core, i18n). Reaching for a raw primitive in a feature is a one-off element outside the system, which is un-portable. The no-ad-hoc-ui rail (MYT-79) is the companion: it bans raw <div>/className/style in feature code. The cross-feature-component boundary is deferred to MYT-83, since no feature directories exist yet.

Accessibility & token-contrast

The a11y gate is real assertions, not just the Storybook addon (which is a dev-time aid): each component test runs jest-axe plus explicit keyboard-interaction tests (Tab/Esc/Arrow/Enter/Space), a Modal focus-trap-and-return test, and a Toast/Banner live-region test. A token-level contrast check uses the generator's wcagContrast to verify the focus-ring and interactive-border 3:1 claims that axe does not check. Every interactive control — icon-only ones included — carries a ≥44px hit target and an accessible name.

Operating this piece

Add a primitive to the library

  1. Add the contract type under frontend/client-core/src/contract/<name>.ts and re-export it (export type) from contract/index.ts.
  2. Create frontend/ui/src/components/<Name>/<Name>.tsx, typed (props: <Name>Props); export it (and its props type) from frontend/ui/src/index.ts.
  3. Style from token utilities only (bg-ember-600, never raw hex). Use cn() for class composition and CVA for variants.
  4. Add <Name>.stories.tsx following the doc template (autodocs, state matrix, a11y notes, do/don't). The story-coverage gate fails without it.
  5. Add <Name>.test.tsx with RTL behavior + jest-axe + the relevant keyboard tests.
  6. Run pnpm --filter @mythrun/ui typecheck lint lint:css test test:coverage story-coverage and pnpm --filter @mythrun/client-core typecheck lint test:coverage.

Add or change a token

  1. For a static scale: edit frontend/client-core/src/tokens/scales.ts and mirror it into frontend/ui/src/styles/theme.css (the drift-guard test asserts they match).
  2. For a palette color: edit generate-palette.mjs, then pnpm --filter @mythrun/ui build to regenerate colors.generated.css + tokens.manifest.json; the round-trip test re-asserts idempotency.
  3. For a theme-aware semantic alias: edit semantic.css (the :root/.dark pair + the @theme inline surface), and extend the alias list in the token test.
  4. Record any contract-affecting change in frontend/client-core/CHANGELOG.md.
