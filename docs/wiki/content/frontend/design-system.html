Design system

mythrunUI — the brand-aligned, token-driven component library the whole app composes. The system before the app: ~35 primitives (layout, responsive, type, controls, overlays, feedback, display, brand) each typed against a platform-neutral contract, styled from a single token vocabulary, responsive by construction (they shrink, wrap, and truncate so nothing spills a phone-width row), light/dark at runtime, documented in one frontend-level Storybook, and held in place by lint, accessibility, and mobile-viewport CI gates. Two packages carry it — @mythrun/client-core (the platform-neutral brain: the component contract + the token data) and @mythrun/ui (the web implementation that turns the contract into DOM).

Why a contract layer at all — Mythrun ships web first, then ports to true-native iOS/Android later (not React-Native-Web, not Capacitor). For that port to be a mechanical translation rather than a rewrite, the component API has to be platform-neutral from day one. So the prop/variant types (ButtonProps, …) live in a DOM-free package and the web implementation is typed against them. A future @mythrun/ui-native implements the same contract; tsc catches any prop-surface drift between the two. This is the frontend's portability rule R2 made structural — the contract layer and the api-purity lint (below) are how that rule is enforced in code.

Three packages, one direction

The dependency arrow points one way: client-core ← ui ← web. @mythrun/client-core is the base — born in this issue holding only the component contract and token data, it imported nothing but react (for ReactNode in a child slot) and culori (in the build-time token generator). MYT-83 then grew it into the full platform-neutral client brain — the data layer, the session store, the platform interfaces, and the i18n catalog (see App shell & data layer), pulling in zustand, @tanstack/react-query, i18next, and the @mythrun/contract wire types — but it still touches no DOM. @mythrun/ui is the web design system: it implements the contract with DOM, Radix, and Tailwind, and it owns all web CSS. @mythrun/web is the app — it composes the library's public components and never reaches past them.

@mythrun/ui consumes the contract via import type — erased at compile time, so there is no runtime coupling and no circular import now that @mythrun/client-core has grown its stores and data layer (MYT-83). It invokes the token generator only in its build script, never in shipped component code. The seam stays thin on purpose.

The contract — a typed seam enforced as a pair

The contract is the set of exported *Props types under client-core/src/contract/, surfaced as a type-only subpath, @mythrun/client-core/contract. ButtonProps, InputProps, SelectProps, … — prop shapes and variant unions, nothing else. The barrel (contract/index.ts) re-exports them all with export type only, so the package root stays free of runtime values; a test asserts that property.

Each web component is typed (props: ButtonProps) against its contract type. tsc then checks that the implementation's prop surface satisfies the contract — so when the native impl is written and typed the same way, prop-surface drift is a compile error. But tsc checks prop shape, not behavior, and does not by itself forbid a web-only excess prop: a stray className? passthrough can structurally satisfy (props: ButtonProps). That gap is closed by the second half of the pair.

Conformance = tsc (satisfies) + API-purity lint (does not exceed) — the phrase "tsc guarantees parity" is deliberately avoided. tsc proves the impl is at least the contract; the API-purity lint (below) proves it is at most the contract — no DOM-only props leaked onto the public surface. Together they pin the API to exactly the platform-neutral contract. Behavioral parity is documented in the contract and verified by each component's tests, not claimed by the compiler.

So the native impl is a mechanical translation, the contract fixes a few cross-cutting conventions once: ref forwarding on every component; a single controlled/uncontrolled signature shape (value / defaultValue / onChange) across all inputs; and polymorphism expressed neutrally — a Button-as-Link routes through the Link primitive, never Radix's DOM-coupled asChild (which has no native analog and would fail API-purity). asChild / Slot stays an internal web-impl detail. Contract changes are recorded in client-core/CHANGELOG.md — a breaking change is a deliberate, reviewed event, because a second consumer will implement the same contract later.

The token foundation, relocated

The design tokens were born in @mythrun/ui (MYT-81). This issue relocates the platform-neutral half of them into client-core: the OKLCH palette generator (generate-palette.mjs, with its culori dependency) and the raw token-scale data (scales.ts — spacing, radius, control/icon sizes, z-index, motion, typography roles, weights, tracking, measure, breakpoints, and the twelve curated avatar pigments). These are exposed as the build-time subpath @mythrun/client-core/tokens. No CSS moves.

The pigments widened into full ramps (MYT-87) — the eleven non-hero brand pigments (moss, pine, verdigris, lapis, iris, heather, rose, sienna, ochre, umber, slate) began as single mid-tone values, so two of them, being near-equiluminant, couldn't dither against each other. The generator now runs each pigment through the same OKLCH luminance ladder ember and the semantic ramps ride, emitting all ten steps (--color-{hue}-{step}) — the authored mid-tone lands unchanged on its nearest rung, and the rest of the ramp is generated around it. That turns the palette into a full grid a world cover can pick a genuine light-of-one-hue × dark-of-another from and always read. The change is additive (light and dark variants of colours that already existed) and flows through the same manifest + drift guard as every other token.
Generator moves, web CSS stays — the token values are platform-neutral data (a native impl emits the same numbers into NativeWind). But the web @theme emission — the :root/.dark flip, @theme inline, semantic.css, base.css — is a web-face concern and must not live in the DOM-free base layer. So only the generator + scale data + manifest (JS/JSON) move; @mythrun/ui imports the generator and runs it at build time (pnpm --filter @mythrun/ui build → build:tokens) to emit colors.generated.css back into its own src/styles/. A round-trip test asserts the relocated generator reproduces the committed CSS byte-for-byte — the real idempotency check that the move changed nothing.

The MYT-82 token work also completes the foundation MYT-81 left partial: it adds the spacing, sizing, border, surface-tier, focus, interaction-state, status-intent, z-index, and motion scales the components consume, and it settles the design language (below) by removing the soft-shadow tokens. Static scales live as typed data in scales.ts and are mirrored into theme.css by hand; a drift-guard test asserts the two never diverge. Theme-aware tokens (focus ring, --border-strong, surface tiers, status intents) stay in semantic.css because they flip per theme.

The design language — flat 1-bit

The brand's "Parchment & Ink / Obra Dinn" register, taken seriously. This is where the visual identity finally settles, in the brand's favor over the older UX spec's "light, airy, soft shadows."

  • Radius: 0px everywhere. Sharp corners match the pixel-art icons.
  • Depth via borders and paper-tier surfaces, not shadows. The MYT-81 soft-shadow tokens are removed. Interactive control boundaries use --border-strong (≥3:1 contrast); faint --border is reserved for decorative dividers.
  • Focus ring: 2px hard square outline, 2px offset, no glow — and theme-aware. --focus-ring-color: var(--accent-fg) — the foreground accent, not the fill — resolves to ember-500 in light and ember-300 in dark, so it clears WCAG 3:1 on both surfaces.
  • Interaction states are token-swaps (discrete steps), never translucent overlays.
The accent is two tokens — a fill and a foreground (MYT-86) — a single --accent can't satisfy both ways the color is used. As a fill (--accent, the primary button's background) it carries on-accent text, so it must be dark enough for paper-50 to read on top of it. As a foreground (--accent-fg: link text, the focus ring 2px outside the control, the ghost-field caret) it is drawn directly on the page and must contrast against it — the opposite constraint. In light mode the hero ember serves both, so the two mirror. In dark mode the windows don't overlap: the fill darkens to ember-400 (so paper-50 clears AA on a primary button), which is then too dark to read or ring against the dark page, so the foreground stays lighter (ember-300). Splitting the token is what lets dark-mode buttons, links, and focus rings all clear AA at once; the focus ring keys to the foreground half. The token-contrast gate (below) checks these claims at the token level, since axe does not verify a color against its background.

Theme mode

The token layer keys light and dark off a single .dark class on the document root (the :root/.dark flip above); MYT-84 adds the runtime that toggles it. A ThemeProvider (in @mythrun/ui, the DOM-capable package) holds the active theme, applies or removes .dark on <html>, and persists the choice to localStorage. Its default is the stored value, falling back to the OS prefers-color-scheme. A useTheme() hook exposes { theme, toggle, setTheme } — the contract type lives in client-core/contract/theme.ts, DOM-free, so only the side-effecting impl is web-bound.

The visible control is the ThemeToggle — a square button that flips the theme, carrying the sun glyph in light and the moon in dark. Its placement chooses how it sits: fab (the default) is fixed top-right, so a genesis screen renders a bare <ThemeToggle/> over the crown without reaching for raw layout; inline (MYT-86) drops the fixed positioning for an in-flow nav control — the landing page seats it in its nav row beside the sign-in button. Its sun/moon come from the real Pixelarticons glyphs added to the swappable Icon map (glyphs.ts) and to the closed IconName union — replacing the hand-authored placeholders the set is not allowed to ship.

A pre-paint inline script, not a React effect — if the .dark class were applied only once the ThemeProvider mounts, a dark-mode reload would paint one light frame before React hydrated and corrected it: a flash of the wrong theme. So a tiny inline script in index.html resolves the same value (stored mythrun-theme ?? OS preference) and sets the class before first paint; the provider reconciles to the identical value on mount, so there is no flip on hydrate. The script is the one place this logic is deliberately duplicated — it must run before any bundle does.
The inverted surface rides the existing token blocks, not a third set (MYT-86) — surface="reversed" is simply .dark (always dark, whatever the page). surface="inverted" is different: it must be the opposite of the current theme — dark on a light page, light on a dark page — so the landing footer always reads as a deliberate break the page grades into. Rather than author a new token set, the .surface-inverted class is added as an extra selector on the two blocks that already exist: it joins the dark block (.dark, .surface-inverted) so it goes dark on a light page, and joins the light block scoped under dark (.dark .surface-inverted) so it goes light on a dark page. Zero token values are duplicated — the whole semantic vocabulary just flips inside the scope, the same cascade that drives .dark. (Because the region is a real theme flip, a child must re-theme through the semantic utilities, never a hand-written dark: variant — on a dark page the light footer is a .dark descendant, so a dark: rule would fire backwards.)

The build stack

The widely-adopted "shadcn pattern," chosen partly because it ports cleanly. Behavior and accessibility come from Radix (the unified radix-ui package): unstyled primitives supply focus-trap, focus-return, keyboard navigation, portals, and ARIA wiring; we style them 100% from our tokens. Variants are CVA (class-variance-authority) — but the variant→class mapping is internal to the web impl, never crossing the contract. Classes are merged through a single cn() util (clsx + tailwind-merge). Icons are pixelarticons per-icon component imports behind a swappable Icon API. The brand's one sanctioned gradient is the Dither — a locked 4×4-Bayer band between two palette colors (from→to, R3 — never a raw color), for committed high-contrast transitions only, never a smooth gradient; a flip hangs the dense end at the top edge for the genesis-screen crown.

The unified radix-ui package, not individual @radix-ui/react-* — shadcn migrated to the single package in early 2026; the individual packages risk a React-19 peer-dependency skew that pnpm's strict resolution hard-fails. The native mirror is rn-primitives (same API) — the seam the native impl swaps behind. CVA is the recorded swap target's predecessor: if it stalls (single-maintainer), tailwind-variants is the pre-chosen replacement, and because CVA never crosses the contract the swap is contained.

The primitive set

Each primitive lands in @mythrun/ui/src/components/<Name>/ with its web impl, a Storybook story, and a Vitest + RTL + axe test, typed against a contract type in client-core. The set reads as cognitive layers, leaves first:

  • Layout — Stack, Box, Grid, Divider. These expose a token-typed style vocabulary (gap: SpaceToken), so they pass API-purity by construction. (MYT-83 added two token-typed Box variants — a reversed dark surface and a full-viewport minHeight="screen" floor, on 100dvh for mobile — for the dithered 404; see App shell & data layer. MYT-84 added a numeric Stack grow weight — proportional flex spacers that seat content with a deliberate vertical rhythm, e.g. the genesis screens' optically-above-center card. MYT-86 added a semantic-landmark as prop to Box — nav / main / footer / header / section, so a page wraps a real landmark element without raw DOM — plus two more surfaces: none, transparent (paints no background, so a landmark wrapper inherits the page field instead of laying a panel tone over it), and inverted, theme-inverting — dark on a light page, light on a dark page — the landing footer's field. MYT-87 added a px minColumnPx track to Grid — an auto-fill minimum in raw pixels rather than a SpaceToken (the space scale caps well below a card width), the fluid shelf mechanism the campaign hub packs cover cards on — and a tone="ink" Divider, a deliberate structural cut dark in both themes, the seam between a cover card's cover art and its body.)
  • Responsive — Show, a show/hide switch between two visually distinct layouts (the hub's desktop card grid vs its mobile index list). It toggles visibility at a breakpoint with full static class strings — a pair of sibling Shows (above ⊕ below the same step) renders exactly one, and the hidden branch is display:none, out of the layout and the a11y tree, so the off-screen layout's headings and links never leak to assistive tech.
  • Typography — Text (roles now include subtitle, the italic muted narrative sub-line, and meta, the mono ledger line the hub reads a campaign's state into), Heading, Link (router-aware, i18n, plus an unstyled variant that drops the accent tint from its subtree while keeping the focus ring — a whole-card or whole-row link that shouldn't paint its contents link-accent), VisuallyHidden.
  • Leaves — Icon, Spinner — composed by the controls (Button's loading state, IconButton).
  • Controls — Button (incl. loading, a native leading-icon slot — a platform-neutral icon prop, not an asChild DOM trick, carrying the Google/Discord provider marks on the sign-in buttons, plus MYT-90 aria-expanded/aria-controls disclosure props for a button that toggles a revealable region, e.g. the character sheet's "See full sheet"), IconButton (requires an accessible name), Input, TextArea (autosizing), Select, Checkbox, Radio/RadioGroup, Switch, and SeamlessInput — the borderless ghost field for one-question creation flows.
  • Forms — FormField (label + helper + error + required/invalid) and Label. The error string is an i18n key, so the error-rendering contract — including server/LLM-rejection messages routed inline — is designed once, not improvised per field.
  • Containers & overlays — Card (header/body/footer slots, plus a responsive collapse mode — a bordered card at sm and up, dropping its border/surface/padding to sit native and inline below the breakpoint, the genesis screens' card, and a frame="dashed" variant — an outline waiting to be filled, the hub's empty-state "Unwritten" cover), CoverCard (a portrait "made-object" card with a full-bleed cover header, an ink seam, and a foot-pinned imprint — the fixed cover geometry the neutral Card doesn't model), Modal, Popover, Tooltip, Tabs, Menu.
  • Feedback — Banner (inline, persistent), Toast (transient, global), Spinner.
  • Display — Avatar/AvatarGroup (image-with-initials fallback, twelve curated pigments; AvatarGroup gained a size and a surface prop — its overlap ring follows either the page or a card surface, so seals clustered on a card don't halo), CoverDither (a card-scale full-field Bayer gradient between two WorldColors — a world's cover art, distinct from the fixed-geometry transition-strip Dither), Badge, Dither.
  • Brand — Logomark (the 64-px pixel-art mark, crisp-scaled, ink/ember tone), Wordmark (the Tyma Garamont logotype), Lockup (primary / stacked) and HorizontalLockup (secondary). Each takes a neutral size + a required aria-label and paints in monochrome currentColor, so it flips ink↔cream with the theme. The provider marks GoogleMark + DiscordMark are kept apart in src/brand-marks/ (not src/components/) and ride the Button icon slot on the OAuth sign-in screen.
Provider marks live outside src/components/ — the Google "G" is four locked brand colors and the Discord mark is locked blurple; the providers' sign-in guidelines mandate them, so they cannot be design tokens. But no-ad-hoc-color scans every string under src/components/** and would (correctly) reject those hex literals. So the two provider marks sit in src/brand-marks/, outside the token zone — an external-asset carve-out, not a hole in the rule. The Mythrun marks (Logomark/Wordmark/Lockup) are token-clean (monochrome currentColor) and stay under src/components/.
Banner vs Toast — inline vs subsystem — a Banner is a leaf: inline, contextual, persistent, rendered where the message belongs. A Toast is a subsystem: an app-root provider and portal, a queue (max-visible + dedupe), aria-live politeness, auto-dismiss that respects prefers-reduced-motion, and an imperative toast() API callable from anywhere. toast() is the one runtime value the library exports that isn't a component — it ships from @mythrun/ui, not the type-only contract barrel.

Feature-specific composites — the campaign card, roll cards, chat messages, the character sheet — are deliberately out of scope here. They get built inside their own feature issues, never ad-hoc. But their reusable parts land in the system: the campaign hub gave mythrunUI the CoverCard, CoverDither, and Show primitives plus the Card/Grid/Avatar/Text/Link extensions above, while the campaign-specific CampaignCard that composes them stays a screen component. The line is reusability, not feature-adjacency — a book-cover card is a general shape; "a campaign's card" is not. The world-generation experience drew the same line: it contributed the general FullBleedStage layout primitive (a stage that cancels the app-frame's content insets to run a canvas edge-to-edge on phones), the Drawer edge-handle sheet (a mount-persistent mobile sheet summoned from a pinned handle, its children surviving close→open), and the useViewportNarrow breakpoint hook to the system, while its fog-, graph-, status-card, loading, and reveal-transition composites (WorldGenFog, WorldGenGraph, WorldGenStatusCard, WorldGenLoading, RevealTransition) stay feature components documented on that page. The character-creation experience (MYT-90) drew the line the same way: its screen composites — LevelCard, FreeformPrompt, GuidedBuilder, CharacterLoadingBeat (a Dither reuse), CharacterSheetReveal, and PartyRoster — are controlled/presentational feature components (their sequencing lives in a client-core reducer, not the component) documented on that page, while the reusable primitive extension it needed landed in the system as the Button disclosure props above.

Responsive by construction

Responsiveness is part of the contract, not a per-screen afterthought (MYT-97). The layout and text primitives shrink, wrap, and truncate on their own, so a row composed from them fits a phone-width viewport without the feature author hand-managing flex. The contract grew four intrinsic affordances: Stack gains a wrap flag (flow children onto a second main-axis line); Text gains truncate (single-line ellipsis) for the flexible item that should absorb a row's shrink, and noShrink for a short fixed label or value that must hold its width; Button and Icon carry shrink-0 by construction — a fixed affordance never squishes beside shrinking text. Underneath, the Stack web impl sets min-width: 0 on every direct child by default — flex's min-width: auto floors a child at its content width and forces overflow otherwise, so this blanket unblocker is what lets a long child shrink at all; the fixed primitives opt back out of it with shrink-0.

Intrinsic-first, not breakpoint-first — the primitive fixes itself at any width rather than every consumer reaching for a media query. A Stack of a flexible truncate Text plus a couple of noShrink labels resolves a constrained row by itself; breakpoint collapse stays available for the cases that genuinely need it, but the default is that a component simply doesn't spill. This is the half MYT-97 made first-class after the app-frame header overflowed at phone width because the primitives had no shrink/wrap/truncate to reach for. The behavior is contract-level, so the future native impl honors it the same way — truncate maps to numberOfLines={1}, noShrink to flexShrink: 0; only the web's min-w-0 mechanism is a DOM detail.
noShrink for a fixed label, not truncate everywhere — a single-token label (a wordmark, a credit balance) squeezed below its own width doesn't truncate cleanly; it spills its box and collides with the next item. So fixed-width text opts out of the row's shrink and the one flexible sibling — the truncate Text — absorbs all of it. The overflow gate (below) catches both the sideways-scroll case and this intra-row collision.

Storybook

Storybook 9 (Vite builder) is the visual catalogue and the authoring surface. MYT-97 consolidated it to one frontend-level Storybook hosted in @mythrun/web (frontend/.storybook/) that scans both the design-system stories (../ui/src/**) and the app-shell screen stories (../src/**); the ui package's own Storybook was retired. Each component's story still follows a doc template the story-coverage gate can assert: an autodocs props table, the all-states matrix (default / hover / active / focus-visible / disabled / loading / invalid / read-only / selected, the relevant subset per component), a11y notes, do/don't, and content/i18n guidance. A foundation story renders the token specimens; a patterns story shows a composed Character-Creation flow. A light/warm-dark toggle exercises both themes.

One Storybook, hosted in web, not ui — the mobile-viewport gate has to render both the primitives and the assembled screens, so a single catalogue is simplest. It lives in @mythrun/web because web already depends on ui: hosting the web screen stories inside the ui package's Storybook would point ui at web and invert the dependency arrow into a cycle. Stories themselves stay co-located with their code (ui/src/components/<Name>, src/routes); only the Storybook host moved up a level.
Tailwind v4 needs explicit Storybook wiring — Storybook builds its preview through its own Vite config, separate from the app's. Without pushing @tailwindcss/vite into that config via viteFinal in frontend/.storybook/main.ts, the @import "tailwindcss" never compiles and every story renders unstyled. That one line is load-bearing.

Enforcement — rules as CI gates

The methodology rule is that every reusable component lives in mythrunUI and has a story, and that anything the team cares about becomes a CI gate rather than a style note. MYT-82 stands up the gates that keep the system from rotting, each registered in the correct package's config and each shipped with a positive-and-negative wiring test (a rule that silently no-ops is worse than no rule).

API-purity (R2)

api-purity.js keeps the public *Props surface platform-neutral: it flags a className/style member, a DOM mouse/pointer/drag event handler, a CSSProperties-typed member, or an exported *Props that extends an HTML-attribute base. Pure AST — no type-checker. The rule lives in client-core (the base layer) so both packages can register it without inverting the dependency direction: client-core applies it to the contract types themselves; @mythrun/ui imports the same rule and applies it to component prop-widening (a (props: ButtonProps & { className?: string }) that would smuggle a DOM prop past the contract). Only exported *Props are the public surface — a non-exported helper interface is the carve-out for internal Radix plumbing.

no-ad-hoc-color (R3)

no-ad-hoc-color.js keeps color in the token layer: it flags a raw hex or rgb()/hsl()/oklch() literal, a Tailwind arbitrary-value color utility (bg-[#abc]), and an inline style color. It scans every string literal and template quasi under src/components/**, not just JSX attributes — because in the CVA pattern the color classes live inside cva({...}) / cn(...) call arguments, where a JSXAttribute-only matcher would miss them. A var(--…) reference is a token and always passes. Component .css is covered separately by a Stylelint pass (excluding the generated colors.generated.css).

Story-coverage

story-coverage.mjs globs the immediate child directories of src/components/ and fails CI if any lacks a *.stories.tsx. The directory-per-component convention is the discriminator — type-only, util, hook, and foundation files aren't under components/<Name>/, so they are exempt by construction. Alongside it, the CI workflow runs a full Storybook production build, which catches story/MDX breakage the existence check can't.

Mobile-viewport overflow gate

The durable half of MYT-97: a @storybook/test-runner postVisit hook (frontend/.storybook/test-runner.ts) renders every story in real Chromium at 375px and 1280px and fails the build if anything scrolls sideways. It is outcome-based — it doesn't care how a story fits (intrinsic shrink or a breakpoint collapse), only that the rendered width never exceeds the viewport (measured as the larger of #storybook-root and document.body, so portaled overlays count too). It also catches the subtler intra-row collision: a fixed item squeezed below its own text spills its box — content wider than the box while overflow stays visible — without the container ever scrolling. A story that is wide by design (Grid, Dither) opts out with parameters.overflowGate: false; an overlay story declares an openSelector so a portal that silently failed to open fails loud instead of measuring an empty root.

A gate, because the absence of one is why the gap shipped — a primitive with no shrink/wrap/truncate passes every unit test, because nothing ever renders it at phone width. Making "no horizontal overflow at 375px" a CI gate is the same move as story-coverage and the lint rails: the property the team cares about becomes a build failure on regression, not a style note a reviewer has to remember to check. The gate runs from @mythrun/web — it measures both the component stories and the app-shell screen stories — inside the frontend-check sweep.

Import boundary (R5)

Feature code composes the library's public surface only. A no-restricted-imports path-ban in @mythrun/web's config forbids feature code from importing the library's internal building blocks (radix-ui, CVA, tailwind-merge/clsx, the icon set) and from deep-importing @mythrun/ui's source — features import from the package root @mythrun/ui (plus React, client-core, i18n). Reaching for a raw primitive in a feature is a one-off element outside the system, which is un-portable. The no-ad-hoc-ui rail (MYT-79) is the companion: it bans raw <div>/className/style in feature code. The cross-feature-component boundary is deferred to MYT-83, since no feature directories exist yet.

Accessibility & token-contrast

The a11y gate is real assertions: each component test runs jest-axe plus explicit keyboard-interaction tests (Tab/Esc/Arrow/Enter/Space), a Modal focus-trap-and-return test, and a Toast/Banner live-region test. A token-level contrast check uses the generator's wcagContrast to verify the focus-ring and interactive-border 3:1 claims that axe does not check, and — since MYT-86 — a dark-accent regression guard (semantic-contrast.test.ts) that asserts paper-50 text on the dark --accent fill, and the split --accent-fg as link text and focus ring against the dark page, all clear AA, so a future palette nudge can't silently sink the accent below threshold. Every interactive control — icon-only ones included — carries a ≥44px hit target and an accessible name. MYT-97 added a second surface: standing up the Storybook test-runner activated the @storybook/addon-a11y axe pass as error on every component story, so an accessibility violation in a real-Chromium render now fails CI too (the addon stopped being merely a dev-time aid). The app-shell screen stories set a11y to off — their accessibility belongs to the flow tickets that build them — and the few Radix overlay specimens carry a documented per-story carve-out for one known aria-hidden-focus false-positive.

Operating this piece

Add a primitive to the library

  1. Add the contract type under frontend/client-core/src/contract/<name>.ts and re-export it (export type) from contract/index.ts.
  2. Create frontend/ui/src/components/<Name>/<Name>.tsx, typed (props: <Name>Props); export it (and its props type) from frontend/ui/src/index.ts.
  3. Style from token utilities only (bg-ember-600, never raw hex). Use cn() for class composition and CVA for variants.
  4. Add <Name>.stories.tsx following the doc template (autodocs, state matrix, a11y notes, do/don't). The story-coverage gate fails without it.
  5. Add <Name>.test.tsx with RTL behavior + jest-axe + the relevant keyboard tests.
  6. Run pnpm --filter @mythrun/ui typecheck lint lint:css test test:coverage story-coverage and pnpm --filter @mythrun/client-core typecheck lint test:coverage.
  7. Run the mobile-viewport sweep — pnpm --filter @mythrun/web build-storybook then pnpm --filter @mythrun/web test-storybook — so the new story passes the 375/1280 overflow gate. If the component is wide by design, opt the story out with parameters: { overflowGate: false } rather than papering over a real overflow.

Add or change a token

  1. For a static scale: edit frontend/client-core/src/tokens/scales.ts and mirror it into frontend/ui/src/styles/theme.css (the drift-guard test asserts they match).
  2. For a palette color: edit generate-palette.mjs, then pnpm --filter @mythrun/ui build to regenerate colors.generated.css + tokens.manifest.json; the round-trip test re-asserts idempotency.
  3. For a theme-aware semantic alias: edit semantic.css (the :root/.dark pair + the @theme inline surface), and extend the alias list in the token test.
  4. Record any contract-affecting change in frontend/client-core/CHANGELOG.md.

Integration points

This page is the design-system half of the Frontend foundation, which covers the same workspace plus the i18n layer, the no-ad-hoc-UI / no-hardcoded-string rails, and the token primer this page builds on.
