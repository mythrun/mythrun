Invites & party

How a campaign fills its table. The owner shares one short link from the campaign page; a friend opens it, sees who invited them, signs in through the app's existing guarded return path, accepts, and makes a character. Meanwhile the owner watches a roster that fills itself in — a party member finishing their character surfaces on the owner's screen without a reload. The frontend half of the shipped invite backend: the panel, the public join card, and the liveness plumbing.

How it fits together

The whole surface sits on the invite routes shipped with onboarding & invites (create / list / revoke / accept, the public preview, the server-side party cap of six). The client-core/api/invites.ts slice wraps them as the only sanctioned reach to that backend — six typed defineEndpoints. ensurePrimaryInvite is the sixth: a single idempotent PUT …/invites/primary that returns the campaign's one primary link, get-or-created atomically server-side (myth-y5c4q — it replaced a client-side list-then-create helper). The preview slice carries skipAuthRetry: true because the join route calls it pre-auth: it answers 200 or 404, never 401, so a signed-out lookup never spins the token-refresh path.

The owner's link — one primary invite, not a dashboard

On the campaign page the owner sees a CampaignInvitePanel — mounted only for the owner (creator === null; invite create/list/revoke are owner-only backend routes, so a non-owner sees nothing where the seam was). It resolves the primary share link on mount through ensurePrimaryInvite — one atomic PUT that returns the existing primary invite or mints one — then offers exactly three actions: copy, native share, and "replace link" (revoke, then re-mint). All the network calls and web globals live in this route wrapper; the mythrunUI InvitePanel is a pure presentational component taking resolved props and neutral callbacks. Terse lifecycle only — a single link, never an invite dashboard.

Native share is progressive enhancement over a clipboard copy — the panel offers a navigator.share button only where the platform has it (canWebShare()), and copy-to-clipboard everywhere. Both are web globals, so they live in the sanctioned platform/web/share.ts carve-out; the DOM-free layers never touch navigator. A user-cancelled share rejects with an AbortError, which is a non-event — the handler swallows it rather than surfacing a false error.
The mounted ref is reset on mount, not just cleared on unmount (the StrictMode fix) — the panel guards its async settles with a mounted ref so a late resolve can't setState after teardown. But under React StrictMode's dev mount → cleanup → remount, a ref that is only cleared in the cleanup stays false after the remount — and every subsequent settle is suppressed, so the panel sticks forever on "preparing your link…". Setting the ref back to true in the mount effect (mirroring useLiveRoster) is what lets the link resolve. A caught invite_cap_reached maps to a calm advisory line; any other failure to the transient error notice with a re-mint affordance.
Resolving the link is one atomic PUT, so the double-mount can't double-mint (myth-y5c4q) — the mounted-ref fix above stops a stale display; a separate StrictMode hazard was the network call itself. ensurePrimaryInvite used to be a client-side list-then-create: read the invites, find the primary, POST one if none. Under the dev double-mount (or two owner tabs) both passes saw no primary and both POSTed, minting two live join links on an access-control surface. It is now a single PUT …/invites/primary whose get-or-create is atomic on the server (a campaign-row lock plus a partial unique index — see the invite backend), so repeated calls return the same code and the race is closed where the guarantee actually lives, not by client timing.

Receiving an invite — the public join route

A share link resolves to /join/:code (${frontendBaseUrl}/join/${inviteCode}), a public route. JoinRoute previews the invite on mount and renders the JoinPreview card — the campaign name, who invited you, and one CTA. The preview endpoint distinguishes three outcomes, and the route forks on them: a revoked or expired code resolves 200 with valid: false (the card renders that in place, still showing the real campaign and owner); a code that never existed throws 404 → invalid, a terminal standalone notice where retry is pointless; a transient failure → error, a calm retry.

The CTA branches on whether the viewer is signed in. Signed in, it accepts inline — acceptInvite, then navigate: an already-a-member goes straight to the campaign, a fresh member to the join-summary and character creation. A failed accept maps through mapAcceptError to one of five calm arms — full (the party cap), revoked, gone, not-found, timeout — that the card surfaces without navigating.

Signed-out acceptance reuses the shipped guarded ?returnTo, introducing no new redirect target — the CTA for a signed-out viewer routes to signinReturnToJoin(code), which url-encodes the /join/:code path onto the existing ?returnTo parameter that the sign-in flow already validates through its isLocalPath guard and OAuth-state round-trip. That flow was built to reject open-redirect vectors; the invite hand-off must reuse it as-is rather than invent a second redirect mechanism. A crafted returnTo to an external host is rejected by the same guard that protects every other return path.
Inline accept, not a home-screen invite banner (a declared deviation) — the UX spec routes a signed-in acceptance through a banner on the home screen; this surface accepts inline on the join route instead and does not build the banner. The join link is the only entry path at launch, so the banner — a discoverability nicety for invites noticed while already browsing — is deferred rather than built speculatively.

The party fills itself in — live roster without a member-joined event

On the owner's party-staging surface the roster is live. useLiveRoster (client-core) replaces the earlier blind five-second poll with the real signal, and useForegroundRefetch (the web port) adds the browser-native fallbacks. A teammate finishing their character appears on the owner's screen without a reload, and the refetch swaps the roster in place — the surface never blinks back to a loading line mid-assembly.

There is no member-joined event, so the roster keys off character_creation_complete — no shipped transport carries a "a member just joined" event. The real liveness signal is the campaign status SSE's character_creation_complete, which fires per member at finalize on the stream the owner already holds. So useLiveRoster treats that event as a pure trigger — any member's completion refetches the whole progress read (the event carries no roster data). For the pre-finalize window (a member accepted but not yet finished), the roster also refetches on each entry into connected (the initial connect and every reconnect), on window focus, and on a visibility-gated slow poll that pauses on a backgrounded tab. A real member_joined event is a possible backend follow-up, not part of this surface.
gathering is a real teammate, distinct from an empty invite slot — the party-roster view-model maps a member who has joined but not yet started a character to a gathering status, not empty. empty is exclusively the synthetic "invite a friend" slot the staging surface appends when soloing; the view-model never emits it. Without the distinction, a genuine teammate who is still deciding would render as the invite-a-friend affordance — the roster would tell the owner to invite someone who is already there. Status reads as prose (owner-first ordering, viewer-marked), never a dot or chip, per the paper register.

The home-card party imprint

The hub card's foot imprint reflects the party assembling: members with a character are pigment Avatar seals, members still building are muted placeholder seals, both in one AvatarGroup so the overlap ring and the +N overflow span the combined cluster. Built seals lead, so a ready party reads first, and the seal cap drops still-building members before built ones. The placeholder Avatar variant — a muted hatch seal for a member without a character yet — is the one reusable primitive extension this surface added to the design system.

Operating this piece

Walk the invite → join → assemble flow (dev)

  1. As the owner, open a campaign and copy the primary link from the invite panel. "Replace link" revokes and re-mints — the old link then previews valid: false.
  2. In a second browser identity (signed out), open /join/:code. You should see the campaign and the inviter; the CTA sends you through sign-in and back to the same join route. Then accept — a fresh member lands on the join-summary and into character creation.
  3. Back on the owner's screen, finish the second character: the owner's roster updates on the character_creation_complete signal without a reload. Tab away and back to confirm the focus refetch.
  4. Probe the arms: a full party previews and then accepts to the full notice; a revoked code previews valid: false; a crafted returnTo to an external host is rejected at sign-in (the open-redirect guard).

Integration points

This surface wraps the invite backend (routes, the party cap, the public preview) and rides the status SSE for liveness through the shipped realtime transport. The signed-out hand-off reuses the OAuth sign-in flow's guarded returnTo. Accepting an invite leads into character creation, whose party-staging surface hosts the live roster and whose view-model owns the gathering status; the hub card renders the party imprint. Every visible element is a mythrunUI component (the InvitePanel, JoinPreview, and the Avatar placeholder variant) over the DOM-free client brain.

Client-core — the brain

Module Role
api/invites.ts The six invite slices (create / list / revoke / preview / accept / ensure-primary). ensurePrimaryInvite is now its own PUT …/invites/primary endpoint (atomic server-side get-or-create), not a composed list-then-create. The preview is public (skipAuthRetry).
invites/accept-arm.ts mapAcceptError / mapPreviewError (typed-code → arm) + signinReturnToJoin / joinPath.
invites/use-live-roster.ts The roster fetch driven by the status SSE (character_creation_complete + reconnect) → in-place progress swap.
contract/invite/types.ts InvitePanelProps / JoinPreviewProps + the AcceptArmKind / PreviewArmKind vocabularies.
character/party-roster-view-model.ts The progress read → roster rows; the gathering vs empty distinction.
