World colour identity

Every world gets a two-colour dither identity — the cover art its campaign cards wear on the home hub. A single Sonnet call at world creation picks the pair from a closed palette; deterministic code guarantees the two ends read as distinct; the pair is stored on the world and inherited by its campaigns.

How it fits together

The identity is a {from, to} pair of WorldColors — two design-token names the CoverDither renders as a top-to-bottom Bayer gradient. The pair is produced once, at world-gen time, by a dedicated stage in the world-generation pipeline, and never regenerated unless an operator forces it. It is plot-free and public-tier-safe: a decorative colour carries no enforced-ignorance concern, so it flows straight into the player-facing hub projection.

The closed palette — a shared runtime enum

A world may only be tinted with a WorldColor: one of 130 tokens — the full grid of 13 colour ramps (the neutral paper ground, the ember brand accent, and the 11 remaining brand pigments) across the 10-rung OKLCH luminance ladder (50 lightest … 900 darkest). Each name is a standard design token, so verdigris-200 resolves uniformly to var(--color-verdigris-200). The set is built programmatically from the ramps × steps grid and validated by a WorldColorPairSchema zod enum.

The enum lives in @mythrun/contract, not client-core — the colour set is the one contract the backend shares with the frontend: the colour stage constrains the LLM's output to it, the route validates a persisted pair against it, and the CoverDither resolves it. @mythrun/contract is the zod-only, React-free package the backend can import; client-core depends on React and cannot cross the wire. The semantic ramps (success/warning/danger/info) are deliberately excluded — a cover is decoration, never a UI-state signal, so a world can never accidentally wear an alarm colour. A client-core drift guard cross-checks every member against the real emitted design tokens, so the set can never name a --color-* that doesn't exist.

Sonnet picks, code guarantees contrast

The world_color stage runs one non-streaming Sonnet generateObject call, structurally constrained to WorldColorPairSchema — the model literally cannot emit an off-brand colour. It sees the world's vibe (name, concept, tone, themes, loaded by the preceding concept_intake stage) and the palette rendered as a hue list plus the ladder steps, and returns a {from, to} pair.

Sonnet, not Haiku — a blind taste-off (12 worlds each) showed Haiku picks serviceable hues but no contrast discipline and leans on neutral paper, while Sonnet's restrained, often-monochromatic taste won decisively. This is one call per world, ever — a negligible tier bump for a real jump in taste, and exactly the Zero-Framework-Cognition move: route the aesthetic judgment to the model that can actually make it, and keep application code out of the colour-picking business.

Code owns exactly one thing: the mechanical contrast floor. The two ends must sit at least six rungs apart on the ladder (rungsApart(from, to) ≥ 6). A full enumeration proved six rungs guarantees ~3.0:1 WCAG contrast in the worst hue combination — five rungs or fewer can dip to ~2.5 and the two dither fields stop reading as distinct. On a miss the stage re-rolls: it feeds the rejected pair back into the prompt so the model avoids it, up to three attempts.

Re-roll, never snap — when a pair fails the floor, the stage does not nudge a colour to a legal rung. That would put an aesthetic decision in application code. Instead it hands the rejection back to Sonnet and lets the model choose again — the aesthetic choice stays with the model the whole way. Both models obeyed the rung rule ~100% of the time in testing, so a passing pair lands on the first attempt in practice; the budget only guards a pathological run. If all three attempts somehow miss, the stage persists the most-separated of the model's own proposals (a best-of fallback) and logs a warning — mechanical selection among the LLM's picks, still not a snap, so a decorative colour choice can never fail world generation.

Dark mode — re-inking, not freezing

The stored pair is a light-mode identity. In dark mode the cover re-inks rather than glaring bright on a dark card: reInkPair drops the lighter end to its hue's smouldering mid-tone (-400) and deepens the darker end to near-black (-900), keeping each end's hue. The cover then reads as a dark object with the colour glowing. This is a pure function of the stored pair — no second LLM call, no second stored value — and the CoverDither applies it in CSS so the theme flips with no re-render.

Stored on the world, backfilled for the rest

Migration 030 adds two nullable TEXT columns to worlds — color_from and color_to. Null means "not generated yet" and renders the hub's muted paper ghost band; the WorldColor enum is enforced at the application and contract layers plus the backfill, not as a DB CHECK, so the column doesn't pin the enum a second time. The stage persists through worlds.setColorPair, an idempotent SET (not a delta), inside a short writes-only transaction after the LLM call completes.

Backfill is mandatory, not a fallback — every world that already reached complete before the stage existed gets a real pair from the same stage. The only no-pair render path is the still-generating window (the ghost band). The alternative — letting an uncoloured world fall back to a default cover at render time — is exactly the silent-stub-fallback the codebase forbids: it would hide missing data behind a plausible-looking default. A test asserts no complete/played world renders a default, and the backfill (below) is the operational half of that guarantee.

Operating this piece

Backfill world colours

  1. The script re-runs the same colour stage (real Sonnet spend) against existing worlds: pnpm world:color-backfill --world <id> colours one world; --all colours every complete world whose pair is still null (the safe, incremental default, re-runnable).
  2. --all --force widens the selection to every complete world and re-rolls the pair — a deliberate full re-colour of the corpus and a real spend event. Run it knowingly, not casually.
  3. Each per-world write goes through the canonical stage runner (generateObject → contrast re-roll → setColorPair), so a backfilled world is indistinguishable from a freshly generated one. The script logs one JSON line per world (id + token cost) and exits non-zero on failure.
  4. After a schema/stage change reaches staging, run --all once so no complete world is left on the ghost band — this is the operational side of the no-default guarantee.

Integration points

The colour stage is one step of the world-gen pipeline, ordered right after concept_intake. The stored pair is surfaced to the client through the campaign hub payload (GET /api/campaigns/mine), which validates it against the same contract before it crosses the wire. The consumer is the CoverDither primitive, which resolves each token to a CSS variable and applies the dark-mode re-ink; the campaign hub screen composes it as each card's cover art.
