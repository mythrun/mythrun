Guided create

The path a player takes to turn three things they love into a campaign: name three favourites, watch a world brief write itself, then read it, optionally rework it once, and commit. Every step before the commit is non-charging — the concept lives in Redis under an opaque preview id and the credit is charged only when the player presses Begin.

How it fits together

Campaign creation forks two ways. Start from an idea is freeform prose the player writes themselves; build from what you love is the guided path, where a Sonnet synthesizer invents an original concept from three media-picks. This page owns the guided path and its preview machinery — the synthesizer, the streamed brief, the rework, and the Redis holding pen the concept waits in. The freeform fork is a passthrough: it carries the player's own prose straight to the commit endpoint, where it is gated for the first and only time (see World gen for the commit-side flow both forks share).

Preview, then commit — because world-gen is expensive — committing kicks off roughly ten minutes of multi-stage Sonnet world generation and debits a credit. So the guided path gives the player a concept to read before they spend anything: synthesize, look, change their mind once, and only then commit. The whole preview loop is deliberately cheap enough to abandon.

The screen state machine

The SPA flow (campaign-new.tsx) is a thin screen state machine over a back-history stack. fork is the permanent root; guided collects the three picks; synthesizing renders the brief as it streams; preview shows the settled concept and its actions; rejection is the calm dead-end. Each screen is pure presentation firing neutral intents — it never navigates itself. The controller owns the carried payloads (the live stream handle, the parked preview, the rejection reason) and maps each intent to the next screen.

The synthesizing beat swaps, it doesn't push — when the brief finishes the controller replaces the top of the history with preview (or rejection) rather than pushing onto it. So a ← back from the preview lands on the guided picks, not on a half-written brief the player can never return to meaningfully. The brief-writing beat is a transition, not a place.

The three picks round-trip through sessionStorage (the client-core draft seam), so a mid-flow reload re-prefills them. The draft deliberately survives synthesize → preview → rework and even a preview that ages out — a start over or a 410 restart re-prefills the same picks. Only an actual commit clears it, exactly once, from the controller.

Synthesize — streamed and non-charging

Pressing find my world opens a one-shot stream against POST /api/campaigns/synthesize-preview/stream. The guided screen owns the open, so every pre-stream failure stays a calm inline notice right where the player can act on it; the moment the 200 head arrives it hands the live stream to the controller and advances to synthesizing, which renders the arriving prose (a paper-register streaming block, no spinner). The server runs the identical guard chain, then hijacks the response into SSE: delta* frames carry the brief's prose, and exactly one terminal frame (complete | rejected | error) closes it. A synchronous twin, POST /api/campaigns/synthesize-preview, returns the whole concept as a single 201 — the dev-tool panel and any non-streaming client drive that one.

Underneath, synthesizeConcept is one Sonnet call at temperature 0.9 through the canonical generateObject wrapper, producing a concept string and an intentSummary (aesthetics, themes, and an internal sourcesInternal list). The streamed variant is its structural twin over streamObject — same prompt, schema, and repair chain — deriving prose deltas from the growing concept field. The validated output, not the streamed text, is authoritative: a post-stream schema repair can rewrite what the player watched arrive, so the terminal frame's concept wins.

The concept has a floor but no ceiling — the synthesizer schema puts a .min(50) on the concept (a too-short brief is malformed) but deliberately no .max(). A max ceiling would terminal-fail an otherwise good over-length generation instead of accepting it, and the concept's destination — worlds.concept — is a bare TEXT column with no length check, so nothing downstream needs a mirror. LLM prose gets a floor, never a cap.
The stream is not the reconnecting SSE client — synthesis is a non-idempotent POST: a silent reconnect would re-run Sonnet and bill a second brief. So startSynthesisStream is its own small client (a zustand store, the StreamingFetch seam — EventSource is banned), and a dropped connection is a terminal failed{stream_interrupted} that keeps the halted partial text on the page, never a retry. The player retries deliberately, from the guided picks. This is why it doesn't reuse the reconnecting transport the play and world-gen flows run on.

The input gate and rejection

Whatever the synthesizer produces is judged by the input gate — one Sonnet call over three axes (does it fit the SRD, is it a thinly-veiled franchise clone, is it inappropriate). The gate receives sourcesInternal too, which closes a prompt-injection path: the synthesizer's own note of what it drew from is visible to the judge but never echoed to the player and never fed to a later stage. An allow verdict parks the concept; a reject becomes a concept_rejected outcome (a 422 on the synchronous route, a terminal rejected frame on the stream — identical payloads).

The player sees a message, never the reasoning — a rejection carries a server-authored rejectionMessage and, on the guided path, the synthesizedConcept that was judged (so the player can adopt it as freeform and adjust it themselves). The model's raw axis reasoning is logged server-side only — it never reaches the response body. The rejection screen falls back to a calm generic line when the model declined to author a message.

content_filtered is a distinct terminal: Anthropic's content policy blocked the prompt, so retrying the same text hits the same filter. That screen offers no rework or edit — only start over.

Rework — one change, gate-pass-only

A parked preview buys the player exactly one change. Ask for one change reveals a note field; POST /api/campaigns/preview/:previewId/rework feeds the parked concept and the note to reviseConcept (again one Sonnet call, same output contract), re-runs the input gate, and — only on a pass — overwrites the stored preview, bumping reworkCount from 0 to 1. A second attempt is a 409. The change note is capped at 800 characters, the same bound the synthesizer puts on a pick's "why I like it": a note is a sentence or two, not an essay.

A rejected rework leaves the budget intact — nothing is persisted until the gate passes. If the revised concept is rejected, the original gated preview and reworkCount: 0 survive untouched — the player still holds their one budgeted change. The rejection still increments the rejection-storm counter, so a loop of rejecting reworks trips the cooldown on the next request rather than burning Sonnet unbounded.

Where the concept lives

Between synthesis and commit the concept sits in Redis, not Postgres — a PreviewRecord (the concept, the intent summary, the rework count) under the key {env}:{region}:campaign-preview:{userId}:{previewId} with a 30-minute TTL. An abandoned preview reaps itself; nothing accumulates. The commit reads the record but doesn't delete it — the TTL is the only cleanup.

The user id is baked into the key — that is the whole IDOR defence — a preview is keyed by the authenticated user, never a client-supplied id. So a stolen or guessed previewId read under a different user simply misses the key and returns the uniform 410 (preview_expired) — the same response a genuinely expired preview gives. There is no surface where user B reads user A's concept.

Commit — from preview to world-gen

Begin calls the shared create endpoint with a wrapped { mode: 'guided', previewId } body. The commit loads the already-gated preview by (authenticated user, previewId) and re-uses its concept verbatim: no re-synthesis, no re-gate. The concept was synthesized and gated during preview and is entirely server-authored — the client only ever held the opaque previewId — so re-gating would burn Sonnet on an input the caller could not have altered. From there the commit debits one world_gen credit inside an advisory-locked transaction and enqueues world generation; that half of the story is World gen. A commit whose preview has aged out returns a 410, and the flow restarts at the guided picks (which the draft re-prefills).

Cost and rate posture

Preview and rework never charge a credit, but they do burn Sonnet, so the same cheap guards run before any model call on every preview route — synchronous, streamed, and rework alike. In order: a Zod body parse (guided-only, exactly three picks), a per-user rate limit of five requests a minute, a read-only rejection-storm cooldown peek, and a non-charging credit-balance peek. Only then does the synthesizer fire. Because the guards run before the SSE hijack, a trip on the streamed route is a plain JSON status the client handles exactly like the synchronous endpoint's errors.

A zero-credit user is stopped before the first token — the credit peek is a non-charging balance check, and it runs before any LLM call even though preview itself doesn't debit. There's no point letting someone synthesize and rework a concept they can never afford to commit; blocking at the peek keeps a zero-balance account from driving Sonnet cost at all.
The storm counter is checked at the start, incremented at the end — the rejection-storm counter increments on each gate rejection but is read at the start of the next request. So a request that trips the threshold (more than three rejections in an hour) still gets its own answer; the following request is the one that 429s into the cooldown. It's the cheapest possible rejection — no LLM call — for a user who has been repeatedly rejected.

Disconnects are handled as cost, not just correctness: the streamed route's SSE sink aborts the Sonnet stream on client close, and the SPA controller closes the stream handle on back-out, replacement, and unmount. A closed tab stops the token burn instead of generating into the void.

Integration points

The streamed synthesis rides the SSE framing described on Realtime transport and Pipeline status, but deliberately as its own one-shot client rather than the reconnecting one. The commit endpoint, the credit debit, and the input gate on the freeform fork all belong to World gen, which this flow hands off to. The parked concept becomes worlds.concept; the campaign it seeds surfaces on the campaign hub. The synchronous preview route is one of the dev tool's targets. The wire union for the stream is SynthesizeStreamEvent in frontend/contract/src/events/synthesize-stream.ts.

Appendix: the preview routes

Route Charges? Terminal outcomes
POST /api/campaigns/synthesize-preview No 201 { previewId, concept } · 422 concept_rejected · 400 / 403 / 429
POST /api/campaigns/synthesize-preview/stream No delta* → complete | rejected | error; guard trips are pre-hijack JSON (400 / 403 / 429)
POST /api/campaigns/preview/:previewId/rework No 200 { previewId, concept } · 409 rework_exhausted · 410 preview_expired · 422 concept_rejected
POST /api/campaigns (guided commit) 1 world_gen 201 { campaignId } · 410 preview_expired — see World gen

Shared bounds and constants: picks are exactly three, each a title (1–200 chars) and a reason (1–800); a rework note is 1–800 chars; the preview TTL is 30 minutes; the rate limit is five requests a minute per user per route; the rejection-storm cooldown trips after more than three gate rejections in an hour.
