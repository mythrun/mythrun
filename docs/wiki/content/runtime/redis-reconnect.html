Redis reconnection

The one reconnection strategy every long-lived Redis client shares, and the split that keeps it honest: at runtime a client reconnects forever after an ElastiCache blip so a single failover no longer severs BullMQ and realtime for the task's lifetime; at boot the same client still fails loud so a genuine misconfiguration crash-loops instead of retrying into the void.

How it fits together

Every long-lived ioredis client in the backend — the API's request-path client, the worker's BullMQ connection, and the dedicated subscriber duplicates the SSE pipeline subscriber and the WS session hub mint — is constructed with a retryStrategy: the closure ioredis calls to decide how long to wait before the next reconnect attempt, and whether to attempt one at all. Returning null from that closure means "give up." A single shared factory, makeReconnectStrategy(label, logger) in backend/src/redis/reconnect-strategy.ts, now backs all of them.

The bug this page exists to prevent — the runtime clients used to be built with retryStrategy: () => null: no reconnection, ever. One ElastiCache blip or failover permanently severed BullMQ and realtime for every ECS task until a manual rollover — a real stalled generation in dev traced back to exactly this. The shared strategy reconnects with bounded exponential backoff and jitter and never gives up, so transient loss self-heals.

The strategy caps the delay, not the attempt count. The backoff is min(200ms · 2attempt−1, 10s) — doubling from a 200 ms base up to a 10 second ceiling — with AWS "equal jitter" applied on top: half the delay is kept as a floor and the other half randomized, so the result lands in [cap/2, cap]. A worker keeps trying indefinitely; only the wait between tries is bounded. Every attempt logs a warn line (event: 'redis.reconnecting') carrying the client's label and the attempt number, so an outage is visible in CloudWatch rather than silent.

Equal jitter, not raw exponential backoff — a fleet of tasks that all lost the same ElastiCache node would otherwise reconnect in lockstep and thundering-herd the recovering node. Keeping half the delay as a floor avoids a herd at zero; randomizing the other half spreads the retries. Capping the delay (not the attempts) is the deliberate choice for a background system: a worker that can't reach Redis is useless anyway, so retrying forever at a 10 second ceiling costs almost nothing and means recovery is automatic the instant the node returns.

The config-vs-transient split

A never-null retry strategy raises an obvious question: if a client reconnects forever, how does a genuine misconfiguration — a wrong host, wrong port, or bad auth — ever surface? It would just reconnect forever too. The answer is that reconnection is the runtime policy; the boot gate is separate and still fails loud. The two client profiles reach that fail-loud guarantee by different routes.

The API / realtime client (createRedisClient) sets enableOfflineQueue: false — a command issued while disconnected rejects promptly rather than buffering. That is deliberate for the request path (a realtime PUBLISH during an outage should drop fast, not queue a stale write), and it doubles as the boot guarantee: the boot-probe ping() rejects promptly while disconnected, so a wrong host surfaces at startup even though the strategy would otherwise reconnect forever.

The BullMQ client (createBullmqRedisClient) can't do that — BullMQ requires maxRetriesPerRequest: null and an enabled offline queue, so a probe ping() against an unreachable Redis buffers and never rejects. It would hang the boot gate forever. So its fail-loud guarantee comes from backend/src/boot/wait-for.ts instead: waitFor races each probe against a per-attempt timeout (PROBE_ATTEMPT_TIMEOUT_MS, 3 seconds) over a bounded retry schedule ([200, 500, 1000, 2000] ms, five attempts total). A hung probe loses the race, the attempts exhaust, and the process exits 1 — a genuine misconfig crash-loops.

Why the timeout is 3 seconds and swallows the late rejection — the per-attempt timeout has to be generous enough that a healthy-but-slow cloud connect (an ElastiCache TLS handshake, typically under a second) clears in a single attempt, yet short enough that a wrong port fails the whole gate quickly. A probe that loses the race can still reject later — ioredis flushing its buffered command on quit — so waitFor pre-attaches a no-op catch to that inflight promise; otherwise the late rejection would surface as an unhandled rejection after the timeout already won. Every boot probe against a BullMQ-profile client MUST go through waitFor for this reason (the ioredis/BullMQ ping-race).
Verified empirically, not just reasoned — the "never-null strategy still fails loud at boot" claim was drilled, not assumed: a docker compose restart of both Redis instances had every client go reconnecting → ready with the four workers resuming and a stalled job reclaimed, while a wrong-port boot exited 1 loud. The split holds only because the two profiles reach fail-loud by two different mechanisms; a single assumption covering both would have been wrong.

Lifecycle logging

Each client also carries lifecycle listeners (attachRedisLifecycleLogging) so an outage and its recovery read cleanly in the logs. The signal budget is deliberate:

  • redis.reconnecting (warn, from the strategy) — one per attempt, with the client label and attempt number. This is the loud, visible outage signal.
  • redis.ready (info) — the connection came up, initially or after a reconnect. This is the recovery signal.
  • redis.end (info, not error) — the connection closed. With a never-null strategy this fires only on an intentional quit()/disconnect() (graceful shutdown), never a give-up, so logging it at error would false-alarm on every deploy.
  • redis.error (debug, not warn) — ioredis emits one error per failed connect attempt during an outage. Logging those at warn would double the noise the strategy's per-attempt line already carries, so the raw errors drop to debug; the error listener's real job is to stop a transient connection error from surfacing as an unhandled "Unhandled error event."

Every client passes its own label — api-redis-realtime, worker-redis-batch, session-hub, pipeline-subscriber:pipeline, session-turn-queue-events, and so on — so a reconnect line names exactly which connection blipped. The subscriber duplicates and the QueueEvents connection each get their own label rather than inheriting the parent's, so an inherited duplicate can't muddy the outage forensics.

Operating this piece

An ElastiCache blip — what self-heals and what pages

  1. The outage announces itself as a burst of warn lines. In CloudWatch Logs Insights: fields @timestamp, label, attempt, delayMs | filter event = 'redis.reconnecting' | sort @timestamp. A climbing attempt on a stable set of labels is a transient blip in progress — the expected, self-healing shape.
  2. Recovery is the matching redis.ready line per label: filter event = 'redis.ready'. Once every blipped label has a redis.ready after its last redis.reconnecting, the fleet has healed — no rollover needed. The BullMQ workers resume and any job that stalled during the gap is reclaimed by BullMQ's stall recovery.
  3. On the realtime side, a blip is not fully transparent to attached clients: the SSE subscriber and the WS hub evict their attached sinks/sockets with redis-resync-required on the post-blip ready, because messages published during the gap may have been missed. Clients reconnect and re-fetch a fresh snapshot or replay — that eviction is expected during a blip, not a bug.
  4. What SHOULD page: a label that logs redis.reconnecting and never reaches redis.ready — a sustained inability to reconnect (a security-group change, a decommissioned node, an auth rotation gone wrong), not a transient failover. That is the case the self-healing loop can't fix on its own.

Diagnose a boot that hangs instead of crashing

  1. A misconfigured Redis URL should crash-loop the task, not hang it. If a task is stuck "starting," check the boot logs for a waitFor(...): exhausted error — that is the fail-loud path firing correctly (the process exits 1 and ECS restarts it, surfacing the misconfig as a crash loop the deploy notices).
  2. If instead the task hangs with no waitFor error, the suspect is a boot probe that bypassed waitFor and called ping() directly on a BullMQ-profile client — that command buffers forever against an unreachable Redis. Every boot probe against a BullMQ-profile connection must go through waitFor so the per-attempt timeout can bound it.
  3. To rehearse the whole loop locally, docker compose restart the Redis containers while pnpm dev and the worker are running, and watch every client go redis.reconnecting → redis.ready. To rehearse the fail-loud path, point a Redis URL at a wrong port and confirm the process exits 1.

Integration points

The BullMQ client is the connection every worker queue and the QueueEvents('session-turn') subscriber ride; its boot ping goes through waitFor. The API / realtime client is what the SSE pipeline subscriber and the WS session hub duplicate() for their dedicated PSUBSCRIBE connections — each duplicate overrides the retry options but threads this same shared strategy under its own label, and each drives a redis-resync-required teardown on the post-blip ready. The redisKeyPrefix envelope those channels use is covered on access control & WS ticket; the ElastiCache cluster itself is provisioned by the data plane.

Appendix: the reconnect surface

Strategy constants

Constant Value Meaning
REDIS_RECONNECT_BASE_MS 200 First-attempt backoff before jitter.
REDIS_RECONNECT_CAP_MS 10 000 Maximum backoff delay. The DELAY is capped; the attempt count never is.
PROBE_ATTEMPT_TIMEOUT_MS 3 000 Per-attempt boot-probe timeout in wait-for.ts; bounds a buffered/hung ping.
RETRY_DELAYS_MS [200, 500, 1000, 2000] Boot-gate backoff schedule — five probe attempts total, then exit 1.

Client profiles

Factory Profile Boot fail-loud via
createRedisClient maxRetriesPerRequest: 1, enableOfflineQueue: false (fast-fail commands) + shared strategy The probe ping() rejects promptly while disconnected (offline queue off).
createBullmqRedisClient maxRetriesPerRequest: null, offline queue on (BullMQ requirement) + shared strategy waitFor's per-attempt probe timeout — the buffered ping never rejects on its own.
