Character integration

When the owner finalizes character creation, a single Opus call sees the whole party plus the whole world plus the owner's free-text notes, and weaves every PC into the world in one structured response — then a single Postgres transaction lands the new PC entities, their facts and relationships (including PC↔PC edges), and flips the campaign live.

How it fits together

Character integration is phase 5 of the campaign lifecycle — the fan-in step that follows the per-player parallel character creation in phase 4. The flow has four moving pieces along the diagram: an owner trigger at the API, a single BullMQ job, a worker handler that does the LLM work outside the database, and a single transaction that lands every write at once. The campaign transitions from status='setup' to status='active' as the last write in that transaction, which is also how the SSE surface learns the pipeline is done.

Owner finalize

The owner POSTs to /api/campaigns/:campaignId/finalize-character-creation with an optional pre_integration_notes field (up to 4000 chars of free text — "Theo and Mira are siblings; Garrett owes the dwarf cleric a debt"). The route runs a transactional UPDATE that writes the notes and gates on WHERE status = 'setup' — a second click after the campaign has already gone active returns 409 not_in_setup without touching the queue. A second gate requires at least one character_concepts row with status='completed' so the integration job never runs against an empty party. On success the route enqueues one character-integration job with the deterministic jobId ci-{campaignId} on the campaign-setup queue and returns 202.

Deterministic jobId, queue-level dedup — BullMQ dedups on duplicate jobIds, so a frantic double-click from the owner is a no-op at the queue layer even before the status='setup' guard catches the second route call. Belt and suspenders, because the integration job is expensive (a 30–120s Opus call) and starting two of them on the same campaign would corrupt the world.

One LLM call, not N

The worker side of the diagram is one BullMQ job that walks one Opus call against one schema. The handler loads the party (every character_concepts row joined with its character sheet and the user's display name), loads the campaign's pre-integration notes and starting situation prose, and loads the world inventory through repo.worldInventory.load, rendered for the prompt by the shared world-dump.ts module. Those four inputs render into a single prompt: every PC's identity and sheet alongside every existing world entity's UUID, name, prose kernel, facts, and outgoing relationships. Opus returns one IntegrationResult covering every PC at once.

Why one Opus call, not N parallel per-player calls — the prototype shipped per-player integration. The structural problem was coherence: if four players each get their own pass, two of them can quietly contradict each other (one PC's backstory says they killed the bandit leader; another's says they're working for him), and the only fix is a post-pass coherence check that hauls the same context back into a fifth LLM call to reconcile. Collapsing visibility into the single pass replaces both calls. PC↔PC relationships also become a first-class output — the model emits "Mira → Theo (sister)" once and the worker mirrors it — instead of two per-player passes each hallucinating their half.

LLM outside the transaction, writes inside it

The Opus call happens before any BEGIN. The handler runs it against the raw pool, not against an open PoolClient: a 30–120s call would otherwise tie up one of the pool's connections for its full duration, and at the worker's BullMQ concurrency of 5 a slow campaign would exhaust the pool inside one minute. Once Opus returns and worker-side validation passes (see below), the handler opens one client, runs BEGIN, walks four ordered passes against it, and runs COMMIT. The four passes share one transaction because the entity IDs minted in pass 1 are foreign-key referenced by passes 2 through 4 — splitting them would leak partial parties on a mid-write failure.

LLM outside the transaction — Anthropic's tail latency on a multi-PC structured generation runs into the upper minutes. The pg pool is sized for short-lived OLTP queries, not Anthropic round-trips. Holding a connection for an Opus call would block other workers (and other API requests sharing the pool) on every concurrent integration. The trade is a wider "did the world change underneath us?" window between read and write, which is acceptable here: the world is stable in setup, the route's status='setup' guard prevents two concurrent integrations, and any unknown-UUID drift in the LLM output is dropped at validation time.

Worker-side validation and PC↔PC mirroring

The handler runs three classes of check on the LLM output before any database write. The first two are hard invariants that, if violated, raise LlmStructuredOutputError and let the AI-SDK wrapper's repair strategy take a second swing:

  • Cardinality: characters.length === party.length — the LLM must emit exactly one PC row per party member, no more, no less.
  • Identity: the set of emitted userId values equals the input party's set — no duplicates, no unknown players.

The third class is softer: any relationship targetId (UUID into entities) or targetUserId (UUID into users) the LLM emitted that doesn't match the loaded inventory is silently dropped and a console.warn is logged. Same for newFacts entries that target an unknown entity.

Why PC↔PC edges are emitted once and mirrored worker-side — the LLM is asked to emit one canonical edge per PC pair (the prompt explicitly says so). The realistic failure mode isn't "the LLM emits zero edges between two PCs the owner described as siblings"; it's "the LLM emits one side and forgets the other." A one-canonical-emission + worker-side mirror is robust to that. Asking for both sides and validating symmetry would just turn a tolerable asymmetry into a hard LlmStructuredOutputError retry loop.
Free LLM prose is validated min-only — no length cap — the proseKernel, fact content, and relationship description fields carry a substance floor (min(...)) but no max(...). The repair strategy fixes malformed JSON, not valid-but-long prose, so a length cap would terminal-fail the stage on output that is structurally fine — wasting the tokens already spent generating it. MYT-64's first real-Opus run surfaced exactly this: a ~1400-char kernel hit the old max(1200) and failed the whole integration. The fix dropped max() from every free-prose field across the LLM-output schemas; caps remain only on short labels, array element counts, numerics, and fields that mirror a DB CHECK.

The proseKernel is prose a player eventually reads, so the template pulls in the shared house-voice fragment through the prompt loader's include directive — the same one the world-gen stages, the session prep, and the live DM carry. A PC's kernel written in a different register than the world around it is a seam the player feels without being able to name.

The single transaction

Writes happen in four passes inside one transaction. Pass 1 inserts an entities row per PC (entity_type='pc', access_level='known'), disambiguating names against the world's existing entities and against other PCs in the same batch — collisions get a (userid-fragment) suffix. The pass builds a userId → entityId map that passes 2–4 reuse. Pass 2 walks each PC: inserts the prose kernel, the per-PC facts (with narrative_status='undelivered'), and the relationships — PC↔world edges resolve through targetId directly, PC↔PC edges resolve through the userId map. Pass 3 writes the newFacts entries onto existing world entities. Pass 4 backfills characters.entity_id, flips every character_concepts.status to 'integrated', and flips campaigns.status to 'active'. Only after COMMIT does the processor mark pipeline_runs completed and publish the stage-completed SSE event. One non-fatal post-pass then runs: because pass 3 inserts new PC-backstory facts onto existing world NPCs after world-gen's embed stage already ran, those rows ship un-embedded — so the processor re-embeds the world's NULL-embedding rows (see world-store retrieval) to keep it searchable. The integration is already committed and stage-completed by then, so a Voyage or DB error in the post-pass logs and is swallowed — it never flips the completed stage to failed.

Status flip is the last write inside the transaction — the SSE phase: complete signal is derived (not published directly): the derive-phase.ts taxonomy reads campaigns.status='active' and returns 'complete'. Putting the flip last in the transaction means subscribers cannot ever observe status='active' against a partial party; if anything earlier in the transaction fails, ROLLBACK takes the status flip with it.

Operating this piece

Re-run a failed integration

  1. Check the failure mode in pipeline_runs:

    SELECT status, error, cost_usd, completed_at
  FROM pipeline_runs
 WHERE campaign_id = '<id>'
   AND stage = 'character_integration'
   AND user_id IS NULL;

    A row with status='failed' and a character_creation_cost_cap_exceeded error means the pre-flight gate fired — raise settings.character_creation_cost_cap_usd and restart the worker (the cap is read at boot, not per job).

  2. The owner re-POSTs /api/campaigns/:campaignId/finalize-character-creation with the same body. The route's status='setup' guard still admits — the integration handler ran but failed, so the campaign is still in setup. The atomic claim re-arms from the prior failed row (the (campaign_id, stage, user_id IS NULL) uniqueness allows replacement on a non-completed prior).

  3. Watch the new attempt on the SSE stream (GET /api/campaigns/:campaignId/status/stream). A clean run ends with one stage-completed event and a phase: complete derived snapshot.

Check the cost-cap status

  1. Sum the character-creation spend so far for a campaign:

    SELECT COALESCE(SUM(cost_usd), 0)::float8 AS spent_usd
  FROM pipeline_runs
 WHERE campaign_id = '<id>'
   AND status = 'completed'
   AND stage IN (
     'character_concept',
     'character_sheet',
     'character_integration'
   );

    The query is the same as sumCharacterCreationStageCosts in cost-cap.ts — widened in MYT-54 to cover the campaign-scoped integration row alongside the per-player character-creation rows so all three roll up into the same budget.

  2. Compare against the active cap: SELECT value FROM settings WHERE key = 'character_creation_cost_cap_usd'. Cap changes need a worker restart to take effect.

Integration points

Upstream: character creation runs the per-player pipeline; integration consumes its concept_output JSONB column (the CharacterConceptOutput payload added in MYT-54 so the integration pass can read each PC's narrative pieces — backstory, personality traits — without re-querying the per-player pipeline's intermediate state). The MYT-53 pipeline ends at character_sheet; the prior per-player character_integration stage is retired.

Sideways: the world inventory rendered into the prompt comes from backend/src/llm/prep/world-dump.ts, shared with the coherence pass in world gen — same inventory shape, same deterministic textual rendering, two consumers.

Downstream: the pipeline-status surface picks up the campaign's new state without any direct publish — the POSTCREATION_STAGES taxonomy in derive-phase.ts includes character_integration, and the campaigns.status='active' flip drives the phase: 'complete' verdict that subscribers see.

Appendix: inputs and outputs

IntegrationResultSchema

The single Zod schema the Opus call validates against (defined in backend/src/llm/schemas/character-integration.ts):

  • characters — array of 1–8 PCIntegration:
    • userId, displayName — echo of the input party member.
    • entity — { name, proseKernel } (a 1–2 paragraph PC summary). The kernel carries a substance floor (min(80)) but no upper bound — free LLM prose is validated min-only.
    • facts — 1–10 fact rows, each { content, tags[], aboutEntityId } where aboutEntityId is either a world entity UUID or null for a self-fact.
    • relationships — 0–10 discriminated-union edges by targetKind: 'npc' | 'faction' | 'location' carry targetId (entity UUID); 'pc' carries targetUserId (the other player's UUID into users).
  • newFacts — optional array of facts to attach to existing world entities (NPCs, factions, locations) where integrating a PC requires it (e.g. "this PC knew NPC X from their backstory"). Each row: { entityId, content, tags[] }.

Lifecycle of character_concepts.status

Status Set by
submitted POST /characters (member writes concept + grounding text).
processing POST /characters — the member's own submit atomically flips the row to processing (committed alongside a character_concept recovery row) and enqueues the per-player job right after that transaction commits (no separate owner trigger).
completed Per-player character-creation pipeline finished — PC sheet exists, no entity yet.
failed Per-player pipeline failed terminally; member can re-POST to reset to submitted.
integrated MYT-54 character-integration handler's pass 4 — PC has an entity row, facts, relationships, and the campaign is now active.

Cost-cap settings key

The cap value is read from settings.character_creation_cost_cap_usd by readCharacterCreationCostCap. The cap covers the per-player character_concept and character_sheet rows plus the campaign-scoped character_integration row — one budget across all character-creation spend. The integration handler's pre-flight estimator is deliberately pessimistic (~1200 output tokens per PC + per-PC prompt overhead + world dump) so a near-cap campaign fires the gate BEFORE the LLM call rather than mid-stream. Cap changes take effect on worker restart.

Schema additions (migration 018)

  • campaigns.pre_integration_notes TEXT — owner-provided free-text relationship notes, ≤4000 chars, NULL when omitted.
  • character_concepts.concept_output JSONB — persists the structured CharacterConceptOutput from MYT-53's per-player stage 2 so the integration pass can read each PC's narrative pieces. JSONB so the shape can evolve.
  • character_concepts.status CHECK extended to include 'integrated'.
  • No new partial unique index — migration 001's idx_pipeline_runs_unique on (COALESCE(world_id, campaign_id), stage, COALESCE(user_id, sentinel)) already enforces uniqueness for the campaign-scoped row with NULL user_id.
