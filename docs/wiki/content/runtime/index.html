Backend

The Node.js server the cognitive tiers will live in. A pnpm workspace, a Fastify app with a single /health endpoint, and a multi-stage Dockerfile that packages it into a minimal runtime image.

How it fits together

The repository is a pnpm monorepo. The root package.json pins pnpm@10.30.3 via packageManager and node >= 24 via engines; pnpm-workspace.yaml declares two workspace packages today — backend/ and docs/wiki/ — and the root exposes the single-word verbs (pnpm test, pnpm typecheck, pnpm lint, pnpm build) that fan out across every workspace via pnpm -r.

Monorepo from day one, not a polyrepo — the backend, the wiki, and every future piece (prep worker, frontend, Terraform-companion tools) share a lockfile, a TypeScript version, and a single CI run. A second repo would double tooling for no real isolation: all of these deploy together.

The backend/ workspace is @mythrun/backend. It depends on Fastify and nothing else in production, with tsx, typescript, and vitest as dev dependencies. The source tree is intentionally shallow right now: two files under src/. app.ts exports buildApp() (a pure factory that returns a Fastify instance with GET /health registered) plus createShutdown(app) (a pure function that returns a signal handler). Nothing in app.ts has side effects on import — no listener, no signal hooks. server.ts is the thin entrypoint: it calls buildApp(), await app.listen on PORT (default 3000) bound to 0.0.0.0, and then registers the createShutdown handler against SIGTERM and SIGINT.

Factory and shutdown live in app.ts, listen in server.ts — Fastify's inject method needs a built-but-not-listening app, and the shutdown handler needs to be unit-testable against a spy on process.exit. Isolating the listen + signal wiring in a separate file means importing app.ts from tests has zero side effects, and the signal handlers are a pure function that takes a Fastify instance and returns a handler — testable in isolation via vi.spyOn(process, 'exit').
SIGTERM handling matters on ECS — ECS sends SIGTERM when it deregisters a task for any reason (rolling deploy, service scale-down, capacity rebalance). Without a handler, Node exits on the default kernel disposition and in-flight requests get truncated. The handler calls app.close() (which stops accepting connections and waits for in-flight requests to drain) before process.exit(0); the 120-second stopTimeout on the task definition gives LLM calls time to finish before ECS sends SIGKILL.

TypeScript and lint

The backend's tsconfig.json turns on every strictness knob that changes code — strict, noUncheckedIndexedAccess, exactOptionalPropertyTypes — with ES2023/NodeNext module resolution. tsconfig.build.json extends it and excludes __tests__/ so the built dist/ carries only runtime code.

ESLint sits at the repo root and runs against every workspace. The config composes typescript-eslint's strict + stylistic type-checked presets, adds a repo-specific ban on default exports (no-restricted-syntax), caps modules at 400 lines and functions at 50, and forbids any and non-null assertions outright. eslint-config-prettier is applied last so Prettier owns formatting.

The container image

backend/Dockerfile is two stages on top of node:24-alpine. Both stage FROM lines resolve via a BASE_IMAGE_REGISTRY ARG: when CI passes --build-arg BASE_IMAGE_REGISTRY=$REGISTRY (the account-specific ECR host), the base image is pulled through the pull-through cache; when unset (local builds), the ARG expands to an empty string and the FROM reference becomes ecr-public/docker/library/node:24-alpine which does not resolve on Docker Hub — local builds must pass the build-arg or keep a one-off Dockerfile.local pointing at docker.io/library/node:24-alpine. The builder stage copies the root lockfile, .npmrc, and the backend's package.json, runs pnpm install --frozen-lockfile --filter @mythrun/backend, then copies the source and builds. The last step of the builder is pnpm --filter @mythrun/backend deploy --prod /app/deploy, which produces a self-contained directory with only the backend's production dependencies. The runtime stage is a fresh node:24-alpine that installs dumb-init, creates a non-root mythrun user, copies /app/deploy in with owner set, and runs dumb-init node dist/server.js.

Registry-host ARG, not a hard-coded ECR URL — hard-coding the ECR host would make the Dockerfile CI-only and lock out local builds. An ARG with an empty default preserves the usual FROM semantics in CI (where the ARG is set) and leaves local developers with one explicit knob.
pnpm deploy instead of copying node_modules — a workspace's node_modules is a forest of symlinks pointing back into the pnpm store and sibling packages. Copying that across a stage gives you dangling symlinks. pnpm deploy materializes a proper single-package tree suitable for the runtime image.
inject-workspace-packages=true in .npmrc — without this, pnpm deploy refuses to bundle workspace dependencies without the --legacy flag. The flag worked but is deprecated; the .npmrc setting is the supported path on pnpm 10.
dumb-init as PID 1 — Node.js doesn't reap zombie children or forward signals correctly when it runs as PID 1 under Docker. dumb-init is ~20 KB, forwards SIGTERM so docker stop shuts down gracefully, and costs nothing at idle.
Non-root mythrun user — the runtime user exists only to own /app. It has no shell, no sudo, no home directory worth mentioning. ECS and most scanners flag containers running as root; this sidesteps the finding and costs nothing.

The image declares a HEALTHCHECK that hits http://localhost:3000/health every 30 s. Dockerfile metadata carries the OCI source/title/license labels so registries render a useful preview without a separate manifest step.

The .dockerignore pair

Two .dockerignore files work together. The root one is authoritative — it's what Docker reads when the build context is the repo root (docker build -f backend/Dockerfile .). It excludes node_modules, dist, tests, the .git directory, .github, docs/, infra/, .beads/, .claude/, the wiki build output, project-level tooling configs (.prettier*, eslint.config.js, .nvmrc), and every editor/OS droppings pattern — shaving roughly 100 MB off a cold build context. backend/.dockerignore is a narrower duplicate kept alongside the Dockerfile as a readable hint for anyone building with backend/ as context; Docker only uses it in that case.

Operating this piece

Run the backend locally

  1. From the repo root: pnpm install.
  2. pnpm dev — starts the backend under tsx watch, reloading on file changes.
  3. curl localhost:3000/health should return {"status":"ok"}.

Run the full verification suite

  1. pnpm install && pnpm test && pnpm typecheck && pnpm lint — the "done when" of every implementation ticket. All four must exit 0.
  2. Each command fans out across every workspace via pnpm -r; a failure in any workspace fails the root command.

Build and run the container image locally

  1. The default FROM path in backend/Dockerfile expects the ECR pull-through cache and won't resolve on a laptop. For local builds, keep a one-off backend/Dockerfile.local whose FROM lines point at docker.io/library/node:24-alpine, or rewrite FROM to that image in place while iterating.
  2. From the repo root: docker build -t mythrun -f backend/Dockerfile.local . — build context is the repo root so the lockfile, .npmrc, and pnpm-workspace.yaml are visible.
  3. docker run -p 3000:3000 mythrun.
  4. curl localhost:3000/health should return {"status":"ok"}.
  5. docker inspect --format='{{.State.Health.Status}}' <container> confirms the HEALTHCHECK is reporting healthy.

Add a new workspace package

  1. Create the directory with its own package.json (scoped @mythrun/*).
  2. Add the directory to pnpm-workspace.yaml. Root pnpm -r commands pick it up automatically.
  3. Add the scripts the root commands fan out to (test, typecheck, lint, optionally build). Workspaces without a given script are silently skipped.
  4. pnpm install from the root to materialize dependencies and update the lockfile.

Integration points

The data plane owns the Postgres and Redis endpoints this service will eventually connect to; the network module owns the ecs security group the container will launch into. Cognitive-tier code (Fast Thinker, Slow Thinker, Scribe, DM Trigger) lands as additional modules under backend/src/; they'll share this server's lifecycle, config, and Dockerfile.
