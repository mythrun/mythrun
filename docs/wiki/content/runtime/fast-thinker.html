Fast Thinker

The player-facing prose tier — a Sonnet model driving an interleaved agentic tool loop: it streams narration, calls deterministic tools (roll_dice, roll_skill_check) when the scene needs mechanical truth, pulls world knowledge it lacks through three Slow-Thinker-gated lookup tools (search_lore, characters_known_to, faction_tree), and writes prose informed by each tool's result rather than deciding the outcome itself. It runs under enforced ignorance by construction — its context type carries only public facts, and the one tool seam that reaches the full, secret-bearing world store hands the result to the Slow Thinker to vet before any text comes back, so plot and NPC secrets have nowhere to live. After its prose it appends a lightweight, public-by-construction fact-delta — the new named things it introduced this turn — stripped from the player stream and the transcript by a delimiter guard and handed to the post-turn Scribe. The session-turn conductor calls it once per DM turn — as of myth-d6knq through a post-render audit gate that catches pure-prose boundary violations at that single seam; everything the player reads is its output.

How it fits together

A DM turn's Fast Thinker pass is a multi-step generation, not a single prompt. The SessionController calls SonnetFastThinker.render(ctx, emit); the FT builds its prompt, runs the Vercel AI SDK's tool loop on Sonnet, and consumes the resulting stream. The model alternates between writing prose and calling tools: it narrates, decides a check is needed, calls roll_skill_check, receives the resolved outcome as a constraint, and continues narrating around that outcome — all inside one render call. The loop ends when the model stops calling tools or the per-turn cap fires.

The SDK's tool loop, not a hand-rolled one — streamText + tool() + stopWhen + prepareStep + the typed fullStream (text-delta / tool-call / tool-result / error / abort parts) + per-message cache breakpoints cover every requirement, including the cap's graceful prose close. The SDK's deterministic tool loop is plumbing — like BullMQ — not delegated reasoning, so using it does not cross the Zero-Framework-Cognition line: the prose is the model's job, the dice and skill math are deterministic code, and re-implementing the loop would be strictly more bug surface for no capability gain.

The wrapper: streamTextWithTools

The FT never reaches into the 'ai' package directly (a lint rule forbids it). It calls streamTextWithTools, the net-new streaming-with-tools primitive added to the LLM client's ai.ts alongside generateObject / streamObject / generateText. The wrapper exposes the fullStream plus two distinct usage promises — the final step's usage (the context-fill signal, and as of myth-zd6pn the number the whole session bound is built on) and the cumulative totalUsage across all steps (the spend number, observability only) — and threads the per-turn timeout through the SDK's native timeout.

Errors and timeouts arrive as in-band stream parts, not throws — verified against the installed SDK: when the provider errors mid-stream or the per-turn timeout fires, streamText enqueues an error / abort part and closes the stream gracefully — the for await does not throw on its own. So the consume loop must throw on both, or a truncated turn ends "normally" and gets persisted as canon. There is also no mid-turn retry: the SDK's internal retry only fires on raw retryable API errors, which the middleware has already mapped away. A divergent re-stream under one turn is worse than a rare dead turn, so a failure after any frame has shipped is terminal — see the turn lifecycle.
Final-step usage and total usage are different numbers — the SDK's per-call usage is the final step only; cumulative spend is totalUsage. A five-step turn billed off the final step would under-count four Sonnet passes, so the wrapper names both explicitly. The usage promises are also pre-handled: on a zero-step failure they reject, and the wrapper attaches no-op catches so an FT that throws out of its consume loop never leaves an unhandled rejection to kill the worker.

The consume loop: the single emission point

render iterates fullStream and emits player-visible frames in stream-part order: a text-delta becomes a text_delta frame, a tool-result becomes a skill_check, dice_roll, or dm_correction frame built from the result and its call args. Tools never emit — all emission happens here, in one place. As it consumes, the loop also assembles the returned multi-part AssistantMessage directly from the stream parts (text deltas coalesce into text parts split at tool boundaries; tool-call and tool-result parts append at their positions), so the persisted turn is Mythrun-owned and never coupled to the SDK's own message shape.

Why emit from the consume loop and not from inside a tool — the SDK executes tools at its internal pipeline pace, ahead of the consumer, so an emit from inside a tool's execute could hit the wire before the prose deltas that preceded the tool call in the model's output. fullStream interleaves tool-call / tool-result parts at their true positions, so part-order emission is model-output order. It also serializes the player-visible frames of parallel same-step tool calls (a full-party "everyone roll Perception") deterministically, even though the SDK may run those resolvers concurrently. Frames carry no sequence number, so arrival order is the only ordering — which makes this invariant load-bearing.

The cap and the prose close

FT_MAX_TOOL_STEPS (5) bounds the loop via stopWhen: stepCountIs(...): up to four tool-calling steps plus one prose-close step. A full-party group check fits in a single step through parallel tool calls, so the cap is rarely the binding limit.

The forced close is an injected instruction, not toolChoice: 'none' — verified against the Anthropic provider: toolChoice: 'none' strips the tools param entirely, and an Anthropic request whose history holds tool blocks but defines no tools is rejected with a 400 — exactly on the turns that hit the cap. So prepareStep on the final step keeps tools defined and appends a close instruction ("wrap up in prose, do not call tools"). If the model defies it and emits a tool call on the final step, that dangling call has no result; it is dropped from the persisted turn (and logged), so the rebuilt history stays clean and never 400s the next turn.

The tool registry: pure resolvers

ft-tools.ts (buildFtTools) is the extension point — the place tools register as their resolvers land. MYT-68 wired two (roll_dice, roll_skill_check); MYT-70 added the six Rules Lawyer ledger tools (cast_spell, spend_resource, acquire_resource, adjust_hp, update_condition, take_rest); MYT-72 added the three world-knowledge lookups (search_lore, characters_known_to, faction_tree — the section below); MYT-75 added the two combat L1 tools (initiate_combat, resolve_combat). Tools are pure resolvers: their execute returns data only, never emits a frame, and the SDK feeds each result back to the model as the next step's input.

The combat tools are pure resolvers too — and the resolver, not the model, owns the fight — initiate_combat.execute rolls initiative and runs the single-shot resolver (a whole fight as one big skill check — the same skill-check shape, scaled up: a Haiku table generates a DC + four tiered outcomes, a dice roll selects the tier, the matched tier becomes the model's narration constraint). The FT narrates that outcome and reports its mechanical results through resolve_combat; it never decides who won. Both return data only — the durable mode flip, the ledger write, and the combat frames all happen outside execute, at the turn's commit, never inside the tool (the SDK runs execute ahead of the consumer). The FT prompt directs the model to route all of a fight's HP and conditions through resolve_combat rather than the out-of-combat ledger tools, so the combat resolver is the single authority for the encounter's stakes.
The ledger tools return a structured constraint, never throw, never emit — each ledger tool's execute delegates to a total Rules Lawyer resolver and returns its LedgerResolution as data. On ok:true the consume loop emits a ledger_update frame the same way it emits a skill_check; on ok:false the constraint object surfaces unchanged and the model narrates how the attempt falls short. The SDK-assigned toolCallId threads into the resolver as the journal idempotency key. The tools' model-facing schemas are deliberately flat z.objects with a kind enum, not discriminated unions: the Anthropic tool API requires every input_schema to have a root "type": "object", and Zod's discriminated union emits a root oneOf with no top-level type — which the API rejects. The per-kind requirements are enforced in execute + the resolver instead. This was found by the MYT-70 smoke, not by typecheck.
  • roll_dice — { count, sides } over the standard die set; returns { results, total }. The bounds are enforced in code (Zod plus a defensive clamp in the engine) — an unbounded count would stall the worker, which holds the session lock. For non-skill rolls (damage, wild magic). No modifier param: a "2d6+3" total would be LLM arithmetic, acceptable here and never treated as mechanical truth (authoritative damage math is the combat engine's job, later).
  • roll_skill_check — { character_name, skill, context, advantage?, disadvantage? }; the full pre-generated-DC-table flow below. character_name resolves against the session roster, a closed known set, never a free-text DB key.
The resolver's injected dependency is a scoped projection, not the whole repo — the tool loop adds a third inbound channel to the FT (tool results), which has no type-level enforced-ignorance bound. The discipline is held by scope: the skill-check resolver receives only a narrow mechanical-reads projection (findSessionParticipantCharacterByName), not the full repository, so no tool can casually return a repo-fetched secret-tier string. The MYT-70 ledger tools take the same shape: they receive the scoped LedgerOps surface and a per-turn transaction runner, not the whole repository. The one tool family that must reach the full, secret-bearing world store — the three world-knowledge lookups — is held by the same principle taken further: it never gets the store's raw output at all. It is Slow-Thinker-gated (the section below), so the only string that crosses back to the FT is the Slow Thinker's vetted relay.

The dice engine (Principle #4)

dice/engine.ts is pure functions over crypto.randomInt — the LLM never generates a random number. rollD20WithType returns the kept roll for advantage/disadvantage (roll twice, keep higher/lower), rollDice sums a pool with a defensive bound, calculateModifier is floor((score − 10) / 2), and resolveRollType applies the 5e rule that advantage and disadvantage cancel to a normal roll. An injectable RNG makes every path deterministically unit-testable.

The skill-check resolver (Principle #5)

skill-check.ts is the pre-generated-DC-table flow — and it is total: every failure arm returns a structured error constraint rather than throwing, because an uncaught throw would surface as a tool-error part the loop continues past, letting the model narrate an outcome with no roll. The steps:

  1. Resolve the roller from the session roster (session_participants joined to characters). The name is normalized (trim + case-fold) and matched exactly against the closed participant set — structural validation, no fuzzy matching. No match or an ambiguous name → an error constraint, never a throw.
  2. Compute the modifier — the ability modifier from the character's score plus the per-skill proficiency bonus, read from character_skills.proficiency_level: none → +0, proficient → +PB, expertise → +2×PB, using the authoritative characters.proficiency_bonus column. Both sides of the skill join are normalized (the stored skill name is itself unconstrained LLM output), and an absent row defaults to none.
  3. Pre-generate the DC table — one Haiku call returns { dc, outcomes: { fail, success, great_success } }, the outcomes authored as narrative constraints, not dialogue. The FT turn's abort signal is threaded into this nested call so a turn timeout cancels the in-flight DC generation with no orphaned spend.
  4. Roll and match — rollD20WithType + the modifier → total; the tier is total ≥ dc+5 → great_success, ≥ dc → success, else fail. The matched outcome string is the constraint. No nat-1 / nat-20 crit on ability checks — that is RAW only for attack rolls.
Roll, then match — never prose pre-written for an outcome — this is CLAUDE.md non-negotiable #5. Haiku generates the DC and three outcome descriptions before the roll; code rolls deterministically; the matched tier is injected as a constraint the FT narrates around. The model writes how a check fails or succeeds, informed by the outcome — it never decides the outcome. The frame and the persisted row both carry character_name, because in multiplayer every client must see whose check fired.
Fail-soft, so the turn never dies on a bad check — if the Haiku DC call fails or aborts, the resolver falls back to a fixed moderate DC with tier-neutral outcome templates, and the deterministic roll + tier match still run against it, so "roll then match" still holds. An unknown character, an ambiguous name, or an unmapped skill each returns an error constraint and the ft-system prompt instructs the model not to invent a result. roll_dice out of range returns a tool-error the model narrates around. Every arm is logged.

Enforced ignorance and the prompt

The FT's grounding is two things: the curated, enforced-ignorance-safe prep document (session_preps.ft_context, loaded into FtTurnContext.ftContext — see the conductor), and the full verbatim session transcript reconstructed each turn from session_messages. It is never a summary. The ft-system.txt prompt is a multiplayer rewrite of the prototype's single-player one: it encodes the participant roster + character-name attribution, the tool protocol ("call the tool, then narrate the returned constraint; never decide an outcome; never roll yourself"), enforced ignorance (never reveal what a character can't know), and how to handle an error constraint without inventing a result. MYT-70 added a Resources & The Ledger section: it teaches the six ledger tools, the rock principle (improvised objects are narrated, never spent), the three-branch reasoning for a not-found debit (environmental → narrate; fiction already granted → acquire_resource first; never established → correct gently), that binding constraints are authoritative outcomes, actor-scoping (mutate only the acting player's character), and that the [Party ledger: …] tail names resources canonically — reuse those names exactly.

MYT-69 added the NPC-authenticity half of the prompt — the FT's side of the Slow Thinker's social clock. NPCs are normal people, not quest dispensers: a stranger gets weather, prices, and wary politeness, not the NPC's troubles or secrets; small talk is the texture of the world, played in full; trust is earned across a conversation, and what an NPC has to share, the story tells the FT when it is time — via a direction. Two craft rules ride alongside: the check-frequency rule carves out genuine no-stakes chat (checks gate attempts to change a mind, deceive, or read what's hidden — never ordinary conversation), and a successful social check against an NPC whose depths the FT doesn't know yields demeanor or plausible public content, never invented hidden plot.

myth-d6knq hardened the craft rules after the weekend playtest, four additions with one theme — the DM finishes what it starts and nothing more. Supply what you promise: when the narration has a character read a document, recall a date, or deliver a name, the actual words must appear in the prose — "she reads the letter and her face falls" without the letter's words is a broken promise; the only reasons to withhold are a failed check or a genuine secret the story has not given the FT. Stop at an unforced choice: when the scene reaches a fork the party has not chosen — a figure walking away, a door, a split road — the narration ends at the choice; the DM never picks the branch. Never end the session in a normal turn: no "— End of Session —" markers, no send-off flourishes; closings belong only to the dedicated farewell flow. And never correct earlier narration inline — a correction goes through the structured channel below, never a mid-scene "let me correct that" written into the story.

myth-b4xt added a Tools Resolve Silently rule, the same theme carried one layer deeper: every tool the FT calls — dice, skill checks, spells, the resource ledger, lore lookups, corrections — is invisible machinery, and the player sees only the fiction it produces. The prompt forbids narrating the decision to reach for a tool, the reasoning behind it, or the bookkeeping that follows: no "no check needed yet — let the scene breathe," no "Burning Hands is a first-level slot, so I'll spend that one," no "technically that's difficult terrain." The FT resolves the tool, then writes only what happens in the world — a spent slot is the power guttering out on the page, a found blade is the character's hand closing around the hilt, an emptied purse is a pocket turned inside-out. When a mechanical fact matters to a player, the fiction carries it, never a ledger note or an aside about the gears turning.

The same silence now covers the FT's own inputs. Staging audits caught the model naming its scaffolding in the prose — "the session context says the passage narrows", "as provided", "the stage direction" — words that belong to the machine and not to the world. The rule is absolute: no reference to the context, the system, the instructions, the notes it was handed. If the passage narrows, it narrows because the bone closes in. Two more prompt additions came from the same audits. The FT may use *italics* and **bold** for a word or short phrase that genuinely carries weight, and nothing else — no headings, lists, links, tables, or code, because its output is running prose and the client renders exactly that vocabulary. And the prompt now pulls in shared/prose-register, the one house-voice fragment the prep stages share, through the prompt loader's include directive — so a register change lands on the prep engine and the live DM in the same edit instead of drifting between them.

A correction turn gets its own framing: the correction comes first and is the whole job. The FT may not continue the scene, advance time, resolve anything open, or narrate any new event before the issue_correction call, and afterwards at most a sentence or two that quietly restores the scene and hands it back to the players. If there is nothing to restore, it calls the tool and stops.

The silent-tools rule lives in the prompt, deliberately not in the audit gate — these leaks (a stray "I'll roll Perception here," a slot-accounting aside) surface on tool-calling turns, and the audit gate fails open on exactly those turns — it is a pure-prose boundary check, not a machinery-leak check, and a turn that called tools is outside its remit. So the discipline is authored as a craft rule the model follows, not a post-hoc gate that would catch it — adding a machinery-leak class to the gate would false-negative precisely where the leaks live. The same terse instruction is repeated in the prompt's closing hard-rules list, where the FT is most likely to still be attending to it as it writes.
The FT cannot plot-dump what it does not know — that is the authenticity engine — these prompt rules only hold because enforced ignorance is structural. The FT has no playbook, no secrets, no plot in its context, so it genuinely cannot hand a stranger a quest hook. The Slow Thinker holds the secrets and the social clock and decides, post-hoc, when a conversation has earned a reveal — portioning out exactly what an NPC entrusts via a stage direction. Without the split, the carve-out would be a prompting suggestion the model could ignore; with it, the FT's ignorance is the boundary.
The running summary is the Slow Thinker's tool, not the FT's memory — the FT never reads the running summary. It holds the literal full transcript every turn, so there is no compressed history to hallucinate around. The summary is the Slow Thinker's own compression; it plays no role in FT grounding or recovery. Removing it from the FT's context type is what makes "secrets have nowhere to live" structural rather than a convention.

Context repair: entity cards and the farewell filter

Two changes from the same playtest reshape what the FT's context actually contains: one adds grounding the FT was missing, one removes teaching it should never have received.

Entity cards: canon for names spoken mid-session

The prep doc grounds the entities a session opens on. But a canon NPC can enter play later, by spoken name — a player mentions them, a direction steers the scene toward them — and their card never reached the FT's context. The model then does the only thing it can: invent the attributes (the live bug — a canon-female ship captain rendered male for an entire session). The fix (myth-dwyuw) runs before each render: the turn worker scans the recent transcript window (~40 rows, including this turn's player messages) for the world's known-tier entity names, and appends one compact card per match — name, type, and that entity's known-tier facts — to the base ft_context as a labelled "established canon, do not contradict" block (augmentFtContextWithEntityCards in turn-context.ts, over the pure matcher in entity-card-scan.ts).

Known-tier only — and enforced ignorance is structural, not a filter — the card builder never decides tiers. Both repo reads it makes — the entity list and the fact fetch — request accessLevels: ['known'] and nothing else, so discoverable and secret material has no code path into a card: there is nothing downstream to filter because the data never leaves the store. This is the CLAUDE.md hard boundary applied the same way the context type applies it — secrets have nowhere to live — and an enforced-ignorance regression test pins it: it seeds secret and discoverable facts on a matched entity and asserts the injected block carries none of them. The block's label is deliberately plot-free too: it says only that these are already-established, player-visible canon.
Deterministic ≥2-token name matching, not a model call — "which canon names appear in this text" is structural matching against a closed known set, the sanctioned Zero-Framework-Cognition exception (the same family as schema checks and the roster's exact-match roller resolution) — no judgment about meaning is being made, so no Haiku call is owed. The rules keep it honest: names are normalized (case-folded, punctuation to boundaries) and a match requires a contiguous run of at least two name tokens at word boundaries — robust to honorifics without a title list ("Captain Marsen Roud" is matched by a transcript's "Marsen Roud") — while a single-token name never matches at all, because one common word colliding with a short name would inject a wrong card far more often than it would help.

The rest is discipline around the edges. Cards are capped (six per turn, earliest-mentioned first) so the injected block cannot bloat the cached context. The augment is idempotent by construction: the base ft_context is re-derived from scratch every turn and the appended block is never persisted, and any entity the prep doc already names is suppressed — no duplicate cards. Player characters are dropped from the scan (the roster and the per-turn party ledger already ground them). And the whole augment is fail-soft: any failure logs and returns the base context unchanged — grounding is additive, and a degraded turn must not crash.

The farewell filter

The opposite problem: the context read was returning teaching the FT should never see. A farewell turn's send-off prose — the real, in-fiction "— End of Session One —" close — persists to the transcript like any DM turn, and the FT's context reconstruction faithfully returned it. The model learned the pattern: dramatic close → emit the marker. It began self-authoring fake "— End of Session —" closings in ordinary mid-session turns, each one persisting and re-entering its own context, reinforcing the habit. myth-n98pc cuts the loop at the read: listFtContextRows now excludes every row whose trigger_kind is farewell, so a send-off is teardown the FT never re-reads as scene state.

Filtered from the FT's read, kept for everyone else's — the farewell rows stay in the transcript, and the analysis-side read (listForAnalysis) still surfaces them: the post-session reconcile and analysis need the closing beats (where the party settled, who departed) precisely because the player-less farewell turn never runs a Scribe. The predicate is IS DISTINCT FROM 'farewell', not <>, because player rows and most DM rows carry a NULL trigger_kind — a plain inequality would silently drop the entire transcript. Only the FT's self-priming channel is cut; the durable record is untouched.

Player agency: the FT never plays another player's character

In multiplayer the FT voices the world — NPCs, environment, consequences — and never a player character. When one character addresses another (Brenna asks Onwe a question), or an NPC challenges a PC whose player has not yet answered, the FT holds the floor: it narrates only what the world does in response — the NPC waits, presses, the room holds its breath — and leaves the reply to that character's player. A pause the players fill is correct; a line the FT wrote for a silent character is a bug. The ft-system.txt Player Characters Belong to Their Players section spells the boundary out: never author another PC's speech, decision, movement, or equipment, never roll a check for an action a player did not declare, and never emit the players' own CharacterName: input format. It holds even when a question seems to demand a particular character's expertise ("you're the notary, what does the seal mean?") — the expert read belongs to that player, not the DM.

A prompt alone cannot guarantee that, so the tool layer enforces it structurally. ft-tools.ts wraps roll_skill_check and search_lore in a deterministic player-agency gate: a call whose character — or lore asker — is a session participant who did not act this turn is refused with a soft in-fiction error, so the FT cannot roll dice or recall knowledge on a silent player's behalf. The gate reads two new FtToolDeps fields: participantNames, the PC roster, used to tell a player character from an NPC (an NPC asker is never gated — an NPC has no player to defer to); and actingCharacters, the set of PCs who acted this turn. The conductor fills that set — normalized — before it renders, from the batch's trailing run of player messages after the last DM turn. A player-less turn (a correction, a farewell, a proactive beat) leaves the set empty, so every PC-attributed skill or lore call is refused: no player acted, so the FT speaks only for the world.

The gate is structural because the prompt could not guarantee it — authoring a silent player's turn (voicing their dialogue, deciding their actions, moving them, even rolling their checks) was the single most quality-damaging FT behavior, found in live multiplayer playtests. The DM-trigger classifier is not at fault: it correctly sits back on a PC-to-PC address. The FT is the actor, and a strongly-worded prompt still slipped — the model would reach for a dice or lore tool "on behalf of" the addressed character. So the tool boundary refuses the call outright. This is a Zero-Framework-Cognition exception of the sanctioned kind: mechanical policy enforcement (is this name a participant, and did they act?), not model judgment — the same category as a rate limit or a schema check. Single-player is immune for free: it runs the solo trigger kind (the classifier is bypassed) and has no second PC to puppet.

One residual leaked past both layers. On a forced turn the FT could still open its prose with a player character's Name: prefix — the players' input format bleeding into the DM's narration. Left alone, that line persists into the transcript and re-enters the FT's own context next turn, teaching it to keep writing in the attributed format: a contamination cycle. So after the turn is assembled, stripLeadingPcPrefix (applied by stripPcPrefixFromParts) normalizes a leading <PC name>: off the first text part of the durable message, before persist and before the Scribe reads it. Only the very start of the first part is touched — a PC name mid-prose, or an NPC's name, is left alone — so the players' input format never enters the durable transcript or the FT's own next-turn context, breaking the cycle at its source.

That strip runs at finalize — after every delta has already streamed. So the durable record was clean while the table still watched a Sable: block appear on screen, styled as DM narration; a staging run caught exactly that. myth-aiiao adds the live twin. A LivePcPrefixGate holds back the opening of the turn's first text run — bounded to roughly forty characters — until a leading <participant>: is either confirmed (stripped, so the live text matches the durable normalization byte for byte) or ruled out (released verbatim). The hold releases at the first tool boundary as well as on completion, so prose is never delayed past a tool call, and a text-less boundary leaves the gate armed for the first real text run.

Deterministic and first-run-only, mirroring the durable strip — this is string normalization against a known roster, not a judgment, so it is code (the same ZFC carve-out the agency gate sits in). After the first decision every subsequent delta passes straight through untouched, so the cost is a few characters of latency once per turn and nothing thereafter. The character cap matters: without it, pathological leading whitespace could hold a turn's prose back indefinitely, which would be a worse failure than the leak.

The weekend playtest found the semantic sibling of that leak. On a scene switch — a player's message opens a new location or a new line of action while another PC's scene hangs unresolved — the FT would close the old scene by authoring the absent character's dialogue or movement inline, woven smoothly into the narration: no tool call for the agency gate to refuse, no Name: prefix for the strip to catch. Two things answer it. The prompt's new scene-switch rule draws the exact line: a new scene answers that message; a prior scene left hanging simply ends unresolved; another PC's words may be repeated only verbatim from the transcript, and their plans carried out only when that player explicitly declared them — executing a stated intent honors the player, inventing new intent is the bug. And because a prompt alone has already proven insufficient on this boundary, a third layer backstops the first two: every rendered turn now passes a post-render Haiku audit at the conductor's render seam, which classifies exactly this violation (among two others) and — when it is safe to — re-renders the turn once with a corrective instruction. The gate lives on the session-turn page; the layering is the point here: prompt rule, deterministic tool gate, live prefix hold-back, durable prefix strip, semantic post-audit — each catches what the one before it structurally cannot. And the audit's correction now reaches a seated player too, through the whole-turn replace the worker pushes after persist.

The correction channel: issue_correction

Sometimes the DM must amend its own earlier narration — the Scribe's retcon arrives as a fused [[DM CORRECTION: …]] marker, or the model catches a name it got wrong. The old shape was an inline walk-back delivered in prose ("A moment — let me correct something: …"). myth-d6knq replaces it with a structured tool: issue_correction, a pure resolver like every other tool, whose text is the correction in the DM's own voice — terse, honest, in-fiction, no explanation of why. The consume loop emits the result as a dm_correction frame (like any other tool frame, from the single emission point), the codec persists the exchange as its own dm_correction row, and the client renders it as a set-apart errata slip — never as story prose. An inline correction is now a bug by definition: the prompt forbids it, and the post-render audit classifies one as a violation. The tool is not player-agency-gated — the DM is correcting its own narration, never acting for a player character.

On a correction turn the FT also withholds anything it writes before the tool call. Left alone the model opens with machinery preamble — "let me process that first" — which is neither narration nor correction, and it was reaching both the live stream and the durable transcript. The consume loop buffers pre-correction text out of both sinks and discards the buffer the moment issue_correction fires; trailing narration then streams normally.

Fail open if the correction never comes — a correction turn that produces no issue_correction call is malformed, but the withheld text was ordinary prose. So the buffer is flushed at stream end rather than dropped: a malformed turn degrades to a normal one instead of silently losing a whole turn's writing. On the happy path the buffer is already empty by then.
A separate channel, because an amended fact must not survive wrong in canon — an inline correction fails at both ends of the pipeline. On the player side it masquerades as fiction: prose and errata are typographically identical, so the table can't tell "the world changed" from "the DM misspoke." On the canon side it is worse: the wrong fact is already in the durable transcript, which re-enters the FT's own context and feeds the Scribe's extraction — so the mistake can outlive its correction. The structured channel closes the loop at every re-entry point. The persisted dm_correction row is included in the FT context read, so the codec decodes it back into the tool exchange and the FT re-reads its own correction next turn — without that, the model could re-assert the very fact it just amended. And the conductor folds each correction into the Scribe's prose payload as a framed [Correction to earlier narration: …] amendment, so the extractor reads it as an amendment rather than canonizing the superseded form. The transport carries the frame live and replays the row on reconnect.

The world delta: the FT proposes its own facts

When the FT names a new NPC, invents a tavern, or establishes a relationship, that has to become in-session canon. The FT emits those proposals itself: after its player-facing prose, and only after it, the ft-system.txt prompt lets it append a newline-anchored [[WORLD_DELTA]] marker followed by one line of JSON listing the new entities, facts, and relationships introduced this turn. The section is optional (omit it when nothing new landed), public-only by mandate (the FT has no secrets to list), and parsed against the flat WorldDeltaSchema at turn end. The parsed delta rides the returned AssistantMessage and is carried onto the Scribe job; a parse failure fail-softs (the prose already shipped).

A dual-sink delimiter guard strips the section from BOTH the player stream and the transcript — the [[WORLD_DELTA]] section is internal machinery: a player must never see it, and it must never enter the durable transcript, where the FT would re-read its own JSON as if it were prose. So the consume loop routes the text-delta substream through a stateful, char-by-char filter that sits between the stream and both downstream sinks — the live player emit AND the assembler that builds the persisted message. Only the pre-delimiter prose reaches either; everything from the newline-anchored literal onward is suppressed and captured for parsing. Guarding one sink and not the other would defeat the point — the guard feeds a single callback wired to both. The leading newline is part of the matched literal, walked with a KMP re-anchor, so an ordinary mid-sentence bracket can never arm it and a partial match pending at a delta or tool boundary is held back and coalesced when it resolves.

World-knowledge lookups: the Slow-Thinker-gated read seam

The FT knows only what its curated ft_context holds. When a scene needs a fact it lacks — a topic an asker would have to recall, who someone is connected to, how a faction is structured — it calls one of three lookup tools: search_lore (semantic recall over the lore vectors), characters_known_to (who a character knows), and faction_tree (an organization's hierarchy). Each is the live-play consumer of the world-store retrieval substrate, but the FT never touches that substrate directly. Every lookup runs the same four-step flow — gate → resolve → ST-vet → relay — and the FT only ever receives the final relay string. The orchestrator (runWorldFactLookup) owns the flow; the tool's execute just supplies a per-substrate resolver closure and shapes the result.

The whole flow exists because the world store cannot be tier-filtered at the read layer — retrieval deliberately over-pulls every access tier (known, discoverable, secret) on purpose, so the only place a secret can be held back is downstream. If the FT could read the over-pulled result, enforced ignorance would be gone. So the lookup is built inside-out: the FT asks a question, deterministic code over-pulls, and the Slow Thinker — the one tier holding the secrets — decides what is safe and writes the answer. The relay is the only string that crosses back. The FT never learns a Slow Thinker ran; the relay reads as the asker's own recollection.

Step 1 — the contextual skill-gate (Haiku)

Before any store read, world-lookup-gate.ts decides whether the asker can even recall the topic. This is the established Principle #5 pre-roll pattern: a Haiku call judges how plausible the recall is relative to the asker's public standing and returns a flat DC table — an auto_success flag (a foregone conclusion, no roll), or a DC plus three outcome tiers. The roll itself is the same deterministic dice engine the skill check uses; a failed roll short-circuits the flow (the resolver and the Opus vet never run, so a failed recall costs nothing past the gate). The DC is contextual, not topic-absolute: a blacksmith recalling forge-craft is trivial; the same blacksmith recalling a distant mage college's politics is a long shot.

The gate sees PUBLIC standing only — secret-aware overrides are the vet's job — the gate's "would they even know?" judgment must run on what is publicly true of the asker, never on a hidden role. A covert council member asking about that council looks, to the gate, like an ordinary citizen — so the gate sets a real DC. Letting the gate auto-succeed on a secret would leak the secret through the mechanics (an instant, no-roll recall is a tell). The secret-aware standing override — treating the asker as obviously knowing because a hidden role makes it so — lives downstream in the Slow-Thinker vet, which holds the playbook. The gate's fail-soft keeps the discipline intact: a blown Haiku call returns a moderate fallback DC (never auto-success), and the deterministic roll still runs, so "roll then match" holds on a model outage.
The DM channel rolls a real check; the NPC channel rolls a hidden, fabricated one — a lookup carries a channel. On the dm channel a player character is recalling, so the gate computes a real modifier off that PC's sheet (the knowledge skill — one of history / arcana / religion / nature / investigation / medicine / survival / insight — its proficiency level, the ability modifier) and the roll is visible to the table. On the npc channel an NPC is conveying what it knows; an NPC has no sheet, so the gate fabricates a stable per-NPC recall modifier — a sha256(entityId)-seeded value in a fixed band, so the same NPC always recalls at the same competence — and the roll is hidden. A visible NPC roll, or a visible instant auto-success, would leak how learned (or how secretly placed) that NPC is, so the publisher renders an NPC lookup identically to a hidden pass.

Step 2 — resolve (over-pull) and Step 3 — the ST-vet (Opus)

On a pass (or auto-success), the tool's resolver closure runs the matching retrieval resolver and renders the result as a tier-annotated block — each row prefixed with its [tier=…] access level, secrets included. That block never reaches the FT. It goes to st-lookup-vet.ts: a synchronous Opus call that holds the secret sd_playbook, sees the over-pulled tier-annotated results, the recent narration, and the channel, and emits one of three modes — relay (surface a tier-safe answer it found), none (the gap is genuinely empty after gating), or invent (a real gap with a healthy resolver — fabricate a tone- and thread-consistent fact that becomes canon for the session). Its text is the player-facing answer, surfaced verbatim, exactly as the Slow Thinker's stage directions are authoritative prose.

Node over-pull, but the characters_known_to walk crosses known edges only — over-pull is a node-content policy: the resolver hands the vet secret nodes, tier-annotated, to gate. Relationship edges are different, because the walk's result carries only node tiers — the edges it crossed are invisible downstream, so no vet could gate a secret connection after the fact. The FT lookup therefore calls charactersKnownTo with edgeAccessLevels: ['known'] (myth-got9q): a secret connection's reachability never enters the FT-facing walk. Node over-pull is unchanged — a secret NPC at the end of a known edge still surfaces to the ST-vet. When play reveals a connection, the Scribe flips that edge to known and it starts traversing.
A synchronous Opus vet, per lookup, mid-turn — not the async post-turn Slow Thinker — the FT needs the answer now, inside the turn, to narrate from it. So unlike the post-hoc Slow Thinker that runs off the turn path, this vet is a blocking call on the hot path. It is pinned to a 45-second timeout — well under the FT's 180-second turn budget — so the vet's own fail-soft fires before a turn-level abort could terminal-fail the turn. It is the same model tier as the narrative director (Opus) because the judgment is the same judgment: what is safe to reveal, given everything the world hides. Paying for an Opus call on every world-knowledge lookup is the cost of making the tier boundary real rather than a prompting suggestion.
The vet's raw output is redacted from logs and diagnostics — this is the one Mythrun LLM call whose raw model output reasons over secrets. The LLM client's generateObject normally captures a snippet of the raw text and the Zod validation issues into the repair WARN log and the rethrown error's diagnostic — invaluable for debugging a malformed response, but here a vehicle for a secret to spill into a log line. The vet sets redactRawText: true, which nulls both the snippet and the issue messages on this call only; every other caller's diagnostics are unchanged. And because the vet's text is authoritative prose, a repaired response is discarded, not surfaced: a repair re-authors the JSON with a different model, which could re-author the safety-critical text, so the orchestrator treats "a repair was attempted" as a fail-soft.

Step 4 — relay, and fail-soft everywhere

The orchestrator surfaces the vet's text verbatim — it never re-authors. The tool returns a data-only { result, skill_gate, roll_hidden } shape: result is the relay the model narrates from, and skill_gate / roll_hidden are secret-free mechanical metadata (the roll numbers and the public outcome constraint, never the playbook) the consume loop maps to a skill_check frame the same way an ordinary check emits one. The orchestrator is total: every failure arm degrades to a clean, channel-appropriate in-fiction blank ("You can't quite bring it to mind." / "They don't seem to know."), never a raw error, never an unvetted result. A resolver throw becomes a degraded empty pull the vet is told about (so it won't confidently invent over an infra blip); a vet error, timeout, or repaired response becomes the fail-soft relay. A wrong lookup cannot crash the turn that holds the session lock.

Enforced ignorance is structural here too: the playbook is captured in an opaque closure — the secret sd_playbook never appears on any object the FT tool layer can reach. The per-turn wiring (lookup-wiring.ts) reads it through a dedicated narrow repo surface — separate from the FT's own { ftContext }-only prep read — and captures it inside the vet closure. What the tool registry receives is an opaque vet function whose input type is the vet's fields minus sdPlaybook; ft-tools.ts has no playbook field and never references a playbook string. So even a future tool that spreads the lookup deps cannot reach the secret: it isn't there to reach. An enforced-ignorance unit test asserts the wired deps object carries no sdPlaybook key.
The relay is persisted, not stripped — and that is safe by construction — the three lookup tools collapse to one world_fact_lookup row kind in the transcript codec (the tool name rides the row JSON so the exact tool restores on read-back). The relay is written into the durable transcript like any tool result, because the FT's full-transcript memory is the session's only continuity — a stripped lookup would make the FT forget what it just told the player. This is safe precisely because the ST-vet sanitized the text before it ever reached the orchestrator: the only thing that lands in the transcript is the already-vetted, secret-free relay.

The working set ∪ canon read-merge (MYT-73)

The lookups also read what the session itself invented. A fact relayed or invented turn 5 has to be recallable turn 9, so each lookup tool reads the working set unioned with canon. search_lore loads the turn's working set and cosine-ranks each item's embedding against the same query vector searchLore already embedded — no second Voyage call — and merges the top matches into the canon hit set before rendering the tier-annotated block; the graph walks flat-append the working set's entity and relationship items. Symmetrically, when a vet relays or invents a fact, the tool records that vetted relay (with the vet's tier, now surfaced out of the vet) into a per-turn injection sink the Scribe carries onto its job — that is how this turn's invented facts enter the working set in the first place.

The merge funnels through the same gate; an NPC's claim stays attributed — a working-set hit is merged before the block goes to the ST-vet, so the over-pull/tier-gate boundary applies to it exactly as to a canon row (a secret-tier working-set item is gated by the vet, never filtered out at the merge). And a working-set item carries provenance: a DM-channel relay is objective, an NPC-channel relay is an attributed claim tagged with the NPC's identity. The merge renders an attributed item with a [claim by {npc}] prefix, so neither the vet nor the prose downstream ever elevates an NPC's claim to objective world truth. The FT never reads the working set as a context field — only down this gated path; its FtTurnContext.workingSet stays empty by construction.

Prompt caching: the cost lever

Holding the full transcript every turn is only affordable with prompt caching, so the FT attaches an ephemeral cache_control breakpoint to the system message (which carries the immutable ft_context head — the ideal anchor) and to the last settled history message (the end of the prior turn). Each of the up-to-five steps then re-uses the cached prefix rather than re-paying full input price on the accumulating tool-result tail.

Cache breakpoints ride per-message provider options, never the call level — verified against the provider: the Anthropic provider reads cache_control only from a message's or part's providerOptions, never from the call-level providerOptions.anthropic. A top-level setting is silently inert — no error, just full input price on every step of every turn. That is why the system prompt is passed as a system-role message (not the SDK's system: param) and why the middleware logs cacheReadTokens: a mis-placed breakpoint is otherwise invisible. The smoke asserts cache reads are non-zero on turn ≥ 2.
The standing directive is a raw tail message after the breakpoints — when the Slow Thinker has a live standing directive, the worker reads it from its Redis slot and threads it onto FtTurnContext.standingDirective; buildModelMessages appends it as one raw [DM direction: …] user message after placing the cache breakpoints. The MYT-70 [Party ledger: …] snapshot tail rides the same always-uncached zone, appended in pinned order (the ledger tail first, then the directive). Both ride past the last breakpoint, so neither perturbs the cached prefix and neither shifts the sliding-breakpoint index. It is render-only: never persisted, never pushed into ftHistory (which would render through the codec's attribution as a phantom "Player"). A one-shot direction, by contrast, is fused onto the last user message by the conductor before this assembly runs — fuse-then-append, so the one-shot lands on the real player message, not the ephemeral tail. On an audit-gate retry only, one more tail rides this same uncached zone, appended last — closest to generation, the most urgent instruction: the [System correction: …] corrective instruction naming the violation to avoid. Render-only, like the others; absent on every normal first-attempt render.

The context ceiling is the session-length bound

Caching makes holding the whole transcript affordable; it does not make it unbounded. The FT re-sends every message every turn with no compaction, so the model's input window — not a token budget, not anyone's patience — is the hard limit on how long a session can run. ft-config.ts names it: FT_CONTEXT_WINDOW_TOKENS (1,000,000, read off the Anthropic Models API for the configured FT_MODEL rather than assumed) minus FT_CONTEXT_HEADROOM_TOKENS (150,000) gives FT_USABLE_CONTEXT_TOKENS, 850,000.

As of myth-zd6pn that is not merely a bound but the bound, and it has a name of its own: SESSION_FT_CONTEXT_BUDGET, defined as exactly FT_USABLE_CONTEXT_TOKENS. Four things divide by it — the turn worker's auto-end, the player-facing progress fraction, and the Slow Thinker's wind-down and convergence arms — and all four read one Redis level, session:{cId}:ftcontext, so a session's length, the bar describing it, and the DM's decision to start landing cannot come apart.

The session used to be metered on something else entirely, and it was wrong (myth-zd6pn) — the bound was SESSION_TOKEN_BUDGET: 545,000 cumulative gross tokens summed across every tier. Two independent errors sat inside that. It accumulated a quantity that is really a level — the FT re-sends one transcript per call, it does not stack them, so summing turns counts the same context over and over. And it counted cache reads 1:1 against a ceiling that was calibrated before prompt caching existed; once the per-message breakpoints put the FT at a measured 91–96% cache-read rate, the meter filled roughly ten times faster than the spend it stood for. Sessions auto-ended around turn 14 — some nineteen minutes — against a session unit sold as roughly three hours, with this window about 4% full. The constant is retired. Metering the window is the honest version of the same intent: it is the quantity that genuinely runs out.
This is a length bound, not a cost bound, and nothing currently caps cost — worth being plain about, because the retired constant looked like both and was neither. A cache-read token fills exactly as much window as an uncached one at roughly a tenth of the price, so window fill answers how much session is left and says nothing about what the session cost. Sessions consequently now run far longer than they did, with no per-session spend ceiling behind them. That is an open product decision rather than an oversight: a spend cap has to be metered on priced usage — uncached input, cache read and cache write each at their own rate, per the billing model — and would live beside this constant as its own, not folded into it.
The usable ceiling sits below the real one on purpose — a session has to end before the window is full, not when it is. The reserve covers what the ending itself still has to fit: one more whole FT turn (the farewell), its up-to-FT_MAX_TOOL_STEPS tool round-trips, and its output, which the model line caps at 128K. 150K — 15% — clears that with margin. Running to the real ceiling instead would trade a graceful send-off for a provider 400 mid-turn, which is the failure mode that was actually ending sessions for as long as the auto-end was wired to a counter nothing wrote. Because the reserve is already inside FT_USABLE_CONTEXT_TOKENS, ending at SESSION_FT_CONTEXT_BUDGET still leaves a whole farewell turn's worth of room; the ceiling and the send-off are not in tension.
A model bump can shrink the session without moving a single constant — the 2026-07-26 move to Sonnet 5 re-verified both numbers live and found them unchanged: 1M in, 128K out. But Sonnet 5 ships a new tokenizer that spends about 35.6% more tokens on identical text (measured on 6KB of our own prep prompt: 1175 → 1593; Opus is unchanged). Same window in tokens is roughly 26% smaller in prose. Nothing in the config moved; the thing it measures did. These constants are deliberately not auto-scaled off a model change — session length against cost per session is a product decision, not a silent side effect. At the time the compensating move was made explicitly, on the then-separate SESSION_TOKEN_BUDGET; that constant is now retired and the window is the bound, so a tokenizer shift like this one no longer has a second dial to move. It shortens the session in prose directly, and the only honest response is to say so rather than to quietly widen the ceiling. Re-check both numbers whenever FT_MODEL moves; they are not the same across the model line (Haiku 4.5's window is 200K).

The measurement itself comes off the render. streamTextWithTools exposes the final step's usage separately from the cumulative total, and the FT returns that step's inputTokens as contextTokens on the assistant message — the last step's prompt is the largest single one of the turn and so the honest reading of how full the window actually is. The turn worker stores it as the session's context level; everything downstream reads that, not this. It is read best-effort — the promise rejects on a zero-step failure, and this runs after the prose has already streamed, so a usage hiccup leaves the previous level standing and never costs the table a rendered turn.

Integration points

The Fast Thinker is the player-facing cognitive tier behind the session-turn conductor's tier seam; its prose, fact-delta, and lookup injections feed the post-turn Scribe, and the Slow Thinker now runs off the turn path — its stage directions reach the FT as a fused one-shot (on the player's last message) and a standing tail message, both consumed silently. A Scribe-authored retcon reaches the FT the same way, as a fused [[DM CORRECTION: …]] marker it delivers openly — through the issue_correction tool as a structured dm_correction frame, never as inline prose. It runs through the LLM client's streamTextWithTools wrapper (Sonnet) and its skill-check resolver makes a nested Haiku call through the same abstraction. Its roller resolution and per-skill proficiency reads come from the repository layer's characters.findSessionParticipantCharacterByName. The frames it emits (skill_check, dice_roll, plus the streamed text_delta) flow through the worker-latched emitter to the session transport's wire contract, and the multi-part assistant message it returns is persisted to the PG-direct transcript by the conductor.

The world-knowledge lookups make the FT the live-play consumer of the world-store retrieval substrate — its searchLore / findSimilarEntities resolvers and the charactersKnownTo / factionTree graph walks — through the boot-probed Voyage embedder the worker threads in. The asker (a PC, or an NPC by name) is resolved through the repository layer's characters.findSessionParticipantCharacterByName and a world-scoped entities.findIdByWorldAndNormalizedName. The lookup's Opus vet is the synchronous face of the Slow Thinker (the same tier that, post-turn, writes stage directions off the hot path), and the tier it stamps on a relayed or invented fact rides the injection into the Scribe's working set. The per-turn lookup wiring (lookup-wiring.ts) and the campaign's worldId resolution live in turn-context.ts, both built by the turn worker when it constructs the tier seam.
