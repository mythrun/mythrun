Session prep

Before a session can run, one Opus call produces the three prep documents that session needs — a Fast-Thinker-safe ft_context, a secrets-bearing sd_playbook, and (MYT-101) the player-facing opening the DM reads aloud to open the table — and a dedicated BullMQ worker vets the opening against that same generation's secrets, then persists all three to session_preps. The job is keyed on (campaign_id, session_number), so re-enqueuing the same session is a resume, not a duplicate. A prep failure is session-scoped: it never fails the campaign. The Opus call streams, so two parallel signals come off it: phase events (a player's "the DM is preparing tonight's session" loading screen) and the live prose itself (a dev-only inspector). Those two signals ride two different Redis channels — and that split is what makes enforced ignorance structural rather than a runtime filter.

How it fits together

The generation primitive — generateSessionPrep — shipped first, ahead of any caller. This piece is the orchestration around it: a session-prep BullMQ job, a processor that owns the job's pipeline_runs lifecycle, a dedicated queue and worker, and a repo.sessionPreps binder that lands the result. The shape mirrors character integration — claim a stage, do the LLM work outside any transaction, persist, mark completed with cost — but differs in two deliberate ways the rest of this page calls out: there is no cost cap, and a failure does not touch the campaign.

The enqueue side is a four-route HTTP plugin — backend/src/routes/session-preps.ts — that lands further down this page. The trigger route calls queue.add with jobId = sp-{campaignId}-{sessionNumber}; the job carries a two-field payload, campaignId and sessionNumber. The worker is the consumer end, and the queue's lifecycle (created at boot, drained at shutdown) lives in server-queues.ts.

The dedicated queue and worker

Session prep gets its own queue (QUEUE_SESSION_PREP = 'session-prep') and its own Worker at CONCURRENCY_SESSION_PREP = 3, alongside the existing world-gen and campaign-setup pair in backend/src/worker/bullmq-config.ts. Both the dedicated worker container and the API process register the same processor against this queue. The API side also constructs a producer handle for the queue — built by buildSessionPrepQueue in backend/src/server-queues.ts, threaded onto AppDeps.sessionPrepQueue, and handed to the trigger route so a POST /session-prep can enqueue. Its connection bookkeeping is created at boot and closed cleanly at shutdown.

A third queue, not a slot on campaign-setup — session prep is a single long Opus stream (the slowest call in the system, see below). Folding it onto the campaign-setup queue would let one in-flight prep starve the per-player character-creation jobs of worker slots, and vice versa. A separate queue with its own concurrency cap keeps each stage's saturation independent — the same reasoning that split world-gen from campaign-setup in the first place.

The queue's job options match world-gen's: attempts: 2 with exponential backoff (30s), and removeOnComplete / removeOnFail both pruning terminal jobs so a future re-enqueue with the same jobId isn't silently swallowed by a leftover completed record. At shutdown the worker is closed before the queue (an in-flight Opus prep gets to finish, then the queue's Redis bookkeeping is released), ahead of the rest of the boot chain.

Claim, generate, persist, mark

The processor (session-prep-processor.ts) walks the same per-stage lifecycle the other prep processors use. It claims a pipeline_runs row via atomicClaimStage on (campaign, stage) — but the stage string embeds the session number: session-prep:{sessionNumber}. That's what gives each session its own claim row on a table that keys on (campaign, stage). A claim that comes back completed is an idempotent re-entry (BullMQ retried an already-done job) and returns cleanly; a lost-race result means another worker won and also returns cleanly.

Session number in the stage string, not a new table key — pipeline_runs already keys claims on (campaign, stage). Putting the session number inside the stage label (session-prep:3) reuses that machinery to give session 3 a claim row distinct from session 4's, without a schema change. The atomic claim is what makes re-enqueue a resume: a second job for an already-completed session no-ops at claim time.

With the claim held, the processor publishes a prep-started phase event, resolves the campaign's world_id, reads the prior-session context (the summaries and the latest handoff from the previous session's analysis), and calls generateSessionPrep — one Opus streamObject producing the three prose documents. That call runs against the raw pool, outside any open transaction: it is the slowest single call in the system (a 9-minute timeout, two long markdown documents), and holding a pooled connection for its full duration would starve the rest of the worker. The LLM client page covers the generation primitive — the omniscient serializer, the maxOutputTokens ceiling, the enforced-ignorance split that lives inside the prompt, and the optional onProseDelta callback the processor threads in to capture the stream as it lands.

On success the processor deterministically appends the prior handoff's verbatim voice and atmosphere excerpts to the generated ft_context, vets the opening against this generation's own secrets — a gate that persists nothing if it trips — then persists the three artifacts to session_preps through repo.sessionPreps.insert (ON CONFLICT (campaign_id, session_number) DO NOTHING — the first persisted row wins), marks the pipeline_runs row completed with the call's cost (Opus generation plus the opening tripwire's Haiku spend), and publishes a prep-ready event carrying the recorded costUsd. On any error it publishes prep-failed with the terminal flag instead. These three prep-* arms are the entire player-visible signal — they ride the campaign's pipeline channel, never the prose.

Vetting the opening against its own playbook

The opening is the one prep artifact that reaches players as prose, and an all-seeing model wrote it — the same enforced-ignorance hazard the ft_context carries, now on a document delivered verbatim to the table. So before the insert, the processor runs the opening through the secret tripwire (runSecretTripwire), checking it against this same generation's sd_playbook — the complete secret surface the opening was drawn from. The check is recall-biased, like the scribe's per-turn breach detector: any breached verdict, regardless of confidence, fails the stage. The failure is retryable — it re-throws as a non-terminal error, so BullMQ re-runs the job and a fresh generation may pass — and it persists nothing: the vet runs before insert, so a tripped opening takes the whole prep down with it. There is no half-written prep with a leaky opening; the row is all-or-nothing.

The opening is vetted, the ft_context is not — because only the opening is player-facing prose — the ft_context reaches no player directly; it is grounding the Fast Thinker reads and rewrites, and enforced ignorance for it lives in the prompt's own omniscient-serializer split (discoverable / secret material never enters it). The opening is different: /start delivers it verbatim as the session's first DM row, with no Fast Thinker in the loop to launder it. Verbatim player-facing prose from an omniscient author is exactly the shape enforced ignorance exists to catch, so it gets a runtime gate the ft_context doesn't need. Vetting against the generation's own playbook — not a broader secret store — keeps the check tight: the only secrets the opening could plausibly leak are the ones this prep just wrote down.

This whole LLM path is now smoke-validated against real Opus. The session-prep smoke loads a captured ready-to-play world into mythrun_test and invokes the processor directly, confirming the live behaviors this page describes: the per-call Opus timeout fires from the generation primitive, re-enqueuing an already-completed session resumes idempotently (the atomic claim no-ops), and persistence is partial-generation-safe — the session_preps row lands only after the stream resolves to a complete object, so an interrupted stream leaves no half-written prep. It is a manual, not-in-CI run (real Opus, ~$0.50 measured); the runbook is below.

Consuming the prior-session handoff

From session 2 onward, prep no longer generates in a vacuum — it opens on where the last session left the party. The post-session analysis wrote two things to the prior sessions row: a summary (a player-facing recap) and a handoff (the secret-aware SessionHandoff). The prep processor reads them through repo.sessions.getPriorContextForPrep — the campaign's prior ended sessions that have a written analysis, newest-first, capped — and routes them into prep two different ways.

The paraphrasable inputs go into the prep prompt. buildPriorSessionContext unwraps each row's chronological summary and takes the latest row's handoff; serializeWorldStateForPrep renders a "Where We Left Off" block from the handoff — time of day, party positions and conditions, unresolved threads (most-urgent first), and each returning NPC's current disposition. The prep LLM is free to reword all of that.

Verbatim NPC voice is concatenated onto ft_context, never run through the prep LLM — the handoff also carries a few of each major NPC's exact late-session lines and each location's exact atmosphere snippet. Their whole value is that they're verbatim: routing them through the prep LLM would let it reword them, defeating the cross-session voice consistency they exist for (the recurring failure is an NPC whose hard-won late-session voice resets to a generic first-impression next session). So the processor builds a fixed "Returning characters and places" section with buildReturningVoicesSection and concatenates it onto the generated ft_context after the Opus call returns — a deterministic string append, never a paraphrase. The disposition lines are prompt input; the voice lines are a post-generation graft.
Tolerant parsing; not reconcile-gated — every prior row is parsed with safeParse / try-catch, so a malformed or legacy row degrades to omission rather than throwing mid-prep. And the read filters on summary IS NOT NULL, not on reconciled_at: the handoff is transcript-derived narrative state, independent of the canon-fold, so a prior session whose reconcile is still pending (or failed) still contributes its recap and anchor. A session with no written analysis simply contributes nothing — prep opens without an anchor, never blocked.
Dedicated prep-* arms, not the generic stage-* events — an earlier cut of this processor reused the pipeline's generic stage-completed / stage-failed arms, but their shapes drifted (they expect a userId and a durationMs the session-prep job has no use for, and carried a free-form message the contract doesn't define). The three purpose-built arms — prep-started { sessionNumber }, prep-ready { sessionNumber, costUsd }, prep-failed { sessionNumber, terminal } — carry exactly the fields a prep loading screen needs and nothing a Fast Thinker could mistake for narrative. They're added to the pipeline event contract alongside the world-gen and character-creation arms.

Two channels off one stream

generateSessionPrep already streamed its result under the hood — the original code just awaited the final object and threw the intermediate chunks away. The processor now passes an onProseDelta(field, text) callback into the stage, so consuming the partial stream costs no extra LLM tokens: the same bytes that were being discarded are now forwarded as they arrive. (The stage page covers the delta mechanics — per-field length-diff, the mid-escape resync.) What the processor does with those deltas is the load-bearing design choice on this page.

The processor holds two publishers, both built by makePipelinePublishers in backend/src/worker/publishers.ts, and they write to two different Redis channels:

  • publishEvent → {redisKeyPrefix}pipeline:campaign:{id} — the existing player-facing channel. The three prep-* phase events go here. This is what the player's prep-status loading screen reads.
  • publishProse → {redisKeyPrefix}prep:campaign:{id} — a new, parallel channel that exists only to carry prep-delta prose. The onProseDelta callback wraps each delta in a prep-delta event and publishes it here. The only consumer is the dev-only prose route the dev tool subscribes to.
Prose rides its own channel exposed only in dev — structural enforced ignorance — the sd_playbook half of the stream is, by design, full of secrets: clues, revelation conditions, what the depth markers in ft_context are pointing at. There is no runtime leak guard on prep prose (the Haiku leak-classifier idea was descoped), so the channel split is the control. Phase events ("preparing… ready") are the only thing a player's surface can subscribe to. The prose never touches the player channel — it's published to prep:campaign:, and the single route that serves that channel is registered only when AUTH_MODE=bypass, so it is literally absent in a production boot. A player has no route to reach prep prose; leaking sd_playbook would require building one that doesn't exist.
Why the boundary holds even if someone wires it wrong — the split is defended at three independent layers, so no single mistake leaks prose. Compile-time: prep-delta is a ProseEvent, deliberately not a member of the PipelineEvent union, and publishEvent only accepts PipelineEvent — so publishEvent(id, prepDelta) doesn't type-check. Runtime: the pipeline channel's subscriber carries a type tripwire that drops any message whose type isn't a known pipeline event before it reaches a sink — so even a stray prep-delta hand-published onto pipeline: is discarded. Topology: in production no prose route and no prose subscriber are constructed at all. Defeating enforced ignorance would mean changing the types, removing the tripwire, AND registering the dev route in prod — none of which happens by accident.

A publishProse failure is swallowed: the onProseDelta callback is fire-and-forget (a rejected publish is caught and dropped), and the stage wraps the callback in its own try/catch so a throwing sink can never abort generation. Prose is cosmetic, dev-only telemetry; the persisted documents and the prep-* phase events are the durable output, and neither depends on a prose delta landing.

Cost is recorded, not capped

The processor prices the Opus call via computeCostUsd and writes it onto the pipeline_runs row — the same observability every prep stage carries. Unlike world generation and character integration, there is no cost-cap pre-flight and no credit debit here.

No cost cap, no credit debit at prep time — the world-gen and character-creation caps exist to bound an open-ended pipeline that can chain many calls. Session prep is a single call whose cost is structurally bounded by its maxOutputTokens ceiling (16384 tokens) — there is no runaway loop to fence. The recorded cost is for attribution and dashboards, not a gate. And no credit moves here: the session credit is debited later, at the /start path in Session Runtime, through credits.tryDebitForSession. Prep is preparatory work the runtime pays for when the session actually begins.

A prep failure is session-scoped

On any error the processor classifies it with isTerminalError, marks the pipeline_runs row failed, and publishes a prep-failed event carrying the terminal flag. A non-terminal error is re-thrown so BullMQ retries with backoff; a terminal error returns cleanly so BullMQ marks the job done (retrying the same payload wouldn't help). What it deliberately does not do — on either path — is call repo.campaigns.setFailed.

Why a prep failure does not fail the campaign — character integration flips the campaign to failed on a terminal error because integration is a one-time bring-up step: if it can't complete, the campaign genuinely can't go live. Session prep is different — it runs once per session, repeatedly over a campaign's life. A failed prep for session 5 says nothing about the campaign's health; the campaign stays at its current status and a later attempt can succeed. Resume is sound because the (campaign_id, session_number) claim row and the session_preps unique constraint together make re-enqueue idempotent: a retry either finds the prior row completed (no-op) or re-runs into the same ON CONFLICT DO NOTHING landing.

The persistence row and its unique constraint

session_preps holds one row per prepared session: ft_context, sd_playbook, the MYT-101 opening (migration 034, nullable TEXT — the tripwire-vetted introduction, NULL on pre-MYT-101 rows), an optional snapshot_id (the world snapshot a session is pinned to, populated by Session Runtime), and the usual id + timestamp. Migration 022 adds a named UNIQUE (campaign_id, session_number) constraint — the original schema had only a non-unique index. That constraint is what makes the processor's INSERT … ON CONFLICT resume sound: without it, a retried job could write a second prep for the same session. The repo.sessionPreps binder exposes insert (the ON-CONFLICT landing), existsFor (the resume existence check), and getBy (the read Session Runtime uses to load the docs at session start) — plus three binders the HTTP surface added: listFor(campaignId) (every prep for a campaign, ordered by session), getById(prepId) (a single prep by its own id), and deleteFor(campaignId, sessionNumber) (the row half of a reset). All six are ClientLike binders, so the reset path can run deleteFor inside a transaction alongside the stage re-arm.

The HTTP surface: four routes, one safe projection

backend/src/routes/session-preps.ts is the plugin that lets a caller drive prep over HTTP. It registers four routes on the campaign, all under the same campaign-membership guard but at two different roles:

  • POST /api/campaigns/:campaignId/session-prep — trigger (owner). Validates the body (sessionNumber, defaulting to 1), enqueues the session-prep job with jobId = sp-{campaignId}-{n}, and returns 202. It does not check whether a prep already exists.
  • GET /api/campaigns/:campaignId/session-preps — list (member). Returns every prep for the campaign, each as a SafeSessionPrep (below).
  • GET /api/campaigns/:campaignId/session-preps/:prepId — read (member). Returns one prep as a SafeSessionPrep, or 404 if the id is unknown or belongs to a different campaign.
  • POST /api/campaigns/:campaignId/reset-prep — reset (owner). Deletes the prep row and re-arms its pipeline stage so a later trigger regenerates cleanly.
Trigger always enqueues; it doesn't pre-check existence — the route is a thin, idempotent enqueue. A second POST for an already-prepared session is harmless: the fixed jobId dedupes it at the queue, and even if a job runs, the processor's atomic claim comes back completed and the ON CONFLICT DO NOTHING insert no-ops. Pushing the existence check into the route would duplicate logic the queue and the claim already enforce, and would race anything in flight. The 202 means "accepted for processing," not "a new prep was created."
Read 404s on cross-campaign, not 403 — getById looks a prep up by its own id, which isn't scoped to a campaign. The route compares the row's campaignId to the path and returns 404 prep_not_found when they differ — the same response as a genuinely-absent id. A 403 would confirm that some campaign owns the id; the 404 leaks nothing about preps in campaigns the caller can't see.

SafeSessionPrep: the HTTP enforced-ignorance gate

The persisted row carries both prep documents — the Fast-Thinker-safe ft_context and the secrets-bearing sd_playbook. The HTTP surface serves a projection, SafeSessionPrep, that carries the id, session number, ftContext, snapshotId, and createdAt — and deliberately not sdPlaybook. toSafeSessionPrep(row) builds that shape field by field; both read routes pass every row through it before reply.send.

An explicit literal, never a spread — the projection IS the gate — the backend declares no Fastify response schemas, so reply.send(obj) serializes every own-enumerable property of obj. There is no schema layer downstream to strip sdPlaybook. That makes toSafeSessionPrep the entire runtime control, and it is written as a field-by-field literal on purpose. A { ...row, /* omit playbook */ } spread would type-check under structural typing and ship sdPlaybook to the wire — the type system can't catch the leak because the extra field is still assignable. The explicit literal can only emit the five fields it names, and an exact-key test pins the shape so adding a field to the row can't silently widen the HTTP response.
This is the HTTP half of the same enforced-ignorance split the prose channel defends — sd_playbook never crosses the HTTP boundary at all. The two consumers that legitimately need the playbook read it another way: the Slow Thinker's st-evaluation worker loads it in-process through repo.sessionPreps.getBy (no HTTP hop, on its own narrow secret-bearing repo interface), and the dev tool watches it live over the dev-only prose stream, never via these routes. So the playbook reaches exactly the two surfaces entitled to it, by two paths that bypass the public HTTP API entirely.

Reset: delete the row and re-arm the stage, atomically

POST /reset-prep exists so an operator (or, later, Session Runtime) can throw away a bad prep and regenerate. It does two writes inside a single repo.transaction: sessionPreps.deleteFor(campaignId, sessionNumber) drops the persisted row, and pipelineRuns.resetStage flips the session-prep:{n} claim row back to pending (clearing started_at, completed_at, and error). After the reset, a fresh POST /session-prep re-runs from a clean slate.

Both writes in one transaction, because the claim row is the resume key — the processor treats a completed claim as "already done, no-op." If the reset deleted the session_preps row but left the claim completed, a re-trigger would short-circuit at claim time and never regenerate — the prep would be gone with no way to rebuild it. Re-arming the stage is what makes the delete recoverable. Doing both in one transaction means a reset is all-or-nothing: there's no window where the row is gone but the stage still reads done. resetStage is a plain UPDATE on the binder, composable into the same transaction as deleteFor.
Reset doesn't fence a prep that's mid-flight — nothing stops an owner from resetting while a generation job is still running. That's deliberate: the worst case is the in-flight job lands its ON CONFLICT DO NOTHING insert after the delete (re-creating the row the operator just removed), or finishes against a stage the reset already re-armed. Either way the data stays consistent — there's no corruption, just a possibly-confusing "I reset it but a prep reappeared." A lock to make reset-while-active strictly serial would add machinery for a dev-and-operator surface that doesn't yet have a concurrent caller; Session Runtime will own that sequencing when it drives this surface for real.

All four routes are declared in backend/src/contract/backend-routes.ts (the non-pipeline HTTP contract) and exercised by the dev tool's four session-prep panels on the World page — which is what keeps the route-exhaustion ship gate green. The trigger and reset routes are owner-only and rate-limited at 5/min per user; list and read are member-level at 30/min.

Operating this piece

Trigger or reset a session prep over HTTP

  1. Trigger generation for a session (owner, body optional — defaults to session 1):

    POST /api/campaigns/<id>/session-prep
{ "sessionNumber": 1 }
→ 202 { campaignId, sessionNumber }

    The 202 means the job was accepted, not that a new prep exists. Watch the campaign's SSE stream for prep-started → prep-ready (see below).

  2. List the campaign's preps, or read one — both return the sd_playbook-free shape: 

    GET /api/campaigns/<id>/session-preps          → { preps: [SafeSessionPrep, ...] }
GET /api/campaigns/<id>/session-preps/<prepId> → SafeSessionPrep | 404

  3. Reset a session to regenerate from scratch (owner). This deletes the row and re-arms the stage in one transaction: 

    POST /api/campaigns/<id>/reset-prep
{ "sessionNumber": 1 }
→ 200 { campaignId, sessionNumber, reset: true }

    Then re-trigger with POST /session-prep for a clean run.

Re-run a failed session prep

  1. Check the failure mode for the session in pipeline_runs:

    SELECT status, error, cost_usd, completed_at
  FROM pipeline_runs
 WHERE campaign_id = '<id>'
   AND stage = 'session-prep:<n>'
   AND user_id IS NULL;

    A failed row carries the classified error. The campaign's own status is untouched — a failed prep never moves it.

  2. Re-enqueue the same (campaign, session_number) job. The atomic claim re-arms from the prior failed row, the prep re-runs, and the ON CONFLICT (campaign_id, session_number) DO NOTHING insert keeps the run idempotent. If a prior attempt already persisted a session_preps row, the claim comes back completed and the job no-ops.

  3. Watch the attempt on the campaign's SSE stream. A clean run opens with one prep-started and ends with one prep-ready event carrying the recorded costUsd; a failure publishes prep-failed with its terminal flag. To watch the prose stream itself, attach the dev tool's prose pane (dev-only — see the dev tool page).

Confirm a session prep landed

  1. Read the persisted docs for a session:

    SELECT id, session_number, length(ft_context), length(sd_playbook), snapshot_id, created_at
  FROM session_preps
 WHERE campaign_id = '<id>'
   AND session_number = '<n>';

    Exactly one row per (campaign, session) — the UNIQUE constraint guarantees it. No row means prep hasn't completed; check pipeline_runs for an in-flight or failed stage.

Run the session-prep smoke

  1. Migrate the test database so it has a current schema: pnpm db:migrate:test. The smoke targets mythrun_test (DATABASE_URL_TEST), not the dev DB — don't run it concurrently with pnpm test, which also uses mythrun_test.

  2. Run pnpm smoke:session-prep. It loads the captured ready-to-play fixture into mythrun_test and invokes the processor directly (no HTTP, no worker) against real Opus — a manual run, not part of CI, ~$0.50 per the measured reference.

  3. The run asserts the plumbing this page describes: a prep-started precedes a prep-ready carrying a positive costUsd; a session_preps row lands with non-empty, non-identical ft_context and sd_playbook; and the session-prep:1 pipeline_runs row is completed with a positive cost. Prose-delta counts are diagnostic only (a field repaired by the Haiku-then-Sonnet pass may stream no deltas yet still resolve), so they warn rather than fail. A clean run prints SMOKE PASSED; any miss exits non-zero. On pass it cleans up the fixture's world and characters.

Regenerate the ready-to-play fixture

  1. Migrate the test DB (pnpm db:migrate:test), then boot a server and worker against mythrun_test — DATABASE_URL set to DATABASE_URL_TEST, a real Anthropic key, Redis up, AUTH_MODE=bypass. The driver talks pure HTTP to the bypass-auth backend; the server owns the DB.

  2. Run tsx scripts/smoke/fixtures/drive-ready-to-play.ts. It drives the real campaign pipeline — world generation, character creation — to campaign.status='active' against live Opus (world-gen alone runs ~20–25 min; the driver supports resume via SMOKE_RESUME_CAMPAIGN if a run is interrupted) and prints the resulting campaign id. One owner-member plus one character is the minimum viable ready-to-play graph the prep serializer reads.

  3. Capture the graph: pnpm capture:ready-to-play <campaignId>. The capture CLI walks the fixture manifest (world, entities, prose, facts, relationships, the campaign and its members + characters) and writes ready-to-play-campaign.json. Commit that JSON — it is the fixture the session-prep smoke replays, so no future smoke run needs to re-drive the ~25-minute pipeline.

Integration points

Upstream: the generation primitive on the LLM client page — the omniscient serializer, the two-field schema, the maxOutputTokens ceiling, the onProseDelta streaming seam, and the in-prompt enforced-ignorance split that keeps discoverable / secret material out of ft_context; and the prior session's post-session analysis, whose summary + handoff this prep reads to open on where the table left off. Sideways: the worker registers this queue's Worker as a third peer and is one of the two entrypoints that wire publishProse (the other is the API container's in-process worker); the repository layer holds the sessionPreps binder; the session-prep job name lives in backend/src/contract/pipeline-jobs.ts and is now a fully dev-tool-covered job (the prose pane is its driver). The two SSE consumption surfaces live elsewhere: the player-facing prep-status route reads the phase channel, and the dev-only prose route + its prose subscriber are documented on pipeline status alongside the rest of the SSE plumbing. The four HTTP routes register through app.ts, declare into backend/src/contract/backend-routes.ts, and are driven by the dev tool's four session-prep panels on the World page (dev tool); the producer queue handle reaches them via AppDeps.sessionPrepQueue, built by buildSessionPrepQueue in server-queues.ts (see the repository layer for the AppDeps shape). Downstream: Session Runtime reads session_preps at /start through the in-process repo.sessionPreps.getBy binder, debits the session credit, feeds ft_context to the Fast Thinker and sd_playbook to the Slow Thinker, and (MYT-101) delivers the vetted opening as the session's first DM row — the playbook reaches the Slow Thinker in-process, never over the HTTP surface, which serves only SafeSessionPrep.
