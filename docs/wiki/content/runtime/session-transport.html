Session transport

The live multiplayer layer: a ticket-authed WebSocket per player, a cross-container fan-out hub modeled on the SSE pipeline subscriber, ordered persist-then-broadcast chat, sequence-based reconnection replay, and a crash-safe TTL-presence model that suspends an empty session through a self-validating BullMQ job. This is the transport floor the DM-turn pipeline builds on: it carries player chat and presence frames, and its SessionHub fan-out is also the path the turn worker streams dm_thinking / text_delta / turn_end frames through.

How it fits together

A session is a live play room scoped to one campaign — at most one active at a time. Three HTTP routes bracket its lifecycle (routes/sessions.ts): POST /api/sessions/:campaignId/start creates the row, debits a credit, and resets the per-session Redis state (below); GET /api/sessions/:campaignId/active returns a field-allowlisted view of the live row or null; GET /api/sessions/:sessionId/messages replays the persisted transcript for REST gap-fill. The live transport itself is a single WebSocket route — GET /ws/session/:sessionId, registered by wsSessionRoutes over @fastify/websocket — that a player upgrades into after minting a ws-ticket. Once connected, every player message flows through the same path: a server-assigned sequence number, an append to session_messages, then a fan-out across every API container via Redis pub/sub.

One active session per campaign, enforced in the schema — the idx_sessions_one_active partial-unique index (a campaign can hold exactly one row with status = 'active') is what makes the campaignId a stable key for all the Redis transport state below (session:{campaignId}:…). Two players racing /start can't both win — the second INSERT raises a 23505 the route maps to a clean 409 session_already_active rather than a 500. Keying live state on campaignId rather than sessionId means a reconnect after a suspend/resume cold-starts against the same Redis keyspace without threading the new sessionId everywhere.

Starting a session: the atomicity-critical ordering

POST /:campaignId/start is member-guarded but the campaign owner pays. After six preconditions (campaign is active, no session already active, every confirmed member already has an integrated character — the silent-lockout guard, below, — a session prep exists for the next session number — enqueued on demand if it doesn't, below, — MYT-74a — the campaign's prior session is fully reconciled, and — MYT-74b — no session-end is mid-flight), the handler runs a fixed five-step sequence whose ordering is load-bearing:

The no-session-active check must precede the prep check (MYT-92) — the ordering of the first three preconditions is itself load-bearing, and a mid-session-join bug caught by the play screen's E2E is why. maxSessionNumber counts the live session, so while session N is active the computed "next" number is N+1, whose prep legitimately does not exist yet. With the prep check ahead of the active check, a member whose /start raced an already-running session got answered 409 prep_not_ready — a false signal that pinned them on the atmospheric prep beat forever — instead of 409 session_already_active, which tells the client to look up the running session (GET …/active) and join it. When a session is live, that fact dominates every other precondition, so the active-session guard now runs second, right after the campaign-active check and before prep. The play screen's start flow depends on this discrimination: it drives the prep beat only on a real prep_not_ready, and the join path only on session_already_active.
The silent-lockout guard names who the table is waiting on (myth-mnik3) — the third precondition returns 409 members_without_characters when any confirmed member (invite accepted, not suspended) still has no integrated character in the campaign. Such a member's WS connect is rejected server-side — the upgrade throws NoCharacterForParticipantError and closes 4404 (below) — so starting the session anyway would strand them in ambient quiet while the rest of the party plays. The guard queries listConfirmedMembersWithoutCharacter, whose character_id IS NULL predicate mirrors the exact character-row join the WS connect resolves against, so the guard and the transport agree on "has a character" by construction. It runs immediately before the session INSERT — the last precondition, past the point any concurrent character-integration could still be racing — and the 409 body carries each blocking member's userId and displayName, ordered by join time, so the play screen's blocked hold can render who the table waits on rather than an unexplained refusal. Suspended users are excluded: they can never reach the WS connect, so listing them would block a session on a seat that could never sit down.
A missing prep self-heals — /start enqueues it before answering prep_not_ready (MYT-102) — the prep precondition does more than gate. When no prep row exists for the next session number, the handler enqueues the session-prep job on demand and only then returns 409 prep_not_ready. This closes the first-session showstopper: nothing else in the player flow triggered session 1's prep (only the manual dev route did), so a first /start used to leave the player on the atmospheric "the DM is preparing tonight's session" beat forever. The enqueue is idempotent — the fixed jobId sp-{campaignId}-{n} dedups against a job a prior /start (or the dev route) already queued, and existsFor short-circuits the instant the worker lands the row — so the play screen's prep SSE flips to ready on prep-ready and re-attempts /start, which now finds the row and proceeds. The producer handle is optional on the route: a deployment that wired no sessionPrepQueue logs a loud prep_queue_absent warn and still returns the 409 rather than throwing, so the self-heal degrades to the old wait-for-a-trigger behavior instead of a 500.
The reconcile-pending interlock (MYT-74a) — the fourth precondition returns 409 reconcile_pending while the campaign's most-recent session is ended_at IS NOT NULL AND reconciled_at IS NULL. The working set is campaign-keyed and idx_sessions_one_active frees the slot the instant status flips to ended, so without this guard a new session could append onto the same Redis working-set list the prior session's still-pending reconcile is about to load and clear() — silent canon loss on a normal flow. The block holds until the end-of-session reconcile commits the prior session's canon and clears its working set; reconcile is fast (seconds), so it is brief in the happy path. An active most-recent session has ended_at = NULL and never trips here — the no-session-already-active precondition owns that case.
The session-ending interlock (MYT-74b) — the fifth precondition returns 409 session_ending while the campaign's ending flag is set. MYT-74b moved the status flip to the finalize, which runs after the farewell turn renders, so during that window the row is still status='active' with ended_at = NULL — the reconcile_pending guard (which reads ended_at) can't see the end yet. The ending flag is set at the very start of the end flow, so this guard fences the whole begin-of-end → finalize window. Together the two 409s cover the full lifecycle from the moment a session begins ending until its canon is committed.
  1. Mint the sessionId up front, so the credit debit's idempotency key (= sessionId) is known before either the INSERT or the debit.
  2. INSERT the session row first. A concurrent /start that already took the idx_sessions_one_active slot surfaces here as a 23505 → 409 (closing the race; never 500).
  3. Debit one session credit from the owner — self-managing transaction, idempotent on sessionId. Insufficient credits → deleteById the just-created row (it must not occupy the one-active slot unpaid) → 402.
  4. Initialize the Redis :state blob, parking the FastThinker's prep context (ftContext, from session_preps.ft_context) and the world tone alongside the participant list — so the turn worker reads them per turn without a Postgres round-trip. A fresh session leaves the :seq counter unset, so the first nextSeq returns 1.
  5. Deliver the prep-generated opening (MYT-101) as the session's first DM row — a single dm_text append at seq 1, trigger_kind session_opening, consuming that first nextSeq. A deterministic persist of already-vetted prose: no LLM call, no trigger-system involvement. A legacy prep with no opening fails soft — the session starts silent, logged loudly at WARN.
The FT context is loaded once at session start, fail-soft on a missing prep — the prep doc is immutable per session, so it is read once into the hot :state blob rather than per turn. A session whose prep stage never ran (or whose row was deleted in the narrow window between the precondition check and this read) still starts — the FastThinker degrades to transcript-only grounding, logged loudly at warn, never a 409. The world tone is read with a tier-neutral minimal accessor (getToneAndEra), not the plot-bearing world record, so the enforced-ignorance boundary holds even on this turn-worker-facing path. If the blob is later evicted mid-session, the turn worker re-loads ftContext from Postgres rather than silently losing the canon.
Row-before-debit, with a delete-on-failure rollback — the debit and the row insert can't share one Postgres transaction: the debit runs its own transaction against the credit ledger. So the row goes in first to win the one-active slot, then the debit runs; if it fails on no-credits, the row is deleted so the campaign isn't left with an unpaid active session wedging the slot. The delete is itself wrapped — a cleanup failure logs and still returns 402, never a 500, because the money invariant already holds (no debit happened, and the active-session guard blocks a double-charge on retry). The only fallout of a failed cleanup is a stranded row, diagnosable from the logged line.

Delivering the opening: a persisted first frame, no live publish

Every session opens the way a human DM opens a table — with a spoken introduction. The session prep generated and tripwire-vetted that prose (the opening document); /start's fifth step delivers it. Delivery is a plain persist: one dm_text row appended through appendDmTurn with a fresh turnId, user_id NULL, and trigger_kind: 'session_opening'. Its seq comes from the same :seq counter every turn draws on, so the opening takes seq 1 and the session's first live turn starts at seq 2. This is ZFC in the small: the prose was pre-generated and pre-vetted at prep time, so start touches no model and no trigger system — it moves an already-settled document into the transcript.

Persist-only, no live broadcast — and that is provably sufficient — the opening lands as an ordinary settled row, with no accompanying pub/sub publish, and every participant still sees it. The proof is a timing invariant: a socket can only open with a WS ticket, and a ticket binds to a sessionId that does not exist until /start has minted the row and returned. So no socket can be listening while /start runs — there is no live audience to broadcast to. Every client, the starter included, connects afterward and pulls the opening through the persisted-transcript replay (listAfterSeq) — served both by the reconnect frame and the GET /messages backfill — the same path that carries every settled DM row. A live publish would fan out to zero sockets; the persisted row is what actually reaches the table.
The opening is fiction the party experienced, so it is not excluded from post-session analysis — trigger_kind has a second reader: the post-session analysis structurally drops correction and farewell rows from NPC voice-excerpt selection (they point at buried secrets). session_opening is deliberately left out of that exclusion set — the opening is real narrative the table opened on, the same status as any DM prose, so the analysis should draw on it rather than fence it off. Migration 035 adds session_opening to the closed trigger_kind CHECK set for exactly this: a recorded, first-class trigger kind, distinct from the turn-trigger kinds because it is not a turn.

The upgrade handshake is the enforced-ignorance boundary's entry point

GET /ws/session/:sessionId opts out of the JWT chain (config.auth: 'public') because a browser-native WebSocket can't send an Authorization header — but "public" here means "no JWT," not "unauthenticated." The auth boundary is the route's preHandler, wsSessionAuth, which @fastify/websocket v11 runs before the upgrade completes: any reply.code(…).send() it issues rejects the handshake with no socket opening at all. The handshake runs six checks in order:

  1. No ?ticket query param → 401 ws_ticket_missing.
  2. consumeWsTicket (an atomic GETDEL). A null return (consumed / expired / missing) → 401 ws_ticket_invalid; a throw (a transient Redis fault on the GETDEL itself) → 503 ws_ticket_store_unavailable.
  3. Ticket's sessionId must equal the path's :sessionId → else 401 ws_ticket_session_mismatch.
  4. Load the session row: not found → 404; not active → 409 session_not_active.
  5. Re-check campaign membership against the session row's campaignId (never the ticket's claimed value), with the same "pending invite is not a member" predicate as requireCampaignMember → else 403 not_campaign_member.
  6. Re-check the account's standing (users.isSuspended) → 403 account_suspended, the same answer the HTTP surface gives.
The suspension check cannot be inherited from the mint route (myth-ficc) — a ticket minted while a player was in good standing stays valid for its 30-second TTL, so without a check here a just-banned player still gets a socket. It fails closed in both directions: a missing row reads as suspended, and a thrown Postgres fault propagates to the route error handler as a 500, which is also no upgrade. Every outcome other than "definitely allowed" ends without a socket. This is also what keeps the permanently-suspended system user — the demo world's owner — off the transport entirely.
Blocking new sockets is only half of enforcement; the hub kills live ones — suspending someone who is already at the table must not wait for them to reconnect. The SessionHub exposes closeUser, which closes and deregisters every socket that container holds for the user, across all campaigns, with a distinct application close code (4403 account_suspended) so the client can tell a ban from a resync and stop reconnecting — a reconnect would need a fresh ticket, and the mint route already refuses. The deregister is the part that actually enforces: a closed-but-still-registered socket keeps receiving fan-out until its close event lands. Each close is independently guarded so one already-torn-down socket cannot abort the sweep. It is deliberately local-only — a user's sockets on other API containers are those containers' to kill.
The campaignId the handler trusts comes from the loaded session row, not the ticket — a successful consumeWsTicket only proves some member minted a ticket in the last 30 seconds. It does not prove membership at upgrade time, and it must not be trusted to name the campaign: binding the upgrade to the ticket's claimed campaignId against a different URL session would let a ticket minted for session A authorize a socket on session B. So the handshake loads the session, reads its campaignId, and re-queries campaign_members. The ws-ticket page's "five load-bearing assertions for the future handler" are all honored here — this is that handler.
401 vs 503 on ticket consume, fail-closed either way — the SPA's reconnect logic differentiates: a 401 means the ticket is dead, so re-mint and retry; a 503 means Redis is wobbling, so back off and retry. Collapsing both into a generic 500 would make the client back off on a transient that should retry immediately, or hammer on a dead ticket. Both paths reject the handshake with no socket — the boundary fails closed.

Connect: presence, registration, then the first frame

Past the handshake, handleConnection mints a fresh per-connection id (connId) for this socket — a user may hold several concurrent sockets (multiple tabs or devices) and each is tracked independently by its own connId (below). It resolves the participant's character and writes the session_participants row (sessionParticipants.join resolves the character server-side — the client never supplies a character_id, and a member with no integrated character surfaces as a typed NoCharacterForParticipantError that closes the socket with the distinct 4404 'no_character' code (below) rather than a raw FK violation or a generic 1011). It then records this connection's presence key and registers the socket under its connId before broadcasting the join, so the new socket is in the registry when the fan-out comes back around. On join it also appends the character name to the :state participant roster (the list the FT system prompt uses) — covering mid-session joins by construction, and never removed on leave (a departed character is still in the scene).

One more thing happens at join, before any message can be accepted: the connection raises the campaign's :seq counter to the session's durable MAX(seq) — the join-time floor-guard (a myth-rf5rn follow-up). reseedSeq is raise-only, so on a healthy counter this is a no-op; on a counter that expired over a long idle, it restores the floor before the write window opens. Why the write path's collision heal (below) is not enough on its own is its rationale's story.

The :state roster is the FT prompt's, not the skill-check resolver's source of truth — the roster update is a read-modify-write on the hot blob, so two simultaneous joins can lose a name to last-write-wins until the next join. That is acceptable here because the skill-check resolver resolves rollers against session_participants (the authoritative row store), not this list — correctness never depends on the blob roster, and the turn worker reads the roster for the FT prompt from session_participants in deterministic order anyway.

The first server frame is deterministic. A fresh connect (no ?lastSeq) broadcasts a player_joined and sends session_ready. A reconnect (?lastSeq=N) instead builds a session_reconnect replay frame and sends it directly on the socket — a synchronous send that reaches this socket ahead of the player_joined (which only arrives after a Redis pub/sub round-trip). The player_joined broadcast is gated on presence: the connection checks userConnectionCount before recording its own presence key and fires player_joined only when this is the user's first live connection — a second tab opens silently rather than re-announcing a player already at the table.

Both first frames now carry the session-progress floor when there is one, so a joining client renders the real fraction immediately instead of sitting at empty until the next turn completes. The read is read-only — the turn worker alone raises the floor — and the field is omitted at zero and on any read failure, because an absent field means "no statement" while a zero would be a claim. It is guarded independently on both arms: a progress hiccup must never cost a player their connection or their replay.

session_ready is effectively dead code, and that is a trap — the shipped web client seeds its lastSeq at 0 rather than leaving it null, and 0 is a valid seq, so every real connection — first join included — arrives as lastSeq=0 and takes the reconnect branch. Only a client that never seeds (the ws-transport smoke, curl) reaches session_ready at all. Any new per-connect payload must therefore ride session_reconnect to reach players; putting it only on session_ready looks correct, passes its test, and ships nothing. The two arms are kept in sync deliberately, and the code says so at both sites.
register-before-replay, so live frames during the DB read aren't lost — the socket is registered with the hub before the reconnect replay reads session_messages. Any frame published live during that DB read is then delivered to this socket too; the client's seq-dedup drops the overlap with the replay batch. A read-then-register ordering would drop exactly that gap. This is the same ordering discipline the hub-resync path relies on.

Inbound chat: persist-then-broadcast with a server-assigned seq

Every inbound frame is parsed and classified at the transport boundary (parseClientFrame + classifyClientFrame): non-JSON, a missing type, or a type not on the CLIENT_FRAME_TYPES allowlist (player_message, typing_start, typing_stop, the MYT-67 dm_invoke summon, and the MYT-74a end_session summon) is silently dropped. A typing_* frame broadcasts immediately with no sequence and no persistence. A player_message goes through persist-then-broadcast: assign a server-ordered seq via Redis INCR, append it to session_messages, then publish the frame through the hub.

Two control frames carry no chat text. dm_invoke is the explicit DM summon (above). end_session (MYT-74a) is the explicit session-end summon. As of MYT-74b it begins the end rather than finalizing inline: it resolves the world id (blob-cached campaign → world), claims the ending flag, cancels the pending suspend, and enqueues a player-less farewell turn. The turn worker renders the send-off, then runs the finalize (flip to ended → enqueue reconcile + analysis → broadcast a structural session_end) in the turn's finally — so the table sees the live send-off before the close. Once a session is ending, the ending flag (a cheap realtime-Redis read) gates the inbound handler: every frame except a redundant end_session is dropped, so no new turn starts after end. A read failure on the flag fails open (the worker's own commit/write gates are the durable interlocks regardless).

The inbound handler is also the server side of the DM trigger system. Past the persist-and-broadcast, it writes the per-campaign trigger state (the typing key, the last-activity stamp, the max-wait anchor) and reschedules the quiet-window debounce that decides when the DM responds — after the message is persisted and broadcast, so a queue failure logs at warn and never loses the message. A dm_invoke frame (or an @dm-prefixed message) is the explicit summon: it carries no chat text, is never persisted, and fires the DM immediately rather than waiting on the window. The mechanics of all of that live on the DM trigger page; this transport is where the frames are observed.

Only player_message carries a seq; presence frames never do — clients render the seq stream in seq order, not arrival order, and gap-detect to trigger a reconnect replay. Presence and control frames (player_joined, player_left, typing_*, session_ready, error) are out-of-band: they're never persisted to session_messages and are absent from the replay, so they must never carry a seq a client could gap-detect on — that would corrupt reconnect-replay ordering. The prep-generated opening (MYT-101) is the session's first persisted row and takes seq 1, so the first player_message is seq 2 — or seq 1 when a legacy prep delivered no opening.
Persist before broadcast, and a unique index that fails loud — the durable transcript is the source of truth for replay, so a message is written before it's fanned out. Migration 023 adds UNIQUE(session_id, seq): a re-used number raises a 23505 rather than silently corrupting the ordering. A collision means the Redis counter fell behind the durable rows — a one-off reseed race, or (myth-rf5rn) the :seq key expiring after a >2h idle stretch, which restarts INCR at 1 and makes every blind retry collide again. So the route heals on the collision signal: it reseeds the counter to the durable MAX(seq) (reseedSeq never lowers a live counter, so the benign race case degrades to a no-op), takes a fresh number, and retries once — the message lands at MAX+1 instead of being dropped. A second collision after the heal re-throws as the pathological state it is. If the broadcast throws after the append succeeds, the message is still durable — the client gap-detects the missing seq and REST-backfills via GET …/messages.
Two layers: heal on the collision in flight, floor-guard at join — the original fix reasoned that the unique violation is the exact signal the counter is behind — no probe detects the state more precisely, and healing there means the healthy path pays nothing. That holds, but only for the colliding case, and the post-fix live smoke caught the case the collision heal structurally cannot see. The counter is campaign-scoped and carries across sessions, so a later session's durable rows start high — session two's opening might sit at seq 50. When the key expires over a long idle and INCR restarts at 1, the low numbers it hands out were used by a prior session; the unique index is (session_id, seq), so nothing collides. The messages persist silently before the session's opening row, corrupting transcript order — and the trigger debounce reads every new message as older than the DM's last response, so the DM goes permanently silent with no error anywhere. No write-side signal exists for that state, which is why the guard moved to the one place that can see it coming: the WS join path raises the counter to the session's durable floor before any message is accepted. reseedSeq is raise-only — it never lowers a live counter, so a healthy counter (or a race with a sibling join's raise) degrades to a no-op rather than re-handing-out used numbers. The collision heal stays as the in-flight backstop for a counter that expires mid-connection; the turn worker's persistTurn runs the same heal on its seq-block allocation, and all the writers branch on the shared isSeqUniqueViolation classifier, colocated with the repo that owns the constraint.
A bad inbound frame drops; it never kills the socket — the whole inbound path is a per-frame error boundary. A malformed frame, an oversized text (capped at 4 KB of untrusted input, distinct from the no-max rule on LLM-generated prose), or a transient Redis fault on persist/publish drops that one frame and keeps the connection alive. The worst case is one lost message, logged. A library-level maxPayload (16 KB) rejects oversized frames before the handler even runs; the in-handler text cap is the second line of defense.

The SessionHub: cross-container fan-out

The transport runs across many ECS tasks, and two players in the same campaign may be connected to different containers. The SessionHub bridges them with Redis pub/sub — one channel per campaign, session:campaign:{campaignId}, derived from the shared contract/session-channel.ts helper (the same helper the turn worker's publisher consumes, so a worker in another process can't publish to a channel the hub doesn't subscribe to). Each API process holds one dedicated PSUBSCRIBE'd Redis client (a duplicate() of redisRealtime) and an in-memory writable registry, Map<campaignId, Map<connId, { userId, socket }>>. When any container publishes a frame, every container's subscriber receives the pmessage and sends it to every socket registered locally for that campaign — all of a user's tabs, every user. This is structurally the SSE pipeline subscriber with two WS-specific differences: the registry holds writable sockets keyed per connection (not a set of read-only SSE sinks), and a resync teardown closes the socket rather than ending a sink.

Per-connection identity, so a second tab never orphans the first (myth-wat0m) — the registry inner map keys by connId, not userId. The earlier per-user map overwrote its entry when a user opened a second tab: only the newest socket received frames, closing either tab broadcast a spurious player_left and scheduled a suspend under a live session, and the surviving tab froze on "thinking" until reload. Keying per connection makes a user's concurrent sockets independent — register adds to the user's connection set without evicting a sibling, deregister removes exactly the leaving connId (a stale close can't evict a live tab), and pmessage fans out to all of them. The same per-connection identity runs end to end: the presence key carries a connId suffix, player_joined fires only on a user's first connection and player_left / clearTyping only when their last one drops, and the suspend gate counts distinct users (below). Old per-user-shaped presence keys still parse during a rolling deploy — a compat test pins this — and lapse under their own TTL, so a mixed-version fleet never strands presence.
A dedicated subscriber client, not the shared realtime one — once an ioredis client enters subscriber mode it rejects almost all other commands, so the PSUBSCRIBE client must be separate from the one the route (or the cross-process turn worker) uses to publish, INCR, and rate-limit. The same split the pipeline subscriber makes. The initial psubscribe is awaited before createSessionHub returns, so a publish immediately after construction is reliably delivered.
Reconnect → close every socket → clients replay — if the subscriber drops and reconnects, it may have missed messages published during the gap. Rather than try to reconcile, the hub closes every registered socket with WS code 1011 (redis-resync-required); clients reconnect and pull a fresh session_reconnect replay, which is the canonical recovery path anyway. The very first ready event is the initial connect (nothing missed yet) and is exempt — only a later reconnect triggers the teardown. A single dead socket whose send throws is evicted from the registry in place so it can't wedge the others.

Reconnection replay

A client that drops reconnects with ?lastSeq=N — the highest seq it has rendered. buildReconnectFrame returns a session_reconnect carrying every persisted row with seq > N, the current participant list, and the session mode. As of MYT-68 that includes the DM-turn rows: a player_message row replays as a player_message frame; a dm_text row replays as a consolidated dm_message frame; skill_check / dice_roll rows are reconstructed from their stored JSON content into their respective frames; the six MYT-70 ledger-tool rows reconstruct into ledger_update frame(s) from the row's persisted LedgerResolution; and a myth-d6knq dm_correction row (tool-JSON content, like a roll row) reconstructs into a dm_correction frame carrying the row's seq, the same drop-graceful way. So a reconnecting client sees the prior DM turns, not just the player chat. The replay is also the heal path for an audit-corrected turn: when the turn worker's audit gate persisted a corrected render that differs from what streamed live, the reconnect's whole-turn replace is how a live viewer's copy converges on the durable record — the corrected retry is deliberately never re-streamed. Author display and character names are resolved through two in-memory maps built once from campaign-wide reads — no per-message DB lookup. An author who has since left the campaign falls back to a stable "Former player" byline; their prose history still replays intact.

The row-to-frame mapping now lives on its own, and the turn worker publishes through it — rowToReplayFrame moved out of ws-session.ts into session/replay-frames.ts. That is not tidying: the audit gate's repair used to reach only players who happened to reconnect, which is not something a table does mid-session. The turn worker now rebuilds the corrected turn's frames through this exact function and publishes them as a live session_reconnect carrying one turn. Because the frames come from the persisted, seq-bearing rows, the client's high-water mark advances precisely as it would on a real reconnect, and its per-turnId whole-turn replace repairs that turn and leaves the rest alone. One mapping, two callers — a second implementation would drift, and the drift would be invisible until a corrected turn rendered differently on the two paths.
A corrupt DM row drops one frame, never breaks the reconnect — the DM-row replay reconstruction reads the stored JSON through narrow accessors, not a schema that fails loud. This is a transport-replay path, so a malformed or unknown-type row yields null and is dropped (logged), and the rest of the replay still ships. That differs deliberately from the turn worker's history reconstruction, which does fail loud on an incoherent transcript — there, an incoherent row is a persistence-layer invariant violation that must crash the turn; here, it is one missing frame in a best-effort replay.
A ledger row replays as 0, 1, or N frames — and ok:false is silent — the Rules Lawyer persists a row for every adjudicated call, including rejections, but only a successful mutation has a player-visible delta to replay. So the reconstructor discriminates on the stored output's ok field first: an ok:false rejection replays as an empty array with no warning (it is expected, not corruption); an ok:true single payload replays as one frame; and a take_rest row, whose payload is an array (one entry per rested character), replays as one frame each. A genuinely malformed row still warns and drops, as above.
lastSeq is structurally validated at the boundary — parseLastSeq accepts only a non-negative integer; absent, empty, negative, or non-integer input is treated as a fresh connect (null → session_ready). This is a transport-layer structural check (the ZFC structural-validation exception), mirroring the drop-on-malformed posture of the inbound frame parser. The REST GET …/messages?afterSeq=N route applies the same discipline more strictly — a /^\d+$/ match so '', -1, 1.5, and hex don't silently coerce — returning 400 bad_after_seq on anything malformed.

Presence, heartbeat, and crash-safe suspend

Presence is not a counter — it's one TTL key per live connection, session:{campaignId}:conn:{containerId}:{userId}:{connId}, set with a 60-second expiry. The connId suffix (myth-wat0m) makes the key per socket, so a user's multiple tabs each hold an independent key and closing one drops only that key. The heartbeat pings every 30 seconds (terminating a socket that hasn't ponged within a 10-second grace) and refreshes this connection's presence key on each ping, so a live socket never lapses. Two counters read these keys with SCAN (never KEYS, which blocks the single-threaded Redis event loop on a shared cluster): countPresence counts distinct users with at least one live connection — the number that gates suspend, so a user with two tabs counts once — and userConnectionCount counts one user's live sockets, the read that gates the first-connection player_joined and last-drop player_left.

TTL keys keyed by containerId, not an INCR/DECR counter — a bare counter leaks or goes negative under failure. A container that crashes skips its socket close handlers and would never decrement, leaving a session that looks permanently occupied; a double-fire would push it negative. Per-connection TTL keys self-heal: a crashed container's presence simply lapses after 60 seconds. The containerId (a per-process UUID generated once at boot) and the per-socket connId together namespace the keys, so neither two containers' presence for the same user nor a user's two tabs on one container collide.

When a disconnect drops the campaign to zero distinct users (countPresence == 0 — the last connection of the last user, after deregister has removed this connId), handleDisconnect schedules a delayed BullMQ suspend job — a five-minute grace window keyed suspend-{sessionId}. A user with another tab still open never trips this. A returning player cancels the pending job on connect. The processor (processSuspendJob) is idempotent and self-validating: on fire it re-reads distinct-user presence and only suspends when it's genuinely zero. Suspend flushes the live :state to a Postgres checkpoint, keeps status = 'active' (suspend is not end), and holds the Redis transport keys for ~2 hours so a quick reconnect cold-starts from live Redis rather than the checkpoint.

The presence re-read is the guarantee; the cancel is only an optimization — a player can reconnect during the grace window and the cancel can race the fire (the job transitioning delayed→active just as the cancel's remove lands), and BullMQ's jobId-dedup can in principle leave a phantom job. Neither matters: the processor re-reads presence and bails if anyone is connected, so an over-schedule is inert. The handler also fails safe — if countPresence itself throws on disconnect, it schedules the suspend anyway, because the processor's re-read gates the actual suspend. An over-schedule wastes a wakeup; an under-schedule would strand an empty session live forever.
The checkpoint target is a documented overload, pending a real column — the sessions table has no dedicated checkpoint column yet, and adding one is a schema migration this transport task didn't own. So the checkpoint writes a self-describing { kind: 'myt65-checkpoint', maxSeq, state } envelope into the existing st_running_summary TEXT column through repo.sessions.update. The kind discriminator lets a future reader tell a MYT-65 checkpoint apart from any other use of the column. The maxSeq recorded is the durable MAX(session_messages.seq) — never the raw :seq counter (which sits one ahead between INCR and the row insert) — so a crash-recovery reseed never re-hands-out a number a message already used. A dedicated session_checkpoints row is the long-term home. The envelope's kind bumped to myt69-checkpoint when the turn flush shrank to usage-only, so the recovery reader fails loud on the old shape rather than reading a stale flush contract.
The active-session route returns a response allowlist — the summary must not leak — the checkpoint folds the running summary into sessions.st_running_summary, and GET /api/sessions/:campaignId/active used to return the full mapped Session row — that column included — to any campaign member. Inert while the summary was an empty stub, but the moment the Slow Thinker writes rapport and reveal-ladder state into it (MYT-69), a member could read secret-adjacent narrative state with one REST call after any suspend. So the route now returns an explicit allowlist (id / status / sessionNumber / timestamps — never stRunningSummary or any checkpoint material), pinned by a route test. The persist into the column stays — it is the crash-recovery cold-start input; the fix is at the read boundary, not the write.

The wire contract scope

contract/session-events.ts is the declarative wire contract — a client-frame allowlist, a server-frame allowlist, and discriminated-union payload types per direction, mirroring pipeline-events.ts. MYT-65 shipped the player-chat-and-presence subset. MYT-66 adds the first DM-turn frames as server → client only: dm_thinking, text_delta, turn_end, and turn_error, each carrying a turnId and no seq. The turn worker publishes them; this transport's hub fans them out. MYT-67 adds one client → server frame, dm_invoke (the explicit "@DM button" summon, no payload fields) — and deliberately adds no server frame: the trigger decision rides a dev-only structured log, never the player transport, because the hub fans every published frame to all sockets with no audience filter and a dm_trigger frame would leak the classifier's reasoning to players (see DM trigger). MYT-68 adds the DM-turn mechanical frames the FT tool loop emits — skill_check and dice_roll (server → client), live-streamed during a turn with no seq and replayed from the persisted rows on reconnect (then carrying the row seq), plus dm_message, a replay-only frame for the consolidated DM prose row (live prose streams as text_delta). MYT-70 adds one more server → client frame, ledger_update — the Rules Lawyer's character-sheet delta, one flat member whose kind discriminates which post-mutation value fields are populated, on the same live-then-replayed lifecycle as the mechanical frames. MYT-74a adds the session-end lifecycle pair: the end_session client frame (a bare summon, no payload) and the session_end server frame (a one-shot { reason: 'normal' } broadcast — the live session is over and its end-of-session reconcile and analysis have been fired). MYT-74b re-times the session_end broadcast: it now follows the player-less farewell turn's send-off prose (rendered through the normal DM-turn frames) rather than firing the instant the summon lands, so the table gets a narrative close before the structural one. The session_end frame carries no seq (a control frame, like the presence frames) and is not persisted or replayed — a reconnect to an ended session is rejected at the ws-ticket handshake (status !== 'active'), so there is no replay path. MYT-75 builds the combat L1 frames the contract had reserved: three server → client frames (mode_change, combat_started, combat_resolved) on the same live-then-replayed lifecycle as the mechanical frames, and one client → server frame, resume_combat (the any-member resume summon, no payload). myth-d6knq adds the correction channel's frame: dm_correction (server → client) — the DM amending its own earlier narration through the FT's issue_correction tool, never inline prose. Live it is exactly { type: 'dm_correction', turnId, text } (no seq); on reconnect it replays from its persisted row, then carrying the row's seq — the same live-then-replayed lifecycle as the mechanical frames. It is not DM narration: the client renders it as a set-apart errata slip in the transcript, never as story prose, so a correction can never masquerade as the fiction it corrects. The rest — st_evaluation, scribe_result, and the others — is still deliberately absent until its surface is built.

The contract grows only as handlers ship, so unbuilt frames can't be broadcast — the classifyClientFrame tripwire rejects any client frame type not in CLIENT_FRAME_TYPES at the transport boundary. The server-frame allowlist plays the same role on the outbound side: a frame type is added only when something produces it. MYT-66 added the four DM-turn streaming frames and MYT-68 the mechanical frames precisely because the turn worker now produces them. roll_complete is deliberately not added to the client allowlist — no server handler consumes it yet; it lands with the frontend roll-animation issue. Adding it early would make the transport accept a frame nothing handles. Same structural-gate discipline the pipeline subscriber uses (ZFC structural exception — not LLM cognition).
Roll-reveal gating is client-side, not a server-held buffer — the worker emits the skill_check / dice_roll frame then the dependent narration deltas, in order; the frontend (a later milestone) plays the dice animation and reveals the buffered narration locally. This is a deliberate amendment to the earlier server-synchronized-reveal model: a cross-process session lock cannot be held pending a human animation ack without stalling the worker and the queue. The tradeoff is that reveal timing becomes per-client — the roll result is identical for everyone (resolved once, deterministically); only the animation beat desyncs — and turn_end now fires at model speed, before a client finishes animating.

Combat mode: a real server-side mode the transport enforces

The session-state blob has always carried a first-class mode (exploration | combat); MYT-75's combat L1 is the first thing to exercise it, and the transport is where that mode becomes more than a display flag. When a fight resolves, the session sits in combat mode showing the result, and the inbound handler drops every inbound frame except resume_combat (and end_session) — the same drop-gate shape the end-of-session ending flag uses. The resume_combat summon is any-member and guarded by a tryMarkResumed SET-NX claim, so two simultaneous "okay"s flip the mode and clear the session:{cId}:combat blob exactly once.

The drop-gate is what makes mode a mode — without it, a player typing while the combat result is on screen would re-arm the DM trigger and fire a normal exploration turn over the unresolved fight. Gating inbound frames to resume_combat while in combat mode moves the enforcement from the UI to the server: the session genuinely cannot do anything but resume until the party acknowledges the fight. It mirrors the existing ending-flag gate exactly, so the two server-side modes share one shape.

The reconnect-replay path is combat-aware: a member who reconnects mid-fight reads the :combat blob and gets a synthetic combat frame (a combat_resolved from the stored result if the fight has resolved, a combat_started from the roster and initiative if it is still resolving) rather than a blank combat screen. The :combat key is added to the TTL-refresh set so a suspend mid-fight never lets it lapse and wedge the session in combat mode with no result. The combat frames themselves are intra-turn control frames — not persisted to session_messages, hence the synthetic-replay path — while the fight's player-facing prose persists as an ordinary dm_text row and replays the normal way.

Operating this piece

Trace a failed WS upgrade

  1. The HTTP status on the rejected handshake discriminates the cause: 401 ws_ticket_missing (no ?ticket), 401 ws_ticket_invalid (consumed / expired / unknown ticket), 401 ws_ticket_session_mismatch (ticket minted for a different session), 404 session_not_found, 409 session_not_active, 403 not_campaign_member, or 503 ws_ticket_store_unavailable (transient Redis fault).
  2. A repeating 401 ws_ticket_invalid from one client usually means the SPA isn't minting a fresh ticket per upgrade attempt — tickets are single-use. Confirm the mint route returns 201 just before each upgrade.
  3. A 503 points at ElastiCache. Check for a failover; the ticket consume is a single GETDEL with no retry layer between the handshake and Redis.

Diagnose a session that won't suspend (or suspends too eagerly)

  1. Count live presence keys for the campaign: SCAN for ${MYTHRUN_ENV}:${REGION_PREFIX}:session:{campaignId}:conn:*. Each match is one open socket (a user with two tabs shows two keys); suspend gates on the number of distinct users behind them, so read the :{userId}: segment, not the raw key count. A non-empty match means at least one connection is still considered live (or a crashed container's key hasn't lapsed yet — the keys carry a 60-second TTL).
  2. Inspect the delayed suspend job in BullMQ: jobId suspend-{sessionId} on the session-suspend queue. A present delayed job means a suspend is pending; its absence after the last disconnect means either a reconnect cancelled it or it already fired.
  3. The processor logs its observed presence count and whether it suspended. A job that fires and finds presence > 0 bails by design — that's the cancel racing the fire, not a bug.

Read a suspended session's checkpoint

  1. The checkpoint envelope lives in sessions.st_running_summary as JSON with kind: 'myt65-checkpoint'. maxSeq is the durable last-persisted sequence; state is the live :state blob at suspend time.
  2. Suspend leaves status = 'active' — a suspended session is still active, just unoccupied. Do not treat a populated checkpoint as an ended-session signal.

Integration points

Upstream: a player earns the credential on the access control & WS ticket page — POST /api/sessions/:id/ws-ticket mints the single-use ticket this route's handshake consumes. The backend runtime registers @fastify/websocket, constructs the SessionHub (closed in createShutdown before app.close), generates the per-process containerId, and builds the session-suspend BullMQ Worker on a dedicated connection — the same shape as the prep workers, with the mandatory waitFor ping-probe before new Worker(...). The fan-out mirrors the pipeline status SSE subscriber. Durable state lives in sessions, session_messages, and session_participants through the repository layer; see the schema for those tables. The DM-turn pipeline extends the wire contract with the server-streamed turn frames and publishes them through this transport's SessionHub; it also adds the per-turn LLM-tier keys to the session-state module documented here. As of MYT-69 that module's :summary key is owned by the Slow Thinker job (the turn flush is usage-only, and setRunningSummary is the summary's only writer), the ST's spend tracks on a dedicated :usage:st counter summed at every read, and the session-start route resets the spend + summary keys (resetSessionSpend). The DM trigger system hangs off this inbound handler: it observes the typing and message frames here, writes its own trigger-state Redis keys, and reschedules the quiet-window debounce that decides when a DM turn fires — and adds the dm_invoke client frame to the contract. The end-of-session reconciliation story closes the lifecycle this transport opens: the end_session frame and the budget auto-end both begin an orchestration that quiesces this transport (the ending gate, cancelSuspend) and enqueues a farewell turn; the turn worker's finalize then flips the session row and fires the reconcile + analysis workers. The /start route's twin 409s — reconcile_pending and session_ending — block the next session across the whole window from begin-of-end until the prior canon commits. The transport's session_messages store also gained the migration-028 trigger_kind column: the turn controller stamps each DM row's originating trigger so the post-session analysis can exclude correction and farewell rows, and the repo's listForAnalysis read serves the analysis worker its transcript tail. The client that drives all of this from the player's side — the start flow's precondition arms, the streamed transcript, optimistic own-messages, reconnect replay, and the presence line — is the frontend live play screen.
