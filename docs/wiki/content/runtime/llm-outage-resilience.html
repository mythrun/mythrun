LLM outage resilience

How Mythrun survives an Anthropic API outage: every failed LLM call is classified at one boundary, connectivity failures feed a Redis-shared sitewide verdict, a 60-second probe cycle discovers recovery and clears it, prep pipelines park themselves and resume on their own, and the app frame shows one quiet prose strip while it lasts.

The incident that shaped it

On 2026-07-30 a single hung HTTPS connection during a world build sat silent for undici's default five-minute headers timeout, its retry was doomed by the stage's already-spent call budget, and the player saw "The world stalled" on the first transient failure. Three user-stated goals fell out of the post-mortem: discover an API outage fast, show a sitewide indicator while it lasts, and clear it automatically on recovery. The design (v5, four blind review rounds) added a fourth behavior that does most of the actual work: prep pipelines that hit a transient failure should ride it out on their own instead of surfacing a dead end.

The system splits into a passive detector (real traffic reports its own failures), an active recovery probe (the only synthetic traffic, and only while degraded), a parking mechanism for prep jobs, and a notice surface. Each piece is useful alone; together they close the loop the diagram shows.

Failing fast: two transport dispatchers

llm-fetch.ts builds a custom fetch that every Anthropic request now flows through (models.ts hands it to createAnthropic({ fetch }), so all three tier constants carry it). It holds two undici Agents with different timeout profiles and picks one per request, mechanically: the provider body is a JSON string, so a body containing "stream":true routes to the streaming dispatcher and anything else — including a non-string body — routes non-streaming. Streaming requests get a tight leash (10s connect / 60s headers / 120s body idle); non-streaming requests keep a 300s backstop.

Why headers-timeout only works for streams — on a non-streaming Anthropic call, response headers arrive together with the finished completion, so a hung connection and a healthy still-thinking Opus call are the same wire state and no tight timeout can tell them apart. A streaming response returns headers within seconds, which makes headers-arrival a valid hang detector — but only on that dispatcher. This asymmetry runs through the whole design: it is why prep calls migrated to streaming transport, and why the abort-classification rule below is dispatcher-aware.
npm undici, matched by code, never instanceof — the Agent and fetch both come from the npm undici package (mixing an npm-undici Agent into Node's global fetch is unsupported), and the lockfile carries a transitive undici@5 beside the npm undici@7 — two realms of the same error classes exist at runtime, so the classifier matches undici errors by their UND_ERR_* code strings. The one pre-authorized type assertion in the feature lives at this boundary: npm-undici's fetch types are structurally incompatible with global fetch's in both directions, while the runtime is fully compatible for everything the AI SDK sends.

The fetch also records an observation per request — {mode, headersArrived} — and exposes it to the classification boundary through a per-attempt exchange keyed on the attempt's AbortSignal identity, last-invocation-wins. That last part matters: SDK-internal retries share one signal, and without it a first invocation's late headers arrival would pollute the classification of the attempt that actually failed.

Two axes, one walk: the failure taxonomy

classify-llm-error.ts is a pure, import-free module that classifies every failed call along two independent axes: retry-worthy (should the attempt loop try again?) and outage-signal (should this failure count toward the sitewide window?), plus a failure class (connectivity | rate-limit | abort | other) that the parking predicate reads downstream. The two axes deliberately disagree in places: a 429 is retry-worthy but never outage signal (rate limiting is our traffic shape, not their outage); a non-streaming wall-clock abort is retry-worthy but never outage signal (no headers at abort is the healthy state on that dispatcher); a schema-validation failure is neither.

Classification is an unwrap walk, bounded at depth 5, over whatever shape surfaced: the SDK's AI_RetryError takes its retry verdict from the last member but its outage verdict from any member (the incident's own shape was [headers-timeout, abort] — last-member-only would discard the genuine signal); APICallError status codes count only at ≥400, because mid-body connection deaths arrive as "Failed to process successful response" with statusCode: 200 and the real undici error in cause; anything with a cause recurses. Base cases match by string: the UND_ERR_* family, connect/DNS/socket errnos, TLS-layer codes, and HTTP 5xx/529. The dispatcher-aware abort rule closes the walk: an abort that never saw headers is connectivity on the streaming dispatcher and a plain retryable abort on the non-streaming one — the transport observation exists to carry exactly that bit.

One mapping addition rides in the middleware rather than the classifier: mid-stream Anthropic error events on an open stream (overloaded_error, api_error) arrive as raw JSON payloads, not Error instances. The middleware's in-stream arm maps them to LlmOverloadedError and the new LlmUpstreamError, carrying the raw payload as cause so the walk still sees it. Without that arm the generic fallback mints Error("[object Object]") and a partial overload on the streaming path dies unclassified.

Wrapper-owned attempts

Before this feature there was no application-level retry loop — "Failed after 2 attempts" in old logs was the AI SDK's internal maxRetries. The contract now lives in ai.ts: a prep call site passes stageBudgetMs and the wrapper owns the attempts (SDK retries forced to 0). Internally the loop drives the SDK's streaming transport (streamText + Output.object) and assembles the final validated object, so the tight streaming dispatcher watches every attempt; the external contract — schema in, validated object plus usage out, same repair chain — is unchanged.

Every attempt gets the FULL remaining budget — the loop never divides remaining time across attempts. Hang detection rides the transport timeouts (a hung attempt costs at most ~60–120s), so a healthy long attempt is never killed by arithmetic. The design review established that any division re-creates the incident's doomed retry: attempt two inherits a sliver of budget, cannot finish healthily, and dies as a misclassified abort. The companion rule is the retry gate: a retry starts only if the remaining budget still fits expectedHealthyDurationMs (60s default for fast calls; slow stages pass their observed healthy duration) — starting a retry that cannot healthily finish wastes spend and ends in the same misclassified abort.

Retry-worthy failures retry up to three total attempts with a fresh AbortController and jittered backoff ≤2s; a 429 waits max(jitter, retry-after) and the gate accounts the wait against the budget. External aborts win — after any failed attempt, if the caller's own signal is aborted the loop bails with no retry and no report. Schema failures run the existing haiku-then-sonnet repair chain inside the attempt, bounded by the attempt's remaining budget, and — new — a connectivity-classed repair failure surfaces to the loop as a retryable transport failure instead of silently converting to a terminal schema error. The loop's scope is deliberate: only calls whose output ai.ts assembles internally. Externally-consumed streams (the world-gen stages that feed partials to SSE mid-flight) get classification and reporting only — a consumed stream cannot be transparently re-driven, and a naive retry would double-publish partials. Their retry unit is the whole stage, via parking.

The sitewide verdict: a Redis state machine

llm-health.ts holds the fleet-shared outage state under llm-health:* keys (behind the usual redisKeyPrefix, so worktree / test / staging isolation holds). Every connectivity-class attempt failure reports into a 30-minute rolling ZSET window through a boot-injected sink (setLlmHealthSink — the API server and the worker both bind it to tracker.report at boot; ai.ts itself stays dependency-free, and a sink failure is logged and eaten, never surfaced to the calling stage). The state machine: 

healthy  --(≥3 connectivity failures within 10 min spanning
            ≥2 distinct call sites OR ≥2 distinct jobs)-->  degraded
degraded --(3 consecutive probe cycles all-succeed; counter reset by
            any probe failure OR any new connectivity report)--> healthy
The distinctness rule — one world failing one stage repeatedly never trips the sitewide strip (that player is covered by the parked hold copy on their own surfaces); one world failing two consecutive stages trips it; two worlds failing the same stage trips it. The 10-minute arming window matches failure-manifestation latency — hang events arrive minutes apart per pipeline, and a tight window could never assemble three at launch concurrency. The clear side carries its own hysteresis, so the wide window cannot flap.
Both transitions are Lua scripts — arm is evaluate-window + SET NX + seed the models SET in one atomic unit; clear is verify-counter + DEL of all four keys in one. The design review showed every check-then-act variant leaks a race (a concurrent reporter's counter reset lost to a clear that already decided, or a double-arm). The implicated model ids live in a separate Redis SET rather than a JSON array inside the state blob for the same reason: SADD is atomic and commutative; a read-modify-write JSON array is a lost-update race across concurrent reporters. Window scores come from Redis TIME, never local clocks.

Every key carries a 30-minute TTL that only still-down probe cycles refresh — so if the probe worker dies mid-outage, the degraded state expires on its own rather than pinning the strip up forever. Transitions emit llm_health.degraded / llm_health.recovered structured logs carrying the model set and a window summary, so triage works from CloudWatch without Redis access.

The recovery probe

llm-health-probe.ts runs as a BullMQ repeatable job on its own queue, one cycle every 60 seconds, registered idempotently via upsertJobScheduler on every worker boot. A healthy cycle is one Redis GET plus a cheap armed-stamp scan. A degraded cycle probes every implicated model in parallel — SMEMBERS llm-health:models, falling back to all three tier constants when the set is empty (an empty set must never be a vacuous success). Each probe is one minimal single-attempt call: SDK retries 0, outside the attempt loop, 30s wall clock, cost attributed to a reserved system label. All targets succeeding increments the clear counter; any failure resets it and refreshes the state TTL. Single-flight is a timing invariant — a full cycle always finishes inside the 60s interval — not a concurrency setting.

The probe suppresses thinking and its own health reports — Claude 5 models think adaptively by default, and an unsuppressed probe that thinks past its 30s wall clock reads as a probe failure against a healthy API, fail-closing the strip indefinitely; the probe passes thinking: disabled and counts success as "the call resolved," regardless of finish reason. It also passes skipHealthReport: a probe failure must feed the clear counter only — reported into the arming window it would supply exactly the call-site diversity the arm threshold needs, letting the probe manufacture a sitewide outage from one struggling model.

When the counter reaches three, the Lua clear fires and the cycle runs the recovery fast-path: scan runs with armed resume stamps and promote() their delayed jobs so parked worlds wake immediately instead of waiting out a 15-minute ladder rung. The scan is guarded by a fire-once net — a promote-pending flag set before the scan and cleared only after it completes — so a probe-worker death (or a Postgres blip) between clear and scan leaves the flag up and the next healthy cycle re-runs the full scan rather than stranding tail-rung worlds. Healthy cycles without the flag promote past-due stamps only: a future-dated stamp is a ladder delay in progress, and hot-promoting it every 60s would burn the park budget. Job identity recovery parses ids at fixed UUID widths (sp-/cc- ids embed hyphens — never split('-')), and every promote is catch-and-continue because the natural wake may have raced. Known hysteresis, accepted: three probe cycles plus the poll interval ≈ up to four minutes of stale "down" copy after true recovery, and a stale in-flight non-streaming call can reset the counter once more.

Parking: the job delays itself

When a prep processor (world-gen, session-prep, character-creation) contains a non-terminal failure whose class is park-eligible — connectivity or rate-limit; a sustained 429 window is exactly what a backoff ladder rides out, though rate-limit still never feeds the strip — and park budget remains, it does three things: mark the stage row failed exactly as today, persist a resume stamp, and re-arm its own BullMQ job with job.moveToDelayed(now + delay) followed by a DelayedError throw (the control signal BullMQ expects for a sanctioned self-delay — the containment wrapper recognizes it and logs at info, not error). The same job wakes itself later: no add, no dedup interaction, single-flight by construction.

The stage row stays failed; the STAMP is what means "parked" — the wake claims the stage through the normal claim path, and a claim only succeeds against a failed (or stuck) row. Leaving the row running would make the wake's claim return lost-race and skip the parked stage — silent world corruption. So parked and genuinely-failed runs are byte-identical in pipeline_runs; the llm_resume_stamps row (migration 038, keyed (pipeline, entity_id)) is the single discriminator, and every status derivation reads it.

The stamp's fields split by consumer. next_resume_at arms the wake and clears on stage claim — the overdue predicate needs "armed and past due" to go false the moment the stage starts. resume_attempt (the ladder rung), park_consumed_ms (the spent budget), and last_error_class (the hold copy's key) all survive claims and clear only on stage completion — clearing them on claim would reset the ladder to the 30-second rung on every wake, hot-cycling a solo-world outage with unbounded spend. The ladder runs 30s → 2m → 5m → 15m and holds at 15m; the budget is total parked wall-clock, park_consumed_ms ≥ 6h, not a rung count.

A wall-clock budget, decoupled from the sitewide state — a solo-world outage can never trip the sitewide threshold (the distinctness rule), so its parks must self-fund; a rung count would burn a solo world out in ~40 minutes, while 6 hours of parked wall-clock rides out a realistic provider incident. The coupling runs the other way too: while the site is known-degraded, waking attempts re-park without consuming budget — each processor reads the health state before claiming (check, then claim, then attempt, pinned in that order), so a world parked through a long sitewide outage still has its full ladder when the API returns. Exhaustion lands on today's failed path — the retryable surface, never the terminal "start fresh" view — and a manual retry after exhaustion starts a fresh episode (fresh 6-hour budget, rung 1): mid-outage, the retry button must arm a new ride, not instantly re-exhaust.

Safety nets

Three nets close the gaps parking opens (and one it merely inherited). First, the stage claim in pipeline_runs gained a distinct in-flight result for running-not-stuck rows, and every processor loop now stops on it with a retryable throw instead of skipping past the stage. That fixes a pre-existing defect the wake path would have amplified: BullMQ's stall handling re-drives a dead worker's job once, the dead attempt's row sits running under the stuck-reset threshold, and the old lost-race branch silently completed worlds with missing stages.

Second, terminal broker failures. A parked run's wake that dies terminally (stall-count exhaustion) leaves an entity in-progress forever with no job — the overdue predicate cannot see it because the claim already disarmed the stamp. prep-queue-events.ts subscribes QueueEvents on the three prep queues (the MYT-67 session-turn precedent, each on its own dedicated blocking connection) and recovers identity from the broker event's jobId alone, parsed at fixed UUID widths — the prep queues keep removeOnFail: {count: 0} (age-retention would reintroduce the held-jobId dedup landmine), so the job object is already gone. The handler cross-checks the resume stamp, drives the pipeline's existing terminal path, and clears the stamp last.

Third, the overdue arm: a stamp whose next_resume_at passed more than five minutes ago without a stage start derives as failed/retryable — a pure row predicate, no queue I/O. The manual-retry routes, which can reach the queue, additionally check for a live job holding the base id before re-adding (a held id makes the add a silent no-op), so a backlogged-but-alive wake answers the in-progress shape instead of being offered a duplicate retry.

The player-facing surface

GET /api/llm-health is a public route (mirroring /health/ready — it serves a binary {state, since} with no tenant data, and the poll must not burn a JWT verify per tab per minute) doing one Redis read through the tracker. The frame polls it every 60 seconds and renders the NoticeStrip — a slim quiet prose strip under the sticky bar, no icons, no dismiss — while degraded. The frontend hook treats "degraded" as a positive assertion only: a failed poll reads as ok, because the strip relays the backend's Redis verdict rather than detecting outages itself. The strip's copy stays true during a partial-model outage (an Opus-only outage arms it while Sonnet answers every live turn), which is why it says "unsteady," not "down."

Parked prep runs get their own hold copy on the surfaces that watch them — the worldgen generating and reveal views, session-prep waits, and character-creation loading. The class is keyed off the snapshot/status derivation (the persisted stamp), never only the live SSE event: CloudFront buffers SSE, and the generating view invites leave-and-return, so the hold must re-derive on every reconnect. While parked, the hold copy owns the wait narrative — the ETA countdown and the "still working" stalled line are suppressed, because "Still working" and "the making was interrupted" must never share a screen. The world-gen experience page covers the view mechanics.

Operating this piece

Check, arm, or clear the outage state (local / staging)

  1. pnpm --filter @mythrun/backend exec tsx scripts/smoke/llm-health-smoke.ts status — prints the tracker's state and implicated models. The script loads config through loadEnv(), so it writes under the REAL derived key prefix (${env}:${region}:) — a hand-read REDIS_KEY_PREFIX writes keys the server never sees.
  2. … llm-health-smoke.ts arm — fires three connectivity reports across two call sites through the production Lua arm path. The strip rises within one poll interval.
  3. … llm-health-smoke.ts clear — DELs state, counter, window, and models.

Manually clear a stuck degraded state (production)

  1. Production Redis is in-VPC: use the ECS run-task / exec path to reach it (see smoke testing for the pattern).
  2. DEL the four keys under the environment's prefix: llm-health:state, llm-health:probe-successes, llm-health:window, llm-health:models.
  3. The strip clears on the next poll. Parked jobs keep their ladders; the next healthy probe cycle promotes past-due stamps.

Pre-emptively arm during a known incident

  1. SET <prefix>llm-health:state '{"since":<epoch-ms>}' and SADD <prefix>llm-health:models <model-id…>.
  2. This raises the strip and — because processors read the health state before claiming — stops parked runs from consuming their ladders while the incident lasts.

Diagnose a degradation from CloudWatch

  1. Filter on event: 'llm_health.degraded' — the log line carries the implicated model set and a window summary (call sites, job ids), so triage needs no Redis access.
  2. llm_health.probe_cycle_failed lines show which models are still failing while degraded; llm_health.recovered carries the outage duration.
  3. Park activity logs as world_gen.stage_parked (and the session-prep / character-creation equivalents) plus job.parked at the containment boundary, and wake promotions as llm_health.resume_promoted.

Integration points

The LLM client page documents the wrapper this feature instrumented — the transport fetch rides under models.ts's provider, and the attempt loop is a seam of ai.ts's generateObject. The worker registers the probe queue, the QueueEvents subscribers, and the health sink at boot. The three prep pipelines — world gen, session prep, and character creation — own their park sites and wake claims; character integration never parks but shares the stop-on-in-flight claim discipline. Pipeline status explains how the stamp reaches phase derivations and SSE snapshots. On the frontend, the app shell owns the strip and the poll, and the world-gen experience owns the parked hold views.
