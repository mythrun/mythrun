Cost measurement

The harness that answers "what does a turn actually cost?" with a number nobody has to trust. A scenario driver exercises the real stack against the real Anthropic API, a measurement window closes when the queues drain, and every llm.call line inside that window is priced against the billing rate table and asserted against a pinned band. It exists because the cheap alternatives — reading token counts off a dashboard, or pricing the SDK's inputTokens directly — are wrong by three to five times on a cached call, and because a caching optimization that silently stops working looks exactly like one that never worked.

How it fits together

pnpm cost:smoke <s1|s2|s4|s5> runs one scenario end to end: a liveness gate, a drive, a capture, an assertion pass, and a one-page report. The four scenarios cover the money paths — S-1 scripts ten player turns over a real WebSocket session, S-2 re-asserts S-1's window for cache health rather than re-driving it, S-4 walks character-finalize through integration into session prep, and S-5 generates a world. Runs are serial and on demand. None of this is wired into pre-push or CI: a full suite costs a few dollars of live spend, and a gate that bills money on every push is a gate people learn to skip.

The window is the measurement

A scenario's cost is "every LLM call this scenario caused", which is a harder boundary than it looks. Work continues after the last user-visible event: in a measured 10-turn session the Slow Thinker's final evaluation landed 64 seconds after the last frame reached the client. So the window does not close on the driver finishing — it closes on drained-queue quiescence, when waiting, active, and delayed all read zero across the queues that scenario touches, held for a settle interval. The opening edge matters as much: fromMs is stamped after the scenario's setup work (a world, a session prep) and before the first measured turn, so setup spend that a real player would not pay per-turn stays outside the numbers.

Each scenario derives its own queue set — copying S-1's list into a new scenario is the obvious shortcut and it under-measures. S-1 omits the reconcile and analysis queues correctly, because those fire only from the farewell path and a scripted session never ends that way. A scenario that does end its session and inherits that list would drop two Opus calls from its totals and still report a confident PASS.

Capture reads the logs, not the database

The dev stack tees raw pino NDJSON to backend/logs/dev-<date>.log (API leg) and dev-worker-<date>.log (worker leg), which is what the harness reads. Both legs are merged, lines outside the window are dropped, and what remains is filtered by scope: a line counts only if it carries the run's sessionId or campaignId. That filter is why the call-site stamps are load-bearing rather than nice-to-have — an unstamped call does not fail the filter loudly, it simply never appears.

Two escape hatches keep that strictness honest. Lines that fall inside a session window but carry a foreign stage — the structured-output repair path re-stamps a retry with the parent world-gen stage while keeping the session id — are dropped and reported, never silently filtered. And the genuinely id-less calls, the preview-time concept synthesis that runs before any campaign row exists, are captured by a separate stage-and-window-only pass that cannot double-count against the scoped one.

Pricing, and why it is not a multiplication

The SDK reports inputTokens as a sum of fresh input, cache reads, and cache writes. Pricing that number against the input rate is the intuitive move and it overstates a healthy Fast Thinker line by 3.7×. The derivation the harness uses instead: 

base    = inputTokens − cacheReadTokens − cacheWriteTokens   @ input rate
reads   = cacheReadTokens                                    @ 0.1 × input rate
writes  = cacheWriteTokens                                   @ 1.25 × input rate
output  = outputTokens                                       @ output rate

Rates come from billing/model-pricing.ts and nowhere else, so the harness and the credit ledger can never disagree about what a model costs. An unknown model throws rather than guessing, and a negative base — which would mean the SDK's sum semantics had changed underneath us — throws too.

Bands, not numbers

expected-costs.json holds a per-component entry with a tolerance, seeded from three to five live baselines rather than a single run. The tolerances are wide where reality is wide: Fast Thinker cost per turn carries ±35% because prose length genuinely varies (output tokens nearly doubled between two otherwise-identical runs), while the S-4 prep path sits inside a much tighter ceiling because three runs landed within 4.7% of each other. Dollar figures are only ever pinned from runs the harness itself measured — never from a planning document — because a band seeded from an estimate asserts the estimate, not the system.

Cache health is asserted separately, as violations rather than dollars: on S-2, every Slow Thinker evaluation, gate, and tripwire call must show cache reads, with narrow accommodations for the first cold write of a session and for gaps that outlive the five-minute cache TTL. The gate and tripwire arms additionally carry the measured token size of their stable span, because a prompt cache only engages above a model-specific minimum — 4,096 tokens on Haiku. The gate's span measures 4,753, which is roughly 650 tokens of headroom: if a future prompt trim shortens the playbook, caching stops silently, so the arm is written to log rather than fail when the span drops under the floor.

Assert the mean of a scenario, not a single call — per-call cost is dominated by model nondeterminism, so a per-call assertion would flap constantly and get muted. Scenario means over a fixed script are stable enough to hold a band, and a real regression (a cache breakpoint that stopped matching, a prompt that doubled) moves the mean well outside it.

Operating this piece

Run a cost smoke locally

  1. Start the dev stack with pnpm dev — the log capture the harness reads comes from that wrapper, so a stack started any other way produces an empty capture.
  2. From backend/, run pnpm cost:smoke s1 (or s2 / s4 / s5). Expect a few dollars of real spend for a full sweep.
  3. Leave the stack alone while it runs. Editing anything under backend/src/ restarts a watch-mode server mid-run and kills the in-flight session.
  4. Read the report table: PASS/FAIL per component, plus INFO rows for components that are captured but not yet banded.

Re-check a manifest edit without paying again

  1. A successful drive saves its window and scope ids under backend/logs/cost-smoke/.
  2. Run pnpm cost:smoke <scenario> --reassert to replay that saved window through extraction and assertion with no LLM calls at all.
  3. Use this whenever you are tuning tolerances — re-driving to test a band edit is pure waste.

Re-pin a band after an intentional change

  1. Run the affected scenario three times and record the actuals.
  2. Update the entry in backend/scripts/cost/expected-costs.json — the mean for cost-shaped rows, a ceiling with headroom for rows where the spread is small.
  3. --reassert the saved window to confirm the new band accepts the observed run.
  4. Say in the commit message what changed and why the old band no longer describes the system.

Integration points

The lines this harness reads are produced by the LLM client's logging middleware, and priced with the same table the billing metering path uses. The caching this harness proves lives in the Slow Thinker and Scribe prompts. A weekly unattended run is wired on staging and described in smoke testing; it emits a cost_smoke.failed line on either failure path so a metric filter can catch it.
