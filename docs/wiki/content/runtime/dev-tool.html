Dev tool

A local-only engineering UI that drives the development backend through a Vite proxy, plus the ship gate that keeps it honest. The tool itself is throwaway — not a prototype of the production frontend. The gate is the durable piece: a single command (pnpm dev-tool:check) that fails CI when the prep-pipeline's HTTP, SSE, or BullMQ contracts grow an entry the dev tool can't drive.

How it fits together

The dev tool is a tiny Vite + vanilla TypeScript workspace under backend/dev-tool/, exposed as @mythrun/dev-tool in the monorepo. It serves on http://127.0.0.1:5273 via pnpm dev:dev-tool and talks to the local backend on localhost:3000 (or whatever PORT is set in backend/.env.development). The browser only ever sees same-origin requests because Vite's dev server proxies /api/* and /health/* to the local backend process; no CORS plugin sits on the backend.

Local-only, not staging-pointable — Mythrun ships a six-layer defense against the auth-bypass plugin ever booting in a deployed environment (see JWT middleware). A dev tool that could swap origins to point at staging would be an internet-exposed surface that mints requests with arbitrary x-mythrun-dev-sub identities — a credentialless RCE on auth. There is no env switcher, no staging mode, no CORS plugin. Staging validation goes through smoke testing instead.

Five files do the work. vite.config.ts binds the dev server to 127.0.0.1 with strictPort: true and reads PORT out of backend/.env.development at config time so the proxy target stays in lockstep with the backend without a second source of truth. src/identity.ts owns the DEV_SUBS list (dev-user-1 through dev-user-5) and persists the active selection in localStorage under mythrun.devtool.devSub. src/api-client.ts is the single fetch wrapper: every HTTP call in the app goes through apiCall(path, init), which stamps x-mythrun-dev-sub on every request and rejects absolute or protocol-relative paths. src/main.ts mounts the page; src/components/ holds the per-panel UI — currently the health panel, the pipeline status panel (an SSE consumer for /api/campaigns/:campaignId/status/stream), and the campaign-create, campaign-details, and credit-ledger panels added with the world-gen pipeline. Character-creation consumers will land alongside their routes.

Vanilla TS, not React — the dev tool's job is to make HTTP calls and render their responses. Adding React + a state lib would land 400 KB of dependencies for a throwaway. Vanilla DOM with one apiCall helper keeps the codebase small enough that a contributor can read the whole thing in one sitting and reason about every fetch path without grepping through hooks.

Bring-up

From the repo root, three commands. pnpm install materializes the workspace and its Vite dependencies. pnpm dev brings up the backend under tsx watch with the local Postgres + Redis stack (see backend overview). pnpm dev:dev-tool starts Vite on 127.0.0.1:5273; opening that URL loads the page and the smoke panel fires a GET /health/ready through the proxy. A green result means every layer of the stack — Vite, the proxy, Fastify, the boot-gate-managed pg + Redis clients — is healthy.

Smoke through the proxy, not direct to localhost:3000 — exercising the proxy path on the very first render means the bring-up failure modes (proxy target wrong, backend not running, env file not loaded) surface immediately and visibly, instead of hiding until the first identity-stamped call.

The identity switcher

The header carries a dropdown wired to the DEV_SUBS list. The selected value lives in localStorage under mythrun.devtool.devSub; api-client.ts reads it on every call and sets it as the x-mythrun-dev-sub header. The Phase 0 smoke panel hits /health/ready, which is a public route — identity has no observable effect on the response. That's expected: the surface that consumes the header lands in MYT-50 alongside the first authenticated pipeline routes, and the auth-bypass plugin (dev-only) is what reads the header to populate request.user. Future multi-player flows switch identities between requests to act as different players against the same world or campaign.

Five identities, not three — the world-and-campaign pipeline spec calls for 2–5 player groups; five synthetic users cover that range with one spare for solo-test scenarios. MYT-51's seed migration is responsible for inserting exactly those rows in Postgres so authenticated routes work end-to-end; the dev tool holds the canonical list, the migration consumes it.

The ship gate

The gate exists because the dev tool is the only place inside the repo where the prep pipeline's HTTP, SSE, and BullMQ surfaces are exercised by a human. Without enforcement, "add a new route" silently means "the dev tool has no way to trigger or observe it" — the next contributor to touch that area finds out by guesswork. The gate makes the wiring an explicit, mechanical step.

Three files at backend/src/contract/ are the source of truth: pipeline-routes.ts (HTTP routes, format 'METHOD /api/path'), pipeline-events.ts (SSE event names), and pipeline-jobs.ts (BullMQ job names). Each is a readonly string[] typed array, seeded empty at Phase 0; entries accumulate as MYT-50 onward lands real routes. backend/dev-tool/coverage.json declares what the dev tool actually covers, in three matching arrays plus an exempt object whose values are human reasons for entries the tool deliberately skips.

pnpm dev-tool:check runs backend/scripts/dev-tool-check.ts, which loads the three contract constants and the coverage JSON, then calls the pure checkCoverage(contracts, coverage) function from backend/src/dev-tool-check/check-coverage.ts. The function errors when a contract entry is missing from coverage and not in exempt, errors when an exempt reason is shorter than 20 characters, errors when an exempt entry references a contract entry that no longer exists, and warns when a coverage entry is no longer in the contract. Errors exit the script with code 1; warnings don't.

Pure function under a CLI shell, not a single script — the same pure checkCoverage runs under Vitest with synthetic fixtures, so the gate's behavior is exercised on every test run, not only when a contributor remembers to run the CLI. The CLI shell is the thinnest possible filesystem-and-process wrapper around the pure core.

CI wires the gate through .github/workflows/dev-tool-check.yml, a peer of wiki-check.yml: it runs on every pull_request and on push: branches: [main], scoped via paths: to the gated surface so unrelated PRs don't pay CI minutes. The install step is pnpm install --frozen-lockfile --filter @mythrun/backend... — the backend workspace is everything the script needs.

A dedicated workflow file, not a step in deploy.yml — deploy.yml only fires on push-to-main, so a PR that broke the contract would slip past review. Adding the step there would also bloat the deploy job's running time without improving coverage. The peer-workflow pattern matches what wiki-check.yml already does for the same reasons.

The Phase 0 contracts are empty, so today the gate is a no-op that proves the wiring works. The shape locks in now: adding a pipeline route is a three-file change in a single PR — append to pipeline-routes.ts, add the UI in backend/dev-tool/src/, extend coverage.json's routes array. Forgetting any one of them red-CI's the gate. Events and jobs follow the same pattern with their own contract files and arrays.

The exempt list

coverage.json's exempt object lets the gate accept "contract entry exists, but the dev tool deliberately doesn't drive it." Each entry is keyed by the contract string and its value is a free-text reason; the gate enforces a 20-character minimum so the failure mode "punt past the gate with 'TODO'" doesn't fly. A real reason names who decided to exempt, why, and ideally points at the Linear issue that will eventually address the gap. The list is reviewed in PR like any other code change.

20-character floor, not a free-form text field — pre-blind-review, the exempt reason was unvalidated. The blind reviewers noted that without a minimum, the gate's escape hatch becomes a single keystroke. Twenty characters is enough room for "MYT-NN tracked, defer" and short enough that "we'll exempt this for now" stays uncomfortable.

Hard rules

Five conventions are enforced by code review and the structure of the codebase itself:

  • Local-only by design. No env switcher, no staging mode, no @fastify/cors plugin on the backend. Staging validation lives in smoke testing; the dev tool exists to iterate on the local backend.
  • All HTTP calls go through api-client.ts's apiCall. No bare fetch anywhere else. No absolute URLs. The path guard rejects bare URLs (missing leading /) AND protocol-relative paths (leading //) because fetch('//evil.com/x') would otherwise resolve against the page origin's scheme and leak x-mythrun-dev-sub to a foreign origin.
  • Use .textContent, never .innerHTML. Defense against any stored-XSS-shaped response surface ever appearing in a future panel. Cheap, mandatory.
  • No secrets in localStorage. Only mythrun.devtool.devSub lives there. Tokens, JWTs, Anthropic keys do not. If a future surface needs a token, it goes in-memory or sessionStorage at minimum.
  • The ship gate is not skippable. pnpm dev-tool:check runs on every PR; merging a contract change without the matching coverage entry (or a real exempt reason) is a red CI build, not a "we'll fix it in a follow-up."

Operating this piece

Run the dev tool locally

  1. Bring up the backend per the backend page: pnpm db:up, then pnpm dev in one terminal. Wait for the app.listen log line.
  2. In a second terminal, from the repo root: pnpm dev:dev-tool. Vite reports Local: http://127.0.0.1:5273/.
  3. Open the URL. The health panel fires GET /health/ready on load; a 200 response with {"ready":true} means the proxy, backend, and data layer are all live.
  4. Pick an identity from the header dropdown. The selection persists across reloads via localStorage. Every subsequent call carries it as x-mythrun-dev-sub.

Add a pipeline route (the shape the gate enforces)

  1. Append the route to backend/src/contract/pipeline-routes.ts in the 'METHOD /api/path' form. This is the source of truth.
  2. Add the route handler under backend/src/routes/ and wire it into app.ts's plugin registration.
  3. Add a component under backend/dev-tool/src/components/ that drives the new route via apiCall, and mount it in main.ts.
  4. Add the same 'METHOD /api/path' string to the routes array in backend/dev-tool/coverage.json.
  5. pnpm dev-tool:check locally — must exit 0. If it errors, the message names exactly which contract entry is uncovered or which exempt reason is too short. The same PR contains all four changes. CI runs the same check on push.

Exempt a contract entry (rare)

  1. Add the contract string as a key under coverage.exempt.<routes|events|jobs> in backend/dev-tool/coverage.json. The value is the reason.
  2. Write a real reason of at least 20 characters: who decided, why the dev tool can't drive it, and the Linear/MYT-* issue tracking the gap. The gate errors on shorter strings.
  3. Open the PR with the exempt change visible alongside the contract change. Reviewers push back if the reason isn't substantive.
  4. When the issue lands and adds coverage, the exempt entry is removed in the same PR — leaving a stale exempt entry whose contract entry has moved into coverage.routes is fine, but leaving an exempt entry whose contract entry no longer exists is an error and red-CI's the gate.

Diagnose a failing dev-tool:check

  1. The script prints one error: line per problem before the summary. Read the line — each names the kind (routes / events / jobs), the entry, and the action required.
  2. "in contract but not in coverage and not in exempt" — the contract grew an entry the dev tool doesn't drive. Either add the UI + coverage entry, or add an exempt entry with a real reason.
  3. "exempt reason is too short" — the value under exempt.<kind>[entry] is < 20 characters. Write a real reason.
  4. "in exempt but no longer in contract" — the contract entry was removed but the exempt entry wasn't. Drop the exempt entry.
  5. Warnings (warn: prefix) — coverage entry no longer in contract. Non-fatal; consider removing the coverage line.

Integration points

The dev tool drives the backend's HTTP surface through the Vite proxy; it consumes the same x-mythrun-dev-sub header the auth-bypass plugin in the JWT middleware reads to populate request.user in development. The ship gate's contract files (backend/src/contract/) are the seam future world-and-campaign pipeline routes register against; the spec amendment in docs/specs/2026-04-13-world-campaign-pipeline.md §12 codifies the local-only stance. Staging validation goes through smoke testing, not this tool.
