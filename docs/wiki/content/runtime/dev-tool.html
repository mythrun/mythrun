Dev tool

A local-only engineering UI: a Vite-served single-page shell that exposes every backend route as its own endpoint × method panel, with a shell-owned active-campaign store and a persistent right-side wire-log drawer that owns the SSE stream. The tool itself is throwaway — not a prototype of the production frontend. The ship gate (pnpm dev-tool:check) plus a registry-invariant test keep coverage honest.

How it fits together

The dev tool is a Vite + vanilla TypeScript workspace under backend/dev-tool/, exposed as @mythrun/dev-tool in the monorepo. It serves on http://127.0.0.1:5273 via pnpm dev:dev-tool and talks to the local backend on localhost:3000 (or whatever PORT is set in backend/.env.development). The browser only sees same-origin requests because Vite's dev server proxies /api/* and /health/* to the local backend process; no CORS plugin sits on the backend.

Local-only, not staging-pointable — Mythrun ships a six-layer defense against the auth-bypass plugin ever booting in a deployed environment (see JWT middleware). A dev tool that could swap origins to point at staging would be an internet-exposed surface that mints requests with arbitrary x-mythrun-dev-sub identities — a credentialless RCE on auth. There is no env switcher, no staging mode, no CORS plugin. Staging validation goes through smoke testing instead.

The shell

src/main.ts mounts two long-lived pieces into the page's <header> and <main> on load: the identity switcher (a dropdown wired to DEV_SUBS from src/identity.ts) and the shell composition root (src/shell/shell.ts). The shell carves <main> into a banner row on top of a horizontal flex row containing sidebar | mainPane | drawer. Banner + sidebar + drawer mount once and persist for the lifetime of the page. The mainPane is the single slot the shell lazy-mounts a panel into when the user clicks a sidebar leaf, tearing the previous panel down before mounting the next.

Mount one panel at a time, not all of them at once — the pre-myth-mbdc layout registered fourteen panels into a single vertical-scroll page; every backend interaction lived in one giant column. As route count grew past forty, panels were competing for attention, the page was unscrollably long, and panels with their own EventSource each opened sibling connections to the same SSE stream. The shell + sidebar + lazy-mount pattern collapses the surface to "one endpoint × method visible at a time" and pushes the SSE socket up to one shared owner (the drawer).

Every panel returns a PanelHandle = { root, unmount() } from its mount function. The shell holds the currently-active handle; on sidebar selection change it calls activePanel.unmount(), clears the mainPane's children, looks up the new panel's mount function in the PANEL_MOUNTS map, and mounts it. Panels self-register on import by calling registerPanelMount(method, path, mountFn) from the shell — so the side-effect imports at the top of main.ts are what populate the map. The sidebar's selected leaf persists across reloads in localStorage under devtool.selectedPanel.

Self-registration, not a central panel list — a central registry would mean every new panel ticks two files (the panel itself + the registry list) and the registry would grow into a hand-maintained merge-conflict magnet. Self-registration via registerPanelMount means the panel module declares the route it implements at the point that knowledge lives, and main.ts just imports the file. The invariant tests at __tests__/verify-registry.test.ts catch the obvious failure modes (panel exists but not imported; route in the contract but no panel).

The sidebar

src/shell/sidebar.ts renders the leaf list, grouped into six sections — CAMPAIGNS, WORLD, CHARACTERS, USERS & ACCESS, BILLING, SYSTEM — in that fixed order. Each leaf is one endpoint × method pair from src/shell/route-registry.ts's ROUTE_PANELS array; the leaf renders the HTTP method dimmed alongside a human-friendly label ("Create", "Roster", "Grant credits"). Leaves whose route carries requiresCampaign: true render disabled (dimmed, cursor-not-allowed) when the active-campaign store is null, and become selectable the moment a campaign is picked.

ROUTE_PANELS is the source of truth for the sidebar's contents. Adding a new backend route is a four-file change: append to backend/src/contract/backend-routes.ts, append to ROUTE_PANELS with its section and label, ship the panel module under src/components/, and either add the panel to a pipeline contract's coverage or list it as exempt. The route-registry.test.ts invariant errors when a backend route is neither in ROUTE_PANELS nor in EXEMPT_ROUTES.

The active-campaign store

src/shell/active-campaign.ts owns the single source of truth for "which campaign is the operator currently working on." It persists to localStorage under devtool.activeCampaignId and exposes getActiveCampaignId(), setActiveCampaignId(id | null), and onActiveCampaignChanged(cb). The CAMPAIGNS / My campaigns panel sets the active id when the operator clicks a row; the banner reads it to render its anchor; the sidebar re-renders on change to enable or dim requiresCampaign leaves; the drawer's subscription manager opens an EventSource for the new id and closes the one for the old.

Shell-owned store, not panel-to-panel custom events — the pre-myth-mbdc layout used four custom DOM events (mythrun.watchcampaign / mythrun.closewatch / mythrun.opendetails / *.clear) to fan a click in one panel out to siblings. With panels now lazy-mounted one at a time the bus pattern broke down: the listener panel might not be mounted when the event fires. A shell-owned store + subscriber callbacks works regardless of which panel happens to be visible. The four custom events are gone.

A sibling activeCharacterId key co-lives in the same module. The CHARACTERS / Roster panel sets it when the operator clicks "view" on a completed character; the CHARACTERS / Character panel reads it on mount. Clearing the campaign id automatically clears the character id — a character only exists in the context of its campaign.

The wire-log drawer

src/shell/drawer/drawer.ts is the persistent right-side pane that owns every SSE subscription for the page. It composes four pieces: a subscription manager (subscriptions.ts) that holds one EventSource per subscribed campaign id, an in-process pub/sub event bus (event-bus.ts) that fans messages out to in-page subscribers, a 500-event FIFO ring buffer (buffer.ts) that holds the recent-history view, and the drawer's own UI controls (pause / clear / export-to-clipboard, collapsible to a 36-px stripe). The shell wires the trio together once at mount time and the drawer renders rows on every bus.publish.

One EventSource per active campaign, owned by the drawer — multiple panels need to react to the same SSE stream (status, snapshot, members, character views). In the old layout each opened its own connection, multiplying open sockets and tripping the per-user rate limit on GET /status/stream (see pipeline status). Centralising the socket in the drawer and fanning out through an in-process bus means one socket per active campaign, and panels become cheap bus subscribers.

Auto-subscribe happens at two points: on shell mount, if the active-campaign id is non-null, and on identity switch, after the bridge re-runs subscriptions.subscribe(active). Unsubscribe happens when the active id changes (the old EventSource closes), when identity changes (every open socket closes via closeAll()), and when the shell itself unmounts. Pause + clear state persists across reloads in localStorage.

The identity bridge

src/shell/identity-bridge.ts registers a single window-level listener for mythrun.identitychanged — the event the identity switcher dispatches when the operator picks a new dev-user-N. The handler runs the shell's onIdentityChange callback, which closes every drawer subscription, re-subscribes to the active campaign id (if any), and re-renders the sidebar. The bridge replaces the four panel-specific clear-on-identity-switch listeners (closewatch + createpanel.clear + detailspanel.clear + ledgerpanel.clear) from the old shell. One listener at the shell level is enough because the active panel's unmount path runs its own cleanup, and the shell-owned stores are what panels read from on mount.

The panels

Every backend route gets its own panel. As of the myth-mbdc reorg there are 41 leaves in ROUTE_PANELS grouped across six sidebar sections, with a handful of routes (Stripe webhook, registration helpers) sitting in EXEMPT_ROUTES because they don't make sense as a UI surface. Panels share a split-view skeleton at src/components/_shared/panel-skeleton.ts (title + action pane on the left + feedback pane on the right + a data-state attribute the verifier keys on) and a handful of shared renderers (error-block.ts for error display, json-disclosure.ts for expandable JSON dumps, progress-strip.ts for long-running flows). Panels that need live wire data subscribe to the drawer's bus rather than opening their own EventSource.

One panel per endpoint × method, not multi-purpose composites — the old layout had a single "character-creation panel" that bundled five routes and a "billing panel" that bundled four. Each composite carried its own UI state machine, its own custom events, and its own special-cases for what to show when. Splitting them into single-purpose siblings collapses every panel to "render the action, fire the call, render the response," and the sidebar becomes a navigation map of the backend rather than an arbitrary list of features.

Identity

The header's identity dropdown is wired to the DEV_SUBS list (dev-user-1 through dev-user-5) from src/identity.ts. The selected value lives in localStorage under mythrun.devtool.devSub; src/api-client.ts reads it on every call and stamps it as x-mythrun-dev-sub. On first load main.ts self-bootstraps the active sub against POST /api/users/register so a developer landing on the page against a clean DB sees working panels without manual setup. Identity switches dispatch mythrun.identitychanged, which the identity-bridge catches and uses to drive the drawer + sidebar re-sync.

Verify-registry invariants

backend/dev-tool/__tests__/verify-registry.test.ts is the build-time gate against the registry rotting. It enforces four invariants. Forward coverage: every module under src/components/ that exports a mount* function has a matching entry in the verifier's PANEL_REGISTRY. Reverse coverage: every registered panel id is imported (or side-effect-imported) by main.ts, so registering a panel that nothing pulls into the bundle is a red test. Route exhaustion: the union of every panel's exercises arrays plus EXEMPT_ROUTES covers every entry in BACKEND_ROUTES. Exempt validity: every EXEMPT_ROUTES entry must itself be in BACKEND_ROUTES (so a stale exempt entry that names a removed route fails the test).

A test, not a runtime check — invariants enforced at runtime fail in the browser, with no actionable signal. As a vitest test they fail at CI time with a clear message ("panel X is registered but not imported by main.ts") and the build never reaches the dev server.

The ship gate

The dev tool is the only place inside the repo where the prep pipeline's HTTP, SSE, and BullMQ surfaces are exercised by a human. Without enforcement, "add a new route" silently means "the dev tool has no way to trigger or observe it" — the next contributor finds out by guesswork. The gate makes the wiring an explicit, mechanical step.

Three files at backend/src/contract/ are the source of truth: pipeline-routes.ts (HTTP routes, format 'METHOD /api/path'), pipeline-events.ts (SSE event names), and pipeline-jobs.ts (BullMQ job names). Each is a readonly string[]. backend/dev-tool/coverage.json declares what the dev tool actually covers, in three matching arrays plus an exempt object whose values are human reasons for entries the tool deliberately skips. pnpm dev-tool:check runs backend/scripts/dev-tool-check.ts, which loads the contracts and the coverage JSON and calls the pure checkCoverage(contracts, coverage) function from backend/src/dev-tool-check/check-coverage.ts. It errors when a contract entry is missing from coverage and not exempt, when an exempt reason is shorter than 20 characters, and when an exempt entry references a contract entry that no longer exists; it warns when a coverage entry is no longer in the contract.

Pure function under a CLI shell, not a single script — the same pure checkCoverage runs under Vitest with synthetic fixtures, so the gate's behaviour is exercised on every test run, not only when a contributor remembers to run the CLI. The CLI shell is the thinnest possible filesystem-and-process wrapper around the pure core.

CI wires the gate through .github/workflows/dev-tool-check.yml, a peer of wiki-check.yml: it runs on every pull_request and on push: branches: [main], scoped via paths: to the gated surface so unrelated PRs don't pay CI minutes. The pipeline contract files are populated and the gate is load-bearing: the routes, events, and BullMQ jobs that ride the registry today are all driven by panels in the dev tool with zero exempt entries.

The exempt list

Two distinct exempt lists exist — one for the pipeline contracts (coverage.json's exempt object, enforced by dev-tool-check) and one for the all-routes panel-registry invariant (EXEMPT_ROUTES in route-registry.ts, enforced by the vitest test). The pipeline contracts' exempt object is currently empty. The route-registry's EXEMPT_ROUTES currently lists three entries: POST /webhooks/stripe (signature-verified consumer, no human UI), POST /api/users/register (probe-helper embedded inside the USERS / Me panel, exercised by the verify harness's identity-bootstrap step), and GET /api/users/check-username (same shape, embedded in the register probe-helper).

20-character minimum on exempt reasons — without a floor, the gate's escape hatch becomes a single keystroke. Twenty characters is enough room for "MYT-NN tracked, defer" and short enough that "we'll exempt this for now" stays uncomfortable.

Hard rules

Five conventions are enforced by code review and the structure of the codebase itself:

  • Local-only by design. No env switcher, no staging mode, no @fastify/cors plugin on the backend. Staging validation lives in smoke testing.
  • All HTTP calls go through api-client.ts's apiCall. No bare fetch anywhere else. No absolute URLs. The path guard rejects bare URLs (missing leading /) AND protocol-relative paths (leading //) so fetch('//evil.com/x') can't leak x-mythrun-dev-sub to a foreign origin.
  • Use .textContent, never .innerHTML. Defense against any stored-XSS-shaped response surface ever appearing in a future panel.
  • No secrets in localStorage. Only mythrun.devtool.devSub, devtool.activeCampaignId, devtool.activeCharacterId, and a few UI prefs (selected panel, drawer open/paused state) live there. Tokens, JWTs, Anthropic keys do not.
  • The ship gate is not skippable. pnpm dev-tool:check runs on every PR; merging a contract change without the matching coverage entry (or a real exempt reason) is a red CI build.

Operating this piece

Run the dev tool locally

  1. Bring up the backend per the backend page: pnpm db:up, then pnpm dev in one terminal. Wait for the app.listen log line.
  2. In a second terminal, from the repo root: pnpm dev:dev-tool. Vite reports Local: http://127.0.0.1:5273/.
  3. Open the URL. The shell mounts, the sidebar populates from ROUTE_PANELS, the banner reports the active campaign (or "(no active campaign)"), and the drawer renders empty. If the active sub doesn't have a users row yet, main.ts's bootstrap fires POST /api/users/register automatically.
  4. Pick an identity from the header dropdown. The selection persists across reloads via localStorage. Every subsequent call carries it as x-mythrun-dev-sub; the drawer re-subscribes to the active campaign as the new identity.

Add a pipeline route (the shape the gate enforces)

  1. Append the route to backend/src/contract/pipeline-routes.ts in the 'METHOD /api/path' form. (And to backend-routes.ts for the all-routes invariant.)
  2. Add the route handler under backend/src/routes/ and wire it into app.ts's plugin registration.
  3. Add a panel module under backend/dev-tool/src/components/ that drives the route via apiCall. The module exports a mount<Panel> function returning PanelHandle, calls registerPanelMount(method, path, mount...) at the top level, and is side-effect-imported by main.ts. Add an entry in src/shell/route-registry.ts's ROUTE_PANELS with the section and label.
  4. Add the same 'METHOD /api/path' string to the routes array in backend/dev-tool/coverage.json.
  5. pnpm dev-tool:check locally — must exit 0. pnpm --filter @mythrun/backend test backend/dev-tool/__tests__/verify-registry.test.ts locally — must pass. The same PR contains all five changes; CI runs the same checks on push.

Exempt a contract entry (rare)

  1. Add the contract string as a key under coverage.exempt.<routes|events|jobs> in backend/dev-tool/coverage.json. The value is the reason.
  2. Write a real reason of at least 20 characters: who decided, why the dev tool can't drive it, and the Linear/MYT-* issue tracking the gap.
  3. Open the PR with the exempt change visible alongside the contract change. Reviewers push back if the reason isn't substantive.
  4. When the issue lands and adds coverage, the exempt entry is removed in the same PR — leaving a stale exempt entry whose contract entry no longer exists red-CI's the gate.

Diagnose a failing dev-tool:check

  1. The script prints one error: line per problem. Read the line — each names the kind (routes / events / jobs), the entry, and the action required.
  2. "in contract but not in coverage and not in exempt" — add the panel + coverage entry, or add an exempt entry with a real reason.
  3. "exempt reason is too short" — write a real reason (≥ 20 characters).
  4. "in exempt but no longer in contract" — drop the exempt entry.
  5. Warnings (warn: prefix) — coverage entry no longer in contract. Non-fatal; consider removing the coverage line.

Integration points

The dev tool drives the backend's HTTP surface through the Vite proxy and consumes the same x-mythrun-dev-sub header the auth-bypass plugin in the JWT middleware reads to populate request.user in development. The wire-log drawer attaches to the pipeline status stream, which the world-gen worker publishes events into. Staging validation goes through smoke testing, not this tool.
