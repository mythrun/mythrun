Character creation

The per-player parallel character-creation surface. After world-gen completes and the wiki snapshot is fetchable, the owner picks one of the three generated starting situations for the entire party and a party-wide starting level (1–5), and each member submits a character (a concept text plus a situation-grounding text). The starting level is the one deterministic input the pipeline injects rather than letting the model choose it (ZFC); everything else about the character is the model's interpretation of the player's prose. Every POST /characters commits one transaction that flips the player's character_concepts row to 'processing' AND seeds a character_concept recovery row in pipeline_runs, then — after that transaction commits — enqueues one character-creation job on the campaign-setup BullMQ queue. There is no separate owner fan-out step. Each job walks three stages (location_selection → character_concept → character_sheet) and ends with a populated characters row plus the structured concept_output JSONB blob the character integration pass consumes. The status panel and live-events feed render per-player progress via the existing campaign-scoped channel. Materializing the PC as an entities row, writing PC↔world facts and relationships, and weaving the party together happen later — in the single campaign-scoped Opus pass MYT-54 fires when the owner finalizes character creation.

How it fits together

Character creation is phase 4 of the campaign lifecycle. Phase 2 (world generation) and phase 3 (wiki read via GET /api/campaigns/:campaignId/world-snapshot) ship today. Phase 5 (cross-PC integration) shipped in MYT-54; phase 1 (pre-world-gen lobby retrofit) is a separate bead. MYT-53 owns the middle two steps — owner picks situation, members submit characters and the per-player pipeline auto-fires on submit — plus the three-stage worker pipeline that turns those submissions into characters ready for the campaign-scoped integration pass. MYT-90 extended the owner's setup with a party-wide starting level (a second owner pick, threaded deterministically into the sheet stage), taught the starting_situation stage to emit a per-situation invitation whisper (the elicitation the player answers to write the grounding text), and added the reveal's reset ("Start over") and confirmation ("This is me") self-routes. The character-creation experience page documents the frontend flow those routes drive.

Strict order, not permissive — players cannot submit characters until the owner has chosen a starting situation. The strictness eliminates a class of edge cases ("what if a player submitted before the owner picked?") and makes the frontend trivial: the POST /characters route returns 409 'starting_situation_not_chosen' until campaigns.starting_situation_index is set, and the lobby displays a "waiting on owner" state. The owner choosing one situation for the entire party (not per-character) is the other half of the same simplification — different characters cannot have different starting situations and still play together. Once the situation is chosen, members no longer need an owner action to start their pipeline — submitting their character flips the row to processing (committed alongside a recovery row) and enqueues the job right after that transaction commits.

The two-prompt model

The character-submission body carries two load-bearing text fields, and the separation is what gives players agency on both axes:

  • conceptText (20–4000 chars): "Who is this character?" — identity, race, class, background, personality, backstory. Stage 2 (character_concept) consumes it.
  • situationGroundingText (20–2000 chars, always required): "Why is this character at this tavern?" — the player's framing of how their PC arrives at the owner-chosen opening. The MYT-54 integration pass consumes it when weaving the PC into the world.

Without the grounding prompt the integration pass has only a generic "introduce this PC to the world" instruction to work with; with it, the pass has the player's specific entry-point narrative to weave through the PC's facts and PC↔world relationships. The frontend reframes the grounding prompt for late joiners ("describe the situation the party is currently in and how your character fits") but the backend column is the same.

MYT-90 gave the grounding prompt a grounded elicitation. Each of the three starting situations now carries an invitation — a short 2nd-person whisper the world-gen starting_situation stage writes in the same call as the situation's title and prose, so it names that hook's concrete draw rather than gesturing at generic mystery ("What secrets will you uncover in this city of whispers?"). The frontend surfaces the chosen situation's invitation as the second one-question step, and the player's answer becomes situationGroundingText. The field is stored on the situation entry's JSONB, so it is optional on read — worlds generated before MYT-90 have no invitation, and GET /starting-situations passes the older shape through with a generic client fallback rather than hard-failing Zod.

MYT-102 corrected the shape of that whisper. The first staging playtest surfaced invitations that presumed a history the player's character could not have — a newcomer arriving at the opening scene was asked "the toll-clerk's manifests don't add up and you're the only one who noticed; what kept you counting?", a question only an established local can answer. The prompt now demands an arrival-draw: it poses the hook as a rumor, a visible circumstance, or a reason-to-arrive that a character who knows nothing about the world can answer ("What brings you up the pass this late in the season, and what have you heard about the beacons going dark?"). It may name places and public facts, and it may reference an NPC only as an observable stranger ("the harbormaster who keeps late hours") — never as an acquaintance the character already knows.

The invitation is player-facing, so its input is known-tier only (MYT-102) — the starting_situation stage that writes the invitation reads its entity context through listProseByTypeForStartingSituation, which filters entities.access_level = 'known'. A secret or discoverable entity's name or prose can never enter the generation context, so an invitation cannot leak a plot secret into the picker a player reads before they even have a character. This is the same deterministic-leak boundary as the MYT-89 relationship tiering, applied to the first player-facing surface world-gen produces. Worlds generated before MYT-102 keep their older, untiered invitations — the entries are write-once at world gen, and regeneration is out of scope.
Both fields required in v1; guided-choices deferred to its own bead — the freeform path is the only consumer today, so the body schema is a two-field object with both strings required (20..4000 / 20..2000, mirroring the CHECK bounds in migration 016). The character_concepts.guided_choices JSONB column persists as the default {}; a future guided-character-creation bead lights up the picker UI, extends the body schema to accept a third field, and lights up the deterministic-assembly path in stages 2–3 without reshaping the route. Dropping the optional field today means a sharper 400 on bad bodies and one less branch to keep covered.

The routes, split into five cohesive modules

The route surface grew past the 400-line module cap, so campaign-characters.ts is now a thin composer: it owns the shared plugin options and queue types and registers five nested plugins, each a coherent slice of the lifecycle. The registered plugin (campaignCharactersPlugin) and its exported types keep their identity, so app.ts, server-queues, and the route tests import from here unchanged. Route registration is instance-global (no shared decorators to leak), so the split is behaviour-neutral — the onRoute/onReady contract hooks on the root app still fire for routes registered inside the nested plugins.

Split by lifecycle slice, not alphabetically — the five modules each own one phase of the member's or owner's journey: campaign-setup-routes (owner picks situation + level, member reads the situation list), character-concept-routes (the member's own concept write lifecycle — submit, reset, confirm), character-roster-routes (the two read-back rosters), world-read-routes (the character sheet + world reads a member makes), and campaign-lifecycle-routes (finalize + archive). A reader tracing "what happens when a player clicks Start over" lands in one file, not a 900-line grab-bag.

Every route carries config.pipelineRoute = true and is registered in backend/src/contract/pipeline-routes.ts, so the boot-time route-audit invariant keeps the plugins, the contract, and the dev tool honest in lockstep — a new route that skips pipeline-routes.ts fails app boot, and one that skips contract/backend-routes.ts reds the drift test. The character-creation job kind is registered in backend/src/contract/pipeline-jobs.ts with the deterministic id cc-<campaignId>-<userId> so a duplicate POST while a job is in flight becomes a no-op at the queue layer.

Why character_concepts is its own table, not a column on campaign_members — campaign_members is a join table; concept input is conceptually separate from membership. One row per (campaign_id, user_id) matches campaign_members's grain exactly, and a composite FK to (campaign_members.campaign_id, campaign_members.user_id) means removing a member cascades the concept row out. The concept lifecycle (status, error JSON, resubmit edits) stays self-contained rather than mixing with membership state.

The three stages

The processor in backend/src/llm/prep/character-creation-processor.ts mirrors the world-gen processor's outer loop: it claims each stage atomically, runs the LLM call outside any transaction, and marks the row completed or failed on the pool. Each stage handler owns its own persist transaction — the character_sheet stage opens one client and runs the whole sheet (character row + four satellite tables) under a single BEGIN/COMMIT, rolling back on any constraint failure. The atomic-claim helper from world-gen is parameterised on an optional userId, so character-creation rows in pipeline_runs are keyed on (world_id, stage, user_id) rather than (world_id, stage, NULL) — N players run N concurrent rows per stage without colliding. Per-player failure does not abort other parallel jobs. The fourth stage (character_integration) sketched in earlier drafts was retired in MYT-54 — its job moved to the campaign-scoped single-pass the owner triggers when every player's row reaches completed.

The sheet co-evolved with the live ledger (MYT-70)

The character sheet is also the seed for the live character ledger the Rules Lawyer debits during play, so the character_sheet stage's schema and prompt grew to emit the ledger's structure. The model now produces starting_gold, a hit_die size, a spellcasting_progression archetype (full | half | third | pact | none), and per-row flags: consumable on equipment, ritual on spells, and a max_uses + recharge pair on limited features. Spell slots themselves are not asked of the model — code derives them from (progression, level) against the SRD slot tables and writes the per-level character_spell_slots rows at finalize.

The model emits one structured judgment, code derives the slots (ZFC) — the free-text class name is never string-matched. The model picks the progression archetype; the deterministic SRD tables turn (progression, level) into the slot grid. The stage also gained a coherence loop: a sheet that is Zod-valid but mechanically incoherent against those tables (a level-9 spell on a level-1 caster) triggers a full regeneration, bounded by a max attempt count, then terminal-fails loud rather than persisting a brickable character.
The prepared pin and the dedupe-merge are load-bearing for the tools — the Rules Lawyer keys casting on prepared ("currently castable," not "uses the prepare mechanic"), so the prompt is explicit that always-castable casters (sorcerers) emit all leveled spells prepared: true. And because the ledger matches items/features/spells by normalized name under a unique index, the stage mechanically dedupe-merges the model's output before insert (equipment sums quantities; features and spells keep-first) so an LLM duplicate can't terminal-fail the insert or corrupt a debit's rowcount math. The detail lives on the character ledger page.

The table's per-stage costs are the lower-bound point estimate (2K input / 1–2K output per Sonnet call, 2K input / 1K output for Opus). Realistic per-player cost is $0.20–$0.50 once the world snapshot input (8–15K tokens for a full world) and the player's grounding text reach normal sizes. A cost-cap circuit breaker receives settings.character_creation_cost_cap_usd (default $5.00) as injected CharacterCreationDeps.costCapUsd — read once by server.ts at process boot via readCostCapsAtBoot and held for the worker's lifetime. Each per-player job compares cumulative cost against the injected cap; over-cap aborts the player's stages with character_creation_cost_cap_exceeded, leaving other parallel jobs untouched. The $5 default covers ~10 players at the realistic upper bound, with headroom for the multiplayer concurrency target of 5–8 per party. An operator-edited cap requires a worker restart to take effect — by design, since the cap is global policy and worker process lifetime is the natural enforcement window.

Stages 2–3 are Sonnet — the parent pipeline spec sketched all character-creation stages as Opus. Stages 2–3 produce bounded structured output (a portable-character payload, D&D 5e SRD-compliant mechanical rows); Sonnet handles that reliably and is ~3× cheaper input, 5× cheaper output. The load-bearing PC↔world integration is Opus, but it runs out of band — see the campaign-scoped integration pass.

Starting level: the one deterministic input

Everything about a character is the model's interpretation of the player's prose — except its level. The party plays at one starting level (1–5), the owner picks it, and the pipeline threads it in deterministically. Migration 033_starting_level.sql adds campaigns.starting_level SMALLINT (CHECKed NULL OR BETWEEN 1 AND 5, matching the sibling starting_situation_index shape) alongside character_concepts.confirmed_at TIMESTAMPTZ. The owner sets the level between the situation pick and character creation (POST /starting-level), and the submit gate refuses characters (409 'starting_level_not_chosen') until it is set — the same strict-order discipline as the situation gate.

The level is injected, never generated (ZFC) — the level is a known input, not a D&D judgment the model should make. The character_concept stage still emits a level field, but the processor overrides it with campaign.starting_level before persisting the concept output — the model's echo is discarded, not trusted. That single override carries every downstream consumer, because they all read narrative.level: the persisted characters.level, the hit-dice pool, spellSlotsFor, and validateCoherence. The invariant is exact — persisted character.level == campaign.starting_level. A null starting_level when a job runs is a broken invariant (the submit gate should guarantee it), so the processor fails loud rather than silently substituting level 1 and shipping a wrong-level character.

The sheet prompt is level-parametric. A {{level}} placeholder threads narrative.level through every rule — proficiency bonus by level, HP summed across all N levels, features gained through level N, the subclass features once the class has a subclass by that level, the level-4 ASI, and Extra Attack at 5. It also teaches caster onset, which is the subtle trap: half-casters (paladin, ranger) get no spell slots until level 2 and third-casters none below level 3, so a level-1 paladin that emitted a leveled spell would burn the three-attempt regenerate budget and terminal-fail. The prompt states the onset explicitly per progression archetype (full/half/third/pact).

Two 5e-fidelity rules on the skills table were tightened (myth-wj43). Skill names are now a native enum of the canonical 18 (Acrobatics … Survival), spelled exactly — the schema is z.enum(CANONICAL_SKILLS), not free text — so a mis-spelling (Sleight Of Hand), a saving throw, or a tool proficiency (Thieves' Tools) can never be written to character_skills. Expertise (double proficiency bonus) is now the 2014 RAW rule, and like caster onset it is class-and-level gated: a rogue takes exactly two expertise skills at level 1 (the second pair arrives at level 6, above the level-5 cap), a bard takes two at level 3 or higher and none below it, and every other class takes none. The prompt names the same 18 skills and the same expertise rule the schema enforces — a prompt+schema co-evolution so the model's structured output is already shaped to what will validate.

The enum is a write-side constraint that mirrors the read-side lookup — a skill's proficiency only counts at play time if its name matches the live proficiency table (session/skill-check.ts's SKILL_ABILITIES, matched on lower(trim(name))). Free text silently missed that join — a sheet with "Sleight Of Hand" persisted clean and then granted no bonus at the table, an invisible failure. The native enum constrains the provider's structured output to the canonical spellings up front, and any drift terminal-fails the stage loudly rather than persisting an unmatchable name; the 18 names are kept in lockstep with the read-side twin, pinned by the schema tests.

validateCoherence is the deterministic backstop that runs after every sheet generation, over structured fields only — no CON-mod guesswork, no class-name string-matching. It keeps the two shipped invariants (every leveled spell's level ≤ maxSlotLevel(progression, level); leveled spells present ⟹ progression ≠ none) and MYT-90 adds two more: proficiency_bonus matches the level (1–4 → +2, 5 → +3), and max_hit_points sits inside an HP band derived from hit_die, the CON modifier, and the level (with a small per-level slack for racial HP like Hill Dwarf's +1/level, so a legal sheet never false-fails the ceiling). A violation raises a CharacterSheetCoherenceError, which triggers a bounded full regeneration and then a loud terminal fail rather than persisting a brickable character.

The guard asserts validity, not level-appropriateness — a sheet that is internally consistent but under-leveled (a level-5 build that reads like a level-3 one) still passes; the check proves the sheet isn't mechanically impossible, not that it earned every level-5 feature. Two things are deliberately not gated here: ASI/feat presence and subclass-feature presence at level N. There is no pre-ASI baseline to diff the final ability scores against, and detecting a feat would mean string-matching free-prose features[] — a ZFC violation. Those ride on prompt quality and the guided builder, not on this deterministic shell. Level-appropriateness at the top of the 1–5 range is the acknowledged residual risk (the reason the range is bounded and both ends carry a constructed-state real-LLM smoke), not something the validator claims to catch.

Reset and confirmation: surviving the reveal

Two small self-scoped routes make the reveal robust to a reload and a change of heart. A 'completed' concept is locked — POST /characters rejects it — so Start over can't just re-submit. POST /characters/reset flips the caller's own completed (or failed) concept back to a resubmittable state and DELETEs the generated sheet in one transaction, so the next submit re-runs the pipeline from scratch (it costs another round of Sonnet calls, by design — a genuine re-roll). The reset is guarded transactionally: it refuses (409 'not_resettable') once the character is 'integrated' or the campaign is 'active', because you can't unwind a character that is already woven into a running game. The same route also unwinds a stale 'processing' concept — one no live worker has touched for 10 minutes — which is the player-side arm of the resilience layer below; a fresh 'processing' row stays locked.

confirmed_at is what keeps a reload from bouncing the player — the window between a concept reaching 'completed' and the campaign going 'active' is where the player reads their sheet and waits for the party. Without a persisted marker, a reload in that window would land the player back on the reveal every time. The frontend routing table keys the reveal→party-staging split on confirmed_at: This is me (POST /characters/confirm) stamps it, idempotently, and a reload thereafter routes straight to party staging. It is a durable-state answer to a refresh-survival requirement, not a UI flag.

Lifecycle and late joiners

A member can submit a character as soon as two gates are satisfied: worlds.status = 'complete' and campaigns.starting_situation_index IS NOT NULL. Until both gates hold, POST /characters returns 409 with the specific gate code (world_not_complete or starting_situation_not_chosen). Once a row exists in 'submitted', the player can re-POST to update the prose; the route refuses updates while the row is 'processing' or 'completed' (409 concept_locked).

Enqueue after commit, with a recovery row inside the commit — the queue.add sits AFTER the submit transaction commits, never inside BEGIN. A queue.add wrapped in BEGIN/COMMIT is the "enqueued but the commit rolled back" zombie-job shape this refactor exists to eliminate. The trade is the opposite window: a Redis blip between COMMIT and queue.add could leave a concept stranded at 'processing' with no job ever running. The fix is to seed a 'pending' character_concept row in pipeline_runs inside the same transaction (mirroring world-gen's seed-row contract). A missed enqueue therefore leaves a resumable trace: derivePhase maps the 'pending' character_concept row to 'character_creation', and the worker's campaign-user atomic claim re-arms that pending row to 'running' via ON CONFLICT rather than double-inserting.

The flow is symmetric for late joiners — members who accept invites after the rest of the party has submitted — since the per-player job fires on the member's own POST, not an owner action:

  1. Late member accepts an invite. Their campaign_members row exists; no character_concepts row yet.
  2. Late member POSTs /characters. One transaction creates the row, flips it to 'processing', and seeds the recovery row; the per-player job is enqueued right after that transaction commits. No owner action required. Other members' 'completed' rows are untouched.
  3. Late-joiner's character creation runs in parallel with any other in-flight jobs.

Failure handling is per-player and resubmittable. On terminal stage failure the processor sets character_concepts.status='failed' and writes the error JSON; the player re-POSTs /characters, which commits the reset-row + recovery-row transaction and then re-enqueues the job after commit (no separate owner trigger). The processor's re-run is idempotent at the stage boundary, not delete-and-recreate: stage 3 detects an existing characters row for (campaign_id, user_id) and UPDATEs rather than INSERTs (TRUNCATE-then-INSERT on the four sub-tables). The frontend reframes the second prompt for late joiners ("describe the situation the party is currently in and how your character fits") but both forms map to the same situation_grounding_text column.

Resubmit-after-failure is idempotent on stage outputs, not a clean slate — the alternative (DELETE the partial character row on failure) would force the player to re-enter their prose just because a Sonnet call timed out once. Idempotent re-runs let a transient Anthropic 503 self-heal without losing the player's input or the work stage 2 already completed. The UNIQUE(campaign_id, user_id) on campaign_characters would otherwise turn the re-run into a constraint violation. Players who genuinely want a clean slate (different name, race, class) re-roll through an admin path — there is no member-facing DELETE in v1.

Surviving a stuck job — the resilience layer

The first staging playtest turned up a failure the enqueue-after-commit recovery above did not cover: a character-creation job that finished both Sonnet calls and then hung — the worker task alive, its BullMQ lock renewing, no further logs — leaving the player's concept at 'processing' with no way forward. MYT-102 laid down the first containment layers; the worker-resilience pass that followed (after a wedged staging job proved a hang renews its BullMQ lock forever) hardened them into the current set — two watchdogs, a failure listener, a player-side reset, and an owner-side resume — each catching a failure the others miss.

A per-stage watchdog, and its trip is terminal. Each stage's whole execution — the LLM calls and the persistence — races a hard wall clock (CHARACTER_CREATION_STAGE_TIMEOUT_MS, 5 minutes, ~5× the slowest healthy stage). On a trip the watchdog throws the cross-workstream unrecoverable shape (terminal: true, surfaced as errorCode 'job_timeout'), so the processor's terminal arm marks the pipeline_runs row failed, flips the concept to 'failed' right there in the loop, and publishes stage-failed { willRetry: false } — the player sees the failure immediately and resubmits.

Terminal, not retry — a deliberate reversal — the watchdog originally threw terminal: false so BullMQ's attempts: 2 policy would drive one retry, on the theory that a hang might be transient. That non-terminal choice turned out to be the wedge: at a 5-minute threshold a trip is overwhelmingly a genuine hang, the retry hangs the same way, and a non-terminal throw on an unrecoverable stage keeps retrying while the concept sits at 'processing' with nothing the player can do. Retrying a hang and resubmitting after a fast fail re-run the exact same pipeline either way — failing fast just hands the re-run decision to the player minutes sooner. The in-code comment on the timeout constant documents the reversal.
The watchdog wraps the stage, not just the model call — the staging hang happened after both Sonnet calls returned, somewhere inside the stage's own await chain, so bounding only the LLM call would not have caught it. The abandoned stage promise's late writes are harmless: persistence is idempotent and the atomic stage-claim re-arms a pending/failed row rather than double-inserting, so a slow stage that finishes after the watchdog fired cannot corrupt the resubmit's re-run.

A whole-job watchdog on top of the per-stage one. The processor factory wraps the entire job in a second, wider wall clock (CHARACTER_CREATION_JOB_TIMEOUT_MS, 16 minutes), so every await in the job is bounded — including the orchestration loop's own DB and Redis awaits (the atomic stage claim, the pipeline_runs and character_concepts writes, the event publish) that sit outside any stage and therefore outside the per-stage watchdog. On a trip the job promise settles as a terminal failure, BullMQ's attempts exhaust, and the failure listener below flips the concept. The shared withJobTimeout helper lives in the worker's job-containment layer.

Why a second watchdog at all — the staging hang's defining symptom was that the BullMQ lock kept renewing: the worker task was alive and awaiting, so nothing at the queue layer would ever reclaim the job. A stall in an orchestration await — a wedged DB connection between stages, say — slips past the per-stage watchdog and renews the lock forever. The job-level cap guarantees no await anywhere in the job can hold the worker slot indefinitely. It is deliberately more than 3× the per-stage cap, so an in-stage hang always trips the tighter watchdog first (which fails the concept in-loop); the backstop fires only when the sum of individually under-cap awaits wedges the job.

An exhausted-transient listener. A genuinely transient failure (an Anthropic rate-limit, an overload) still rethrows non-terminally so BullMQ retries, but the final failed attempt used to leave the concept at 'processing' forever — the concept flip only ran on terminal errors, and nothing produced a job-level failure. The worker now attaches handleCharacterCreationJobFailure to the campaign-setup worker's 'failed' event. It acts only once BullMQ has exhausted every attempt (attemptsMade >= attempts) — a transient's last failed retry, or the whole-job watchdog's trip — and then flips the concept to 'failed', publishes a terminal stage-failed { willRetry: false, errorCode }, and logs loud. It never throws (it catches and logs internally), so it can't crash BullMQ's emitter, and it skips a concept that already reached 'completed' — a late 'failed' event must never unwind a finished character.

A player-side reset for a stale 'processing' row. Every layer above runs worker-side, and the staging hang proved a job can wedge in a way none of them can reach — a stalled await never returns control, so no code on the worker flips the row. POST /characters/reset — the same "Start over" route from the reveal — therefore also matches a 'processing' concept whose updated_at has not advanced for 10 minutes (STALE_PROCESSING_RESET_MS). The player resets and resubmits without any operator involved; a fresh 'processing' row — an active worker mid-stage — stays locked behind 409 'not_resettable'.

Why 10 minutes — a healthy job bumps the concept row's updated_at as it moves through the pipeline, and its longest legitimate silent gap is one stage's LLM calls plus persistence — comfortably under the 5-minute per-stage watchdog. Ten minutes of silence therefore means no live worker is driving the row. And it sits just below the 16-minute whole-job cap, so a player can self-serve a recovery slightly before the backstop fails the job on its own: the reset is the fast path, the watchdogs the guarantee.

An owner-triggered resume. The last gap is a concept stranded with no live job at all — the "committed the seed row, then a Redis blip ate the queue.add" window from the enqueue-after-commit discussion above, or a transient that exhausted before the listener existed. POST /api/campaigns/:campaignId/resume's character_creation arm sweeps them: listStuckProcessing finds every 'processing' concept whose per-player pipeline has a 'pending' or 'failed' stage row and no 'running' one (a healthy in-flight member under the watchdog is never swept), and re-adds each one's cc-<campaignId>-<userId> job. It replies 202 with the count re-enqueued, 409 nothing_to_resume when nothing is stuck, and 503 queue_not_ready when the queue isn't wired on the deployment. It is the same campaign resume endpoint the world-gen recovery uses — the character_creation phase arm is this sweep.

Every failure publish now carries errorCode, not reason — the character-creation processor used to publish the raw error message on a reason field no consumer read; the stage-failed contract (shared with world-gen and the dev-tool live-events panel) keys on a sanitized errorCode. MYT-102 aligned all three publish sites — the cost-cap breaker, the terminal/non-terminal catch arms, and the exhausted-transient listener — onto errorCode, so a character-creation failure renders in the status surface exactly like a world-gen one. One consequence: the queue-wiring for the resume arm surfaced a latent boot gap — app.ts forwarded only the world-gen queue to the campaigns routes, so the character_creation resume would have answered 503 in every real deployment until the character-creation queue was threaded through alongside it.

Cross-PC integration moved to MYT-54

The per-player pipeline now ends at stage 3 (character_sheet). MYT-54 retired the per-player character_integration stage 4 outright: PCs no longer become entities rows from the per-player pass. Instead, MYT-53's stage 2 (character_concept) persists its structured output to the new character_concepts.concept_output JSONB column, and the owner-triggered character integration pass reads every PC's concept output plus the world inventory in one Opus call and writes every PC entity, fact, and relationship (including PC↔PC edges) in a single transaction.

Two consequences for the per-player surface this page documents:

  • A character_concepts row reaches status='completed' after stage 3 finishes. The fifth lifecycle state, 'integrated', is set by the MYT-54 integration handler, not by anything on this page.
  • The cost-cap budget (character_creation_cost_cap_usd) covers both the per-player character_concept + character_sheet rows and the campaign-scoped character_integration row — one budget across all character-creation spend.

Operating this piece

Exercise the routes end-to-end

The Characters workflow page in the dev tool composes the per-player panels inline: starting situations (read-only list), situation pick (owner), submit character concept (member), creation progress, roster, character view, members, and finalize-character-creation. Switching identities via the dev-tool's identity switcher lets one operator impersonate every player against a single campaign and walk the full submit → processing → completed flow (no manual fan-out step — each submit enqueues its own job). Direct psql + curl remain useful for shape verification — concept rows in character_concepts, PC rows in entities, the four sub-table rows in character_* — but the page is the primary driver. The route-audit contract test (backend/src/contract/__tests__/pipeline-routes.test.ts) verifies registration drift as a side-effect of any backend type-check.

Recovering a stuck character

  1. Confirm the concept is genuinely stuck: a character_concepts row at 'processing' whose per-player pipeline_runs rows are 'pending' or 'failed' with none 'running' (SELECT status, stage FROM pipeline_runs WHERE campaign_id = … AND user_id = …). A 'running' row means a worker is still on it under the 5-minute watchdog — let the watchdog trip (it terminal-fails the concept, and the member resubmits) rather than resuming underneath it.
  2. Have the owner call POST /api/campaigns/:campaignId/resume. The character_creation arm re-enqueues every stuck member's job and replies 202 { reEnqueued }; 409 nothing_to_resume means nothing matched the sweep (the concept is healthy or already terminal), and 503 queue_not_ready means the character-creation queue isn't wired on this deployment.
  3. Watch the re-driven job in the dev tool's wire-log drawer — the concept re-runs from its first incomplete stage (stage 3 UPDATEs an existing characters row rather than double-inserting).

Reset a stale-processing concept (player self-serve)

  1. Symptom: a member's creation has sat at 'processing' with no visible progress for over 10 minutes. With DB access, confirm staleness directly: SELECT status, updated_at FROM character_concepts WHERE campaign_id = … AND user_id = … — a live worker bumps updated_at as the pipeline progresses, so a silent 10-minute gap means no worker is driving the row.
  2. The member calls POST /api/campaigns/:campaignId/characters/reset (the frontend's "Start over"). Once the row has been stale for 10 minutes the reset matches it, flips it back to 'submitted', and deletes any partial sheet in the same transaction. A 409 'not_resettable' means the row is still fresh — an active worker may own it, so wait out the window rather than fighting the lock.
  3. The member re-POSTs /characters with their concept and grounding text; the pipeline re-runs from scratch as a normal submit.
  4. No operator action is required — the reset is member-scoped and self-serve. The owner-side /resume sweep (previous runbook) remains the tool for a concept stranded with no job at all.

Integration points

Upstream: world gen populates worlds.starting_situation_entries (extended in MYT-53 + myth-k1ee) — stage starting_situation emits a structured three-entry array alongside the existing prose blob, with each entry carrying a title (LLM-emitted, 5–60 chars), a locationName (worker-resolved from entities.name via locationEntityId), and — since MYT-90 — the 2nd-person invitation whisper the freeform path uses to elicit the grounding text. GET /starting-situations passes the JSONB through verbatim so older worlds without the new fields keep rendering. Downstream: the pipeline status surface carries per-player events on the same campaign-scoped channel (pipeline:campaign:{campaignId}) — each event payload carries user_id so subscribers can route per-player. The dev tool's live-events panel renders character-creation lifecycle and entity / edge events the same way it renders world-gen events.

Appendix: schema additions

Migration 016_character_concepts.sql adds one new table, two new columns, and one extended CHECK:

  • character_concepts — one row per (campaign_id, user_id). Carries concept_text, situation_grounding_text, guided_choices JSONB (reserved for the guided-mode follow-on; the route never writes it in v1), status (submitted | processing | completed | failed), and an error JSONB. Composite FK to campaign_members(campaign_id, user_id) ON DELETE CASCADE.
  • campaigns.starting_situation_index SMALLINT — CHECKed to NULL or {0, 1, 2}.
  • worlds.starting_situation_entries JSONB NOT NULL DEFAULT '[]' — the structured array of three { index, locationEntityId, prose } entries the world-gen starting_situation stage now also emits.
  • entities.entity_type CHECK extended to allow 'pc' — PCs are conceptually distinct from NPCs (one is owned by a real user, the other is purely game-fiction), so reusing 'npc' would force every "list NPCs" path to add a PC-exclusion filter.

Migration 033_starting_level.sql (MYT-90) adds two columns and no new table: campaigns.starting_level SMALLINT CHECKed NULL OR BETWEEN 1 AND 5 (the owner's party-wide level pick), and character_concepts.confirmed_at TIMESTAMPTZ (the "This is me" timestamp, null until confirmed). The situation invitation whisper needs no migration — it rides inside the existing worlds.starting_situation_entries JSONB and is read back as an optional field.

The migration also seeds settings('character_creation_cost_cap_usd', '5.00'); server.ts's readCostCapsAtBoot helper reads it once on startup and injects the value as CharacterCreationDeps.costCapUsd. The sumCharacterCreationStageCosts(campaignId) aggregation in cost-cap.ts still runs per-job — filtered on WHERE campaign_id = $1 AND user_id IS NOT NULL AND status = 'completed' — so character-creation costs and world-gen costs are budgeted separately. Only the cap value moved to boot-time read; the cumulative-cost lookup is per-job by necessity.
