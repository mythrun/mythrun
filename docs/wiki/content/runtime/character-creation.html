Character creation

The per-player parallel character-creation surface. After world-gen completes and the wiki snapshot is fetchable, the owner picks one of the three generated starting situations for the entire party, members each submit a character (a concept text plus a situation-grounding text), and the owner triggers fan-out. Fan-out enqueues one character-creation job per submitted player on the campaign-setup BullMQ queue; each job walks four stages (location_selection → character_concept → character_sheet → character_integration) and ends with the PC as a real entities row of type 'pc', joined to a populated characters row, with PC↔world relationships and facts written into the world. Cross-PC weaving and the owner's established-relationships prompt are MYT-54's scope; MYT-53 is per-player only.

How it fits together

Character creation is phase 4 of the campaign lifecycle. Phase 2 (world generation) and phase 3 (wiki read via GET /api/campaigns/:campaignId/world-snapshot) ship today. Phase 5 (cross-PC integration) is MYT-54; phase 1 (pre-world-gen lobby retrofit) is a separate bead. MYT-53 owns the middle three steps — owner picks situation, members submit characters, owner triggers fan-out — plus the four-stage per-player worker pipeline that turns those submissions into PCs in the world.

Strict order, not permissive — players cannot submit characters until the owner has chosen a starting situation. The strictness eliminates a class of edge cases ("what if a player submitted before the owner picked?") and makes the frontend trivial: the POST /characters route returns 409 'starting_situation_not_chosen' until campaigns.starting_situation_index is set, and the lobby displays a "waiting on owner" state. The owner choosing one situation for the entire party (not per-character) is the other half of the same simplification — different characters cannot have different starting situations and still play together.

The two-prompt model

The character-submission body carries two load-bearing text fields, and the separation is what gives players agency on both axes:

  • conceptText (20–4000 chars): "Who is this character?" — identity, race, class, background, personality, backstory. Stage 2 (character_concept) consumes it.
  • situationGroundingText (20–2000 chars, always required): "Why is this character at this tavern?" — the player's framing of how their PC arrives at the owner-chosen opening. Stage 4 (character_integration) consumes it.

Without the grounding prompt, stage 4 has only a generic "introduce this PC to the world" instruction to work with; with it, stage 4 has the player's specific entry-point narrative to weave through the PC's facts and PC↔world relationships. The frontend reframes the grounding prompt for late joiners ("describe the situation the party is currently in and how your character fits") but the backend column is the same.

Both fields required in v1; guidedChoices reserved for later — the POST body schema accepts an optional guidedChoices object (defaulted to {}), and the route asserts at least one of { conceptText, guidedChoices } is present (400 concept_or_guided_required). In v1 the guided path is never populated and conceptText is effectively required; a future guided-character-creation bead lights up the picker UI and the deterministic-assembly path in stages 2–3 without reshaping the endpoint.

The nine routes

Method & path Auth Purpose
POST /api/campaigns/:campaignId/starting-situation Owner Sets campaigns.starting_situation_index to one of {0, 1, 2}. Idempotent while all character_concepts rows are still 'submitted' or absent.
POST /api/campaigns/:campaignId/start-character-creation Owner Atomically flips every 'submitted' row to 'processing' and enqueues one character-creation job per row on the campaign-setup queue. Idempotent under double-click — a second call picks up any new late-joiner rows.
POST /api/campaigns/:campaignId/archive Owner Soft-deletes the campaign by flipping campaigns.status to 'archived'.
POST /api/campaigns/:campaignId/characters Member UPSERTs the caller's character_concepts row with { conceptText, guidedChoices?, situationGroundingText }. Allowed when the row is absent, 'submitted', or 'failed' (failed → submitted resets the row). Returns 409 'concept_locked' for 'processing' / 'completed'.
GET /api/campaigns/:campaignId/starting-situations Member Returns the three world-generated starting situations (worlds.starting_situation_entries) plus the chosen index, if any.
GET /api/campaigns/:campaignId/characters Member Per-member roster: userId, display name, concept status (none | submitted | processing | completed | failed), and characterId once the row exists.
GET /api/campaigns/:campaignId/characters/:charId Member The portable character — narrative half + mechanics + the four sub-tables (skills, features, equipment, spells).
GET /api/campaigns/:campaignId/hierarchy Member Tier-filtered entity hierarchy for the campaign's world (known-only by default; dev bypass widens). Mirrors the world-snapshot tier semantics.
GET /api/campaigns/:campaignId/random-tables Member The world-gen stage-6 output — the world's per-domain random tables, surfaced to members so the dev tool and any future session-runtime UI can render them.

All nine routes carry config.pipelineRoute = true and are registered in backend/src/contract/pipeline-routes.ts, so the boot-time route-audit invariant keeps the plugin, the contract, and the dev tool honest in lockstep. The character-creation job kind is registered in backend/src/contract/pipeline-jobs.ts.

Why character_concepts is its own table, not a column on campaign_members — campaign_members is a join table; concept input is conceptually separate from membership. One row per (campaign_id, user_id) matches campaign_members's grain exactly, and a composite FK to (campaign_members.campaign_id, campaign_members.user_id) means removing a member cascades the concept row out. The concept lifecycle (status, error JSON, resubmit edits) stays self-contained rather than mixing with membership state.

The four stages

The processor in backend/src/llm/prep/character-creation-processor.ts parallels world-gen-processor.ts: the outer scope owns BEGIN / COMMIT / ROLLBACK and publishes finalized events post-COMMIT; the stage handlers write to the passed client and accumulate events. The atomic-claim helper from world-gen is parameterised on an optional userId, so character-creation rows in pipeline_runs are keyed on (world_id, stage, user_id) rather than (world_id, stage, NULL) — N players run N concurrent rows per stage without colliding. Per-player failure does not abort other parallel jobs.

Stage Model Latency Cost (lower bound) Persists
location_selection none ~0.1s $0 Resolves campaigns.starting_situation_index → worlds.starting_situation_entries[index].locationEntityId. Validates the location entity still exists. Defers the actual fact write to stage 4 (the PC entity doesn't exist until then); stage 4 re-derives the same id from the same source records.
character_concept Sonnet generateObject ~5–10s ~$0.02 Narrative-half payload only (name, race, class, background, alignment, traits, ideals, bonds, flaws, backstory). Held in worker memory; nothing is INSERTed yet because characters has NOT NULL mechanicals that stage 3 generates.
character_sheet Sonnet generateObject ~10–20s ~$0.04 Ability scores, HP / max HP / AC / proficiency bonus, plus the four sub-tables (character_skills, character_features, character_equipment, character_spells). Single transaction: INSERT into characters (narrative + mechanics together) + INSERT into campaign_characters + bulk-INSERT into the four sub-tables. characters.entity_id stays NULL until stage 4.
character_integration ★ Opus streamObject ~15–30s ~$0.10 INSERTs the PC entities row (entity_type='pc', access_level='known'), backfills characters.entity_id, writes PC↔world relationship rows + PC↔world fact rows including the deferred "starts at $location" fact (re-derived from campaigns.starting_situation_index + worlds.starting_situation_entries). Streams entity-added when the PC is created and edge-added for each relationship.

The table's per-stage costs are the lower-bound point estimate (2K input / 1–2K output per Sonnet call, 2K input / 1K output for Opus). Realistic per-player cost is $0.20–$0.50 once the world snapshot input (8–15K tokens for a full world) and the player's grounding text reach normal sizes. A cost-cap circuit breaker reads settings.character_creation_cost_cap_usd (default $5.00) at the start of each per-player job; over-cap aborts the player's stages with character_creation_cost_cap_exceeded, leaving other parallel jobs untouched. The $5 default covers ~10 players at the realistic upper bound, with headroom for the multiplayer concurrency target of 5–8 per party.

Stages 2–3 are Sonnet, stage 4 is Opus — the parent pipeline spec sketched all four stages as Opus. Stages 2–3 produce bounded structured output (a portable-character payload, D&D 5e SRD-compliant mechanical rows); Sonnet handles that reliably and is ~3× cheaper input, 5× cheaper output. Stage 4 is the load-bearing PC↔world integration: it receives the world snapshot, the player's grounding text, and the chosen situation, and produces a coherent narrative weave (relationships + facts tagged with the PC entity) while also streaming for SSE consumption. The narrative-judgement and cross-reference work matches the Slow Thinker role; Opus is the right tier here.

Lifecycle and late joiners

A member can submit a character as soon as two gates are satisfied: worlds.status = 'complete' and campaigns.starting_situation_index IS NOT NULL. Until both gates hold, POST /characters returns 409 with the specific gate code (world_not_complete or starting_situation_not_chosen). Once a row exists in 'submitted', the player can re-POST to update the prose; the route refuses updates while the row is 'processing' or 'completed' (409 concept_locked).

The owner can trigger start-character-creation any time and as often as they like. Each call enqueues for whatever's currently in 'submitted'; a double-click is safe because the WHERE clause skips 'processing' and 'completed' rows. Late joiners — members who accept invites after the initial fan-out — follow the same flow:

  1. Late member accepts an invite. Their campaign_members row exists; no character_concepts row yet.
  2. Late member POSTs /characters. New row created, status='submitted'.
  3. Owner re-POSTs /start-character-creation. Atomic claim flips only the new row to 'processing', enqueues that one job. Other members' 'completed' rows are untouched.
  4. Late-joiner's character creation runs in parallel with any other in-flight jobs.

Failure handling is per-player and resubmittable. On terminal stage failure the processor sets character_concepts.status='failed' and writes the error JSON; the player can re-POST /characters to reset the row to 'submitted' and the owner re-triggers fan-out. The processor's re-run is idempotent at the stage boundary, not delete-and-recreate: stage 3 detects an existing characters row for (campaign_id, user_id) and UPDATEs rather than INSERTs (TRUNCATE-then-INSERT on the four sub-tables); stage 4 detects an existing characters.entity_id and skips the entity creation (TRUNCATE-then-INSERT on PC-tagged relationships / facts). The frontend reframes the second prompt for late joiners ("describe the situation the party is currently in and how your character fits") but both forms map to the same situation_grounding_text column.

Resubmit-after-failure is idempotent on stage outputs, not a clean slate — the alternative (DELETE the partial PC + sub-table rows on failure) would force the player to re-enter their prose just because stage 4 timed out once. Idempotent re-runs let a transient Anthropic 503 self-heal without losing the player's input or the work stages 2–3 already completed. The UNIQUE(campaign_id, user_id) on campaign_characters + UNIQUE(world_id, name) on entities would otherwise turn the re-run into a constraint violation. Players who genuinely want a clean slate (different name, race, class) re-roll through an admin path — there is no member-facing DELETE in v1.

Cross-PC integration is MYT-54, not MYT-53

Stage 4 (character_integration) is per-player only. It writes PC↔world relationships and PC↔world facts; it does not touch PC↔PC links. Players who want explicit cross-character relationships ("we're siblings", "I owe him money") get that in MYT-54, which layers on top of MYT-53's per-player output:

  • MYT-54 adds a post-fan-out barrier that waits for every per-player job to reach 'completed'.
  • MYT-54 adds an owner-only prompt at fan-out time: "any established relationships between characters to give the LLM upfront?"
  • MYT-54's cross-PC integration stage reads that input and every per-player PC, then writes cross-PC relationship edges and cross-references in facts.

MYT-53's data shapes are designed so MYT-54 can layer on without reshaping per-player output — PC entities, relationships, and facts already exist as first-class rows that the cross-PC pass can read and amend.

Operating this piece

Exercise the routes end-to-end

T23 lands backend/dev-tool/src/components/character-creation-panel.ts, which binds to mythrun.watchcampaign, renders the per-member roster, and exposes the owner action buttons ("Pick starting situation" and "Start character creation"). Until T23 ships, the routes are exercised via curl + SSE inspection + direct psql on the character_concepts and characters tables. The route-audit contract test (backend/src/contract/__tests__/pipeline-routes.test.ts) verifies registration drift as a side-effect of any backend type-check.

Integration points

Upstream: world gen populates worlds.starting_situation_entries (extended in MYT-53) — stage starting_situation now emits a structured three-entry array alongside the existing prose blob, so GET /starting-situations can render the { index, locationEntityId, prose } shape members pick from. Downstream: the pipeline status surface carries per-player events on the same campaign-scoped channel (pipeline:campaign:{campaignId}) — each event payload carries user_id so subscribers can route per-player. The dev tool's live-events panel renders character-creation lifecycle and entity / edge events the same way it renders world-gen events.

Appendix: schema additions

Migration 016_character_concepts.sql adds one new table, two new columns, and one extended CHECK:

  • character_concepts — one row per (campaign_id, user_id). Carries concept_text, situation_grounding_text, guided_choices (always {} in v1), status (submitted | processing | completed | failed), and an error JSONB. Composite FK to campaign_members(campaign_id, user_id) ON DELETE CASCADE.
  • campaigns.starting_situation_index SMALLINT — CHECKed to NULL or {0, 1, 2}.
  • worlds.starting_situation_entries JSONB NOT NULL DEFAULT '[]' — the structured array of three { index, locationEntityId, prose } entries the world-gen starting_situation stage now also emits.
  • entities.entity_type CHECK extended to allow 'pc' — PCs are conceptually distinct from NPCs (one is owned by a real user, the other is purely game-fiction), so reusing 'npc' would force every "list NPCs" path to add a PC-exclusion filter.

The migration also seeds settings('character_creation_cost_cap_usd', '5.00'); the worker reads it at the start of each per-player job via the sumCharacterCreationStageCosts(campaignId) aggregation in cost-cap.ts, filtered on WHERE campaign_id = $1 AND user_id IS NOT NULL AND status = 'completed' so character-creation costs and world-gen costs are budgeted separately.
