Access control & WS ticket

How an authenticated request becomes an authorized one — Fastify preHandler factories that gate campaign-scoped and world-scoped routes — and how the SPA earns a single-use 30-second Redis ticket to authenticate its WebSocket upgrade. A boot-time allowlist refuses any misconfiguration that would short-circuit the chain.

How it fits together

The JWT middleware attaches a claims-only request.user = { sub, cognitoUsername, scopes }. Onboarding's requireOnboarded follows: it looks up the users row by cognito_sub, refuses suspended accounts, and attaches a frozen request.dbUser. The two layers above this page deal with who the caller is. This page is the next step — what they're allowed to touch.

Two factories in backend/src/auth/access-control.ts produce the per-route guards. requireCampaignMember(repo, role?) reads request.dbUser and either request.params.campaignId or a request.resolvedCampaignId set by an upstream resolver, then queries repo.campaigns.getMembership and refuses with 403 not_campaign_member on a missing membership or 403 not_campaign_<role> on a role mismatch. requireWorldCreator(repo) reads request.params.worldId, fetches the world row, and refuses with 404 world_not_found when the row is absent or 403 not_world_creator when world.created_by doesn't match the caller. Both factories take the Repo at registration time and return a preHandlerAsyncHookHandler per route.

Factories returning per-route hooks, not fastify-plugin-wrapped plugins — per-route preHandler arrays don't go through Fastify's encapsulation in the first place; the hook just runs in the route's request lifecycle. Wrapping with fastify-plugin would add ceremony for nothing. The same factories also can't be hoisted to app.addHook('preHandler', ...) at parent scope — they'd fire on every 404 with empty params and throw on every unmatched path. Per-route arrays cleanly avoid that.
403 on non-membership, not 404 — the design briefly considered hiding campaign existence by returning 404 to non-members. Campaign and session ids are UUIDv7 (74 bits of random per id on top of a timestamp prefix; non-enumerable in practice), so existence isn't discoverable by brute force, and the 403/404 split lets the caller distinguish "you can't" from "doesn't exist" — a real signal during dev. World-creator drift (404 when missing, 403 when wrong creator) is intentional for the same reason: the URL carries the worldId; if it's invalid the right answer is 404.

The frozen request.dbUser contract

requireOnboarded attaches request.dbUser with Object.freeze(row) after the cognito-sub lookup succeeds and the suspended_at check passes. TypeScript's readonly is structural-only — the runtime freeze is the actual guarantee that a buggy or malicious downstream hook can't swap fields in place. requireDbUser(request) is the narrowing helper every access-control factory and route handler reaches through; it throws if request.dbUser is missing, which would only happen on a route that bypassed requireOnboarded entirely.

Suspend enforcement happens here, not in a delayed token-revocation flow — Cognito access tokens have a 1-hour lifetime; without a per-request gate, an admin who suspends a user would have to wait up to an hour for the suspension to bite. The synchronous suspended_at IS NOT NULL check in requireOnboarded closes that window. Banned users see 403 {code: 'account_suspended'} on every protected request until they're reactivated.
Cognito-sub vs internal user id, surfaced as two fields — request.user.sub is the Cognito sub claim; request.dbUser.id is the Mythrun-internal UUID the schema's foreign keys point at. Most access-control checks need the latter (campaign membership is keyed on users.id), and re-fetching the row inside every guard would mean a per-request DB hit on top of the one requireOnboarded already paid. Threading the row through as request.dbUser reuses the lookup the earlier hook already did.

Param-name conventions

The factories read :campaignId and :worldId by name from request.params. This is load-bearing — every campaign-rooted route under /api/campaigns/:campaignId/* and every world-rooted route under /api/worlds/:worldId/* honors it. Routes whose URL doesn't carry the right id directly use a small upstream preHandler that resolves the URL's id and assigns request.resolvedCampaignId (or, in the future, request.resolvedWorldId).

The session ws-ticket route is the canonical example: its URL is /api/sessions/:id/ws-ticket where :id is a sessionId. The first preHandler fetches repo.sessions.getById(:id), returns 404 session_not_found if absent, and otherwise sets request.resolvedCampaignId = session.campaignId. The second preHandler is requireCampaignMember(repo), which reads the resolved id.

Augmentation field, not a mutation of request.params — the alternative was splicing campaignId into request.params directly. Fastify v5 populates request.params during routing (before any hook fires) and schema validation runs in preValidation, so a splice in preHandler is invisible to the validator. The augmentation field is still the right call for a different reason: the route's typed Params: { id: string } shape becomes a partial truth, and any OpenAPI or route-introspection tool reading the typed shape would never see campaignId. A typed augmentation field on FastifyRequest makes the data flow explicit.

The boot-time allowlist

access-control-allowlist.ts is a fastify-plugin that wires two hooks: onRoute scans every route registration's preHandler array for a hook carrying the ACCESS_CONTROL_MARKER symbol property (set by the factory on its return value). When it finds one, it inspects the route's config.auth: if the value is 'public' or 'jwt-no-db' — the two settings that short-circuit requireOnboarded and leave request.dbUser undefined — the route is recorded as an offender. onReady throws if the offender list is non-empty, and app.ready() propagates the throw so the deploy fails before the app accepts traffic.

Boot-time gate, not a runtime tripwire — without this hook, a contributor who wires requireCampaignMember onto a config.auth: 'public' route would ship a 500-on-every-request bug that surfaces only in CloudWatch when traffic arrives. The boot gate fails the deploy on a misconfigured registration, in the same place it fails for an unrecognized jwt-no-db route from the JWT_NO_DB_ALLOWLIST. Mirroring the existing pattern keeps the operator's mental model consistent.
Symbol-keyed marker, not function.name reflection — the earlier draft identified guarded routes by reading hook.name === 'requireCampaignMember'. TypeScript's emit can disambiguate inner named function expressions by appending a numeric suffix when the inner name shadows the outer, so the comparison is brittle. Setting a Symbol('mythrun.access-control') property on the returned hook is robust against any name mangling and can't collide with anything Fastify or a future middleware puts on the function.

The WS ticket exchange

WebSocket upgrades can't carry an Authorization header — the browser's WebSocket API doesn't expose one — so they need a different credential. The standard pattern is a single-use short-lived token the SPA fetches over a normal authenticated HTTP request and passes as a query parameter on the WS connect URL. backend/src/auth/ws-ticket.ts implements that store; POST /api/sessions/:id/ws-ticket mints; the session transport upgrade handshake consumes.

mintWsTicket generates a 64-character hex nonce (randomBytes(32) = 256 bits of entropy), JSON-encodes a { userId, sessionId, campaignId } payload, and writes it to Redis under ${keyPrefix}${nonce} with a 30-second TTL via SET … EX 30. The function returns { ticket, expiresAt }; expiresAt is computed Node-side after the round-trip and is informational only.

consumeWsTicket calls ioredis 5.x's typed redis.getdel — atomic read-and-delete in a single round-trip — parses the value, validates the three required string fields, and returns the payload or null. The four causes of null (ticket never existed, ticket already consumed, ticket TTL expired, payload corrupt) are deliberately indistinguishable: consumers treat null as "reject the upgrade with no further reasoning."

GETDEL, not GET + DEL — a non-atomic read-then-delete races: two concurrent consumers could both read before either deleted, both succeed, and the ticket would be used twice. GETDEL (Redis 6.2+, supported by ElastiCache for Redis) is single-round-trip, single-command, atomic. Lua-wrapped GET+DEL has the same atomicity but adds round-trip + scripting overhead with no benefit. The single-use property is what bounds any leak — a leaked ticket (CDN log, browser extension, screen-share) is dead the moment a consumer reads it.
30-second TTL, not 10 or 60 — the source spec said 10s, the Linear ticket said 60s. 30s tolerates SPA hydration plus mobile network blips without giving a leaked ticket any meaningful window. The legitimate client typically consumes within 1-2 seconds of mint; the rest is slack.
Redis errors aren't silently null — a Redis transient (failover, connection refused, MaxRetriesPerRequestError) surfaces as a Promise rejection from getdel. The WS upgrade handler treats the rejection as 503 (transient store unavailability) and the null return as 401 (ticket invalid). The SPA's reconnect logic differentiates: 401 → re-mint and retry; 503 → backoff and retry. Collapsing them into a single response code would make the SPA backoff on a transient that should retry immediately.

Key prefix: ${MYTHRUN_ENV}:${REGION_PREFIX}:ws:ticket:

Staging and production share a single ElastiCache replication group — there is no per-environment cluster split. Without a per-environment key prefix, a staging mint would land in the same keyspace as production reads. backend/src/config/env.ts derives env.redisKeyPrefix as ${MYTHRUN_ENV}:${REGION_PREFIX}:; the ws-ticket helpers append ws:ticket: for their sub-namespace. MYTHRUN_ENV is the new env var the serving module wires from var.environment into the API task definition; REGION_PREFIX already existed (currently use1). MYT-39 is the first code consumer of the convention; every future Redis-keyed subsystem extends it with its own suffix.

Tickets live on redisRealtime, not redisBatch — both resolve to the same single-cluster ElastiCache instance today, but the pin is forward-looking: when the realtime/batch split lands, the ws-ticket store has to live on whichever cluster the WS upgrade handler reads from, otherwise consumeWsTicket becomes a cross-cluster lookup and 100% misses. Tickets must also not collide with BullMQ's bull: namespace conventions on the batch cluster — keeping ws-ticket on realtime keeps the namespaces disjoint by storage as well as by name.

The mint route's preHandler chain

POST /api/sessions/:id/ws-ticket is registered with three load-bearing pieces of config:

  • Default auth (no opt-out). The route inherits the JWT verify + requireOnboarded chain that every default-auth route gets. By the time the route's own preHandler array fires, request.dbUser is attached and frozen.
  • Per-user rate limit, 30/min. The global @fastify/rate-limit is registered with global: false, so without an opt-in this endpoint would be uncapped — an authenticated user could mint tickets in a tight loop against Redis + Postgres. The cap is keyed on requireDbUser(req).id rather than IP, so a CG-NAT pool doesn't share the budget. The store is Redis-backed (per MYT-45) so the cap applies fleet-wide across ECS tasks, not per-task.
  • Two-step preHandler array. Step 1 resolves session.campaignId onto request.resolvedCampaignId; step 2 is requireCampaignMember(repo) reading that field. Splitting the resolver from the membership check keeps the access-control factory generic across "URL carries :campaignId" and "URL carries something we have to resolve" — every other campaign-rooted route reuses requireCampaignMember directly without the resolver step.

The consumer: the WebSocket upgrade handler

This page owns the mint half of the exchange and the consumeWsTicket helper. The WebSocket upgrade handler that calls the helper now exists — it's the handshake on the session transport route (GET /ws/session/:sessionId). Five load-bearing assertions bound how that handler uses a consumed ticket, and the transport handler honors all five:

  1. Re-validate campaign_members on upgrade. A successful consumeWsTicket only proves some member of the campaign minted the ticket within the last 30 seconds. It does NOT prove membership at upgrade time. The handler re-queries repo.campaigns.getMembership — against the loaded session row's campaignId, not the ticket's claimed value — and rejects if the member row is absent or the invite is unaccepted.
  2. Distinguish null from Redis errors. null → 401 (ticket invalid). Promise rejection from getdel → 503 (transient store unavailability). The SPA's reconnect logic differentiates.
  3. Treat expiresAt as informational only. The upgrade's accept/reject is the ground truth.
  4. Surface 401-on-upgrade as a re-mintable error. A leaked-and-consumed ticket manifests as 401; the SPA re-mints. Don't fail hard.
  5. Don't try to distinguish causes of null. Ticket never existed / already consumed / TTL expired / payload corrupt are deliberately indistinguishable. No telemetry that branches on the cause.

Operating this piece

Add a new campaign-rooted route

  1. Use :campaignId in the URL (e.g. /api/campaigns/:campaignId/foo). Default-auth — no config.auth entry — so the JWT chain and requireOnboarded run upstream.
  2. Add requireCampaignMember(repo, role?) to the route's preHandler array. Pass 'owner' when the operation is owner-only; omit the role to require any accepted member.
  3. Read request.dbUser via requireDbUser(request) in the handler; request.campaignMember is also attached and carries the role / invite-accepted status if you need it.
  4. Run pnpm test --filter @mythrun/backend. The access-control-allowlist test suite asserts the boot crash if you accidentally paired the middleware with config.auth: 'public'; you'll see it before the route reaches CI.

Add a route whose URL doesn't carry :campaignId

  1. Mirror routes/sessions.ts: a first preHandler that resolves the URL's id to a campaignId and assigns request.resolvedCampaignId, then requireCampaignMember(repo) as the second entry.
  2. The first preHandler is responsible for the not-found case (e.g. 404 session_not_found); the membership middleware doesn't see that path because resolvedCampaignId is unset and the resolver returned early.
  3. Don't splice the campaignId into request.params. The augmentation field keeps the route's typed Params shape honest for type-introspection tools.

Diagnose a WS-ticket mint failure

  1. The HTTP status discriminates: 401 (no JWT / bad JWT — see JWT middleware logs), 403 (username_required from requireOnboarded, account_suspended, or not_campaign_member), 404 (session_not_found), 429 (per-user rate limit hit), 5xx (Redis transient).
  2. For 5xx during mint, check ElastiCache for failover. The mint is a single SET … EX 30 and surfaces any cluster-side disruption as a 5xx response — there's no retry layer between the route and Redis.
  3. For 429 spikes from a single user, the SPA is probably retry-looping on a different upstream failure (e.g. a flaky WS upgrade). Inspect the SPA's reconnect logic before raising the per-route cap.

Integration points

Upstream: JWT middleware attaches request.user; onboarding's requireOnboarded attaches request.dbUser and refuses suspended accounts. Downstream: the repository layer's repo.campaigns.getMembership, repo.sessions.getById, and repo.worlds.getById are the read-side seams; the backend runtime's AppDeps threads redisRealtime + redisKeyPrefix into the sessions plugin. The serving module is what wires MYTHRUN_ENV into the API task definition. The minted ticket's consumer is the session transport upgrade handshake.
