Identity

The Cognito User Pool every player signs in to, fronted by the Hosted UI, federated to Google and Discord, consumed by the API container as four env vars, and brokered by a thin backend-for-frontend that trades the OAuth code for tokens and parks the refresh token in an httpOnly cookie. Federated only — no email/password, no client secret, no Cognito-managed credentials anywhere.

How it fits together

Identity lives in infra/modules/auth/ and composes into the per-env workspace alongside serving. The module ships one User Pool, one App Client, one Hosted UI domain, two IdPs (Google + Discord), and two Secrets Manager shells the IdPs read on apply. Outputs are wired straight into the API task definition's environment, where the JWT middleware picks them up to validate access tokens.

Federated only — no email + password — Mythrun's audience overlaps near-totally with people who already hold Google or Discord accounts. Adding email + password would inherit a tail of operational and security work — password storage and rotation, reset flows, brute-force defense, MFA implementation, breach-narrative blast radius — for a marginal pool of users who can't sign in with one of the two big OAuth providers. That trade is wrong for a TTRPG product; recovery-email and provider-linking are post-launch follow-ups (see myth-geri) if real users surface account-loss complaints.

The User Pool itself

aws_cognito_user_pool.main is named mythrun-<env>-users, sets username_attributes = ["email"] so OAuth's email claim is the natural sign-in key, and carries deletion_protection = "ACTIVE". mfa_configuration is OFF for staging — federated providers handle their own second factor — and is on the Launch checklist to revisit. The recovery setting is verified_email with priority 1, which never actually fires (no Cognito-stored password to recover) but the API contract demands a recovery mechanism be set even on a federated-only pool.

Region-pinned, no auth-DR posture — Cognito User Pools are region resources. The Pool, the App Client, the IdPs, the Hosted UI domain, and the issuer URL all bake us-east-1 in, and Cognito has no native cross-region replication or PITR. A us-east-1 outage means staging auth is down for the duration. The myth-fhri follow-up — a nightly user-record export to S3 — gives us user-record-granularity recovery for the corruption case (someone fat-fingers a pool delete), which is the failure mode worth defending against. A region outage simply waits.

The App Client and PKCE

aws_cognito_user_pool_client.main is the App Client the SPA talks to. Three settings decide its security shape: generate_secret = false makes it a public client, allowed_oauth_flows = ["code"] with allowed_oauth_scopes = ["openid", "email", "profile"] pins it to Authorization Code grant, and Cognito enforces PKCE automatically on any public client doing the code grant — there is no separate "require PKCE" toggle. The browser generates a code_verifier per sign-in, sends a hash up with the /oauth2/authorize request, and proves possession by sending the verifier back with the token exchange. No secret in the JS bundle, no secret to leak.

Public client, not confidential — a confidential client (with generate_secret = true) would force the SPA to either embed the secret in JavaScript (defeats the point) or proxy every token exchange through the backend (an extra round trip per sign-in for nothing better than PKCE already gives us). The PKCE-public-client pattern is the industry default for SPA + OAuth; we follow it.

explicit_auth_flows = ["ALLOW_USER_AUTH"] pins the InitiateAuth/AdminInitiateAuth surface closed. The SPA never calls those — it goes through Hosted UI's /oauth2/token exchange — so this list is effectively a deny-everything narrow pin against future provider drift. ALLOW_USER_AUTH is the only value AWS accepts here while refresh_token_rotation is enabled, which it is: each refresh-token use mints a new token and invalidates the prior one (Auth spec §6.3).

Why ALLOW_REFRESH_TOKEN_AUTH is not in the list — Cognito rejects ALLOW_REFRESH_TOKEN_AUTH alongside refresh_token_rotation = ENABLED with an InvalidParameterException. The two settings describe the same refresh path and Cognito won't let both be set. ALLOW_USER_AUTH is the modern selection-based flow that is rotation-compatible. Without an explicit list at all, Cognito's omitted-default would re-introduce ALLOW_USER_SRP_AUTH + ALLOW_CUSTOM_AUTH, defeating the federated-only intent.
Why retry_grace_period_seconds is 60, not 0 — the SPA keeps its access token in memory only, so it runs a token refresh on every page load. With a zero grace, a reload-race — two near-simultaneous refreshes from a fast reload or a second open tab — has the second request present a token the first just rotated away; Cognito rejects it as already-used and the user is logged out. A 60-second grace keeps a just-rotated token usable long enough for the in-flight request to land, so the race resolves instead of bouncing the session. The MYT-84 staging smoke surfaced this the moment the cookie actually began to persist.

callback_urls and logout_urls are non-empty allowlists Cognito enforces at the /oauth2/authorize redirect. Staging carries https://staging.mythrun.com/auth/callback only — the production composition (see myth-8pcx) will add the real mythrun.com URLs onto a separate prod App Client. prevent_user_existence_errors = "ENABLED" stops Cognito's default error-response shapes from leaking whether a given email is registered.

One real callback, not a localhost convenience entry — the MYT-36 buildout pointed the staging App Client at http://localhost:5173/auth/callback so a developer could click the flow through before any frontend was deployed. Once the staging frontend shipped and the SPA's OAuth flow was wired (MYT-84), the localhost entry was dropped for the deployed origin. Real OAuth is staging-only; local dev never touches Cognito — it runs the auth bypass seam instead. Keeping the allowlist to exactly the one origin in use means a stolen authorization code can't be replayed against a developer's loopback.

The Hosted UI domain and the /login vs /oauth2/authorize choice

aws_cognito_user_pool_domain.main reserves the mythrun-<env> prefix on AWS's free Cognito-managed domain — the resolved name is mythrun-staging.auth.us-east-1.amazoncognito.com (built in outputs.tf from a data.aws_region.current data source so the module is region-portable). No DNS work, no certificate hand-off from the DNS module, no CloudFront distribution to maintain. Production gets a custom auth.mythrun.com in a follow-up; the module reserves a future var.custom_domain for that.

Why the SPA hits /oauth2/authorize, not /login — Hosted UI's /login endpoint always renders the IdP picker (Google / Discord / email password placeholder) regardless of whether identity_provider=Google is on the query string — that parameter is a hint, not a directive. The production frontend instead hits /oauth2/authorize directly with the provider name pinned, which bypasses the picker entirely and routes the user straight to the chosen IdP. The Auth & Users spec §3 has the full URL shape; this is just the infrastructure side of the handshake.

Two-pass apply, gated by idps_enabled

The module has a chicken-and-egg problem: the IdP resources read OAuth credentials from Secrets Manager, but those credentials don't exist until a human registers an OAuth app at Google's and Discord's developer portals — and the human can't register the OAuth app until they have the Hosted UI's redirect URI to paste into the registration form. We solve it the same way bootstrap-database and RDS provisioning do: a Boolean flag that gates the IdP-creation half of the module, with a manual handoff in the middle.

Apply 1 runs with idps_enabled = false. It creates the User Pool, App Client (with supported_identity_providers = ["COGNITO"] — Cognito rejects an empty list), Hosted UI domain, and the two Secrets Manager shells with placeholder JSON ({ "client_id": "PLACEHOLDER", "client_secret": "PLACEHOLDER" }). The operator then registers the OAuth apps at Google Cloud Console and the Discord Developer Portal — pasting the Hosted UI redirect URI in each one — copies back the client_id and client_secret, and writes them into Secrets Manager: 

aws secretsmanager put-secret-value \
  --secret-id mythrun/staging/google-oauth \
  --secret-string '{"client_id":"…","client_secret":"…"}'

Apply 2 flips idps_enabled = true. The two data.aws_secretsmanager_secret_version data sources resolve, the IdP resources are created reading those values, and the App Client's supported_identity_providers updates to ["Google", "Discord"]. A depends_on from the App Client to both IdP resources prevents Terraform from running the IdP-create and the App-Client-update in parallel — without it, Cognito rejects the App Client update with InvalidParameterException: Identity provider Google does not exist.

Don't pin version_id on the secrets data source — leaving version_stage at its default (AWSCURRENT) means each put-secret-value rotation is picked up on the next plan with no Terraform code change. Pinning a specific version_id would freeze the data source and turn every rotation into a code-edit-and-PR cycle, which is exactly the friction the runbook below avoids.

Discord as an OIDC provider

Discord is configured with provider_type = "OIDC", not the legacy OAuth-only path the parent Auth & Users spec §2.4 originally cited. Discord publishes a working OIDC discovery document at https://discord.com/.well-known/openid-configuration and a spec-compliant userinfo endpoint at https://discord.com/api/oauth2/userinfo (note: not the legacy /api/users/@me path — that's the Discord-bot/non-OIDC API). Going OIDC means Cognito mints an id_token from Discord's claims and attribute mapping references OIDC standard names (sub, preferred_username, email, picture).

OIDC over the legacy OAuth-only path — the OAuth-only configuration would have meant a custom claim-mapping shim (Cognito → Discord-shape JSON), a runtime dependency on Discord's non-standard /api/users/@me endpoint, and a different attribute-mapping vocabulary than the Google IdP uses. OIDC gives us discovery, standard claim names, and a single attribute-mapping idiom across both providers. The parent Auth & Users spec §2.4 has been corrected to match.

The OIDC scope list is openid identify email: openid gates the userinfo endpoint and returns sub, identify is required to receive preferred_username and picture, and email adds email + email_verified. All three are needed for the attribute mapping to populate. The OIDC endpoints are pinned in HCL — Cognito can autodiscover from the issuer's well-known doc, but pinning removes a runtime dependency on Discord's discovery-doc availability and makes the contract auditable from Terraform.

Why lifecycle.ignore_changes on specific provider_details keys — Cognito server-side populates keys we don't set in HCL. Google's IdP fills in standard endpoints (authorize_url, token_url, oidc_issuer, attributes_url, token_request_method) because provider_type = "Google" implies them. Discord's IdP fills in attributes_url_add_attributes. Without the targeted ignore_changes blocks, every terraform plan after apply would surface perpetual diff on those keys. Ignoring a specific list (not the whole map) keeps real drift on client_id/client_secret/authorize_scopes visible.

The four env vars wired into the API task

The module's outputs — user_pool_id, app_client_id, hosted_ui_domain, issuer_url — flow into the serving module's extra_env input as COGNITO_USER_POOL_ID, COGNITO_APP_CLIENT_ID, COGNITO_HOSTED_UI_DOMAIN, and COGNITO_ISSUER_URL. They land on every registered task-definition revision and are now consumed by the JWT middleware: userPoolId + appClientId drive Cognito access-token verification, the issuer_url output's JWKS at ${issuer_url}/.well-known/jwks.json is what the verifier hydrates at boot, and the four are also re-checked in bypass mode to refuse activation if any are populated.

No COGNITO_CLIENT_SECRET env var, deliberately — MYT-25 had speculatively wired a cognito-client-secret Secrets Manager shell and a matching COGNITO_CLIENT_SECRET entry on the API task definition. Public clients have no client secret; both were removed in MYT-36 to prevent MYT-37's first deploy from injecting the literal "PLACEHOLDER" string into process.env and producing a confusing failure later in the auth flow.

The BFF token exchange

The pool and the App Client are only half the sign-in. The other half is a thin backend-for-frontend (BFF) — three routes under backend/src/routes/auth.ts — that stands between the SPA and Cognito's token endpoint so the long-lived refresh token never enters JavaScript. The SPA runs the PKCE authorize redirect itself and comes back holding a one-shot code plus the matching code_verifier; from there the backend takes over.

Why a BFF and not a pure-SPA token exchange — a public SPA client can complete the PKCE exchange itself, but then the refresh_token lives in the browser, and any place a SPA can store it (localStorage, an in-JS variable) an XSS payload can read it — a 30-day credential exfiltrated in one line. Moving the exchange server-side lets the backend keep the refresh token in an httpOnly cookie that script cannot touch; the SPA only ever holds the short-lived access token, in memory. The cost is one backend hop per sign-in and per token refresh, which is cheap against the blast-radius reduction.

All Cognito HTTP in the BFF goes through one abstraction, backend/src/auth/cognito-oauth-client.ts — the same "one layer for one external API" convention the LLM client follows. It wraps Cognito's /oauth2/token and /oauth2/revoke form-encoded endpoints behind exchangeCode / refresh / revoke; there is no inline fetch in the route handlers. Because the client is public, every call carries the client_id and no secret. The three routes:

  • POST /api/auth/session — the SPA posts { code, codeVerifier }. The backend derives the redirect_uri itself from FRONTEND_BASE_URL (never trusting a client-supplied value), runs the authorization-code grant, sets the refresh cookie, and returns { accessToken, expiresIn, name } — where name is the id_token's name claim, the prefill for the display-name onboarding moment. A missing refresh_token in Cognito's response is a 502, not a half-built session.
  • POST /api/auth/refresh — reads the cookie, runs the refresh-token grant, and re-sets the rotated token (rotation is on, so the prior one is retired — after the 60-second grace that lets a reload-race resolve). No cookie, or a rejected grant, clears the cookie and answers 401 — the SPA falls back to sign-in.
  • POST /api/auth/logout — best-effort revoke at Cognito, then clear the cookie and answer 204. The revoke is best-effort because the already-issued access JWT stays valid until its ≤1h expiry regardless; clearing the cookie is the part that must always happen.

The refresh cookie (backend/src/auth/refresh-cookie.ts) is named mythrun_refresh and carries HttpOnly + Secure + SameSite=Lax, a Path=/api/auth scope, and a 30-day max-age. It is host-only — no Domain attribute — so it never broadens to sibling subdomains, and it rides only the /api/auth/* fetches, which the SPA makes with credentials: 'include' against its own origin: the API is reached through the same-origin CloudFront /api/* proxy, so a Set-Cookie on a refresh response is first-party. clearCookie mirrors the same attributes so the browser clears the same cookie it set.

SameSite=Lax under a same-origin proxy, not SameSite=None — because CloudFront proxies staging.mythrun.com/api/* straight to the API, the SPA and its backend present as one origin, and the refresh cookie is set first-party. That lets it be Lax — the stricter choice, never sent on a cross-site request. The earlier attempt served the API split-origin (SPA at staging.mythrun.com, API at staging-api.mythrun.com) and reached for SameSite=None to bridge the two origins — and still failed: Safari's ITP refuses to store a cookie set via a cross-origin fetch at all, even when both hosts share the mythrun.com registrable domain. So the cookie silently never persisted and every reload bounced the user to sign-in (the on-load /refresh reached the BFF with no cookie and 401'd). Collapsing to one origin removes the cross-origin Set-Cookie entirely; Lax is then both correct and the tighter default (MYT-84).
The Origin-CSRF guard, plus /session's JSON-only gate — with the cookie back to SameSite=Lax the browser already withholds it from cross-site requests, so CSRF is largely closed for free. The Origin check stays as defense-in-depth: every browser sends an Origin header on a state-changing POST, so all three routes reject a present-but-mismatched Origin (anything other than FRONTEND_BASE_URL) with 403 forbidden_origin. An absent Origin is allowed — that's a non-browser caller, which can't hold a victim's httpOnly cookie anyway. On top of the Origin check, /session stays JSON-only with no form-body parser: it rejects anything but application/json with a 415, and a browser can auto-submit a cross-site form POST without a preflight but cannot send application/json cross-origin without tripping CORS first — so an attacker can't silently plant a session cookie from another origin. The three routes are also public in the route allowlist — the caller has no access token yet on /session, and /refresh + /logout authenticate by the cookie, not a Bearer — and each is per-IP rate-limited.

The BFF registers only when AUTH_MODE=real (it needs the Hosted UI domain + App Client id, and it pulls in @fastify/cookie). Local dev runs bypass and never reaches these routes — which is why the staging App Client's callback list no longer carries a localhost entry. Server-side, pino redacts the cookie and set-cookie headers from logs so the refresh token never lands in CloudWatch.

Operating this piece

Rotate an OAuth client secret

  1. At the provider — Google Cloud Console (APIs & Services → Credentials → the Mythrun OAuth 2.0 Client ID) or Discord Developer Portal (Applications → Mythrun → OAuth2 → Reset Secret) — generate a new client_secret. Copy both the (unchanged) client_id and the new client_secret.
  2. Push the new pair into Secrets Manager: 
    aws secretsmanager put-secret-value \
  --secret-id mythrun/<env>/<google|discord>-oauth \
  --secret-string '{"client_id":"<same>","client_secret":"<new>"}'
  3. Run terraform apply in the env workspace. The data.aws_secretsmanager_secret_version data source picks up AWSCURRENT (no version_id pin), and the IdP resource updates its provider_details.client_secret in place. No Cognito downtime, no user-side action.
  4. Click through a sign-in (see the verification runbook below) to confirm the new secret is live on Cognito's side.

Recover from an accidental User Pool deletion

  1. Don't panic — deletion_protection = "ACTIVE" means the only ways the Pool can actually disappear are (a) someone disabled the protection in console first, or (b) the Terraform state was edited out-of-band. Either way the resource is gone, every existing JWT is invalid, and every user record is lost.
  2. Restore from the most recent myth-fhri nightly export in S3 if it exists (this follow-up ships post-launch). Without it, accept the user-record loss — federated sign-in still works for every player from a fresh "first login" record.
  3. terraform apply in the env workspace recreates the Pool, App Client, and Hosted UI domain. Pool and App Client IDs will be different — the four COGNITO_* env vars change.
  4. Update the OAuth redirect URI lists at Google Cloud Console and the Discord Developer Portal — they reference the Hosted UI domain, which has changed. The mythrun-<env> domain prefix should be the same; verify the resolved mythrun-<env>.auth.us-east-1.amazoncognito.com is unchanged.
  5. Run a CI deploy so the API service rolls onto the new task-definition revision (the one carrying the new COGNITO_* values).
  6. Click through the verification runbook below to confirm both providers work end-to-end.

Verify a sign-in flow click-through

  1. Construct the authorize URL by hand (the SPA does this in production): 
    https://mythrun-staging.auth.us-east-1.amazoncognito.com/oauth2/authorize
  ?client_id=<COGNITO_APP_CLIENT_ID>
  &response_type=code
  &scope=openid+email+profile
  &identity_provider=Google
  &redirect_uri=https://staging.mythrun.com/auth/callback
  &code_challenge=<sha256(code_verifier), base64url>
  &code_challenge_method=S256
  2. Open it in a browser. Expect a direct redirect to Google's sign-in page (no Cognito IdP picker — that's the difference between /oauth2/authorize and /login).
  3. Sign in with a Google account. Expect a redirect back to https://staging.mythrun.com/auth/callback?code=…&state=…. The deployed SPA now handles this leg itself — it posts the code to the BFF's /api/auth/session and lands you on the Hub — so the simplest end-to-end check is just "did I reach the Hub?". To isolate a Cognito-side problem from a SPA-side one, grab the code from the redirect in DevTools' network tab before the SPA consumes it (the code is single-use) and run the manual exchange below.
  4. Exchange the code against Cognito directly — the same grant the BFF runs server-side: 
    curl -X POST https://mythrun-staging.auth.us-east-1.amazoncognito.com/oauth2/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=authorization_code" \
  -d "client_id=<COGNITO_APP_CLIENT_ID>" \
  -d "code=<code from the redirect>" \
  -d "code_verifier=<the verifier from step 1>" \
  -d "redirect_uri=https://staging.mythrun.com/auth/callback"
    Expect a JSON response with id_token, access_token, and refresh_token. Decode the id_token at jwt.io and check that iss matches COGNITO_ISSUER_URL and that the identities[0].providerName is Google.
  5. Repeat with identity_provider=Discord to verify the second IdP.

Integration points

The four COGNITO_* env vars land on the API task definition via serving's extra_env input — the same plumbing staging uses for BOOT_GATE_ENABLED. The JWT middleware consumes them on every API boot — verifying tokens against issuer_url's JWKS and refusing to start in bypass mode if any of the four are populated. The same vars feed the BFF token exchange above, whose access token then carries the verified sub the onboarding flow turns into a user row on first sign-in; the SPA app shell is the client half that runs the PKCE redirect and stores the access token in memory. The OAuth client credentials live in Secrets Manager alongside the other per-env secrets the platform owns. Discord's OIDC userinfo endpoint and Google's OAuth flow are the two external integration points; both are pinned in provider_details rather than autodiscovered, so a Discord /.well-known/openid-configuration outage doesn't stop sign-ins on a cold terraform apply.
