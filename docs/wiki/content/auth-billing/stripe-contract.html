Stripe contract

How Mythrun pins its commercial relationship with Stripe: a closed enum of lookup_keys in code, a cached SDK client pinned to one API version, a read-only boot probe that fails closed if Stripe's catalog drifts, and a restricted-key boundary that makes mutation impossible on the wire. No price_* ID is hardcoded in backend code; price stays in Stripe.

How it fits together

Six files in backend/src/billing/ and backend/eslint-rules/ hold the whole surface: lookup-keys.ts declares every SKU as a closed TypeScript enum, stripe-client.ts caches the SDK client pinned to one apiVersion, probe.ts verifies on every boot that Stripe's live catalog matches the enum and populates the module-level sku-cache.ts the rest of the system reads, and two ESLint rules under backend/eslint-rules/ reject any source pattern that would mutate the catalog from the SDK. Two env vars (STRIPE_SECRET_KEY, STRIPE_WEBHOOK_SECRET) wire it to the running container; the boot gate calls the probe between waitFor(pg, redis×2) and app.listen, so a contract mismatch turns the deploy red and triggers an ECS rollback before traffic ever reaches the new tasks. The webhook plugin is what consumes the STRIPE_WEBHOOK_SECRET at request time; everything Stripe-call-shaped on the request path resolves through the cached client and the cached SKU snapshot.

Lookup keys, not price IDs — Stripe price objects are immutable: changing a price's amount means archiving the old one and creating a new price_* ID. If backend code referenced prices by ID, every price-amount change would be a code-and-deploy ceremony to swap the constant. Lookup keys are a stable indirection: backend code says tier_wayfarer, Stripe holds the active price under that lookup key, and operators re-point the lookup key to a new price object in the Dashboard whenever the dollar amount needs to change. The probe is what guarantees the indirection still resolves on every boot.

The closed enum and what it carries

lookup-keys.ts exports a LOOKUP_KEYS object literal with five entries: three subscription tiers (tier_wayfarer, tier_sojourner, tier_mythwright) and two a-la-carte SKUs (sku_session, sku_world). Each entry is a LookupKeySpec declaring the lookup key itself, a display name that matches the Stripe product name, the price type (recurring for tiers, one_time for SKUs), and the credit-allocation contract — how many sessions and worlds a successful purchase or billing cycle grants. The TypeScript union type LookupKey is derived from the same five strings, so any code path that takes a lookup key gets compile-time narrowing across the closed set.

Allocation lives in TypeScript, not in a database table — migration 006 dropped the subscription_tiers and session_packs config tables that earlier designs anchored the allocation against. A DB-resident config is right when operators need to change values without a deploy; for Mythrun's pricing surface (five SKUs, hand-curated by Miklos, no operator-tunable knob), the cost-of-change is dominated by the spec patch and the social decision, not the table-edit ceremony. A checked-in TS enum gives type safety, code-review for every change, and grep-ability across the codebase. If the surface ever grows beyond hand-curation the contract can move back into a table without breaking consumers — they all flow through LOOKUP_KEYS.

The cached SDK client

stripe-client.ts exports getStripeClient(env) — a module-level cache that constructs one Stripe instance the first time it's called and returns it on every subsequent call. The instance is pinned to apiVersion: '2026-04-22.dahlia', the Stripe API release line in force at MYT-41 design time. Bumping that version is a deliberate spec patch: it changes webhook payload shapes and field names, the SDK type-narrows apiVersion to a literal union of valid values, and the boot probe re-runs against the new shape. Routine maintenance reviews Stripe's API changelog every six months; bumps happen only when there's a feature Mythrun needs or a breaking change with a sunset date.

Pinned apiVersion, not "use whatever Stripe's account default is" — Stripe lets you set a per-account default API version in the Dashboard, but that's an action at a distance: a Dashboard click could silently change the shape of webhook payloads and SDK responses the deployed binary saw the previous day. Pinning in code means the wire format is whatever the binary was built against, full stop. Upgrading is a code change reviewed and rolled like any other.
Module-level cache, no rotation API — the cache is process-scoped on purpose. Rotating the Stripe key requires rolling the ECS service after Secrets Manager updates so the new process picks up the new value at boot. There is no in-process "swap clients" path because there is no in-process secret-rotation requirement, and adding one would split the contract surface. Tests that need a different env mock the SDK at the import boundary (Vitest's vi.mock); they do not reach into this cache.

The boot probe and its four error classes

probe.ts exports probeStripeContract(stripe, logger). It runs stripe.prices.list once with the closed-enum lookup keys as the filter, active: true, and expand: ['data.product'] so the response includes whether each price's parent product is active. The probe verifies, for each lookup key, that the Stripe response contains exactly one active price whose currency is usd, whose type matches the enum (recurring vs one_time), whose unit_amount is positive, whose billing_scheme is per_unit, whose transform_quantity is null, whose tax_behavior is unspecified, whose product is active, and — for tiers — whose recurring shape is monthly licensed (interval = 'month', interval_count = 1, usage_type = 'licensed'). Each verified entry is recorded in the module-level SKU cache so the rest of the system can resolve lookup_key ↔ price_id without hitting Stripe at request time. The probe then performs a second contract check against the account's default Customer Portal configuration to verify the asymmetric upgrade-immediate / downgrade-at-renewal shape downgrades depend on.

The probe distinguishes four failure modes by throwing different typed errors:

  • BillingProbeAuthError — Stripe replied 401/403. The fix is to rotate STRIPE_SECRET_KEY; retrying won't help. Thrown immediately on StripeAuthenticationError or StripePermissionError, no backoff.
  • BillingProbeError — Stripe replied with a price set that doesn't match the contract. The error message lists every mismatch (missing lookup key, wrong currency, archived product, duplicate active price under one lookup key, etc.). The fix is in the Stripe Dashboard, not in code. Thrown after a single successful round-trip; no retry would change the answer.
  • BillingProbeStripeAPIChangeError — Stripe returned has_more: true on a query bounded by the enum size. With at most five lookup keys, that's structurally impossible against today's prices.list API; the only way it fires is if Stripe changes the API contract. The fix is a code change to handle the new shape.
  • BillingProbeTransientError — Stripe replied with a 5xx, a network timeout, or a rate-limit error. The probe retries up to three times with exponential backoff (1s, 2s, 4s) plus up to one second of jitter; only after the budget is exhausted does this error throw. The fix is usually waiting; the throw still fails the deploy because starting a binary that can't reach Stripe is worse than deferring the rollover.
Four error classes, not one generic "probe failed" — a single error class would put the operator in front of a stack trace and force them to read it to know which knob to turn. The four classes encode the actual decision tree on the error type: auth → rotate the secret; contract → fix the Dashboard; API change → write code; transient → wait, then retry. Each class carries a bootId (a UUID generated per probe invocation) so a CloudWatch query can reconstruct one boot's probe events end-to-end across the four log lines the probe emits (billing.probe_started, billing.probe_transient_retry, billing.probe_passed / billing.probe_failed / billing.probe_auth_failed / billing.probe_transient_failed).
Duplicate detection fails loud, not silent last-wins — if the Stripe Dashboard ends up with two active prices under the same lookup key (a tired operator forgot to archive the old one before creating the new), the SDK happily returns both. A naive map[lookup_key] = price reduction would silently take whichever came last, and the charged amount on the next purchase would be a coin flip. The probe counts occurrences first, reports any lookup key with n > 1 as a mismatch, and skips it from the per-price contract checks so the diagnostic stays clean.

The SKU cache and its public projection

sku-cache.ts is a module-level snapshot the probe writes into on a successful pass: a byLookupKey map and a byPriceId reverse map (both keyed on the SkuInternalEntry shape, which carries stripe_price_id alongside the display fields), plus a publicListing array of the same entries with stripe_price_id stripped. The cache is process-scoped and never refreshed within a process — a price drift in Stripe is caught at the next deploy boundary, when the new tasks re-run the probe.

Three consumers read the cache: the /api/billing/skus route serves the public listing as a marketing-page payload; webhook handlers use byPriceId to resolve the lookup_key from a Stripe-side price.id they receive on invoice.paid; the checkout and tier-upgrade routes use byLookupKey to resolve the cart items' price IDs and to compare tier amounts.

Internal vs public projection split — every Stripe price has an internal price_* ID that the SDK needs and the marketing page does not. Returning the full internal entry on the public route would expose a piece of catalogue plumbing on an unauthenticated endpoint. Two projections — one with the price ID, one without — make the least-disclosure principle structurally enforced rather than convention-enforced.

The Customer Portal config probe

After the prices-list pass, the probe runs a second contract check against stripe.billingPortal.configurations.list({ active: true, is_default: true }). It expects exactly one default config back and verifies two fields: features.subscription_update.proration_behavior === 'create_prorations', and schedule_at_period_end.conditions includes a { type: 'decreasing_item_amount' } entry (the asymmetry that defers downgrades to period end while leaving upgrades to take effect immediately). A mismatch throws BillingProbePortalConfigError; the deploy fails the same way a price-list mismatch would.

The Portal carries downgrades; the API carries upgrades — Mythrun routes upgrades through POST /api/billing/upgrade-tier because the upgrade path needs proration_date = current_period_start to make the upgrade non-gameable, and the Portal's create_prorations behavior doesn't expose that knob. Downgrades go through Portal Switch Plan with schedule_at_period_end, which defers the change until the period boundary so a user who downgrades on day 1 keeps their paid tier until day 30. The probe verifies the Portal config carries this asymmetric shape; without it, downgrades would take effect immediately and the user would lose tier access they'd already paid for.

The boot-gate wiring

server.ts's boot-gate path runs the probe in a fixed sequence: load env (which validates STRIPE_SECRET_KEY's rk_ prefix), open the pg pool and two Redis clients, sequentially waitFor all three to return healthy, construct the cached Stripe client, await probeStripeContract, then build the Fastify app and listen. Anything thrown by the probe propagates out of main()'s try block, lands in the catch, runs closePartials over the pg + redis clients, sets process.exitCode = 1, and arms the five-second watchdog. The deploy pipeline sees the non-zero exit, ECS marks the task unhealthy, and the CircuitBreaker rolls the deployment back. New tasks never go into rotation with a broken billing contract.

Probe runs after data probes, before app.listen — running it earlier would race against pg/redis becoming reachable; running it later would mean the listening socket is open before the probe has run, so a fast health check could mark a contract-broken task healthy. Between waitFor and listen is the one slot where every prerequisite is true and the failure-mode is "task crashes before serving traffic," which is exactly what the deploy pipeline is shaped to roll back from.

The restricted-key boundary

config/env.ts rejects any STRIPE_SECRET_KEY that doesn't start with rk_. Mythrun deploys with Stripe restricted keys (read on Prices, write on Subscriptions and Customer-Portal sessions, nothing else); full-permission keys (sk_*) are forbidden in deployed environments. The actual price-mutation boundary is the restricted key itself — Stripe rejects any prices.create, products.update, etc. at the API edge regardless of what the SDK call looks like — but the env-load check catches the foot-gun where someone misrotates a full-permission key into Secrets Manager. With a sk_* key in place, the boot probe (which is read-only) would still pass, and the defense-in-depth stack would silently degrade to "we trust app code not to mutate prices" instead of "Stripe rejects mutations at the network layer."

STRIPE_WEBHOOK_SECRET follows a softer rule: any non-empty value is accepted at env-load. The actual gate is at the webhook plugin's signature verification: stripe.webhooks.constructEvent is invoked unconditionally on every delivery; any signature mismatch fails closed and returns 400. There is no bypass branch for the literal string anywhere — a misconfigured secret produces a webhook that rejects every event Stripe sends, which surfaces in the Stripe Dashboard's webhook attempts UI within minutes.

The ESLint AST tripwires

backend/eslint-rules/no-stripe-price-mutations.cjs is an AST rule that pattern-matches stripe.<namespace>.<method>(...) calls and rejects any in the banned set: prices.create, prices.update, products.create, products.update, products.del, coupons.create, coupons.update, coupons.del, promotionCodes.create, promotionCodes.update. no-stripe-subscription-price-mutation.cjs closes the price-change-via-subscription-item-update backdoor: any call shaped like stripe.subscriptions.update(id, { items: [{ price: 'price_X' }] }) trips the rule. Quantity-only item updates and other subscription-update fields (cancel_at_period_end, metadata, pause_collection) remain allowed — the restricted key needs Subscriptions: write for the cancel flows.

Both rules are registered under the mythrun plugin namespace in eslint.config.js at error severity, so a violation fails pnpm lint in CI. A config-wiring smoke test under backend/eslint-rules/__tests__/ spawns a child eslint pointed at a banned-pattern fixture and expects a non-zero exit with the rule name in the output — catches the failure mode where a rule ships but isn't registered.

Code-review tripwire on top of the restricted key, not instead of it — the restricted key is the actual security boundary; the ESLint rules are a redundant catch-it-at-review layer. Pattern-evasion paths the rules don't catch (bracket access stripe['products']['create'](...), alias rebinding, (stripe as any) casts) are documented at the top of each rule. None of those paths get past the restricted key. The rules' value is "an honest mistake in a PR shows up as a lint failure on the diff," not "this is what makes mutation impossible."

Operating this piece

Rotate the Stripe restricted key

  1. Mint a new restricted key in the Stripe Dashboard with the same scope (Prices: read, Products: read, Subscriptions: write, Checkout sessions: write, Billing portal: write, Customers: read+write, Webhooks endpoints: read; nothing in the Prices: write or Products: write columns).
  2. Write the new value to the per-env Secrets Manager shell: aws secretsmanager put-secret-value --secret-id mythrun/<env>/stripe-secret-key --secret-string <value>. The shell has ignore_changes = [secret_string] on its Terraform version, so this write is safe and out-of-band — Terraform won't try to overwrite it.
  3. Roll the API service so running tasks pick up the new secret on their next boot: aws ecs update-service --cluster mythrun --service mythrun-<env>-api --force-new-deployment. The boot probe re-runs against the new key. If the new key's permissions are wrong, you'll see BillingProbeAuthError in CloudWatch and the deployment will roll back.
  4. Once the rollover completes, revoke the old key in the Stripe Dashboard. Don't reverse the order — revoking before the rollover finishes will fail a probe mid-flight.

Diagnose a failed billing probe

  1. Find the billing.probe_failed / billing.probe_auth_failed / billing.probe_transient_failed log line in CloudWatch — every probe carries a bootId UUID for cross-line correlation: 
    filter event like /billing.probe/
| fields @timestamp, event, bootId, mismatchCount, mismatches, err
| sort @timestamp desc
| limit 50
  2. billing.probe_auth_failed → the restricted key is wrong, expired, or its scope doesn't include Prices: read. Mint a new key (see above) or check the Dashboard for the permissions on the existing one.
  3. billing.probe_failed with a mismatches array → Stripe's catalog drifted from the contract. Each mismatch names the lookup key and what's wrong (missing, duplicate, wrong currency, archived product, etc.). The fix is in the Stripe Dashboard: archive duplicates, reactivate products, repoint lookup keys to active prices.
  4. billing.probe_transient_failed after three retries → Stripe is having a bad minute, or the VPC's NAT egress is degraded. Check status.stripe.com; re-run the deploy once Stripe recovers.
  5. BillingProbeStripeAPIChangeError → Stripe changed the prices.list API contract. This requires a code change in probe.ts to handle the new shape; check Stripe's API changelog for the breaking change and bump STRIPE_API_VERSION in stripe-client.ts alongside the fix.

Add a new tier or SKU

  1. Pick a lookup key that follows the existing convention (tier_* for recurring, sku_* for one-time). Add the entry to LOOKUP_KEYS in backend/src/billing/lookup-keys.ts with the display name, type, and credit-allocation contract.
  2. In the Stripe Dashboard (test mode first, then production after launch), create the product, a price under it, and set the price's lookup_key to match the enum value. Confirm the price is monthly licensed for tiers, USD, no tax handling, no quantity transformation.
  3. Run pnpm dev locally with the test-mode key in backend/.env.development. The boot probe should log billing.probe_passed with the new count. If it logs billing.probe_failed, the Dashboard shape doesn't match — fix it there.
  4. Ship the code change through the normal deploy pipeline. The probe re-runs against staging's Stripe account on every deploy, then against production's. A drift between the two surfaces as a probe failure on the second deploy.
  5. If LOOKUP_KEYS ever grows past 100 entries, the probe needs pagination — there's a static guardrail at the top of probe.ts that throws a load-time error well before the Stripe API's 100-element lookup_keys filter cap silently truncates.

Integration points

The two Stripe secrets live in Secrets Manager as per-env shells and are wired into the API task definition by the serving module; rotating them follows the manual-secret rotation runbook on the serving page. The boot probe runs inside the backend's boot gate; a probe throw uses the same fail-closed-and-rollback path as a pg/Redis probe failure. The webhook plugin is the request-time consumer of STRIPE_WEBHOOK_SECRET and the byPriceId reverse map, and the billing routes consume the cached SKU listing for the public catalogue and resolve cart items via byLookupKey. The schema's migration 007 holds the four billing tables the webhook handlers write to (purchases, user_subscriptions, billing_history, plus the new FK columns on credit_ledger); the repository layer exposes the matching namespaces.
