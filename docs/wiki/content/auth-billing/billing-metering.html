Billing metering

How a live session's LLM cost is tracked, how trial and paid credit are kept mutually exclusive, how the demo world is wired as the trial entry-point, and how the rate map stays aligned with Anthropic's published pricing.

How it fits together

Mythrun charges users a fixed price per session at the consumer surface (Stripe handles the money). Internally, every LLM call inside a session has a real Anthropic-side cost, and the Session Runtime needs that running total to know when to start ramping the narrative toward a graceful close. The data plane that ships in MYT-43 is four concerns wrapped into one cluster: per-session cost metering, the credit-consumption primitive that powers session start, the trial / paid mutual-exclusion rule, and the demo world that acts as the trial entry-point. A daily price-check workflow keeps the rate map honest.

Postgres-only metering, no Redis live counter — earlier drafts followed a “Redis live counter, Postgres 5-min checkpoint” pattern from the source spec. Re-evaluation: at ~7 LLM calls per second across 500 concurrent sessions (and a 1–3 ms Postgres read against a 200–2000 ms LLM round-trip), Redis was paying complexity cost (cross-source consistency, lossy checkpoint windows, crash-recovery reconciliation) for benefits we don't need. The metering path now writes per call to session_usage and reads the running totals back from the same UPSERT — no extra round-trip, no Redis layer. Redis still earns its keep elsewhere (WS session-state cache, the WS-ticket store, rate-limit backing); it just doesn't fit the cost-tracking workload.

Per-session cost metering

repo.sessions.recordUsage is the seam every LLM call's accounting flows through. The signature is recordUsage(sessionId, model, deltas) where deltas carries inputTokens, outputTokens, and the optional cacheWriteTokens / cacheReadTokens. The function computes the call's USD contribution at write time, then runs an UPSERT against session_usage keyed on session_id: the first call inserts a row, every subsequent call increments the running totals on the existing row. The post-update row is returned, so the caller has the cumulative estimated_cost_usd immediately and can compute “did we just cross 80% of the cost cap?” inline.

One row per session, not one row per LLM call — per-call rows would give a fully detailed audit but add a hot-path INSERT per turn, multiply the analytics surface, and inflate the simplest receipt query (“what did this session cost?”) from a SELECT to a SUM-over-thousands-of-rows. The single-row UPSERT is the cheapest shape that still answers every question the Session Runtime, dashboards, and end-of-session receipts need; the per-model breakdown is deferred to a future analytics table if it ever earns its keep. The idx_session_usage_one_per_session partial unique index pins the contract at the DB layer.

session_usage keeps three input-side token classes as separate columns — input_tokens (base prompt), cache_write_tokens (5-min cache write), cache_read_tokens (cache read) — alongside output_tokens and estimated_cost_usd. Migration 008 dropped the abandoned budget_limit_tokens column: token-budget enforcement is replaced by cost-cap + Fast-Thinker context-cap + Slow-Thinker narrative wrap, all of which the Session Runtime emits through the same ST-driven graceful-close path.

Cost cap, not a model-blind token budget — a 500K-token cap means $37.50 of Opus or $2.50 of Haiku — a ~15× cost variance for the “same” budget. Cost is the metric that matches what we actually pay Anthropic and what the player paid Stripe for the session. The cap value lives as a global setting (env var or settings row) read by the Session Runtime at startup; not a per-row column on session_usage, because every session has the same cap and a per-row column would be redundant noise.

repo.sessions.budgetSummary is the read-side for non-hot-path consumers (receipts, dashboards, end-of-session reports, future crash-recovery state). Plain SELECT, returns the row or null for sessions with no LLM calls yet. The Session Runtime hot path deliberately does not call budgetSummary — it uses recordUsage's return value, saving one round-trip per turn.

Bad sessionId is a tripwire, not a silent no-op: recordUsage throws SessionNotFoundError when the SELECT-FROM clause matches zero sessions rows. The hot path should never see this; firing means an upstream bug routed an LLM call to a deleted or fictional session. recordUsage is also non-idempotent under retry — a retried call double-counts. The Session Runtime is responsible for not retrying after a partial failure; if real retry-safety is ever needed, a per-call reportingId + composite unique constraint is the documented next step.

The pricing constants and the 4-rate model

backend/src/billing/model-pricing.ts exports MODEL_PRICING — USD per million tokens for each model we use, across all four rate categories Anthropic publishes: base input, output, 5-minute cache write (1.25× input), cache read at any TTL (0.10× input). computeCostUsd(model, deltas) is the pure function that weights each delta by its rate and returns dollars. The constants live in the billing module, not the LLM module, because cost is a billing concern; the LLM client logs token counts only and leaves the rate-map as the billing module's responsibility.

5-minute cache only; 1-hour cache rate not tracked — Anthropic offers two cache TTLs (5-minute ephemeral and 1-hour extended). Their write costs differ: 1.25× input for 5-min, 2× input for 1-hour. A typical 3-hour Mythrun session at one turn per minute reads the cache >100 times after a single write, and TTL refreshes on every read at no charge — so the 5-min cache stays warm across the whole session. The 1-hour cache only wins for pathological pause patterns. We track the 5-min rate; computeCostUsd throws if a 1-hour cache token count is ever passed in, so a regression here fails loud rather than silently mis-charging by treating 1-hour writes as 5-min-rate writes.
Approximate cost, not billing — Stripe charges the user a fixed $/session; these rates power internal cost-cap signaling, dashboards, and CloudWatch alarms. Drift up to a few percent is acceptable directionally. The event: 'llm.call' log line still carries raw token counts as the durable signal — the Mythrun-wide rate map can change without rewriting log history.

Trial and paid: mutual exclusion, not trial-FIRST

A user's credit ledger contains either unexpired trial credits or unexpired paid credits, never both at the same time. The invariant is maintained by auto-burning the trial credit on the first paid grant. This replaces the source spec's earlier “trial-FIRST consumption” rule that asked the debit recipe to drain trial credit first.

Why mutual exclusion beats trial-FIRST — trial-FIRST means a user who buys credit while still inside their trial would experience trial-mode (45-min cap, demo world, reduced budget) on their first paid session, then full-mode after the trial drained. That's a bad UX: the user paid, and the next session should unambiguously be the full experience. Burning the trial at purchase time pins the contract: paid grant → trial gone, every subsequent debit consumes paid credit. The rule lives at the grant call site, not the debit call site, so callers of atomicDebit don't have to reason about FIFO ordering across source types.

The trial-burn happens inside grantInTx when the grant's sourceType is 'purchase' or 'subscription' (other source types — gift, trial, refund — do not burn). The helper sums the unexpired trial balance for the same (userId, creditType), then writes a single negative-amount debit row for that exact balance. The burn's source_id is a deterministic UUIDv5 derived from (userId, creditType) against a Mythrun-pinned namespace UUID; webhook redelivery sees the existing burn row, the ON CONFLICT … DO NOTHING clause makes the second attempt a no-op, and the new paid grant lands its own row regardless.

UUIDv5, not a string-keyed source_id — credit_ledger.source_id is declared UUID per migration 001, so a string like 'trial-burn:<userId>:<creditType>' would fail with invalid input syntax for type uuid on the first burn call. UUIDv5 (RFC 4122 §4.3 — SHA-1 of namespace-bytes || name-bytes, with version + variant bits set) is the standard way to derive a deterministic UUID from input. The implementation is a ~15-line helper at backend/src/repo/uuidv5.ts, single-purpose; we don't depend on the uuid npm package because UUIDv5 is the only flavor we need from it (UUIDv7 already lives in repo/uuidv7.ts). The namespace UUID (019700e0-0000-7000-8000-000000000003) is generated once and never changes — rotating it would orphan existing burn rows from their idempotency check.

The trial-mode signal: consumedSourceType

Under mutual exclusion, all unexpired positive credits at any moment are the same source-type class. atomicDebit reads the source_type of the FIFO-oldest unexpired positive credit before writing the debit, and returns it as consumedSourceType on the result. The Session Runtime reads consumedSourceType === 'trial' as the trial-mode signal — no separate “is this user on trial?” lookup. The result shape is { entry, consumedSourceType }; tests + handlers narrow on the discriminator.

tryDebitForSession(userId, sessionId) is the thin wrapper the Session Runtime's session-start route will call. It debits exactly one session credit (the per-session $/cost is observability-only — Stripe charges a fixed $/session at the consumer surface), keys the debit's source_id off sessionId for per-user idempotency, and translates the InsufficientCreditsError path into a typed { ok: false, code: 'insufficient_credits', available, required } result the route layer maps to 402 Payment Required. Other errors (UserNotFoundError, IdempotencyConflictError, DebitTimeoutError) still throw — the typed result is for the “you're out of credits” gentle-UX path only.

402 Payment Required, not 403 or 409 — 402 is the literal-meaning HTTP status for “you can't have this resource until you pay.” Frontends match on status to render the gentle out-of-credits UX (purchase prompts) vs. the error UX (other 4xx/5xx). The body shape {code: 'insufficient_credits', available, required} matches the rest of the codebase's {code: '<snake_case>'} convention. The route that consumes tryDebitForSession is out of scope for MYT-43; it lands when the Session Runtime ships the session-create endpoint.

The demo world: trial entry-point

Trial-mode sessions need a world to play in. worlds.is_demo is the at-most-one-demo flag, enforced by the partial unique index idx_worlds_one_demo (only rows with is_demo=true participate in uniqueness; retired demo rows with is_demo=false can accumulate freely). Migration 008 seeds one placeholder demo world owned by a new system users row. repo.worlds.getDemo() returns the singleton row.

The system user is permanently suspended — the seeded system users row owns the demo world (and any future platform-seeded content). It has no Cognito identity; the cognito_sub is set to the literal 'system:mythrun', which can't collide with a real Cognito-issued sub. The suspended_at column is set to a 1970 sentinel timestamp so the row can never authenticate even if a future bug routed a JWT to that cognito_sub — the requireOnboarded gate refuses any user with a non-null suspended_at.

The placeholder demo world ships with a stub concept (“Trial-mode demo world. Narrative content authored separately.”) and is_public=false — it's a fork-source, not a browsable public world. Real narrative content (concept, tone, themes, NPCs, opening situation) lands later as an UPDATE to the same row; that authoring task is out of MYT-43's scope and tracked outside Linear. The Session Runtime's fork-on-trial-start logic is also separate; MYT-43 ships only the schema, the seed, and the helper.

The daily price check

MODEL_PRICING is hardcoded — Anthropic exposes no programmatic pricing API to query at runtime, and a third-party JSON like LiteLLM's would put us behind someone else's SLA with no commitment to schema stability. The .github/workflows/llm-price-check.yml workflow runs daily at 14:00 UTC (~9am Eastern). It fetches the public Anthropic pricing docs page, sends the rendered text to Haiku with a Zod-validated structured-output schema (scripts/check-pricing.ts), sanity-bounds the result, and diffs against MODEL_PRICING with a 1e-6 USD/MTok epsilon. Any difference exits non-zero and the existing CI alarm pipeline pages on it.

Multiplier-based sanity bounds, not just absolutes — an order-of-magnitude hallucination (Haiku returning $25 for input where it's actually $5) is one failure mode; wrong-cache-tier confusion (Haiku returning the 1-hour cache write rate where the docs say 5-min) is the subtler one. Multiplier ranges (cacheWrite must be 1.0×–2.5× input, cacheRead must be 0.05×–0.20× input) catch the wrong-tier shape that absolute bounds would miss. If a multiplier check fires, the script exits 2 and a human reviews the page before any code change.
A separate Anthropic API key for the price check — the workflow reads secrets.ANTHROPIC_API_KEY_PRICE_CHECK, distinct from the production ANTHROPIC_API_KEY. Cost is trivial (~1 Haiku call per day at ~3K input + ~500 output tokens ≈ $0.005/day = ~$1.80/year), and isolating the key keeps the prod key's blast radius zero if this CI key ever leaks. Rotating the price-check key is operationally independent.

The Haiku prompt template lives at backend/src/llm/prompts/billing/pricing-extract.txt per the project's prompts-as-files convention. It instructs Haiku to extract by display name, ignore the 1-hour cache write rate, and produce the four required rates per model. The script then maps display names back to MODEL_PRICING slugs via the MODEL_DISPLAY_NAMES table (Anthropic's docs page lists models by display name like “Claude Opus 4.7” — not by slug like claude-opus-4-7).

Operating this piece

Bump MODEL_PRICING after a rate change

  1. The LLM price check workflow has reported drift. Read the workflow output: it lists each drifted rate as <slug>.<rate>: ours=X docs=Y delta=Z.
  2. Cross-check against the Anthropic pricing docs by hand. The workflow's Haiku extractor is fallible; a human eyeballs the page before any code change.
  3. Edit backend/src/billing/model-pricing.ts with the new rates. Keep the constant's structure intact (input / output / cacheWrite / cacheRead per model).
  4. Run pnpm --filter backend test src/billing/__tests__/model-pricing.test.ts to confirm the per-rate sanity tests still pass.
  5. Trigger the workflow manually (gh workflow run "LLM price check") to verify the fix passes before merging.

Add a new model to tracking

  1. A new model lands in backend/src/llm/models.ts as a tier constant. Decide which tier (HAIKU / SONNET / OPUS) it replaces or adds to.
  2. In backend/src/billing/model-pricing.ts, add an entry to MODEL_PRICING keyed on the model's slug, with the four published rates from Anthropic's docs page.
  3. Add an entry to MODEL_DISPLAY_NAMES mapping the display name on the docs page (e.g. “Claude Sonnet 4.7”) to the slug. Without this mapping, the daily price check will report the model as “new on docs page (informational)” and skip diffing — the model needs both halves to be tracked.
  4. Run the price check manually (pnpm --filter backend exec tsx scripts/check-pricing.ts, with ANTHROPIC_API_KEY set in the env) and confirm it reports OK.

Recover from a drift false positive

  1. The workflow reports drift but the rate hasn't actually changed. Inspect the workflow log: if the diff is < 1e-6 USD/MTok, the epsilon's working as intended and there's no real drift. If the diff is bigger, the Haiku extractor is hallucinating or the docs page has a new layout.
  2. If the page layout changed, the PAGE_MARKER sanity check ('MTok' string presence) would normally catch it and exit 1. If it passed but the extracted values are wrong, tighten the prompt at backend/src/llm/prompts/billing/pricing-extract.txt with explicit examples of the new layout and re-run the workflow.
  3. Don't suppress the alarm by widening the epsilon. The workflow exists to catch real changes; a wider epsilon hides them. If a single rate is flapping in the 1e-5 range, that's floating-point noise from the docs page's rendering; the right fix is to round MODEL_PRICING to match.

Integration points

The repository layer is where recordUsage / budgetSummary / tryDebitForSession / getDemo / grantInTx / atomicDebit live; the per-method contracts and the credit-ledger story are documented there. The schema page covers the session_usage, credit_ledger, and worlds tables migration 008 modifies. The LLM client emits the event: 'llm.call' log line with token counts; this page's recordUsage is where those tokens become a durable cost record. The billing webhook's subscription and purchase handlers call grantInTx, which means trial-burn fires inside their transactions on the first paid grant. The Session Runtime (next milestone) consumes recordUsage's return value to compute the cost-cap wrap-up signal, calls tryDebitForSession at session-start, and reads consumedSourceType === 'trial' as the trial-mode entry signal.
