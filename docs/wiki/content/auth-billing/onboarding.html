Onboarding & Invites

How a Cognito-signed-in player turns into a Mythrun user row, and how a DM-owner pulls others into their campaign by sharing a 12-character invite code. A request-time gate (requireOnboarded) refuses every protected route until the row exists; a small allowlist of routes opt out so the row can be created in the first place.

How it fits together

Sign-in lands the caller a verified Cognito access token (Identity), which the JWT middleware turns into a claims-only request.user = { sub, cognitoUsername, scopes }. None of those claims is "the user row in our database" — that row is created on the first call to POST /api/users/register, and the player can't get there if every protected route pre-emptively rejects them. Onboarding is the small surface that solves that, plus the invite flow that builds on it.

Two HTTP route groups, one Fastify hook, one repo namespace, and one Haiku-backed classifier:

  • requireOnboarded hook — a Fastify plugin that on every protected request issues a 200 ms-bounded SELECT against users; missing row → 403 { code: 'username_required' }; suspended row → 403 { code: 'account_suspended' }; otherwise the row is attached as a frozen request.dbUser for downstream access-control middleware to read.
  • POST /api/users/register + GET /api/users/check-username — both opt out of the gate via config.auth = 'jwt-no-db', and both are pinned to that opt-out by a boot-time allowlist.
  • GET /api/users/me — the gated read every authenticated client pulls on hydration.
  • Seven invite routes on /api/campaigns/:id/invites/* and /api/invites/:code/* — owner-only create / list / revoke / ensure-primary, public preview, accept, members list.
  • repo.invites — the namespace whose acceptInvite is the load-bearing transaction at the heart of the join flow.
  • classifyProfanity — a single Haiku call against the LLM client that flags both offensive content and impersonation in one round-trip.

The requireOnboarded gate and its allowlist

The plugin lives at backend/src/auth/require-onboarded.ts and is registered in buildApp after the auth dispatcher and the rate-limit plugin, so it sees a populated request.user and runs after the per-route limiter. It installs a preHandler hook that branches three ways: config.auth === 'public' → return; config.auth === 'jwt-no-db' → return; default → look up the row by cognito_sub, refuse a missing row with 403 username_required, refuse a row with non-null suspended_at with 403 account_suspended, and otherwise attach Object.freeze(row) to request.dbUser so downstream handlers and access-control middleware can read it without re-querying.

Suspend enforcement is per-request, not delayed by token TTL — Cognito access tokens have a 1-hour lifetime; without this synchronous check, an admin who suspends a user would have to wait up to an hour for the suspension to bite. The cost is one extra column on the read the gate already does (the users SELECT widens to include suspended_at), and the consumer model becomes simple: any non-401 protected request reaching a handler can trust that request.dbUser is a non-suspended row.
Object.freeze the attached row, not just readonly — TypeScript's readonly is structural-only; nothing at runtime stops a downstream hook from rewriting request.dbUser.id in place. Freezing makes the runtime guarantee match the type. The cost is one syscall per request; the payoff is that the access-control factories can read request.dbUser.id as ground truth without a defensive re-fetch.
Two opt-out values, not one — 'public' means "no auth at all" (skipped by the JWT middleware too, used by /health and the invite preview); 'jwt-no-db' means "validate the JWT and attach claims, but skip the DB-row gate." The two answer different questions. The register route is the textbook 'jwt-no-db' case: the client has a JWT, but the row that the gate looks up is the one this very route is about to create.

The 'jwt-no-db' opt-out is the dangerous one — a route that uses it operates without the DB-row guarantee every other handler can rely on, which means it has to validate the caller's identity and authority by other means. To keep that surface tiny, the plugin enforces a hard-coded allowlist at boot:

  • POST::/api/users/register
  • GET::/api/users/check-username

An onRoute hook collects every route registered with config.auth === 'jwt-no-db'; an onReady hook compares the collected set against the allowlist and throws if any unrecognized entry shows up. app.ready() propagates that throw to the boot sequence, which crashes the process — so a future PR that adds a new 'jwt-no-db' route fails CI on the first test that awaits app.ready(), even before any request is fired.

Boot-time allowlist, not a per-request comment in the route file — a comment is a contract enforced by reviewer attention. The allowlist is enforced by the runtime, audited by one screen of code in one file, and impossible to bypass without editing that file plus passing security review on the PR. The hook's error message points reviewers at exactly that workflow.

The lookup itself goes through repo.users.getByCognitoSubWithTimeout, which wraps the read in BEGIN; SET LOCAL statement_timeout = '200ms'; SELECT … ; COMMIT. SET LOCAL only takes effect inside a transaction, so the BEGIN/COMMIT wrapper is load-bearing even though the read is single-statement. SQLSTATE 57014 (statement_timeout) maps to a LookupTimeoutError the plugin lets bubble — the route layer's default setErrorHandler renders it as 503. Bounding the per-request lookup at 200 ms is what stops a wedged Postgres from pinning every connection in the pool.

POST /api/users/register: the one route that creates the row

The handler validates the request shape (username 3-20 chars matching ^[a-zA-Z0-9](?:[a-zA-Z0-9_]{1,18}[a-zA-Z0-9])?$; displayName 1-40 chars), runs both fields through classifyProfanity, then attempts repo.users.create({ cognitoSub, username, displayName }). The interesting cases are the failure paths.

A unique-violation on users_cognito_sub_key means "this caller already onboarded" — the handler reads the existing row and returns one of two shapes:

  • Same username (case-insensitive) → 200 with the existing row and a Content-Location: /api/users/me header. The caller retried, the DB happened to have the row already; success is idempotent.
  • Different username → 409 with { code: 'already_onboarded', currentUsername, requestedUsername }. The caller can't change their username through register; they have to use the (future) profile-edit surface.

A unique-violation on users_username_lower_key (the case-insensitive expression index from migration 005) means "this username is taken." The handler generates a ${requested}${100..999} suggestion, runs it through classifyProfanity up to 3 times, and returns 409 with { code: 'username_taken', suggestion }. The retry budget exists because Haiku occasionally rejects a digit-suffixed variant as borderline-offensive even when the original passed; three rerolls reaches a clean candidate in nearly every observed case.

Suggestion in the conflict response, not after a follow-up call — a separate "suggest me a name" round-trip would mean the SPA hits the API twice on every collision. Folding the suggestion into the 409 cuts that to one. The shape of the suggestion is intentionally obvious (requested + 3 digits) so users understand what changed and can pick a variant they actually want; the API doesn't try to be clever about plausible alternatives.

GET /api/users/check-username: advisory uniqueness check

Same validation pipeline as register, minus the create. Returns { available: true } or { available: false, reason: 'format' | 'offensive' | 'impersonation' | 'taken' }. The route exists for the SPA's "as-you-type" feedback on the username picker — the user shouldn't have to POST a register attempt to learn that admin is rejected.

Advisory-only — register still has to redo the uniqueness check — between a successful check-username and the matching register call, another player could have claimed the same name. The DB's UNIQUE expression index is the actual authority; check-username is a UX nicety. Treating the check as a reservation would introduce a TTL story (when does a reservation expire?) and a denial surface (squat 100 reservations, lock everyone out) for no real product benefit.

POST /api/invites/:inviteCode/accept: the load-bearing transaction

Of the six invite routes, this is the only one with non-trivial logic — accepting an invite has to handle a small braid of races without leaving any inconsistent state. The handler is a one-liner around repo.invites.acceptInvite; the work happens in the transaction the repo runs:

  1. BEGIN; SET LOCAL transaction_isolation = 'read committed'; SET LOCAL lock_timeout = '500ms'; SET LOCAL statement_timeout = '2000ms';
  2. Lock the invite row. SELECT * FROM campaign_invites WHERE invite_code = $1 FOR NO KEY UPDATE. Missing row → { notFound: true } + ROLLBACK. The lock pins the invite for the rest of the transaction so concurrent accepts can't race the expiry/cap checks against an UPDATE … SET expires_at = now() from a revoke.
  3. Membership check first. If the caller is already in campaign_members for this campaign, the transaction commits immediately with { campaignId, alreadyMember: true }. Membership trumps revoke: a player who is already in a campaign sees the same success regardless of whether the invite they used to find out has since been revoked.
  4. Expiry check, only for non-members. expires_at !== null && expires_at <= now() → { revoked: true } + ROLLBACK. The order matters — checking expiry first would 410 a returning member just because the original invite expired.
  5. Cap check. SELECT count(*) from campaign_members; if the count is at PARTY_SIZE_CAP (6), return { campaignFull: true, activeMembers } + ROLLBACK.
  6. INSERT membership with ON CONFLICT. INSERT … VALUES (…) ON CONFLICT (campaign_id, user_id) DO NOTHING RETURNING *. If the FK trips with SQLSTATE 23503, the campaign was deleted between step 2 and here — return { campaignGone: true }. If the INSERT returns zero rows (a concurrent accept via a different invite just landed the row first), return { campaignId, alreadyMember: true } without bumping uses.
  7. Bump uses — only on the rowCount === 1 branch. The user joined via this invite; uses + 1 is what makes the per-invite analytics meaningful.
  8. COMMIT.
Membership check before expiry check — flipping that order produces a real bug: a player who joined the campaign yesterday and revisits the invite link today gets 410 (revoked) instead of 200 (you're already a member, here's the campaign). The ordering pins the contract: once you're in, you're in, regardless of what the invite did after.
Don't bump uses on the ON-CONFLICT-zero-rows branch — two concurrent accepts of two different invites by the same player race; the first one's INSERT wins. If both incremented uses, the loser's invite would record a use it didn't cause. The rowCount === 1 check makes the bump exactly-once-per-actual-join.

Lock-timeout (SQLSTATE 55P03) and statement-timeout (57014) both map to a single InviteTimeoutError the route layer translates to 503 with Retry-After: 1. The dual timeout — 500 ms on row locks, 2000 ms on the whole transaction — separates "another accept is holding the invite" from "the whole DB is wedged" in the SQLSTATE without changing the caller's view.

The other invite routes (cap=25, owner-only)

POST /api/campaigns/:id/invites always mints a fresh invite — additional share links, the dev-tool. Owner-only, enforced by repo.campaigns.getMembership(campaignId, userId) + role-check (404 if the campaign doesn't exist, 403 if the caller isn't its owner). The repo's create takes a FOR NO KEY UPDATE lock on the campaigns row first (lock-order convention: campaigns → invites → members), counts active invites, refuses with InviteCapReachedError at 25, and otherwise generates a 12-char base62 code with rejection sampling (randomBytes + a b < 248 filter, no modulo bias). Under the campaign lock it also sets the new row's is_primary: a campaign's first active invite is its primary, every additional one is not. Up to 3 retries on a UNIQUE collision against the invite_code column; collisions on a 62^12 keyspace are vanishingly unlikely but the retry loop is cheap and removes one failure mode from the ops surface.

PUT /api/campaigns/:id/invites/primary (myth-y5c4q) is the idempotent get-or-create of the campaign's one primary share link — the durable "share this campaign" URL. Owner-only. The repo's ensurePrimary holds the campaign-row lock, returns the existing is_primary invite if there is one, and otherwise mints a fresh code with is_primary = true. Repeated calls return the same code. This is a distinct sub-resource from POST: PUT upserts the single primary, POST always mints another.

Primary is a real column with a DB-level uniqueness guard, not a derived "first row" (myth-y5c4q) — "primary" used to be computed in the repo (the oldest active invite, listForCampaign's i === 0), and the client's ensurePrimaryInvite was a list-then-create read-modify-write. Two concurrent calls — React StrictMode's dev double-mount, or two owner tabs — both saw no primary and both POSTed, minting two live invite codes on an access-control surface. Migration 036 makes primary first-class: an is_primary boolean plus a partial unique index (… (campaign_id) WHERE is_primary) that lets a campaign hold at most one primary, so a second-primary mint fails with a 23505 at the DB layer even outside the app's campaign-row lock. The client's race collapses to the single idempotent PUT above; the list now reads the column, not a positional guess. The migration backfills the invariant by designating each campaign's oldest active invite as its primary (matching the old derived semantics), and revoke clears is_primary alongside expiry — so an is_primary = true row is never expired, the index predicate needs no now() clause, and revoking a primary frees the slot for a fresh one.

GET /api/campaigns/:id/invites lists active invites for the campaign — owner-only. Each row carries primary straight from the is_primary column (migration 036) so the SPA can highlight the default share link; at most one row is ever primary: true, enforced by the partial unique index above.

DELETE /api/campaigns/:id/invites/:inviteCode revokes an invite by setting expires_at = now() and clearing is_primary in the same update. Returns 204 on success, 404 if the (inviteCode, campaignId) tuple doesn't match (the route is keyed on the invite-code, but the path also carries the campaign-id; mismatch is its own 404 to keep the contract simple). Already-accepted memberships are unaffected — revoke prevents future accepts, never retroactively kicks members. Revoking the primary frees the unique-index slot, so the next PUT …/primary mints a fresh one.

GET /api/invites/:inviteCode/preview is the only invite route configured auth: 'public'. The use case: a friend pastes the invite URL in Discord, the recipient clicks it, the SPA loads at /join/<code> and wants to show "Krestyn the Bold invites you to Storms of Bravelos" before the recipient signs in. The repo query joins campaign_invites → campaigns → users (owner), filters out suspended owners (so a banned DM's invites don't keep working), and returns { campaignName, ownerUsername, ownerDisplayName, valid }. No authentication, rate-limited to 10/min/IP, and no information about the recipient is read or written.

Preview is 'public', not 'jwt-no-db' — preview is the only invite route a not-yet-signed-in user hits, deliberately. The jwt-no-db opt-out would require a JWT (and break the pre-OAuth landing UX); the public opt-out skips both gates. The preview is also not in the JWT_NO_DB_ALLOWLIST — it's a separate axis. Adding a route as auth: 'public' doesn't trip the requireOnboarded boot gate; reviewers should still treat it as security-sensitive on its own merits.

GET /api/campaigns/:id/members returns the member roster — any campaign member, not just the owner. The repo joins campaign_members → users, filters out suspended accounts (banned members don't surface to the rest of the party), and returns { userId, role, username, displayName, characterId, joinedAt } rows. The characterId is always null today; it'll be wired up when the characters namespace ships.

The profanity classifier

backend/src/llm/profanity.ts exports classifyProfanity(text): Promise<ProfanityResult> — a single Haiku call against the LLM client that classifies the input across two rejection categories:

  • { profane: true, reason: 'offensive' } — profanity, slurs, sexual content, hate speech, or explicit references to violence.
  • { profane: true, reason: 'impersonation' } — a system role (admin, support, moderator, root), the Mythrun brand or staff, or a technical identifier (noreply, null, undefined, system).
  • { profane: false } otherwise. reason is omitted on the clean path.

Implementation is ten lines of body: load the system prompt from prompts/auth/profanity.txt, call generateText with output: Output.object({ schema: ProfanitySchema }) against HAIKU, return result.output. The schema is a tiny Zod object the SDK validates on the way back; an unparseable response surfaces as LlmStructuredOutputError at the route layer (502). The call is unconditionally awaited from the route handler before any database work, and runs outside any open transaction so the 200-800 ms LLM latency doesn't pin a connection.

One Haiku call, no static fallback list — the previous MYT-38 stub kept a small reserved-username set and a substring-matched LDNOOBW seed list. Both were ZFC-violating heuristics — pattern-matching delegated to local code instead of to the model. The single Haiku call covers both rejection categories in one round-trip; the prompt instructs the model to prefer 'offensive' when both categories apply. Cost is trivial (~50 input + ~10 output tokens, ~$0.0001 per registration at Haiku pricing); 10K registrations/month is ~$1.
Reason vocabulary changed alongside the rewire — the old enum ('reserved' | 'profane') named the static-list mechanism. The new enum ('offensive' | 'impersonation') names the conceptual category the model decided on. This is a breaking change for any consumer that branches on the value, but only the route layer reads it today, and routes were updated in lock-step.

The function is gated behind the LLM client's ANTHROPIC_API_KEY env var; integration tests vi.mock('../llm/profanity.js') to avoid hitting the live API.

Rate limits per route

Rate limits live as per-route config.rateLimit entries against @fastify/rate-limit (registered with global: false, so global is off and routes opt in). The store is Redis-backed (the redisRealtime client) so per-route caps apply fleet-wide across ECS tasks, not per-task — at N running tasks a 10/min/IP cap would otherwise become 10·N/min/IP effective. The current shape:

  • POST /api/users/register — 5/min, keyed on request.user.sub (not IP). Registration is once-per-user; a higher rate is a typo storm or a bot, and one user trying many candidate usernames from one IP is the threat the per-sub key bounds.
  • GET /api/users/check-username — 10/min. As-you-type checks but not per-keystroke — the SPA debounces.
  • Invite create / list / revoke — 30/min. Owner-side admin operations.
  • GET /api/invites/:code/preview — 10/min/IP. Public route.
  • POST /api/invites/:code/accept — 30/min, keyed on request.user.sub (not IP), so a player on a shared NAT isn't penalised for someone else's retries.
  • GET /api/campaigns/:id/members — 60/min.
Per-cognito-sub key for accept, IP key for the rest — accept is the route most likely to fire from a polled retry-loop on the SPA (the user clicks "Join"; the SPA POSTs; network hiccups; SPA retries). Keying on request.user.sub bounds one player's storm without colliding into other players sharing their IP. The IP-keyed routes are either pre-auth (preview) or bursty enough that per-user keying gives no real signal (a busy DM rotating invites).

The store is Redis-backed (per MYT-45) so the limits hold across the ECS service's task replicas instead of per-task. See the rate-limit list above for the per-route shape and the per-sub override on register.

FRONTEND_BASE_URL and the host allowlist

Invite-create responses include inviteUrl: ${frontendBaseUrl}/join/${inviteCode} so the SPA can render a copy-able link without re-implementing the URL shape. The base URL is loaded from the FRONTEND_BASE_URL env var, validated by config/env.ts against an explicit host allowlist:

  • Production allows mythrun.com and staging.mythrun.com.
  • Development and test additionally allow localhost and 127.0.0.1 (any port).
  • The pathname must be /; query string and hash fragment must be empty.
  • The validator returns url.origin — the canonical scheme://host[:port] form — so handlers concatenate paths against a stable shape.
Allowlist + path-must-be-/ closes an open-redirect surface — the base URL drives OAuth redirect targets and invite-link composition; a permissive value (or an attacker-controlled override) would let a misrouted redirect carry tokens off-origin. Allowing any host is one bad ECS task-def env entry away from a credential-leak; pinning the host set and forbidding path/query/hash means a typo can't accidentally pin redirects to a sub-route.

Operating this piece

Add a new jwt-no-db route

  1. Add the route under backend/src/routes/ with { config: { auth: 'jwt-no-db', rateLimit: { … } } }. Validate the request shape by hand (no DB-row guarantee).
  2. Add the route's METHOD::URL string to JWT_NO_DB_ALLOWLIST in backend/src/auth/require-onboarded.ts. URL normalization strips trailing slashes; method is uppercased.
  3. Tag the PR for security review. The reviewer's checklist: does the handler pre-onboarding state safely? Does it write any row that requires a real users.id? Does its failure surface leak whether the caller is already onboarded?
  4. Run pnpm test --filter @mythrun/backend. The require-onboarded.test.ts suite asserts the boot crash on an unrecognized jwt-no-db route — adding the route without updating the allowlist will fail that test.

Diagnose an invite-accept failure

  1. The HTTP status maps to one of: 404 (invite_not_found), 410 (invite_revoked | campaign_gone), 409 (campaign_full), 503 (invite_timeout). Anything else is unexpected and worth a 500-spike alert.
  2. For 503 spikes, check CloudWatch for InviteTimeoutError and read the cause field. cause: 'lock' + sqlstate 55P03 means a different accept (or a revoke) is holding the row past the 500 ms lock-timeout — a sustained rate suggests a live contention pattern. cause: 'statement' + sqlstate 57014 means the whole transaction blew the 2 s budget — usually pg-side; cross against pg metrics.
  3. For 409 spikes, the campaign hit the 6-player cap (or the cap was lowered post-launch). There is no admin override yet; growing the cap is a follow-up bead.
  4. Recovery — invites are stateless from the API's side. Revoke + re-create produces a fresh code. Existing accepted memberships are independent of any individual invite row.

Reset a stuck username during onboarding

  1. A player who 409'd on username_taken and abandoned the flow has nothing to clean up — no row was created.
  2. A player who 409'd on already_onboarded already has a row pinned at a different username and hits this every time they retry. Username changes via the register endpoint are intentionally refused; the player should use the (future) profile-edit surface, or you can manually rewrite users.username via psql in dev/staging if there's no self-service path yet.
  3. The case-insensitive UNIQUE on LOWER(username) is enforced at the DB; you can't rename to a casing-variant of an existing taken name.

Integration points

Upstream: Identity mints the access tokens this surface consumes; the JWT middleware attaches request.user the gate then reads. Downstream: repository layer's users, invites, and campaigns namespaces are the only DB seam this surface touches — users.create, users.getByCognitoSubWithTimeout, users.getByUsername, invites.acceptInvite, campaigns.addMember / getMembership / listMembers. The same campaigns namespace also exposes listConfirmedMembersWithoutCharacter — the predicate the session-start guard uses to refuse a start while any confirmed member still lacks a character; the acceptance flow here is what makes a member "confirmed" (invite_accepted) in the first place. The schema's migration 005 establishes the minimal-claims user shape and the case-insensitive username index this layer relies on; migration 036 adds the is_primary invite column and its partial unique index. The backend runtime page describes the buildApp wiring that registers requireOnboarded, the rate-limit plugin, and these route groups in order. The LLM client page describes the wrapper layer classifyProfanity sits on. Future work: MYT-45 swaps rate-limit storage to Redis; the SPA's first-login screen and invite-landing page consume these endpoints.
