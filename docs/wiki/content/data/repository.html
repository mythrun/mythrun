Repository layer

The single seam every read and write to Postgres flows through. A closure-based factory returns one namespace object per table cluster; callers say repo.users.create(...), never pool.query(...) directly.

How it fits together

createRepo(pool) in backend/src/repo/index.ts is the entry point. It takes a pg.Pool and returns { users, worlds, campaigns, sessions, credits, invites } — one namespace per top-level table cluster. Each namespace is built by a sibling factory (createUsersRepo(pool), createWorldsRepo(pool), …) that closes over the pool and exposes the typed methods for that table. The return type is exported as type Repo; the backend runtime's AppDeps carries it alongside pg, the two Redis clients, and the derived redisKeyPrefix (${MYTHRUN_ENV}:${REGION_PREFIX}:) every Redis-keyed subsystem prepends to its keys; server.ts threads createRepo(pgRef) into buildApp on both boot paths. A second class of namespaces — the four billing-table modules (stripeEvents, purchases, userSubscriptions, billingHistory) — exports plain object literals whose methods take a ClientLike the caller has already opened. Those namespaces don't bind to a pool; they operate inside a transaction the webhook dispatcher already owns.

ClientLike, not Pool, on the billing namespaces — the webhook dispatcher opens one transaction per event and runs every handler's writes inside it. If the billing namespaces took a Pool like the original six do, they'd open their own connection per query and write outside the dispatcher's tx — which would defeat both the idempotency guarantee (the stripe_events insert wouldn't be in the same transaction as the handler's writes) and the timeout discipline (the dispatcher's SET LOCALs wouldn't apply). ClientLike is the structural subset of pg.PoolClient the namespaces actually use; the dispatcher passes its own client in.
Closure factory, not a class — namespaces are bags of pure functions over a shared pool. A class adds this binding hazards (a route handler that destructures const { create } = repo.users and calls create(input) would lose this) and gives nothing back: there's no inheritance story, no protected state, no per-instance overrides. A closure is the smaller shape that solves the same problem.

The CLAUDE.md mandate is concrete: every TS file outside backend/src/repo/ that reads or writes the database calls repo.<namespace>.<method>. No raw pool.query(...) in route handlers, services, or workers. The repo layer is what makes that mandate enforceable — there's one place to grep for SQL changes, one place where parameter binding is audited, one place where the updated_at = now() bump is guaranteed on every UPDATE.

Namespace boundaries: 10 today, 15 deferred

Spec §5 of the Backend Core architecture lists 25 namespaces. This layer ships ten: six pool-bound namespaces (users, worlds, campaigns, sessions, credits, invites) plus four transaction-scoped billing namespaces (stripeEvents, purchases, userSubscriptions, billingHistory) the webhook handlers and billing routes consume. The remaining 15 are tracked as beads under the repo-deferred label and ship batched with their consumers.

Producer batched with consumer — designing a characters namespace with per-skill / feature / equipment / spell add APIs without the character-creation flow designed produces guesses. credits shipped on the same principle: the atomic-debit pattern was held back from the v1 repo until MYT-40 picked up Billing's first consumer-facing surface, because designing grant / debit / getBalance as separate primitives without the spend path in mind is exactly how a TOCTOU race ships. invites followed in MYT-38 alongside its routes consumer; the multi-step acceptInvite transaction (lock invite → membership check first → expiry check → cap check → INSERT with ON CONFLICT → uses-bump) only fell into shape with the HTTP layer co-designed. The deferral list is in the v2 design spec; bd list --label=repo-deferred is the live view.

Within the four shipped namespaces, the method set is similarly scope-cut. worlds.fork is deferred to the prep pipeline — fork semantics involve entity copy and fact deduplication that belong with the pipeline that owns them. sessions.updateRunningSummary is deferred to the Slow Thinker work that consumes it. users.softDelete and campaigns.transferOwnership follow the same rule: no consumer in flight, no API design today.

Camel out, snake in: mappers at the boundary

The schema is snake_case (cognito_sub, created_by, geography_summary); the TypeScript surface is camelCase. Each table has two interfaces: a XxxDbRow in mappers.ts matching what pool.query returns, and a Xxx in types.ts that callers see. A toXxx function bridges them — invoked once per row at the repo boundary.

Explicit mappers, not a pg-types parser — node-postgres lets you register a type parser that rewrites every result row globally. Tempting, but global: it would convert keys for every query in the process, including future code paths that genuinely want raw pool.query for diagnostics or one-off scripts. Keeping the conversion at the repo boundary scopes it to where the API contract is camelCase and leaves the rest of the system alone.

Update input types are spelled out (not Partial<Pick<User, …>>) so exactOptionalPropertyTypes semantics are intentional: each key is omitted to leave the field unchanged, or supplied with a value to set it. The identity field cognitoSub is never in the Update type — mutating it would break Cognito linkage in ways the layer above doesn't want to think about. username and displayName are mutable through Update because the user owns them; the schema catches case-insensitive collisions via users_username_lower_key if a rename conflicts.

Narrowing helpers for enum-like CHECK columns

Several columns in the schema are TEXT with CHECK constraints enforcing a small enum: worlds.status, worlds.moderation_status, campaigns.status, sessions.status, credit_ledger.credit_type, credit_ledger.source_type, campaign_members.role. The schema guarantees the SQL invariant, but the mapper still refuses to bare-cast row.status as 'generating' | 'complete' | 'failed'. Instead, a small helper validates and narrows: 

function toCampaignMemberRole(v: string): 'owner' | 'player' {
  if (v !== 'owner' && v !== 'player') {
    throw new Error(`unexpected campaign_members.role value from DB: ${v}`)
  }
  return v
}
Defense in depth, not paranoia — if a future migration adds a new role option but the TS interface stays at 'owner' | 'player', a bare cast would silently mistype every row. The helper fails loudly at the boundary and the test suite or production logs flag it before the bug spreads. Every CHECK-constrained text column gets one of these.

UUIDv7 in its own seam

backend/src/repo/uuidv7.ts is a one-line wrapper: export const uuidv7 = (): string => uuidv7Pkg(). Every create method generates the id app-side via this function — id UUID PRIMARY KEY in the schema declares no default. Time-ordered ids give clean B-tree locality on PK indexes, which matters for the high-write-rate tables (session_messages, credit_ledger) the future namespaces will land.

The wrapper exists so tests that need deterministic ids can vi.mock('./uuidv7.js'), and so a future swap to a different UUIDv7 library is a one-file change. The migration runner's CLI block uses the same wrapper for its runId — single seam, no second import path of the underlying package.

INSERT … RETURNING *: one round-trip, callers get the row

The Backend Core spec example shows create returning Promise<string> (the new id). The repo deviates: every create uses INSERT ... RETURNING * and returns the full mapped row.

RETURNING *, not just the id — every consumer the next handful of tickets will add (signup flow, prep-pipeline kickoff, session start) immediately needs the created_at, the defaulted status, the database-side now() for updated_at. Returning only the id forces a refetch round-trip. Returning the full row costs marginal extra bandwidth and matches what callers want.

UPDATE … COALESCE($n, col): fixed-form patches

Update methods take a partial patch and emit a single fixed SQL string. Each mutable column is written as col = COALESCE($n, col) — the parameter is either the new value or null, and null means "don't change this field." updated_at is always set to now() in the same statement. 

UPDATE users
   SET username           = COALESCE($2, username),
       display_name       = COALESCE($3, display_name),
       stripe_customer_id = COALESCE($4, stripe_customer_id),
       free_trial_used    = COALESCE($5, free_trial_used),
       updated_at         = now()
 WHERE id = $1
 RETURNING *
Fixed COALESCE, not dynamic SQL — building a SQL string at runtime by walking the patch object's keys is the alternative; it gives "only update what was supplied" without COALESCE's NULL-as-sentinel weirdness. The cost is real: every dynamic builder is an injection surface to audit, an unstable EXPLAIN plan to debug, and a typing puzzle (TypeScript can't tell what columns are in patch). The fixed form has one stable plan, parameterized binding for free, and the column whitelist is in the SQL itself.
Mandatory updated_at = now() on every UPDATE — the schema declares updated_at TIMESTAMPTZ NOT NULL DEFAULT now() but has no BEFORE UPDATE trigger. Forgetting the bump leaves the column stuck at insert time forever, silently breaking any "what changed since" query downstream. Each namespace's integration test asserts updated_at advances after update; the sessions table is the lone exception (no updated_at column, only started_at + ended_at).
COALESCE caveat: nullable fields can't be cleared — passing { stripeCustomerId: null } to users.update is indistinguishable from omitting the key entirely; both encode as a SQL null parameter and the COALESCE leaves the column unchanged. This is a deliberate v1 trade-off, documented at the type site. When a real consumer needs to clear a stripe id (a customer-record reset, a refund-flow rebuild), the API grows a sentinel value or a dedicated clearStripeCustomerId() method — not before.

The boot gate's stub pool, composed

The boot gate has two paths. With BOOT_GATE_ENABLED=1, server.ts opens a real pool and calls createRepo(pgRef). With the gate off, fallbackStart constructs a stub pool whose query throws synchronously — and then calls createRepo(stubPool) over it. Any repo method invoked on that stub repo propagates the throw naturally, the same way it would for any other unreachable database.

Compose over the stub pool, don't Proxy the namespace layer — an earlier design used a Proxy to fake the entire { users, worlds, … } shape with throwing methods. The bug: repo.users.create() would throw on repo.users (a function-shaped Proxy trap), not on create(), and the error message would say "namespace not available" instead of "repo unavailable: BOOT_GATE_ENABLED is off." Composing createRepo over the stub pool inherits the pool's existing throw contract; no special-casing in the repo factory.

Per-namespace shape

users — create, getById, getByCognitoSub, getByCognitoSubWithTimeout, getByUsername, update; plus the standalone findOrCreateStripeCustomer(pool, stripe, userId) helper exported alongside the closure. Each getByX maps 1:1 to a column with an index that supports it (or, for getByUsername, the users_username_lower_key expression index); adding a method is the deliberate act of sanctioning a new lookup path. A generic getBy(filter) would silently accept filters with no supporting index — a sequential-scan trap that wouldn't surface until production load — and would force readers to inspect every call site to learn which lookup shape was used. We accept the small cost of "several methods instead of one" to get index-as-API-surface and exact searchability.

findOrCreateStripeCustomer is a three-phase prefetch-then-write — the helper has to call Stripe's customers.create with an idempotency key, and that SDK call cannot run inside a held DB transaction (a Stripe outage would pin the PoolClient). Phase 1 reads the existing stripe_customer_id in a short tx; if populated, return immediately. Phase 2 calls Stripe outside any tx, deterministic idempotency-key (customer_for_${userId}) so concurrent racers all hit the same Stripe-side record. Phase 3 opens a short tx with the MYT-40 timeout discipline, re-reads the row FOR UPDATE, and either uses a racer's value (the cus_* we just minted becomes a Stripe-side orphan) or writes our own. The helper is exported as a function rather than as a method on the closure so the billing routes can call it without going through the closure's pool-binding.
getByCognitoSubWithTimeout wraps the read in a transaction — the requireOnboarded hook calls this on every protected request to confirm a real users row exists for the caller's cognitoSub. A wedged Postgres would otherwise pin the request thread until pg's default statement_timeout fires (or never, if it isn't set). The method opens a dedicated client, runs BEGIN; SET LOCAL statement_timeout = '200ms'; + the SELECT, commits, and releases — bounding any single lookup to the configured budget. SET LOCAL only takes effect inside a transaction, so the BEGIN/COMMIT wrapper isn't optional even though the read itself is single-statement. SQLSTATE 57014 (statement_timeout) maps to a LookupTimeoutError the route layer translates to a 503.

getByUsername uses WHERE LOWER(username) = LOWER($1) so the users_username_lower_key expression index serves the lookup directly — case-folding on both sides keeps the planner from falling to a sequential scan. The case-insensitive uniqueness story is in the schema page's identity-cluster section; the repo simply consumes that invariant.

worlds — create, getById, listByUser, update, updateStatus, incrementForkCount. updateStatus is a one-purpose UPDATE on status alone; the prep pipeline calls it many times per run, and a dedicated method keeps pipeline tracing legible. listByUser is the simple ownership filter WHERE created_by = $1 ORDER BY created_at DESC — no JOIN.

campaigns — create, getById, listByUser, update, plus four membership methods: addMember, getMembership, getOwner, listMembers. listByUser joins campaign_members directly in SQL to filter to "campaigns I'm a member of with an accepted invite." addMember uses INSERT … ON CONFLICT (campaign_id, user_id) DO NOTHING RETURNING * so a re-add is idempotent — when the conflict swallows the row, the method falls through to a follow-up SELECT and returns the existing membership. listMembers joins users for username + display_name and filters out suspended accounts so a banned member doesn't surface in another player's roster.

Membership methods on campaigns, not their own namespace — the v2 namespace plan reserved a campaign_members namespace, but membership is read and written exclusively in service of campaign-scoped operations (owner check, member list, invite acceptance). A separate namespace would force every consumer to import two factories and reason about ordering between them. Keeping the methods on campaigns matches how callers think — "what's true about this campaign" — and lets the lock-order convention (campaigns → invites → members) sit naturally inside one factory's transactions.

sessions — create, getById, getActiveByCampaign, listByCampaign, update. getActiveByCampaign uses LIMIT 1 defensively — the partial-unique index idx_sessions_one_active guarantees at most one active row per campaign, but the LIMIT 1 at the SQL site makes the contract self-documenting.

sessions.update doesn't bump updated_at — the sessions table doesn't have an updated_at column at all (only started_at + ended_at, which carry the lifecycle a session row needs). The "every UPDATE bumps updated_at" rule applies wherever the column exists; this one is the documented exception.

credits — balance, grant, atomicDebit, listEntries. The full credit-ledger story has its own section below; the short version is "balance is a SUM over an append-only ledger; debits go through a transaction-scoped lock anchored on the user row, not on the ledger."

invites — create, getByCode, getCodePreview, listForCampaign, revoke, acceptInvite. Invites are how new players join a campaign in MYT-38's onboarding flow; getCodePreview is the only read this layer exposes to unauthenticated callers (the public preview the SPA shows on the join page before the user signs in). The rest are authenticated. The non-trivial method is acceptInvite — its own section below.

The credits namespace: append-only ledger with an atomic spend

credit_ledger is the only place credit balance lives — the schema page covers the table shape and migration 004's defense-in-depth invariants. The repo surface the rest of the system sees is four pool-bound methods plus two transaction-bound helpers (grantInTx + recordClawback) exported as standalone functions.

balance(userId, type) is a single read: SELECT COALESCE(SUM(amount), 0) filtered by user_id, credit_type, and expires_at IS NULL OR expires_at > now(). Expired grants drop out; debits stay in (they're immutable consumption). Two credit types live on the same table — session and world_gen — and they're isolated: a session debit never sees world-gen grants.

grant(input) writes a positive-amount entry with source_type in purchase | subscription | gift | trial | refund; the closure-bound version opens its own short tx with the user-row lock. atomicDebit(input) writes a negative-amount entry with source_type = 'debit'; the amount is a positive integer in the input, recorded as -amount in the row so polarity invariants hold at the DB layer. Both methods take the per-user transaction lock described next.

grantInTx + recordClawback are standalone exports for webhook handlers — the closure's grant opens its own connection and tx, which is the right shape for one-off grants from route handlers (a manual gift) but the wrong shape for the webhook dispatcher's already-open tx. The standalone grantInTx(tx, input) takes a ClientLike and runs only the INSERT (still re-acquires the user-row lock — Postgres allows tuple-lock re-entrancy on the same xid). recordClawback(tx, input) is its negative-amount sibling for refund events: writes source_type = 'refund' with a negative amount and an FK to the originating billing_history row. Both let the webhook handlers compose one transaction across the stripe_events idempotency check, the audit row write, and the credit grant — a single COMMIT covers all three.
Lock the users row, not the ledger — the natural-feeling design is SELECT … FROM credit_ledger … FOR UPDATE, then read the balance, then INSERT. It doesn't work: PostgreSQL row locks are physical, not predicate. FOR UPDATE on a query that returns zero rows locks zero tuples, so two concurrent debits on a fresh user both see balance = 0 and both succeed. The fix is anchoring on a row that always exists — SELECT id FROM users WHERE id = $1 FOR UPDATE — which serializes every concurrent atomicDebit and grant for that user. The first transaction takes the lock, reads the balance, inserts the debit, commits; the second one waits, then sees the new balance. grant takes the same lock for symmetry: any operation that could decrease available balance (today: atomicDebit; future: refund clawbacks) goes through the same gate.

Each transaction starts with three SET LOCALs: transaction_isolation = 'read committed' (defense in depth — the pool default already provides this; the SET LOCAL makes it per-transaction explicit so a future pool-config drift can't silently change the contract); lock_timeout = 1s (cap on how long the FOR UPDATE waits before giving up — bounds pool exhaustion under load); and statement_timeout = 5s (cap on the whole transaction, the second of two distinct failure modes). Both timeouts surface as the same error subclass to callers; the SQLSTATE distinguishes them in logs.

atomicDebit requires a sourceId — the per-user idempotency key. The method does the idempotency check first, before the balance check: a retry of the same (userId, creditType, sourceId) returns the prior entry without inserting a second row. A different amount with the same key throws IdempotencyConflictError; the same amount returns the original. The DB-level uniq_credit_ledger_debit_idempotency partial-unique index from migration 004 is the safety net for any future caller that bypasses the repo.

Don't gate on balance(); atomicDebit IS the gate — the tempting consumer pattern is "check balance, decide whether to act, then debit." That's a TOCTOU race regardless of how the lock is implemented: the balance read and the spend decision happen outside any transaction. The repo's contract is that atomicDebit either succeeds and returns the new entry, or throws InsufficientCreditsError with the actual available balance — callers branch on the result, not on a prior balance() call. The error class is exported from credits-errors.ts for HTTP-layer mapping.

Errors callers narrow on: InsufficientCreditsError (balance check failed — available + requested in the error), IdempotencyConflictError (same sourceId, different amount), UserNotFoundError (the user-row anchor came up empty — the spec's required invariant before any other check), and DebitTimeoutError (lock or statement timeout fired — sqlstate 55P03 or 57014 mapped to one error class). Every error path ROLLBACKs the transaction explicitly so connections never leak in idle in transaction state; the integration test asserts this on every error class.

listEntries(userId, opts) is the audit view — DESC by (granted_at, id), default limit 100 (overridable; null means no LIMIT). It includes expired entries, unlike balance(), because the audit story is "what happened to this user's credits over time," not "what can they spend right now."

The four billing namespaces: transaction-scoped, no pool binding

stripeEvents, purchases, userSubscriptions, and billingHistory are exported as plain object literals, not closure-built factories. Their methods take a ClientLike as the first argument: the webhook dispatcher opens one transaction per event and threads its PoolClient through every handler call inside it. Two of them (userSubscriptions and billingHistory) are also called from the pool-bound billing routes; for that consumer the route passes a Pool directly (Pool's query shape is a structural superset of PoolClient's, so the same method signature works for both).

stripeEvents exposes one method: recordOrSkip(tx, event_id, event_type) runs an INSERT ... ON CONFLICT (event_id) DO NOTHING RETURNING event_id and returns either 'inserted' or 'duplicate'. The dispatcher branches on the result: 'duplicate' means the event was already processed and the rest of the tx is skipped.

purchases exposes insertMany, getByPaymentIntent, and markRefunded. insertMany runs a single multi-row INSERT for à-la-carte cart lines, using the composite (stripe_payment_intent_id, lookup_key) UNIQUE for idempotency — a redelivered checkout.session.completed for the same payment intent is a no-op. markRefunded flips status='refunded' on a row the refund handler has resolved.

userSubscriptions exposes upsertFromStripe, markCanceled, and getActiveForUser. The first is the load-bearing method: a single INSERT ... ON CONFLICT (stripe_subscription_id) DO UPDATE with a strict WHERE excluded.stripe_event_created_at > user_subscriptions.stripe_event_created_at filter rejects same-second or earlier deliveries as no-ops. Combined with stripe_events idempotency, this absorbs both Stripe's at-least-once delivery and Stripe's no-guaranteed-ordering across event types.

Strict > on the stale-event filter, not >= — Stripe doesn't guarantee event-ordering by created timestamp at second precision. Two events for the same subscription can carry the same created second; the second one to arrive could be the one that fires first on a multi-worker setup. >= would let the second-arriving same-second event overwrite the first; > rejects it as a no-op. The checkout.session.completed + customer.subscription.created race is the textbook example: both fire within the same second on a fresh checkout.

billingHistory exposes append, find, listByUser, and markRefunded. append uses the composite (kind, source_id_stripe) UNIQUE with ON CONFLICT DO NOTHING + follow-up SELECT so a redelivered event is a no-op. listByUser is the cursor-paginated query backing GET /api/billing/history; the cursor is a (occurred_at, id) pair so two events at the same second don't drop a row at the page boundary.

(timestamp, id) cursor, not offset pagination — Stripe events arrive near-real-time and the audit feed grows append-only. Offset pagination drifts on every new row written between page fetches. A (occurred_at, id) cursor is stable; the row id breaks ties when two events share the same Stripe second-precision timestamp.

Tests: real Postgres, TRUNCATE-based reset

Each namespace has an integration test under backend/src/repo/__tests__/<ns>.test.ts that runs against a real Postgres (the docker-compose stack locally, the CI Postgres service in CI). beforeAll runs all migrations once; beforeEach calls a helper that TRUNCATE … RESTART IDENTITY CASCADEs every application table in dependency order. The schema stays intact across tests; only data is reset, which is roughly 50× faster than re-running migrations between every test.

mappers.test.ts is a pure unit test over the mapper functions and the narrowing helpers — hand-constructed XxxDbRow objects, no DB. Schema-parity invariants (table names, CHECK constraints, FK rules) live in the schema-parity test from MYT-33; the repo tests trust that and exercise behavior, not structure.

credits.test.ts adds two test groups beyond the per-namespace shape: a schema-invariants block that asserts each migration-004 CHECK rejects the row it's supposed to (and includes an EXPLAIN assertion that the idempotency SELECT uses the partial-unique index, not a sequential scan), and a concurrency block run against a separate small pool that exercises parallel debits. The race tests cover the empty-ledger case (the bug the user-row lock fixes), the exactly-one-succeeds case, the parallel-same-sourceId idempotency case, the lock-timeout case, and a "every error path issues ROLLBACK" sweep that catches idle-in-transaction leaks.

Integration points

The migrations runner shares the uuidv7() wrapper — both the CLI's runId and every repo create read from backend/src/repo/uuidv7.ts. The backend runtime's AppDeps carries the repo alongside pg; the billing routes and the onboarding routes consume it as the seam for all data access. The four billing namespaces are also imported directly by the webhook handlers (transaction-scoped consumers don't need a pool binding). The schema is what the repo's queries are typed against — every XxxDbRow matches a table the migration files define.
